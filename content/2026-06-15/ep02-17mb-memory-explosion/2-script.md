## 钩子（前 3 秒 · 冷开，不依赖上下文）
Claude Code 查个版本号，凭什么吃掉你 1 个 G 内存？
你敲一句 `claude --version`，就想看一行版本号。
结果电脑内存「唰」地飙到 966 兆，差不多 1 个 G。
就为打印一行字——Anthropic 自己的工程师也懵了。

## 案发
更邪门的是：同样这个文件，换 Node 来跑，内存只要两百兆出头。
一份产物，两种跑法，内存差了好几倍。
说明问题不在代码写得烂，在**跑它的那个引擎**。
> 视觉：内存条动画——一个 17MB 大方块塞进引擎，内存条瞬间拉满变红。

## 排查
第一反应肯定是内存泄漏，或者依赖装太多。
都不是。打包出来的 CLI，是**一个 17MB 的单文件 JS**。
泄漏会越跑越涨，它是一启动就爆——那就不是漏，是**一次性吃太多**。

## 真凶
真凶是两个引擎「性格」不一样。
Claude Code 用 Bun，底层是 JavaScriptCore 引擎；Node 用的是 V8。
JSC 拿到文件，会把整个 17MB **全量解析**成字节码、还顺手 JIT 编译一遍——一口气全嚼碎。
V8 是**懒解析**：用到哪段才解析哪段，没碰到的先放着。
> 视觉：自助餐比喻——JSC 是上来把整桌菜全吃光（撑爆），V8 是饿了才去拿一盘。
17MB 一次性全解析，内存自然就上去了。

## 破案
那思路就清楚了：不用换引擎，**把一个大文件切小**。
构建时打开代码分割，一个 17MB 的大块，拆成 **600 多个小 chunk**。
JSC 这下不用全嚼了，按需加载——`--version` 用到哪几块就解析哪几块。
结果：`--version` 的内存从 966 兆**降到 35 兆**，差不多 **27 倍**。
连完整加载也从 1 个 G 多降到五百兆左右。
> 视觉：数字对比大字报 966MB → 35MB，红条缩成一格绿条；旁边标「÷27」。

## 彩蛋（兼容性手术）
切完还有个坑。Bun 有个专属写法 `import.meta.require`，Node 不认。
所以构建完还要做一道「手术」：扫一遍产物，把这种 Bun 专属写法，自动替换成 Node 也能跑的兼容版本。
这样**同一份产物，Bun 和 Node 都能跑**。工程上这才算闭环。

## 结尾钩 + 互动
所以你看，有时候性能问题不在你的业务代码，在**底下那层你没注意的引擎**。
省内存只是开始——下一集，讲它怎么帮你省**真金白银的 token 钱**。
互动留个问题：你项目打包出来的产物多大？**超过 5MB 的，评论区报个数。**
