- **正文/简介**：做 AI 应用的都知道 prompt 缓存能省一大笔钱，命中缓存那部分输入 token 的价钱直接打到一折，可它说崩就崩、崩了你还经常不知道为什么。Claude Code 干脆给缓存装了个黑匣子：缓存的命中规则很死，请求前缀得跟上次一字节都不差，系统提示、工具定义、模型、一个开关变一点缓存就全废。一个真实请求里藏着几十个工具、十几个 beta 开关、推理强度、缓存策略，排查像大海捞针。它的思路很朴素：每次发请求前，把所有可能搞崩缓存的因素逐项拍一张哈希快照——系统提示一个哈希、模型一个、beta 列表一个、缓存控制单独一个（专门抓范围或有效期偷偷翻转），最关键的是工具不揉成一个哈希，而是每个工具的 schema 单独算、单独存。下次请求回来逐项比对，哪项变了哪项就是嫌疑人，再拼成人话比如"工具变了多两个少零个"。为什么工具非要拆到逐个？因为最阴的崩法是工具一个没多没少、但某个工具的描述悄悄改了——源码注释写得很直白，这种"工具集没变 schema 变了"占了工具类缓存崩的百分之七十七。它还有阈值：缓存命中 token 掉超过百分之五、且绝对值至少掉两千个才算真崩，小波动忽略免得误报。确认崩了就用 diff 把崩前崩后的完整 prompt 状态做成补丁文件写进日志，开 debug 逐字看，等于一份缓存的验尸报告。最让我服的是它的诚实：要是客户端啥都没变、也没超过缓存有效期，源码注释说这种约九成是服务端的路由或驱逐，它不甩锅给你、直接标注"大概率服务端"。所以这套黑匣子不只抓你的 bug，也能洗清你的代码。做 AI 应用的朋友，把缓存命中率做成你系统的监控指标，崩了能定位比闷头烧钱强太多。每句结论都可溯源到源码，系列每天更一期。
