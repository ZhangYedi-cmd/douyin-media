# 第 10 课大纲：架构抉择：AI 时代 CLI 为什么比 MCP 更好用？

## 1. 课程定位与痛点
- **目标受众**：盲目追逐新协议概念、把所有功能不加区分全部写成 MCP Server，导致 AI 上下文瞬间被撑爆、模型经常调用错工具的开发者与架构师。
- **核心痛点**：缺乏工具协议与工程架构选型的底层认知；不明白 MCP 的上下文成本机制；不知道为什么在生产环境中传统命令行（CLI）反而比 MCP 更加稳定可靠。
- **课时建议**：深度技术架构与架构师心法课，篇幅随内容讲透自然展开，重点把上下文经济学（Context Economics）、懒加载机制与工具选型矩阵讲透。

## 2. 课程目标
- 深入对比 MCP（Model Context Protocol）与 CLI（Command Line Interface）的底层运行机制。
- 深刻理解上下文经济学：静态 JSONSchema 全量常驻 vs 命令行懒加载（Lazy Tool Discovery）。
- 深刻理解为什么确定性业务逻辑与状态写操作应该全面收敛到 CLI。
- 掌握在 AI Agentic 系统中何时选用 MCP、何时选用 CLI 的精准决策模型。

## 3. 核心思路与私教心法
- **Token 就是金钱与智商**：把几千行的 MCP 工具定义塞进 System Prompt，不仅消耗 Token，更会严重稀释模型的注意力（Attention）。
- **CLI 是人类、脚本与 AI 的最大公约数**：CLI 可以在终端手动单测，可以在 CI/CD 跑，可以在子进程跑，AI 只需要通过 `--help` 就能自学使用。

## 4. 详细内容大纲（标注篇幅与重点分配）

### 一级标题 1：[★ 核心重点 · WHAT & WHY · 大篇幅讲透] 当红炸子鸡 MCP 的美好愿景与现实困境
- 二级标题 1.1：[★ 核心重点 · WHAT · 协议初衷] 什么是 MCP？它解决了什么？
  - **WHAT 协议定位**：由 Anthropic 主导的标准协议，旨在统一跨应用、跨 SaaS 的数据连接标准。
- 二级标题 1.2：[★ 核心重点 · WHY · 隐藏代价剖析] MCP 的暗面：上下文经济学危机
  - **WHY 为什么会撑爆上下文**：MCP 在客户端启动时，会将所有注册工具的完整 JSONSchema 参数定义全量注入到每一次请求的 System Prompt 中。挂载 5 个 MCP Server 就会白白常驻 4000-8000 Token。
- 二级标题 1.3：[★ 核心重点 · WHY · 注意力稀释] 工具过载（Tool Overload）导致的智能退化
  - **WHY 为什么会选错工具**：当 Prompt 里充斥着数十个工具定义时，大模型的注意力被严重分散，幻觉率大幅上升，经常在错误的时机调用错误的工具。

### 一级标题 2：[★ 核心重点 · WHAT & WHY · 大篇幅讲透] 老兵不死：为什么 CLI 在 AI 时代重新称王？
- 二级标题 2.1：[★ 核心重点 · WHAT & WHY · 核心机制] 懒加载发现（Lazy Tool Discovery）
  - **WHAT 运行机制**：平时不向大模型注入任何参数定义；当大模型需要使用某个工具时，跑一条 `command --help` 查看参数说明，读懂后立刻调用，用完即走，零上下文常驻。
- 二级标题 2.2：[★ 核心重点 · WHAT & 架构优势] 标准输入输出与高确定性
  - **WHAT 接口标准**：纯粹的 stdin/stdout/stderr 与 Exit Code（0 成功，非 0 失败），天然适合状态机拦截。
- 二级标题 2.3：[★ 核心重点 · WHAT & 环境通用] 跨运行时通用性
  - **WHAT 复用价值**：人类在终端可以单测、定时任务可以无头调用、Web 控制台后端可以 `execFile` 调用，大模型与人类共享同一套工具栈。

### 一级标题 3：[★ 核心重点 · WHAT · 维度对比] 全方位技术选型矩阵
- 二级标题 3.1：上下文常驻成本（千级 Token 常驻 vs 零常驻）
- 二级标题 3.2：可测试性与排错难度（必须启动协议层 vs 终端一行命令秒级单测）
- 二级标题 3.3：进程开销与长连接稳定性对比

| 评估维度 | MCP 协议工具 | CLI 命令行工具 |
|---|---|---|
| 上下文消耗 | 每次请求全量常驻 JSONSchema | 按需运行 `--help` 懒加载，用完即走 |
| 测试与调试 | 依赖专门的 MCP Inspector 或宿主连接 | 本地终端直接输入命令敲回车即可验证 |
| 跨环境复用 | 绑定在支持 MCP 的 Agent 宿主内 | 人类终端、CI/CD、Cron、Web 后端皆可调用 |
| 状态确定性 | 受模型理解 JSON 准确度影响 | 参数硬校验，Exit Code 确定性返回 |

### 一级标题 4：[★ 核心重点 · WHAT & 决策落地] 架构师决策模型：什么场景用 MCP？什么场景用 CLI？
- 二级标题 4.1：MCP 最佳适用场景：只读数据检索、跨 SaaS 资源连接（如 Notion 只读搜索、GitHub PR 只读检索）
- 二级标题 4.2：CLI 最佳适用场景：状态变更、重度文件 I/O、复杂长耗时流水线、音视频录制与发布
- 二级标题 4.3：在自媒体流水线中的架构实践：只读检索用 `agent-reach`，一切状态写操作全面收敛至 `media` CLI

## 5. 验收标准与作业
- 盘点你当前 Agent 宿主已配置的所有工具，计算它们占用的上下文 Token 比例。
- 将一个原本写成 MCP 的文件写操作工具，重构为一个轻量级的 CLI 命令行并编写测试。
