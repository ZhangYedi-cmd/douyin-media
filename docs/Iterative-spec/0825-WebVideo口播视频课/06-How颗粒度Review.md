## 总评

**18 篇的「命令层」全部合格，多数实操课甚至优秀（第 3、6、7、12 课给出可复制命令 + 验收句 + 派工契约）；真正的缺口集中在「实现逻辑层」——尤其是后端三件套。**

04 清单宣称的「How 四件事齐全」，检的是**接口/契约层**（命令清单、两个方案、技术栈、核心流程），这一层确实补全了。但用户反馈的「颗粒度偏粗、缺一个真人一点点带着你实现」，落在比四件事更细的一格：**当组件是 CLI 或 server 时，课程讲清了它对外做什么，却没讲清 AI 在里面造了什么、每块在干什么、为什么这么设计。** 对零工程背景学员，「口述每块在干什么」这个 03 规范的硬判据，在后端课上是达不到的——不是学员不会讲，是课程没给可讲的东西。

三处用户点名的后端实现，诊断高度一致：**CLI 参数解析、CLI 命令本体的运行机制、无头 `claude -p` 的进程管理与回调，课程的讲述停在「用 commander 声明式注册」和「server 派 claude -p」各一句话，真实实现里决定成败的设计（参数校验契约、写事务、env 剔除、3 秒回调窗口、幂等锁、队列）全部缺席。** 学员照 course 派工，AI 交回来的货在这几处必然自由发挥，而学员没有判据去验。

优先级分布：**阻断级 5 处**（集中在飞书 server 进程管理与 CLI 事务边界，不补则学员的飞书版 server 跑不通 / 不可逆动作有双发风险 / 无法验收）；**建议级 14 处**（集中在第 6、8、17 课的实现逻辑层，补了才有「真人带着实现」的代入感；其中原列第 16 课面板的 3 处已由新第 16 课后端课部分消化）；**保持级 8 处**（详见 §三，这些细节展开反而违背「讲设计不讲实现」）。

## 一、用户特指的后端实现专项

### 专项一 · CLI 参数解析（parser）

**现状**：第 6 课 §三只给一句「命令框架用 commander，声明式注册命令和选项，省掉手写参数解析，代价是多一个依赖」；§四的 spec 写了行为契约，但参数形态、校验点、错误码、退出码、JSON 信封全缺。学员派工时，AI 对「参数怎么定义、怎么校验、报错长什么样」完全自由发挥，验收时也没有判据。

**真实实现里该讲而未讲的**（对照 `packages/cli/src/common.ts`、`envelope.ts`、`commands/flip.ts`、`core/errors.ts`）：

1. **参数形态**：`flip <slug> <status>` 是**位置参数**，`--reason` 是选项；每个写命令都挂**全局选项** `--root/--json/--dry-run`；写者身份走环境变量 `MEDIA_ACTOR`（缺省系统用户名）。学员没有「位置参数 vs 选项 vs 全局选项 vs env」这一层概念，spec 里不会写，AI 会自创。
2. **校验顺序与错误码**：真实 flip 的校验是「先查 status 是否合法值（E_BAD_ARG）→ 查迁移表这条边存不存在（E_ILLEGAL_TRANSITION，报合法出边）→ 边要求理由但缺 `--reason`（E_MISSING_REASON）」。错误码是**集中定义**的 `MediaError`，不是命令里散抛。
3. **退出码表**：0 成功 / 1 规则拒绝（非法参数、非法迁移）/ 2 用法错误（commander 产生）/ 3 锁冲突 / 4 解析损坏。课程只提过 check 的「有 error 退出码为 1」，整张表没讲。
4. **JSON 信封**：`--json` 输出统一形状 `{ok, cmd, data, writes?, alerts?}`（成功）／`{ok:false, cmd, error:{code,message}}`（失败）。这是「AI 和人共读」的接口，课程只说了 check 输出 JSON，没说信封形状。
5. **帮助页是活文档**：`media flip --help` 渲染 `state.ts` 的迁移表——命令自述合法性。设计哲学（规则唯一定义在 core、命令壳薄转发）课程讲了两层，但「帮助页自述规则」这个落点没讲。

**建议补法**（落在第 6 课 §四 spec 之后，加一节「参数与错误契约」，可粘贴进学员的 spec）：

```markdown
## media 的参数与错误契约（本 spec 的通用约定）
- 每个写命令都带三个全局选项：--root <路径>、--json、--dry-run；写者身份读环境变量 MEDIA_ACTOR，不设则取系统用户名。
- flip 的参数：位置参数 <slug> <status>；--reason <text> 只有 requiresReason 的边（rejected）必填，其它边给了也忽略。
- 校验顺序固定：先查 status 是合法值 → 再查迁移表这条边存在 → 边要求理由但缺 --reason 则报错。校验规则收进领域层（迁移表同一处），命令壳只调用、不散写 if。
- 报错三件套：错误码（E_BAD_ARG / E_ILLEGAL_TRANSITION / E_MISSING_REASON / E_NOT_FOUND）+ 人话 + 非法迁移必须列出当前状态全部合法出边。
- 退出码：0 成功 / 1 规则拒绝 / 3 锁冲突。有 error 的 check 退出码为 1。
- --json 输出信封：成功 {"ok":true,"cmd":"flip","data":{...},"writes":[...],"alerts":[...]}；失败 {"ok":false,"cmd":"flip","error":{"code":"...","message":"..."}}。
```

**验收补两条**：`media flip my-first-video published` 应报 E_ILLEGAL_TRANSITION 且列出 review 合法出边、退出码 1；`media flip my-first-video rejected` 不带 `--reason` 应报 E_MISSING_REASON。

**AI 会怎么错（补进 §五）**：把 `--reason` 设计成每条边都必填（实际只有 rejected 要）；把参数校验散在各命令里写 if（该收进 core 的迁移表同一处）；`--json` 输出自创形状（该统一信封）。

**优先级：建议级**（不补学员仍能造出能跑的 4 命令 CLI，但验收能力弱、`--json`/退出码这类机器契约会自由发挥；这正是 03 判据「验不了货」的典型）。

### 专项二 · CLI 命令本体（一条命令从输入到落盘的完整路径）

**现状**：第 6 课 §六给出 promote 的 **8 步领域路径**（输入 slug → 读 backlog → 翻 picked → 回填 content_path → 清 next_up → 建目录 → 写 meta → 收口），这是全课最好的「核心流程」示范。但它停在**领域层**——五处账「一次落盘、要么全做完要么全不做」这句承诺，没有给出文件系统层面的运行机制。真实实现里决定「原子性」的那层，课程没讲。

**真实实现里该讲而未讲的**（对照 `core/writer.ts` 的 `runTransaction`）：

1. **写事务序**：拿锁 → 建快照 → `plan()` 里做**全部校验**（任一失败 = 零写入）→ `--dry-run` 打印计划退出 → 内存算好全部新内容 → **temp 写完再 rename**（原子替换，写不坏半截）→ 同锁内重生成 dashboard 机器区 → append audit → 释放锁 → 尾部自动跑 check 附尾输出。
2. **锁**：并发两个 `media` 写命令（比如定时任务和人同时 promote）会锁冲突，`E_LOCKED` 退出码 3。课程讲「原子操作」但没讲并发下怎么防——这是「一次落盘」在多人/多进程场景的保证。
3. **audit.jsonl**：每次写命令 append 一行 `{ts, actor, cmd, argv, result, files}`。这是「结构化事件/可审计」在 CLI 层的落地（第 8 课讲的是飞书按钮事件，media 自己的审计轨迹课程全课没提）。
4. **尾部 check**：写事务跑完自动重算快照、跑 alerts 附在输出里。课程把 check 当独立命令讲，没讲「每个写命令自带 check 尾部」这个让 AI 干完活立刻自查的设计。

**建议补法**（落在第 6 课 §六之后，加一节「写事务，一条命令的运行时路径」，让学员能口述「在哪校验、在哪翻转、在哪收口」）：

```markdown
## 一条写命令的运行时路径（口述版）
拿锁（同一时刻同一仓只许一个写命令）→ 读全仓快照 → 在快照上做全部校验，任一失败整条命令零写入 → 把五处改动算成一个写计划 → 逐文件写临时文件、写完改名替换（不写坏半截）→ 同一把锁内重建 dashboard 机器区 → 追加一行审计（谁、何时、改了哪些文件）→ 释放锁 → 尾部自动跑一遍 check，把告警附在输出里。
```

**派工契约补一句**：「写入必须是事务：先全部校验、再一次性落盘，中途失败不留半套账；并发写要加锁，撞锁报错；写命令要记写者身份和变更清单（audit）。」

**验收补三条**：`git status` 看 `tools/console/.runtime/audit.jsonl` 多了一行；故意同时跑两条 `media promote`，应有一条报锁冲突（E_LOCKED）；中途 Ctrl-C，`meta.yaml` 和 `backlog.yaml` 不应出现「改了一半」的状态。

**AI 会怎么错（补进 §五）**：顺序改五个文件、不锁（两条命令并发写坏账）；把校验和写入混在一起（先改一个文件再校验下一个，失败留半套）；不记 audit。

**优先级：建议级**（8 步领域路径已给出，事务细节是「原子性」承诺的底层支撑，补了学员才能验「要么全做完要么全不做」；该节同时把 03 规范 §三 第 4 件事「核心流程」从领域层补到运行时层）。

### 专项三 · Claude Code 进程管理与回调（无头 `claude -p` 的拉起、排队、回传）

**现状**：第 8 课 sequenceDiagram 画了「server 派 claude -p /publish --publish → 真发 → publish-done 记账 → 更新卡片」，正文说「轮询 meta.status 判成败」；第 17 课面板说「server 用 spawn claude -p 起任务，先回 202 加 jobId，进度走 SSE」。**新插入的第 16 课后端课已把 env 剔除、工具白名单、幂等锁、读状态不读退出码、单并发队列、cc-stream 全部讲清（见 §六 B5–B9 标注「已覆盖」）**；仍缺的落点收敛为三处：取消优雅终止、全量重建前提、快写参数白名单。第 8 课自身停在**表面形态**，真实实现里决定「能不能安全跑通」的四件事全缺席。

**真实实现里该讲而未讲的**（对照 `tools/feishu-bot/server.py`、`packages/cc-stream/src/spawn.ts`、`packages/server/src/jobs/runner.ts`）：

1. **环境变量剔除**（最致命）：`claude -p` 子进程必须从 env 里删掉 `ANTHROPIC_API_KEY`——本机该变量是 OAuth token（`sk-ant-oat01-…`），子 claude 会把它当 API key 用，直接 Invalid API key。飞书 server 和 cc-stream 都做了这件事。课程全课没提。学员的 AI 写 server 时根本不会知道要删这个 env，飞书版发布必失败。
2. **3 秒回调窗口**：飞书卡片回调必须在 3 秒内响应，重活（拼物料、派 claude、等发布）必须甩到后台线程；卡片更新两路走（响应里带 `resp.card` 原子更新 + 异步 PATCH 兜底）。课程说「server 只处理事件」，没说 3 秒时限。AI 若同步跑发布，回调超时，卡死。
3. **幂等锁**：同一 slug 正在发布时再点「确认发布」，必须拒绝（真实实现：旧路径本地 `_publishing` set，新路径 job runner 的 409 `JOB_DUPLICATE`）。飞书会重投回调、人也可能连点，无锁则不可逆动作并发双发。课程 8 的本地版 spec 和飞书版清单都没提。
4. **跨进程交接**（生产版架构）：飞书 server 不再直接 `spawn claude -p`，而是 `POST` 给 console job runner（`:5170` 的 `/api/actions/publish`）拿到 jobId，再每 10 秒轮询 `GET /api/jobs/:id`；server 重启任务表丢失时返回 `unknown` 态，人要核 `meta.status`，不误报成功/失败。课程 8 的「server 派 claude -p」是旧路径；生产版这条 S8 交接完全没讲。
5. **优雅终止与队列**（第 17 课面板慢作业）：JobRunner 单并发队列 + lockKey 去重（同 slug 不能并发 publish/rework/create）+ 取消时 SIGTERM→10 秒宽限→SIGKILL。第 17 课只说「spawn claude -p 起任务，先回 202」；新第 16 课后端课已补单并发与去重，取消优雅终止仍是唯一缺口。
6. **`--allowedTools` 白名单**：无头 claude 只给白名单工具（发布链要用的那几个）。课程没提。

**建议补法**：

- **第 8 课**在飞书版进阶五步之后，加一节「无头 claude 的安全拉起，四件事」：

```markdown
## server 收到按钮后，那台无头 claude 怎么被安全拉起
1. 环境剔除：子进程 env 删掉 ANTHROPIC_API_KEY（本机它是 OAuth token，不删会被当成 API key，发布必失败）。
2. 工具白名单：claude -p 只给发布链要用的 --allowedTools，不给任意工具。
3. 超时与终止：超时先 SIGTERM、10 秒宽限后 SIGKILL；别让卡死的 claude 永久占着。
4. 结果不读退出码：轮询 meta.status 翻到 published 才算成功——claude 可能自己没崩、但 skill 崩在记账之前。
回调还要守三件事：3 秒内必须响应，重活甩后台线程；卡片更新两路走（响应带新卡 + 异步补一张）；同一条重复点击要有幂等锁，否则不可逆动作并发双发。
```

- **第 17 课**慢作业段补一句队列语义：单并发（同一时刻只跑一个慢作业）、同 slug 去重（正在 publish 的不许再 publish，返回 409）、取消用优雅终止。（新第 16 课后端课已覆盖单并发与去重，此句补在面板侧与后端呼应。）
- **验收补**：飞书版跑通后，连点两次「确认发布」，应只发一次（第二条被拒）；把 `ANTHROPIC_API_KEY` 留在环境里跑一次，应看到发布失败的错误信息而非「成功」。
- **AI 会怎么错（补进第 8 课 §四）**：不删 API key env；把回调做成同步重活导致超时；不设幂等锁导致双击双发；用 `claude -p` 的退出码判成败（实际要轮询 status 账）。

**优先级：阻断级**（飞书进阶路径。env 剔除不补则发布必失败，3 秒窗口不补则回调超时，幂等锁不补则有不可逆双发风险——学员照做既会卡死、也验不了货；新第 16 课后端课已覆盖的队列语义为建议级）。

## 六、深度思考专项：为什么用 A 不用 B（以 0818 看板工作台 spec 为基准）

> 补记（2026-08-26）：作者读 `docs/Iterative-spec/0818-看板工作台/`（CLI/后端/前端三份拍板 + 01/02 执行方案 + 04 一致性Review + 00 总览）后追加。**本专项是上一版缺失的维度。** 作者判断「很多实现讲得太糙」的根不在命令层——在**实现决策层**：课程讲清了选 A 不选 B 的「产品/交互层」取舍（第 6 课 CLI vs 脚本 vs skill、第 7 课直接调 sau vs 独立脚本 vs 包装 skill、第 17 课 markdown vs Web UI），却把「为什么这样落实现」的深度思考省了。而 0818 方案包里，每一个实现决策都带明确的「否掉谁、为什么否」。下面的决策点课程**现状只给结论或根本没提**，按「spec 原文 → 为什么 A 不用 B → 落进哪课」列出，供后续补课引用。全部落点仍守「学员不写代码」边界：是 spec 内容与验收判据，不是让学员学写码。

### A. CLI 层（落第 6 课）

1. **写命令 = 事务（拿锁→快照→全部校验→temp 替换→同锁重建 dashboard→audit→尾部 check）**。spec：CLI 拍板 §5.2/§11、01 执行 §2.0 事务序、§2.17 运行时文件。为什么 A 不用 B：**顺序改五个文件的 B 失败即留半套账**（meta 翻了、backlog 没翻，正是历史双层不同步事故）；校验在内存全过才落盘 = 任一失败零写入，diff 只含白名单行，可验收。课程只讲「要么全做完要么全不做」承诺，没讲运行时序（06 专项二已补 What，这里补 Why）。落点：第 6 课 §六后「写事务，为什么 A 不用 B」口述段。

2. **YAML 用 Document API 定点编辑，禁整篇重写**。spec：CLI 拍板 §4（`backlog.yaml`/`meta.yaml` 的灵魂在注释里，常规 js-yaml dump 抹全部注释 = 本 CLI 最大翻车点）、01 执行 §2.15（改值不换节点，注释自动原位保留）。为什么 A 不用 B：**注释是账的注释**（终检记录、取题说明、清扫留痕全在 status 行注释里），整篇重写 = 抹账 + 无 diff 可比。课程只提过「只改目标字段、不动其它字节」一句方向，没讲为什么非它不可。落点：第 6 课 §四 spec 前加一句「写路径必须保注释——YAML 的注释就是审计留痕，AI 若整篇重写等于抹账，验收看 git diff 只许目标字段」。

3. **`--json` 统一信封 + 退出码表 + `MEDIA_ACTOR`**。spec：01 执行 §2.0（信封 `{ok,cmd,data,writes,alerts}`、退出码 0/1/3、actor 归因）。为什么 A 不用 B：统一机器契约是**server 动作层 + 治理线日巡的共同消费接口**，各命令自创形状则下游没人敢吃；`MEDIA_ACTOR` env 注入让 audit.jsonl 记得出这笔账是 feishu/console/定时 agent 谁改的——**写者归因是审计的生存前提**。课程只提 check 输出 JSON、error 退出码 1。落点：第 6 课 §三后「参数与错误契约」（06 专项一 What）+ 这里 Why。

4. **`media flip` 拒绝 published/scheduled，强制走 publish-done**。spec：01 执行 §2.6 校验（发布是三翻齐事务，单翻 meta 必造双层不同步——对「Step 5 唯一记账」铁律的机械保护）。为什么 A 不用 B：允许 flip 直达 published = **绕过三翻齐**（backlog 不翻、dashboard 不重建），单翻 meta 和双翻丢一翻都是历史事故源；把这条边焊死在命令里，人/AI 想违规都违不了。课程现状最危险：第 6 课 mermaid 把 `approved → published` 画成普通 flip 边（06 报告已标跨课口径断裂），第 8 课却说 flip 硬拒绝——**照第 6 课自建 CLI 的学员会造出能违规的命令**。落点：第 6 课 mermaid 补注「published 只能走 publish-done，flip 硬拒绝」+ Why。

### B. 无头 claude -p 进程层（落第 8 课为主，第 16 课为辅）

5. **env 剔除 `ANTHROPIC_API_KEY`**。spec：后端拍板 §6 防坑点 1、02 执行 spawn.ts `dropEnv` 默认值。为什么 A 不用 B：本机这个变量是 **OAuth token（`sk-ant-oat01-…`），子 claude 误当 API key → Invalid API key 发布必失败**；剔除后回落 `~/.claude` 登录凭证。这是「真实世界会抖」最便宜的一课——不是架构选择题，是**环境语义**（同名变量在不同机器/进程含义不同）。课程全没提。落点：第 8 课飞书版后「无头 claude 安全拉起四件事」第 1 条（06 专项三 What）+ 这条 Why。

6. **幂等锁（同 slug 同刻只许一个发布/重做任务）**。spec：后端拍板 §6 B5、02 执行 §2.3（继承 feishu `_publishing` set 的教训——回调重投/人连点会双发）。为什么 A 不用 B：发布不可逆，双击双发**没有后悔药**；飞书会重投回调、人会连点，无锁则靠人的自觉防错。课程第 8 课本地版 spec 和飞书版清单都没提。落点：第 8 课回调三件事第 3 条（06 专项三）+ 这条 Why。

7. **成败判定读状态，不读文字/不读退出码**。spec：后端拍板 §6 防坑点 4、§7.4 信任分级（模型文本 `text` 只展示、工具事件驱动步骤条、**文件状态 `meta.status` 是唯一裁决**）。为什么 A 不用 B：claude 进程可能没崩、但 skill 崩在记账之前（退出码 0 ≠ 发布成功）；解析自然语言输出判成败 = 拿叙述当证据，信任分级禁止。课程第 8 课讲了「轮询 meta.status、不验 exit code」方向对，但没讲背后的**三级信任原则**（文本永不驱动状态）——这恰是「为什么」最有价值的部分。落点：第 8 课把「读状态不读字」从一句话补成三级信任。

8. **单并发 + 内存任务表，不引队列中间件**。spec：后端拍板 §6 B5（流水线本来串行，一个 Map + 子进程句柄）。为什么 A 不用 B：规模不到（单人流水线），引 BullMQ/Celery 是**为了没出现的并发**付架构税；崩溃安全不靠队列持久化，靠**真相在文件里**——server 挂了任务表丢了无所谓，重启后快照 + `media check` 给出真实状态（「事件可丢、状态可重建」延伸到任务层）。**已覆盖**：新第 16 课后端课补了「幂等锁 409 + 单并发」队列语义，第 17 课面板慢作业段呼应即可。

9. **cc-stream 独立成零依赖叶子包（引擎进包、知识留外）**。spec：后端拍板 §7.3、02 执行 §2.7。为什么 A 不用 B：里程碑匹配表是**领域知识**（认识发布/meta.yaml）留 server，传输/归一/里程碑引擎是**通用能力**进包——包可跨项目复用，且包内没有任何一行认识领域 = 换项目零成本；信任分级纪律靠包边界焊死。**已覆盖**：新第 16 课后端课已讲「三层解析 + cc-stream 独立包（引擎进包、知识留外）」；第 17 课面板只引结论即可。

10. **飞书回调 3 秒窗口，重活甩线程**。spec：CLI 拍板 §6.1、02 执行 S8（3 秒窗口纪律；卡片更新两路走：响应带 `resp.card` 原子更新 + 异步 PATCH 兜底）。为什么 A 不用 B：飞书要求回调 3 秒内响应，同步跑发布 = 必然超时卡死；「响应先回 + 后台干活 + 异步补卡」是平台时限逼出来的形态。课程第 8 课说「server 只处理事件」没说时限。落点：第 8 课回调三件事第 2 条 + Why。

### C. 前端选型层（落第 17 课面板）

11. **React 推翻 vanilla 零构建**。spec：前端拍板 F1（前提变了：该分析针对**只读看板**，产品升级为裁决台后，审批/dry-run 确认流/job 进度全是**有状态交互组件**——vanilla 的「保存/恢复 UI 态」补丁本质是**手搓乞丐版 React**）。为什么 A 不用 B：这是课程「前提变结论跟着变」的教科书案例，且 spec 给了具体的 B 之痛（保存/恢复 UI 态、`esc()` 注入纪律）。课程第 17 课讲了「升级成裁决台才换 React」，但没讲 B 具体痛在哪。落点：第 17 课选型段补「vanilla 为什么撑不住有状态交互」。

12. **不上状态管理库（redux/zustand/react-query 均不）**。spec：前端拍板 F6（后端「SSE 只推 refresh + revision」的模型**天然消解前端缓存/失效问题**）。为什么 A 不用 B：状态库解决的是前端缓存与失效管理，这套系统**把缓存问题压回源头**（前端不缓存账本就没有失效）——为不存在的问题引依赖。课程第 17 课讲了「前端不缓存账本就没有缓存失效」这个原理，但没点破它直接对应「所以不上状态库」的选型。落点：第 17 课选型段把原理和选型钉在一起。

13. **全量重建不增量**。spec：后端拍板 §3 决策 1（百余小文件全量 <100ms；5 条警报全是跨源交叉校验，增量失效图≈全量）。为什么 A 不用 B：增量优化的收益（省 100ms）远小于复杂度（增量失效图 ≈ 全量还要写失效传播），YAGNI。课程第 17 课讲了「revision 加一全站重拉」没讲「server 每次全量重建」这个前提。落点：第 17 课 §数据层一句「server 不维护增量，账本一变全量重建快照（全仓百余小文件，<100ms），这是零状态库的物理前提」；新第 16 课后端课可一并补该前提。

14. **token 不上完整认证系统**。spec：后端拍板 §5（单机单用户，bind 127.0.0.1 + 启动生成 token 防浏览器侧 CSRF，**到此为止，不上认证系统**）。为什么 A 不用 B：威胁模型只有「本机浏览器到本机 server」，完整认证是为不存在的多用户场景付税。**已覆盖**：新第 16 课后端课已讲「token 按威胁模型定档」，第 17 课只需引结论。

### D. 跨课的一条架构主线

15. **「写者与读者经文件系统解耦」**。spec：后端拍板 §5（界面数据更新不走响应，走 chokidar→快照→SSE 链路）、§11「文件系统即总线」（飞书与看板两进程零直接耦合）。这是串起第 6（media 记账）、第 8（飞书 server）、第 17（看板 server）三课的**同一根梁**：所有写者都往文件写，所有读者都从文件读，谁改的账由 audit 记、谁看了什么由快照决定，组件之间不互相认识。课程各课讲了局部（第 17 课「写者与读者经文件系统解耦」一句），没把它立成**贯穿模块二到模块三的架构原则**。**已覆盖**：结课第 18 课总纲已加「文件系统即总线」并入真相源与状态机要素、并新增进程管理要素，回指 6/8/16/17 四课。

**小结**：以上 15 条决策点，spec 里每一处都带「否掉谁、为什么否」，这是「真人一点点带着实现」最有价值的部分——学员学到的不只是「系统长这样」，而是「每块设计是怎么被逼出来的」。课程要体现深度思考，补的不是代码，是**决策推演**：每课至少一处「为什么 A 不用 B」落到实现层，且能口述 B 错在哪。

## 七、概念铺垫专项：前置依赖体检（03 规范 §二.5）

> 补记（2026-08-26）：沿用户指出的「CC 消息体解析缺概念铺垫」放大成一次全课体检（subagent 通读 18 课 + 作者交叉验证第 6 课）。标尺 = 03 规范 §二.5「由浅至深，前置依赖单调，后节不引用前节没立的概念」。判据：某课用到一概念，第 0 课基线推不出、前课没立或立不够、本课没就地垫，三全中才算断崖。

### 总评

**18 课的核心概念链整体立住了，零断崖。** 状态机（第 0/5/6 课三级建立）、迁移表（6 §四）、三翻齐（5/6 立、7 §三收紧）、SDD（6 §八立、9/12/14/16 复用）、结构化事件（8 §七）、漏斗归因（13 §一）、限幅表/熄火线（14）、lessons Lx 回指（15）——全部「前课立过、本课引用清晰」。真实缺位集中在**第 17 课面板前端实现层 + 两个贯穿性术语（退出码、git 工作区）**，共 8 处（含作者交叉验证补 1 处）。

### 断崖清单（按课程）

**1. 第 3 课 §八「别拿退出码当验收」——退出码概念未立（中）**
- 用到：L16 静默失败「每条命令都体面地退出了」；§5.2 验收句先用「exit 1」。此后第 4/6/7/8 课多处在用「退出码 1」「server 不信进程的退出码」。
- 卡点：D1 不知道「命令跑完会返回一个整数、0 成功非 0 出错」这个机制，也不理解「体面退出（码 0）」和「干成了」是两回事。
- 铺垫：第 3 课 §八 起手一句立概念「命令跑完会返回一个数字，叫退出码，0 表示成功、非 0 表示出错，终端一般不显示但脚本能读到」，再接教训，后课复用即有出处。

**2. 第 6 课 §三 技术栈——「编译期」未落人话（低，作者交叉验证补）**
- 用到：「非法的 status 在编译期就被拦一道，比运行时发现强」。
- 卡点：D1 不知道「代码有编译这道工序」，「编译期 vs 运行时」是工程默认。
- 铺垫：换成本课口吻「类型系统像一道筛子，状态值写错在工具跑起来之前就拦下，不用等跑的时候才发现错」。（subagent 未单列、第 6 课整体标 0，作者补。）

**3. 第 14 课 §四/§五——git 工作区心智模型未立（低）**
- 用到：「改动留在 git 工作区供人 diff 复核」「自动档改动不能直接 commit」。
- 卡点：D1 的 git 模型只有「提交/存档」，不知道「工作区 vs 已提交」两态，也就不懂「留工作区 = 固化前人眼可查、可回滚」是安全机制。
- 铺垫：第 14 课 §四 就地一句「git 里文件分『已提交』和『还没提交』两种状态，改动先停在『还没提交』（工作区），人用 git diff 能看到改了什么，确认后才由人 commit 固化；自动档只改到工作区，就是让每一步改动在固化前都过得了人眼」。

**4. 第 17 课 §写动作/§面板——server 怎么知道 claude 跑到哪一步（高，与 §六.B9 同一落点；新第 16 课后端课已垫 cc-stream，此条为面板侧的二次铺垫）**
- 用到：「每一步广播一条 job 快照」「推 job:<id> 事件，带任务全量快照」「useJob 消费任务的事件流」。
- 卡点：按第 8 课黑盒模型理解的 D1 会懵——server 又没在终端里盯着，怎么知道现在到「等授权」还是「真发」？claude -p 不是黑盒吗？「job 快照」从哪冒出来的？还会误以为 server 靠读 claude 的话理解进度（那正和「验产物不验文本」矛盾）。
- 铺垫（先垫概念，再讲引擎，再进 §六.B9 的 why）：「无头 claude 干活时会把每一步动作（调用了哪个工具、改了哪个文件）以机器可读的事件流吐出来，server 解析这些事件画进度；但进度只是展示，成功失败仍然只认 meta.status 账——进度可丢，裁决不能丢」。这一句既接通第 8 课黑盒模型，又垫好 cc-stream 概念（新第 16 课后端课已把该概念立住，面板课复用并回指第 16 课）。

**5. 第 17 课 §选型/§先建一页——proxy 未立（低）**
- 用到：「dev 是 vite dev 加 proxy /api」「SSE 走 proxy 要关缓冲」；验收「revision 收不到多半是 proxy 缓冲没关」。
- 卡点：照抄「加 proxy /api」不知道它是干嘛的，验收排查无从下手。
- 铺垫：§先建一页第一步一句「开发时网页和后端是两个独立程序、各占一个端口，proxy 让网页把 /api 开头的请求转给后端那个端口；SSE 是长连接，proxy 若缓冲会堵住它，所以要关缓冲」。

**6. 第 17 课 §面板/§spec——前端路由/SPA 未立（低）**
- 用到：「路由 /overview」「react-router-dom」。
- 卡点：D1 把「路由」往网络路径方向猜，不清楚「一个网页里有六个 URL、每个地址一屏」。
- 铺垫：§面板六页路径之后一句「路由就是给网页里每一页分配一个网址后缀，/overview 进总览页，react-router-dom 是负责这件事的库」。

**7. 第 17 课 §spec/§数据层——hook 未立（低）**
- 用到：「只走 usePageData 和 useJob 两个 hook」「组件里不裸 fetch」。
- 卡点：不知道 hook 和普通函数区别，不理解「组件自己拉数据」为什么算违规——而它恰是防缓存失效设计的关键约束。
- 铺垫：§数据层一句「hook 就是封装好的函数。全站只从 usePageData/useJob 两个口子拿数据，组件若自己发请求就绕过『版本号一变就整站重拉』的统一机制，所以 spec 把它写成硬约束」。

**8. 第 17 课 §选型——构建产物入 git 与第 1 课规则张力（低，属跨课口径非纯概念）**
- 用到：「构建产物进 git，clone 即跑」（第 1 课立过「构建产物不入 git，clone 后要先构建」）。
- 卡点：D1 会问两课到底哪个对，照第 1 课的通用化理解会觉得第 17 课违规。
- 铺垫：该句后补半句回指「这和第 1 课说的不冲突——CLI 编译产物重、clone 后构建一次就行；前端 dist 轻、进 git 是为了 clone 即跑、不强制装前端工具链，两条规则各管一个组件」。
