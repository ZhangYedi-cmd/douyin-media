# 第 5 课 内容工厂的骨架，目录、状态机、账号大脑

> 代码仓库：<https://git.aicodex.cc/devlist/douyin-media>
> 对应分支：`05-content-factory`

模块一收官时你手里有一条完整的口播视频，还有第 4 课结尾留下的那个问题。第一条做完了，等条目攒到十来条，哪条写完稿、哪条还卡在配音等着审，谁记得住。做第二条时你大概率会把第一条的文件挪来挪去腾地方，做到第五条，目录已经长成没人敢动的样子。

模块一教你造一件作品，模块二把它变成工厂。**模块二开工前，先把账立起来**。工厂和作坊的第一道分水岭是账，每件在制品此刻处于哪道工序、下一步归谁，账上一查便知。这一课不产任何内容，专门立骨架，货架和账本先立起来，开工是下一课以后的事。

这一课照着课程仓搭出四样东西，`content/` 内容目录（一条内容住一个目录）、`content/_backlog/` 选题池总账、`brain/` 账号大脑五件套、`dashboard.md` 看板雏形。做完后你手里有四件齐的骨架、一份成文的 brain 五件套初稿，还能口述两层状态账各管什么、说出阶段为什么记在字段里。

## 一、工厂先有货架，再谈开工

先给本课在整个系统里定位。模块一的四件套解决怎么造，本课解决造出来的东西放哪、状态记哪、决策依据从哪来。货架和账本在开工前就位，后面的每一课都往这上面挂东西。

骨架分三层，外加一张投影，摆在一张地图上长这样。

```plain
第 1 层 货架   content/<日期>/<slug>/   一条内容一个目录，档案住这（meta.yaml + 阶段 md）
第 2 层 账本   content/_backlog/        选题池总账，库存住这（粗三态 + next_up）
              各目录 meta.yaml          在制状态机，细账住这（六态加时间戳）
第 3 层 大脑   brain/                   决策依据五件套
投影层（只读） dashboard.md             看板快照，不记任何账
```

再配一条判断公式。往后凡是要决定"某样东西记在哪"，先问它属于四类里的哪一类。库存进 backlog，在制进 meta，决策进 brain，视图进 dashboard 且只读。四类各归各，混了就是账乱。

投影层这一行标着只读，原因在 §七。它和另外三层性质不同，前三层是真相源，它是投影。

![内容工厂由货架、账本、大脑和只读投影组成](imgs/lesson-05/01-layered-stack-factory-skeleton.png)

这四样没有一样住在数据库里。第 0 课 §4.2 对数据库取舍只给了比喻级结论，完整对比在这里展开。这里把它讲成一次技术选型，因为后面每一课都建在这个选择上。

先说可选方案。方案 A，上一个数据库，SQLite 或 Postgres，把内容、状态、选题建成表。方案 B，账本全部写成 git 仓库里的文本文件，YAML 加 Markdown。这套系统选了 B。

为什么选 B，四个理由。第一，账变要能审，每一次状态翻转都是一次 git 提交，人看 diff 就能审这一笔账对不对，错账能回滚，数据库的变更没有这种天生的审阅形态，要另建审计表。第二，AI 读写文件零成本，AI 能直接读 meta.yaml、改一个字段、交一份 diff 回来，人验收这份 diff 就行，换成数据库，AI 要连库、学 schema、写 SQL，每一步都是新的出错点。第三，规模小，几十条内容、几百条选题，数据库的查询优势用不上，文本文件更轻。第四，单文件好去重，选题池就是一个 backlog.yaml，去重、查状态、统计都在这一个文件里做完，课程仓的 backlog README 把这条写进了头一句。

选文件挡掉了三类坑。数据库的 schema 迁移要维护，连接要管理，AI 连库失败又是一类排障场景，这些坑在这个系统里全部绕开。

代价也要说清。文本文件没有查询语言，统计要靠脚本扫 YAML；字段合法性没有数据库约束兜底，得另立校验，那正是第 6 课要造的 media 命令；并发靠 git 串行化，两个流程同时写同一份账要排队。这三样代价换来可审、可回滚、AI 零门槛读写，这笔账划得来。

## 二、一条内容住一个目录

骨架的第一件货，是给每条内容一个固定目录。课程仓 main 分支的 `content/_template/` 就是标准间样板，先复制进你的仓。摘法还是第 1 课那条，`git checkout main -- 路径` 把 main 上指定路径的文件复制进你当前分支，不换分支。

```bash
mkdir -p content && git checkout main -- content/_template
ls content/_template
# meta.yaml  1-brief.md  2-script.md  3-review.md  4-publish.md  5-retro.md  assets/  README.md
```

逐条拆这三步。`mkdir -p content` 建出内容根目录，已存在也不报错；`git checkout main -- content/_template` 从 main 分支把样板整目录复制过来；`ls` 验一眼，八个顶层条目都在才算数，其中七个是内容档案，五个阶段文件加 meta.yaml 加 assets，README 是使用说明，不算条目。

五个编号文件对应内容的五个阶段，选题简报、口播稿、审核记录、发布物料、复盘。模板 README 里有一张"谁产、何时产、必产吗"的表，值得整个读一遍，这里说两个要点。第一，文件按需生产，一次过审就不用建 3-review.md，档案按需生长。第二，进 git 的只有档案层（这些 md 加 meta.yaml），第 2 课那种 Vite 工作区（build/）和成片 mp4 本体全部 gitignore，仓库存账不存货。

真正的主角是 `meta.yaml`，每条内容的身份证加状态卡。

```yaml
# content/_template/meta.yaml（节选）
slug:                      # 短标识，同目录名
title:                     # 工作标题
type:                      # kouban(口播) | tuwen(图文)
pillar:                    # depth(技术深度) | traffic(流量型)
status: ideated            # 状态只经 media 命令翻转，不手编
source:                    # 选题来源，指回 backlog 条目
schedule:                  # 计划发布时间
publish_url:               # 发布后回填
timestamps:
  ideated:
  drafting:
  review:
  approved:
  published:
  retro_done:
```

这张字段清单里 `status` 是唯一合法的状态入口，后面所有翻转都落在这个字段上。`timestamps` 六个时间戳和六个状态一一对应，状态走到哪一步，时间就记到哪一行。`source` 记选题来源，回头指向 backlog 里的某条 id，这个指针到 §四会派上用场。

新建一条内容就是把模板复制到 `content/<发布日>/<slug>/`，路径三段，发布日、短标识、目录名。拿模块一做的那条视频练手，给它建档，走一遍完整路径。

第一步，建目录，把模板复制成 `content/2026-08-25/my-first-video/`。第二步，填 meta.yaml，这一步别手敲，派给 AI，让 AI 读 `content/_template/meta.yaml` 和你新目录的 meta.yaml，照着模板把字段补全，交回你核对。核对五个字段，slug 写 `my-first-video`，type 写 `kouban`，status 写 `ideated`，source 留空或指向对应选题，timestamps 里 ideated 记上当前时间。第三步，把模块一产出的 script 归到 2-script.md，成片 mp4 放进 assets/，同时记住它不进 git。

顺带认一下 YAML 的格式。它是缩进分层的文本格式，一行一个字段，键和值用英文冒号加空格隔开，注释用井号开头。缩进错位 AI 会读错层级，所以别手填，让 AI 改，你核对。

这里 AI 最容易出错的地方是建完目录就收工。它把模板复制过去，meta.yaml 里的 status 留在模板默认的 ideated，甚至干脆不填，source 也不回填。这条内容在账上等于没记上，看板和选题池都读不出它到底做到哪一步。验收时别只看目录存在，打开 meta.yaml 确认 status、source、timestamps 都有值。

**应看到什么**。`ls content/_template` 列出八个顶层条目，七个是内容档案，README 是使用说明；你的第一条内容目录已建好，meta.yaml 填齐，script 归位，status 有值。

## 三、阶段写在字段里，不写在文件夹上

阶段不靠目录位置，靠 meta.yaml 里的一个字段，这是本课第一个要停下来对比的设计决策。

很多人的直觉是按阶段建文件夹，草稿箱、待审核、已发布，内容做到哪一步就挪进哪个文件夹，文件夹就是状态。这套系统选了相反的路，内容全生命周期住同一个目录，阶段是 meta.yaml 里的一个字段。

挪文件夹这条路，代价主要压在引用上。一条内容做到一半，脚本和选题池里都记着它的路径，比如 content/2026-08-25/my-first-video。目录一挪，这些记录齐齐指向空位，处处要追着改。git 也帮不上忙，它把挪动记成删一条加一条，这条内容从草稿到成片的演变史被切成了几段，git log 里拼不出连续的时间线。真要出事还在并发，两个流程如果同时挪同一条内容，先后顺序谁定，一错就乱。

改字段没有这些事。路径从头到尾不变，git 里是一条连续的历史，一次改动就是一个原子提交。这就是这套系统把阶段写成字段的原因。

一句话记住这个设计，**状态是数据，不是位置**。内容住哪个目录，跟它做到哪一步，是两件互不相干的事。后面每一课都建在这句话上。

![固定目录加状态字段与挪文件夹表达状态的对比](imgs/lesson-05/02-split-compare-state-location.png)

**应看到什么**。你的第一条内容从建档到发布，目录路径始终是同一个；阶段变化只体现在 meta.yaml 的 status 字段上，git log 里是一条连续的时间线。

## 四、选题池，一本粗账

内容有了固定位置，还没进厂的选题放哪。课程仓的答案是一本总账。

```bash
mkdir -p content/_backlog && git checkout main -- content/_backlog/backlog.yaml
head -30 content/_backlog/backlog.yaml   # 头部注释是这本账的完整说明书
```

每条候选选题是账上一条记录，带 id、标题、赛道（depth 深度或 traffic 流量）、六维打分、标签、入池日期。现在填三五条你想做的题进去。这一步同样派给 AI，让 AI 读 `content/_backlog/backlog.yaml`，照着头注格式补三到五条 idea，交回你核对。核对四个字段，id 不重复，标题是你真在想的题，赛道在 depth 和 traffic 里选，六维打分先凭感觉给。打分怎么打模块四会教，现在先占位。

头注里有一段"状态分两层，别混"，是本课第二个心智模型。backlog 只管粗粒度三态，idea（还在池里）、picked（已提去做）、published（已发布收官），细粒度的 drafting、review、approved 全在各条内容自己的 meta.yaml 里，backlog 不镜像它们。两本账靠双向指针互认，backlog 条目的 content_path 指向内容目录，meta.yaml 的 source 指回 backlog id。

两张账的关系画出来是这样。

```mermaid
flowchart TB
    subgraph backlog["backlog.yaml 选题池总账（粗账）"]
        idea["idea 池内"] --> picked["picked 已提去做"]
        picked --> publishedB["published 已发布"]
    end

    dir["content/日期/slug/ 一条内容一个目录"]

    subgraph meta["该目录 meta.yaml（细账）"]
        ideated["ideated"] --> drafting["drafting"]
        drafting --> review["review"]
        review --> approved["approved"]
        approved --> publishedM["published"]
        publishedM --> retro["retro_done"]
    end

    picked -. content_path 指向 .-> dir
    dir -. meta.source 指回 id .-> idea
```

图里两条虚线是双向指针。上面那条，promote 一题时 backlog 条目翻成 picked，同时回填 content_path 指向内容目录；下面那条，内容目录的 meta.source 指回这条选题的 id，两条线一正一反，两边能互相找到对方。粗账跑粗三态，细账跑六态，两本账各管一段，谁也不复制谁。细账这条链画的是主路径，打回、拒绝这些分支藏在迁移表里，第 6 课造 media 命令时再展开。

为什么不合成一本账。粗账管库存，池里还有多少货、哪条该先做；细账管在制，这一条走到哪道工序。两边关心的问题、翻动的频率、读它的人都不同。硬合成一本，每次工序翻转都要改总账，总账改得频繁，库存视角就看不清楚了。

账本顶部还有一个 `next_up` 指针，人工钦点下一条要做的题。它的用法留给模块三，现在只需要知道账本给人留了插手的位置。

**应看到什么**。`head -30 backlog.yaml` 能看到"状态分两层"这段头注；你手填的三五条 idea 格式合规；你能不看笔记说出粗账管哪三态、细账住哪、双向指针怎么互认。

## 五、账号大脑五件套

骨架第三块管决策依据。做内容每天都在做判断，选什么题、用什么语气、追不追这个热点，判断得有依据，依据不能散落在你脑子里，得写成 AI 每次干活都能读到的文件。课程仓把它叫 brain，五个文件各管一摊。

先看五件套各装什么字段，这是一张清单。

```plain
brain/positioning.md   一句话定位、目标人群、内容支柱（深度/流量）、内容比例、发布节奏、不做什么
brain/persona.md       人设、口播语气、图文语气、禁忌、待补充的空位
brain/style-guide.md   标题钩子库、口播时长结构、图文规范、违禁词、视觉资产
brain/sources.md       素材源（流量源/深度源）、关键词矩阵、对标账号的引用
brain/benchmarks.md    对标账号表、爆款拆解模板、自己沉淀的有效打法
```

benchmarks.md 有实打实的内容，课程仓里已经住着一批真实的对标账号，唐国梁Tommy 做 Claude Code 源码和 Agent 框架，卢菁博士做硬核拆解，LLM张老师做架构讲解，还有英文侧的 AI Engineer 和 Yifan。每一条都标着平台、方向、值得学什么、来源，起步锚定"技术背景加高流量"。这份表就是决策依据落成文件的样子，第 13 课复盘反哺时它会持续变厚。

这五件不用你从零写，让 AI 生成初稿，但要分两段走，中间插一道人审边界。brain 五件套在课程仓 main 分支上，当前分支没有就先摘过来，用 §二的摘法。

```bash
git checkout main -- brain/
ls brain/
```

第一段，让 AI 只出清单，不写内容。

```plain
读 brain/ 下五个文件，学习它们的结构和字段。
给我列一张字段清单：每个文件要填哪些字段，哪些字段有确定的默认值，哪些必须采访我才能定，哪些可以留空。
先别写任何内容，只交清单。
```

你拿这张清单做一件事，划边界。哪些字段 AI 能直接定（比如格式、结构），哪些必须采访你（账号方向、目标人群、你能持续产出什么、你欣赏哪些账号），哪些先留空。这一步人说了算，AI 不许猜。

第二段，等边界划好，再让它采访并生成。

```plain
按我们划好的边界，逐一采访我：我的账号方向、目标人群、我能持续产出什么、我欣赏哪些账号。
按采访结果为我生成 brain/ 五件套初稿，结构对齐课程仓模板。
拿不准的字段写"待补充"，不要编造。
```

最后一句是硬约束。课程仓的 persona.md 里至今留着几个待办勾选框，固定开场白、结尾引导语，都标着待补充。空位留着等真实数据来填，比编一个像样的答案强。这些空位就是第 13 课复盘反哺的落点。

AI 在这步最容易犯的错，是把"待补充"的字段编上瞎猜的答案，或者照抄课程仓的定位当自己的定位。你划的那道人审边界，就是用来挡住这两种错。验收时逐字段过一遍，看到编造就打回，看到空位就留空。

**应看到什么**。五件套初稿成文，字段清单和你划的边界对齐，所有拿不准的地方写的是"待补充"。

## 六、写给 AI 看的人设文档

生成的初稿别急着收工，用一个标准过一遍。这份文档是给 AI 消费的，它和写给人看的人设文案是两回事。看课程仓 persona.md 里的写法。

```markdown
- 开口 3 秒给钩子（痛点、反常识、结论前置）。
- 一句话一个点，短句为主，口语优先。
- 别空喊"太强了""绝了"，说清强在哪。
```

三条全是可执行判据。"要有吸引力"这种话 AI 没法执行，"开口 3 秒给钩子"它能执行也能被检查。给 AI 的文档有三个要求。判据要能执行，AI 照着能做、做完能查；禁忌要具体到词，直接列出哪些词不能说；拿不准的字段留空位，标待补充，等真实数据来填。你手里的初稿按这三条改一轮，把形容词换成动作，把"大概这类内容"换成明确的支柱和配比。

这也是心法"关键结论落文档"的又一次落地，落点从一次对话的结论升级成了账号的长期决策依据。生命周期越长的文件，越值得写成机器可执行的样子。

**应看到什么**。你的 persona 里找不出一句"要有吸引力"这种空话，每条都是能被执行、能被检查的动作句。

## 七、dashboard 只是投影

骨架最后一块。账都分散在各条 meta.yaml 和 backlog.yaml 里，想看全局就得挨个翻，于是需要一张看板。课程仓 dashboard.md 的头部把自己的身份交代得清清楚楚，它自称"派生视图"，紧接着声明状态从各条 meta.yaml 汇总、选题池从 backlog.yaml 汇总。

第 3 课的真相源纪律在这里升级成系统级版本。meta.yaml 和 backlog.yaml 是真相源，dashboard 是投影，投影可以过期、可以重建，唯独不能反过来当账本改。有人在看板上手改一个状态，真相源没动，下次重建投影时改动消失，更坏的是消失前它还误导过所有看它的人。

AI 在这个环节最常犯的错，就是把手改 dashboard 当成记账。它为了让看板好看，直接在 dashboard.md 里把一个 status 改成 published，meta.yaml 里的字段纹丝不动。重建投影那一刻，这处改动消失，看板又和真相源一致了。所以给 AI 的规矩只有一条，dashboard 只读，改状态必须去动 meta 或 backlog。

![meta 与 backlog 真相源投射出只读 dashboard](imgs/lesson-05/03-scene-metaphor-dashboard-projection.png)

现在建你自己的 dashboard.md，头部照抄那句声明，正文先手工画一张在制表，把你那条已建档的内容填进去。手工同步很快就会让你厌烦，这正是下一课的引子。

最后把三处账串起来走一遍，看一次状态翻转怎么收口。先分清两类翻转。细粒度翻转，比如 drafting 到 review，只动 meta 一处，backlog 不镜像它。三处一起收口只发生在跨过发布这道边界的时候，以发布为例。

一条内容出审通过，meta.status 是 approved，选题池里对应条目是 picked，content_path 已指向这个目录。现在要发布，三处账要一起收口。

第一步，改 meta。status 从 approved 翻到 published，timestamps.published 记上时间，publish_url 回填作品链接。第二步，改 backlog。找到 source 指的那个条目，status 从 picked 翻到 published。第三步，重建 dashboard。重新生成投影，这条内容从在制表挪进已发布。

三处都动完，这一笔账才记完。漏掉任何一处，下一轮复盘或看板就会对不上。今天这三处靠你手改、靠自觉，改 meta 还要记得同步 backlog 和 dashboard，这正是下一课要解决的痛点。

**应看到什么**。你的 dashboard.md 头部有"派生视图"这句声明，正文有一张在制表，里面列着那条已建档的内容；你能不看笔记口述发布时三处账的收口顺序。

**几个判断带走**。主判断一条，先立账，再开工，每件在制品处于哪道工序，账上一查便知。三句支撑，阶段是字段，内容终身住一个目录；库存进 backlog，在制进 meta，两本账不镜像；dashboard 是投影，能重建，不能改。

留一个问题收尾。账本结构立好了，但每次状态翻转都要人手改 yaml，改 meta 还要记得同步 backlog 和 dashboard，三处账靠自觉。下一课先做一个实验，把记账交给 AI 自觉完成，看它怎么漏，然后用这门课第一次完整的 SDD，让 AI 造出一个替你记账的命令行工具。
