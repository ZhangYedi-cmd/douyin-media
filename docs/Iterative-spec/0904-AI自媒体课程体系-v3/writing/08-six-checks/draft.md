# 造六个检测脚本：把检查点表钉成能跑的契约

六个脚本要不要自动下 PASS 或者 FAIL，不是写代码那一刻才知道的。它能不能被写成一句断言，上一课分类的时候就已经定了。这一课要做的，是把这条已经定好的界线，变成六个能跑的脚本。

上一课把配音质检拆成了一张六行四列的检查点表：出错点、量什么、怎么量、阈值、谁来判。六项里，真相源不同步、合成不全、段内死气这三项归机器判，语速离群、多音字读错、组件大字与口播不一致这三项归人判。表定完，上一课结尾留了一句话，你手上的表还只是表：“下一课把这六项逐条造成脚本。表还只是表，怎么变成能跑出数字的脚本？”

这一课的输入正是这张表，加上你自己第 05、06 课做出的那条内容的 `build/` 工程：分段文案 `audio-segments.json`，逐段配音 `public/audio/<chapter>/<step>.mp3`。产出一件东西：一个全量的 `dubbing-check` skill，六个检测脚本，一个去停顿的 `depause.mjs`，一份把它们串起来的 `SKILL.md`。这一课你不写一行代码，六个脚本和 `depause.mjs` 全部由 AI 产出，你只定契约、审结果、判要不要重来。

## 1. 六个脚本的共同契约：先定形状，再动手写

一个检查能不能自动判 PASS 或者 FAIL，取决于它测的那个东西本身有没有唯一对错。真相源不同步、合成不全、段内死气这三项，判法是文本对不对得上、文件在不在、静音超没超过阈值，答案只有一个，符合条件就是有问题，不符合就没问题，不需要人代入语境。语速离群、多音字读错、组件大字与口播不一致这三项，能测到数，但数字本身不能直接下结论：语速慢半拍可能是这段本来就该慢；多音字候选列出来了，具体该读哪个音要看上下文；组件里的大字和口播对不上，也要看它们在画面上是并列的关键词标签还是逐字复述的整句。这三项检查该做的事是把候选摆出来，不该做的事是替人拍板。

这条线不是写脚本时现拍的。它是上一课已经定好的三条判据（能写成断言、只能靠人看、现在写不了）里的前两类，六项检查点全部落在这两类，第三类现在没有对应的项。六个脚本刚好把前两类都覆盖：三个判 PASS/FAIL，三个只报候选。

契约要写死三件事：输入统一、输出统一、退出码分两类。这三条先用一条 Prompt 定出来，再套进每一个脚本，脚本自己不用再想一遍。

### 1.1 输入统一：都读 build/ 里的 audio-segments.json，用同一个工程目录参数

六个脚本要拼出配音文件的路径，都得先知道 `build/` 在哪。让每个脚本各自约定一套参数名，是给后面的裁判（下一课要造的角色）添麻烦，它得记住六份不同的调用方式。契约把这条钉死：脚本接受一个位置参数，指向那条内容的工程目录，缺省用当前目录；脚本内部先读这个目录下的 `audio-segments.json`，再按它给出的 `chapter` 和 `step` 拼出 `public/audio/<chapter>/<step>.mp3` 的路径。这份文件里的每一段记录一条 `chapter`、一个 `step` 编号和对应的口播文本，是六个脚本共用的分段索引。

### 1.2 输出统一：每段一行 `✗`/`✓`，末尾一句汇总结论

裁判要在一堆输出里快速找到出问题的段，最快的办法是让每个脚本都按同一种格式说话：有问题的段打一行，问题类型加段号；没问题的段不单独打印，省得刷屏；跑完打一句汇总，写清楚这一批一共查了多少段、有多少段有问题。这条格式统一之后，裁判读六份输出不用先弄懂六种不同的排版，直接扫有没有 `✗` 就知道要不要往下看。

### 1.3 退出码分两类：完整性、死气、真相源同步判 FAIL 直接 exit 1；语速离群、多音字、音画一致只列候选，恒 exit 0

退出码是脚本和外面世界唯一的握手信号。硬门槛类判完直接给结论，退出码就该带着这个结论走：有问题 `exit 1`，没问题 `exit 0`，下一课的裁判可以直接看退出码知道要不要拦。候选类连它自己都判不了对错，退出码要是也来一个 `exit 1`，等于让脚本冒充了裁判的角色，裁判反而分不清这条 FAIL 是真出了事还是只是列了几条建议。候选类脚本恒定 `exit 0`，它的产出价值全在打印出来的候选清单里，不在退出码里。

契约的这三条定完，就该让 AI 把它落成一张表，脚本名对应哪个检查点、属于哪一类、退出码怎么定，全部摆出来，方便后面照着表批量写。

```
给这六项检查点定一份共同契约：都接受同一个"工程目录"参数，都读 audio-segments.json，
输出格式都是「每段一行结果 + 末尾一句汇总」；六项里，完整性、死气、真相源同步这三项属于能
写成断言的硬门槛，退出码按有问题 exit 1、无问题 exit 0；语速离群、多音字、音画一致这三项
只能列候选给人判断，脚本只打印风险点，不设 exit 1，退出码恒为 0。按这份契约写出一张六行表，
每行：脚本名 / 检查点 / 属于哪一类 / 退出码策略。
```

AI 交回来的表大致是这个样子：

| 脚本名 | 检查点 | 类别 | 退出码策略 |
|---|---|---|---|
| check-source-sync.mjs | 真相源不同步 | 硬门槛 | 有问题 exit 1，无问题 exit 0 |
| check-completeness.mjs | 合成不全 | 硬门槛 | 有问题 exit 1，无问题 exit 0 |
| check-silence.mjs | 段内死气 | 硬门槛 | 有问题 exit 1，无问题 exit 0 |
| check-pace.mjs | 语速离群 | 候选 | 恒 exit 0，只列风险点 |
| check-pronunciation.mjs | 多音字读错 | 候选 | 恒 exit 0，只列候选 |
| check-av-consistency.mjs | 组件大字与口播不一致 | 候选 | 恒 exit 0，只列候选 |

拿回这张表要审两件事。第一，类别栏和上一课检查点表里机器判、人判两栏对不对得上，六行里三行硬门槛、三行候选，数目不对多半是 AI 把语速离群这类只能测到数、测不出对错的一项，也塞进了硬门槛，改回来。第二，脚本名和检查点是不是一一对应，别出现一个脚本名对两个检查点，或者一个检查点没脚本接的情况。这张表定完，六个脚本谁先写、剩下的怎么批量出，需要一个样板。

## 2. 造一个样板，照样板批量复制剩下五个

六个脚本结构同构，不该写六条 Prompt 一个个造。契约已经把输入、输出、退出码全钉死了，脚本之间真正不同的只有中间那一小段判断逻辑：读到的段该怎么判有没有问题。这件事只要交给 AI 做一次，剩下五个照着样板复制，一条 Prompt 就能批量出。写六条 Prompt 一个个单独造，是没用上契约已经定死这件事，Prompt 数量跟着脚本数量线性增长，白费力气。

### 2.1 挑一个硬门槛类先造样板：完整性检查最简单

三个硬门槛里，完整性检查逻辑最短：文件存不存在、字节数是不是接近零、时长是不是大于零、段数跟 `audio-segments.json` 记录的条数对不对得上，四条判完就出结论，不需要额外的外部工具，也不用像死气检查那样调 ffmpeg 的 silencedetect 滤镜。挑这个当样板，AI 能一次把契约的三条落成一份可读的实现，后面复制其余五个时改的只是判断逻辑那一小段，输入怎么拿、输出怎么打、退出码怎么给这三件事照抄。

```
按上一步的契约表，写 check-completeness.mjs：读 audio-segments.json，
逐段检查 public/audio/<chapter>/<step>.mp3 是否存在、非 0 字节、时长 > 0，段数与
audio-segments.json 一致；不一致的每段打印一行，末尾汇总，属于硬门槛，有问题 exit 1。
```

AI 交回来的骨架大致是这个样子：逐段核对文件，缺失或时长异常的打一行 `✗`，最后按有没有坏段决定退出码。

```javascript
for (const s of segs) {
  const mp3 = join(PRES, "public", "audio", s.chapter, `${s.step}.mp3`);
  if (!existsSync(mp3)) { console.log(`✗ 缺失 ${s.chapter}/${s.step}`); bad++; continue; }
  const dur = ffprobeDuration(mp3);
  if (!dur || dur < 0.3) { console.log(`✗ 时长异常 ${s.chapter}/${s.step} (${dur}s)`); bad++; }
}
console.log(bad ? `✗ ${bad} 段有问题` : `✓ 全部 ${segs.length} 段完整`);
process.exit(bad ? 1 : 0);
```

拿回这份脚本先跑一遍，审三点：跑出来的段数是不是等于 `audio-segments.json` 里的条数，不等多半是路径拼错了，`chapter` 和 `step` 两个字段的取值没对上文件名；退出码是不是真的会在有问题时变成 1，故意改一段文件名制造缺失，跑一遍看退出码；打印格式是不是每段一行、末尾一句汇总，跟契约表里定的一致。这三点都过了，样板才算立住，剩下五个照它复制。

### 2.2 照样板批量复制剩下五个，含 depause.mjs

样板立住之后，剩下五个脚本和一个去停顿工具，一条 Prompt 一起交出去。真相源同步、死气检查这两个硬门槛，判断逻辑分别是逐段比对分段文案和源文案是否一致、用 ffmpeg 的 silencedetect 滤镜扫段内静音是否超过阈值；语速离群、多音字读错、音画一致这三个候选类，判断逻辑分别是算纯发音语速标出偏离整体的段、扫多音字候选列出上下文、把组件里的中文长句和对应段口播原文并排列出来。这五份判断逻辑跟契约的输入输出退出码规则拼起来，AI 一次就能写完。

```
照 check-completeness.mjs 的结构，按契约表剩下五行，依次写出
check-silence.mjs（死气检查，硬门槛）、check-source-sync.mjs（真相源同步，硬门槛）、
check-pace.mjs（语速离群，候选类）、check-pronunciation.mjs（多音字，候选类）、
check-av-consistency.mjs（音画一致，候选类），以及 rec/depause.mjs（去停顿工具，按
"去停顿不切词、不能原地写、跑完必须复扫"三条约束实现）。
```

前五个脚本审的方式跟样板一样：跑一遍看退出码和输出格式对不对得上契约。`depause.mjs` 不一样，它不是检查脚本，是改文件的工具，审的重点从退出码换成了三条约束有没有真的落进实现里：

```
depause.mjs 的参数契约不锁死具体命令行格式，由你交给 AI 的 Prompt 自己定，但下面三条
不能少：
1. 只切静音区中段，不切词——保留静音两端各留一点呼吸空间。
2. 绝不原地写——输入输出是同一个文件名时，ffmpeg 会截断输入且静默成功，改完的文件
   反而变短或损坏；正确做法是写到临时文件，改完再移动覆盖原文件。
3. 跑完必须用 silencedetect 复扫，验证违规数是不是真的降到了 0，不能只看命令有没
   有报错。
```

这三条不是随便定的。原地写这一条踩过真实的坑：批量去停顿时如果直接把输出路径写成和输入一样，ffmpeg 打开输出文件的那一刻就把输入截断了，命令本身不会报错，17 段跑完看着一切正常，实际上死气一处没少，这个案例记在 `pipeline/lessons.md` 的 L16 里。不切词这一条防的是另一头：切得太狠会把停顿两侧的字尾也削掉，听起来像被剪辑过。复扫这一条防的是光信任退出码：`process.exit` 只能证明脚本自己没崩，证明不了它真的把静音压下去了，复扫用的是跟死气检查同一把尺子，跑完还有段落超阈值，说明改动没生效或者改错了文件。

依着这三条约束把参数契约交给 AI 自己定，不代表随便写。跑完 `depause.mjs` 之后如果发现某一段的时长和之前一模一样，多半是脚本按输入等于输出的方式原地写了，改法是回到第二条约束，确认它写的是临时文件再覆盖。跑完之后复扫仍然报违规，多半是压缩幅度定得太小，静音区间只压到了阈值边缘，没真正压过去，让 AI 把压缩后的目标时长调低一点，重新跑一遍。

六个脚本加上 `depause.mjs` 现在都能跑了，但它们各自为政，还没打包成一个可复用的整体。

## 3. 打包成 skill：一份 SKILL.md 把脚本变成检查清单

脚本单独能跑，不等于能被下一课的裁判直接拿去用。裁判要知道该按什么顺序跑、每项检查点对应哪个脚本、跑出的结果怎么读，这层说明书是 `SKILL.md` 的活，脚本自己不管这件事。参考流水线里 `.claude/skills/dubbing-check/SKILL.md` 那份文件按开工前、合成后、录屏前、录屏后四个时点组织了整条链，这是它自己踩坑攒出来的形状，不是你现在这份文件该照抄的模板；你这一课定案的六项检查点覆盖的是从配音合成完到录屏前这一段，按上一课的检查点表重新分组织，用不上参考文件里那四个时点。

六项检查点按跑的时机能分成三组。多音字读错这一项只看分段文案的文本，不需要 mp3 文件已经生成，放在合成前跑。真相源同步、合成不全、段内死气、语速离群这四项都要读实际生成的 mp3 文件，放在合成后跑；真相源同步排在最前面，文案对不上的时候，段全不全已经不重要了，全的也是一批旧文案。组件大字与口播不一致这一项对照的是网页演示里的视觉组件文件，跟音频文件没关系，放在录屏前的最后一次巡检里跑，避免录完屏才发现画面文案和口播对不上。

```
把六个脚本和 depause.mjs 整理成 dubbing-check 的 SKILL.md：按检查点编号列出每个
脚本对应哪个检查点、怎么调用、退出码怎么读；末尾给一条"一页流程"，按合成前/合成后/录屏前
的顺序把六项检查点串成一条能贴在工位上的清单。
```

拿回 `SKILL.md` 要核一件容易漏的事：语速离群和多音字读错这两项候选类，判完之后结论落在哪个文件里，`SKILL.md` 里必须写清楚。参考流水线里 `check-pace.mjs` 打印的提示信息写的是把结论记进 `rec/segment-overrides.json`，但这条课程从第 07 课起统一按 `pipeline/2-create.md` 步骤 3 和 `pipeline/lessons.md` 的说法走：改动记进 `build/` 内那份 `tts.config.json` 的 `overrides` 字段，不新建别的文件。这两处说法不一致，写 `SKILL.md` 的时候用课程统一的口径，别把参考流水线脚本里打印的提示原样抄进去。

`SKILL.md` 落盘之后，一个全量的 `dubbing-check` skill 就交付完成了：六个检测脚本，一个 `depause.mjs`，一份把它们串起来的 `SKILL.md`。

六项检查点从表变成了能跑的脚本，退出码按能断言、只能候选分成了两类，打包进了这一份 skill。脚本只负责吐数字和候选清单，PASS 还是 FAIL 现在还是你自己拍板：跑完六个脚本，硬门槛那三个报了 exit 1，你得自己去改；候选那三个列了风险点，你得自己看该不该管。下一课要把判断这件事从你手上交出去，换一个独立的裁判角色来接。六个脚本能出数字了，可下判断的还是你。让写稿的那个 AI 自己判自己的活，行不行？
