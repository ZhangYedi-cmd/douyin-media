# 立骨架：仓库、目录、契约

上一课交付了 `docs/00-toolchain.md` 和一份跑过的自检输出：十项工具，按来源分类整理，每项配安装命令、自检命令、期望输出。上一课结尾留了一句话：十项工具装齐、验证过了，但它们各自为政，没有一个仓库把它们串起来，选题模块不知道创作环节要什么，发布模块也不知道审核结果写在哪。

这一课的输入是你口述的目录切法，和已经装好的这批工具；产出四项内容：目录树、`CLAUDE.md`、`pipeline/` 下五份阶段契约骨架、`content/` 模板与 `backlog.yaml` 头部，合起来是一个能 `git init` 的骨架仓。

骨架搭得稳不稳，最后用一个标准来验证：让 AI 只读这几份文件，看它能否准确复述出整条流水线的运转逻辑。如果复述不出来或者理解有偏差，通常是因为骨架中的边界没有交代清楚，我们回过头把规则补齐就好。

## 一、目录树设计：六个目录各管什么

先说一种看着很整齐、实际会出问题的切法：按文件类型分。所有 md 放一个目录，所有 yaml 放一个目录，脚本再放一个目录。这样初建目录时很省事，但到了第一次跨阶段交接就会出问题：创作要读的语气规范和它写出来的口播稿，分到了两个目录，契约里写一条交接路径要跨两三层目录去索引。以后业务逻辑一旦调整，往往很难理清到底要改动多少处散落文件。

换一个判断标准：文件归入哪个目录，取决于它是流程哪一步产出、哪一步读取，不看后缀名。这样任何环节的输入输出边界变了，受影响的文件天然聚在一起，不用满仓库找。

按这个标准划分出六个目录，各自分工明确：

```
仓库根/
├── CLAUDE.md      # 全局总纲，AI 每次开工先读，不属于六目录之一
├── pipeline/      # 五份阶段契约 + 一份编排入口 + 一份踩坑登记簿
├── content/       # 一条内容一个目录，加三个下划线开头的公共子目录
├── brain/         # 账号的判断依据，第 04 课填内容
├── harness/       # 另一条线的产物，课程里统一称作治理线，只产出报告和变更提议，不产出内容，第 21 课才正式建立
├── tools/         # 自己造的命令行工具，第 12 课起才有
└── docs/          # 只读历史存档，规则文本不住这里
```

六目录职责对照表：

| 目录 | 装什么 | 谁来写 | 谁来读 |
|---|---|---|---|
| `pipeline/` | 五份阶段契约、一份编排入口 `daily-run.md`、一份踩坑登记簿 `lessons.md`（这一课先建成空文件） | 你 | AI 跑到哪一段读哪一份 |
| `content/` | 一条内容一个目录，加 `_template`（新建内容的底本）、`_backlog`（选题池）、`_research`（每次调研留的快照，这一课不用去动它）三个公共子目录 | 取题这一步建目录，创作往里写 | 下一段拿它当输入，人审时也读 |
| `brain/` | 定位、人设、风格、信息源、有效打法五份文件 | 你写，复盘只出提议，人点头才改 | 选题和创作两段读 |
| `harness/` | 治理任务的注册表和报告模板，只产报告和变更提议 | 后面课的产物 | 后面课的产物 |
| `tools/` | 自己造的命令行工具 `media`，管状态记账 | 后面课的产物 | 后面课的产物 |
| `docs/` | 只读历史存档，前两课那两份文件挪进来，落盘之后不再更新 | 你和 AI 落盘那天写 | 事后回查 |

`docs/` 是这张表里唯一一个不在流程线上的目录，它存放的是决策当时的设计快照，这条约束要写进 `CLAUDE.md`。`harness/` 和 `tools/` 现在建成空目录就够，等第 12、21 课有实际产物再填。

空目录会撞上一个具体的坑：git 只追踪文件，不追踪目录。`brain/`、`content/_backlog/`、`content/_research/` 现在都是空的，`git init` 之后它们不会进版本库。`git status` 显示目录已建但没提交，通常就是这个原因，各放一个空的 `.gitkeep` 文件就能留住结构。

目录建好后大多还是空的，AI 此时打开仓库，依然不知道该从哪一份文件开始读起。

## 二、CLAUDE.md：一张你自己填的规格表

`CLAUDE.md` 放在仓库根目录，Claude Code 每次开会话会把它读进上下文，这类文件官方叫项目记忆，作用是不用你每次手动重复讲一遍规则。全局读取会持续消耗上下文 Token。如果写了对实际任务没有约束力的泛化说明，每次开工都在无谓占用宝贵的上下文空间。比如“这是一个抖音内容自动化项目，采用模块化设计”这类套话，删去后对任何执行环节都没有影响，放在里面反而会分散关键指令的注意力。

这套流水线的 `CLAUDE.md` 分五节：系统一句话、开工前必读、内容红线、流程纪律、文档架构约定。这五节的准则一致：写进去的每一条规则，都必须能在实际执行中改变 AI 的动作；无法判定真伪的条目一律不写。内容红线最容易写虚，比如“内容要优质”就无法衡量；而不编造数据、技术结论可溯源、时效性内容标注来源与日期，这三条可以明确判定，去核对事实就能见分晓。

这份文件很难直接照搬别人的现成范例。不同账号的内容支柱怎么划分、遇到什么情况必须重做、哪些关键节点必须由人工把关，这些判断因账号而异。直接引用其他项目的规则，AI 执行时带入的就是别人的逻辑。因此我们准备了一张规格表，带你按项梳理自己的专属规范。

规格表：五节各一行，回答什么问题、判据是什么。

| 节 | 这节回答什么问题 | 判据是什么 |
|---|---|---|
| 系统一句话 | 这套流水线由哪几条线组成，各自的终点在哪 | 每条线要能说出它停在哪一步 |
| 开工前必读 | 每次动手前必须读哪些文件 | 给出具体路径，写明这是硬约束不是参考 |
| 内容红线 | 什么情况直接重做 | 每一条都能判真假，不能写成程度词 |
| 流程纪律 | 哪些动作机器不能自己拍板 | 写死停在第几步，不写“注意把关”这类空话 |
| 文档架构约定 | 一条规则该写在哪、写几处 | 同一条规则只出现一次，其余位置写引用 |

把这张表口述给 AI，让它整理成文件：

```
我在搭一条内容自动化流水线的仓库，根目录要放一份 CLAUDE.md，
它是每次开工前必读的总纲，分五节：系统一句话、开工前必读、
内容红线、流程纪律、文档架构约定。
下面五段是我口述的内容，一段对一节：
<系统一句话：这套流水线由哪几条线组成，每条各自停在哪一步>
<开工前必读：动手前必须读的文件，逐条给路径>
<内容红线：什么情况必须重做，逐条列>
<流程纪律：哪些动作不能自己拍板，各自停在第几步>
<文档架构约定：一条规则该写在哪个文件，重复出现了怎么处理>
按这五节整理成 CLAUDE.md，一段对一节，不要合并也不要拆分。
每一条你判不出真假的，不要替我补成一句听着完整的话，
单独列在文末一节，写清是哪条、为什么判不出，等我改。
第三节和第四节里，我说了要重做或者要停但没说清楚具体条件的，
也列进同一节问我，不要自己猜一个条件补上。
```

拿到生成结果后，建议先翻看文末列出的待确认项。判不出真假的条目耐心逐条调整，如果一时定不准不妨先删去，只保留边界明确的规则。接着核对五节内容与上面的规格表是否一一对应。多出来的往往是具体的操作细节，把它们挪到阶段契约或对应的 skill 里，让总纲保持清爽专注。

如果 AI 在执行时反复确认已经交代过的事情，通常是因为那条规则界定模糊，它读完不知道按哪条执行。

流程纪律这一节，这套流水线写的是一句话：工作日全自动只跑到出审为止，发布必须人审通过。这句话和第 01 课的两处闸门对齐，但分工不同：总纲设定全流程的兜底边界，至于具体停在第几步、由谁触发，则在阶段契约里明确。后续哪怕往流水线里追加新动作，总纲这句话也能直接兜住，不用等新契约补齐才生效。

总纲填完，五节都有了明确界限。但流程纪律只框定了整体边界，具体到每个环节的输入文件、产出物以及在哪里暂停，还要依靠各阶段契约来清晰约定。

## 三、pipeline 五份阶段契约：骨架与审查点

契约与操作细节必须分开存放，因为两者的改动频率完全不在一个量级。配音换模型、录屏调参数，一个月可能要调好几次；而某个阶段的输入输出规范，半年都不用动一次。如果混在一份文件里，改一次参数就要动一次契约，日常调参本是常见操作，若每次微调都牵扯阶段契约并需要核对上下游，维护成本就会明显偏高。

因此阶段契约只写四项要素，具体操作步骤全部沉淀到 skill 中：

- 输入：该环节开工要读哪些文件，逐条给出路径。
- 输出：执行完毕后在磁盘留下什么，标明哪些必产、哪些按需产。
- 状态翻转：环节结束时内容状态如何流转，由哪条命令修改。
- 闸口：是否存在必须等待人工确认的节点，停在第几步，由谁审批。

这五份契约会反复引用一条尚未实现的命令：`media`。它是第 12 到 16 课要开发的命令行工具，负责取题和状态记账，当前阶段只是占位符。契约里先写上命令名不影响搭建骨架，但必须在旁边注明该命令暂未实现，现阶段靠手动修改 `content/<日期>/<slug>/meta.yaml` 过渡。若不加这句说明，AI 执行时会盲目调用该命令，报错后甚至会自行捏造一套状态值。合法状态值只在 `media flip --help` 中唯一定义，五份契约无需重复罗列。

这五份契约的篇幅差异很大：最长的创作契约 `pipeline/2-create.md` 当前约 85 行，最短的选题契约 `pipeline/1-ideate.md` 只有 22 行。契约精简是正常现象；如果篇幅过长，通常是不小心把具体操作步骤写进去了。

### 3.1 选题与取题：1-ideate.md

选题契约开头就写死一条纪律：执行细节全部收录在 `douyin-ideate` skill 中。抓取、打分、去重、清理的具体实现都不写进契约，避免双处维护导致规则脱节。契约本身仅保留四项要素。输入包含 `brain/` 中的定位、信息源、有效打法，以及现存的选题池 `backlog.yaml`。输出是入池的候选题、调研报告快照，以及 `dashboard.md` 的一行计数（该文件为流水线顺带更新的汇总表，本课无需手动创建）。状态流转依赖 `media backlog add`、`media backlog sweep`、`media promote` 等命令。闸口体现在取题优先级规则中，人工挑题本身就是一道卡点。

### 3.2 创作：2-create.md（含出审前终检闸）

创作契约篇幅最长，因为该阶段的分支最多：包含口播和图文两条路径，其中口播又分为网页制作、配音、审批、录屏、封面五步。骨架同样遵循四项要素。输入是 `1-brief.md` 以及 `brain/persona.md`、`brain/style-guide.md`。输出是成片与封面等媒体文件，加上出审前必须准备就绪的发布物料 `4-publish.md`。状态翻转与其他契约复用同一套记账机制。闸口设有两处，一处是配音审批，另一处是出审前的终检闸。

出审前终检闸这处卡点，源于一次真实的线上事故：早期一条内容出审时漏掉了 `4-publish.md`，人工在飞书点击通过后，紧接着的发布确认卡由于缺失标题当场报错，流程中断。这起教训记录在参考流水线的 `pipeline/lessons.md` 中，编号 L5；你当前把这个文件保持为空即可，后续踩坑后再行补充。这份物料虽然编号排在第 4、名为发布物料，容易让人联想成发布阶段的产物，但创作契约的终检闸明确规定：它必须由创作环节在出审前就准备齐全。

### 3.3 出审：3-review.md

出审契约最短，因为这一段本身动作单一：人在飞书点过或者打回。输入是待审的成片和封面，经通知类 skill 推一张审核卡。输出是一份审核记录，写清审核人、结论、修改意见。状态翻转由人的选择决定，过就往下走，打回就退回创作。闸口就是这一段本身，人不点头，流程不往前走。

### 3.4 发布：4-publish.md

发布契约掌管全流程唯一不可逆的操作，因此设置了双层闸口：先通过 dry-run 生成最终发布命令与物料，推送到终端做二次确认，人工确认后才执行真实发布。输入为创作环节产出的发布物料，契约明确规定此处只消费不生产，字段定义以创作契约的终检闸为准。输出为发布成功后的记账动作，一次性写全状态、时间与链接。这是全流程状态记账的唯一入口，其他环节不得代为变更。

### 3.5 编排入口：daily-run.md

`daily-run.md` 属于编排文件而非阶段契约，不适用前面四要素的固定模板。它记录的是当天的调度顺序：先取哪条选题、按什么优先级推进、执行到哪一步终止。若强行套用四要素结构反而写不完整，因为它与契约文件的定位截然不同，无需生搬硬套。

在编写契约时，明确不该写什么，和明确该写什么同样重要。生成契约前先对照三条删减标准。一是凡是重复其他文件已定规则的，一律改为路径引用。二是写成具体操作步骤的，全部移至对应 skill。三是列出全部状态值清单的直接删掉，只声明当前环节的状态流转区间，状态定义只保留一处。踩坑经历统一记录在 `pipeline/lessons.md`，当前文件保持为空即可，无需凭空捏造案例。契约中涉及对应规则时，只需标注编号反向关联。

```
我要写五份阶段契约，放在 pipeline/ 下，各自对应选题、创作、出审、发布，
再加一份不算契约的编排入口。前四份每份只写四件事：
输入（这一段开工要读哪些文件，给路径）、
输出（跑完在磁盘上留下什么，标必产还是按需）、
状态翻转（这一段结束时状态从什么变成什么，由哪条命令改，
命令还不存在的写"待造，现在靠手改 meta.yaml"）、
闸口（有没有必须停下来等人的地方，停在第几步，谁来点头）。
下面是我口述的四段：
<逐段口述：段名、输入、输出、状态怎么变、停不停>
编排入口那份只写当天的执行顺序，不套四件事的模板。
生成之前告诉我：这五份契约彼此之间有没有重复写同一条规则，
以及有没有和你刚帮我写的 CLAUDE.md 重复。
路径写我给过的原文，我没给的写"待定"，不要补一个看着合理的路径。
每份契约生成完，末尾单独列一节：这份文件里哪句话在别处也出现过。
```

拿到结果先看每份末尾那一节，重复项每一处挑一个位置留下，其余改成引用。留哪一处的标准只有一条：这条规则要改的时候，你只需要改一个地方。五份契约里若有哪一份罗列了完整的状态值清单，多数情况下是口述时把状态说成了一串名词，应改为只说明本阶段从什么状态变迁到什么状态。

契约讲清楚了段与段之间怎么交接文件，但交接的那些文件，比如 `1-brief.md`、`2-script.md`、`4-publish.md`，此刻在磁盘上一个都不存在。

## 四、content 模板与 backlog.yaml 头部：骨架与审查点

一条内容一个目录，路径是 `content/<日期>/<slug>/`。新建一条内容，就是把 `content/_template/` 整个复制过去。模板目录的核心是一份产物清单，明确各文件的生产方、产出时机与必要性。

`content/_template/` 骨架清单：

| 文件 | 谁产 / 何时产 | 必产吗 |
|---|---|---|
| `meta.yaml` | 取题这一步，目录建出来的同时 | 必产 |
| `1-brief.md` | 取题这一步，从选题池条目回填 | 必产 |
| `2-script.md` | 创作阶段，口播稿唯一真相源 | 必产 |
| `3-review.md` | 人审有意见要留时 | 按需，一次过审可以不建 |
| `4-publish.md` | 创作阶段，出审之前 | 必产（对齐阶段 2 的终检闸） |
| `5-retro.md` | 发布之后，治理线复盘时填 | 治理线负责的产物 |

这张表的每一行都要和第三节的契约对得上。`4-publish.md` 这一行最容易走偏，缘由前面讲过：编号排第 4、名字又叫发布物料，容易误以为是阶段 4 的产物，实际上创作契约的终检闸明确规定必须在出审前就绪。模板这一层如果照字面编号排产出时机，会和契约实际写的时机对不上，这条对齐要在生成模板骨架的时候一起核。

`assets/` 装的是成品媒体：封面小图和成片。封面这类小文件进版本库没问题。但成片是几十兆的视频文件，几个月就会撑大仓库，所以成片视频与创作时的临时工程目录（这里称作 `build/`）都不进版本库，只保留空目录结构。

每个内容目录下的 `meta.yaml` 是其状态的唯一依据，需要提前约定字段结构。包括短标识 `slug`、工作标题、类型（口播或图文）、`status`、选题来源、计划发布时间、发布链接，以及各状态的时间戳。状态只能记录在 `status` 字段中，切忌通过挪动目录位置来表示阶段。最典型的例子是审核打回：内容未通过时状态从 `review` 退回 `drafting`，目录路径保持不动；若用目录位置表达状态，一旦打回就得迁移目录，所有历史引用路径都会断裂。

选题池那一头，`content/_backlog/backlog.yaml` 是候选题的唯一真相来源，头部注释写在文件最上方，让每个改它的人先看见三件事：

- 这个文件管什么：所有候选题、状态、发布后回填的数据都在这一个文件里，不散到别处。
- 两层状态各管什么：池子管粗粒度三态 `idea`、`picked`、`published`，加上 `expired`、`rejected`、`archived` 三个异常态；内容目录的 `meta.yaml` 管细粒度状态，池子不镜像它。
- 取题指针：一个 `next_up` 字段，如果人工想指定下一条优先做什么，直接填入它的 id，取题完成后自动清空置回。这是人工介入的一种形式：事前指定好参数，人即使不在电脑前，流水线也能照常推进。

两层状态边界若不写清，当天就会发生状态冲突：同一条内容在选题池里仍显示 `idea`，内容目录的 `meta.yaml` 却已经成了 `drafting`。这通常是因为取题时只建了目录，漏掉了同步更新池子状态。分工写在头部注释中，维护者第一眼就能看清该改哪一层。

```
我要给两样东西定骨架：content/_template/ 六份文件（不含 assets），
以及 content/_backlog/backlog.yaml 的文件头部。
先看第三节生成的五份契约，把每份契约输出小节里提到的产物名字都摘出来，
标出哪些是 content 目录下的具体文件。
再按这份对照表生成 content/_template/ 骨架清单：
<逐份口述：文件名、谁产、什么时候产、必产还是按需>
然后生成 backlog.yaml 头部骨架，写清楚：这个文件管什么、
两层状态各管什么（粗粒度几态、细粒度几态、谁镜像谁）、
取题指针字段叫什么、由谁填、什么时候清空。
每一处生成完，标出这个文件名或字段名，在第三节的哪份契约里出现过；
契约里没提到过的名字单独列出来问我，不要自己造一个理由说它该在。
```

拿到结果只核一件事：清单里出现的每个文件名、字段名，能不能在第三节的契约输出小节里找到出处。找不到出处的，通常要么是契约漏写了这项产出，要么是模板里多列了非必要文件。遇到这两种情况，我们回到契约或模板中补齐对齐即可。

骨架仓的四部分结构至此搭建完成：目录树、`CLAUDE.md`、五份阶段契约、`content/` 模板与选题池头部。各模块的规则是否统一自洽，还需要做最终校验。

## 五、验证：让 AI 只读契约复述流程

验收动作是让 AI 只读你写的这几份契约，把流程复述出来。这条判据和第 01 课核端到端流程图时是同一套，换了输入：那时你手上只有口述，AI 复述的是你说的话；现在你手上有落成文件的契约，AI 复述的是文件写的话。复述结果和你的意图对不上，说明契约本身没交代清楚，跟 AI 理解力无关。

```
读 CLAUDE.md、pipeline/ 下的 daily-run.md 和五份阶段契约、
content/_template/ 全部文件、content/_backlog/backlog.yaml 的头部注释，
只读这些，不要推测文件里没写的事。
输出两部分内容。
一是汇总表格，一行对应一个阶段，共四列：阶段名、契约文件、输入文件、输出文件。
文件路径必须在所读文件中原样存在，找不到的填"契约未定义"。
二是人工卡点清单，列出所有需要停顿等待人工处理的节点，一行一条，
每条写清三项：处于哪一步、由什么触发、需要人工做什么决策。
仅列出明确要求暂停或发送通知的点，不输出状态名和状态迁移规则。
```

拿到结果核三点。

第一点，抽查表格中的文件路径，去仓库核实是否存在。如果契约中只写了模糊的目录，AI 容易自行推断出一条表面合理的虚构路径，仓库里其实根本找不到该文件。

第二点，核查人工卡点是否遗漏了异常阻塞场景。常见的漏洞是只列出了出审和确认发布两道常规闸门，漏掉了执行报错必须人工介入的情况。若出现遗漏，需回头检查编排文件 `daily-run.md` 中的“阻塞即上报”规则是否明确；如果写得过于偏向底层错误处理，AI 会将其当作代码实现细节忽略，而不视作流程暂停点。

第三点，凡是 AI 复述时补充得比契约还要详尽的地方，建议都对照原文核验一遍。它额外补充的部分，往往是契约原文中表述不够严谨的漏洞，顺带把这些盲区补齐，整套骨架会更加扎实。

这三点对应三条明确的验证标准：表格中的路径必须在已知文件中完全吻合；停顿等待的卡点数量与预期一致；表格中不得出现契约未提及的文件。三项核对均通过，骨架搭建才算达标。

对上了就 `git init`，把临时工程目录和媒体本体挡在版本库外面。

```
content/*/*/build/
content/*/*/assets/*.mp4
```

现在的仓库已经能够被 AI 准确理解：包含哪些流程阶段、各阶段输入输出是什么、在哪几个节点需要等待人工确认。骨架搭好了，AI 能够依据契约复述流程，但它还不清楚账号应当聚焦于什么领域、使用怎样的语气去表达。这些核心业务规则究竟该存放在哪里？
