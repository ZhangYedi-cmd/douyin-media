# 立骨架：仓库、目录、契约

上一课交付了 `docs/00-toolchain.md` 和一份全绿的自检输出：十件工具，每件一条安装命令、一条自检命令，跑完全部通过。工具装齐了，但它们互不认识。选题工具产出的调研结果，创作工具不知道去哪读；发布这一步，也查不到审核给的结论存在哪里。本课的输入是你口述的目录切法，和已经装好的这批工具；产出四件东西：目录树、`CLAUDE.md`、`pipeline/` 下五份阶段契约的骨架、`content/` 目录的模板与 `backlog.yaml` 头部，合起来是一个能 `git init` 的骨架仓。

骨架搭得对不对，最后靠一件事验证：AI 只读这几份文件，能不能把你的流程原样复述出来。复述不出来或者复述错了，说明骨架本身没写清楚，不是 AI 理解力不够。这条判据贯穿全课，最后一节会用它做验收。

## 1. 目录树设计：六个目录各管什么

先说一种看着很整齐、实际会出问题的切法：按文件类型分。所有 md 放一个目录，所有 yaml 放一个目录，脚本再放一个目录。这样建目录的时候很顺手，出问题的时机在第一次跨阶段交接：创作要读的语气规范和它写出来的口播稿，被分进两个目录，契约里写一条交接路径要跨两三层去指。想改一件事，你说不清要动几个地方。

换一个判断标准：一份东西住哪个目录，由它是流程里哪一段的产出、被哪一段读来决定，不看它的文件后缀。这样任何一段的输入输出边界改了，受影响的文件天然就聚在一起，不用满仓库找。

本仓按这个标准切成六个目录，各自只装一类东西：

```
仓库根/
├── CLAUDE.md      # 全局总纲，AI 每次开工先读，不属于六目录之一
├── pipeline/      # 五份阶段契约 + 一份编排入口 + 一份踩坑登记簿
├── content/       # 一条内容一个目录，加三个下划线开头的公共子目录
├── brain/         # 账号的判断依据，第 04 课填内容
├── harness/       # 另一条线，只产报告和变更提议，不产内容，第 21 课才立
├── tools/         # 自己造的命令行工具，第 12 课起才有
└── docs/          # 只读历史存档，规则文本不住这里
```

六目录职责对照表：

| 目录 | 装什么 | 谁来写 | 谁来读 |
|---|---|---|---|
| `pipeline/` | 五份阶段契约、一份编排入口 `daily-run.md`、一份踩坑登记簿 `lessons.md` | 你 | AI 跑到哪一段读哪一份 |
| `content/` | 一条内容一个目录，加 `_template`（新建内容的底本）、`_backlog`（选题池）、`_research`（调研快照）三个公共子目录 | 取题这一步建目录，创作往里写 | 下一段拿它当输入，人审时也读 |
| `brain/` | 定位、人设、风格、信息源、有效打法五份文件 | 你写，复盘只出提议，人点头才改 | 选题和创作两段读 |
| `harness/` | 治理任务的注册表和报告模板，只产报告和变更提议 | 后面课的产物 | 后面课的产物 |
| `tools/` | 自己造的命令行工具 `media`，管状态记账 | 后面课的产物 | 后面课的产物 |
| `docs/` | 只读历史存档，前两课那两份文件挪进来，落盘之后不再更新 | 你和 AI 落盘那天写 | 事后回查 |

`docs/` 是这张表里唯一一个不在流程线上的目录，它存的是当时怎么想的快照。这条约束要在建目录当天就写进 `CLAUDE.md`，理由下一节讲。`harness/` 和 `tools/` 现在建成空目录就够，等第 12、21 课有实际产物再填。

空目录会撞上一个具体的坑：git 只追踪文件，不追踪目录。`brain/`、`content/_backlog/`、`content/_research/` 现在都是空的，`git init` 之后它们不会进版本库。`git status` 显示目录已建但没提交，多半就是这个原因，各放一个空的 `.gitkeep` 文件就能留住结构。

目录建完还都是空的，AI 打开这个仓库不知道先读哪份。这件事要有一份文件说了算，下一节把它填出来。

## 2. CLAUDE.md：规格表而不是成品

`CLAUDE.md` 放在仓库根目录，Claude Code 每次开会话会把它读进上下文，这类文件官方叫项目记忆，作用是不用你每次手动重复讲一遍规则。每次都被读，这件事有代价：读了不改变任何一次执行的句子，你每次开工都在为它付一次读取成本。所以这份文件不该写成项目介绍。写一句这是一个抖音内容自动化项目，采用模块化设计，删掉它不影响任何一次执行，那就是白占位置。

本仓的 `CLAUDE.md` 分五节：系统一句话、干活前必读、内容红线、流程纪律、文档架构约定。这五节的判据都一样：写进去的每一条，要能在某次执行里改变 AI 的做法，判不出真假的条目不算数。内容红线那节最容易写虚，内容要优质这种话判不出真假；不编造数据、技术结论可溯源、时效性内容标注来源与日期，这三条判得出真假，出去核对一遍事实就知道对不对。

这份文件不是抄一份别人的现成范例就能用的。你的账号支柱怎么分、什么情况必须重做、哪些动作不能自己拍板，这些判断只有你自己给得出来，抄一份别的账号的 `CLAUDE.md`，AI 读出来的是别人的判断，不是你的。所以这一课不给你一份成品抄，给一张规格表，你自己填空。

规格表：五节各一行，回答什么问题、判据是什么。

| 节 | 这节回答什么问题 | 判据是什么 |
|---|---|---|
| 系统一句话 | 这套流水线由哪几条线组成，各自的终点在哪 | 每条线要能说出它停在哪一步 |
| 干活前必读 | 每次动手前必须读哪些文件 | 给出具体路径，写明这是硬约束不是参考 |
| 内容红线 | 什么情况直接重做 | 每一条都能判真假，不能写成程度词 |
| 流程纪律 | 哪些动作机器不能自己拍板 | 写死停在第几步，不写"注意把关"这类空话 |
| 文档架构约定 | 一条规则该写在哪、写几处 | 同一条规则只出现一次，其余位置写引用 |

把这张表口述给 AI，让它整理成文件：

```
我在搭一条内容自动化流水线的仓库，根目录要放一份 CLAUDE.md，
它是每次开工前必读的总纲，分五节：系统一句话、干活前必读、
内容红线、流程纪律、文档架构约定。
下面五段是我口述的内容，一段对一节：
<系统一句话：这套流水线由哪几条线组成，每条各自停在哪一步>
<干活前必读：动手前必须读的文件，逐条给路径>
<内容红线：什么情况必须重做，逐条列>
<流程纪律：哪些动作不能自己拍板，各自停在第几步>
<文档架构约定：一条规则该写在哪个文件，重复出现了怎么处理>
按这五节整理成 CLAUDE.md，一段对一节，不要合并也不要拆分。
每一条你判不出真假的，不要替我补成一句听着完整的话，
单独列在文末一节，写清是哪条、为什么判不出，等我改。
第三节和第四节里，我说了要重做或者要停但没说清楚具体条件的，
也列进同一节问我，不要自己猜一个条件补上。
```

拿到结果先看文末那一节，判不出真假的条目逐条改，改不动就删，不留一条你自己也说不清楚的规则。再核一遍五节和上面规格表能不能一一对上，多出来的内容多半是 AI 把某条规则的操作细节也写了进去，这些要挪到第 3 节讲的阶段契约或者对应 skill 里，不留在总纲里。

AI 干活时反复回来问同一件已经写过的事，多半是那一条判不出真假，它读完不知道该按哪条走。

流程纪律这一节，本仓写的是一句话：工作日全自动只跑到出审为止，发布必须人审通过。这句话和第 01 课那两处闸门讲的是同一件事，分工不一样：总纲这一句给全流程共同的边界，具体停在第几步、由谁触发，写在下一节要讲的阶段契约里。往流程里加一段新动作的时候，总纲这句已经把它罩住了，不用等新契约写完才有约束。

总纲填完，五节都能判真假了。每一段具体吃什么、吐什么，还没写。

## 3. pipeline 五份阶段契约：骨架与审查点

契约和操作细节要分开住，因为它们改动的频率差一个量级。配音换个模型、录屏调个参数，一个月能改好几次；选题这一段吃什么吐什么，半年不动一次。写在同一份文件里，改一次参数就要动一次契约，你每次都要回头确认另外四份和总纲还对不对得上，这个成本不该由参数改动来付。

所以一份阶段契约只写四件事，操作怎么做住 skill：

- **输入**：这一段开工要读哪些文件，逐条给路径。
- **输出**：跑完在磁盘上留下什么，哪些必产、哪些按需产。
- **状态翻转**：这一段结束时这条内容的状态从什么变成什么，由哪条命令改。
- **闸口**：有没有必须停下来等人的地方，停在第几步，由谁点头。

本仓这五份契约体量差得很大，最长的创作契约 `pipeline/2-create.md` 现在 85 行，最短的选题契约 `pipeline/1-ideate.md` 只有 22 行。契约短是常态，写得比这长很多，多半是把操作步骤也写了进去。

### 3.1 选题与取题：1-ideate.md

选题契约开头就写死一条纪律：执行细节全在 `douyin-ideate` 这个 skill 里，抓取、打分、去重、清扫的具体做法都不进契约，两处各写一份必然会有一天对不上。契约本身只留四件事的骨架：输入是 `brain/` 里的定位、信息源、有效打法，加现存的选题池 `backlog.yaml`；输出是候选题全部入池、一份调研报告快照、`dashboard.md` 里的一段计数；状态翻转经 `media backlog add`、`media backlog sweep`、`media promote` 这几条命令，具体状态值定义在别处，契约里不重复列；闸口写在取题优先级那句话里，人挑题这个动作本身就是一道闸。

### 3.2 创作：2-create.md（含出审前终检闸）

创作契约体量最大，因为这一段的分支最多：口播和图文两条路，口播那条又有做网页、配音、审批、录屏、封面五步。骨架照样是四件事：输入是 `1-brief.md` 和 `brain/persona.md`、`brain/style-guide.md`；输出是成片和封面这些媒体文件，加一份出审前必产的发布物料 `4-publish.md`；状态翻转和其余四份契约共用一套记账方式；闸口有两处，一处是配音审批，一处是出审前的终检闸。

出审前终检闸这处闸口，是从一次真实事故里定下来的：早期有一条内容出审时没产 `4-publish.md`，人在飞书点了通过，紧接着的确认发布卡当场报缺标题，发不出去。这份文件编号排第 4、名字又叫发布物料，很容易被理解成阶段 4 才产的东西，但它归创作这一段产，出审之前必须齐。这条教训现在写进创作契约的终检闸清单，回指一个编号方便查出处。

### 3.3 出审：3-review.md

出审契约最短，因为这一段本身动作单一：人在飞书点过或者打回。输入是待审的成片和封面，经通知类 skill 推一张审核卡；输出是一份审核记录，写清审核人、结论、修改意见；状态翻转由人的选择决定，过就往下走，打回就退回创作；闸口就是这一段本身，人不点头，流程不往前走。

### 3.4 发布：4-publish.md

发布契约管的是全流水线唯一一处真正不可逆的动作，所以闸口写了两层：先按 dry-run 拼出最终命令和物料，推回去做二次确认，人点确认之后才真发。输入是创作那段产出的发布物料，契约里明写这一份只消费不产，字段定义以创作契约的终检闸为准；输出是发布成功之后的一次记账动作，状态、时间、链接一次性写全，契约里也点明这是状态记账的唯一位置，别的环节不能代替它改状态。

### 3.5 编排入口：daily-run.md

`daily-run.md` 不算阶段契约，前面那把四件事的尺子不套在它身上。它写的是当天的执行顺序：先取哪条题、按什么优先级取、跑到哪一步为止，属于编排文件，不是某一段的输入输出说明。把它硬套进四件事的模板，会发现填不满，这恰好说明它和前面四份不是同一类东西，硬凑齐反而是错的。

五份契约里，写清楚哪些内容不该出现，和写清楚该出现什么内容同样重要。生成之前记住三条删除判据：复述了别的文件里已经写死的规则，改成一句引用；写成了具体操作步骤的，挪去对应的 skill；列出了状态值完整清单的，删掉，只留这一段从什么变到什么，具体值的定义只住一处。

本仓五份契约都在几处引用别的文件，不重复写规则。合法状态值只定义在一处，五份契约一律写一句"见 `media flip --help`"；`media` 是第 12 到 16 课要造的命令行工具，管取题和状态记账，现在它还只是一个名字。契约里先按名字指路不影响你现在把骨架写完，但要在旁边标一句这条命令现在还不存在，在那之前状态靠手改 `content/<日期>/<slug>/meta.yaml`，是临时做法。不标这一句，AI 跑到这一步会去试这条命令，试不到就自己编一套状态值出来。踩坑的故事只登记在 `pipeline/lessons.md`，契约里相关那条规则标一个编号回指过去，不把来龙去脉写进规则本身。

```
我要写五份阶段契约，放在 pipeline/ 下，各自对应选题、创作、出审、发布，
再加一份不算契约的编排入口。前四份每份只写四件事：
输入（这一段开工要读哪些文件，给路径）、
输出（跑完在磁盘上留下什么，标必产还是按需）、
状态翻转（这一段结束时状态从什么变成什么，由哪条命令改，
命令还不存在的写"待造，现在靠手改 meta.yaml"）、
闸口（有没有必须停下来等人的地方，停在第几步，谁来点头）。
下面是我口述的四段：
<逐段口述：段名、输入、输出、状态怎么变、停不停>
编排入口那份只写当天的执行顺序，不套四件事的模板。
生成之前告诉我：契约里出现了哪几处规则，在其它文件里已经写过一遍。
路径写我给过的原文，我没给的写"待定"，不要补一个看着合理的路径。
每份契约生成完，末尾单独列一节：这份文件里哪句话在别处也出现过。
```

拿到结果先看每份末尾那一节，重复项每一处挑一个位置留下，其余改成引用。留哪一处的标准只有一条：这条规则要改的时候，你只需要改一个地方。五份契约里如果哪一份带着一整段状态值列表，多半是口述的时候把状态说成了一串名词，改成只说这一段从什么变到什么。

契约讲的是段与段之间怎么交接。这些文件本身长什么样，还没定。

## 4. content 模板与 backlog.yaml 头部：骨架与审查点

一条内容一个目录，路径是 `content/<日期>/<slug>/`。新建一条内容，就是把 `content/_template/` 整个复制过去。模板里现成的东西是一张对照表：哪份文件谁产、什么时候产、是不是必产。

`content/_template/` 骨架清单：

| 文件 | 谁产 / 何时产 | 必产吗 |
|---|---|---|
| `meta.yaml` | 取题这一步，目录建出来的同时 | 必产 |
| `1-brief.md` | 取题这一步，从选题池条目回填 | 必产 |
| `2-script.md` | 创作阶段，口播稿唯一真相源 | 必产 |
| `3-review.md` | 人审有意见要留时 | 按需，一次过审可以不建 |
| `4-publish.md` | 创作阶段，出审之前 | 必产（对齐第 3 节的终检闸） |
| `5-retro.md` | 发布之后，治理线复盘时填 | 治理线负责的产物 |

这张表的每一行都要和第 3 节的契约对得上。`4-publish.md` 这一行最容易走偏：它排在第 4，名字又叫发布，照文件编号猜会以为它是阶段 4 才产的东西，实际上创作契约的终检闸写死它出审之前必须齐。模板这一层如果照字面编号排产出时机，会和契约实际写的时机对不上，这条对齐要在生成模板骨架的时候一起核。

`assets/` 装的是成品媒体：封面小图和成片。封面这类小文件进版本库没问题，成片是几十兆的视频文件，几个月就能把版本库撑大，这类大文件和创作时用的临时工程目录都不进 git，只留目录本身。

`meta.yaml` 是一条内容的状态真相源，字段先定下来才能让 AI 生成骨架：短标识 `slug`、工作标题、类型（口播或图文）、`status`、这条题的来源、计划发布时间、发布后回填的链接，再加一组时点，每个状态各记一个日期。状态只写在 `status` 这一个字段里，不靠目录位置表示阶段，理由在打回这件事上最明显：一条内容被人审打回，状态从 `review` 退回 `drafting`，目录一动不动；要是拿目录位置表示阶段，打回就得挪目录，所有指向它的路径全断。

选题池那一头，`content/_backlog/backlog.yaml` 是候选题的唯一真相来源，头部注释写在文件最上方，让每个改它的人先看见三件事：

- **这个文件管什么**：所有候选题、状态、发布后回填的数据都在这一个文件里，不散到别处。
- **两层状态各管什么**：池子管粗粒度三态 `idea`、`picked`、`published`，加上 `expired`、`rejected`、`archived` 三个异常态；内容目录的 `meta.yaml` 管细粒度状态，池子不镜像它。
- **取题指针**：一个 `next_up` 字段，人钦点下一条做哪个就填它的 id，取题之后置回空。这是人出现的一种位置，事前给条件，人不在场流水线照跑。

两层状态这一条不写清楚，当天就会撞上：同一条内容在池子里还写着 `idea`，内容目录的 `meta.yaml` 已经是 `drafting`。这种情况多半是取题那一步只建了目录，忘了回头翻池子的状态。分工写在头部，改它的人第一眼就看得见该改哪一层。

```
我要给两样东西定骨架：content/_template/ 六份文件（不含 assets），
以及 content/_backlog/backlog.yaml 的文件头部。
先看第 3 节生成的五份契约，把每份契约输出小节里提到的产物名字都摘出来，
标出哪些是 content 目录下的具体文件。
再按这份对照表生成 content/_template/ 骨架清单：
<逐份口述：文件名、谁产、什么时候产、必产还是按需>
然后生成 backlog.yaml 头部骨架，写清楚：这个文件管什么、
两层状态各管什么（粗粒度几态、细粒度几态、谁镜像谁）、
取题指针字段叫什么、由谁填、什么时候清空。
每一处生成完，标出这个文件名或字段名，在第 3 节的哪份契约里出现过；
契约里没提到过的名字单独列出来问我，不要自己造一个理由说它该在。
```

拿到结果只核一件事：清单里出现的每个文件名、字段名，能不能在第 3 节的契约输出小节里找到出处。找不到出处的，要么是契约漏写了这项产出，要么是这里凭空多造了一样东西，两种情况都要回头改，不能留着不管。

骨架仓的四件东西到这里都搭完了：目录树、`CLAUDE.md`、五份契约骨架、`content/` 模板和选题池头部。这些文件之间说的是不是同一件事，还没有验证过。

## 5. 验证：让 AI 只读契约复述流程

验收动作是让 AI 只读你写的这几份契约，把流程复述出来。这条判据和第 01 课核端到端流程图时是同一套，换了输入：那时你手上只有口述，AI 复述的是你说的话；现在你手上有落成文件的契约，AI 复述的是文件写的话。复述结果和你的意图对不上，说明契约本身没写清楚，不是 AI 理解错了。

00-ADR.md 里给这一段定的出口条件正是这一句：让 AI 只读契约复述流程，复述结果和你的意图对得上。

```
读 CLAUDE.md、pipeline/ 下的 daily-run.md 和五份阶段契约、
content/_template/ 全部文件，只读这些，不要推测文件里没写的事。
输出两样东西。
第一样是一张表，一行一个阶段，四列：阶段名、契约文件、输入文件、输出文件。
文件路径必须在读过的这些文件里原样出现过，找不到的格子写"契约里没写"。
第二样是一份清单，列出所有会停下来等人的位置，一条一行，
每条写清三件事：在哪一步、由什么触发、人要做什么决定。
只列这些文件里明确写了要停下来或者要通知人的位置，不要输出状态名和状态迁移规则。
```

拿到结果核三点。

第一点，表里的文件路径挑三条去仓库里查在不在。契约里提到一个目录名，很容易被补成一个看着合理的完整路径，实际那个文件根本不存在。

第二点，会停下来的位置有没有漏掉异常那一类。常见的结果是只列出了出审和确认发布两道闸，撞了墙要喊人的那几种没列进去。真出现这种情况，回头看编排文件 `daily-run.md` 里"阻塞即上报"那条纪律写得够不够清楚，写成了错误处理细节，AI 会把它当实现细节收走，不当成停顿点。

第三点，凡是它写得比契约还完整的地方，都回去对一遍原文。它补出来的部分，通常是你契约里没写清楚的地方，这些地方比这张表本身更值得回头改。

这三点各自落到一条能判真假的判据上：表里的路径要能在读过的那些文件里原样查到；会停下来的位置条数，和你自己心里数的那几处对得上；表里不出现任何契约没写过的文件名。三条都过了，这轮骨架才算搭对。

对上了就 `git init`，把临时工程目录和媒体本体挡在版本库外面。

```
content/*/*/build/
content/*/*/assets/*.mp4
```

这个仓库现在能被 AI 读懂了：流程分几段、每段吃什么吐什么、在哪儿停下来等人。它不知道的是内容本身：这条题该不该做、这段话该用什么口气说，这些判断眼下还只在你自己脑子里。骨架有了，AI 能读你的契约复述流程，可它不知道你的账号该做什么内容、用什么口气说话。这些判断依据写在哪？
