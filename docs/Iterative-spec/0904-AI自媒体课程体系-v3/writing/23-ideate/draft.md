# 选题池与外网情报：情报从外面来，反馈从复盘来

上一课把 `douyin-retro` skill 造出来了，采集、记账、产出三段各自能重复跑：登录复用第 20 课 `douyin-publish` 的方式，每拉到一个窗口的数据就调 `media metrics record` 记一笔，只有 7 天窗口才回填 `backlog.yaml` 对应条目的 `metrics` 字段。用附录脱敏样例或者真实播放数据跑出来的复盘报告也有了一份，按曝光到点击、点击到完播、完播到互动、互动到关注四道转化逐一比对基线。只归因第一个跌破基线的那一环。

复盘能把一条内容的成败归因，提议能改大脑。可选题池空了，拿什么内容去发？

复盘管的是已经发出去的内容，这一课管的是还没发的。抖音那边真实的观众偏好，只有复盘这一条来路能摸到，选题池自己会烂，得有一条线专门喂它，喂的料只能从外网抓，不能碰抖音平台本身。这就是这一课的记忆锚点：情报只从外网来，抖音那边的信号靠复盘反向补。

这一课的输入是 `brain/sources.md`（第 04 课填好的三层词表）、`brain/positioning.md`（第 04 课定的深度流量排产比例）、`content/_backlog/backlog.yaml`（头部到现在只写了三件事：文件管什么、两层状态、取题指针）。产出两样东西：一个 `douyin-ideate` skill，一批真实入池的候选。

## 1. 选题池的数据契约：为什么只入不出会烂

参考流水线自己撞过一次教训：backlog 里躺着 9 条 idea，一查创建日期，全都超过 24 天，内容早就过时了。原因很简单：选题池只往里加候选，从来没有一条规则把旧候选清出去，躺得越久，跟当下热点脱节得越厉害。

`idea`、`picked`、`published` 这三态解决的是一条候选走到哪一步这个问题，管不了它是不是还新鲜。一条深度选题躺半个月可能还能用，一条蹭着某个新模型发布的流量选题躺半个月，热度早就散了。要让池子不烂，得再加一层：过期规则，把该退场的候选自动挪出待选范围；候选之间还得能查重，不然同一个话题被重复抓进来两次，排序时占了两个位置，实际上只值一条。

你自己的 `backlog.yaml` 头部到现在只定了三件事：这个文件管什么、粗粒度状态和细粒度状态怎么分工、`next_up` 指针怎么用。第 03 课写的这三件事还是够用的，`idea`、`picked`、`published` 三态，加异常态，取题时人钦点 `next_up` 这个字段，这些都不用改。这一课要往里补的是候选本身该带哪些字段，尤其是打分和去重要用到的那几个，现在的头部注释里还一个都没写。参考流水线自己的候选字段长这个样子，本课按这个形状把你的 `backlog.yaml` 补齐：

| 字段 | 管什么 | 什么时候写 |
|---|---|---|
| status | 在 idea、picked、published 三态之外，加两个异常态：expired（过期清扫翻的）、archived（撞题合并或剔除后翻的） | 建候选时先是 idea，之后被清扫、被合并、被取用各自翻一次 |
| tags | 归一化的主题标签，30 天去重比对靠这一列 | 入池时打分那一步一起给 |
| scores、tier、score | 六维打分的原始分、分级、加权总分，第 3 节展开这套怎么定 | 入池时打分那一步一起给 |
| urgency | queue（可排队）还是 today（当天必发），决定过期清扫的宽限期长短 | 入池时判定 |
| metrics | 发布后回填的表现数据 | 第 22 课已经在用，7 天窗口的 `media metrics record` 会回填这一列 |

取题指针这一层不用动，第 03 课定的规则还成立：人钦点下一条要做哪个就填它的 id，`daily-run` 优先取它，取完置回空；不填的时候按 `score` 取最高分那条。这条链路现在缺的只是 `score` 这个字段本身还没人产出来，第 3 节把这个补上。

```
把上面这张表列的字段形状写进 content/_backlog/backlog.yaml 的头部
注释：候选未来会带 status（补两个异常态 expired、archived）、tags、
score/tier/scores、urgency、metrics 这几个新字段，每个字段写清楚它
管什么、大概什么时候会被写入。status 的两个异常态谁能自动翻、谁要
等人审，这条规则先不用写进注释，后面几节定了再补。改完贴出你写的
这段注释，不要连着候选样例数据一起生成，这一步只定字段形状。
```

拿到结果核两点：新加的字段有没有说清楚谁写、什么时候写，不能写成一句宽泛的记录打分信息；两个异常态有没有跟 idea、picked、published 三态混在一起变成一套六态并列，第 03 课定的两层规则是粗粒度三态加异常态，不是六态平铺。

如果 AI 补的注释把 backlog 的 status 说成会跟 content 目录 `meta.yaml` 的细粒度状态保持同步，多半是它没顾上第 03 课定的单一真相源规则：backlog 管粗粒度，`meta.yaml` 管细粒度，backlog 不镜像它。回头把这条规则读给它，让它删掉那句同步的说法。

数据契约定了，backlog 里现在还是空的，得有东西真正往里灌。

## 2. agent-reach 情报采集：只从外网来，不爬抖音

灌的料从哪儿来，这是第一个要拍板的事。

最省事的做法是让 AI 直接打开抖音网页，扒热搜榜、扒同类账号的评论区，这样看到的确实是平台第一手的偏好信号。这条路走不通：抖音主站反爬很重，headless 浏览器抓不到内容。换成能操作真实浏览器的工具也不行，得有人守在电脑前替它过验证码、点确认，这门课定的规矩是流水线要能无人值守跑。一步要人盯着，这条链路当场就断了，不是没本事抓，是这条路径本身进不了无人值守的流程。

情报只能往外走，抓 AI 圈的一手动态：X、Reddit、Hacker News、GitHub Trending、arxiv 这几条不用碰抖音本身的渠道。抖音这一侧真实的受众偏好，走另一条路补。一条内容发布之后，复盘从创作者中心把完播率、涨粉这些数据拉回来，归因写进变更提议，人审通过后回写 `brain/benchmarks.md`，下一轮打分才会用上这次的真实反馈。第 22 课已经把这条路走通了，这一课要做的是喂料这一头。外网抓的是这个圈子此刻有什么、为什么值得做，复盘补的是自己账号的观众到底吃不吃这一套。前者靠 `douyin-ideate` 每两天抓一轮，后者靠 `douyin-retro` 一条内容发布之后跑一轮，两条路各管各的，谁也替代不了谁。

agent-reach 第 02 课已经装好，`agent-reach doctor` 当时只验证过网页、YouTube、RSS 这三条不用登录的渠道，小红书、Twitter 这类要登录态的渠道留到真正用到选题调研的这一课再配，现在就是这一课。

```bash
agent-reach doctor
```

这条命令会把每个信息渠道的连通状态列出来，哪条还没通，跟着它给的提示逐条处理，不用自己去记每个渠道单独的配置步骤。X 和 Reddit 这两条选题真正要用，这次重点看这两条有没有变绿；Hacker News、GitHub、arxiv 本身就不用登录，这次应该是本来就通的。

Reddit 这条如果一直显示不可用，多半是缺了代理，读 Reddit 的帖子这一步本身就要走代理，光登录成功不够。

这几条渠道抓什么，靠 `brain/sources.md` 第 04 课已经填好的三层词表指路，不用重新定义。Layer A 是平台体裁词，判断这类内容在这个平台上以什么形式在火；Layer B 是深度域词，对应技术深度支柱的具体技术名词；Layer C 是流量信号词，追新闻和新模型热度，这一层半年后大概率要换一批。词表填好没有额外动作，`douyin-ideate` skill 会直接读它。

情报抓来了，怎么变成一份排好序的选题清单？

## 3. douyin-ideate skill 封装：双赛道打分与入池

同一条线索，该归深度赛道还是流量赛道？两条赛道该给几分？打完分谁先做谁后做？这几个问题落在一个 skill 里回答。

抓取引擎解决从哪儿弄到料这件事，两条赛道共用同一套；打分模型解决弄到的料该不该做、先做哪个这件事，两条赛道各自一套权重。前者不管内容深不深，只管抓没抓到；后者才真正决定这条候选值不值得进池子。

打分这套东西不是凭空定的。参考流水线借的是 Jonah Berger 那本《疯传》里提出的 STEPPS 模型：内容能不能被人转发出去，看社交货币、诱因、情绪、公开性、实用价值、故事这六件事。短视频这个媒介比文章多一层，用户会不会看到一半就划走，STEPPS 里没有这一项，所以参考流水线把六个维度重新配了一遍，不是照搬。你自己的账号打分维度要不要照抄这六个名字，看你账号内容形态跟参考流水线像不像，名字和权重都可以改。

深度题和流量题拼的不是一回事：深度题靠有没有用、看不看得完，流量题靠够不够新、够不够炸。参考流水线给深度赛道配的起步权重是实用 0.30、完播 0.25、社交 0.15、惊奇 0.15、时效 0.10、触发 0.05，流量赛道换成时效 0.30、惊奇 0.25、完播 0.20、实用 0.10、社交 0.10、触发 0.05。两条赛道权重加起来都是 1，只是权重最高的两项换了位置。这套权重跑过一轮之后改过一次：深度赛道的时效权重从 0.05 提到 0.10，因为旗舰产品发布这类深度实测题也得趁热做；流量赛道的实用权重同样从 0.05 提到 0.10，因为真正有用的实测反而是流量最好的一类。这两处改动是参考流水线自己试跑一轮之后调的，是起步值，不是钉死的规律，你自己账号跑几轮之后一样能改。

规格表填清楚这个 skill 要做的四件事：

| 环节 | 这一步做什么 | 判据是什么 |
|---|---|---|
| 打分 | 每条候选先判深度还是流量赛道，按对应赛道的权重打分 | 每个维度都要能说出 5 分长什么样，不能写成内容质量高这种判不了的词 |
| 形式判定 | 打完分顺手判口播还是图文 | 判不出来时深度默认口播，流量速览默认图文 |
| 产出报告 | 写成 `content/_research/research-<日期>.md` | 报告是排好序的清单，不是抓取记录的堆砌 |
| 入池 | 候选按字段契约写入 backlog.yaml | 经 `media backlog add`，撞车的候选默认拒收，规则第 4 节讲 |

把这张表口述给 AI，让它整理成 skill：

```
我要给仓库加一个 douyin-ideate skill，双赛道打分选题池：
采集这一步复用 brain/sources.md 的三层词表，agent-reach 抓 X、
Reddit、HN、GitHub Trending、arxiv 这几条渠道，不碰抖音平台本身。
打分这一步分深度、流量两条赛道，各配一套 6 维加权公式，维度自己
起名字、自己定 5 分长什么样，不要照抄任何示例的名字，权重两条赛
道分别要解释为什么这么配。深度流量最终混排比例，从 brain/
positioning.md 里我自己定的那个排产数字来读，不要自己编一个。
形式判定按打分结果顺手给，判不出来时深度默认口播、流量默认图文。
产出两份东西：research/research-<日期>.md 调研报告快照，和写入
backlog.yaml 的候选字段（按我们第 1 节定的字段形状）。
入池经 media backlog add，撞车的候选按它自己的规则处理，你不用
自己另外实现一套去重。
按这几段整理成 SKILL.md，打分公式单独拆一份 references/scoring.md，
报告格式单独拆一份 references/report.md。
```

候选整理成文件之后，入池是一条命令的事：

```bash
media backlog add content/_research/candidates-2026-09-04.yaml
```

```
已入池 6 条，拒收 1 条
  + 2026-09-04-004 xxx
  x #3 xxx（撞 2026-08-20-002，共享标签 claude-code,agent）
```

审三点：六个维度是不是各自能问出一个能打分的问题，判不了的词要打回去重写；两条赛道的权重加起来是不是都等于 1；混排比例有没有真的去读 `positioning.md` 里你自己定的那个数字，不是随手编一个比例。

如果 AI 给两条赛道配的权重看着不一样，其实换算下来是同一套排序，比如只是把两个数字对调了个位置但没解释为什么，多半是它没有真的想清楚深度题和流量题背后各自靠什么赢。让它逐条讲清楚每个维度权重为什么这么定，讲不出来的维度权重打回去重定。

候选入池了，重复题和过期题怎么防？

## 4. 去重与清扫：撞题不进池，过期就退池

第 21 课那次真实的 `backlog-gardener` 报告扫过 14 条候选，两两核对标签，查出两组标签有重叠。一组是标题、链接都指向同一件事，但两条候选各自写明了错峰发布的理由，不是重复；另一组标签只有一个重合，展开看角度并不相同，是标签体系不够细导致的假重叠。两组最后都没有被判定成撞题，报告只是把重叠的地方挑出来，判不判撞题这件事本身还是交给了人。

这个例子正好把这一课要划的边界摆出来：查出候选之间标签有没有重叠，这件事机器能自己干，交集算出来是多少不需要判断；这两条到底算不算同一个话题、该留哪条该并哪条，这件事得看内容，是判断，得停下来等人。

| 动作 | 触发命令 | 能不能自动 |
|---|---|---|
| 新候选入池去重 | `media backlog add` | 能，标签交集大于等于 2，或者标题子串加链接完全重合，直接拒收 |
| 过期清扫 | `media backlog sweep --apply` | 能，urgency 是 today 的候选超 2 天、六维打分里时效分大于等于 4 的候选超 7 天，自动翻成 expired |
| 撞题合并或剔除 | `media backlog apply` | 不能，先出一份变更提议报告，人审通过才落地，这条命令只作用于还是 idea 状态的条目 |

前两条能自动，不是因为它们不重要，是因为规则本身已经被人看过一遍：标签交集算两个的阈值、过期清扫两天和七天的窗口，这些数字写进命令的时候就是人拍板的，命令跑的时候只是照章执行，不产生新判断。

第三条不一样，两条候选算不算真撞车，得看它们的内容差异有多大。第 21 课那次 14 条候选里两组标签重叠最后都没判撞题，靠的是人把内容摊开看了一遍，这种判断现在还没法交给机器做。第 21 课定的资产读写表已经把这条边界写死了，这一课延续这条规矩，不重新讨论。

清扫先看一遍再真落盘：

```bash
media backlog sweep
media backlog sweep --apply
```

```
（dry-run）命中 3 条
  2026-08-10-002  today>2d  xxx
  2026-08-05-001  timeliness4>7d  xxx
```

不加 `--apply` 缺省就是预演，只报会清扫掉哪几条，不改文件；确认这几条确实该清，再加 `--apply` 真落盘，状态行后面会追加一条注释留痕，写明是哪条规则清的，不是人手动改的。

如果两条内容型很接近的候选，`media backlog add` 却都放行了，一条都没被拒收，多半是 tags 写法没有归一化，同一个概念一条写 Claude Code，另一条写 claude-code，去重比对的是精确字符串交集，大小写和连字符不统一，交集永远算不出 2，去重就形同虚设。整理 tags 的时候统一成一套写法，这条规则值得写进 douyin-ideate skill 自己的注意事项里。

治理线现在有几个任务分头跑？

## 5. 选题池养起来之后

一个能抓料、打分、入池、清扫的 douyin-ideate skill 有了，情报从外网来，抖音那边的真实反馈靠复盘反向补，这条边界这一课定死了。一批真实入池的候选也有了，backlog.yaml 不再是空的。

治理线现在只有复盘和选题两个任务真正跑通过，其余几个还只是名字，没有真正跑起来过。

选题池能自己养起来了。四个治理任务各跑各的，谁来决定今天该跑哪几个？
