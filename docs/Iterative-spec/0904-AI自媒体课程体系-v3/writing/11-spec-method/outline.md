大纲照任务卡 `plan/cards/11.md` 的「2.1 大纲」块展开，节的数目、顺序、每节的核心判断与交付物均不改。局部调整只有两处，均为落笔层面的展开，不改变判据或交付物本身：

1. 卡片第 2 节"调研"与第 4 节"决策"分别写着"学员此时手上有……第 08 课那六个检测脚本，作为回看素材"和"用第 08 课六个检测脚本回看举一条例子"，据此把第 2-7 节（调研到验证）都串在同一个贯穿例子上——回看第 8 课"六个检测脚本要不要合并成一个大脚本"这个当初没被摆上台面的互斥选型点，逐步走一遍六步。第 8 节收口时再整体回看，避免每节各配一个孤立小例子导致读者要来回切换上下文。
2. 卡片没有明确"docs/spec/ 目录约定"这件交付物落在哪一节，本大纲把它放进第 1 节结尾，作为进入六步之前先定好"文件落在哪"，避免六步过程中每次讲到模板都要重新交代目录问题。

记忆锚点：六步方法的分量都压在"讨论选型"这一步——不逼 AI 给每个方案当一次辩护人，前面摆再多候选也是陪衬。

开篇契约：按第 10 课成稿实际写法复述——上一课交付了一次真实的 FAIL 到修到重合成到 PASS 的完整过程记录，自愈回路合上了，同时留下一堆手改的 `meta.yaml`；本课输入是十课攒下来的全部经验，尤其第 10 课那次真实的自愈过程；本课产出两件东西：一份 `docs/spec/` 目录约定，和六步方法的四件套模板（调研 / ADR / 执行方案 / 施工记录）。

## 1. 从一条 prompt 到大件：什么时候要换挡
核心判断: 能不能把一件事直接交给一条 prompt，看的是有没有互斥路线、错了返工贵不贵，不看代码行数或字数。
支撑材料: 第 10 课结尾的手改 meta.yaml 遗留问题；ADR D3（教法分档不按行数）
交付物: 三条判据的清单（互斥路线 / 跨文件跨组件 / 决策要不要留痕）+ `docs/spec/` 目录约定
二级标题: none
收尾交接: 判据摆出来了，进入六步的第一步：调研。

## 2. 调研：把选型空间摊开
核心判断: 调研不是自由讨论，是让 AI 先列出互斥候选清单，人确认后逐个填进同一张表，表列必须固定。
支撑材料: 第 8 课六个检测脚本作为回看素材；调研节方案对比表固定列
交付物: 「先出候选清单」的 Prompt + 固定四列对比表（方案 / 适用前提 / 代价 / 已知失败模式），用「六个脚本要不要合并成一个大脚本」填一版
二级标题: 2.1 让 AI 先出候选清单，人确认再往下走 / 2.2 对比表怎么填
收尾交接: 候选摆齐了，但表里每个方案的优点都是 AI 自己写的，偏向性还没被逼出来，进入讨论选型。

## 3. 讨论选型：逼每个方案当自己的辩护人
核心判断: AI 列方案时会不自觉把自己想选的写得更饱满，讨论选型这一步单独存在，就是为了逼它给每个方案找活路。
支撑材料: ADR D4 理由原文；0818 一致性 Review 选项对比表写法
交付物: 辩护式 Prompt 模板（成立前提 / 代价 / 主动交代失败模式 / 不许下综合结论），套进六脚本例子跑一版
二级标题: none
收尾交接: 每个方案的弱点都被自己说出来了，可以拍板了，进入决策。

## 4. 决策：把选择钉成 ADR
核心判断: ADR 只记四件事，决策 / 理由 / 被否方案 / 反悔成本，多写别的就是在替执行方案抢戏。
支撑材料: 00-ADR.md 里 D1-D16 的写法；六脚本例子的辩护结论
交付物: ADR 模板（四项固定），用六脚本例子补一条"为什么不合并成一个大脚本"的 ADR
二级标题: none
收尾交接: 决策落了纸，但落纸的决策还变不成代码，中间差一份能让 AI 照着施工的规格，进入写 SPEC。

## 5. 写 SPEC：把决策展开成可施工的规格
核心判断: 执行方案只有四节，节名不许各课改写：实施步骤、命令（或接口/页面）× 功能 × 详细设计、对外契约、风险与待定项。
支撑材料: 0818 执行版总览末尾模板原文；01-CLI执行方案.md 实施步骤表写法
交付物: 执行方案四节模板原文（照抄），套进六脚本例子的"风险与待定项"一节，指出第 10 课真实撞见的 overrides 文件口径打架
二级标题: none
收尾交接: 规格能施工了，但纸面上的规格和真跑起来的东西之间还差一步，进入执行。

## 6. 执行：照 SPEC 交付里程碑
核心判断: 执行不是一次性把 SPEC 全部实现完，是切里程碑，每个里程碑一个能跑的出口条件。
支撑材料: 0818 CLI 执行方案 M1/M2 出口条件原文（反例「基本完成」，正例真实验证动作）
交付物: 里程碑出口条件写法，套进六脚本例子给一条真实形状的出口条件
二级标题: none
收尾交接: 里程碑出口条件写清楚了，但过了出口条件不等于东西是对的，进入验证。

## 7. 验证：一句能跑的验证动作收口
核心判断: 验证要验的是"写路径真的只有一条"这类容易自己以为对了的东西，光靠肉眼看代码不够，要留下可以回查的证据。
支撑材料: 0818 施工记录.md 的裁决台账写法
交付物: 施工记录模板（里程碑 / 出口条件 / 实际结果 / 卡在哪 / 怎么绕过去）
二级标题: none
收尾交接: 六步走完一轮了，回头拿这一课自己举的例子对一遍。

## 8. 回看六步：如果第 08 课走过这条路
核心判断: 六步方法定完了，用第 08 课六个检测脚本回看一遍，如果当初先调研、先讨论选型，会多出哪条 ADR、少踩哪个坑；六步只是纸上过了一遍，还没真正拿一件大事练手。
支撑材料: 第 10 课 overrides 文件口径打架的真实记录（反例）
交付物: 一份"多出什么、少踩什么"的对照收束
二级标题: none
收尾交接: 六步方法有了，拿第一件重活来练——状态写入口这件事，先走前三步：调研、讨论选型、拍板，一行代码都不写。
