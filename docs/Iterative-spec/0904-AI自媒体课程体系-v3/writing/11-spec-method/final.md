# SPEC 方法：从调研到验证的六步

上一课（第 10 课，自愈回路与三轮熔断）结尾留了一个待解的问题。自愈回路合上了，但前期手工修改了不少 meta.yaml。后续还有体量更大的系统组件要实现，包括状态中枢、飞书闸口、控制台。一条 prompt 已经无法承载这种体量的任务，需要建立规范的方法让 AI 协同完成。解决这个问题的关键在讨论选型这一步。前面的调研梳理候选方案、后面的决策沉淀 ADR 都相对明确。核心在于引导 AI 客观剖析推荐方案的失效场景。如果缺少这一步，列出再多候选方案也容易流于形式。

第 10 课交付的是一次真实的自愈过程。dubbing-reviewer 首轮判定 FAIL。随后按照问题类别逐项修改 tts.config.json 的 overrides，润色文案并消除停顿。重新合成音频后，第二轮判定 PASS。整个处置过程完整记录在对应的记录文件中。若三轮仍未通过，流程也有明确规定。meta.yaml 中不设专门的挂起状态，保持 status 为 drafting。同时补充一行说明注明卡在第几轮，严格遵守“阻塞即上报”的规则通知人工介入。这条回路能够顺利运行，前提在于问题规模刚好能收敛在一条 prompt 内。修改配置、微调脚本、去除停顿，均为单文件、单步骤的操作，出现问题重新执行即可。

本课要处理的是另一类场景：工程规模超出单条 prompt 的承载范围。例如后续将要开发的 media CLI、飞书审核闸口以及本地控制台。本课先不编写具体的工具代码，而是把整套工程规范与工作流定下来。输入来自前十课积累的实践经验，特别是第 10 课自愈过程总结的教训。产出两项规范。一是 docs/spec/ 目录约定，规定六步流程产物的存放位置。二是配套的四件套模板（调研、ADR、执行方案、施工记录），规定每个环节的具体格式。定好这两项规范后，后续核心模块均可直接沿用。无论是第 12 至 16 课开发 media CLI，还是第 18 至 19 课接入飞书闸口、第 26 至 28 课构建控制台，都不再需要反复确认格式。

## 一、从一条 prompt 到大件：什么时候要换挡

是否需要启动六步流程，关键看决策失误时推倒重来的代价，并不单纯取决于代码行数或文字描述的多寡。第 8 课的六个检测脚本总计两百余行代码。后续控制台中，单是负责解析进程输出的模块就有两百多行，而它仅是五个功能包中的一小部分。两者的核心差异在于决策的扩散面。后者的模块组织方式存在多条路线可选，一旦选型偏差，会直接波及后续多个包的接口形态。而前者在当时几乎没有分歧，六个检查点对应六个独立脚本是最直接的组织方式。

启动六步流程的判据具体拆解为三条。任何一条命中即应启动，不必三条全占。这三条判据用于判断是否需要执行完整的 SPEC 六步流程。这与第 6 课验证信号表中判断检查点能否写成断言的三条判据完全不同，阅读时应当加以区分：

- 路线选错是否存在推倒重来的高昂成本：失误后是只需局部调整，还是会牵连已写好的关联模块。
- 任务是否跨越多个文件或组件：仅在单个文件内完成的小改动，通常不存在真正互斥的技术路线。
- 决策是否需要形成文字留存给后续维护者：几个月后被问及选型依据若无法溯源，说明该决策最初就应当规范落档。

这三条判据的核心关注点一致：防止选型风险在后续开发中扩散放大。只要命中其中一条，就应当先在纸面上推演方案与边界，把潜在隐患排查在前，避免写完代码后再返工重写。

后续介绍的六个步骤，均以第 8 课的六个检测脚本当作案例。它的体量适中，试错代价小，可以在有限篇幅内把流程推演清晰。第 8 课当初的架构直觉很准确，这里借用该案例把六步规范的动作完整演练一遍。而后续需要重度推演的 media CLI、飞书闸口、控制台等模块，由于业务复杂度更高、决策影响面更广，留待后续专节逐步展开。

六步流程的各个关键阶段都需要产生对应的文档。这些文件的存放路径需要预先规范，避免编写中途路径混乱。约定如下：在 docs/ 下创建 spec/ 目录，其子目录按功能代号命名。一个模块代号对应四个按序编号的文件：

```
docs/spec/media/
├── 00-调研.md
├── 01-ADR.md
├── 02-执行方案.md
└── 03-施工记录.md
```

参考流水线采用日期加事项的方式命名，每次迭代另起一个日期目录。本课程对应的三个核心模块相对聚焦，分别采用 media、feishu-gate、console 三个代号目录即可，无需按日期滚动。当前仓库中若尚未创建 docs/spec/ 目录，按照本课规范直接新建即可。第 12 至 16 课的 media CLI 文档放在 docs/spec/media/ 目录。第 18 至 19 课的飞书闸口文档放在 docs/spec/feishu-gate/ 目录。第 26 至 28 课的控制台文档放在 docs/spec/console/ 目录。所有技术决策与实施方案都在统一目录结构下沉淀。

明确了启动判据与归档目录，接下来从第一步开始，先梳理出清晰的选型空间。

## 二、调研：列出候选方案并填对比表

调研环节切忌漫无边际地发散。若让 AI 随意列举可能性，讨论往往停留在表面而无法形成有效沉淀。调研阶段要踏实完成两项具体工作：首先要求 AI 将互斥的备选方案梳理成候选清单，由人工确认没有遗漏；确认无误后，再将各个方案逐一填入统一维度的对比表中。对比表的表头列必须保持固定，保证各模块调研文档在后续维护时口径一致。

### 2.1 让 AI 先出候选清单，人确认再往下走

先出候选清单这一步不能跳过。若直接让 AI 边构思边填表，它往往会详写自己倾向的方案，而对其他路线草草带过。这样生成的表格虽然看似完整，实际上缺乏公平对比。正确的做法是先单独索取一份纯粹的候选清单，经人工审阅确认无遗漏后，再进入填表环节。

第 8 课中的六个检测脚本采用了独立文件的方式编写。从定义契约、实现样板、批量复制到封装为 skill，整个过程十分顺畅。当时未曾停下来讨论是否合并为一个大脚本，实践证明选独立脚本是合理的。现在借这个案例补一次完整的调研推演，先把两条互斥的技术路线明确摆出：

```
我要给"六个配音检测点该怎么组织"这件事定一个方案。先不填表，只列出所有互斥的候选，
每个候选一句话说清楚它的核心思路，列完等我确认。
```

AI 给出的候选清单通常包含两项：方案一，六个独立脚本，每个检查点对应一个文件；方案二，一个集合脚本，内部按检查点划分子函数，一次执行跑完全部检测。人工核对确认备选方案完备后，再推进到对比表编写。

若 AI 只返回了一个候选方案，常见原因是提示词本身隐含了预设倾向。例如若提问“如何把六个脚本整合成一个”，AI 会顺着整合思路回答，忽略其他可行分支。此时应调整提问，去除诱导性字眼，重新获取无偏倾向的候选。

### 2.2 对比表怎么填：方案、适用前提、代价、已知失败模式

调研对比表固定包含四列：方案、适用前提、代价、已知失败模式。适用前提说明该方案在何种场景下成立，代价说明采用该方案所需付出的额外成本，已知失败模式说明该方案在何种边界条件下会出问题。这三列信息为下一步的讨论选型提供了基础素材，调研阶段先梳理初版，选型讨论时再深入推敲。

以六个检测脚本为例，对比表梳理如下：

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 六个独立脚本 | 检查点之间输出格式和退出码策略不同，硬门槛判 PASS 或 FAIL，候选类只列风险点 | 六份文件要维护同一套输入解析逻辑，容易在细节上跑偏 | 六个脚本各自实现输入解析，漏改一处会导致某个脚本单独读错路径 |
| 一个大脚本，按检查点分函数 | 六项检查逻辑高度相似，想复用一份入口代码 | 改一处检查点的判断逻辑，理论上不该影响别处，但都在同一个文件里，回归测试的范围不好收窄 | 硬门槛和候选类的退出码语义混在一次进程返回值里，裁判读结果时分不清是硬失败还是候选提示 |

对比表填写完成后，两个方案看起来各有千秋。方案一的维护代价和方案二的语义冲突还停留在推测层面。此时调研阶段应当在此收口，更深层次的优劣权衡交由讨论选型环节进一步验证。

## 三、讨论选型：让每个方案自己当辩护人

调研对比表中展示的势均力敌往往只停留在表面。AI 在罗列方案时，通常会对排在首位或自身更偏好的路线展开更充分的论述，而对辅助选项简略交代。这是生成模型的常见现象。讨论选型这一步的意义，就在于引导模型跳出预设立场：不再泛泛询问哪个方案更好，而是要求模型为各个方案分别辩护，明确指出在何种具体条件下该方案会败下阵来。

提问方式要聚焦且客观。若只是宽泛询问方案有何不足，模型往往给出不痛不痒的修辞性回答。辩护式提问应当对每个候选依次要求明确四项内容，包括成立前提、具体代价、在什么场景下会失败且输给谁，同时严禁给出“综合来看更优”等总结性定论。第四点尤为关键，避免模型过早代替人工决策，拍板定夺属于下一步的职责。

```
针对"六个独立脚本"和"一个大脚本按检查点分函数"这两个候选，分别扮演它们的辩护人，
依次回答四件事：
1. 这个方案成立的前提是什么，什么场景下选它是对的
2. 选它的代价是什么，谁来承担这份代价
3. 主动交代它已知的失败模式：什么情况下它会输，输给哪个候选
4. 不要下"综合来看方案更好"这类结论，只交代前三条
两个方案都要独立走完这四步，不要在中途比较。
```

将该提示词套用于检测脚本的选型演练，AI 给出的辩护论据条理清晰。六个独立脚本的成立前提在于，各检查点的判定逻辑与退出码机制存在客观差异，拆分能保持各脚本职责清晰。它的代价在于六个文件都需重复解析输入契约，一旦契约调整可能出现修改遗漏。它的失败模式在于随着检查点逐步扩展，执行调度成本呈线性增加。一个集合脚本的前提在于复用入口解析代码，降低冗余。它的代价在于各检测逻辑耦合在同一文件，局部修改时回归验证范围难以有效收敛。它的失败模式在于硬门槛与软性建议的退出码混杂，调用方无法直接基于返回值区分故障级别，必须额外解析输出文本。

这两组具体的失败模式，远比调研表里的宽泛罗列更有参考价值。这正是讨论选型环节的核心目标：将潜在风险具体化为可预期的边界缺陷。

如果在应用该提示词时，AI 对某个候选方案无法讲出具体的失败模式，只是机械重复已有表述，通常是提问方式带有暗示性。例如若提问“六个独立脚本是否比单脚本更清晰”，AI 便容易顺着提问迎合作答。此时应当调整为中立问法，并将各项要求拆解为独立小问依次确认。

当所有方案的边界约束与薄弱点都清晰呈现后，便具备了最终拍板决策的条件。

## 四、决策：把选择写成 ADR

讨论选型厘清了各方案的明确缺陷。决策环节的任务是根据当前业务场景进行权衡，把最终选型及其依据记录为清晰规范的架构决策记录（ADR）。一份规范的 ADR 仅需涵盖四项关键内容：决策、理由、被否方案、反悔成本。无需过早塞入具体代码细节，执行层面的细化属于后续执行方案的范畴。ADR 专注于说明选了什么以及为什么这样选。

在脚本组织案例中，独立脚本方案的短板在于调用开销增加，而单脚本方案的短板在于退出码语义混杂。权衡的关键在于下游消费者的诉求。后续第 9 课将要构建的评审裁判依赖进程退出码执行拦截。若退出码语义混杂，裁判必须引入额外的文本解析逻辑，导致架构耦合度升高。而调度开销在当前场景中影响有限：配音检测仅在内容合成时偶发调用，多执行几条脚本只多耗费数秒机器时间，并不破坏系统的分层结构。

```
决策：六项配音检查点各自写成独立脚本，不合并成一个大脚本。
理由：硬门槛（判 PASS 或 FAIL）和候选类（只列风险点）两类脚本的退出码语义不同，
  合并成一个进程会让裁判角色无法直接靠退出码分辨是硬失败还是候选提示，这条代价比
  调用成本线性增长影响更大，因为裁判角色本来就是靠退出码做判断的。
被否方案：一个大脚本，按检查点分函数，统一入口。
反悔成本：中。往后检查点数量涨到十几个，调用成本会变成真实负担，到时候要把六个
  脚本收拢成一个带多个子命令的工具，但退出码语义仍然按硬门槛和候选类分开，不会
  退回到一个进程混着返回。
```

该 ADR 的结论与第 8 课实际采用的独立脚本方案一致。规范流程的意义在于将决策依据清晰白纸黑字沉淀下来，避免日后遗忘。有了这份文档，后续维护者查阅时便能清楚了解设计初衷，不必重复就“为何不合并脚本”展开无休止的争论。

## 五、写 SPEC：把决策展开成可施工的规格

ADR 明确了技术方向，但宏观决策仍需转化为可施工的技术规格。连接决策与代码落地的桥梁就是执行方案。执行方案严格固定为四个章节，各章节名称保持一致：实施步骤、功能详细设计（视具体场景采用命令、接口或页面乘功能展开）、对外契约、风险与待定项。这套执行方案模板源自工程实践的沉淀，本课将其确立为后续复杂模块的通用规范：

```
# 0X-<部分>执行方案
## 1. 实施步骤    第 1 步…第 N 步；每步 = 做什么 / 产出物 / 验收标准 / 依赖
## 2. <命令|接口|页面> × 功能 × 详细设计    逐条穷举
## 3. 对外契约    本部分提供给 / 依赖其他部分的接口
## 4. 风险与待定项    拍板未覆盖的点全部落这里，标注需要用户裁决的项
```

第二节的组织粒度根据具体实现对象灵活调整。编写命令行工具时围绕命令与功能展开，构建数据接口时围绕接口与方法展开，开发前端页面时围绕视图与组件展开。这一节要求逐项详细罗列，避免使用“其余项依此类推”等省略表述。第 8 课六个脚本的详细设计，实质上就是清晰界定每个脚本的输入参数、计算逻辑、输出格式以及退出码语义，这正是第二节所要求的详实度。

第四节风险与待定项常常被忽视，然而它恰恰是提前化解工程隐患的关键防线。第 10 课中就有一个典型案例。当时 pipeline/2-create.md 规定将调整记录写入 build 目录下的 tts.config.json 的 overrides 字段。然而 .claude/agents/dubbing-reviewer.md 示例中写成了 segment-overrides.json，导致两处规范出现偏差。第 10 课最终将规范收敛至 tts.config.json 的 overrides，当前配置已完全对齐。如果第 8 课在制定执行方案时，便在风险与待定项中明确提出非硬性检查结果的沉淀文件路径，这类规范冲突在早期就能得到解决，无需留到联调阶段临时调整。

以六个检测脚本为例，风险与待定项可作如下梳理：软性候选类检查点（语速偏离、多音字读错、音画对齐）的分析结果最终沉淀至哪个文件，在设计初期尚未最终裁定。建议统一沉淀至 build 目录下的 tts.config.json 中，并在后续构建评审角色时与文档示例同步核准。

当技术规格细化到足以支撑实施后，下一步便是将规格拆解为切实可行的执行节奏。

## 六、执行：照 SPEC 交付里程碑

具体执行时应当合理划分里程碑，为每个里程碑设定客观明确的验收条件，避免试图一次性交付完整系统。验收条件必须是具备可判定性的确定陈述，诸如“功能基本完备”或“大部分用例跑通”等含糊表述均不具备验收价值。

在构建控制台 CLI 工具时，参考规范为各个里程碑定义了硬性验收标准。第一个里程碑的验收标准为：真实仓库下 media check 执行通过，且 YAML 文件内原有注释零丢失。第二个里程碑的验收标准为：全仓状态写入入口保持唯一，连续 7 天内元数据、选题池与看板中的机器更新记录均能在 audit.jsonl 中找到对应行。这些验收标准表述精准，执行者无需二次确认，通过执行具体命令即可明确验证结果。

- 反例：六个检测脚本编写完毕，流程大致顺畅。
- 正例：在 build/ 目录下执行全部检测脚本，人为删除单段音频切片制造缺损，验证 check-completeness.mjs 退出码由 0 变为 1。验证语速偏离、多音字读错、音画对齐三个软性检测脚本的退出码始终保持为 0。

如果验收条件流于空泛，往往反映出设计者尚未想透具体的交付状态。遇到这种情况，可先梳理执行路径，随后再行补充可执行的检验命令，不能任由模糊表述留存。

里程碑验收合格证明流程在既定用例下能够运行，但这并不代表深层次的设计约束已然满足。例如“状态写操作入口唯一”这一类全局不变性约束，仍需通过专项测试予以确认。

## 七、验证：一句能跑的验证动作收口

验证环节核查的重点，往往是开发者自以为已经正确、容易产生盲区的边界。以“状态写操作入口唯一”为例，仅凭静态浏览代码容易得出正常的错觉，因为当前编写的函数确实收拢在指定入口。然而其他脚本是否存在越权改写的隐藏路径，仅靠肉眼巡检很难完全杜绝遗漏。因此验证必须依靠可留痕、可复查的自动化手段，不能凭直觉下结论。

验证阶段的产出是一份规范的施工记录。施工记录按照里程碑逐项跟踪，明确包含里程碑名称、验收标准、实测结果、阻塞点以及规避解法。这份记录是后续系统维护的重要资产。参考规范在构建控制台时，按功能模块详细记录了验收结论与关键发现，明确写明了测试过程中暴露的具体问题与修复方案，而不是草草写下“验收通过”便结束流程。

```
配音检测脚本施工记录（假设走过六步）
里程碑：六个独立脚本全部写出并可独立跑通
出口条件：对 build/ 目录跑六个脚本，故意制造一段缺失 mp3，硬门槛三项退出码变 1，
  候选三项退出码恒为 0
实际结果：<填真实跑出来的退出码>
卡在哪：<没卡住写"无"，卡住了写清楚具体报错>
怎么绕过去：<真解决了写解法，没解决写留给谁接手>
```

一份合格的施工记录，应当让未参与开发的协作者仅凭文档记录即可独立复核里程碑的达成状态。若文档能够支撑这种独立判断，验证便真正落实到位。如果阻塞点与规避解法长期留空或描述含混，说明验收动作并未深入执行，需要对照验收标准重新复核。

至此，六个步骤在示范案例中完整推演了一遍。我们可以对照实际经验做个复盘。

## 八、回看六步：如果第 08 课走过这条路

本课通过回溯的方式梳理了六步方法。第 8 课的六个检测脚本已经开发完毕，本课以其为样板补充了调研与 ADR。选用这个轻量案例作为演示，是因为其规模适中且试错成本较低，能够在较短篇幅内把六个步骤清晰演示清楚。而后续需要重度推演的 media CLI、飞书闸口、控制台等模块，复杂度更高，影响范围更广，需要在专属章节中完整实践。

回顾整个推演过程，规范的六步流程带来的是一份经得起检验的决策档案。为什么六项检查没有合并为单一脚本，核心理由是退出码语义必须保持纯粹。这一理由清晰沉淀在文档中，而不是零散停留在口头讨论里。同时，前文提及的 overrides 配置文件口径分歧，若在方案初期便通过风险与待定项机制预先界定，就能及早消除隐患，避免后期联调时返工调整。

规范方法已经确立。下一课推进第一项核心开发任务：状态写入入口的重构。我们严格遵循调研、讨论选型、架构决策的前三步流程，在正式编写代码前把方案彻底推敲清楚。
