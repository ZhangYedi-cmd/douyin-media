# 收官：形态坐标与 1:1 验收

六页整站跑起来了，这套东西建完了。它到底是个什么形态，哪些出口不能关？第 28 课收尾留下的就是这句问，这一课接着往下走。

第 28 课交付了六页整站和验收输出。读 API 全通，六个快照接口加 file、asset、health，加 SSE 推送 revision。写 API 也全通，四条快写直接转成 media 命令，三类慢作业靠 cc-stream 拉起无头 CC，再用裁决函数收口。单端口出整站，六个页面逐一打开能看，快写和慢作业两条写路径都在真实界面上走过一遍。控制台建完了，生产线和治理线现在都有了一个能点的地方，不用再靠翻文件和日志才知道跑到哪。

这一课不再造新东西。本课的输入是第 01 到 28 课全部成稿的收尾段、第 06 课的四位置模型表、你自己第 24 课的治理总调度、第 25 课的裁决函数、第 17 课的不可逆动作表。还有第 10 课的三轮熔断、第 15 到 16 课的写路径唯一性、第 04 课不许出现判不了的词那条审校标准。产出三件东西：一张形态坐标表、一份撤档判据、一份能逐条跑的 1:1 验收报告。

记忆锚点是一句话：全书 28 课积累的判断落在同一条线上，不是 28 个并列的知识点。从第 01 课人固定出现在三个位置，到第 28 课六页整站两条写路径都通，每一课往这条线上加了一层约束。1:1 验收对的是这条线的结构和工具，不是抄你的账号。

## 1. 回收：从端到端走查到六页整站

单独看某一课的判断，看不出它在整体里补的是哪个缺口。第 01 课那句人固定出现在三个位置，单看是一条流程结论，放回整条线上看，它是后面 17 到 19 课那道人审闸口要保护的东西。锚点收成一条线才有意义。

## 2. 四位置模型收尾：验证信号的第三个去处

第 06 课那张四位置模型表，第三格叫文档，这个名字第 06 课已经钉死。文档如果没人主动去读，实际上就等于没人管。第 06 课另有一张四代演进表，第三代叫护栏代，那张表说的是工具形态整体的样子，跟这里的四位置模型是两件不同的事，回收时各自用各自的名字，不能混着用。

| 位置 | 信号长什么样 | 谁负责推进 | 风险 | 第 26 到 28 课新增的验证点 |
|---|---|---|---|---|
| 流向人 | 一条通知，或者一份等人打开看的记录 | 人自己 | 人必须在场，不在场就卡住 | 六页可看：人逐页打开确认没有报错、数据展示正确 |
| 流向机器 | 一个可以直接判断真假的结果，比如退出码 | 程序或者代理自己 | 判据得先能写成这种结果 | 读 API 全通：六个快照接口加 file、asset、health 逐条探测返回结构；写路径唯一性：media check 的退出码和 audit.jsonl |
| 流向文档 | 一份报告、日志或者待勾清单 | 没有固定的下一步，谁想起来谁去读 | 落了盘，没人保证有人读，读了也可能拿错证据 | 无新增，26 到 28 课新增的两类检查都能写成断言或需要人现场看一眼，没有落进这一格 |
| 没人管 | 打印在终端，没有落进任何地方 | 没有下一步 | 这一步等于白跑 | 无新增 |

六页可看落在流向人这一格。页面好不好用、数据看着对不对，现在没有写成脚本断言，靠人打开六页逐页确认。读 API 全通和写路径唯一性两条落在流向机器这一格，因为它们各自都有一个能直接判真假的结果：前者是接口返回的结构，后者是退出码和审计记录里能不能查到那一行。信号流向的账对齐了，可以退一步看这套系统整体是什么形态。

## 3. 形态坐标：脚本集合、工作流，还是 agent 系统

这套东西不是三选一，是一条从脚本集合到能自主决策的 agent 系统的连续轴。判据只有四条：谁触发、谁判断、谁执行、出错谁兜底。

| 形态 | 谁触发 | 谁判断 | 谁执行 | 出错谁兜底 |
|---|---|---|---|---|
| 脚本集合 | 人手动敲每一条命令 | 人 | 各自独立的脚本，互不知道对方 | 人 |
| 工作流 | 编排文件或者调度器按固定条件、固定时间触发 | 部分交给能写成断言的检查点，不可逆的动作和内容质量类的判断仍旧留给人 | 多个组件按预先定好的顺序接力执行 | 熔断到某个上限后转人工，人处理完继续走 |
| agent 系统 | 系统自己评估现在该不该做这件事，不靠固定时间表 | 系统自己根据历史结果动态调整判据，不用人预先写死阈值 | 系统自己拍板要不要应用一次变更 | 系统自己先止损，人只做事后抽查 |

当前建出来的版本落在中段偏工作流的位置。让 AI 按这张表逐环节标点，标出的结果比凭印象猜要可信，也比自己一格一格对着回忆前几课的实现更省事：

```
读我第 24 课交付的 harness-dispatcher 和 tasks.md 任务注册表、
第 25 课交付的 cc-stream 包和裁决函数、第 28 课的整站验收记录。
参照这张判据表（谁触发/谁判断/谁执行/出错谁兜底），把选题、创作、
出审、发布、治理这五个环节，逐个标出它现在落在脚本集合、工作流、
还是 agent 系统这一格，每格给一句依据，依据必须能在我这三课的
交付物里指出具体文件或记录，指不出来就写没有依据。
最后单独一句：这个环节要往下一格挪，先要满足什么前提，不要建议
我现在就去挪，只说前提是什么。
```

拿回结果核一件事：给出的依据是不是真的指向了某份文件或者某条记录，比如指向 harness/tasks.md 里某个任务的 trigger 字段。听着有道理但查无实据的描述不算依据，这种格子多半是它没打开对应文件，凭常识猜了一个像话的答案。

拿治理这一环节练一遍，能看出这条轴不是越靠右越好。治理线现在触发和执行都已经自动化：harness-dispatcher 会自己判断谁到点，四个治理 skill 会自己跑出报告和提议，这一段听着已经很像 agent 系统。可提议落笔这一步仍旧卡在人审，account-audit 能拿到调参权限，但这一课它只交一份心跳报告，自动档那部分逻辑要等账本攒够样本才会第一次真的动。治理线故意停在这一格，不是没做到，往下一格挪的前提是先把只提议不落笔这条铁律松绑，而这条铁律恰恰是下一节要讲的不能关的出口之一。

坐标画完了，接下来要说清楚这套系统里哪些开关不能关。

## 4. 撤档判据：哪些出口一关，系统就退化

这套系统能无人值守跑，不代表可以把所有闸口都关掉。闸口和无人值守是两件事，关错一个闸口，退化的不是效率，是可信度。

| 出口 | 关掉之后退化成什么 |
|---|---|
| 人审闸口（第 17 到 19 课的出审与确认发布两道闸门） | 发布这个不可逆动作，没人在真正发出去之前看最后一眼。第 01 课七项判据里事实、语气、定位这三项现在只归人判，闸口一关，这三项风险直接放行到公开可见，收不回来 |
| 三轮熔断上限（第 10 课） | 自愈循环会在同一个问题上一直重试，不会主动把该转人工的信号交出来。人反而更晚知道这条内容卡在哪一步，卡住的问题被拖着，不是被解决 |
| 治理线只提议不落笔（第 21、24 课） | 复盘提议、选题池清扫这类判断绕过人审直接改 brain 大脑或状态字段，账号打法可能被一次误判的复盘悄悄带偏，中途没有人签字确认 |
| 写入口唯一性校验（第 15、16 课的 media check） | 状态漂移不会在它发生的时候被发现，比如 meta.yaml 已经翻到发布状态，backlog.yaml 里对应的条目还停在取题状态，这正是第 16 课 CHK-01 双层不同步这条规则要抓的情况。要等到某个环节真的对不上号，才会被人工揪出来，退回第 16 课之前看着对但没有证据的状态 |
| 只认文件的裁决（第 25 课的裁决函数） | 改成信任进程自己上报的退出码或者自述，一次静默失败就会被当成成功放过。第 06 课讲过退出码本身也会骗人，这个问题会重新出现在无人值守这条线上 |

坐标和撤档判据都有了，最后一件事是怎么证明建的这套和课程承诺的功能对等。

## 5. 验收怎么用，加结构项：五条判据

### 5.1 验收怎么用：给的是回第几课，不是分数

每一项过不了，报告里写的是你缺的是什么、回第几课第几节，不写扣了几分。这份报告是路标，不是成绩单。结构项问的是东西在不在、能不能跑，不问内容对不对。内容对不对因人而异，一个只写技术深度的账号和一个只写生活记录的账号，写出来的 brain 文件不该长一个样，这不是缺陷。

### 5.2 结构项：五条判据，每条一个能跑的验证动作

| 判据 | 命令或操作 | 通过标准 |
|---|---|---|
| ①生产线跑得通 | 一条内容从选题到出审全程走一次 | 每一步都落到该落的文件里：选题池状态翻转、简报生成、创作产物齐全、出审卡片推出 |
| ②治理线四个任务能被同一个调度器派活 | 跑一次 harness-dispatcher，对照自己 tasks.md 的任务注册表 | 到点的任务被派出去，没到点的写清楚差几天，账本 index.jsonl 里有对应记录 |
| ③状态写入口唯一，media check 能问出漂移并返退出码 | 跑 media check，再手改一次 meta.yaml 把状态改成和 backlog.yaml 对不上，重新跑一遍 | 第一次跑退出码干净；手改之后再跑，CHK-01 那条规则能把这处双层不同步抓出来，退出码变成非零 |
| ④控制台单端口起站六页可看两条写路径都通 | 单端口打开六页，各点一次快写和一次慢作业 | 六页逐一打开没有报错；一次快写经 SSE 回流到页面；一次慢作业推进到成功、失败或者被取消三种终态之一 |
| ⑤学员从头到尾没有手写过一行实现代码 | 翻自己仓库的 commit 历史或者和 AI 的对话记录 | 没有手改过实现文件，改 meta.yaml、backlog.yaml 这类数据文件不算 |

五条判据不用人一条条比对着数字算，让 AI 按这张表逐条给结论：

```
按下面五条判据逐条判断过还是不过，每条只给过或者不过，不给百分比、
不给等级、不打分。
①生产线跑得通；②治理线四个任务能被同一个调度器派活；③状态写入口
唯一，media check 能问出漂移并返退出码；④控制台单端口起站六页可看
两条写路径都通；⑤我从头到尾没有手写过一行实现代码。
过的写一句依据，依据要能在我仓库里指出具体文件、命令或者记录。
不过的写缺什么，加回第几课第几节补，不许只写不过两个字。
判断依据只看东西在不在、能不能跑，不比对我账号的具体内容写得
像不像参考仓库。
```

拿回结果核两点。第一，过的那几条给出的依据是不是真的指向了一份文件或者一条记录，只写符合预期不算依据。第二，不过的那几条有没有精确到第几课第几节，只写去前面补一下的，退回去让它重新查。

判据⑤最容易被想当然写成过，回头翻一遍 commit 历史再确认一次。如果某次提交直接改了 `.ts` 或者 `.py` 文件的业务逻辑，不是 `meta.yaml`、`backlog.yaml` 这类数据文件，这一条要判不过。回第 14 课收尾说的那条纪律：AI 写代码，人只问过没过。

结构项能不能过，机器说了算。内容项就不一样了。

## 6. 内容项：只看有没有、判不判得了，不比对着抄

brain 五份、CLAUDE.md、五份阶段契约这类东西必须因人而异。验收内容项时只问这份文件存在吗、里面的判断能不能被判断，不问和参考仓库写得像不像。一个专攻技术深度的账号和一个偏娱乐向的账号，brain 里的内容注定长得不一样，这不是差距，是两个账号本来就该有不同的定位。

可判性检查沿用第 04 课那条标准：技术深度和流量型六比四，判得了；以深度为主兼顾流量，判不了。

| 文件 | 存在性检查 | 可判性检查 |
|---|---|---|
| brain/positioning.md | 文件存在，账号定位一栏有内容 | 内容比例能不能拆成一个具体数字，能不能拿去排今天做哪条题 |
| brain/persona.md | 文件存在，语气条目有内容 | 语气描述是不是判断句，不是形容词堆砌 |
| brain/style-guide.md | 文件存在，规范条目有内容 | 每条规范能不能对照一篇口播稿逐条打勾，不能只是一句原则 |
| brain/sources.md | 文件存在，素材来源有内容 | 每个来源能不能落到一个具体渠道或者账号，不是泛泛写多看同行 |
| CLAUDE.md | 文件存在，流程纪律和治理线铁律两节都有内容 | 每条纪律能不能对照一次真实操作判断有没有违反，不是一句口号 |

结构项和内容项都过完一遍，全书收官。

## 7. 收尾：全书收官

这一课交付了一张形态坐标表、一份撤档判据，以及一份能逐条跑的 1:1 验收报告。结构项机器可判，内容项按存在性和可判性检查，判不过的地方指向具体是哪一课哪一节没做完，不是一个分数。

全书 29 课到这里收官。这一课结束时，你手上应该有一套功能对等的流水线，以及一份能证明它对等的验收报告。功能对等指的是这条线上的结构和工具，不是账号内容抄得像不像，账号内容原本就该是你自己的判断，不是参考仓库的。就这么回事，剩下的路自己走。
