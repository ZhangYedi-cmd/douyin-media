# 人审闸口：可逆的 AI 自行，不可逆的等人

上一课把状态中枢立住了：全量 `media` 命令收敛成写状态的唯一入口，`03-施工记录.md` 记了两个里程碑的出口条件，`media check` 在自己仓库跑通、退出码干净，`audit.jsonl` 证明了每一次改动都留了痕迹。上一课收尾的时候留了一句话：状态中枢立住了，机器能自己改状态。可有些动作改错了收不回来，哪些动作不能让机器自己拍板？这一课回答这句话。

这一课的记忆锚点是：可逆的 AI 自行，不可逆的等人。输入是 `tools/console/packages/core/src/state.ts` 里 `review` 状态的三条出边、`pipeline/3-review.md` 和 `pipeline/4-publish.md` 全文、`CLAUDE.md` 的流程纪律那一节。产出两件东西：一张不可逆动作表，一份卡片字段草案。

## 1. 判据：错了能不能收回，不是会不会犯错

要不要给一个动作设人审闸口，问的不是 AI 会不会判断错。AI 会判断错，这是前提，不是需要论证的新闻。真正要问的是：判断错了，这个动作能不能撤回。能撤回的，大不了再改一次，代价是多花几分钟；不能撤回的，改错了就是改错了，没有再来一次这个选项。

这条判据跟前面几课立的自愈回路是两件事，容易被并到一起想，实际是两条不同的维度。第 10 课把配音质检的判错、改、复判接成了一个能自己转起来的回路，三轮不过就停下来交人，这条回路解决的是准不准的问题，回路转得越顺，AI 判对的概率越高。但判对的概率再高，也不会让一个不可逆的动作变得可逆。第 01 课列过出审前机器已经查完的七项：声画一致、音频自然度这些能写成一条命令判真假的，都归了机器；事实、语气、定位这些写不出判定命令的，归了人。那条判据看的是这项工作机器能不能干。这一课的四类判据看的是另一条线：干完了这个动作能不能收回。两条线经常重叠，一个技术结论判得越准，出问题的概率越低，但概率降到再低，`sau douyin upload-video` 跑完了照样是跑完了，收不回来这件事本身没有变。

四类动作收不回。第一类，发出去收不回：内容一旦真的发布到抖音，推荐算法立刻开始分发，看过的人、截过的图、留过的评论，删视频也换不回来。这条流水线里对应的真实动作是 `sau douyin upload-video`，经 `douyin-publish` skill 真发。第二类，花钱：`tts-dub` 批量合成配音时调的是 MiniMax 的付费接口，`pipeline/2-create.md` 里写了先探一次余额，余额不够会返回 1008 停线报充值。这条判据要看的不是余额够不够，是钱花出去这件事本身，一旦一批配音合成成功，这笔钱就花掉了，就算这条内容后来被废弃，钱也退不回来。第三类，对外可见：跟第一类经常是同一个动作，但角度不一样。发出去收不回，说的是技术上这个动作没有反悔按钮；对外可见，说的是就算技术上能把视频删掉，看过的人、转发的截图已经在外面了，公开这件事本身不可逆。一个动作同时踩中这两条判据，不是巧合，是因为发布这个动作本来就同时具备这两种性质。第四类，覆盖真相源：`media publish-done` 一次做三件记账，把 `meta.yaml` 翻到终态并回填发布时间和链接、把 `backlog.yaml` 对应条目同步翻转、把 `dashboard.md` 在制表里移出这一条。这次记账把原来的状态字段直接覆盖掉了，如果记错了链接或者记错了时间，想知道原来的值是什么，只能翻 `audit.jsonl` 里那一行去反推，`meta.yaml` 本身已经看不出改之前是什么样。

对照一下可逆的那一类。`media flip` 做的是单文件状态翻转，比如把一条内容从 `review` 翻回 `drafting`。这个动作不涉及花钱，不对外发布，也不做终态记账覆盖，翻错了直接再翻一次翻回去就行，成本是重新走一遍流程，不是没法挽回的动作。

| 类别 | 判据 | 本流水线对应的真实动作 | 可逆吗 |
|---|---|---|---|
| 发出去收不回 | 动作完成后没有技术上的撤销手段 | `sau douyin upload-video`（经 `douyin-publish` skill 真发） | 不可逆 |
| 花钱 | 调用付费服务，一旦成功费用已产生 | `tts-dub` 批量合成配音，调 MiniMax 付费接口 | 不可逆 |
| 对外可见 | 动作结果被外部真实用户看到、留下痕迹 | 抖音发布后内容进入推荐池，被看过、被截图 | 不可逆 |
| 覆盖真相源 | 动作直接改写状态字段，原值不再留痕 | `media publish-done` 三件记账（meta.yaml、backlog.yaml、dashboard.md） | 不可逆 |
| （对照） | 只改单文件状态，不花钱、不对外、不做终态覆盖 | `media flip`（比如 `review` 翻回 `drafting`） | 可逆，翻错了再翻一次 |

这张表不是靠脑子想出来的，是让 AI 先把流水线上会写文件、调外部服务的动作全部列一遍，再按四类判据分好类：

```
读一遍 pipeline/2-create.md、pipeline/3-review.md、pipeline/4-publish.md、
tools/console/packages/core/src/state.ts，
把这条流水线上会写文件或调用外部服务的动作全部列出来，按四类判据分类：
发出去收不回、花钱、对外可见、覆盖真相源。
剩下改错了能再改一次的动作单独放一栏，别混进不可逆那四类里。
每个动作写清楚它对应哪条真实命令或脚本，不要用你自己编的名字。
输出一张表，动作 / 判据类别 / 命令或脚本名，我要逐格核对有没有真实出处。
```

拿到这张表先核对两件事：每一格填的命令或脚本名在仓库里是不是真的存在，划进不可逆那四类的动作是不是真的对得上判据。如果 AI 把某个只改了一个字段又能随时翻回去的动作也划进不可逆那一栏，多半是把动作陌生和动作不可逆这两件事混了。前者是没跑过这个动作，跑几次就熟了；后者是动作本身的性质，不会因为跑熟了就变得可逆。判据只认后者。

四类判据定完，接下来要在真实流程里找到这些动作各自落在哪条状态出边上。

## 2. 闸口位置：定在哪条边上

闸口不是设在 AI 最容易出错的地方，是设在出了错收不回的那条边前面。这句话听着像是同义反复，但把 `review` 状态实际的出边摆出来看，会发现这两种设法差得很远。

`tools/console/packages/core/src/state.ts` 里 `review` 状态一共三条合法出边，全部经 `media flip` 触发。第一条，`review` 到 `drafting`，打回重做，不需要写理由。第二条，`review` 到 `approved`，通过，同样不需要理由。第三条，`review` 到 `rejected`，打回挂待办，这条需要理由，`state.ts` 里标了 `requiresReason: true`。

这三条边，无论走哪一条，都还能再改回来。打回 `drafting` 的可以重新走一遍创作再交回 `review`；`rejected` 的可以再翻回 `drafting` 重做；就连过了审进了 `approved` 的，也能退回 `drafting`。`state.ts` 这条边旁边留了一句注释，写的是审批后反悔改稿，说明这条退路是特意补上的，不是漏判。

三条出边全部可逆，这正是 `pipeline/3-review.md` 写的工作日全自动只跑到出审为止的原因：自动化可以一路跑到这三条边前面，因为无论走哪条错了都还有救。`CLAUDE.md` 流程纪律那一节把这条规矩钉得更死，写的是发布必须人审通过。这条规矩管的不只是要不要有人审，三条出边本身也从来不允许机器自己拍板走哪条，只是走错了代价不大。

这张表不是凭记忆背出来的，让 AI 去 `state.ts` 和两份阶段契约里对照着找：

```
读 tools/console/packages/core/src/state.ts 里 review 状态的三条出边，
和 pipeline/3-review.md、pipeline/4-publish.md、CLAUDE.md 的流程纪律那一节，
把 review 的三条出边整理成一张表：出边 / via 命令 / 要不要理由 / 谁触发 /
改错了能不能再改回来。
再单独加一行：approved 状态之后走向真发和记账的那条边，同样这五列，
标出它和前三条的区别在哪。
```

真正不可逆的那条边，在 `approved` 之后。`pipeline/4-publish.md` 写得很直接：铁律是先 dry-run 拼出命令和物料，经 `feishu-notify` 推回飞书做二次确认，人点确认才真发。这条边对应的命令是 `media publish-done`，跑完这条命令，第一类判据里说的真发、花钱、对外可见、覆盖真相源，四件事全部已经发生，没有翻回去这个选项。

| 出边 | via 命令 | 需要理由 | 谁触发 | 改错了能不能再改回来 |
|---|---|---|---|---|
| `review` 到 `drafting`（打回重做） | flip | 否 | 人 | 能，重新走创作再交回 `review` |
| `review` 到 `approved`（通过） | flip | 否 | 人 | 能，`approved` 还能退回 `drafting` |
| `review` 到 `rejected`（打回挂待办） | flip | 是 | 人 | 能，`rejected` 还能翻回 `drafting` |
| `approved` 之后真发 + 记账 | publish-done | （命令层不强制，但动作本身不可逆） | 人（二次确认后） | 不能 |

这张表看着有点反直觉：`review` 的三条出边全都是人触发的，闸口好像已经设过一次了，为什么还要再设一道。原因是这三条边虽然都要人点按钮，但点错了代价很小，属于流程内部的可逆循环；真正决定这套系统安不安全的，不是这三条边有没有人参与，是 `approved` 之后那条边有没有人参与。如果哪天为了省事把 `publish-done` 也接成自动触发，出审这一关照样在，但闸口已经名存实亡了，因为真正不可逆的那一步已经不需要人点头。闸口位置定了，接下来定这道闸具体长什么样，人在飞书上看到什么、点什么。

## 3. 卡片放什么：三十秒判完的信息配额

卡片要让人三十秒内判完，前提是信息够但不多。字段太少，人没法判断；字段太多，人得从一堆无关信息里挑出要看的那几条，反而比不做卡片还慢。哪些字段必须直接上卡，哪些字段点进去看，是这一节要划的线。这份草案不是最终实现，是留给第 18、19 课的约束。这条闸口这一版只做飞书，这是参考仓库的历史实现，需要企业或团队账号才能建自建应用，这一条会在第 18、19 课动手前反复确认。

先看审核卡要判的六项。`pipeline/3-review.md` 列了六项人审清单：事实、时效、定位、语气、合规、观感。第 01 课把这六项的名字列出来了，说这六项没有对应的检测脚本，全靠人凭经验现场判断。这一课把判据补上，判据不是让人凭感觉，是给出一句能核对的标准。

事实这一项，判的是技术结论有没有出处：官方文档、开源项目的提交记录、可复现的评测，三选一，查不到出处就判不通过，不能因为读着顺就当成对的。

时效这一项，判的是涉及最新发布或版本更新的内容有没有标来源和抓取日期。这条容易在写完之后过期：抓取时是最新版本，等到出审时可能已经被官方更新覆盖，标了日期至少能看出这个结论是什么时候查的。

定位这一项，判的是内容贴不贴合 `brain/positioning.md` 定的账号支柱，逐条核对，不是凭印象觉得差不多。

语气这一项，回收第 01 课的钩子冷启动判据：第一句脱离上一集单独读，能不能站得住。

合规这一项，对照 `CLAUDE.md` 的内容红线逐条核，无违禁词、无违规导流、无夸大承诺。这条最容易漏检的地方是同音词，文字扫描扫不出发音接近的违禁词，得靠人耳朵听。

观感这一项，封面是不是竖版比例、有没有拿横屏视频帧充数（这是第 05 课定的封面判据），加上字幕逐字看一遍有没有错别字。

| 判据 | 判什么 |
|---|---|
| 事实 | 技术结论能否在官方文档、提交记录或可复现评测里查到出处 |
| 时效 | 涉及最新发布的内容是否标了来源和抓取日期 |
| 定位 | 是否贴合 `brain/positioning.md` 定的账号支柱，逐条核对 |
| 语气 | 第一句脱离上一集单独读，能不能站得住 |
| 合规 | 对照内容红线逐条核，含发音相近的违禁词 |
| 观感 | 封面是否竖版且未拿横屏帧充数，字幕逐字有无错别字 |

这六项判据，接下来要走一条 Prompt，让 AI 补进你自己第 03 课写的骨架 `pipeline/3-review.md`。你这份文件目前只有输入、输出、状态翻转、闸口四项，六项判据这一段还是空的：

```
把这六项人审判据加进我的 pipeline/3-review.md：
事实：技术结论能否在官方文档、提交记录或可复现评测里查到出处。
时效：涉及最新发布的内容是否标了来源和抓取日期。
定位：是否贴合我的 brain/positioning.md 定的账号支柱。
语气：第一句脱离上一集单独读，能不能站得住。
合规：对照我的内容红线逐条核，含发音相近的违禁词。
观感：封面是否竖版且未拿横屏帧充数，字幕逐字有无错别字。
按我文件现有的结构插进去，不要改动我已经写好的输入、输出、状态翻转、闸口四项，
改完把整份文件贴给我看一遍。
```

判据定了，接下来是卡片本身。这条流水线上有两处闸门，出审和确认发布，第 01 课已经列过。审核卡对应出审，确认发布卡对应 `approved` 之后的二次确认。两张卡各自的字段配额不一样。

审核卡要让人三十秒判完六项判据，直接上卡的字段只能是六项判据里能一眼扫过去的部分：标题和钩子首句（判语气）、选题定位标签（判定位）、封面缩略图（判观感的一半）。事实、时效、合规这三项没法压缩成一眼看完的摘要，需要点进去看，口播稿全文链接放在卡片上，点进去看完整文案。人在这几项上花的时间没法省，卡片能省的是找文件、切窗口的时间，不是判断本身的时间。

按钮这一版做两个：通过、打回。打回带一个文本输入框，写打回原因。通过对应 `review` 到 `approved` 这条边；打回对应 `review` 到 `drafting` 这条边，原因写进 `3-review.md`。

`state.ts` 里 `review` 其实还有第三条出边，打回挂待办到 `rejected`，这一版卡片先不单独做这个按钮。要不要把打回拆成两种、什么时候该直接挂 `rejected` 而不是回 `drafting` 重做，这个决策留给第 18、19 课走 SPEC 六步时定，不在这一课草率拍板。

确认发布卡对应的是 `approved` 之后那条不可逆的边，`pipeline/4-publish.md` 写的 dry-run 铁律：先拼出完整的发布命令和物料，推回飞书，人点确认才真发。这张卡上要放的是这次真发会用到的全部具体信息：完整拼好的 `sau douyin upload-video` 命令、标题、话题标签、封面路径、媒体文件清单。这里没有点进去看这一说，因为要确认的就是这些字段本身对不对，藏起来反而增加误发的风险。按钮同样两个：确认发布、取消。确认发布触发真执行，成功后走 `media publish-done` 记账；取消停在 `approved`，不做任何状态翻转，等着下一次有人点确认发布。

| 卡片 | 卡片作用 | 上卡字段 | 点进去看 | 按钮 | 触发后去哪 |
|---|---|---|---|---|---|
| 审核卡 | 出审闸口，判六项人审判据 | 标题、钩子首句、定位标签、封面缩略图 | 口播稿全文 | 通过 / 打回（带原因） | 通过到 `approved`；打回到 `drafting`，原因写进 `3-review.md` |
| 确认发布卡 | `approved` 之后的二次确认，防误发 | 完整发布命令、标题、话题标签、封面路径、媒体文件清单 | 无（字段本身就是要确认的东西） | 确认发布 / 取消 | 确认发布触发真执行，成功后 `media publish-done` 记账；取消停在 `approved` |

如果卡片上的字段拉得又长又满，三十秒判不完，多半是把点进去看那一栏的字段也一起塞上了卡。审核卡的口播稿全文如果直接铺在卡片正文里，人得先划到底才能点按钮，这跟没做卡片区别不大，点进去看这个动作本身就是配额的一部分，不是偷懒。

字段草案定了，接下来是把它变成一条能跑的技术通道，这够得上走完整 SPEC 六步。

## 4. 收尾：第二件重活

不可逆动作表划清了什么改错能再来一次，什么不能：`media flip` 可逆，真发抖音、付费配音、公开可见、终态记账这四类不可逆。卡片字段草案定了人要看什么、点什么：审核卡放六项判据能一眼扫过去的部分，点进去看口播稿全文；确认发布卡把发布命令原样摊开，不留藏起来的字段。

但草案只是字段清单，背后还有一堆没定的东西。飞书通道是走长连接还是走公网 webhook，卡片的 JSON 结构具体怎么拆成几层元素，按钮点下去之后飞书那边给多长的响应窗口、超时了会怎样。一个飞书应用如果以后要服务多条业务线，怎么防止彼此的按钮事件串到对方头上，这几件事一件都还没定。不是这一课漏了，是这一课的判据够不到这一层，字段草案是接口，接口背后的实现是另一件重活。

不可逆动作表和卡片字段草案有了。这是第二件重活，六步再走一遍：飞书通道要定哪几件事？
