# 人审闸口：可逆的 AI 自行，不可逆的等人

上一课把状态中枢立住了。全量 `media` 命令收敛成写状态的唯一入口，`03-施工记录.md` 记了两个里程碑的出口条件。`media check` 在本地仓库顺利跑通，退出码干净，`audit.jsonl` 证明每次改动都留了痕迹。上一课收尾时留了一个问题：状态中枢立住后，机器能自己改状态；可有些动作改错了收不回来，哪些动作不能让机器自己拍板？这一课回答这个问题。

这一课的记忆锚点是：可逆的 AI 自行，不可逆的等人。
输入包含三项内容。一是第 14 课 core 包 state 模块中 review 状态的三条出边（路径依你 SPEC 中的定义为准）。二是 `pipeline/3-review.md` 与 `pipeline/4-publish.md` 全文。三是 `CLAUDE.md` 的流程纪律章节。
产出包含两项：一张不可逆动作表，一份卡片字段草案。

## 一、判据：错了能不能收回

判断要不要给动作设人审闸口，核心不用纠结 AI 会不会算错。AI 难免会出错，这是正常前提，不需要额外论证。真正关键的考量是，如果判断错了，这个动作能不能撤回。能撤回的操作大不了再执行一次，代价只是多花几分钟。不能撤回的操作，一旦改错就没有重新来的机会。

这条判据和前面几课建立的自愈回路属于两个不同维度，容易被混在一起考虑。
第 10 课把配音质检的纠错、修改与复判连成能自我调整的循环回路，三轮不通过就交给人处理。这条回路解决的是准确度问题。回路运行越顺畅，AI 判对的概率就越高。
但准确率再高，也不能把不可逆的动作变成可逆动作。
第 01 课提过出审前机器检查完毕的七项内容。声画一致、音频自然度等能用命令行判断正误的交给机器。事实、语气和定位等写不出自动判断脚本的交给人工。
那条判据衡量的是机器能不能做这项工作。
这一课的判据衡量的是另一条基准：动作执行完毕后能不能收回。
两类考量在业务上常有交叉。技术结论判断得越准，出纰漏的概率越低。但即便概率降到极低，一旦执行完发布，操作就已经发生，无法撤回的事实并没有改变。

流水线上的不可逆动作通常归为四类：发出去无法撤回、产生扣费、对外公开可见、覆盖真相源。可以让 AI 遍历流水线中所有写文件和调外部服务的动作，逐一依据这四类标准核对：

```
读一遍我的 pipeline/2-create.md、pipeline/3-review.md、pipeline/4-publish.md，
和我 core 包里的 state 模块，
把这条流水线上会写文件或调用外部服务的动作全部列出来，按四类判据分类：
发出去收不回、花钱、对外可见、覆盖真相源。
剩下改错了能再改一次的动作单独放一栏，别混进不可逆那四类里。
每个动作写清楚它对应哪条真实命令或脚本，不要用你自己编的名字，
你的文件里没写到的地方就留空，不要替我猜。
输出一张表，动作 / 判据类别 / 命令或脚本名，我要逐格核对有没有真实出处。
```

参考流水线自己跑这条 Prompt，整理出的表大致是这样：

| 类别 | 判据 | 对应的真实动作 | 可逆吗 |
|---|---|---|---|
| 发出去收不回 | 动作完成后没有技术上的撤销手段 | `sau douyin upload-video`（经 `douyin-publish` skill 真发） | 不可逆 |
| 花钱 | 调用付费服务，一旦成功费用已产生 | `tts-dub` 批量合成配音，调用 MiniMax 付费接口。参考流水线的 `pipeline/2-create.md` 中写明先探测一次余额。余额不足时返回 1008 暂停并提示充值。这项判据衡量的是扣费动作本身。一批配音合成成功后，费用无法退回 | 不可逆 |
| 对外可见 | 动作结果被外部真实用户看到、留下痕迹 | 与第一类常为同一动作，但视角不同。发出去无法撤回指技术上缺少撤回手段；对外可见指即便后续删除视频，已浏览的用户和截图依然留存在外 | 不可逆 |
| 覆盖真相源 | 动作直接改写状态字段，原值不再留痕 | `media publish-done` 一次完成三处记账：在 `meta.yaml` 中翻转为终态并回填时间和链接、同步翻转 `backlog.yaml`、从 `dashboard.md` 移出在制表。若记错需要查找原值，只能通过 `audit.jsonl` 反查 | 不可逆 |
| （对照） | 只改单文件状态，不花钱、不对外、不做终态覆盖 | `media flip`（例如将内容从 `review` 翻回 `drafting`），若翻错只需重新执行命令翻回即可 | 可逆 |

拿到这张表，先结合自己的项目核对两件事：每一行填写的命令或脚本名在本地仓库中是否存在；归入不可逆分类的动作是否切实符合判据。
如果本地的 `pipeline/2-create.md` 写得相对概括，没有体现 1008 这类具体错误码细节，并不意味着文件有误。你的项目所选用的配音服务和余额提示方式可能完全不同。判据关注的是扣费行为本身，而非某一个具体的错误码。
如果 AI 将某个仅修改单个字段且能随时恢复的操作归入不可逆类别，常见原因是混淆了概念。一是动作陌生，之前没执行过，多操作几次就熟悉了。二是动作本身的性质不可逆，不会因为熟悉操作就变得可逆。判据只以动作本身的性质为准。

四类判据理顺之后，接下来需要梳理这些动作分别对应状态机的哪一条出边。

## 二、闸口位置：定在哪条边上

闸口应该设在出错后无法撤回的那条边之前，而非设在 AI 最容易出错的环节。这两种设计思路差异很大，结合 `review` 状态的实际出边梳理会很直观。

在第 13 课规范中，`review` 状态共有三条合法出边，全部通过 `media flip` 命令触发。
第一条是 `review` 到 `drafting`，表示打回重做，不需要附加理由。
第二条是 `review` 到 `approved`，表示审核通过，同样不需要理由。
第三条是 `review` 到 `rejected`，表示打回并挂起待办。这条出边需要理由，`media flip` 执行时必须附带 `--reason` 参数。
这三条边无论走哪一条，后续都可以重新调整。
打回到 `drafting` 可以重新执行创作流程，再提交回 `review`。
处于 `rejected` 状态的内容也可以翻回 `drafting` 重新制作。
如果状态机中给 `approved` 预留了退回 `drafting` 的出边，通过后依然允许撤回重新改稿。参考流水线的 state 模块中专门保留了这条边，代码注释标明用于审批后撤回修改，说明该退路是主动设计的防线。
即便你的规范当初没有保留退回边，让 `approved` 成为单向流转，也不会影响这一课的结论。因为真正不可逆的出边始终位于 `approved` 之后，在两种设计下判据都成立。

真正不可逆的出边位于 `approved` 之后。
参考流水线的 `pipeline/4-publish.md` 包含一项明确约束：发布前必须先执行 dry-run 生成发布命令与物料摘要，通过 `feishu-notify` 发送至飞书进行二次确认，必须在人工点击确认后才允许真正发布。
该出边对应的记账命令是 `media publish-done`。执行完这条命令后，真实发布、接口扣费、公开可见、覆盖真相源这四项操作均已发生，系统便不再提供撤销选项。

把这五条边摆到一张表里，让 AI 去你自己的 state 模块和阶段契约里对照着找：

```
读我 core 包里的 state 模块，找出 review 状态的三条出边，
和我自己的 pipeline/3-review.md、pipeline/4-publish.md、CLAUDE.md 的流程纪律那一节，
把 review 的三条出边整理成一张表：出边 / via 命令 / 要不要理由 / 谁触发 /
改错了能不能再改回来。
再单独加一行：approved 状态之后走向真发和记账的那条边，同样这五列，
标出它和前三条的区别在哪。
我自己的阶段契约文件如果还没写到这个细节，留空或标注待补，不要替我编。
```

参考流水线跑出来的表大致是这样。如果你自己的 SPEC 当初没留 `approved` 退回 `drafting` 这条边，把对应那一行删掉，其余四行按你自己 `media flip`、`media publish-done` 的真实行为核对：

| 出边 | via 命令 | 需要理由 | 谁触发 | 改错了能不能再改回来 |
|---|---|---|---|---|
| `review` 到 `drafting`（打回重做） | flip | 否 | 人 | 能，重新走创作再交回 `review` |
| `review` 到 `approved`（通过） | flip | 否 | 人 | 能，`approved` 还能退回 `drafting` |
| `review` 到 `rejected`（打回挂待办） | flip | 是 | 人 | 能，`rejected` 还能翻回 `drafting` |
| `approved` 之后真发与记账 | publish-done | 命令层不强制，但动作本身不可逆 | 人（二次确认后） | 不能 |

这张表最容易产生误解的地方在于：`review` 的三条出边都是由人工触发的，容易让人误以为闸口已经设立完毕，无需在 `approved` 之后再增设一道防线。
这三条出边即便误触，调整的代价依然很小，属于流程内部的可逆循环。真正决定系统运行安全性的关键，在于 `approved` 之后的那条出边是否有人工介入。
如果为了省事将 `publish-done` 接入自动触发，虽然出审环节依然存在，但闸口功能实际已经失效，因为不可逆的发布环节已经脱离了人工确认。

闸口位置明确后，接下来需要规划人工在飞书上查看的内容和可执行的操作，也就是下一节要规划的卡片字段配额。

## 三、卡片放什么：三十秒判完的信息配额

卡片要让人在三十秒内完成判断，前提是信息量恰到好处。字段太少无法作为判断依据；字段过多，人工需要在一堆冗余信息中费力检索，效率还不如不设卡片。
哪些字段必须直接呈现在卡片上，哪些字段适合折叠收纳、需要时点开查阅，是这一节要划定的边界。
这份草案是给第 18、19 课提供的设计约束。这里的闸口通信当前基于飞书实现，沿用参考仓库的技术选型。创建企业自建应用需要相应权限，在进入第 18、19 课实操前需要提前确认。

先看审核卡需要评估的六项内容。参考流水线的 `pipeline/3-review.md` 整理了六项人审清单：事实、时效、定位、语气、合规、观感。
第 01 课梳理过这六项的名称，并说明它们缺乏现成的自动化脚本，需要人工进行综合判断。
这一课需要将具体的判据补全，为每项给出明确的核对准则，避免停留在主观感受层面。

关于事实，重点核对技术结论是否有据可循。可以在官方文档、开源项目提交记录或可复现的评测记录中三选一。若查无出处则判为不通过，不能仅凭读着顺畅就默认正确。

关于时效，重点核查涉及最新版本或新动态的内容是否注明信息源和获取日期。这类内容容易随时间推移而失效。采集时可能属于最新动态，待到出审阶段可能已有新的官方变更。标明日期有助于明确判断的时效基准。

关于定位，对照 `brain/positioning.md` 设定的账号支柱逐项对照，避免仅凭粗略印象估算。

关于语气，回顾第 01 课的冷启动判据：单独抽离第一句开头，脱离上下文也能自然立得住。

关于合规，对照 `CLAUDE.md` 的内容红线逐项排查，确保无违禁词、无违规导流且无夸大承诺。其中常见疏漏是发音相近的谐音词，自动化文本检索容易遗漏，需要人工听辨确认。

关于观感，确认封面是否符合竖屏比例，是否避免直接截取横屏视频帧充数，同时通读字幕排除错别字。

| 判据 | 判什么 |
|---|---|
| 事实 | 技术结论能否在官方文档、提交记录或可复现评测里查到出处 |
| 时效 | 涉及最新发布的内容是否标了来源和抓取日期 |
| 定位 | 是否贴合 `brain/positioning.md` 定的账号支柱，逐条核对 |
| 语气 | 第一句脱离上一集单独读，能不能站得住 |
| 合规 | 对照内容红线逐条核，含发音相近的违禁词 |
| 观感 | 封面是否竖版且未拿横屏帧充数，字幕逐字有无错别字 |

这六项判据要走一条 Prompt，补进你自己第 03 课写的骨架 `pipeline/3-review.md`。你这份文件目前只有输入、输出、状态翻转、闸口四项，六项判据这一段还是空的：

```
把这六项人审判据加进我的 pipeline/3-review.md：
事实：技术结论能否在官方文档、提交记录或可复现评测里查到出处。
时效：涉及最新发布的内容是否标了来源和抓取日期。
定位：是否贴合我的 brain/positioning.md 定的账号支柱。
语气：第一句脱离上一集单独读，能不能站得住。
合规：对照我的内容红线逐条核，含发音相近的违禁词。
观感：封面是否竖版且未拿横屏帧充数，字幕逐字有无错别字。
按我文件现有的结构插进去，不要改动我已经写好的输入、输出、状态翻转、闸口四项，
改完把整份文件贴给我看一遍。
```

判据明确之后，接下来拆解卡片本身的交互设计。流水线上包含两道闸门：出审与确认发布。
审核卡对应出审环节，确认发布卡对应 `approved` 之后的二次确认。两张卡片承载的字段配额各有侧重。

审核卡的目标是支持三十秒内评估六项判据。直接在卡片展示的字段，只能是便于快速浏览的内容：标题与首句钩子（用于评估语气）、选题定位标签（用于评估定位）、封面缩略图（用于评估部分观感）。
事实、时效和合规三项无法浓缩为简单摘要，需要在卡片附带口播稿全文链接，供点击查阅完整文案。人工在细致核对上花费的时间省不掉，卡片的作用是节省在不同窗口和目录间来回查找文件的时间。

卡片配置两个操作按钮：通过与打回。点击打回时提供文本框填写原因。
点击通过对应 `review` 流转至 `approved` 的出边。
点击打回对应 `review` 退回 `drafting` 的出边，打回原因同步记录到 `3-review.md`。
本地状态机中 `review` 往往还包含第三条出边（打回并挂起至 `rejected`），本版卡片暂不单独设置该按钮。是否将打回拆分出第二种路径、何时挂起至 `rejected` 而非退回 `drafting`，留待第 18 与 19 课的规范流程中明确，不在本课过早限定。

确认发布卡对应 `approved` 之后不可逆的操作边。参考流水线的 `pipeline/4-publish.md` 中有一项核心要求：必须先通过 dry-run 生成完整的发布命令与物料信息，推送至飞书供人工核对，经人工确认后才执行真实发布。
该卡片需要列出真发所需的全部具体信息：拼接完整的 `sau douyin upload-video` 命令、标题、话题标签、封面路径以及媒体文件清单。
这里无需设计折叠隐藏，所需确认的核心内容正是这些字段本身，隐匿信息反而会增加误发风险。

操作按钮同样设置两个：确认发布与取消。
点击确认发布将执行真发动作，发布成功后调用 `media publish-done` 进行记账。点击取消则维持在 `approved` 状态，不执行状态流转，等待后续人工重新确认。

| 卡片 | 卡片作用 | 上卡字段 | 点进去看 | 按钮 | 触发后去哪 |
|---|---|---|---|---|---|
| 审核卡 | 出审闸口，判六项人审判据 | 标题、钩子首句、定位标签、封面缩略图 | 口播稿全文 | 通过 / 打回（带原因） | 通过到 `approved`；打回到 `drafting`，原因写进 `3-review.md` |
| 确认发布卡 | `approved` 之后的二次确认，防误发 | 完整发布命令、标题、话题标签、封面路径、媒体文件清单 | 无，字段本身就是要确认的东西 | 确认发布 / 取消 | 确认发布触发真执行，成功后 `media publish-done` 记账；取消停在 `approved` |

如果卡片字段排布过长，导致无法在三十秒内完成浏览，常见原因是将属于二级查阅的内容一股脑放到了卡片正面。若把完整的口播稿直接铺在审核卡片上，人工需要划屏翻到底部才能找到操作按钮，这就失去了卡片的便捷性。将详细内容收进二级链接查看，是字段配额规划的必要策略。

字段草案清晰后，将其落地为可运行的技术通道，需要进入完整的 SPEC 流程。

## 四、收尾：第二件重活

不可逆动作表理清了哪些操作改错后可以重来，哪些操作无法撤销：`media flip` 属于可逆操作；而真实发布、付费配音、公开呈现与终态记账属于不可逆操作。
卡片字段草案明确了人工在各个节点需要审阅和点击的内容：审核卡呈现快速浏览字段，二级链接呈现口播全文；确认发布卡完整展示发布命令和关联物料，不隐藏关键参数。

草案目前明确了字段清单，后续的技术实现仍有一系列具体问题需要解决：
飞书通道选用长连接还是公网 webhook 方案；
卡片的消息结构如何分层组织；
用户点击按钮后飞书接口保留多久的响应超时窗口；
如果单个飞书应用后续扩展至多条业务线，如何隔离事件避免按钮回调相互干扰。

这些技术细节需要一套完整的规范来收敛。不可逆动作表和卡片字段草案已经就绪，接下来的任务是在第 18 课展开飞书通道 SPEC 的推导。
