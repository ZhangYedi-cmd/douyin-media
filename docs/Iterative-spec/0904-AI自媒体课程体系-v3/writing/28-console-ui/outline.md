## 1. AppShell 与两个数据 hook：先立骨架不建页面
核心判断: 六个页面共用同一套取数逻辑，骨架课先把「怎么拿快照」「怎么听变化」做成 hook，页面只管拿到数据之后怎么摆。
支撑材料: 参考流水线 `packages/ui/src/` 的 AppShell、快照 hook、SSE hook 实现（调研待补）；附录 overview.html 的 sidebar/topbar 结构
交付物: 一张职责表（AppShell / 快照 hook / SSE 订阅 hook 各负责什么）；一条 Prompt 让 AI 实现 AppShell（导航+布局）和两个 hook
二级标题: 不分
收尾交接: 骨架立起来了，可以往里面摆颜色和第一批页面

## 2. theme token 映射：抄设计稿的颜色，不重新配色
核心判断: theme.css 里的 token 是设计稿唯一的真相源，前端不自己挑颜色，把 token 映射进组件库配置就够了
支撑材料: 附录 css/theme.css 的 token 列表（--accent/--success/--warn/--danger/--radius-*/--text-*）
交付物: 一张映射表（token 名/组件库配置项，至少覆盖强调色、成功/警告/危险色、圆角、字号）；一条 Prompt 让 AI 读 theme.css 生成映射代码
二级标题: 不分
收尾交接: 视觉基调定了，可以落第一批页面了

## 3. P1 总览、P3 详情：先落头两页
核心判断: 总览页只做一件事，十秒内告诉人今天正常吗、有几条在制、有什么要我处理，不做操作入口；详情页是唯一既展示又触发写操作的页面，决策区按钮按 allowedTransitions 动态渲染，不把状态机逻辑抄一遍搬到前端
支撑材料: 附录 overview.html（今日运行卡/警报/待办结构）、detail.html（审核决策区、readiness、check-list、发布确认弹窗的 publish-steps 预览）
交付物: 两条 Prompt（P1 接 GET /api/overview；P3 接 GET /api/content/:slug + 写 API）；两组验收清单
二级标题: 3.1 P1 总览：晨检、警报、分级待办 / 3.2 P3 详情：读为主、决策为辅
收尾交接: 两页可用了，数据层的路子跑通，剩下四页照着补

## 4. P4 选题池、P5 治理线：照骨架补，界面说人话不说系统话
核心判断: 这两页字段最多来自内部技术命名（触发方式、状态标记），界面文案要按对照表换成工作流语言，不能把契约文档的措辞原样搬上屏幕
支撑材料: 附录 backlog.html、harness.html 结构；附录 26-界面用语对照表.md（状态词、触发方式、页面副标题三张表）
交付物: 一条 Prompt 落成两页，数据接 GET /api/backlog、GET /api/harness，写操作接 backlog-apply、apply-proposal；一张文案核对清单
二级标题: 不分
收尾交接: 选题池和治理线能看能点了，还剩两页

## 5. P2 看板、P6 数据复盘：只读页面的最后两块
核心判断: 看板是全局状态的横向铺开，数据复盘是发布之后的效果回看，两页都只读，不接写操作
支撑材料: 附录 kanban.html（看板列结构）、metrics.html（空态「暂无数据」的现有写法）
交付物: 一条 Prompt 落成两页，数据接 GET /api/contents、GET /api/metrics；验收清单两点
二级标题: 不分
收尾交接: 六页全部落地，剩最后一步：拼成一个能直接打开、并且验证过读写两条路径的站点

## 6. 单端口出整站，并验证读写两条路径都通
核心判断: 开发和生产不是两套部署形态，前端构建产物交给 server 托管静态文件，一个端口就能起整站；模块 7 出口条件是六页能看、快写和慢作业两条写路径都能从界面上真的走一遍
支撑材料: 参考流水线 server 静态托管实现（调研待补）；第 25 课 cc-stream 的里程碑展示思路（慢作业进度参考）
交付物: 一条命令块（构建前端+启动 server+打开浏览器验证六页可达）；四点验收清单
二级标题: 6.1 单端口出整站：前端构建产物由 server 托管 / 6.2 验证：六页可看，两条写路径都通
收尾交接: 六页整站跑起来了，这套东西建完了
