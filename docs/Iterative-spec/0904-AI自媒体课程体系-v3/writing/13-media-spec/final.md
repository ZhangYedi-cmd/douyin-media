# media 写 SPEC：把决策拆到能施工的粒度

上一课交付了 `docs/spec/media/00-调研.md` 和 `01-ADR.md`，四组互斥路线（入口形态、YAML 写法、并发保护、派生视图）都拍完板了。但 ADR 只回答了一件事：选哪条路。它没有回答第二件事：这条路上有十几条命令，每一条的参数是什么、读哪些文件、写哪些字段、失败了怎么报，AI 拿着一份只写着决策结论的文档，照样没法动手写代码。

记忆锚点：决策落了纸不等于能施工，执行方案要把每条命令拆到读什么、写什么字段、失败怎么报这个粒度，AI 才照得着做。这一课的输入是这两份文件，加上第 11 课钉死的执行方案四节模板；产出是一件东西：`docs/spec/media/02-执行方案.md`。

## 1. 开篇：把决策展开成规格

写 SPEC 这一步不产代码。产的是一份文档，四节，节名和节序都不许改，直接抄第 11 课钉死的格式：

```
# 02-执行方案
## 1. 实施步骤    按顺序编号第 1 步到第 N 步；每步 = 做什么 / 产出物 / 验收标准 / 依赖
## 2. 命令 × 功能 × 详细设计    逐条穷举
## 3. 对外契约    本部分提供给 / 依赖其他部分的接口
## 4. 风险与待定项    拍板未覆盖的点全部落这里，标注需要用户裁决的项
```

第二节的单位换成了命令，因为这次要造的是 media 这个命令行工具，不是接口也不是页面，其余三节的名字原样照抄。

为什么 ADR 不够用，举个具体的例子。你的 ADR 里可能写着并发保护这一项选了文件锁，理由是实现简单、不用起一个数据库或者常驻进程。这句话对不对，够不够，取决于你接下来打算怎么用。AI 拿着这一句话去写代码，得自己决定锁文件放在哪、锁多久算陈旧、抢占失败的时候退出码该是几、报错信息里要不要写清楚是哪个进程占着锁。这些问题 ADR 一个都没答，但代码里每一处都得有一个确定的答案。执行方案要做的，就是把这些还没被回答的问题，一条一条摆出来，逐条给答案。

参考流水线里有一份长得几乎一样的文档，`docs/Iterative-spec/0818-看板工作台/01-CLI执行方案.md`，五百多行。它开头第一句话写得很直白：本文只做两件事，把拍板拆成天级步骤，把每条命令与 core 模块写到可照抄实现的粒度，决策理由一律回指拍板章节，不复述。这句话本身就是这一课要立住的判断：SPEC 文档不重新讲一遍为什么，为什么已经在 ADR 里定过了；它只管把定下的东西翻译成能照着写代码的粒度。你自己的 `02-执行方案.md` 不用有那份文档那么大的篇幅，它撑的是看板项目三个包的施工，你只写 media 一个命令行工具，但四节的骨架和这个粒度要求是一样的。

模板定了，先填最费工的一块：十四条命令。

## 2. 命令 × 功能 × 详细设计：十四条逐条穷举

### 2.1 十四条命令逐条四件套（参数 / 读什么 / 写什么字段 / 失败怎么报）

这里说的四件套，指参数、读、写、失败怎么报这四项，跟第 11 课起用的六步方法四件套（调研模板、ADR 模板、执行方案模板、施工记录模板）不是一回事，两边只是凑巧都是四项，别混着用。

只写命令名加一句话描述，AI 写代码时会自己去补没写清楚的地方。比如只写 media flip 命令用来翻转状态，AI 多半会自己决定要不要做事务、要不要在写之前先校验、失败了要不要报错退出。这些决定十有八九跟你想要的不一样。四件套把每条命令的输入输出边界锁死：参数是什么、要读哪些文件才能判断这次操作合不合法、合法之后具体写哪个文件的哪个字段、不合法的时候报什么错。四项一个都不能少，读命令的写这一栏填无，也要显式写出来，不能跳过不提。

参考流水线是怎么填这四栏的，拿它的 flip 命令举个例子：

| 项 | 内容 |
|---|---|
| 参数 | slug（必填）、目标状态（必填）、--reason（仅目标为 rejected 时必填） |
| 读 | 该条内容自己的元数据文件 |
| 写 | 元数据文件的状态字段和对应的时间戳字段，外加派生看板的机器区 |
| 失败怎么报 | 目标状态不在当前状态的合法出边里，报错并在提示里列出当前状态还能去哪几个状态；rejected 没带 --reason 单独报一种错；目标是发布类状态一律拒绝，提示改走发布收尾命令 |

表里说的机器区，指看板文件里由标记圈出来的一块，内容每次由命令自动重新算出来重写；标记外的叙事文字仍然是人手写的，命令不碰。

这张表最后一行是这条命令里最容易被漏写的部分：报错不能只说不合法，要在提示信息里带上当前状态还能去哪几个状态，AI 看到用户在错误状态上重试才有得选，不用回头再问一遍。

十四条命令具体是哪十四条，ADR 没定，第 12 课的四组决策定的是怎么写，不是写哪些，这份清单要在这一课里先钉住。pipeline 五份契约（1-ideate.md、2-create.md、3-review.md、4-publish.md、daily-run.md）里描述的取题、出审、发布收尾三步，是你已经手改过 meta.yaml、backlog.yaml 记账的地方；飞书那边的审核回调（17 到 19 课）、选题池的入池和清扫（23 课）、复盘收口（22 课），这三类你现在还没碰到，是后面几课才会加进来的写点。六类动作加起来，一类至少对应一条写命令，命令清单现在就把还没碰到的三类位置留出来，理由是入口一次定完，比以后每加一课就回来改一次执行方案省事；再加上不动文件、只回答问题的查询和体检类命令。两类加起来，落地是十四条：

读命令（5）：总览与单条查询（st）、模拟取题（next）、选题池查询（backlog ls）、一致性体检（check）、产物体检（doctor）。

写命令（9）：取题记账（promote）、状态翻转（flip）、发布收尾（publish-done）、批量入池（backlog add）、机械清扫（backlog sweep）、落地人审提议（backlog apply）、人钦点取题指针（next-up）、重建看板（dashboard rebuild）、复盘数据落账（metrics record）。

```
读 docs/spec/media/01-ADR.md 里关于入口形态和 YAML 写法的两条决策。
下面这十四条命令，逐条拆成四件套，一条不许省：
读命令：st、next、backlog ls、check、doctor
写命令：promote、flip、publish-done、backlog add、backlog sweep、
       backlog apply、next-up、dashboard rebuild、metrics record
1. 参数：必填参数、可选参数、每个参数的取值范围
2. 读：这条命令要读仓库里哪些文件才能判断这次操作合不合法
3. 写：写命令写清楚具体改哪个文件的哪个字段；只读命令这一栏写无
4. 失败怎么报：校验不过时报什么错误、提示信息里要不要写出当前状态
   还能去哪几个状态
写命令额外标一句：这条命令要不要走完整事务
（拿锁、算写计划、支持 dry-run、原子落盘、写审计记录这一整套），
还是只改一处字段就够。字段名和写法按我的 01-ADR.md 里的决策来定，
不要照抄任何示例里的字段名。
```

拿到结果审三点。第一，十四条是不是一条不少，AI 有时候会把两条相近的命令自己合成一条，得数一遍。第二，每条的失败怎么报是不是给出了具体的报错类型和提示语，不能是一句会报错这种空话。第三，事务性写命令是不是标出了要不要走完整的事务流程，只改一处的轻量写命令和要保证多文件一起落盘的重写命令，不能用同一套实现。

如果 AI 交回来的结果里有的命令写了参数却没写失败怎么报，多半是没把四件套当成硬性模板，只当成了一个参考格式。这时可以在 Prompt 里再补一句：四项一个不能少，写不出来的那一项也要注明为什么写不出来。

只读命令里有一条 check，它读的东西比别的命令都多，值得单独说一句。它读的是全仓的状态快照，判定标准是一整套规则，参考流水线里这套规则一共八条，从双层状态对不上、条目断链、超时没人回填，到疑似哪天忘了出内容，各管一类问题：

| 规则 | 级别 | 判定什么 |
|---|---|---|
| CHK-01 双层不同步 | error | meta 的状态和 backlog 的状态没对上 |
| CHK-02 断链 | error | backlog 是已取题状态，但对应目录或元数据缺失 |
| CHK-03 超时未回填 | error | 定时发布的状态停留太久没人回填结果 |
| CHK-04 审核积压 | warn | 停在审核状态太久没人处理 |
| CHK-05 链接待补 | warn | 已发布但没有回填作品链接 |
| CHK-06 指针断裂 | warn | 元数据里的来源指针和选题池对不上 |
| CHK-07 临近过期 | info | 选题快要被清扫规则命中 |
| CHK-08 疑似空跑 | warn | 到了该出内容的时间点还没有新内容，也没人上报 |

这八条规则盯的字段（状态、来源指针、发布链接），都是你从第 03 课起就一直在用的同一批字段，拿这张表当自己 check 命令的起点没问题；如果你的 01-ADR.md 给某个字段起了别的名字，把规则对应到自己的字段名上再抄，不要连名字一起照搬。八条，不是七条，这是很容易在转述时漏一条的地方，写自己这一节的时候拿这张表逐条核对，别凭印象数。

### 2.2 状态迁移表：谁能到谁、谁触发、前置条件是什么

状态机不能写成一段散文，写成散文的后果是每次有人要判断某个跳转合不合法，都得重新读一遍那段话，读出来的理解还可能不一样。按数据描述规则写成表，一眼就能查：从哪个状态、到哪个状态、谁触发这次跳转、前置条件是什么、需不需要附理由。

你手改过的元数据状态，到现在只有三档：ideated、drafting、review（第 10 课成稿写得明白，合法的状态值到目前为止只有这几档）。approved、scheduled、published、rejected、retro_done 这五档，是参考流水线全套状态机里发布之后才会用到的名字，你还没碰过；选题池那边，你用过的是 idea、picked，published、expired、rejected、archived 同样是后面几课才会用到。执行方案要做的不是造新名字，是趁这一课把迁移表画全，等第 20 课真正发布时不用回头再补。挑几行做个样子：

| from | to | 触发命令 | 前置条件 | 需要理由 |
|---|---|---|---|---|
| ideated | drafting | flip | 无 | 否 |
| review | approved | flip | 无 | 否 |
| review | rejected | flip | 无 | 是 |
| approved | published | publish-done | 当前状态是 approved | 否 |
| published | retro_done | flip | 只能由治理线那条线触发，生产线不能碰 | 否 |

最后一行值得多说一句：同一个命令，谁在什么场景下能调，也是迁移表要管的事。发布之后转复盘完成这一步不是任何人都能触发，是治理线专属的动作，生产线的自动化不能顺手把它翻了。这类前置条件写进表里，比写在旁边的一段说明文字里更不容易被漏看。

```
参考我们从第 03 课开始手改元数据和选题池时实际用过的全部状态值，
画两张迁移表：
1. 元数据的状态迁移表：from / to / 触发命令 / 前置条件 / 是否需要理由
2. 选题池的状态迁移表：同样五列
穷举每一个当前状态能合法到达的下一个状态，没写到的组合视为非法。
特别检查这两类边：审批之后允许反悔退回上一个状态吗，如果允许，
在哪个状态生效；哪几条跳转只能由治理线触发，生产线的自动化不能碰。
这两类是最容易漏写或者写反的地方。
```

如果状态迁移表里出现了一个你从来没在过去十二课手改过的新状态名，多半是 AI 照抄了别处看到的状态机习惯，回去对照你自己 01-ADR.md 和过去手改过的元数据文件核实一遍，不属于你这个项目的状态名不要收进表里。

十四条命令拆到能施工的粒度了，还差一件事：这么多命令分几批做。

## 3. 实施步骤：里程碑怎么切

里程碑不是按代码模块切的。不能说先把底层的解析和状态机部分做完，再做命令行外壳这一部分，这是按技术边界切，不是按能不能验证切。真正该问的是：做到哪一步，能拿真实数据跑出一句能验的话。跑不出这句话，这个里程碑就还没到终点，哪怕代码看起来已经写完了。这门课后面两课的课名直接叫执行 M1、执行 M2，下文也用 M1、M2 指代这两个里程碑。

参考流水线是这么切的：M1 做完读命令、事务写入引擎，加两条历史上出过事故最集中的写命令，M2 补齐剩下的写命令，加上把过去手编的写点全部切换过去。为什么先切这两条写命令，理由写在它自己的方案里：历史事故集中地先切。这两条命令对应的场景，一条是发布收尾三处文件要一起改对却总有一处漏掉，一条是定时发布到点了没人回填结果导致状态卡住没人发现。这两类问题在那条流水线上是真实出过事故的地方，先把出过事故的地方管起来，比先把用得少的命令做完更划算。

这条理由能不能直接搬到你自己的项目上，得看你自己在过去十二课里手改这几个文件的时候，哪几处最容易出错、踩过的坑最集中。这是从你自己的经验里推出来的，不是照抄参考流水线的步骤编号。

```
读 docs/spec/media/02-执行方案.md 现在已经写好的第 2 节
（十四条命令四件套和状态迁移表），提两个里程碑方案：
1. 里程碑不按代码模块切，按能不能拿真实数据跑出一句能验的话切
2. 参考我自己 pipeline 各阶段契约和各个 skill 里现在还在手改
   meta.yaml、backlog.yaml、dashboard.md 的那几处，这十四条命令里
   哪几条对应的手编写点最容易出错，放进第一个里程碑
每个里程碑给三样：里程碑名、做什么（对应哪几条命令）、出口条件。
出口条件必须是一句能跑的验证动作，不许写基本完成、差不多了这类
判不出真假的话。
```

出口条件长什么样，这门课从第 11 课起一直用同一个标准：一句能跑的验证动作。M1 对应的出口条件可以是这样：真实仓库里跑 media check 能通过，YAML 文件里原有的注释一处都没丢。M2 对应的出口条件可以是这样：全仓状态写路径唯一，连续七天内元数据、选题池、看板机器区的每一次变更，都能在审计记录里找到对应的一行。这两句话前半句和后半句都能被单独判定真假，跑一遍命令、翻一遍审计文件就有结论，不需要靠感觉。

AI 给的方案先看两处：十四条命令有没有被 M1、M2 都覆盖到，一条都不能掉在外面没人管；出口条件是不是真的能跑，读一遍能不能立刻想出要执行哪条命令、看哪个文件，想不出来说明这句话还是空话，得接着往下拆。

如果出口条件写出来是基本跑通、大部分场景没问题这类说法，多半是从做完了这个结果倒着往回写判据，而不是先想清楚怎么验证，再决定要不要把这件事放进这个里程碑。倒着写出来的判据大概率判不了真假，得重写。

命令拆完、里程碑切完，这份规格已经可以拿去施工了。

## 4. 对外契约与风险待定项

第三、四节篇幅小，但不能因为篇幅小就省略。对外契约要写清楚这份规格交出去之后谁会用它、它又依赖谁；风险与待定项要把拍板阶段没顾上的点摆出来，不能自己在写文档的时候顺手悄悄拍了板。

对外契约这一节，一句话就能说完这次的核心内容：media 命令是全流水线状态写入的唯一入口，后续课要造的飞书闸口和各个 skill，涉及状态改动的地方都要改成调它，不再自己手改文件。参考流水线在这一节用一张表列出每个消费方拿走了什么契约，比如后端服务拿走的是这套命令的 JSON 输出格式和退出码含义，看板前端拿走的是几个共享的数据类型。这张表的列名固定：消费方、拿走什么契约、说明，你自己这一节暂时用不到消费方这么多，两三行就能列完，写清楚谁会调这些命令、依赖它返回的什么格式就够，不用凑满参考流水线那么多行。

风险与待定项这一节，是给还没被决策覆盖的角落留的地方。参考流水线在这一节留过不少条，比如锁文件放多久算陈旧没有立刻定死，先按一个默认值实现，留了个后续可以调整的口子；再比如某条规则的判定阈值定了默认值但没细究是不是最优，也照实记了下来等以后再调。这些都不是拍脑袋决定的空白，是明确写下来这里还没有答案、以后可能要改的地方。你自己的这一节可能是空的，如果 01-ADR.md 里四组决策已经把能想到的角落都想过了；也可能不是空的，只要你在填前面两节的时候心里冒出过一个没底的问题，就把它记下来，不要自己悄悄选一个答案糊过去。

```
按第 12 课的 01-ADR.md 和刚写完的第 2、3 节，补齐执行方案的第 3、4 节：
第 3 节对外契约，一句话说清楚这份规格谁会用、依赖谁；
第 4 节风险与待定项，把你在生成前两节内容时遇到过的、没有明确答案、
需要我来裁决的点都列出来，每条注明这是个什么问题，不许自己替我拍板。
如果确实一条都想不出来，写一句当前无风险待定项，不要留空。
```

四节都写完，检查一遍：任何一节留白都不许进入下一课的施工。实施步骤、命令详设、对外契约这三节不能是空的占位，风险与待定项如果确实没有可以写一句当前无，但节标题下面不能什么都没有。空着的地方意味着这件事还没有人想过，AI 照着这份规格施工的时候，会在这个缺口上自己拿主意，拿出来的东西大概率不是你要的。

执行方案写完了，可以开始施工。
