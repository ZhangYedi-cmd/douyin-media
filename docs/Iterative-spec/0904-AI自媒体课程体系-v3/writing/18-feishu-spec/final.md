# 飞书通道 SPEC：四个决策点怎么拍板

上一课交付了两份关键物料。一份是不可逆动作表，梳理出发出去无法撤回、产生扣费、对外可见、覆盖真相源这四类动作。另一份是卡片字段草案，列出了飞书卡片上需要呈现的字段初稿。
闸口设在哪里已经明确，但闸口如何落地还没有展开。
这一课针对飞书通道，执行六步 SPEC 方法的前四步：调研、讨论选型、决策与写 SPEC。后续的执行和验证留给第 19 课完成。

除了卡片字段草案，这一课还会用到第 02 课申请飞书自建应用时保存的凭据。包含 App ID、App Secret、Verification Token 与 `chat_id`。
同时也会沿用第 11 课沉淀的六步模板四件套：调研表固定四列、ADR 固定四项、执行方案固定四节与施工记录模板。这些规范直接复用，不再重新定义。
最终产出位于 `docs/spec/feishu-gate/` 目录下的三份文档：`00-调研.md`、`01-ADR.md` 与 `02-执行方案.md`。

记忆锚点：技术选型的关键在于每个方案能否讲清楚在什么边界条件下会失效，而不是凭个人偏好做决定。飞书闸口需要拍板的四件事，各自都存在看似更省事的备选路径。但这些路径往往潜藏着特定场景下的隐患。这一课的目标就是把这些隐患提前摆在台面上论证。

## 一、调研：企业自建应用怎么配，四个决策点是什么

### 1.1 六步配置照做

飞书自建应用的配置在第 02 课已经实操过。
具体包含五个操作：
在开放平台创建企业自建应用，获取 App ID 和 App Secret；
在应用能力中开启机器人并发布应用，把机器人拉入通知群；
在事件与回调中将订阅方式设为长连接，订阅 `card.action.trigger` 事件；
加密策略选择不加密，记录 Verification Token；
妥善保存上述配置字符串以及群聊的 `chat_id`。
这几个步骤依照官方文档操作即可，属于确定性配置。第 02 课已经拿到了对应凭据，这里无需重复操作。

这里需要补充一项前提约束。飞书开放平台要求自建应用挂靠在企业或团队账号下，纯个人版账号无法进入创建自建应用的入口。
你在第 02 课能够创建成功，说明使用的账号满足该条件。
在此单独说明，是因为这是整体流程中唯一需要账号身份资质的前提。这不是安装软件或执行命令能替代的。
后续如果需要在新机器上搭建，或者协助他人配置，先确认对方拥有能够创建自建应用的企业或团队身份。
如果缺乏该身份，飞书支持免费注册单人企业账号，花费几分钟完成认证即可，不涉及额外费用。

基础配置照常执行，接下来的四个待决策点才是六步方法需要深入推导的核心。

### 1.2 四个待决策点长什么样

基础配置明确了如何挂载应用，但尚未规定应用内部的具体协作逻辑。搭建完成之后，有四个核心问题需要决策：

- 通道形态：卡片按钮被点击后，回调事件如何投递到本地服务，选用长连接还是 webhook。
- 卡片结构：从推送待审内容到最终确认发布，中间需要经过几轮人工核对，每轮核对由几张卡片承载。
- 回调窗口：人工点击按钮后，服务端需要在多长时间内返回响应，响应窗口内允许处理哪些任务、应当剥离哪些任务。
- 命名空间：如果同一个飞书应用后续扩展至多条业务线，回调事件如何识别本次点击归属哪条业务线。

这四项决策如果出现偏差，第 19 课在编码实现时就会面临返工。
通道形态选错，服务端需要重构整体网络通信架构。
卡片结构规划不当，按钮与状态流转的映射关系需要推翻重来。
回调窗口处理不当，点击按钮后会毫无反馈，难以排查是网络延迟还是代码异常。
命名空间设计缺失，后续引入新业务线时，旧有代码均需逐一改造。
因此，我们需要逐项执行六步规范进行深入推演。

## 二、长连接与 webhook：两种回调订阅方式的对比

先摆两个候选各自的样子：

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 长连接（飞书官方 SDK 的 WebSocket 模式，服务主动连出去） | 本机无需公网地址，服务主动连向飞书，不依赖外部主动请求 | 服务需常驻运行，连接断开时需自动重连；本地存在常驻进程，重启后需重新拉起 | 常驻进程被误杀或僵尸进程占连接，表现为点击无响应且无新日志 |
| webhook（飞书按 HTTP POST 把回调事件推到指定地址） | 服务已部署在具备公网地址、能被外部直接访问的机器上 | 本机缺乏公网地址时，需额外引入内网穿透工具暴露端口，增加了维护负担 | 内网穿透连接断开或配额耗尽，表现同样为无反馈，但排障环节多了一层外部依赖 |

本地开发机通常不具备公网可达的固定 IP。若选择 webhook，必须先解决网络暴露问题，额外引入一层内网穿透。
依赖越多，系统脆弱点就越多。穿透工具自身存在断连风险和额度限制。这种依赖不属于业务本身需要解决的问题，完全是为满足 webhook 前提而附加的负担。
长连接方案不需要公网地址。服务主动向飞书发起连接，本地机器是否具备公网访问能力均不受影响。

把这条判断走一遍讨论选型，让两个候选各自交代清楚自己的账。这条 Prompt 后面三节复用同一个模板，只换候选和场景描述：

```
针对"长连接"和"webhook"这两个飞书卡片回调订阅方式，分别扮演它们的
支持者，依次回答四件事：
1. 这个方案在什么场景下是对的选择？
2. 选它要多付出什么代价？
3. 主动交代它已知的失败模式：什么情况下它会输，输给对方？
4. 不要下"综合来看方案更好"这类结论，只交代前三条。
两个方案都要独立走完这四步，不要在中途比较。
背景：这台机器是我自己的开发机，日常联网但没有公网可达的固定地址。
```

如果某个方案只罗列优点，讲不清楚具体的失败模式，常见原因是问题背景描述过于模糊。比如对开发机网络条件的描述不够明确，导致模型顺应这种模糊产生偏好。将背景事实明确写定为无公网地址，让各方案据此评估边界，重新提问即可。

通道形态确定采用长连接后，接下来规划卡片本身的拆分方式。

## 三、卡片结构：一张卡还是按流程拆几张

一条内容从提交待审到真实发布，中间涉及三次人工交互节点。
首先是内容审核，决定通过或打回。
打回后需要进一步确认，是自动重做还是挂起转为待办。
审核通过后进入发布确认，展示最终待执行的命令和物料摘要，人工确认后才执行真实发布。
这三次交互所需的展示字段和操作按钮各有不同，直接决定了卡片的结构形态。

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 单卡承载全部字段与按钮（通过、打回、打回原因、确认发布、取消集中于一张卡） | 从审核到发布仅有一两次简单触点，例如打回后直接结束，无需区分重做或挂起 | 每次状态变更均需在单张卡片内动态控制字段显隐，卡片更新逻辑较为复杂 | 打回需要输入原因，若单卡同时堆叠通过按钮、打回按钮、原因输入框与发布按钮，状态切换间隙容易发生误触 |
| 按流程拆分为多张卡片（审核卡、打回原因卡、确认发布卡相互独立） | 审核到发布存在多次交互，且各阶段字段与按钮差异较大 | 卡片状态流转依赖服务端主动推送新卡或原地更新，需要明确维护卡片与状态的映射 | 卡片流转过程中若旧卡未及时更新或失效，可能导致人工误点历史卡片且无法获得预期反馈 |

当前闸口完整覆盖了这三次交互。如果塞入单张卡片，就必须在三种状态间频繁切换展示内容，在状态流转瞬间容易出现显示不一致。
参考流水线采用拆卡方案，由三张卡片分段负责不同环节。
审核卡展示选题标题、类型与目录，提供通过和打回两个按钮。
打回原因卡提供输入框供填写具体理由，提供打回并自动重做、打回并挂待办两个按钮。
确认发布卡展示物料摘要与待执行的命令原文，提供确认发布和取消两个按钮。若物料检查不合格，则仅展示取消按钮。
三张卡片累计包含六个按钮，未设置第七个查看全文按钮。文稿全文与封面图片在推送审核卡之前，已作为独立消息预先发送。人工在点击按钮前已审阅完整物料，卡片上无需重复冗余展示。

这里对第 17 课的卡片字段草案做出了两处演进，需要在此说明。
第 17 课初稿曾设想在审核卡展示封面缩略图并附带口播全文链接，打回按钮自带输入框。
在这一课定稿时调整为：口播文稿与封面改为在推卡前通过独立消息先行发送。飞书单张卡片排版篇幅有限，独立消息更便于直接滑动阅读，省去二级点击展开的步骤。
此外，打回原因由审核卡内的输入框独立拆分为专门的打回原因卡。飞书交互规范要求输入框与提交按钮平铺于同层，强行合并在审核卡容易与通过按钮产生视觉干扰。
第 17 课遗留的决策点（打回后是自动重做还是挂起），在这一课正式确定为打回原因卡上的两个独立按钮。

把这条判断走一遍讨论选型：

```
针对"一张卡装完所有字段和按钮"和"按状态拆审核卡、打回原因卡、
确认发布卡三张卡"这两个方案，分别扮演它们的支持者，依次回答：
1. 这个方案在什么场景下是对的选择？
2. 选它要多付出什么代价？
3. 主动交代它已知的失败模式：什么情况下它会输？
4. 不要下综合结论，只交代前三条。
背景：从审核到发布一共有三次人工触点（通过或打回、打回后选重做
还是挂起、确认发布或取消），三次触点各自的字段和按钮都不一样。
```

结果需要重点关注一项细节：打回原因输入框是否得到了充分讨论。
这是卡片设计中容易忽略的环节。部分方案习惯将打回与填写理由合并为单步操作，但在飞书卡片中，文本输入框有明确的布局规范。
输入框与两个提交按钮必须平铺在同一层级，不可嵌套进容器组件中，否则输入框无法正常渲染。
这一技术细节在第 19 课编码实现打回原因卡时需要特别注意，在此提前记录便于后续排查。

卡片结构明确后，接下来需要界定按钮点击后的响应时限。

## 四、3 秒回调窗口：同步与异步路径的分工

人工点击卡片按钮后，飞书服务端要求在 3 秒内返回响应。如果超时，飞书会将此次回调判定为失败并抛出错误码。
该时限由平台底层协议规定，无法协商。我们能够掌控的是在 3 秒窗口内安排哪些操作，剥离哪些操作。

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 同步路径仅处理内存操作与状态标记 | 3 秒内操作极轻量：判断归属事件、拼接提示文本、组织原地更新的卡片数据 | 耗时任务需剥离至异步执行。用户点击后先看到处理中的提示，而非最终结果 | 若不慎在同步路径加入网络调用，网络抖动时容易突破 3 秒限制 |
| 同步路径同步执行完整任务后再返回 | 任务本身能稳定在 3 秒内执行完毕 | 涉及状态记账、文件读写或外部进程调用的操作耗时波动较大，难以保障稳定在 3 秒内返回 | 启动子进程执行真实发布或重做通常需要数秒至数分钟，同步等待通常会导致回调超时 |

真正的重做或发布操作依赖外部子进程执行，耗时不可控，无法在 3 秒内完成。因此同步路径必须严格限制在轻量操作范围。

同步路径负责识别本次回调是否归属本机处理（内存字符串比对）、组装向用户展示的轻量提示文案（内存文本拼接），以及构建用于原地更新的卡片数据。卡片数据可直接随响应体同步返回，无需额外发起网络请求。
参考流水线还将打回护栏的检测置于同步路径。通过读取本地审核记录文件，快速统计当前内容的重做次数。这类单次本地文件读取耗时极短，可以纳入同步窗口。

异步路径则承载重型任务。
第一，执行状态记账，调用第 15 课收敛且经第 16 课验证的 `media flip` 写入命令。
第二，拼装发布物料。
第三，启动子进程推进重做或发布任务，向抖音平台推流。
第四，将最终处理结果异步写回卡片。
最后一步容易被忽视：卡片虽然在同步阶段已通过响应体完成一次即时更新，但在耗时任务结束后，通常需要再次更新卡片以展示终态结果。这第二次更新属于独立的网络请求，必须放入异步路径执行。

同步和异步两条路径的分工，是这条决策要落进执行方案的核心内容，先用一张表把两边各自装哪些动作定死，供第 19 课直接对着实现：

| 路径 | 装的动作 | 允许的操作类型 |
|---|---|---|
| 同步（3 秒窗口内） | 命名空间校验、组装提示文案、组装原地更新卡片、读取本地文件核验打回次数 | 内存操作、单次本地轻量文件读取，严禁网络请求 |
| 异步（另起线程或子进程） | 执行状态记账、组装发布物料、启动子进程执行重做或发布、向飞书推送终态卡片 | 允许网络请求与子进程调度，不受 3 秒时限约束 |

飞书回调超时报错的错误码为 -356。在参考流水线的排错记录中，该错误通常源于两类情形。一类是点击的卡片不属于当前服务管辖，事件被静默忽略导致飞书未能收到应答；另一类是同步路径中误引入了网络通信，导致处理耗时超出 3 秒。遇到该错误时，可优先排查同步路径中是否混入了非内存操作。

回调窗口界定完毕后，最后一项决策是单个应用如何安全支持多条业务线。

## 五、命名空间隔离：一个应用服务两条线

飞书自建应用可以加入多个群组，也可同时服务多个业务工程。如果后续在抖音流水线之外引入新的业务线，甚至共用同一个沟通群，服务需要准确识别每次按钮点击归属哪个项目。

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 各业务线创建独立应用 | 各业务线均在开放平台申请专属应用，隔离 App ID | 每条业务线均需重复完整的申请配置流程，增加了凭据维护成本 | 无。从源头隔离不存在串线风险，代价主要在于前期申请和日常维护成本 |
| 复用单一应用，通过命名空间字段过滤 | 已有现成应用，希望复用以减少重复配置 | 卡片按钮 value 载荷中需统一注入命名空间标识，收到回调时需先行比对过滤 | 多实例监听时飞书按负载均衡投递，不广播；若未匹配命名空间直接丢弃，旧卡容易被静默忽略 |

关于复用应用的失败模式，需要清晰理解飞书底层的投递机制。当多个服务实例同时建立长连接监听同一个应用时，飞书采用负载均衡策略将事件投递给其中某一个实例，而非向所有实例广播。
如果两条业务线各自启动服务监听同一应用，某次按钮点击可能被另一条业务线的服务接收。
命名空间字段的作用，是在事件被接收后提供判断依据。接收方首先校验事件的命名空间是否与自身匹配。若不匹配则立即丢弃，不越权处理非归属任务，从而保障各自处理流程不受干扰。

这项决策在实现层面十分清晰：卡片所有交互按钮的 value 结构中统一增加命名空间字段。服务端接收到回调后，首要操作是将该字段与本地配置比对。若不一致则直接返回，终止后续处理。

把这条走一遍讨论选型：

```
针对"各业务线各建独立应用"和"复用同一个应用，靠卡片 value 里的
命名空间字段过滤"这两个方案，分别扮演它们的支持者，依次回答：
1. 这个方案在什么场景下是对的选择？
2. 选它要多付出什么代价？
3. 主动交代它已知的失败模式：什么情况下它会输？
4. 不要下综合结论，只交代前三条。
背景：目前只有一条业务线在用这个应用，但以后可能会加第二条，
第二条线要不要单独申请应用还没定。
```

排障记录：若点击卡片后系统无响应，常见原因是卡片中的命名空间与当前服务配置不一致，导致事件被静默过滤。可优先核对点击的是否为最新推送的卡片，排查历史旧卡中命名空间字段缺失的情况。

四个决策点推导完毕后，统一收敛至正式的 ADR 与执行方案中。

## 六、决策与写 SPEC：ADR 四项与执行方案四节

四个决策点统一收敛进同一份 `01-ADR.md`，记录为四条独立条目，避免文档碎片化。执行方案同样汇总为一份 `02-执行方案.md`，按统一的四节规范组织。相关文档规范存放在 `docs/spec/feishu-gate/` 目录下。

`00-调研.md` 完整收录本课第 2 至 5 节的四组对比表，依次呈现通道形态、卡片结构、回调窗口与命名空间，并在每张表前简要阐明对比维度。该文档不重复选型论证细节，论证过程由 ADR 中的决策理由进行引用。

`01-ADR.md` 四项固定：决策、理由、被否方案、反悔成本，多的字段不加：

```
ADR-1 通道形态
决策：长连接（飞书官方 SDK 的 WebSocket 模式）。
理由：开发机没有公网可达的地址，webhook 需要额外接一层内网穿透
  工具，多一层依赖就多一层会挂的地方；长连接是服务主动连出去，
  不依赖机器本身能不能被外部访问到。
被否方案：webhook。
反悔成本：中。以后如果服务改跑在一台有公网地址的机器上，换成
  webhook 只需要改接入方式，业务处理逻辑不用动；但现在这个阶段
  换成 webhook，要先解决没有公网地址这个前提缺失的问题。

ADR-2 卡片结构
决策：按状态拆三张卡——审核卡、打回原因卡、确认发布卡，各两个
  按钮，没有查看全文按钮。
理由：从审核到发布有三次人工触点，三次触点的字段和按钮完全不同，
  装进一张卡意味着同一张卡要在三种状态间切换显示内容，比拆成
  三张卡更容易在状态切换的瞬间露出破绽；文稿全文和封面已经用
  独立消息先发过，卡片不需要重复承载。
被否方案：一张卡装完全部字段和按钮。
反悔成本：低。三张卡各自独立，以后要再加一次人工触点（比如
  发布后再加一次复核），加一张新卡不影响已有的三张。

ADR-3 回调窗口
决策：同步路径只做内存操作和状态标记，重活（状态记账、拼物料、
  起子进程做重做或发布、更新最终结果）全部甩到异步路径。
理由：飞书要求 3 秒内响应，超时报错；真正的重活背后是起子进程，
  耗时是秒级到分钟级，稳定在 3 秒内跑完做不到。
被否方案：同步路径直接跑完重活再返回。
反悔成本：高。想改回同步路径直接跑完重活再返回，前提是重活本身
  能稳定压缩到 3 秒内，但状态记账、拼物料、起子进程这几步只要沾上
  网络调用或者进程调度，耗时就不受控，这个前提基本凑不齐，退不
  回去。

ADR-4 命名空间隔离
决策：复用同一个应用，靠卡片 value 里的命名空间字段过滤，不属于
  自己命名空间的事件收到即丢弃，不处理也不报错。
理由：目前只有一条业务线，暂时不需要为了隔离而重复申请应用；
  命名空间字段的实现成本是一个字段的读写比较，比维护多套应用
  凭据轻。
被否方案：各业务线各建独立应用。
反悔成本：低。以后真的要拆成独立应用，把命名空间字段原样保留
  当冗余校验也不影响正确性，不需要先删掉这套过滤逻辑再拆分。
```

`02-执行方案.md` 沿用第 11 课固定下来的四节模板，第二节的单位换成决策点：

```
# 02-执行方案
## 1. 实施步骤
## 2. 决策点 × 功能 × 详细设计
## 3. 对外契约
## 4. 风险与待定项
```

第 1 节实施步骤，以能否用真实点击验证具体结果为切分依据，不按代码模块切分。
整体规划为三个阶段。
第 1 步，搭建仅做命名空间校验与日志记录的服务骨架。产出物为稳定常驻的后台进程。验收标准是在飞书中点击测试卡片，本地日志准确记录该点击匹配自身命名空间。依赖第 02 课保存的 App ID、App Secret 与 Verification Token。
第 2 步，接入三张卡片模板与按钮事件分发。产出物为具备发送能力的三张卡片。验收标准是从推送审核卡到点击确认发布卡，完整交互流程在真实走查中全部跑通。依赖第 1 步的服务骨架。
第 3 步，落实 3 秒窗口内的同步与异步拆分。验收标准为人为增加异步操作延时，同步响应依然在时限内成功返回，不触发超时异常。依赖第 2 步已调通的事件分发。

第 2 节详细设计部分，对四个决策点逐一落实具体实现方案。
通道形态方面，核心功能是实现服务常驻并监听回调。详细设计选用飞书官方 SDK 的长连接客户端。App ID、App Secret 与 Verification Token 从本地未纳入版本库的配置文件中读取。启动前需检测并排除残留进程占用连接。
卡片结构方面，核心功能是构建三张卡片的模板并支持状态联动。详细设计依据第 3 节规划的字段表分别编写。特别注意打回原因卡的输入框与两个提交按钮必须平铺在同一层级，严禁嵌套额外容器。
回调窗口方面，核心功能是划定窗口内外的任务边界。详细设计严格遵循第 4 节的分类表格。同步路径生成的卡片更新内容直接通过响应体同步返回，避免额外产生网络调用。
命名空间方面，核心功能是完成回调事件的业务过滤。详细设计要求卡片交互载荷统一附带命名空间字段。服务端接收到回调后首先进行比对，若不匹配则直接返回并终止后续流程。

第 3 节对外契约部分，明确本规范的上下游依赖关系。
这份 SPEC 直接指导第 19 课的代码实现，同时为第 20 课的发布 Skill 提供通信通道。
上游依赖第 02 课保存的应用凭据，依赖第 14 至 16 课收敛的 `media flip` 与 `media publish-done` 记账命令，以及第 17 课规划的卡片字段草案。

第 4 节风险与待定项部分，记录当前未展开的边界细节，避免过早替后续环节做假设。
主要包含以下事项。
一是自动重做是否需要设定次数上限以及超限后的兜底策略。这不属于本课的核心决策，留待第 19 课结合实际运行表现进行确定。
二是用户在打回原因卡未输入内容直接提交的处理方式。是视为空文本直接流转，还是拦截并提示补充说明，同样交由第 19 课处理。
三是后续接入多业务线时，除命名空间隔离外，是否需要引入更严格的应用权限鉴权。目前尚无多线需求，先行记录作为技术储备。

这一课结束时，四个核心决策点已经明确，`docs/spec/feishu-gate/` 目录下的三份文档已经完备。但在代码层面，常驻服务、卡片模板和回调分发尚未落地。
