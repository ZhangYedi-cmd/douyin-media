## 1. 双线边界：谁消费、谁保养
核心判断: 生产线只会把选题池和账号大脑当存量吃，从不往里补；没有一条独立的、按自己节奏跑的线专门负责保养这些存量资产，它们会越用越薄。
支撑材料: analyzed.md 材料 7（CLAUDE.md「系统一句话」）、材料 11（第 20 课结束时学员手上的清单，只有 pipeline/、brain/、backlog.yaml 头部，没有任何保养机制）
交付物: 生产线／治理线对比表（列：驱动方式、消费还是保养、动作是否可逆）
二级标题: none
收尾交接: 边界画完，第一条要立起来的铁律是治理线凭什么只能提议，不能自己动手改

## 2. 只提议不落笔：治理线的第一条铁律
核心判断: 治理线要碰的是账号大脑这类判断依据，自动改错了没人发现，等于让系统自己改自己判断对错的标准，所以这条边界必须写进契约，不能靠自觉。
支撑材料: analyzed.md 材料 1（harness/README.md 铁律原文）、材料 8（撰稿人自拟反例：误判怎么传导到下一轮选题打分）、材料 5（backlog-gardener 真实报告：存疑项标「建议人审」不自动合并，正例对照）
交付物: Prompt 让 AI 在学员自己的 `CLAUDE.md` 补一节「治理线铁律」；附一个反例（没有这条闸，一次误判会怎样传导到下一轮选题打分）
二级标题: none
收尾交接: 铁律立完，得有一个目录和一个字段把「这笔账归哪条线」钉死

## 3. harness 骨架与 line 字段记账
核心判断: 治理线要有自己的目录和状态迁移，`line` 字段是唯一能让机器判定「这笔账归生产线还是治理线」的地方，不能靠人记。
支撑材料: analyzed.md 材料 4（state.ts 的 TransitionSpec.line 字段与迁移表）、材料 1/2/3（harness/README.md、tasks.md、report-template.md 三份真实文件的结构）
交付物: Prompt 让 AI 起草学员自己的 `harness/README.md`（治理线定位与铁律）+ `harness/tasks.md`（任务注册表空壳，第 24 课填满）+ `harness/report-template.md`（治理执行记录报告模板）
二级标题: none
收尾交接: 骨架立完，读写边界还只是一句话，得落成一张表才防得住漂移

## 4. 资产读写表
