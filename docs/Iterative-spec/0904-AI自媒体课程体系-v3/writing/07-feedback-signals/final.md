# 反馈信号从哪来：把配音质检拆成能写成断言的六项检查点

一个 Loop 转不转得起来，先看它的输入信号有没有在动手写脚本之前就定义清楚。这一课拿配音质检当例子，验证这一句话。配音只是素材，用来把这句话落到具体判据上。

上一课交付了一张填完第 4 列的验证信号去向表：四个去向是流向人、流向机器、流向文档、流向没人管，学员知道哪些格子该交给机器。交给机器就得先有信号，这一课定这条流水线上第一个完整 Loop 的信号源。Loop 指检查出问题、判出该改什么、改完重跑、再拿同一条判据量一次，四步能自己转起来。它转起来的前提是第一步稳：检查这一步量的东西得清楚，量出来的数得可信，不然后面判、改、复核全都建在一个说不准的地基上。

本课处理的范围，是那张去向表里标机器的这一小片：配音合成完的一批 mp3，到录屏之前这一段。这一课的输入是这一片格子，加上学员第 05 课配音合成时自己真碰到过的问题，以及自己第 03 课写、第 04 课起持续在用的 `pipeline/2-create.md` 里配音审批那道闸口，还有 `brain/tts.config.json`。产出一件东西：一张配音批次检查点表，六行四列，行名是出错点，列是量什么、怎么量、阈值、谁来判。写成能跑出数字的脚本是下一课的事。

## 1. 检查点候选：从标机器的格子倒推

检查点不是先想清楚要测什么再列出来的，是倒着从哪些验证格子标了机器这件已定的事往回问出来的。凭空列一遍容易漏，漏掉的那一项通常要等成片出来才冒头，那时候能补救的手段只有重录。

候选靠两样东西倒推。一样是第 05 课配音合成完自己核对时真碰到过的问题：某段 mp3 是 0 字节，限流或者合成失败留下的空文件；听出来某段有字读错了；某段明显特别快或者特别慢；抽帧核对字幕和时长时发现某一步的画面被切断。

另一样是第 06 课那张验证信号去向表里标机器的格子，加上自己写的 `pipeline/2-create.md` 里配音审批那道闸口。这道闸口现在只写了一句话，闸口有两处，一处是配音审批，没有细节，这一课要把细节填进去。

```
下面是我第 05 课配音合成完自己核对时碰到过的问题（贴清单：0 字节的 mp3、读错的字、
特别快或特别慢的段、字幕和时长核对时发现的画面切断）。
下面是我上一课整理的验证信号去向表（贴表格内容），标“机器”的格子对应的就是这些问题。
我自己 pipeline/2-create.md 里配音审批这道闸口现在只有一句话，没有细节。
把这些问题整理成候选检查点清单，每条一句话说清测的是什么，先出清单不写脚本。
```

拿回结果要审两件事。第一，每一条能不能对应回第 05 课真碰到过的情况，或者去向表里标机器的格子；对不上的候选多半是 AI 把自己的常识混了进去，删掉。第二，每一条写的是不是能看见的东西。写“音质不佳”没法用，写“某段 mp3 是 0 字节”或者“某段读错了字”才用得上，因为下一节要判的就是这个候选能不能被程序量出来。

清单如果只列出两三条，多半是 AI 把第 05 课那几个症状原样照抄了一遍，没有往下问这个症状要测的是什么、能不能扩成一类检查。比如“读错的字”这一条症状，往下问一句就能扩成“多音字读错”这一类，不只是这一次这一个字的事。

这门课参考的那条真实流水线，作者自己跑的时候验证过配音合成完到录屏前这一段能落地的检查一共六类：真相源要不要重抽、合成完不完整、段内有没有死气、语速离不离群、多音字读没读错、画面上的大字和口播对不对得上。这不是学员现在这份 `2-create.md` 里已经写的东西，是作者跑参考流水线时踩出来、验证过的分类。

其中完整性、语速离群、多音字、音画一致这四类，跟第 05 课自己碰到的问题正好能对上：0 字节的 mp3 是完整性，特别快特别慢是语速离群，读错的字是多音字，字幕和画面对不上是音画一致。真相源要不要重抽、段内死气这两类，学员现在这一批内容大概率还没撞上；等往后配音批次变多，这两类迟早会出现，先定案比等真出事再补要省一轮返工。

拿这六类对一遍自己列出来的候选清单，看有没有漏。补齐之后落在配音这一段的候选是六项：真相源不同步、合成不全、段内死气、语速离群、多音字读错，以及组件大字与口播文案不一致。这里的组件，指网页演示里每一章的视觉呈现文件，屏幕上逐字显示的大标题写在它里面，跟口播文案是两处各写各的。

六项都列出来了，但混着能自动判和只能人看两种，混在一起往下走，量出来的数字没人知道该不该信。

## 2. 三条判据：能不能现在写成一句断言

一项检查该不该进这一轮 Loop，看的不是它重不重要，是它此刻能不能被写成检查点表里能执行的一行。这一节把六项候选按三个去向分类。能写成断言的，量出来的数不靠语境就能直接给结论。只能靠人看的，量能测到，但同一个数字可能对应两种相反的情况，得有人代入语境才分得清。现在写不了但以后能写的，连能测的量都还没有稳定来源。

判断落在哪一档，先问一个问题：这件事有没有一个能测的量，测出来的数不靠额外语境就能直接给出是非结论？

真相源不同步、合成不全、段内死气这三项，答案是能。文本相不相等、文件在不在、静音时长超没超过某个数，程序取到数就能下结论，不需要人代入上下文再判一次。这三项归能写成断言，判官填机器。

把这三项硬塞进只能靠人看这一档，会发生什么？人工去听整段口播，容易被语气和流畅度带偏，听不出某个具体词被替换成了另一个语义相近的词。参考流水线上真出过这种事：改了文案没重新抽取分段文本，配的还是旧文案，声音和画面对不上，人工听了两轮都没听出来，等成片出去了才发现。机器逐字比对反而不会漏这种细节，硬要用人耳去做机器该做的事，漏检的风险比省下来的核对时间贵得多。

语速离群、多音字读错、组件大字不一致这三项，答案是不能。

语速这一项，量能测到，但同一个数字有两种可能。一段口播如果夹了不少英文词，念出来实际用的时间会比这几个词对应的字数暗示的要长。按字数或音节简单折算出来的语速就会显得偏慢，这其实是折算方式带来的偏差，不是真的念得拖沓。真拖沓和这种假象在数值上长得一样，分它们只能靠人听一遍，机器给不出这个判断。

反过来，如果把语速离群硬判成能写断言，直接给机器一个固定阈值，超过就自动打回重录，会怎样？含英文词多的段会被反复误判成偏慢，一轮又一轮地打回重新合成，返工返的都是假象，真正该看的段反而没空看。机器的判断力用错了地方，比不设这道检查还浪费。

多音字这一项，程序按多音字表能扫出候选，但候选本身分不出对错。配音接口的读音覆盖是按整段生效的，同一段话如果需要一个字读两种音，指哪个都会把另一个带错，这种情况改不了配置，只能改文案。

组件大字这一项，程序能把组件里的中文长句和对应段的口播原文并排列出来，但算不算冲突要看这两句在屏幕上是什么关系。组件里的概念标签和口播是关键词对整句的关系，不算冲突；只有逐字呈现的整句标题或行动号召对不上，才算真问题。这个判断依赖两边在画面上的呈现方式，程序分不清。

这三项归只能靠人看，判官填人，但检查这件事本身仍然要写清楚怎么量、候选怎么出，只是最后拍板这一步留给人。

第三档现在写不了但以后能写，卡在连能测的量都没有稳定来源，比如判断一条内容是否押中了热点，缺一个数据源。这一批候选里没有对应的项，配音这一段能落地的检查都能被归进前两档。

如果为了凑齐检查项，给这类东西硬造一个阈值，比如给热点判断编一个关键词命中数超过三个就算押中，会怎样？这条线没有真实事故或外部标准撑着，判对判错都是蒙的，该拦的拦不住，不该拦的乱拦。用几次之后人会发现这条检查靠不住，慢慢连它报的真问题也一起忽略。一条不可信的检查比没有检查更糟，它把整套质检的信任度都拉低了。

```
把上一步的候选清单按三类分：①能写成断言的（客观可测，如时长/存在性/文本是否一致）；
②只能靠人看的（语气/观感这类主观判断）；③现在写不了但以后能写的（缺数据源，如“是否押中热点”）。
每条给一句话说明属于哪类、为什么。
```

分完类，能写成断言和只能靠人看这两类都要进最终的检查点表：前者归机器判，后者归人判，量什么、怎么量都要写清楚，只是阈值和拍板这两步留给人。现在写不了那一档只讲道理没有产出，这一批里也没有对应的项，不进表。

## 3. 六项检查点定案，以及 overrides 落在哪

阈值不是拍脑袋定的数字，是从错到什么程度会导致返工倒推出来的；同一件改动记在哪个文件的事，前后几课的说法必须是同一个答案，不能各说各话。

### 3.1 六项定案

把上一节分完类的六项摆进四列表：量什么、怎么量、阈值、谁来判。阈值这一列，能给出处的都注明来自哪次真实返工；给不出处的，如实写没有出处，只能拿来排序，不能拿来拦人。

| 出错点 | 量什么 | 怎么量 | 阈值 | 谁来判 |
|---|---|---|---|---|
| 真相源不同步 | 分段文案里每段文本，和章节 narration 对应段的原文 | 逐段逐字比对 | 不相等即问题，没有容忍区间。参考流水线上有过真实事故：改了文案没重新抽取分段文本，配出来是旧文案 | 机器 |
| 合成不全 | 每段 mp3 存不存在、字节数、时长，段数与分段文案是否一致 | 按分段文案逐段核对对应 mp3 | 文件缺失或段数不等即问题，不需要额外来源。字节数与时长偏小只是识别空壳的粗界，不当拦人的判决线；第 05 课自己就见过这种 0 字节的空文件 | 机器 |
| 段内死气 | 段内非句读位置的静音时长 | ffmpeg 的 silencedetect 滤镜先抓所有静音区间，再按阈值筛出内部死气。改完重渲染要用同一个滤镜复扫验证，不能只看命令有没有报错；去停顿的脚本如果把输入输出写成同一个文件名，命令不会报错，死气却原样留着 | 大于 0.45 秒算问题，短于 0.45 秒按正常语气放行。0.45 秒是参考流水线一次真实返工里定下的起步值，跑过几条内容之后可以按自己的返工经验调 | 机器 |
| 语速离群 | 剔除停顿之后的纯发音语速 | 算出每段的语速数值，按数值排序，标出明显偏离整体水平的段 | 没有一次真实事故定过这条线，只能拿数值排序、提示先听哪几段，不能直接拦人 | 人 |
| 多音字读错 | 段文案里出现的多音字，以及它在这段语境里该读哪个音 | 按多音字表扫描每段文案，列出候选 | 无阈值，扫到候选就要人核；读音覆盖按整段生效，同一段里两种读音的冲突，参考流水线的踩坑记录里有真实案例，程序判不出该选哪个 | 人 |
| 组件大字与口播不一致 | 网页演示每章视觉文件里逐字显示的大标题和行动号召，与对应段口播文本 | 把组件里的中文长句和对应段口播原文并排列出来 | 无阈值，只有逐字呈现的整句冲突才算问题，概念标签不算 | 人 |

表里把真相源不同步排在第一行，合成完整性排在后面。文案对不上的时候，段全不全已经不重要了，全的也是一批旧文案。

合成不全这一行的阈值分两层。真正拦人的是文件缺失和段数不等，这两条不存在即错，用不着来源。字节数和时长这两个数不拦人，它们只负责认出空壳，正常段和空壳文件之间差的不是一倍两倍，是一个量级，学员第 05 课自己就核对过这种情况。把认空壳的粗界和真正拦人的判决线分开写，是这一档阈值该有的样子。

```
把“能写成断言”的检查项整理成表格，四列：量什么 / 怎么量 / 阈值 / 谁来判；阈值旁边
写一句这个数字是从哪个真实问题倒推的；再补一句：这批检查项发现的问题，改动都写进 build
内 tts.config.json 的 overrides 字段，不新建别的文件。顺便把这条规则补进我自己
pipeline/2-create.md 里配音审批那一段：配音质检发现的问题，改动进 build 内
tts.config.json 的 overrides，沉淀性规则回写 brain/ 里的账号级模板。
```

### 3.2 overrides 落点：判完的结论记在哪

语速和多音字这两项判完的结论要有地方落，落不下去就又回到了上一课那个流向没人管的格子。落点是 build 内那份 `tts.config.json` 的 `overrides` 字段，按段覆盖语速、音高和注音，全局那几个字段留空。这个字段的结构第 04 课留了位置、第 05 课 tts-dub skill 定了形状：逐段覆盖 speed、pitch、pronunciation，键是 segment id。

这份账号级模板会被复制进当条内容的 `build/`，配音脚本读的是那份副本。这一课判出来的语速和多音字问题，改动写进的正是这份 build 内的副本，只在这条内容里生效；只有沉淀性的读法规则，才回写账号级模板，供以后所有内容复用。

这条规则现在要补进学员自己的 `pipeline/2-create.md`：上一步那条 Prompt 已经让 AI 把它写进配音审批那一段，往后这道闸口不再只是一句配音审批，会带上具体的落点约定。参考流水线另有一种写法，把这条改动叫成 `rec/segment-overrides.json` 这个文件名；这门课统一按 `tts.config.json` 的 `overrides` 走，后面几课不换。

overrides 的键是段号，写成章节名加步号的形式，键指向的只是一个位置。改完某段的读音重新合成，那一段听着一点没变，多半是键指向的段号已经不是你要改的那一段了。删段或者加段会让后面的段整体前移或后移一位，键要跟着重排；不然旧键成了死键，新段一个字没注上。

## 从检查点表到可跑的脚本

把该交给机器的格子拆成六项能写成断言的检查点，量什么、怎么量、阈值、谁来判都定了案，overrides 的落点也统一了，自己的 `pipeline/2-create.md` 也补上了这条规则。表还只是表，没有一行代码能跑出数字，学员这一课也没写一行实现代码，六项定案靠的是核对自己的真实经验、审 AI 交回来的清单、填四列表这三步。
