## 开篇契约

记忆锚点：一个 Loop 转不转得起来，先看它的输入信号有没有在动手写脚本之前就定义清楚——配音质检只是拿来验证这句话的一个例子。

开篇按台账（第 06 课成稿本体缺失，见 analyzed.md 材料缺口）承接：上一课交付了一张填完第 4 列的验证信号去向表（四位置模型：人/机器/文档/没人管），学员知道哪些格子该交给机器。本课开头接的点：交给机器就得有信号，这一课定这条流水线上第一个完整 Loop 的信号源。本课输入是验证信号去向表里标"机器"的那些格子，加上学员第 03 课写、第 04 课起持续在用的 `pipeline/2-create.md` 步骤 3 和 `brain/tts.config.json`。本课产出一件东西：一张配音批次检查点表（六项：量什么 / 怎么量 / 阈值 / 谁来判）。

支撑材料: `.claude/skills/dubbing-check/SKILL.md`（检查点 2、3.1 落在配音批次这一段）+ `pipeline/lessons.md` L2/L3/L10/L16/L17/L18（每条候选的事故出处）
交付物: Prompt 块——读 `pipeline/2-create.md` 步骤 3 和第 06 课验证信号去向表里标"机器"的格子，列出配音批次质检可能覆盖的候选检查点清单，只出清单不写脚本
二级标题: none
收尾交接: 候选清单列出来了，但混着"能自动判"和"只能人看"两种，得先分开，不然量出来的数字没人知道该不该信

## 2. 三条判据：能不能现在写成一句断言

核心判断: 一项检查该不该进这一轮 Loop，看的不是它重不重要，是它此刻能不能被写成一句"是/否"的断言。
支撑材料: `.claude/agents/dubbing-reviewer.md` 裁决口径表（硬门槛 vs 逐条看语境的对照）+ `.claude/skills/dubbing-check/scripts/check-pace.mjs` 源码（语速判据无阈值来源的实证）+ 旧稿 mini-v3-07.md 的量/线/形三条件框架（仅取判据结构口径，不抄措辞）
交付物: Prompt 块——把候选清单按三类分：能写成断言的、只能靠人看的、现在写不了但以后能写的，每条给一句理由
二级标题: none
收尾交接: 分完类，"能写成断言"这一类才是这节课真正要交的六项，剩下两类只讲道理没有产出

## 3. 六项检查点定案，以及 overrides 落在哪

核心判断: 阈值不是拍脑袋定的数字，是从"错到什么程度会导致返工"倒推出来的；同一件"改动记在哪个文件"的事，前后几课的说法必须是同一个答案。
支撑材料: `pipeline/2-create.md` 步骤 3 + 终检闸 B（0.45 秒出处、overrides 落点权威口径）+ `brain/tts.config.json` `_overrides` 字段注释 + `pipeline/lessons.md` L2/L3/L10/L16/L17/L18（六项各自的阈值来源或"没有来源"的实情）
交付物: Prompt 块——把"能写成断言"的检查项整理成四列表（量什么/怎么量/阈值/谁来判），阈值旁边写来源；再补一句改动都写进 build 内 `tts.config.json` 的 `overrides`，不新建别的文件
二级标题:
  3.1 六项定案：四列表（量什么/怎么量/阈值/谁来判）
  3.2 overrides 落点：多音字和单段语速的改动统一落 build 内 `tts.config.json` 的 `overrides`（沉淀性规则回写账号级 `brain/tts.config.json`），一句话注明参考仓库另有 `rec/segment-overrides.json` 的写法（`dubbing-check/SKILL.md`、`check-pace.mjs`、`.claude/agents/dubbing-reviewer.md` 都这么写），课程统一以 `tts.config.json` 的 `overrides` 为准
收尾交接: 六项定案了，表还是表，怎么变成能跑出数字的脚本是下一课的事
