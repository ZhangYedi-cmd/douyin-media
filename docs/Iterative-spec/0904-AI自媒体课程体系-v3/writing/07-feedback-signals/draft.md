# 反馈信号从哪来：把配音质检拆成能写成断言的六项检查点

一个 Loop 转不转得起来，先看它的输入信号有没有在动手写脚本之前就定义清楚。这一课拿配音质检当例子，验证这一句话。配音本身不是重点，它只是用来把这句话落到具体判据上的素材。

上一课交付了一张填完第 4 列的验证信号去向表：四个去向是流向人、流向机器、流向文档、流向没人管，学员知道哪些格子该交给机器。交给机器就得先有信号，这一课定这条流水线上第一个完整 Loop 的信号源。Loop 指检查出问题、判出该改什么、改完重跑、再拿同一条判据量一次，四步能自己转起来。它转起来的前提是第一步稳：检查这一步量的东西得清楚，量出来的数得可信，不然后面判、改、复核全都建在一个说不准的地基上。

本课处理的范围，是那张去向表里标机器的这一小片：配音合成完的一批 mp3，到录屏之前这一段。这一课的输入是这一片格子，加上学员第 03 课写、第 04 课起持续在用的 `pipeline/2-create.md` 步骤 3，以及 `brain/tts.config.json`。产出一件东西：一张配音批次检查点表，六行四列，行名是出错点，列是量什么、怎么量、阈值、谁来判。写成能跑出数字的脚本是下一课的事。

## 1. 检查点候选：从"该交给机器"的格子倒推

检查点不是先想清楚要测什么再列出来的，是倒着从"哪些验证格子标了机器"这件已定的事往回问出来的。凭印象列容易漏，漏掉的那一项通常要等成片出来才冒头，那时候能补救的手段只有重录。

倒推靠两份材料。一份是 `.claude/skills/dubbing-check/SKILL.md`，它把配音到成片这条链上会踩的坑，按开工前、合成后、录屏前、录屏后分成四个检查点，每条都写清了它是从哪次事故来的。配音这一片对应其中的检查点 2（合成后）和 3.1（录屏前的音画一致），检查点 1 是开工前的静态检查，检查点 4 是录屏之后的抽帧验证，都不在这一片的范围里。另一份是 `pipeline/lessons.md`，一张表，一行一个踩过的坑，右边一列写现行规则落在哪个文件。

让 AI 把这两份材料读完再列候选清单，比凭空列一遍要稳：

```
读 pipeline/2-create.md 步骤 3（配音批次质检）和第 06 课那张验证信号去向表里
标“机器”的格子，列出配音批次质检可能覆盖的候选检查点清单，每条一句话说清“测的是什么”，
先出清单不写脚本。
```

拿回结果要审两件事。第一，出处能不能翻回 `dubbing-check/SKILL.md` 或 `pipeline/lessons.md` 的原文，翻不到的候选多半是 AI 把自己的常识混了进去，删掉。第二，每一条写的是不是文件里看得见的东西：写"音质不佳"没法用，写"某段 mp3 是 0 字节"或者"成片画面是新文案、声音是旧文案"才用得上，因为下一节要判的就是这个候选能不能被程序量出来。

清单如果只列出三四条，多半是 AI 把范围理解成了整条流水线的配音步骤，只读了检查点 2 却漏了 3.1；这种情况把 `pipeline/lessons.md` 里的 L2、L3、L10、L16、L17、L18 六条点名给它，让它再核一遍。L10 记的是多音字读错的真实案例，L17 和 L18 记的是修法而不是检测项本身，这两条留到第 3 节用。

两份材料过完，落在配音这一段的候选是六项：真相源不同步、合成不全、段内死气、语速离群、多音字读错，以及组件大字与口播文案不一致。最后一项里的组件，指网页演示里每一章那个视觉文件，屏幕上逐字显示的大标题写在它里面，跟口播文案是两处各写各的。

六项都列出来了，但混着能自动判和只能人看两种，混在一起往下走，量出来的数字没人知道该不该信。

## 2. 三条判据：能不能现在写成一句断言

一项检查该不该进这一轮 Loop，看的不是它重不重要，是它此刻能不能被写成一句检查点表里能执行的话。三条判据分别对应三种归宿：能写成断言的、只能靠人看的、现在写不了但以后能写的。

判断一项检查落在哪一档，先问同一个问题：这件事有没有一个能测的量，测出来的数不靠额外语境就能直接给出是非结论？

真相源不同步、合成不全、段内死气这三项，答案是能。文本相不相等、文件在不在、静音时长超没超过某个数，程序取到数就能下结论，不需要人代入上下文再判一次。这三项归能写成断言，判官填机器。

语速离群、多音字读错、组件大字不一致这三项，答案是不能。量能测到，但同一个数字背后可能对应两种相反的情况，得有人代入语境才分得清。语速这一项，`.claude/skills/dubbing-check/scripts/check-pace.mjs` 真能算出每段剔除停顿后的音节数每秒，脚本里按每个英文词约 1.3 个音节折算——但一段含 `query.ts`、`Anthropic` 这类英文词的话，字面语速会偏慢，那是折算方式带来的统计假象，不是真的念得拖沓，真拖沓和假象在数值上长得一样，分它们只能靠人听一遍。多音字这一项，程序按多音字表能扫出候选，但查不出这一段语境里该读哪个音，合成接口的读音字典还是按字全局生效的，一旦给某个字定了读音，全片所有出现的地方都会跟着改，本仓有一集"执行"和"N 行"共存，把"行"定成 háng 之后"执行"也跟着念错（L10）。组件大字这一项，程序能把组件里的中文长句和对应段的口播原文并排列出来，但算不算冲突要看这两句在屏幕上是什么关系：组件里的概念标签和口播是关键词对整句的关系，不算冲突；只有逐字呈现的整句标题或行动号召对不上，才算真问题。这三项归只能靠人看，判官填人，但检查这件事本身仍然要写清楚：怎么量、候选怎么出，只是最后拍板这一步留给人。

第三档是现在写不了但以后能写，卡在连能测的量都还没有稳定来源，缺一个数据源，比如判断一条内容是否押中了热点。这一批候选里没有对应的项，配音合成完到录屏前这一段能落地的检查，都能被归进前两档，不需要为了凑够三类硬造一个第三档的例子。

```
把上一步的候选清单按三类分：①能写成断言的（客观可测，如时长/存在性/文本是否一致）；
②只能靠人看的（语气/观感这类主观判断）；③现在写不了但以后能写的（缺数据源，如“是否押中热点”）。
每条给一句话说明属于哪类、为什么。
```

这三条判据不是这门课自己拍脑袋定的，第 09 课那份配音批次质检子代理的裁决口径表把六个检查点分成了两类：完整性核对和真相源同步写的是硬门槛，命中就直接判失败；语速、多音字、音画一致写的是逐条看语境才判失败。硬门槛对应的正是量出来的数不靠语境就能下结论的那三项，逐条看语境对应的正是需要人代入上下文才能分辨真假的那三项。两边分出来的类别是一致的，这份材料现在只用来印证判据成立，那个子代理本身是第 09 课才会造的东西，这一课不提前造它，只借它的裁决口径表说明道理站得住。

分完类，能写成断言这一类才是这节课真正要交的六项，剩下的第三档只讲道理没有产出，不算这一课的活。

## 3. 六项检查点定案，以及 overrides 落在哪

阈值不是拍脑袋定的数字，是从错到什么程度会导致返工倒推出来的；同一件"改动记在哪个文件"的事，前后几课的说法必须是同一个答案，不能各说各话。

### 3.1 六项定案

把上一节判完归属的六项摆进四列表，量什么、怎么量、阈值、谁来判。阈值这一列，能给出处的都注明来自哪次真实事故或哪份契约的原句；给不出处的，如实写没有出处，只能拿来排序，不能拿来拦人。

| 出错点 | 量什么 | 怎么量 | 阈值 | 谁来判 |
|---|---|---|---|---|
| 真相源不同步 | 分段文案 `audio-segments.json` 每段文本，和章节 `narrations.ts` 对应段的原文 | 逐段逐字比对 | 不相等即问题，没有容忍区间。来源是 EP02 那次改了 narration 没重抽分段文案，成片画面是新文案、声音是旧文案（L2） | 机器 |
| 合成不全 | 每段 mp3 存不存在、字节数、时长，段数与分段文案是否一致 | 按分段文案逐段核对对应 mp3 | 文件缺失或段数不等即问题，不需要额外来源；字节数与时长偏小只是识别限流失败留下的空壳文件的粗界，不当拦人的判决线 | 机器 |
| 段内死气 | 段内非句读位置的静音时长 | ffmpeg 的 silencedetect 滤镜先抓所有静音区间，再按阈值筛出内部死气 | 大于 0.45 秒算问题，短于 0.45 秒按正常语气放行。来源是 `pipeline/2-create.md` 步骤 3 与 `dubbing-check/SKILL.md` 检查点 2.3 同一句判据，事故出处是 EP02 那次 18 字撑 6.78 秒、含 1 秒死气（L3） | 机器 |
| 语速离群 | 剔除停顿之后的纯发音语速（音节数每秒） | 音节数除以发音时长，发音时长按每处标点扣一段固定秒数估算 | 偏离本批段落均值一定倍数的标准差就标出来，倍数写死在脚本里，没有出处，只能拿来排序、提示先听哪几段。含英文词的段字面偏慢是折算带来的统计假象，要靠人听一遍才分得清真假 | 人 |
| 多音字读错 | 段文案里出现的多音字，以及它在这段语境里该读哪个音 | 按多音字表扫描每段文案，列出候选 | 无阈值，扫到候选就要人核。读音字典按字全局生效，同一个字在全片不同段落有不同读音时，定死一种读法会把另一种带错（L10） | 人 |
| 组件大字与口播不一致 | 网页演示每章视觉文件里逐字显示的大标题和行动号召，与对应段口播文本 | 把组件里的中文长句和对应段口播原文并排列出来 | 无阈值，只有逐字呈现的整句冲突才算问题；组件里的概念标签和口播是关键词对整句的关系，不算冲突 | 人 |

表里排第一的是真相源不同步，不是合成完整性。文案对不上的时候，段全不全已经不重要了，全的也是一批旧文案，这个顺序不是随意排的。

合成不全这一行的阈值写法值得留意：真正拦人的是"文件缺失"和"段数不等"，这两条属于不存在即错，用不着来源；字节数和时长这两个数不拦人，它们只负责认出空壳，串行批量合成偶发限流失败，失败那一段留下的是极小的文件，跟正常段差的不是一倍两倍，是一个量级。把认空壳的粗界和真正拦人的判决线分开写，是这一档阈值该有的样子。

```
把“能写成断言”的检查项整理成表格，四列：量什么 / 怎么量 / 阈值 / 谁来判；阈值旁边
写一句这个数字是从哪个真实问题倒推的；再补一句：这批检查项发现的问题，改动都写进 build
内 tts.config.json 的 overrides 字段，不新建别的文件。
```

### 3.2 overrides 落点：判完的结论记在哪

语速和多音字这两项判完的结论要有地方落，落不下去就又回到了上一课那个流向没人管的格子。落点是 build 内那份 `tts.config.json` 的 `overrides` 字段，按段覆盖语速、音高和注音，全局那几个字段留空。学员第 04 课交付 `brain/tts.config.json` 时已经拿到这个字段的结构，它的注释写得很直接：逐段覆盖 speed、pitch、pronunciation、voice_id，键是 segment id，dubbing-check 发现多音字或语速离群时就填这里。第 05 课起，这份账号级模板被复制进当条内容的 `build/`，配音脚本读的是那份副本；这一课判出来的语速和多音字问题，写进的正是这份 build 内的副本，改动只在这条内容里生效，只有沉淀性的读法规则才回写账号级模板，供以后所有内容复用。

这一条落点，`pipeline/2-create.md` 步骤 3 写得很清楚：多音字、单段语速问题加 build 内 config 的 overrides，沉淀性规则回写 `brain/tts.config.json` 模板。同一个仓库里另有两处写法不一样：`dubbing-check/SKILL.md` 的 2.2 节和 `.claude/agents/dubbing-reviewer.md` 的裁决口径表，说的是 `rec/segment-overrides.json` 这个文件。两处口径不一致，课程统一按 `tts.config.json` 的 `overrides` 为准，因为它是阶段契约，操作细节该服从契约，不是反过来。

overrides 的键是段号，写成章节名加步号的形式，段号说的是位置，不是身份。改完某段的读音重新合成，那一段听着一点没变，多半是键指向的段号已经不是你要改的那一段了：删段或者加段会让后面的段整体前移或后移一位，键要跟着重排，不然旧键成了死键，新段一个字没注上（L18）。

## 从检查点表到可跑的脚本

把该交给机器的格子拆成六项能写成断言的检查点，量什么、怎么量、阈值、谁来判都定了案，overrides 的落点也统一了。表还只是表，没有一行代码能跑出数字，学员这一课也没写一行实现代码，六项定案靠的是读材料、审 AI 交回来的清单、填四列表这三步。

下一课把这六项逐条造成脚本。检查点表定了六项要量什么，表还只是表，怎么变成能跑出数字的脚本？
