## 记忆锚点与开篇（不占编号）
记忆锚点：cc-stream 只认识「子进程 stdout 是一串 JSON 行」这一件事，不认识任何调用方的业务概念；裁决只读文件出结论，不信进程自述。这两条合起来才是「无人值守」的完整定义：既要能自己跑，也要能自己说清跑得对不对、什么时候该停。
开篇逐字接台账第 24 行「结尾抛出的问题」：治理线能自己巡检记账了。可这些都要你敲一次命令才动。怎么让它在你睡觉的时候自己跑？
本课输入：学员已有的 `media` 命令、`douyin-publish`/`douyin-retro`/`douyin-ideate` 等 skill（当被观察对象）、`media` CLI core 包里已有的锁与原子写逻辑（第 12-16 课）。
本课产出：一个 `cc-stream` 包（六个文件：`index.ts`、`normalize.ts`、`milestones.ts`、`spawn.ts`、`transport.ts`、`types.ts`）、一个裁决函数、一套收尾策略，加一次 `claude -p` 跑通。
范围声明：本课只造这些标准件本身，凡涉及「谁来调用它、装进哪个常驻进程」的地方，指的都是学员将在模块 7 造的那个进程——学员此时还没有 console。

## 1. 三层解析：从 JSON 行到里程碑
核心判断: 一条 headless 输出的 JSON 行要经过三层加工——原始行、归一事件、里程碑——每层只做一件事，业务知识留在最外层的调用方，引擎本身不掺和。
支撑材料: `2026-08-18-看板后端与CC进程调度技术方案.md` §7.2 三层解析、§7.3 包边界表；`cc-stream/src/transport.ts`/`normalize.ts`/`milestones.ts` 三个文件的职责分界。
交付物: 三层职责对照表（层 / 输入 / 输出 / 是否认识业务）。
二级标题: none
收尾交接: 三层定完，先把最底下这层——事件怎么归一——的形状钉死。

## 2. 七种归一事件与三档信任分级
核心判断: `say` 和 `thinking` 只展示、永不驱动任何判断，`tool`/`toolDone` 驱动步骤时间线，只有落盘文件才是终局裁决——这条信任分级错了位，AI 的自述会被当成事实。
支撑材料: `cc-stream/src/types.ts` 的 `NormEvent` 联合类型（7 种 kind）及扩容注释、`normalize.ts` 的去重与归一逻辑；`2026-08-18-看板后端与CC进程调度技术方案.md` §7.4 信任分级三条。
交付物: 七种事件对照表（`started`/`tool`/`toolDone`/`say`/`thinking`/`stalling`/`done`，各自：驱动什么 / 是否只展示）+ prompt 生成 `types.ts` 与 `normalize.ts`。
二级标题: none
收尾交接: 事件归一好了，怎么从事件流里认出「走到哪一步了」。

## 3. 里程碑引擎：声明式规则，业务知识留在外面
核心判断: 里程碑表由调用方注入，引擎本身不认识任何一条规则的业务含义——换一个任务类型，只用换规则表，不用改引擎。
支撑材料: `cc-stream/src/milestones.ts` 的 `createMilestoneEngine`；`server/jobs/milestones.ts` 的 `HARNESS_RUN_MILESTONES`（读任务卡→执行技能→产报告→记账四步）当示例。
交付物: 一张示例里程碑表（拿治理线巡检举例：读任务卡 → 执行技能 → 产报告 → 记账四步）+ prompt 生成 `milestones.ts`。
二级标题: none
收尾交接: 引擎齐了，剩下的是怎么真的拉起一个无头进程喂给它。

## 4. 拉起无头 claude -p：三个坑与一次真跑
核心判断: headless 模式下 OAuth token 容易被误当 API key 传进子进程环境，子进程可能卡在某个工具调用里装死，stdout 必须按行解析不能整体读——这三个坑不排掉，无头作业跑不稳；六个文件拼不拼得起来，拿一次最小任务真跑一遍就知道。
支撑材料: `cc-stream/src/spawn.ts` 的 `DEFAULT_DROP_ENV`/`timeoutMs`；`transport.ts` 的逐行 readline；`2026-08-18-看板后端与CC进程调度技术方案.md` §6 四个防坑点；`server/jobs/prompts.ts` 的 `ALLOWED_TOOLS`、`harnessRunPrompt` 当最小任务参考。
交付物: 4.1/4.2 两小节；prompt 生成 `spawn.ts`、`transport.ts`、`index.ts`（导出面）+ 一次真实 `claude -p` 最小任务的跑通记录（prompt 内容、`allowedTools` 白名单、看到的归一事件序列）。
二级标题: 4.1 三个坑（认证 / 超时 / 输出流）/ 4.2 一次真跑验证
收尾交接: cc-stream 包六个文件齐了，能吐出正确的事件流；跑完算不算成功，还得有人拍板。

## 5. 只认文件的裁决，加上守住并发的锁
核心判断: 子进程说「我成功了」和文件真的落到预期状态是两件事，裁决必须复读文件，不能读进程自述或退出码——这和第 09 课「判的人不能改」是同一类约束的第二次出现；同一条内容不能被两个进程同时改，锁不是排队机制，是拿不到直接报错退出，宁可保守拒绝也不排队卡死。
支撑材料: `server/jobs/verdict.ts` 的 `verdictPublish`/`verdictRework`/`verdictCreate`；两份真实日志 `create-20260826125707-bc32.result.json`（撞会话限额，靠 meta.status=drafting 判未完成）、`publish-20260819101820-bd51.result.json`（narration 已经承认失败，裁决模板仍不读它）；`core/lock.ts` 的 `STALE_MS`/`isPidAlive`。
交付物: 5.1/5.2 两小节；裁决函数规格表（输入 / 读哪个文件的哪个字段 / 期望状态集合 / 输出 `ok`+说明）+ 锁规格表（锁文件放哪 / 内容 / 陈旧判据的两个条件 / 抢占后要留痕）+ 两条 prompt（一条生成裁决函数，一条复用/扩展学员自己 `media` CLI core 包里已有的锁逻辑）。
二级标题: 5.1 裁决函数：读条目 meta.yaml 的 status，判它是否落到预期值 / 5.2 单并发与锁：陈旧判据要同时满足「超过时限」和「持锁进程已经不在了」两个条件才能抢占
收尾交接: 裁决和并发管住了，进程本身怎么正常收尾、收不住的时候怎么恢复，还没定。

## 6. 收尾策略：先礼后兵，加恢复规则：内存不可信
核心判断: 超时不能直接一记强杀——先发终止信号给收尾机会，等一段宽限期仍不退才补杀，粗暴强杀会留下半写文件和收不回的孤儿进程；内存里的任务状态同样不可信——它会随进程一起死掉，真相必须活在文件里，人工取消和意外重启都靠这条原则兜底。
支撑材料: `cc-stream/src/spawn.ts` 的 `killGracefully`（`SIGKILL_GRACE_MS = 10_000`）；`server/jobs/runner.ts` 头注「崩溃安全：任务表在内存，server 挂了就丢——真相在文件里」与 `routes/jobs.ts` 的磁盘降级三级兜底（`result.json` → `.jsonl` → 404）。
交付物: 6.1/6.2 两小节；收尾时序表（信号 / 等待时长 / 下一步）+ 恢复规则表（触发场景 / 内存态怎么处理 / 从哪个文件兜底重建结论）+ 一条 prompt 扩展第 4 节 cc-stream 的进程终止逻辑，补上「宽限期后仍未退出再补杀」这一段。
二级标题: 6.1 收尾时序：SIGTERM 先给宽限期，仍不退再 SIGKILL / 6.2 恢复规则：触发场景、内存态怎么处理、从哪个文件兜底重建结论
收尾交接: 无人值守这条线该收口了。
