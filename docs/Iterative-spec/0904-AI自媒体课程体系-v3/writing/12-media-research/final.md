# media 调研与选型讨论：入口形态、YAML 写法、并发保护、派生视图四组路线怎么选

上一课（第 11 课）交付了 docs/spec/ 目录约定和六步模板四件套：调研模板、ADR 模板、执行方案模板、施工记录模板。方法确立后便要在实战中应用。本课以状态写入入口为例，推进六步流程中的前三步：调研、讨论选型与决策。状态写入入口指的是用于统一更新 meta.yaml、backlog.yaml 等文件内状态字段的组件。在此之前，流水线状态主要依靠手工维护文件。

第 10 课结束时留下一句话。自愈回路，也就是判、修、复判轮流交棒的整套流程已经跑通。但前期一路手工修改 meta.yaml，后续还有体量更大的系统组件要构建。手工修改的核心风险是缺乏自动化校验机制的兜底保护。status 字段允许填写哪几个值全凭人工记忆。第 10 课熔断便是一个典型例子：由于缺少专门的挂起状态可用，只能在 status 字段后补充一行说明。一旦写错格式，系统无法及时给出提示。

本课的具体产出是两份文档：00-调研.md 与 01-ADR.md，统一归档于 docs/spec/media/ 目录。media 是当前模块在规范文档中的代号，这与状态写入入口最终的技术形态是两个层面的概念。预先确定代号便于归档文档，并不意味着命令行路线已经预设获胜。

## 一、四组互斥路线：状态写入口该怎么选

本课先不编写代码。在调研、讨论选型、决策这三个步骤中，核心任务是梳理客观事实、推演边界缺陷并完成架构拍板。产出全部沉淀为技术文档。本阶段的核心任务是明确技术路线的选择，具体施工留待后续推进。

四组选型的互斥边界需要预先界定清晰，便于在调研时精准聚焦。

第一组是入口形态。备选方案包括命令行工具、面向对话客户端的协议服务、内部 HTTP 接口，以及维持现状由各环节脚本自行维护。入口形态一旦确立，后续所有调用方都必须遵循统一契约接入。若选定命令行，就不能允许个别脚本私自实现独立判断逻辑。

第二组是 YAML 文件的修改方式。在修改单个字段时，是仅替换被命中的指定字节区间，还是将文件完整解析为对象、更新字段后再全量序列化写回。这是一次性的架构选型。选定之后，后续改写都必须承担对应的方案成本。中途变更路线意味着需要重构依赖原有机制的全部代码。

第三组是并发保护机制。当存在多个写入方并发修改状态时，系统是放任不管、采用互斥锁，还是引入队列统一排队。不同方案针对并发冲突给出的解法截然不同：不设保护意味着后写入者直接覆盖先写入者；互斥锁意味着先获得锁者执行，未获锁者直接失败；队列则意味着按序等待逐步消费。

第四组是派生视图的生成时机。系统中部分文件的内容由状态汇总计算得出，例如聚合在制内容状态的总看板。这类文件是在写操作事务中同步重新生成，还是交由独立进程按需异步更新。在同一事务中处理能够避免视图与真实数据产生时间差，而拆分处理则往往会产生短暂的不一致窗口。

在这四组路线中，决策的扩散面各不相同。入口形态一旦敲定，后续各课编写的子命令以及阶段契约的规范描述都必须严格对齐，重构代价最高。相比之下，派生视图的反悔成本较低，即使视图渲染出现偏差，重新触发计算即可纠偏。在调研阶段不必过早权衡轻重，重点在于理清每组内部的互斥核心。

四组互斥路线清单如下：

| 组别 | 候选方案 | 互斥点 |
|---|---|---|
| 入口形态 | CLI / MCP / 内部 HTTP / 散脚本 | 只能有一个写入口形态，别的调用者都要迁就它 |
| YAML 写法 | 点位编辑 / 整篇 dump | 注释保不保得住是一次性决定 |
| 并发保护 | 文件锁 / 不做 / 队列 | 系统在多写者压力下的行为互相矛盾 |
| 派生视图 | 同事务重生成 / 另起进程 | 要不要接受一段视图落后于真相的时间窗口 |

选型范围明确后，调研阶段的任务是将每组备选方案及其对应的代价汇总至统一表格中，立足事实展开推演，暂不下结论。

## 二、调研：四组路线逐组填对比表

四组路线虽然各自独立，但在调研阶段遵循统一的表格维度：方案、适用前提、代价、已知失败模式。这一阶段暂不作取舍，重点在于引导每个候选方案客观呈现实际边界，具体的优劣交锋留待讨论选型环节展开。

先获取候选清单并经人工确认，再展开对比表。提示词复用上一课确立的标准格式：

```
现在要给流水线的状态写入口做一次调研。这一步只列候选方案、摆事实，不下结论。

针对下面四组问题，各给出 2 到 4 个候选方案，先列出候选清单，等我确认过
再展开成表格。展开时每个方案填一行：方案 / 适用前提（什么场景下选它
是对的）/ 代价（选它要多付出什么）/ 已知失败模式（什么情况下它会输，
能不能举出具体例子）。

四组问题：
1. 状态写入口应该长成什么形态：命令行工具、给对话客户端用的协议服务、
   内部 HTTP 接口，还是维持现在各写各的散脚本？
2. 改一个 YAML 字段，是只改被点中的那一小段字节，还是解析成对象、
   改完整篇重新写回去？
3. 多个写者同时想改状态时，系统怎么办：不做任何保护、加一把文件锁，
   还是排队处理？
4. 从状态里算出来的派生视图，是写操作顺带同步生成，还是交给另一个
   独立进程按需生成？
```

下文展示的四张表格呈现了调研产物的标准形态，供读者对照参考。读者自行生成的候选与措辞通常与示例不完全一致，字段名称或代价的表述也会有所差异。这属于正常现象，核心在于结构符合规范：方案、适用前提、代价、已知失败模式四列完整，不留缺项。

### 2.1 入口形态：CLI / MCP / 内部 HTTP / 散脚本

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| CLI | 人在终端敲、脚本用子进程调、AI 按需查用法，三种调用者要共用同一个入口 | 每加一种能力要多写一条子命令和帮助文本，参数一旦定型，改字段名要牵动全部调用方 | 命令行参数被脚本和文档写死之后，字段改名的代价很高 |
| MCP | 只有一个常驻的对话客户端在用，不会再冒出别的调用者 | 客户端要在每次对话开局把全部工具描述塞进提示词，不管这次任务用不用得上 | 一旦出现第二个调用者，比如一个定时跑的任务，协议层的开销要在两边各实现一遍 |
| 内部 HTTP | 系统里已经有一个常驻服务在跑，想顺带让它也接受写请求 | 状态机的合法性校验要在服务进程里再实现一遍，或者转头去调本该属于写入层的代码，多一层间接 | 写请求经过网络这一层之后，出错信息容易被协议包装层盖住，调用方拿到的往往是个笼统的报错，看不出是哪条业务规则拦的 |
| 散脚本 | 每个环节各写各的，谁改状态谁负责，改起来最快 | 前期零协调成本 | 状态翻转的规则散在多份脚本里各自演化，容易长出第二套不一致的实现，谁改漏了没人拦 |

选择命令行工具作为核心倾向，有两点具体理由。其一在于人机协同的使用模式一致。开发者在终端执行命令，无需预先记忆全部参数，参数遗漏时帮助信息会明确提示。AI 调用同样遵循这一逻辑，无需在会话初始将所有工具细节载入上下文，仅在任务需要时动态查阅使用方式，这属于高效的按需加载。其二在于进程退出码机制。命令执行后的零与非零返回值，属于操作系统层面的确定性状态，无需解析自然语言文本或嵌套对象即可准确获知执行结果。

分散脚本模式在工程实践中有前车之鉴。早期流水线曾分散存在多处状态写入逻辑，多采用各自独立的代码实现，甚至存在直接通过正则表达式修改文本的做法。分散脚本的核心隐患在于缺乏统一规则源，状态机规则演进时难以全面核查，极易出现逻辑不一致的漏洞。

### 2.2 YAML 写法：点位编辑 vs 整篇 dump

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 点位编辑（只改被点中的字节区间，其余字节原样保留） | 文件里带着人写的注释，这些注释是有效信息，不能因为工具改了一个字段就被抹掉 | 每加一种可写字段，都要多写一段在原始字符串里定位这个字段的代码，比直接调用整体序列化麻烦 | 定位逻辑写错了会算错字节区间，把相邻内容一起覆盖掉 |
| 整篇 dump（解析为对象并重新序列化）。 | 适合机器维护的纯配置文件。不包含需要保留的人工排版。 | 一旦存在人工注释，该方案无法予以保留。 | 参考流水线做过真实测试。对 25 个真实 YAML 文件直接解析写回，均无法对齐原文。注释缩进在解析阶段便丢失。 |

这一组选型的判断标准较为明确：状态文件中是否存在人工编写的注释信息，通过代码检索即可验证。在前期编写的 meta.yaml 模板中，即便留存的人工说明仅有数行，也直接确立了技术选型的硬性约束，排除了全量写回路线。

### 2.3 并发保护：文件锁 / 不做 / 队列

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 不做（假设永远只有一个写者在跑） | 现在确实只有一个入口在写，比如手改 meta.yaml 全靠一个人手动操作 | 前期零成本 | 一旦第二个写者出现，比如同时有一次人工操作和一个后台任务都要改状态，先写的会被后写的悄悄覆盖，不会有任何报错 |
| 文件锁 | 写操作本身很快，多个写者是互斥关系，不需要排队处理同一批数据 | 拿不到锁的一方直接失败退出，还要处理进程被杀死后锁没释放的陈旧锁问题 | 陈旧锁不清理，会让后续所有写命令永远拿不到锁 |
| 队列 | 写操作之间有先后依赖，或者写操作本身比较耗时，排队等待的成本能接受 | 要单独维护一套排队和调度的服务，一次写请求从提交到真正落盘之间有一段不确定的等待时间 | 排队服务本身出故障，所有写操作一起堵死，多引入了一个新的单点故障 |

队列模式支持按序调度，但当前状态落盘操作耗时极短，引入队列的代价偏高。在此需要厘清两个维度的安全防线。文件锁解决写入权限的互斥，同一时间仅允许单个写进程进入。原子落盘解决读取时的数据一致性，通过写入临时文件后重命名替换，防止读取方读到写中途的残缺内容。两者定位互补，互斥锁无法替代原子写入，原子写入同样无法防范多进程并发篡改。

### 2.4 派生视图：同事务重生成 vs 另起进程

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 同事务重生成（写操作最后一步顺带把视图重新算一遍，一起落盘） | 视图的数据量不大，重新算一遍的开销可以忽略，且视图必须时刻和真相源保持一致 | 每次写操作都要多算一遍视图，视图的渲染逻辑和写路径耦合在一起，改视图格式要跟着改写路径 | 视图渲染逻辑本身要是抛错，会拖累整次写操作一起失败，得想清楚视图算错了要不要拦住写入 |
| 另起进程（视图交给一个独立命令或后台任务，按需或定时生成） | 视图生成开销比较大，或者晚一点更新也没关系 | 无 | 视图和真相源之间总会留出一段不一致的窗口，后台任务忘了跑或者跑失败没人发现，视图就停在某个旧时间点上不动 |

参考规范中的总看板为 dashboard.md，负责汇集在制内容的当前进展。系统在实践中保留了弹性设计：核心写操作中默认执行同事务重生成，同时保留独立的重建命令作为兜底手段。这表明技术决策并非非此即彼，在主干明确的前提下，保留低成本的兜底路径是明智的做法。

完成四组对比表的梳理后，接下来引导每个候选方案展开自我辩护，剖析各自的失效边界。

## 三、讨论选型：四组各自的辩护人

调研阶段侧重呈现客观事实，选型讨论环节则要求每个方案清晰陈述其适用场景、代价损耗，以及在何种具体边界下会输给既定竞品。本环节严禁输出“综合来看方案 X 更优”等定论，决策权完全保留给人。

使用同一套辩护式提示词，对四组路线分别推演，仅需替换具体组名与候选清单：

```
针对<入口形态>这一组的候选方案<把你自己那一组四列表里的方案列复制
过来>，分别以对应方案支持者的身份，逐个回答：
1. 这个方案在什么场景下是对的选择？
2. 选它要多付出什么代价，时间、心智负担、谁来买单？
3. 主动交代它已知的失败模式：什么情况下它会输，会输给候选清单里的
   哪一个对手？
不要下"综合来看方案 X 更好"这类结论，结论留给我来定。
```

候选清单应当提取自上一节生成的表格，而非照搬教材示例。课文中的示例主要用于对齐格式与维度。

推演完成后，各方案阐述的核心短板清晰呈现，体现出对边界条件的深度剖析：

入口形态一组中，MCP 明确说明了适用前提。若系统仅服务于单挑对话客户端，MCP 表现优秀；一旦出现定时任务等非对话调用方，双向协议维护成本将成倍增长。CLI 方案同样指出了自身的局限：参数契约一旦在文档和脚本中固化，字段重命名的重构成本将波及全仓。

YAML 写法一组中，整篇全量写回明确交代了短板。只要目标文件中包含人工排版或业务注释，全量解析与序列化机制便无法予以保留，这一缺陷由库机制本身决定。

并发保护一组中，队列方案指出了系统脆弱点：排队调度服务自身若发生异常，所有写入操作将被迫中断，系统增添了单点依赖。文件锁方案同样交代了隐患：锁文件未能及时释放会导致后续调用持续受阻，必须配合超时抢占机制协同保障。

派生视图一组中，独立进程模式客观指出：视图与真相源之间客观存在数据同步延迟。除非业务场景完全包容该延迟，否则数据不一致风险难以回避。

若在实际推演中，某个候选方案仅列举优势而回避失败场景，通常是输入的场景描述带有主观诱导。此时应当调整为中性表述重新提问，促使模型充分暴露各方案的工程短板。

当四组候选方案的薄弱点与边界条件充分显现后，便可进入拍板定夺阶段。

## 四、决策：写出四份 ADR

四组技术路线应当独立决策，互不绑定。选定 CLI 并不意味着并发保护也必须采用重型架构，每组决策均基于自身的成本与场景单独衡量。ADR 保持精炼，严格包含决策、理由、被否方案、反悔成本四项，不随意增添冗余字段。

沿用标准 ADR 格式完成四组推演。以下以入口形态的决策为例展示标准结构：

```
ADR-1 入口形态
决策：CLI，统一命令名。
理由：人在终端敲、脚本用子进程调、AI 按需查用法后调用，三种调用者
共用同一个入口，不用为每种调用者各接一套；退出码是三种调用者都认
的确定性信号。
被否方案：MCP，只有唯一的对话客户端在用时协议开销才更为经济，出现非
对话类调用者就要两边各实现一遍；内部 HTTP，写请求经过网络层之后
出错信息容易被包装层盖住；散脚本，现状六个写入口各自演化，容易
长出第二套不一致的实现。
反悔成本：给 CLI 包一层 HTTP 或协议转发壳，代价不大，因为业务规则
都在 CLI 背后，壳只是转发；反过来，先选了散脚本或协议层再往 CLI
收口，要把散在各处的状态机规则一条条挖出来重写，代价高得多。
```

使用如下提示词，将讨论结果导入规范模板，沉淀为四份专属的 ADR 文档：

```
基于上面<组名>这一组的讨论选型结果，写一份 ADR。固定四项：
决策（选了哪个方案）、理由（为什么，引用讨论里的具体理由）、
被否方案（其余候选各自因为什么被否，不许只写"其余方案更差"这类
空话）、反悔成本（以后想换掉这个决策，要付出什么代价）。
不要新加字段。
```

完成推演后，将四份决策统一沉淀至 01-ADR.md。完成后需要核查决策论据的独立性，避免出现“因前一组结论而顺带选择本组”的逻辑缠绕，每份决策都应具备自洽的支撑论据。

### 4.1 入口形态定了什么

见前文展示的 ADR-1 详细内容。

### 4.2 YAML 写法定了什么

参考规范选定点位编辑方案。核心理由在于元数据中的排版与说明属于有效资产，不能在字段修改时被覆盖擦除。被否方案为整篇全量写回，往返测试表明其在解析阶段便丢失了缩进信息。反悔成本属于中等范畴：点位编辑的定位实现虽然相对繁琐，但实现后扩展新字段仅需补充局部匹配逻辑。若反向由全量写回迁移至点位编辑，重构代价显著升高。

### 4.3 并发保护定了什么

参考规范选定文件锁方案，未获锁者立即报错退出，不引入排队机制。核心理由在于状态落盘耗时极短，引入队列将带来不必要的架构复杂度，即时报错更有助于快速定位冲突。被否方案为不做保护以及异步队列，前者存在并发静默覆盖风险，后者引入了额外的单点故障源。反悔成本取决于未来写入开销是否显著增长，在轻量操作前提下保持该架构最为稳健。

### 4.4 派生视图定了什么

参考规范选定同事务同步更新方案。核心理由在于视图必须与真实状态保持严格同步，且看板计算开销较小。被否方案为另起进程异步生成，因其存在状态滞后窗口且容易因任务漏跑导致视图失效。系统保留了独立重建命令作为应急兜底，但不作为日常流转的依赖路径。
