# 润色报告：第14课「执行 M1：core 三件与首批命令」

## 一、诊断问题逐条处理

### 维度6 问题A（材料越界，最严重，已改）

诊断指出多处 Prompt 和验收动作假设读者手上有远超 inventory 保证的数据规模（多条内容、几十条选题池条目），并且直接引用了本仓库真实存在但读者不可能拥有的具体文件（`content/2026-06-19/ep05-permission-pipeline/meta.yaml`，含二十六处真实历史注释）。核对后确认这是真问题：`inventory.md` 第13课结束时清单只保证读者有"一条内容的 `content/<slug>/build/` 工程目录"和"`backlog.yaml` 头部"，本仓库里的具体内容目录、`ep05-permission-pipeline` 这类真实产出、多条状态各异的内容，全部属于本课程最终要 1:1 复刻的目标仓库本身，不是读者当前手上的东西，跟 `tools/console/packages/...` 是同一类material（学员读不到，只能拿来做参照）。

处理：
- parsers 段落：删掉"三十条内容里有一条""另外二十九条"的具体计数，改成"哪怕你现在 content/ 下只有一条内容，这条规则也要现在就定下来"，把设计理由从"读者当前有N条"改成前瞻性论证，不再依赖不存在的规模。
- 往返测试段落：删掉 `content/2026-06-19/ep05-permission-pipeline/meta.yaml` 具体路径和"二十多处注释"的描述，改成 `content/<发布日>/<slug>/` 占位记法（与第05课成稿的写法一致），测试对象改回"你在第05课做出来那一条内容"和 `content/_backlog/backlog.yaml` 本身，不再要求"三五个真实文件"。
- `st`/`next`/`doctor` 示例输出：从虚构的"在制 6 条""体检 30 条"改成与读者真实状态一致的"在制 1 条""体检 1 条"，`next` 的示例改成 `next.ts` 真实存在的空池分支输出"选题池中无 idea 可取"，不再假造一次有候选、有 runnerUp 的结果。
- promote/publish-done 的 dry-run 验收：加了一步明确的准备工作，指导读者用他们从第03课起就在用的手改方式，先往 `backlog.yaml` 加一条测试用的 idea 选题、把自己那条内容的状态手动改成 approved，再跑 dry-run，不再假设这些条件已经存在。
- diff 示例的行号从暗示大文件的 `@@ -42,1` 改成 `@@ -8,1`，并加一句"哪怕你的 backlog.yaml 眼下只有寥寥几行，这条规则也一样成立"，明确不依赖文件规模。
