# 执行 M1：core 三件与首批命令怎么跑起来

上一课完成了 `docs/spec/media/02-执行方案.md`。十四条命令逐条拆成了参数、读什么、写什么字段、失败怎么报这套四件套。两张状态迁移表里，一张管 `meta.yaml` 的八个状态，一张管 `backlog.yaml` 的六个状态。M1、M2 两个里程碑也已切好，各自的出口条件都写成了一句能跑的验证动作。上一课结尾抛出的问题是：执行方案写完，开始施工，第一个里程碑做哪些？

前十三课，学员的职责是想清楚、写下来。判据、契约、SPEC，每一样最终都要落成一份人写的中文文档。从这一课起，分工变了：AI 按 `02-执行方案.md` 施工，学员的重心转为验收，看出口条件过没过。

## 一、开篇：学员的职责从编写转为验收

记忆锚点：从这一课起，学员的职责从定判据变为验收出口条件。AI 负责写代码，人只核验出口条件过没过。

验收纪律有三条原则。第一条，出口条件是否达标是唯一准绳。不必纠结代码风格是否合乎个人审美，也不必限定 AI 的具体编码方式，只要出口条件全部跑通就行。第二条，看不懂就让 AI 解释或重写。主动问一句这段代码在做什么、为什么这么写，成本比自己猜测低得多。第三条，出口条件没达标就换个 Prompt 重来。把没通过的地方讲清楚，让 AI 针对性修改，不要自己上手手改哪怕一行。

第三条原则最容易被打破，也值得说明原因。自己动手改了一行后，这行代码就脱离了 Prompt 的追溯链。下一次调整状态机规则或事务落盘顺序时，AI 读到这一行，无法得知修改背景与意图，往往会将其当成既有设计保留，或者直接当作异常改回去。第 11 课讲验证时提到过，验证要留下可回查的证据，不能仅凭看过了、感觉没问题。手改代码无法沉淀这种证据，只存在于当下的临时记忆中。记忆会随时间模糊，代码也不会主动提示它已偏离规格。

验收纪律定了，先把读路径的地基铺起来。

## 二、core 三件：parsers、state、writer

`media` 这个命令行工具最终会有十几条命令。如果每条命令各自去读文件、各自判断状态是否合法、各自往磁盘上写数据，同一个坑难免会在不同命令里各踩一次。core 包要解决的是这件事：把读、判、写这三块公共逻辑收进三个模块，命令行本身只做参数解析和调用，逻辑只写一遍。

parsers 负责把磁盘上的原始文本变成程序能用的结构化数据，读取几类真相源文件：每条内容自己的 `meta.yaml`、选题池的 `backlog.yaml`，还有治理线记事用的日志文件，比如 `harness/logs/index.jsonl`。这里有个容易被忽略的设计点：单个文件解析失败，不能把整仓的读取一起拖垮。哪怕现在 `content/` 下只有一条内容，这条规则也要提前定下来。以后条目增多，一条 `meta.yaml` 格式写坏了，`st` 这类总览命令仍应把其余健康状态列出来，损坏的那条单独标明解析错误。这项设计要求要写进给 AI 的 Prompt 里，防止 AI 默认采用快速报错策略，一个文件读取失败就导致整个命令崩溃。

state 模块是状态机实现，两张迁移表在这里落成代码，只聚焦一件事：接收一个当前状态和一个目标状态，判断这次跳转是否合法。若不合法就报错，并把当前状态允许流转的目标列出来，报错提示示例如下：

```
E_ILLEGAL_TRANSITION: review → published 非法：review 当前合法出边为 drafting, approved, rejected
```

这条规则在第 13 课已经确定。四件套里“失败怎么报”一栏专门写明了这条规则，state 模块只是将其转化为可执行的判断逻辑，无需推倒重议。

writer 是这一段最费工夫的部分，管全部落盘动作。参考流水线的 writer 模块头注里，落盘顺序写得很直白：

```
落盘顺序：拿锁 → 构建快照 → 在快照上算出写计划（全部校验在此完成，任一失败即零写入）
  → 若是 dry-run 则打印计划退出 → 内存中算出全部新内容 → 逐文件原子落盘
  → 重生成派生视图（同一把锁内）→ 追加一行审计记录 → 释放锁。
```

这个执行顺序经过精心推敲，步骤调换容易引发异常。锁排在第一位，当两个写命令并发触发时，后到达的命令只能等待或报错退出，避免两者同时修改同一个文件。校验放在计算写计划这一步，确保非法状态或错误参数在真正写入磁盘前被拦截。拦截意味着零写入，不会产生改动一半中途失败的中间状态。dry-run 分支安排在计算完写计划之后、实际落盘之前。这样既能完整打印出拟写入内容供检查，又能确保磁盘不产生任何改动。

落盘阶段按文件逐个进行原子写入，先写入临时文件，再通过重命名替换为正式文件。这样能防止外部程序在写入过程中读取到残缺内容。派生视图的重新生成保持在同一把锁内，确保看板文件与真相源始终保持同步。审计记录在文件确认落盘后再追加，避免审计日志记录未实际生效的操作。锁在最后释放，且不论执行成功还是抛出异常都必须确保释放，避免因单次命令失败而阻塞后续所有写操作。

写事务底层由三个职责单一的子模块支撑：一个负责文件锁，一个负责原子写入，一个负责审计记录。每个子模块专注自身职责，不耦合额外判断。这里有一个容易遗漏的细节：操作出错时同样需要记录审计。当写命令因校验未通过被拒绝时，审计文件中同样需要留存一条记录，记明调用方、操作内容、失败结果以及具体原因。这项规则不仅为了完善日志，后续课程还会对其进行检验。M2 的出口条件明确要求，连续七天内每一次状态变更都能在审计文件中查到对应记录，其中也包含被拒绝的尝试。如果缺少失败记录，这一出口条件便无法自证。我们在这一课先把规范建立起来，具体验证留待后续章节展开。

```
参考 02-执行方案.md 里 core 模块的详细设计，
以及十四条命令四件套里读命令和写命令各自的读写字段，实现三个模块：
1. parsers：读 meta.yaml、backlog.yaml 和治理线的日志文件（如 harness/logs/index.jsonl），
   单个文件解析失败要降级返回一个错误标记，不能让整仓读取跟着崩掉
2. state：把我 01-ADR.md 和 02-执行方案.md 里定的两张状态迁移表
   实现成判断函数，不合法的跳转要报错并列出当前状态合法能去的地方
3. writer：一套事务写入的公共实现，供后面所有写命令复用，顺序固定为
   拿锁、算写计划（全部校验在这一步完成）、支持 --dry-run 提前退出、
   原子落盘、同一把锁内重新生成看板、写一行审计记录、释放锁
配一个往返测试：拿我仓库里真实的 meta.yaml 和 backlog.yaml，
读进来解析成结构化数据，再原样写回文本，跟原文件字节级对比要完全一致，
包括注释和注释前的对齐空格都不能变。
```

往返测试之所以要严格对齐到字节级别，重点在于防范隐性格式损坏。参考流水线在首次实现这段逻辑时，曾采用常见写法：先将整份 YAML 解析为内存对象，修改目标字段，再重新序列化写入磁盘。这种做法在全仓测试二十五份真实的 `meta.yaml` 与 `backlog.yaml` 时暴露出严重问题，零改动往返测试全部出现差异。排查发现，YAML 解析库在读取阶段就会丢弃行内注释前面的对齐空格，重新序列化时默认将其压缩为一个空格。这是解析阶段产生的信息丢失，无法通过微调序列化参数挽回。一旦采用完整解析再整体回写的方式，注释排版就会被压缩破坏，与代码编写精度无关。

语义层面的对比容易遗漏注释排版变化。丢失注释既不改变状态机判定，也不影响字段数值，人工审阅时难以察觉。但每次执行写命令，都会导致整个文件的注释排版被格式化重置。往返测试的核心任务就是守住底层格式，保证语义正确的同时兼顾文件格式零损耗。

拿自己的文件执行测试：在第 05 课建立的那一条内容，存放在 `content/<发布日>/<slug>/` 下的 `meta.yaml`，以及 `content/_backlog/backlog.yaml`。这两份文件自第 03 课起手工维护，已沉淀了原有的注释内容。AI 交付的往返测试示例如下：

```
测试：meta.yaml 零改动往返
  raw = 读取你那一条内容目录下 meta.yaml 的原始文本
  roundTripped = 用 parsers 读进来解析成结构化数据，再用 writer 的编辑接口原样写回去
  断言 roundTripped 与 raw 完全相等，一个字节都不能差
```

验收动作用自身那一条内容的 `meta.yaml` 与 `content/_backlog/backlog.yaml` 分别执行测试。只有测试全部通过才算达标，比对产生的 diff 必须完全为空。

如果往返测试产生的 diff 不为空，常见原因是 AI 采用了整文件重写逻辑，未限制在改动区间进行局部字节替换。这正是往返测试重点拦截的情况，此时应要求 AI 改用基于字节区间的局部编辑实现。

往返测试确保了字节级一致性，core 层的地基便已夯实。接下来在其基础上构建上层命令。

## 三、读命令全量：st、next、backlog ls、doctor

读命令优先实现，原因很明确：只读不写，验证成本低，不会损坏现有文件。读命令就绪后，能立即检验 core 三个模块的解析与状态计算是否准确，在推进写命令前形成一道实测防护。

四条命令职责分明。`st` 负责总览与单条查询，不带参数时查看在制内容概览，传入 slug 时显示该条内容的完整信息。`next` 负责模拟取题计算，仅演示当前拟选题目与选取依据，并不实际将状态从 idea 翻转为 picked，真正的取题记账交由 `promote` 执行。`backlog ls` 用于选题池检索，支持按状态、赛道过滤，并可按分数或创建时间排序。`doctor` 负责内容产物的完备性体检，例如检查封面图或字幕文件是否存在。产物体检与状态账本一致性检查分属不同职责，账本一致性核验属于 `check` 命令的工作，留待第 15 课实现。

`next` 是唯一一条只做逻辑判断、不改写文件的读命令，验证时更需要关注细节。不仅要检查最终选中的条目，还要核验其给出的决策理由。输出中应明确展示本次决策是依据最高分数还是人工指定的取题指针，并附带后续候选条目各自的分值，便于人工对照预期顺序完成核对。`doctor` 的设计细节同样关键：体检结果必须分级，缺失封面这类后续可补充的情况标记为警告，核心必要文件缺失则标记为错误，两档级别对应不同的退出码。后续 `pipeline/daily-run.md` 等自动化流程集成该命令时，需要依赖退出码判断流程是否阻断，不能将所有问题混为一谈。

```
参考 02-执行方案.md 里 st、next、backlog ls、doctor 这四条命令各自的
四件套详细设计，用刚实现好的 core 三件实现全部读命令。
这四条只读不写，任何一条都不许出现改动文件的代码路径。
backlog ls 要支持按状态、按赛道筛选，支持按分数或者创建时间排序。
next 除了报选中的那一条，还要报这次决策靠的是分数还是人工指针，
以及紧随其后的候选各自的分数。doctor 的体检结果要分错误和警告两个级别，
必须存在却缺失的文件标错误，能自己补的问题标警告，两级对应不同退出码。
```

验收动作是对每条命令传入真实数据执行，核对输出结果与仓库当前状态。
执行 `st --all`，查看列出的条目与状态是否与实际文件一致。
执行 `next`，观察推荐条目是否符合预期规则。如果选题池尚无正式入池数据，命令应明确提示无可用条目，避免异常报错或盲目选取。
执行 `backlog ls --status idea`，统计条目总数，确认与未取用选题数量相符。
执行 `doctor --all`，检查是否准确汇报已知的文件缺口，例如某条内容尚未生成的封面图。

```
$ media st --all
在制 1 条：
  <slug>  drafting  content/<发布日>/<slug>

$ media next
选题池中无 idea 可取。

$ media doctor --all
doctor 体检 1 条：0 error / 0 warn / 0 info
```

如果选题池中已录入测试选题，但 `next` 选出的结果不符合预期，常见原因是 `backlog.yaml` 中的取题指针指向了非 idea 状态的条目。此时规范的处理机制是忽略失效指针、自动降级按分值选取，并保持进程正常执行。可优先检查输出信息中是否包含指针被忽略的提示，再回查指针所指条目的当前状态。

四条读命令完成验收后，接下来进入写命令的实现，优先覆盖历史操作中最易出错的环节。

## 四、首批写命令：publish-done 与 promote

M1 阶段优先实现两条写命令，其余命令留待第 15 课交付。优先选择这两条命令具备明确考量。回顾此前手工维护 `meta.yaml` 和 `backlog.yaml` 的过程，取题记账与发布收尾两类操作最为频繁，也是一致性疏漏的高发区。取题记账需要同步更新选题池状态、回填生成目录、录入新目录元数据，任一处遗漏都会导致后续追溯断裂。发布收尾更为关键，内容正式发布后，元数据状态、发布时间戳、选题池对应条目状态必须一次性全部同步，局部缺失将直接污染复盘指标。十四条命令中的 `promote` 与 `publish-done` 正好承接这两类场景。优先管住高风险手改操作，是阶段切分的原则。

发布收尾命令的核心目标可概括为“三处同步翻转”：元数据、时间戳、选题池条目必须在同一次操作中完整更新，任何一处失败则整体回滚。单靠人工分布操作，一旦中间环节受到打断，例如修改完元数据后临时离开，剩余文件就会滞留在中间状态，且缺乏告警提示。写命令引入事务机制，保证多处更新具备原子性，要么全部生效，要么全部不生效，消除半修改隐患。

`promote` 的四件套：

| 项 | 内容 |
|---|---|
| 参数 | id 或 `--auto` 二选一（`--auto` 走跟 `next` 同一套取题逻辑）、必填的 `--slug`、可选的 `--date` |
| 读 | 选题池里目标条目的当前状态；内容模板目录在不在；目标目录是不是已经存在 |
| 写 | 选题池那条记录的状态从 idea 翻成 picked 并回填内容目录路径；新建一份内容目录（从模板复制）；新目录里 `meta.yaml` 的标题、类型、赛道、来源等字段 |
| 失败怎么报 | 目标条目不存在报错；状态不为 idea 报错并说明当前是什么状态；目标目录已经存在报错；模板目录缺失报错 |

`publish-done` 的四件套：

| 项 | 内容 |
|---|---|
| 参数 | 必填的 slug、可选的 `--scheduled`（定时发布用）、可选的 `--url`（回填作品链接） |
| 读 | 这条内容当前的状态；它在选题池里对应的那条记录 |
| 写 | approved 状态直接改成 published 或者转成 scheduled，只动元数据；scheduled 状态到点收尾，元数据和选题池那条记录一起翻成 published；已经是 published 状态的只补链接，状态不再动 |
| 失败怎么报 | 状态不在 approved、scheduled、published 三档之内的一律拒绝；已经 published 但没带 `--url` 的补填请求拒绝；选题池里找不到对应记录的拒绝，三处凑不齐就整体不改，不许只改一半 |

```
按 02-执行方案.md 里 promote 和 publish-done 这两条的四件套，
用 core 三件实现这两条写命令。两条都要走完整的写事务：
拿锁、在写计划里做完全部校验、支持 --dry-run、原子落盘、
同一把锁内重新生成看板、写一行审计记录、释放锁。
promote 一次要把选题池状态、内容目录、meta.yaml 三处一起改对；
publish-done 按当前状态分三种情况处理，缺任何一处依赖就整体拒绝，不许只改一半。
```

M1 的出口条件在第 13 课已经明确：在真实仓库中执行 `media check` 能够通过，且 YAML 文件中原有的注释完整留存。此处提到了第 15 课才会实现的命令，但逻辑并不冲突。出口条件定义的是 M1 最终应达到的基线标准，校验工具的开发可按计划分步进行。工具拟检验的状态流转正确性与注释完整性，本课可借助现有手段先行验证。核心分为两步：确保往返测试全部通过，以及针对两条写命令执行 `--dry-run` 预览。待第 15 课实现 `check` 命令后，再执行完整的一致性确认。

验收动作分两步。执行前先准备测试环境：在 `backlog.yaml` 中增加一条状态为 idea 的测试选题，同时将已有那条内容的状态置为 approved。

第一步，分别对 `promote` 和 `publish-done` 跑一次 `--dry-run`，看打印出来的写计划：

```
$ media promote --auto --slug roundtrip-test --dry-run
（dry-run）
  content/_backlog/backlog.yaml
  content/<今天日期>/roundtrip-test
  content/<今天日期>/roundtrip-test/meta.yaml
```

列出的文件和字段要刚好对应四件套表里写的那几处，不能多出一个没预料到的文件。

第二步，把 dry-run 换成真跑一次，跑完之后打开被改的 `meta.yaml` 和 `backlog.yaml`，人工翻一遍确认两件事：状态确实翻转了，原来那些叙事性的注释一行没少。写计划的 diff 应该只包含被改的那几行，比如状态那一行和新加的一行记账注释：

```
--- a/content/_backlog/backlog.yaml
+++ b/content/_backlog/backlog.yaml
@@ -8,1 +8,2 @@
-    status: idea
+    status: picked  # 2026-09-04 promote (media)
```

其余内容不出现在 diff 里，哪怕 `backlog.yaml` 眼下只有寥寥几行，这条规则也一样成立。

如果 dry-run 打印出的写计划中包含了非预期文件，或者整份 `backlog.yaml` 均被标记为改动，无法精确呈现局部变动行，通常是写命令未执行点位编辑，退化为整文件全量重写。这正是 M1 出口条件要求防范的情形。此时应要求 AI 检查 writer 模块实现，确保其基于字节区间执行精准替换，避免全量解析与序列化。

两项检查确认无误后，M1 出口条件在当前阶段的验证即可收官。至此，取题记账与发布收尾两项高频操作告别了手工修改，全面切换为 `promote` 与 `publish-done` 命令行操作。至于常规状态流转、选题入池与清理、人工指针设定、复盘指标回填及看板重建等场景，目前暂沿用既有操作方式，留待第 15 课补齐命令后统一收敛。

core 模块与首批写命令正常运转，M1 阶段出口条件顺利达成。
