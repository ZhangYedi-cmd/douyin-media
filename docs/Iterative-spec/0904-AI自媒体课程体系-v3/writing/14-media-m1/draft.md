# 执行 M1：core 三件与首批命令怎么跑起来

上一课交完了 `docs/spec/media/02-执行方案.md`：十四条命令逐条拆成参数、读什么、写什么字段、失败怎么报这套四件套；两张状态迁移表，一张管 `meta.yaml` 的八个状态，一张管 `backlog.yaml` 的六个状态；M1、M2 两个里程碑切好了，各自的出口条件都写成了一句能跑的验证动作。文章结尾抛出的问题是：执行方案写完，开始施工，第一个里程碑做哪些？

这一课回答这个问题，但回答的方式跟前面几课不一样。前十三课，学员的活是想清楚、写下来，判据、契约、SPEC，每一样最终都要落成一份人写的中文文档。从这一课起，活变了：AI 按 `02-执行方案.md` 施工，学员的活是验收，看出口条件过没过。

## 1. 开篇：规格能施工了，学员只验收不编码

记忆锚点：从这一课起，学员的活从定判据变成验收出口条件，AI 写代码，人只问过没过。

验收纪律就三句话。第一句，出口条件过没过是唯一准绳，不是代码写得漂不漂亮，也不是 AI 有没有按照你脑子里想的方式实现，那是 AI 的自由，出口条件才是硬指标。第二句，看不懂就让 AI 解释或者重写，问一句这段在干什么、为什么这么写，成本比自己去猜低得多。第三句，出口条件没过就换个 Prompt 重来，把没过的地方讲清楚再让 AI 改一遍，不自己上手改一行。

第三句最容易被破坏，也值得多说一句为什么。你自己动手改一行之后，这一行代码从此没有 Prompt 能对应它。下一次要调整状态机规则或者事务落盘的顺序，AI 读到这一行，不知道它是谁改的、为什么改成这样，多半会当成既有设计的一部分保留下来，或者干脆当成 bug 改回去。第 11 课讲验证那一步时说过，验证要留下能回查的证据，不能只凭看过了、应该没问题。手改的一行代码留不下这种证据，它只存在于你当时的记忆里，记忆会过期，代码不会主动告诉任何人它跟规格已经不一致了。

验收纪律定了，先把读路径的地基铺起来。

## 2. core 三件：parsers、state、writer

`media` 这个命令行工具最终会有十几条命令。如果每条命令各自去读文件、各自判断状态合不合法、各自往磁盘上写字节，同一个坑迟早会在不同命令里各摔一次。core 包要解决的是这件事：把读、判、写这三块公共逻辑收进三个模块，命令行本身只做参数解析和调用，逻辑只写一遍。

parsers 负责把磁盘上的原始文本变成程序能用的结构化数据，读的是几类真相源文件：每条内容自己的 `meta.yaml`、选题池的 `backlog.yaml`，还有治理线记事用的日志文件，比如 `harness/logs/index.jsonl`。这里有个容易被忽略的设计点：单个文件解析失败，不能把整仓的读取一起拖垮。三十条内容里有一条的 `meta.yaml` 格式写坏了，`st` 这类总览命令应该照样把另外二十九条的状态列出来，坏掉的那条单独标一个解析错误。这条设计要求得写进给 AI 的 Prompt 里，不然 AI 大概率会图省事，一个文件读不出来就让整个命令崩掉。

state 是状态机，两张迁移表在这里落成代码，只做一件事：给一个当前状态和一个目标状态，判断这次跳转合不合法。不合法就报错，并把当前状态还能去的地方列出来，报错文本大致是这个样子：

```
E_ILLEGAL_TRANSITION: review → published 非法：review 当前合法出边为 drafting, approved, rejected
```

这条规则第 13 课已经定过了，四件套里失败怎么报那一栏专门写了这一句，state 模块只是把它变成能跑的判断逻辑，不重新讨论一遍。

writer 是这一段最费工夫的部分，管全部落盘动作。参考流水线的 writer 模块头注里，落盘顺序写得很直白：

```
落盘顺序：拿锁 → 构建快照 → 在快照上算出写计划（全部校验在此完成，任一失败即零写入）
  → 若是 dry-run 则打印计划退出 → 内存中算出全部新内容 → 逐文件原子落盘
  → 重生成派生视图（同一把锁内）→ 追加一行审计记录 → 释放锁。
```

这个顺序不是随手排的，每一步换个位置都会出问题。锁必须最先拿：两个写命令同时跑，后拿到锁的那个要么等要么直接报错退出，不能两边同时改同一个文件。校验必须在真正写之前全部做完：状态不合法、参数不对，这些判断要在算写计划这一步就抛出来。抛出来意味着后面一行都不会执行到，这次操作是零写入，不会留下改了一半又失败的中间状态。dry-run 的分支要排在算完写计划之后、真正落盘之前，这样它能把要写的东西完整算出来给人看，又保证一个字节都不真的落地。

落盘本身要按文件逐个原子写入，先写到一个临时文件，再改名换成正式文件，防止有别的程序在文件写到一半的时候读到一份不完整的内容。派生视图的重新生成要放在同一把锁里，这样看板文件不会有哪怕一瞬间落后于真相源的机会。审计记录要等文件真的落盘之后才追加，不然审计里可能记着一次实际上没发生的改动。锁最后释放，而且不管中间是成功还是抛错都要释放，否则一次失败的命令会把后面所有写命令都堵死。

写事务底下其实是三个各管一件事的小模块：一个管锁，一个管原子写入，一个管审计记录，各自只做自己那一件事，不掺和别的判断。这里有个细节容易被漏掉：出错的时候也要记一笔审计，不是只有成功才记。一次校验没通过被拒绝的写命令，同样要在审计文件里留一行，记着这次谁调用了什么、结果是失败、原因是什么。这条规则现在看起来只是多一行日志，往后几课会用到它：M2 的出口条件要求连续七天内每一次状态变更都能在审计文件里查到对应的一行，包括那些被拒绝的尝试，缺了失败记录，这句话就没法自证。这一课先把这个习惯立住，验证的那一步留到后面。

```
参考 02-执行方案.md 里 core 模块的详细设计，
以及十四条命令四件套里读命令和写命令各自的读写字段，实现三个模块：
1. parsers：读 meta.yaml、backlog.yaml 和治理线的日志文件（如 harness/logs/index.jsonl），
   单个文件解析失败要降级返回一个错误标记，不能让整仓读取跟着崩掉
2. state：把我 01-ADR.md 和 02-执行方案.md 里定的两张状态迁移表
   实现成判断函数，不合法的跳转要报错并列出当前状态合法能去的地方
3. writer：一套事务写入的公共实现，供后面所有写命令复用，顺序固定为
   拿锁、算写计划（全部校验在这一步完成）、支持 --dry-run 提前退出、
   原子落盘、同一把锁内重新生成看板、写一行审计记录、释放锁
配一个往返测试：拿我仓库里真实的 meta.yaml 和 backlog.yaml，
读进来解析成结构化数据，再原样写回文本，跟原文件字节级对比要完全一致，
包括注释和注释前的对齐空格都不能变。
```

为什么往返测试要卡到字节级别，而不是看内容语义对不对，这里有个真实踩过的坑值得说一下。参考流水线第一次实现这段代码时，用的是最直接的写法：把整份 YAML 解析成对象、改掉要改的字段、再重新序列化成文本写回去。听起来没问题，跑起来才发现事故：拿全仓真实的二十五个 `meta.yaml` 和 `backlog.yaml` 做零改动往返测试，二十五个全部不一致。查下去，根因是 YAML 解析库在解析阶段就把行内注释前面的对齐空格丢了，重新序列化的时候统一压成一个空格。这是解析这一步就已经发生的信息损失，不是调整序列化选项能找回来的。只要走了完整解析再完整吐回去这条路，注释的排版必丢，跟代码写得细不细无关。

这条教训直接决定了往返测试要验到字节这一级，而不是验语义。语义级别的对比会漏掉注释丢失这类问题：丢了注释不影响状态机怎么判断，也不影响哪个字段的值是什么，人肉眼扫一遍代码容易觉得没问题，实际每次写命令跑过都会把全文件的注释排版冲掉一轮。往返测试要验的正是这一层，语义对不对是另一件事，两件事都要过。

拿你自己仓库里的真实文件跑一遍，比如 `content/2026-06-19/ep05-permission-pipeline/meta.yaml` 这份文件，光是开头就有二十多处 `#` 注释，记着真实发布过程中的时间点和终检结论。AI 交回来的往返测试大致长这样：

```
测试：meta.yaml 零改动往返
  raw = 读取 content/2026-06-19/ep05-permission-pipeline/meta.yaml 的原始文本
  roundTripped = 用 parsers 读进来解析成结构化数据，再用 writer 的编辑接口原样写回去
  断言 roundTripped 与 raw 完全相等，一个字节都不能差
```

验收动作是拿你仓库里三五个真实的 `meta.yaml` 和那份 `backlog.yaml` 各跑一遍这个测试，全部通过才算过，跑出来的 diff 应该是空的，不是差异很小。

如果往返测试的 diff 不是空的，多半是 AI 图省事，把整份文件解析完之后又整份重新生成了一遍再写回去，没有只在改动的那一小段字节上做替换。这正是往返测试要拦住的写法，回去让 AI 换成按字节区间编辑的实现。

core 有了，读路径可以往上搭命令了。

## 3. 读命令全量：st、next、backlog ls、doctor

读命令先上，理由很直接：只读不写，验证代价最低，出了问题不会真的改坏任何文件。它们跑起来还能立刻检验 core 三件是不是真的读对了、状态机算得对不对，等于往下走写命令之前多一层实测。

四条命令各管一件事。`st` 是总览和单条查询，不带参数看在制内容的总览，带一个 slug 看这一条的全量信息。`next` 是模拟取题，只算这次会取哪一条、为什么取它，不真的把状态从 idea 翻成 picked，取题记账的动作留给 `promote`。`backlog ls` 是选题池查询，可以按状态、按赛道筛，也能按分数或者创建时间排序。`doctor` 管的是内容产物本身的格式体检，比如封面图在不在、字幕文件在不在，跟状态账本是不是一致是两码事，账本一致性检查是 `check` 命令的活，这一课先不碰，留到第 15 课。

`next` 值得多说一句，因为它是唯一一条纯做判断、不落一个字的读命令，验证起来反而最容易糊弄过去，光看它选中了谁不够，还要看它给出的理由。除了选中的那条，它应该同时报出这次决策靠的是排在最前的分数还是一个人工指定的取题指针、还有紧随其后的两条候选各自的分数，这样你才能对着自己心里的排序核一遍，而不是只信一个结果。`doctor` 也有个容易漏掉的设计点：体检结果要分级，缺封面这种能自己补的问题标成警告，某个必须存在的文件彻底缺失才标成错误，两档级别对应的退出码不一样，后面接自动化调度的时候要靠这个退出码判断能不能继续往下走，不能所有问题都用同一个级别糊在一起。

```
参考 02-执行方案.md 里 st、next、backlog ls、doctor 这四条命令各自的
四件套详细设计，用刚实现好的 core 三件实现全部读命令。
这四条只读不写，任何一条都不许出现改动文件的代码路径。
backlog ls 要支持按状态、按赛道筛选，支持按分数或者创建时间排序。
next 除了报选中的那一条，还要报这次决策靠的是分数还是人工指针，
以及紧随其后的候选各自的分数。doctor 的体检结果要分错误和警告两个级别，
必须存在却缺失的文件标错误，能自己补的问题标警告，两级对应不同退出码。
```

验收动作是对每条命令跑一次真实数据，拿输出跟自己肉眼记得的状态对一遍。跑 `st --all` 数一下总条数，跟你自己心里记的在制内容数量对不对得上；跑 `next` 看它选中的是不是你自己认为该轮到的那一条；跑 `backlog ls --status idea` 数一下条数，跟选题池里还没被取走的条目数对不对得上；跑 `doctor --all` 看有没有报出你自己知道存在的产物缺口，比如某条内容确实还没做封面。

```
$ media st --all
在制 6 条：
  ep14-cache-break-detection  drafting  content/2026-06-28/ep14-cache-break-detection
  spec-driven-development     review    content/2026-07-08/spec-driven-development
  ...

$ media next
取题决策：score
  id=2026-09-01-003  score=8.4  track=depth
  runnerUp: 2026-09-01-005(8.1), 2026-08-30-002(7.9)

$ media doctor --all
[WARN] ep14-cache-break-detection missing-cover: 未找到 cover 文件
doctor 体检 30 条：0 error / 1 warn / 0 info
```

如果 `next` 选出来的题目跟你自己以为该选的对不上，多半是 `backlog.yaml` 里的取题指针指向了一条已经不是 idea 状态的条目。这时候合法的行为是忽略这个指针改按分数选，不是报错卡住，先看输出里有没有一行提示指针被忽略了，再回头去查那条指针指向的条目现在是什么状态。

读路径全通了，写路径先切两个历史事故最集中的命令。

## 4. 首批写命令：publish-done 与 promote

M1 只上两条写命令，剩下七条留到第 15 课，先切这两条不是随便挑的。回头看你从第 03 课起手改 `meta.yaml` 和 `backlog.yaml` 的经历，取题记账和发布收尾这两类动作出现的次数最多，也最容易漏改一处。取题记账要同时改选题池那条记录的状态、回填内容目录、再把新目录里的元数据填一遍，三处漏一处，后面查起来就是一笔糊涂账。发布收尾更麻烦，一条内容真正发布出去之后，元数据的状态、时间戳、选题池那边对应条目的状态得一次性翻对，漏了哪一处，日后复盘的时候数据就是错的。这两类动作对应到十四条命令里，正是 `promote` 和 `publish-done`。参考流水线选第一批写命令时用的也是同一条判断：不按代码模块切，按哪几条命令对应的手编写点最容易出错切，历史事故集中的地方先管起来。

发布收尾这条命令内部常被叫作三翻齐，意思是元数据、时间戳、选题池三处要在同一次操作里一起翻对，缺一处就整体不算数。之所以要靠一条命令而不是靠人手动分三步做，是因为人手动做的时候，中间任何一步被打断，比如改完元数据去改选题池之前被叫走处理别的事，剩下的两处就会停在半改的状态，而且没有任何东西提醒你它们没改完。写命令走事务，要么三处都改，要么一处都不改，不存在半改的状态。

`promote` 的四件套：

| 项 | 内容 |
|---|---|
| 参数 | id 或 `--auto` 二选一（`--auto` 走跟 `next` 同一套取题逻辑）、必填的 `--slug`、可选的 `--date` |
| 读 | 选题池里目标条目的当前状态；内容模板目录在不在；目标目录是不是已经存在 |
| 写 | 选题池那条记录的状态从 idea 翻成 picked 并回填内容目录路径；新建一份内容目录（从模板复制）；新目录里 `meta.yaml` 的标题、类型、赛道、来源等字段 |
| 失败怎么报 | 目标条目不存在报错；状态不是 idea 报错并说明当前是什么状态；目标目录已经存在报错；模板目录缺失报错 |

`publish-done` 的四件套：

| 项 | 内容 |
|---|---|
| 参数 | 必填的 slug、可选的 `--scheduled`（定时发布用）、可选的 `--url`（回填作品链接） |
| 读 | 这条内容当前的状态；它在选题池里对应的那条记录 |
| 写 | approved 状态直接改成 published 或者转成 scheduled，只动元数据；scheduled 状态到点收尾，元数据和选题池那条记录一起翻成 published；已经是 published 状态的只补链接，状态不再动 |
| 失败怎么报 | 状态不在 approved、scheduled、published 三档之内的一律拒绝；已经 published 但没带 `--url` 的补填请求拒绝；选题池里找不到对应记录的拒绝，三处凑不齐就整体不改，不许只改一半 |

```
按 02-执行方案.md 里 promote 和 publish-done 这两条的四件套，
用 core 三件实现这两条写命令。两条都要走完整的写事务：
拿锁、在写计划里做完全部校验、支持 --dry-run、原子落盘、
同一把锁内重新生成看板、写一行审计记录、释放锁。
promote 一次要把选题池状态、内容目录、meta.yaml 三处一起改对；
publish-done 按当前状态分三种情况处理，缺任何一处依赖就整体拒绝，不许只改一半。
```

M1 的出口条件是第 13 课就定死的一句话：真实仓库里跑 `media check` 能通过，YAML 文件里原有的注释一处都没丢。这句话现在还差一半验不了，`check` 这条命令要到下一课才造，这一课没有它可跑。M1 出口条件先用两件事替代验证：往返测试全绿，两条写命令各跑一遍 `--dry-run`。等第 15 课把 `check` 真正造出来，再跑一次真正的 `media check` 做最终确认，这一课先把能验的部分验完。

验收动作分两步。第一步，挑一条你仓库里真实存在的选题池条目和一条已经到了 approved 状态的内容，分别对 `promote` 和 `publish-done` 跑一次 `--dry-run`，看打印出来的写计划：

```
$ media promote --auto --slug roundtrip-test --dry-run
（dry-run）
  content/_backlog/backlog.yaml
  content/2026-09-04/roundtrip-test
  content/2026-09-04/roundtrip-test/meta.yaml
```

列出的文件和字段要刚好对应四件套表里写的那几处，不能多出一个没预料到的文件。

第二步，把 dry-run 换成真跑一次，跑完之后打开被改的 `meta.yaml` 和 `backlog.yaml`，人工翻一遍确认两件事：状态确实翻转了，原来那些叙事性的注释一行没少。写计划的 diff 应该只包含被改的那几行，比如状态那一行和新加的一行记账注释：

```
--- a/content/_backlog/backlog.yaml
+++ b/content/_backlog/backlog.yaml
@@ -42,1 +42,2 @@
-    status: idea
+    status: picked  # 2026-09-04 promote (media)
```

其余内容不出现在 diff 里。

如果 dry-run 打印出来的写计划里出现了没预料到的文件，比如整份 `backlog.yaml` 都被列进了改动范围，只列出被改的那一段却做不到，多半是写命令没有做点位编辑，走的是整份文件重新生成再写回去这条路。这正是 M1 出口条件里注释零丢失要卡住的写法，回去让 AI 检查 writer 的实现有没有真的按字节区间替换，而不是先完整解析再完整吐出来。

两件事都过了，M1 出口条件就算验完了这一课能验的部分。从现在起，取题记账和发布收尾这两处不用再手改 `meta.yaml` 和 `backlog.yaml` 了，改跑 `promote` 和 `publish-done`。状态翻转、选题池的入池和清扫、人工指定取题指针、复盘数据落账、重建看板，这五类动作还没有被搬进来，仍然是手改的老办法，等第 15 课全量补齐再一并收敛。

core 和第一批命令都跑起来了，M1 出口条件过了。

## 5. 收尾：读写各通一半

这一课结束时，手上多了跑得起来的 core 包和 M1 那批命令。parsers、state、writer 三个模块配着能对真实文件跑通的往返测试，四条读命令，两条写命令，M1 出口条件用往返测试和两条写命令的 dry-run 加真跑验过了。

还看不到的是全貌。十四条命令里还有七条没影，`check` 这条专门验账本一致性的命令还没造。前十课手改过的其余五类动作还散在各处：状态翻转还是打开文件改一行，入池和清扫还是手动编辑 `backlog.yaml`，复盘数据落账还是手写进对应字段。这些地方现在还能改对，只是因为你一直盯着，没有一条命令替你把关。

core 和第一批命令跑起来了。剩下的写命令、`check`，还有前十课手改过的那些地方，怎么收敛到这一个入口？
