## 1. 回路怎么接：判、修、复判轮流交棒
核心判断: 自愈回路不是失败了重试一次，是判、修、复判三件事轮流换人做——裁判判完交给主回话改，主回话改完交回裁判判，每次交棒都换一个角色，不是同一个人反复试。
支撑材料: `pipeline/2-create.md` 步骤 4 全文（配音审批 subagent 闸口段落）；`.claude/agents/dubbing-reviewer.md` 的边界段（只判不改）
交付物: Prompt 块——上一课判决 FAIL 时，按 BLOCKING 逐条修（`tts.config.json` 的 `overrides`、文案 normalize、组件整句对齐），改完在 `build/` 里重新跑一遍合成，再派 `dubbing-reviewer` 带轮次号复审
二级标题: none
收尾交接: 环能转起来了，但没人规定它能转几圈，不停下来的话代价谁来兜

## 2. 熔断线画在哪：三轮不过就停，不是统计出来的
核心判断: 三轮上限是这个项目自己拍板的工程约定，全链路返工代价太大（判、改、合成、复判绕一圈都不便宜），不是从大量样本里统计出来的最优轮次，换一个项目、换一个代价结构，答案未必还是 3；同时点破它按批计轮的局限——轮次数的是同一批音频的判、修、复判次数，不是跨批累加，也不是内容条目层面的总重试次数。
支撑材料: `.claude/agents/dubbing-reviewer.md` 裁决口径表和「若 ROUND 已是 3」原文；`pipeline/lessons.md` L10/L16/L17/L18 四条教训作为真实缺陷来源
交付物: 对比表——熔断线（无限重试/1 轮/3 轮）对应的代价与已知问题
二级标题: none
收尾交接: 停在哪定了，停下来之后状态怎么落、谁接手，还没写清楚

## 3. 熔断落地：状态怎么记，人从哪接手
核心判断: 熔断不是把问题扔在原地不管，是把状态如实记下来、按阻塞即上报的铁律推给人；这一步现在只能手改 `meta.yaml`，因为还没有一个统一的状态命令入口，这是临时手段，第 15 课会把它收敛掉；此时学员没有飞书通道，上报动作写成在约定的通道通知人。
支撑材料: `pipeline/daily-run.md`「阻塞即上报」一节；`content/_template/meta.yaml`（状态字段与临时手改的位置）；`tools/console/packages/core/src/state.ts`（合法状态值只到 drafting，没有单独的挂起状态）
交付物: Prompt 块——三轮仍 FAIL 时，把这条内容的 `meta.yaml` 手改留在 `drafting`（此时没有统一的状态命令，只能手改，第 15 课起用 `media` 命令收敛掉）；把裁判最后一轮的 BLOCKING 内容写进 `3-review.md`；按 `daily-run.md`「阻塞即上报」的铁律，在约定的通道推一条文本通知（事件/根因/需要人做什么），只写本地日志不算上报
二级标题: none
收尾交接: 判、修、停三条路都定了，该真跑一次留下记录了

## 4. 跑一次真实闭环，把它记下来
核心判断: 闭环立没立住，看的是有没有一次真实发生过的 FAIL 到 PASS 记录，不是设计文档写得多完整；三类真实缺陷（死气、多音字、同段两读）的修法参考流水线上踩过的教训，各自的边界要点破。
支撑材料: `pipeline/lessons.md` L16（depause 原地写静默失败）、L10（多音字漏注音）、L18（增删段后 overrides 键错位）、L17（同段两读改文案）
交付物: 操作序列——合成到派 `dubbing-reviewer` 判 R1 到 FAIL 按改法修到重合成到派 R2 复审到 PASS（或到 R3 仍 FAIL 走上一节的熔断动作）；把每轮的时间、判决、BLOCKING、改法整理成一份记录存进这条内容目录
二级标题: none
收尾交接: 自愈回路合上了，但一路走来手改了一堆 `meta.yaml`，后面还有几件大得多的东西要造（状态中枢、飞书闸口、控制台），一条 prompt 显然不够，怎么让 AI 造这种量级的东西
