# 飞书通道实现：出站发卡、按钮回流与状态翻转

第 18 课明确了飞书闸口的四个决策点。
选用长连接方案，不依赖 webhook。
将交互拆为三张卡片，每张卡片最多配置两个按钮。
在回调的 3 秒窗口内，同步路径严格限定在内存操作。
卡片按钮的交互载荷中，统一注入命名空间字段。
这些决策已沉淀在 `docs/spec/feishu-gate/` 目录下的 `00-调研.md`、`01-ADR.md` 与 `02-执行方案.md` 中。
这一课不再重复选型讨论，核心任务是将规范转化为稳定运行的服务代码。

记忆锚点：验证闸口是否真正落地，关键看系统状态是否发生改变，而不是看服务输出的日志报告。
该标准需要通过四项具体观察来印证。
第一，卡片是否真实推送到飞书群聊。
第二，点击按钮后是否准确流转到对应的状态出边。
第三，3 秒的回调响应时限是否切实守住。
第四，内容的状态字段是否切实完成了终态流转。
这四项指标均有客观结果可供核查，不依赖服务自身的口头汇报。

本课的输入主要包括三部分。
一是第 18 课沉淀的 `02-执行方案.md`，重点是卡片结构与 3 秒回调窗口条款。
二是本地 core 包 state 模块中 `review` 状态的三条出边定义，用于映射卡片按钮。
三是第 10 课沉淀的熔断机制经验。
最终产出一个能够推送卡片、接收按钮回调并将结果落盘为状态流转的常驻服务。
参考流水线在 `tools/feishu-bot/` 目录下有一套生产环境代码。课程中会引用其架构设计，重点是借鉴其结构形态。实际实现仍需以本地规范为准，驱动模型依照自己的契约进行编写。

创建自建应用需要企业或团队账号的前提，第 18 课已做说明，此处不再赘述。

## 一、出站发卡：三步发送顺序

推送审核信息时，不能将内容压缩为一句简略摘要就交由人工审批。
推送物料需要遵循严格的先后次序。
首先推送口播稿全文或图文简介，确保人工审阅的是真实的文本细节。
其次推送封面图，若是图文类型则完整推送全部配图。
最后推送承载通过与打回两个操作按钮的审核卡。
若次序倒置，人工先看到卡片再去翻找内容，往往容易仅凭片面印象草率确认，这与设立闸口的初衷相违背。

参考流水线中的 `tools/feishu-bot/notify.py` 严格遵循该次序执行。
文稿优先读取 `2-script.md`，若不存在则回退读取 `copy.txt`。
配图方面，口播视频仅推送封面，图文类型则推送全量配图。
最后调用卡片模块组装并推送审核卡。
成片视频由于体积超出飞书限制，不直接上传文件本体，而是在物料摘要中标注文件名，供本地查阅。
这三个步骤应当保持相互独立。若封面上传偶发失败，文稿与审核卡依然需要正常发送，确保人工可以先行审阅已有内容。卡片中明确注明缺失项即可，避免局部异常阻塞整个出审通道。

让 AI 照你自己的执行方案实现这一步：

```
照我 docs/spec/feishu-gate/02-执行方案.md 里卡片结构那一条，
实现出站发卡脚本，发送顺序固定为三步：
1. 先发文稿全文（口播稿优先，没有就用图文简介文本）；
2. 再发配图（口播只发封面，图文发全部配图）；
3. 最后发审核卡，卡片上只放"通过"和"打回"两个按钮，
   按钮的 value 字段要带上命名空间字段，
   具体字段名和取值按我 01-ADR.md 里命名空间隔离那条决策来。
三步之间互相独立：前一步失败也要继续尝试后面的步骤，
不能因为封面传失败就连审核卡也不发。
```

拿到生成代码后，重点检查三项要点。
一是发送次序是否合规，必须遵循先内容物料后卡片的原则。
二是局部步骤失败时，其余步骤是否具备容错并正常执行。
三是按钮交互载荷中是否准确包含了命名空间字段。
命名空间字段容易遗漏。若同一个飞书群挂载了其他项目的机器人，未携带该字段会导致回调事件来源不明。服务端可能误处理外部卡片，或者将本项目的操作当作无关噪音丢弃。

如果卡片推送成功但交互无反应，常见原因是后台的长连接服务尚未启动。
出站脚本负责单向投递消息，并不保证点击后具备处理能力。
在推送卡片之前，先确认长连接监听进程处于正常运行状态，应当作为常规检查动作。

卡片顺利发出后，下一步是解决按钮点击后的事件承接与路由。

## 二、按钮回流：按钮与状态出边的映射

`state.ts` 中 `review` 状态包含三条出边：分别流向 `approved`、`drafting` 与 `rejected`。
但审核卡上仅设置通过与打回两个按钮，遵循了第 18 课规定的单卡最多两个按钮的约束。
三条出边无法直接对应两个按钮。打回操作需要进一步分流为重做与挂起两条路径。
参考流水线的设计是让打回按钮不直接触发状态流转。点击后弹出第二张卡片，即包含输入框的打回原因卡。
打回原因卡上配置两个按钮：打回并自动重做、打回并挂待办。
这两个按钮分别承接对应的状态流转。这样每张卡片均未超出两个按钮的配额，三条出边也得到了妥善映射。

| 卡片 | 按钮 | 触发的出边 | 是否要求填原因 |
|---|---|---|---|
| 审核卡 | 通过 | review 到 approved | 否 |
| 审核卡 | 打回 | 不直接改状态，弹出打回原因卡 | 不涉及 |
| 打回原因卡 | 打回并自动重做 | review 到 drafting | 否 |
| 打回原因卡 | 打回并挂待办 | review 到 rejected | 是 |

最后一列并非随意设定。要求填写原因，指的是改状态命令接收的原因参数不得为空，并不强制要求用户输入文本后按钮才变为可用状态。
参考流水线的处理方式是：用户输入了内容则传递实际文本，未输入则传递默认的占位说明。在这两种情况下，底层命令接收到的参数均为有效非空值，按钮始终保持可交互。
打回原因卡上的输入框对两个按钮通用。打回重做虽然不强制填写理由，但填写的文字会作为重做方向的提示信息传递，未填写也不影响流程推进。

打回并自动重做具有防死循环机制：必须设置重做熔断上限，达到阈值即转交人工，避免无限重做。
第 10 课在配音质检中设置过三轮熔断，但两者的业务场景与触发机制完全不同。
第 10 课的配音熔断由代码脚本判定质量，通过自动化判决器控制同一批音频的重录轮数。
而本课的熔断针对的是人工在飞书端打回的累计次数。人工主观评审缺乏机器能完全量化的指标，不能依赖系统反复自愈。
参考流水线将该上限设定为 `REWORK_LIMIT = 2`，代码注释明确注明主观反馈缺乏客观量化指标，不可无限制循环。
这一限额与第 10 课的配音熔断相互独立，各自对应不同节点的安全防线。

熔断次数的统计方式无需引入额外的状态计数器。直接统计当前内容目录下 `3-review.md` 中记录的打回重做日志行数即可。
该文件是每条内容独立的生命周期留痕文件，来源于内容模板，与全局阶段契约 `pipeline/3-review.md` 属于不同文件。
在每次决定是否触发自动重做前，先统计该文件中的历史打回记录。一旦达到预设上限，本次打回不再触发自动化重做，直接流转至 `rejected` 状态，并将转交人工的原因同步写入留痕文件。

审核卡还有一项后续动作。点击通过按钮后，除了执行状态翻转，还需推送确认发布卡，提示人工进入最后的发布核对阶段。
该卡片所承载的物料细节在下一课深入展开，当前实现只需保证卡片推送动作确实被触发，内容暂时可以使用占位提示。

这张按钮到出边的映射表，是这一课第一次定下来的，`02-执行方案.md` 和 `01-ADR.md` 里都还没有这一条，让 AI 先把这条决策补进你自己的文件，再照它实现：

```
先帮我在 01-ADR.md 里补一条决策：按钮到状态出边怎么对应。
依据两条约束：
1. state.ts 里 review 状态的三条出边（到 approved、到 drafting、
   到 rejected，各自是否要求填原因）；
2. 卡片结构那条决策定的"每张卡最多两个按钮"。
决策内容：审核卡只放通过和打回两个按钮；打回按钮点下去先不改状态，
弹出打回原因卡，卡上一个输入框和两个提交按钮（打回并自动重做、
打回并挂待办），这两个按钮才真正触发状态翻转；自动重做加一条
熔断上限，起步值参考流水线用的是 2，达到上限直接落 rejected 转人工。
决策写完，照它实现：
- 通过按钮触发 review 到 approved，成功后另发一张确认发布卡
  （内容先占位，具体物料下一课再补）；
- 打回按钮只弹卡，不改状态；
- 打回原因卡的两个提交按钮分别接到 drafting 和 rejected，
  挂待办这条人没填原因就用占位说明代替，不能因为没填就不落状态。
```

代码审查重点关注三个检查项。
第一，点击打回按钮是否仅弹出新卡而不改写状态。若直接变更状态，说明二级卡片机制未正确实现。
第二，熔断判断是否置于触发重做之前，必须先比对累计次数再决定流转方向。
第三，点击通过后，确认发布卡是否顺利推送。
若点击按钮后状态未更新，常见原因是按钮配置的动作标识与服务端的判断分支未能对齐。卡片载荷与代码分支拼写不一致，会导致事件无法被准确捕获。

## 三、同步与异步边界：3 秒窗口与状态写入路径

飞书卡片回调协议存在严格约束。服务端必须在 3 秒内完成响应。若超时或响应体格式不符，飞书端将判定回调失败，表现为按钮点击无任何交互反馈。
这是平台协议的刚性要求，而非编码偏好。处理回调的主函数从入口到返回，全程不得包含任何耗时的网络调用或阻塞操作。

同步路径只适宜处理极轻量的任务。
例如读取单次本地文件核对重做次数、内存拼接提示文案、构造待返回的响应体以及轻量通知气泡。这些均属于内存级操作，耗时通常在微秒或毫秒级。
任何耗时命令（如调度 AI 进程）、任何网络通信（包含向飞书二次推送卡片），均应交由后台异步线程处理。回调函数应优先返回应答，耗时任务在后台推进完毕后再异步推送最终通知。

| 路径 | 能做的事 | 不能做的事 |
|---|---|---|
| 同步（3 秒窗口内） | 读文件数已重做次数、拼提示文案、组装响应体和 toast | 调用 claude -p、发起任何 HTTP 请求、等待外部返回 |
| 异步（另起线程） | 状态翻转、拼发布物料、调用 claude -p 走重做、发消息通知结果 | 挡住回调函数的返回 |

在此有一项关键纪律：状态写入必须严格走统一通道，即第 16 课确立的收敛入口。
服务端代码严禁直接修改状态文件，哪怕仅改动单个字段也必须调用统一命令。
第 16 课在本地仓库中收敛了状态修改命令。这一课引入了外部网络服务，使统一写入规范真正被外层服务遵守，形成了跨模块的纪律约束。

参考流水线将状态变更封装为独立函数。函数内部仅负责组装参数，并通过子进程调用 `media flip`，坚决不直接修改文件。
调用时附带身份参数，明确标识触发方。
第 15 课曾回顾过一段演进背景。早期的回调代码曾用正则直接篡改状态文件。后续重构为通过 `media flip` 统一调度，并显式传入操作者身份。这让审计日志能够区分人工在终端操作与飞书卡片点击。
在当前这一课中，该机制必须切实落地：状态变更一律调用 `media flip` 并附加调用者身份标识。

本课在实现路径上做出了明确限定。
参考流水线目前支持将重做与发布任务委托给独立的控制台后端代跑，并通过配置开关进行切换。
但控制台模块在后续课程才会构建。若在本课过早引入该配置，会导致当前服务依赖尚未存在的组件，出现服务挂起无法连通的问题。
因此，本课必须选用自包含的实现路径。
服务自身启动线程调度子进程执行重做命令，自行核验状态文件确认执行结果。
全流程不依赖任何外部后台进程，确保本课交付的服务可以独立完整运行。

```
照我 docs/spec/feishu-gate/02-执行方案.md 里 3 秒回调窗口那一条，
实现回调处理函数，要求：
1. 函数体从进入到 return 之间只做内存操作：
   读文件判断已重做次数、拼提示文案、组装要返回的响应；
2. 任何要调用 claude -p 或者要发起网络请求的动作，
   一律起一个后台线程去做，不挡在 return 之前；
3. 状态翻转只能通过 media flip 去做，
   服务代码里不能出现任何直接改 meta.yaml 的逻辑；
4. 每次调 media flip 都要带上调用者身份这个参数，
   标明这次是飞书回调触发的，跟人在命令行里手敲的区分开；
5. 这一课不接第 26 到 28 课才会有的控制台后端，
   重做和后续要接的发布都用服务自己起线程、
   自己起子进程去跑，不要往一个还没造出来的地方发请求。
```

代码审查重点落实三条准则。
首先，排查主回调函数内是否存在隐匿的网络请求或子进程等待逻辑。
其次，检查状态翻转是否全量收敛至统一命令，检索代码确保没有直接覆写文件的逻辑。
最后，确认每次调用命令时是否附带身份参数，保障审计日志能够清晰追溯触发源头。

卡片点击无反馈，常见原因是同步路径中混入了网络调用或阻塞逻辑。常见误区是在回调函数中直接执行网络发包回写卡片，导致突破 3 秒限制。
另一种异常是状态未翻转且没有报错输出。常见原因是底层 `media flip` 命令执行失败，但异常被空的捕获代码块静默忽略。遇到该情况，需要仔细检查错误处理分支是否正确输出日志。

至此，服务已具备推送卡片、接收回调与流转状态的能力。接下来需要在真实内容上跑通两条分支流程。

## 四、验证：一条内容真走两次人点头

始终遵循开篇的记忆锚点：验证以状态流转为准。里程碑的验收标准必须是明确可执行的验证动作，不可使用模糊的表述。

本课的验收指标是：在真实内容上完整跑通两次人工确认。
一次通过操作，状态由 `review` 流转至 `approved`。
一次打回操作，自动重做完成后状态恢复至 `review`。
这两次流转均需在 `meta.yaml` 中准确体现，同时在留痕文件与审计日志中生成对应记录。
点击、状态翻转与留痕记录三者完备，方算验证通过。

验证动作分两条路径，各自核对结果：

```
取一条真实内容，走完两条路径，每条都核对状态：
路径一（通过）：
  1. 用出站发卡脚本给这条内容发审核卡；
  2. 在飞书上点通过；
  3. 核对 meta.yaml 的状态字段是不是真的翻到了 approved；
  4. 核对是不是收到了下一张确认发布卡（这张卡确认发布是下一课的事，
     这里只核对卡有没有出，不点确认）。
路径二（打回自动重做）：
  1. 对另一条内容发审核卡，点打回，弹出打回原因卡后填一句原因，
     点打回并自动重做；
  2. 核对 meta.yaml 的状态字段有没有先翻到 drafting；
  3. 等重做跑完，核对状态是不是翻回了 review；
  4. 核对 3-review.md 里有没有新增一行打回重做的留痕；
  5. 核对 audit.jsonl 里有没有新增一行，actor 字段是不是服务自己的身份，
     不是敲命令那个人的用户名。
```

第五步核验往往容易被忽略，但它恰恰承载了核心的验证目标。仅看 `meta.yaml` 无法知晓操作的具体触发方。
审计日志中的 `actor` 字段是追溯操作源头的唯一凭据。若此处记录的是本地用户名，说明调用时未正确传入身份参数，依然回退到了默认值。

验证时核查两点：两条分支的状态流转是否在预期步骤发生；`audit.jsonl` 中是否准确记录对应条目且 `actor` 为服务身份。
若重做完成后状态未能恢复至 `review`，常见原因是创作脚本在中间环节发生了挂起。此时服务应当主动记录预警信息，以便准确排查定位。

## 五、收尾：这一课做到的与还没碰的

本课将飞书闸口由设计规范转化为了可运行的服务。卡片按规范次序推送，按钮精准映射到状态出边，回调响应严格恪守 3 秒窗口，状态流转全量遵循统一入口并附带身份标识，真实内容成功走完两次人工确认。
所有验证均依托状态文件与审计日志的实际记录作为支撑。

尚待展开的是最后的发布收尾。通过审核后系统会推送确认发布卡，本课仅验证了该卡片的推送能力。
对于点击确认发布后如何安全触发真实发布、如何避免误发，留待下一课进行深入推演。
