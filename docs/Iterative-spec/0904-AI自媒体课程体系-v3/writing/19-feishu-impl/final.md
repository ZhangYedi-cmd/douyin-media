# 飞书通道实现：出站发卡、按钮回流与状态翻转

第 18 课把飞书闸口的四个决策点定死了：用长连接不用 webhook，三张卡分步、每张卡最多两个按钮，回调的 3 秒窗口里同步路径只做内存操作，卡片按钮的 value 一律带命名空间字段。这四条决策落在你自己 `docs/spec/feishu-gate/` 目录下的三份文件里：`00-调研.md`、`01-ADR.md`、`02-执行方案.md`。这一课不重新讨论这四条，只把它们变成一个真正能跑的服务。

记忆锚点是一句话：闸口信不信自己做成了，只看状态变没变，不信自己的汇报。这句话要拆成四件事去验证：卡是不是真的推出去了，按钮点下去是不是真的落到了对应的状态出边。3 秒窗口有没有真守住，一条内容最后是不是真翻转了状态。这四件事各自都有一个具体的观察结果能去查，不是服务自己说了算。

本课的输入是你自己第 18 课的 `02-执行方案.md`（卡片结构、3 秒回调窗口这几条条款）、`tools/console/packages/core/src/state.ts` 里 `review` 状态的三条出边（第 17 课读过一次，这次要拿它定按钮映射），还有第 10 课立过的三轮熔断经验。产出是一个能推卡、能收按钮、能把结果落成状态的服务。参考流水线自己有一套跑在生产里的实现，住在 `tools/feishu-bot/` 目录下，本课会反复引它，但引的是形状，不是给你抄的现成文件。你自己的实现要从你自己的 SPEC 出发，让 AI 按你定的条款去写。

开自建应用需要企业或团队账号，这件事第 18 课已经交代过，这里不重复。

## 1. 出站发卡：先推内容，再推卡

审核卡不是把内容压缩成一句摘要甩出去等人拍板。真正要推的东西按顺序有三样：先推口播稿全文或图文简介，让人看着真实文字判断；再推封面图，图文类型还要推全部配图；最后才推带通过和打回两个按钮的审核卡。顺序反过来，先看到一张卡再去想这条内容写了什么，等于让人凭一句摘要拍板，跟这道闸口本来要防的事正相反。

参考流水线的 `tools/feishu-bot/notify.py` 就是照这个顺序实现的：文稿优先读 `2-script.md`，没有就回退 `copy.txt`；配图口播类型只推封面，图文类型全部推；最后调用卡片模块拼出审核卡。成片视频本身不推，飞书对文件大小有限制，物料摘要里标一下文件名，要看本体本地打开。这三步任何一步失败都不该拦住下一步，比如封面图上传失败，文稿和卡片还是应该照常推出去，让人先看到能看到的东西，缺什么在卡片描述里说清楚。不能因为一步出错，这条内容整个都出不了审。

让 AI 照你自己的执行方案实现这一步：

```
照我 docs/spec/feishu-gate/02-执行方案.md 里卡片结构那一条，
实现出站发卡脚本，发送顺序固定为三步：
1. 先发文稿全文（口播稿优先，没有就用图文简介文本）；
2. 再发配图（口播只发封面，图文发全部配图）；
3. 最后发审核卡，卡片上只放"通过"和"打回"两个按钮，
   按钮的 value 字段要带上命名空间字段，
   具体字段名和取值按我 01-ADR.md 里命名空间隔离那条决策来。
三步之间互相独立：前一步失败也要继续尝试后面的步骤，
不能因为封面传失败就连审核卡也不发。
```

拿到结果审三点：发送顺序对不对，是不是先内容后卡片；某一步失败时另外两步有没有照常发出去；按钮的 value 里有没有带上命名空间字段。命名空间这一条容易漏，飞书自建应用如果同一个群里挂了别的项目的机器人，两边的卡片按钮如果都不带这个字段，回调打过来时谁都分不清是哪条业务发的按钮，服务要么误处理别人的卡片，要么把自己的卡片当噪音丢掉。

卡片推出去了人却没看到，多半是常驻的长连接服务没起来，这是下一节要讲的东西：出站脚本能把消息发出去，不代表按钮点了有人接。发卡前先确认那个长连接进程在跑，这个习惯要单独养成。

卡推出去了，下一步是按钮点下去之后谁来接。

## 2. 按钮回流：审核卡两个按钮，打回还有第二张卡

`state.ts` 里 `review` 状态有三条出边，到 `approved`、到 `drafting`、到 `rejected`。审核卡上却只有通过和打回两个按钮，这是第 18 课定死的规矩：每张卡最多两个按钮。三条出边配两个按钮，数不对，打回这一个按钮要同时接住两条出边（到 `drafting` 和到 `rejected`），塞不进一张卡。参考流水线的解法是让打回这个按钮不直接触发状态翻转，点下去先弹出第二张卡：一张带输入框的打回原因卡，卡上再放两个按钮，打回并自动重做、打回并挂待办，这两个按钮才真正各自接一条出边。两张卡各自都没超过两个按钮，三条出边也都有地方落。

| 卡片 | 按钮 | 触发的出边 | 是否要求填原因 |
|---|---|---|---|
| 审核卡 | 通过 | review 到 approved | 否 |
| 审核卡 | 打回 | 不直接改状态，弹出打回原因卡 | 不涉及 |
| 打回原因卡 | 打回并自动重做 | review 到 drafting | 否 |
| 打回原因卡 | 打回并挂待办 | review 到 rejected | 是 |

最后一列不是随口加的。要求填原因，落到实现上不是说按钮要等人打完字才能点亮，是说改状态那条命令拿到的原因参数不能是空字符串。参考流水线的做法是人写了就传人写的那段文字，人没写就传一句占位说明，两种情况命令拿到的参数都不为空，按钮从头到尾都能点。打回原因卡上的输入框对两个按钮是共用的，重做这一条出边虽然不要求填原因，但这段文字会当成定向重做的方向说明传下去，不填也能重做，只是少了一句方向提示。

打回并自动重做这条出边还带一条额外的规矩：自动重做要有熔断上限，到了上限就转人工，不能无限重做下去。这条规矩听着耳熟，第 10 课配音质检那条自愈回路也立过一条三轮熔断，但这是两个完全不同的数字，说的也不是同一件事。第 10 课那条三轮，卡的是同一批配音在质检和重做之间来回跑的轮数，触发方是 `dubbing-reviewer` 这个裁判子代理，判的是配音质量能不能过检测脚本那关。这一课的熔断上限，卡的是同一条内容被人在飞书上打回之后自动重做的累计次数，触发方是人点的打回按钮，判的是内容方向对不对，这件事没有客观判据，人打回几次算几次，机器说不出配音那种能量化的门槛。参考流水线把这个数字定成 `REWORK_LIMIT = 2`，注释里说得很直白：主观反馈没有客观判据，不能无限自愈。这个二和第 10 课的三没有换算关系，两条闸口各定各的数字。

熔断次数怎么数也有讲究：不用另开一个计数器，直接数这条内容自己目录下 `3-review.md` 里已经出现过几次打回重做的记录就行。这份文件是每条内容自己的一份留痕文件，来自 `content/_template/` 六份模板之一，跟 `pipeline/3-review.md` 那份全局阶段契约是两个文件，名字撞了，指的不是同一样东西。每次判断要不要触发熔断，先数一遍这份文件里已经有几条打回重做的记录，数到达到上限，这次打回就不再走自动重做，直接落到 `rejected`，同时把转人工的原因也记进这份留痕文件。

审核卡上还有一件事没交代：通过按钮触发之后，除了改状态，还要另外发一张确认发布卡，告诉人下一步在等确认。这张卡该放什么发布物料是下一课的事，这一课的实现只要求这件事真的发生：状态翻到 `approved` 之后必须再发一张卡，内容可以先给一句占位提示。

这张按钮到出边的映射表，是这一课第一次定下来的，`02-执行方案.md` 和 `01-ADR.md` 里都还没有这一条，让 AI 先把这条决策补进你自己的文件，再照它实现：

```
先帮我在 01-ADR.md 里补一条决策：按钮到状态出边怎么对应。
依据两条约束：
1. state.ts 里 review 状态的三条出边（到 approved、到 drafting、
   到 rejected，各自是否要求填原因）；
2. 卡片结构那条决策定的"每张卡最多两个按钮"。
决策内容：审核卡只放通过和打回两个按钮；打回按钮点下去先不改状态，
弹出打回原因卡，卡上一个输入框和两个提交按钮（打回并自动重做、
打回并挂待办），这两个按钮才真正触发状态翻转；自动重做加一条
熔断上限，起步值参考流水线用的是 2，达到上限直接落 rejected 转人工。
决策写完，照它实现：
- 通过按钮触发 review 到 approved，成功后另发一张确认发布卡
  （内容先占位，具体物料下一课再补）；
- 打回按钮只弹卡，不改状态；
- 打回原因卡的两个提交按钮分别接到 drafting 和 rejected，
  挂待办这条人没填原因就用占位说明代替，不能因为没填就不落状态。
```

拿到结果审三点：打回按钮点下去有没有只弹卡不改状态，改了状态说明第二张卡这一层没做对；熔断判断有没有放在真正触发重做之前，先数次数再决定要不要重做；通过之后确认发布卡有没有真的另外发出来。按钮点了状态没变，多半是按钮的动作标识和服务里判断分支的名字对不上，卡片上按钮的 value 写的是一个动作名，服务端判断的分支名却是另一个拼法，两边对不齐，回调打过来谁都没接住。

## 3. 同步与异步边界：3 秒内只改内存，状态只经 media

飞书卡片回调有一个硬约束：3 秒内必须给出响应，超时或者响应体不合法，飞书那边会报错，用户看到的是点了按钮卡片没反应。这条约束不是设计偏好，是协议本身的限制，处理回调的函数体从进入到返回，中间不能出现任何一次网络请求或者需要等待的操作。

同步路径里能做的事很有限：读一个文件判断已经重做过几次，拼一句提示文案，组装要返回的响应体和一句 toast（卡片右上角一闪而过的提示条）。这些都是内存操作，快到可以忽略不计。任何要调用 `claude -p` 这类耗时命令、任何要发起 HTTP 请求（包括更新卡片这个动作本身），都必须甩到一个异步线程里去做，回调函数先返回响应，重活在后台跑完再另外通知结果。

| 路径 | 能做的事 | 不能做的事 |
|---|---|---|
| 同步（3 秒窗口内） | 读文件数已重做次数、拼提示文案、组装响应体和 toast | 调用 claude -p、发起任何 HTTP 请求、等待外部返回 |
| 异步（另起线程） | 状态翻转、拼发布物料、调用 claude -p 走重做、发消息通知结果 | 挡住回调函数的返回 |

这一步还有一条更容易被忽略的约束：状态写入必须只经过一条路，就是第 16 课收敛出来的那个唯一入口。服务自己不能直接改状态文件，哪怕只是想顺手把一个字段翻一下也不行。第 16 课那一课收敛的是同一个仓库内部写命令这一条线，这一课接上的是外部服务，飞书回调驱动的这个服务，是这个唯一入口第一次真的被仓库之外的另一个程序遵守，不再只是同一批命令自己互相认。

参考流水线的做法是把改状态这个动作包成一个函数，函数体里只做一件事：拼好参数，起一个子进程调用 `media flip`（`review` 三条出边在 `state.ts` 里标的调用方式都是这一条命令），不直接碰任何文件。调用的时候额外带上一个身份参数，标明这次改动是谁触发的。这一手不是这一课凭空加的，第 15 课 4.3 节留过一个例子：参考流水线早年飞书回调那段代码是直接用正则表达式改一行状态字段，后来换成了调用 `media flip`，还带上了身份参数，让审计记录能分清这次改动是审核卡触发的还是人在命令行里敲的。那一课说这件事跟学员没关系，因为那时候还没有飞书闸口可以接。现在有了，这一课就要把这件事真正实现出来：改状态一律走 `media flip`，并且带上调用者身份，不能省这个参数图省事。

本课实现还锁一条更具体的路：参考流水线现在默认把重做和发布这两类重活委托给一个独立的控制台后端去代跑，代码里靠一个配置开关切换两条路径，默认值就是委托给控制台。控制台这东西要到第 26 到 28 课才会造出来，这一课要是照着默认配置去实现，等于给自己现在就要交付的服务按上一个还不存在的依赖，服务一启动就等着一个没造出来的东西回应，永远接不上。这一课的实现要锁定另一条路：服务自己起线程、自己起子进程调用重做命令、自己读状态文件判断这次重做有没有成功，全程不依赖任何独立后端，这一课交出去的服务要自己能跑通，不欠着后面的课。

```
照我 docs/spec/feishu-gate/02-执行方案.md 里 3 秒回调窗口那一条，
实现回调处理函数，要求：
1. 函数体从进入到 return 之间只做内存操作：
   读文件判断已重做次数、拼提示文案、组装要返回的响应；
2. 任何要调用 claude -p 或者要发起网络请求的动作，
   一律起一个后台线程去做，不挡在 return 之前；
3. 状态翻转只能通过 media flip 去做，
   服务代码里不能出现任何直接改 meta.yaml 的逻辑；
4. 每次调 media flip 都要带上调用者身份这个参数，
   标明这次是飞书回调触发的，跟人在命令行里手敲的区分开；
5. 这一课不接第 26 到 28 课才会有的控制台后端，
   重做和后续要接的发布都用服务自己起线程、
   自己起子进程去跑，不要往一个还没造出来的地方发请求。
```

拿到结果审三点：函数体扫一遍有没有藏着一次网络调用或者一次子进程等待；状态翻转是不是全部经过同一条命令，代码里搜一遍有没有漏网的直接改文件的代码；每次改状态时身份参数有没有真的带上，留痕能不能分清触发方。

卡片点了没反应，多半是同步路径里混进了一次网络调用或耗时操作。最常见的写法是想图省事，在回调函数里直接顺手把结果也发回去，这一发就是一次 HTTP 请求，窗口就守不住了。另一种常见错法是状态没变但也没报错，多半是 `media flip` 本身失败了，但异常被一个空的 `except` 吞掉，日志里什么都没留。这种情况得回头检查失败路径有没有被静默吃掉。

服务这时候能推卡、收按钮、改状态了。剩下要在一条真实内容上把两条路径都走一遍，看结果对不对得上。

## 4. 验证：一条内容真走两次人点头

还是开篇那句记忆锚点：只看状态变没变。里程碑出口条件要写成一句能跑的验证动作，不能写成基本完成这类判不了真假的话。

这一课的出口条件是：一条真实内容真的走完两次人点头，通过一次让状态从 `review` 翻到 `approved`，打回一次自动重做完再让状态翻回 `review`。两次翻转都能在 `meta.yaml` 里查到，留痕文件和审计记录里也都能查到对应的一行。两次点击、两次翻转、两次落痕，缺一样都不算过。

验证动作分两条路径，各自核对结果：

```
取一条真实内容，走完两条路径，每条都核对状态：
路径一（通过）：
  1. 用出站发卡脚本给这条内容发审核卡；
  2. 在飞书上点通过；
  3. 核对 meta.yaml 的状态字段是不是真的翻到了 approved；
  4. 核对是不是收到了下一张确认发布卡（这张卡确认发布是下一课的事，
     这里只核对卡有没有出，不点确认）。
路径二（打回自动重做）：
  1. 对另一条内容发审核卡，点打回，弹出打回原因卡后填一句原因，
     点打回并自动重做；
  2. 核对 meta.yaml 的状态字段有没有先翻到 drafting；
  3. 等重做跑完，核对状态是不是翻回了 review；
  4. 核对 3-review.md 里有没有新增一行打回重做的留痕；
  5. 核对 audit.jsonl 里有没有新增一行，actor 字段是不是服务自己的身份，
     不是敲命令那个人的用户名。
```

第五步这个核对点最容易被跳过，但恰恰是这一课要证明的东西：这次状态翻转到底是谁改的，光看 `meta.yaml` 看不出来，状态值本身不带身份信息。审计记录里 `actor` 这一格才是唯一能查到触发方的地方，这一格要是写的是敲命令那个人的用户名，说明第 3 节要求的身份参数没真正带进去，还是走了默认值。

拿到结果审两点：两条路径各自的状态翻转是不是都发生在预期的那一步，不早不晚；`audit.jsonl` 里能不能查到对应的两行，`actor` 字段是不是服务自己的身份标识。重做跑完没回到 `review`，多半是卡在了创作过程里的某个需要人工确认的环节。这种情况服务应该照实报一句预警，不能把没做成的事当成做成了，这也是判定服务实现对不对的一个具体检查点。

## 5. 收尾：人点头这一关通了，发布还没做安全

这一课把飞书闸口从纸面上的四条决策变成了一个能跑的服务。卡按正确顺序推出去了，两张卡上的按钮各自落到了对应的状态出边。回调守住了 3 秒窗口。改状态的动作全部经过唯一的记账入口，并且带着调用者身份。一条真实内容也真的走完了两次人点头。这一课能拿出来的证据不是服务没报错，是状态文件和审计记录里能查到的那几行。

还看不到的是最后一步：通过之后，飞书会推出一张确认发布卡，这一课只核对了这张卡有没有出。卡上确认发布这个按钮点下去之后会发生什么，会不会把内容真的发出去，这一课没碰。人点头这一关通了。点头之后真发出去这一步，怎么做才不会误发？
