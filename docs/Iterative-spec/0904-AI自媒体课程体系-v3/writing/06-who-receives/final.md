# 验证信号流向谁

上一课交付了四个产物：一个 `build/` 网页演示工程、一条 `final.mp4` 视频、一张竖版封面图，以及在第 05 课配置出来的 `tts-dub` skill。这条内容从文案起草推进到最终成片，你在关键节点完成了各项确认，并且戴上耳机将整条成片完整听了一遍。确认各项效果符合预期后，完成了最终交付。

这种符合预期的结论究竟从何而来，值得进一步向底层梳理。在全流程中，每一步是否执行正确，最终的判决来自人工判断，裁决逻辑运行在人的意识里。上一课解决的是如何将内容生产出来，本课则要探讨这个裁决动作能否逐步脱离人工在场的硬性依赖。第 01 课梳理的人工介入点清单，标记的是整个流程中哪些环节有人在场。本课则需要切入更深一层：各项检查执行完毕之后，得出的验证结果具体传递给了谁。

本课的输入是你在第 03 课编写的 `pipeline/` 五份契约文件：`1-ideate.md`、`2-create.md`、`3-review.md`、`4-publish.md` 以及 `daily-run.md`。完成本课后，你将整理出一张清晰的去向表，将流程中各个检查步骤的验证结果去向逐项标注清楚。

本课遵循一个明确的判定标准：一套 AI 系统能否实现自主纠错，核心取决于每一步验证执行完毕后，检验结论最终反馈给了谁，而不取决于调用了何种流行框架或模型参数规模。

## 一、四代工具演进与验证结果的去向

在上一课的制作实践中，所用工具已经具备了读取本地文件、执行系统命令以及启动子进程合成音频的能力，不再局限于被动接收文本的问答窗口。然而回看最终的质量判定，依然是人工在终端前逐项审视后给出的结论。工具形态向前演进了一代，但检验结果的反馈通路尚未发生迁移。

在自动化系统的发展历程中，这条边界早已被深入讨论。控制论学者托马斯·谢里登（Thomas Sheridan）在 1974 年提出监督控制模型。他指出自动化系统分工的演进方向，是将人类从紧盯每项具体操作的执行者，逐步转变为制定系统目标、审查最终结果并在异常时介入的监督者。这套分工的价值在于明确权责边界。人类应当聚焦于产物结果是否达标，而不过度卷入具体执行细节。AI 工具的代际演进同样遵循这一规律：越是成熟的形态，人工滞留在执行细节上的时间越短，让渡给系统的自主判定权越多。

依照这个逻辑，AI 工具的演化可以划分为四个阶段，每一阶段的本质分水岭都体现在验证信号最终流向了谁：

第一代是传统问答对话框。人在窗口中提出要求，AI 返回文本回答。判断回答是否准确、下一步该补充何种指令，完全由人脑实时分析。AI 自身没有工具调用能力，无法直接读写本地文件，验证信号只能直接反馈给人工。

第二代是具备工具调用能力的 Agent，这正是上一课所采用的形态。它能够自主读写文件和调用系统命令行。但是在命令执行完毕后，结果由谁消费、遇到错误如何处理，在系统层面并未闭环。面对命令报错，它通常有两种常见表现：要么当场中断等待人工介入，要么携带错误状态盲目继续执行，导致后续步骤持续偏离。无论哪种表现，验证结论的最终接收方依然是人工，需要人工查看终端输出或日志文件来决定下一步行动。工具掌握了执行手段，但判定闭环尚未建立。

第三代在架构上称为护栏代。护栏在这一阶段代指包裹在 Agent 外层的验证层。它的职能是在 Agent 输出结果后进行合规检查，未通过则进行拦截，因而护栏这一表述比宽泛的沙盒更为精准。此处的验证护栏与治理线中的 `harness/` 目录定位不同，后者是本工程中存放长期治理任务的专用目录名。护栏代的核心能力是拦截：不合规的生成内容会被阻断，并记录到审计日志或巡检报告中。但完成拦截并不等同于问题得到修复。这份日志后续由谁阅读、何时介入，在流程上往往没有硬性约束，依然停留在等待人工调阅的阶段。

第四代是具备自愈能力的 Loop。验证结果不再单纯沉淀为静态文档，而是直接回调给发起该步骤的主程序或代理本身。代理根据结构化反馈结果，自主决定是否调整参数并发起重试。第四代相较于第三代的核心递进，在于能够基于被拦截的具体原因执行反向修正。参考工程中的实际实现展现了这一机制。在参考工程的创作契约 `pipeline/2-create.md` 第 4 步中，当音频合成完毕后，主会话会调用名为 `dubbing-reviewer` 的评审子代理展开检验。该子代理运行检验脚本并给出裁决：若各项指标通过则继续流转；若未通过则附带具体的修正指导。主会话接收指导后更新参数重新合成，并再次发起复审。整个流程设定了三轮重试熔断，若三轮复审仍未通过则转入人工审核。在此模式下，验证结论直接反馈给了主任务会话，无需依赖人工手动翻查日志。

第三代与第四代在表象上容易混淆，因为两者均包含先执行检验再获取结论的流程。两者的关键分水岭在于检验完成之后的动作归属。护栏代在完成检查并拦截不合规产物后，其职责已经完结，后续由谁承接并未固化。而在自愈 Loop 中，拦截仅仅是闭环的起点，系统预先定义了由谁解析裁决、如何针对性调整并重新触发执行。判定一套系统属于护栏代还是自愈 Loop，核心看检验之后是否存在预设的自动化衔接动作。

四代工具形态的对比如下：

| 世代 | 信号回给谁 | 人工盯守要求 |
|---|---|---|
| 第一代，对话框 | 直接反馈给人脑，缺乏中间结构化记录 | 每步均需实时盯守 |
| 第二代，工具调用 | 输出到控制台终端，由人工查看后定下一步 | 每步均需实时盯守 |
| 第三代，护栏代 | 沉淀为审计日志或报告，阅读时机未被固化 | 抽样排查，异常时介入 |
| 第四代，自愈 Loop | 回调给发起调用的程序或代理，自主决策重跑 | 仅在熔断超限时介入 |

引入新的开发框架或切换能力更强的模型，通常仅改变了工具层面的表现形式。若校验完成后依然只是产出一份无人主动消费的报告，系统依然无法摆脱对人工的依赖。决定系统能否建立自愈纠错能力的关键，在于信号能否稳固回传至自愈环路中。这是本课分析系统架构的核心切入点。

明确了信号反馈的宏观路径后，落脚到具体的流水线中，会发现信号的实际落点比通用分类更为明确。在实际工程中，信号落点可以进一步细化为四个具体位置。

## 二、四个位置：信号能落在哪

当一个检查步骤执行完毕并得出明确结论后，本课将该结论统称为验证信号。在工程链路中，验证信号的落点主要包括四个位置：人、机器、文档、没人管。这四个类别来自工程实践的总结提炼，用于精确度量单点检查动作的具体流向。护栏代常见的落点是流向文档，自愈 Loop 常见的落点是流向机器。但在实际系统中，不同的检查点可以根据特性分布在不同位置。

第一类是流向人。该位置意味着这一步的检验结论必须由人工进行核对，并且设置了固定明确的通知渠道。判定的依据在于该环节是否明确安排了人工介入，以及是否规定了具体的确认通路。例如你在第 03 课编写的 `3-review.md` 契约通常只列出了三四条规则，但流向人的通道是明确成立的。参考工程的人审契约 `pipeline/3-review.md` 是这一分类的标准案例，其中明确定义了六项审核清单，涵盖事实核验、时效性、账号定位、人设语气、平台合规以及视觉观感。审核流转依托飞书卡片通道，包含通过与打回两个明确出口。通过则进入发布排期，打回则将批注意见写回契约转回创作阶段。`CLAUDE.md` 中的流程规范同样服务于此：工作日自动化任务严格截止于出审节点，正式发布必须经过人工确认。因为外发属于不可逆操作，不可逆动作必须保留人工最终决策权。

第二类是流向机器。该位置意味着当前步骤若判定不合格，异常信号能够直接交由下游程序或子代理消化承接，无需人工中转。上一节提及的 `dubbing-reviewer` 即属于此类。检验脚本返回结构化判定结果，由程序直接决策重新合成或向下流转，全程不需要人工在终端前搬运数据。

第三类是流向文档。这一类型在日常开发中最容易被误以为已经安排妥当。例如在参考工程的 `pipeline/2-create.md` 中，包含一份详尽的出审前终检清单。清单涵盖声画一致、音频自然度、开头引子吸引力、事实合规、封面规格等七个检查维度，每项均配有核对选项。清单条例虽然详尽，但执行核对并勾选的依然是人工，检查产出最终也只是静态保存在文档中。流向文档的判定特征非常明确：如果能够明确指出检验结论记录在哪个具体文件里，但缺乏自动化消费机制，即属于流向文档。

静态清单虽然能够拦截问题，但在缺乏强制联动时容易产生失效风险。在参考工程的历史记录中曾出现过典型事故：文案调整后未重新提取分段文本，导致画面呈现新内容而语音依旧念旧稿。这一音画不同步问题在人工查阅两轮清单后均未被发现。原因在于当时核验依赖的是组件静态截图，截图仅能佐证画面排版，无法验证声音同步性。结论虽然记录在文档中，但如果调阅时选取的佐证依据存在偏差，检查就会失去效果。事故发生后，该检查项被明确要求必须在视频成片上进行抽帧复核。

第四类是没人管。这是最容易被忽视的状态。检验命令正常执行，控制台也打印了输出日志，但该结论既未传达给人，也未被后续代码捕获，更没有落盘保存，终端滚动后信息即丢失。这在自动化流程中较为普遍，例如早期调试时编写的临时打印逻辑，后续未将其返回值接入流程控制中。虽然脚本持续执行，但没有任何系统模块在监听该输出。如果一项检查无法追溯其结论保存在何处、被谁读取，该检查通常应当归入没人管。

流向文档与没人管在本质上具有相似性：两者均未能直接驱动后续动作。差异仅在于前者保留了物理记录，后者则直接随进程结束而湮灭。

四个信号位置的特征对比如下：

| 位置 | 信号呈现形式 | 推进主体 | 潜在风险 |
|---|---|---|---|
| 流向人 | 结构化通知消息，或待人工审阅的记录 | 人工自身 | 强依赖人工在场，人员缺席流程即受阻 |
| 流向机器 | 可直接判定的结构化结果（如退出码） | 程序或代理进程 | 判定规则需能转化为明确的逻辑断言 |
| 流向文档 | 巡检报告、审计日志或勾选清单 | 依赖人工主动调阅 | 存在漏读风险，调阅时可能选取片面佐证 |
| 没人管 | 仅在终端短暂打印控制台日志 | 无后续推进主体 | 检查动作流于形式，无法影响流程走向 |

明确了四类位置的边界后，接下来需要对你当前流水线中的各个检查环节进行逐一映射归类。

## 三、按自己的契约逐条填表

梳理表格时必须以你现有的契约文本为准。你在第 03 课编写的 `pipeline/2-create.md` 是根据自身业务梳理出的骨架，其体量与演进多次的参考工程会有客观差异。你的契约定义到哪一步，表格就如实记录到哪一步。基于自身真实工程提取出的现状，才能为后续优化提供依据。

可以通过提示词让 AI 协助将契约规则逐项提取出来：

```
读我在第 03 课写的 pipeline/ 五份契约：
1-ideate.md、2-create.md、3-review.md、4-publish.md、daily-run.md。
只读这五份文件，不要推测文件里没写的事，也不要照抄某个参考仓库的检查项。
把里面所有检查或者判断某件事对不对的动作挑出来，列成一张表，四列：
1. 这个检查点在哪份契约的哪一步
2. 检查的是什么
3. 现在这一步怎么下判断，依据写在契约原文哪一句
4. 这个判断的结论现在实际去了哪里（我来填，先留空）
第 3 列只写契约里明确写出来的检查动作，契约里没写的写未记录，不要推测。
不要给建议，不要合并步骤，直接输出表格。
```

表格提取出来后，重点核对三个细节。首先核对行数与你预估的检查点数量是否一致，若条目缺失，通常是 AI 将多个子动作进行了合并，应要求其拆开重列。其次核对第 3 列列出的判定依据，必须能够在契约原文中找到对应的条款语句。最后核对引用的文件名与步骤编号是否准确。如果 AI 给出的检查项过于繁复且在原文中无法检索对应语句，通常是因为其脱离了契约原文，凭空推测了检查逻辑。

核对无误后，由你手动补全第 4 列。若该步骤必须人工在场核验，填入流向人。若该步骤的不合格情况能够转化为确定性的逻辑表达式，填入流向机器。若输出仅写入文件等待后续翻阅，填入流向文档。若契约中对该步骤由谁负责未作说明，则保持留空。这表明该环节职责尚未明确，同样是需要如实记录的现状。

## 四、标出该交给机器的格子

具体编写校验脚本属于后续课程的范畴。本节的核心任务在于确立准入条件：表格中标记为流向机器的检查项，需要满足什么标准。核心判据在于：该步骤的校验逻辑，能否提炼为不依赖复杂主观语境的确定性断言。

参考工程中的检验脚本体现了这种分类界限。`dubbing-check` 下包含六个检测脚本，其设计天然分为两类。

其中三个脚本能够直接根据校验结果输出明确的退出码：`check-completeness.mjs` 用于检验生成段数是否匹配；`check-source-sync.mjs` 用于比对分段文案与源文本的一致性；`check-silence.mjs` 用于检测异常静音是否超标。这三项校验无需结合主观上下文，数值超标或文本不符即判定失败。我们可以通过命令行观察退出码的表现：

```bash
node .claude/skills/dubbing-check/scripts/check-completeness.mjs
echo $?
```

另外三个脚本则有所不同：`check-pace.mjs` 仅输出各段语速估算数值；`check-pronunciation.mjs` 仅列出文案中包含的多音字字形；`check-av-consistency.mjs` 在常规执行完毕后仅打印待人工判定的提示。语速估算偏慢可能由于专业英文缩写密集引起，多音字是否读错高度依赖特定语句语义。这类指标天然带有上下文依赖，难以固化为简单的真假判断，因此脚本不宜直接抛出失败退出码中断流程。

针对标记为流向机器的单元格，还需要格外警惕假阳性退出码。参考工程曾发生过一次典型事故：批量去停顿脚本因配置问题，将输出路径写成了与输入路径相同的文件名。命令启动后首先将目标文件清空，导致音频被截断，但底层 ffmpeg 进程并未报错，命令执行后返回退出码 0，而异常停顿依然存在。

因此流水线确立了二次验证规范：执行完处理命令后，必须调用检测脚本基于生成产物重新计算，确认超标数据归零：

```bash
node .claude/skills/dubbing-check/scripts/check-silence.mjs
echo $?
```

二次复扫结果之所以可信，是因为它直接读取最终生成的音频物理文件进行特征解析，而不依赖上一条命令自身上报的状态。对于标记为流向机器的检查点，必须核验其退出码是真正反映了产物合规性，还是仅仅代表命令执行没有崩溃。

对于无法用客观指标度量的维度，无需勉强交由程序裁决。例如封面设计的美感与协调度，参考工程曾发生过因提示词未固化，模型自由生成了无关角色并在人审阶段被打回的情况。这类涉及视觉设计审美以及首句文案吸引力的维度，天然依赖人类综合认知，难以剥离语境编写确定性规则。它们应当稳妥地保留在流向人这一分类中，由人审契约规范其审核流程。

综合来看，一个检查点能否顺利移交给机器，需要依次跨越三道关卡。第一关，该检查项是否能够产出确定性的状态结果或退出码，若无法产出则应当归于流向人。第二关，该退出码是否基于物理产物本身解析得出，若仅代表进程未抛错则不足为凭。第三关，该检查项的量化度量指标、数据来源文件以及超标阈值是否已经明确。例如静音阈值设定为 0.45 秒，该数值来自何种标准、是否需随内容类型动态微调，需要充分的实践依据支撑。完成前两关的判定后，第三关的指标量化则是下一课要重点攻克的目标。

至此，表格中第 4 列已梳理完毕。流向人、流向文档以及没人管的单元格，标明了当前流水线距离全自动化运行仍存在的差距。而流向机器的单元格，则是后续可以开展自动化脚本构建的着力点。明确验证信号最终回传给谁，是构建系统自愈能力的基石。梳理清楚哪些环节应当由程序接管后，接下来的核心任务就是确定这些检测信号应当如何科学采集，这也是下一课探讨的核心课题。
