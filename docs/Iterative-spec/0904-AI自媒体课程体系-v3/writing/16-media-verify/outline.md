## 1. 开篇：造完了，还没证明造对了
核心判断: 验证这一步验的不是代码能不能跑起来，是「写路径真的只有一条」这类容易自己以为已经对了的东西，光靠肉眼看代码不够，要留下能回查的证据。
支撑材料: `courses/11-SPEC方法-从调研到验证的六步.md` 第 7 节验证方法论原文；`06-施工记录.md`（参考流水线）里 core 包验收记录的真实教训（`doc.toString()` 对 25 个真实文件丢注释对齐）作反例
交付物: 一句判据——凡是改了状态的动作，都要能在 `audit.jsonl` 里查到对应的一行，查不到就不算数；两三种真实会撞的墙作反例（两层状态不同步、发布记录无链接）
二级标题: none
收尾交接: 先看怎么留证据——`--dry-run` 和 `audit.jsonl`。

## 2. 留证据：--dry-run 先出计划再执行，audit.jsonl 当账本
核心判断: 写命令先 `--dry-run` 打印会发生什么变更，人确认了再真跑；每次真跑都会在 `audit.jsonl` 追加一行，这行记录是唯一性自证的原始材料。
支撑材料: `tools/console/logs/audit.jsonl` 真实抽样行（flip 被拒绝的 error 行、publish-done 三处文件同时改的 ok 行、promote 新建目录写六字段的 ok 行）；核实 audit.jsonl 只记写命令、不记 check 这条真实边界
交付物: 一次 `--dry-run` 的读法（看懂它打印的变更清单）；一段 `audit.jsonl` 怎么读（哪个字段对应哪次改动，ts/actor/cmd/argv/result/files 各管什么）
二级标题: none
收尾交接: 知道怎么留证据、怎么读证据了，接下来用它自证写路径唯一。

## 3. 自证写路径唯一：media check 在自己仓库跑通
核心判断: 模块 3 的出口条件是一句能跑的验证动作——`media check` 在自己仓库上跑一遍，返回退出码，error 级警报为零才算过；这就是全书状态中枢立住的标志。
支撑材料: `courses/13-media写SPEC.md` 的 CHK-01 到 CHK-08 规则表和 M1/M2 出口条件原文；`tools/console/packages/cli/src/commands/check.ts` 的退出码逻辑（errors > 0 才非零）
交付物: 一条自证清单（`media check` 退出码怎么读；手动改一次 `meta.yaml` 会不会被 check 抓出来；`audit.jsonl` 里能不能找齐最近几次状态变更）
二级标题: none
收尾交接: 唯一性有证据了，最后一件事是把这轮施工的过程记下来。

## 4. 施工记录怎么写：出口条件、卡在哪、怎么绕过去
核心判断: 施工记录不是流水账，是给每个里程碑一行结论——出口条件是什么、实际结果是什么、卡在哪、怎么绕过去，绕不过去的留给以后的人接着看。
支撑材料: `courses/11-SPEC方法-从调研到验证的六步.md` 第 7 节施工记录模板原文；`06-施工记录.md`（参考流水线）的形状（时间线、验收结论表、裁决台账）作框架参考，框成「参考流水线」
交付物: 施工记录模板（里程碑 / 出口条件 / 实际结果 / 卡在哪 / 怎么绕过去），填入 M1、M2 两个里程碑的真实情况
二级标题: none
