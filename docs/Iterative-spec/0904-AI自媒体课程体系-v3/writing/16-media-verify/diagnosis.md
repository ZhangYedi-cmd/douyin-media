# 诊断报告：《验证与收敛：造完不等于造对》（第16课 draft.md）

诊断对象：`docs/Iterative-spec/0904-AI自媒体课程体系-v3/writing/16-media-verify/draft.md`
诊断者身份：会用 Claude Code 或 Cursor，没做过自动化流水线，手上没有参考仓库，只有前 15 课自己做出来的东西。
派发方式：Agent 工具，general-purpose 类型，model sonnet，独立读稿，不知道写作过程。

## 一、哪里读不懂

**1. 开篇核心论断的句子本身读不通（第1节，第2段）**
原文：「验证这一步验的不是代码能不能跑起来。代码跑起来只说明没有语法错误、没有崩溃，跟状态只有一个地方能写这个判断对不对，是两件事。」
问题：这句话是全课的立论起点，但句子本身语法断裂，「是两件事」指代不清，读者猜不出是哪两件事在对比。开篇第一个论证就卡壳。

**2. 「六个字段」与实际出现的字段数对不上（第2节）**
原文先说「六个字段各管一件事」，列了 ts/actor/cmd/argv/result/files，随后解读第一条示例行时又用到「`summary` 里写清楚了原因」，但 `summary` 从未被正式介绍是什么、什么时候出现。这是一处明确的概念空缺。

**3. 「三种真实会撞到的墙」的第三种，指代关系绕（第1节）**
原文：「这一种不是逻辑漏了一步，是工具本身不老实。」「工具本身不老实」是拟人化的模糊说法，读者要读完下一段才能倒推出它指什么。

## 二、哪里太啰唆

**1. 施工记录的定义连用两次否定说同一件事（第4节）**
「施工记录不是流水账，不是把跑过的命令按时间顺序抄一遍。」两句「不是」说的是同一层意思，可以合一句说完。

**2. YAML 丢注释的教训在第4节又完整复述一遍（第4节）**
第1节已经把这段教训讲透，第4节讲 M1 出口条件时又完整复述一遍，内容没有增量。

## 三、哪里逻辑断裂

**1. 「六个字段」的计数与实际讲解内容矛盾**
根源是逻辑计数表述不完整（summary 是条件性出现的第七个字段，没有单独交代），不是纯粹的修辞问题，与「读不懂」第2条同源。

**2. 第1节开篇论证内部的因果链条不完整**
「是两件事」这句本身除了读不通，逻辑上也没有把「两件事」分别是什么讲清楚，导致后面「第二件事」失去了明确的先行词。

## 四、哪里有AI味儿

**1. 「不是……是……」句式在全文反复出现，成为固定套路**
统计到至少五处，包括记忆锚点、第1节两处、第4节一处。同一个「先否定再给出真正答案」的句式反复用来制造揭晓感，读多了显出模板感。

**2. 收尾段落的长句堆砌（第5节）**
六步方法回顾那一大段多处用逗号把好几层意思硬拉进一句话，例如执行那两步的评价句、写 SPEC 那一步救场的评价句，都是一句话塞四五层因果和转折。

## 五、哪里在装

**1. 金句化 / 倒装收束（较重）**
- 全文标题「验证与收敛：造完不等于造对」是对仗式警句。
- 记忆锚点「唯一入口的证据不是嘴上说的，是 `audit.jsonl` 里能查到的那一行」是压出来的金句结构。
- 第5节小标题「状态中枢立住了，但不是所有动作都能自己拍板」同样是对偶转折结构。

**处理决定**：记忆锚点原句和第5节小标题均为任务卡「2.1 大纲」块逐字规定的固定文本（`plan/cards/16.md` 记忆锚点行、第5节标题行），`outline.md` 已声明 `plan: fixed-from-card`，节标题和记忆锚点不许改写，予以保留，不算本课自创的装腔句式，理由记入本文件与 polish-report.md。全文 H1 标题不是卡片强制文本，改成更平实的描述句，去掉对仗痕迹。

**2. 标点：Prompt 块内使用了英文直角双引号**
第4节第三个 Prompt 块内 `"验证方法已定，窗口进行中"` 用了英文引号。代码块内容按机器字段处理不受标点硬禁令约束，但为保持一致性去掉引号改用无引号表述。

**3. 猜心句 / 俯视腔 / 作者加戏 / 黑话堆砌**：无。核实第5节六步回顾段落是任务卡明确要求的收尾结构，论据具体可查证，不算作者加戏。

## 六、材料真实性核查（本课额外检查项）

核对依据：`plan/inventory.md` 第15课结束时清单、第13/14/15课 draft/final 原文、参考仓库 `tools/console/` 与 `docs/Iterative-spec/0818-看板工作台/` 原文。

**结论：没有发现把参考仓库的东西写成读者自己仓库已经发生过的事这个最容易踩的坑。**

1. 两条 `audit.jsonl` 真实示例行：核对 `tools/console/logs/audit.jsonl`，一字不差存在，且用「参考流水线」做了归属标注，未误写成读者自己仓库的记录。
2. 25 个真实文件丢注释对齐的教训：核对 `docs/Iterative-spec/0818-看板工作台/06-施工记录.md`，确认真实记录，课文用「参考流水线自己造类似的写入口时」明确标注归属。
3. 施工记录形状参考：课文描述的骨架（时间线/各部分结论/裁决台账/人工待办）与 `06-施工记录.md` 真实结构吻合，且明确标注是「参考流水线自己那份」。
4. `media flip`、`media check`、`media publish-done`、`--dry-run`、`audit.jsonl`、`01-ADR.md`、`02-执行方案.md`、CHK-01 到 CHK-08 规则表：逐条核对均确认是读者第13到15课真实产出、真实用过的东西。CHK 规则表与第13课 final.md 第79-86行逐字对照一致，进一步核对参考仓库 `alerts.ts` 实现，级别判定吻合。

**唯一次要疑点**：`audit.jsonl`「参考流水线跑了大半个月，这个文件已经积了三千五百多行」这句容易让读者误以为 3500 多行是真实编辑活动的密度，实测这份文件里绝大多数行来自自动化测试反复跑同一批命令，真实指向仓库根目录的行很少。归属标注没错，但对文件成因的刻画比实情更像生产使用痕迹，容易误导读者对自己账本应有行数规模的预期。**已在 final.md 改写这段，明确交代账本主要来自测试重复运行，纠正读者对自己账本行数的预期。**
