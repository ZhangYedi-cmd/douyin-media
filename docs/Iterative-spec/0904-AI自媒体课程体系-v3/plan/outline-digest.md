## 第 01 课 · 一条内容的端到端走查（走查课）

- 记忆锚点：一条内容从选题到发布分五个动作，人只在信号响的时候出现，不是全程盯着。
- 开篇契约：全书第一课，无上一课交付；输入是学员自己口述的流程；产出 `docs/00-walkthrough.md`（流程图 + 人出现点清单）。
- 一级标题：
  1. 一条内容要走的五个动作 —— 五个动作互不看对方内部怎么做，只认输入输出契约，上下游靠文件接力。
  2. 人出现在哪几个位置 —— 人只在三类信号响时出现：事前留条件、闸门拍板（两处）、异常呼叫。
  3. 出审之前，机器已经查完的七项 —— 一项判据归脚本还是归人，看结论能不能被一条命令判真假。
  4. 让 AI 把这两样先画出来 —— 流水线怎么切取决于学员自己，AI 只整理口述，填不出就写待定。
  5. 三个固定的位置（收尾）—— 人固定出现的位置只有三个：出审、确认发布、选题池指针。
- 结尾抛出的问题：流程图和人出现点清单有了，可你手上一个工具都没有。这些环节要跑起来，机器上得先装齐哪些东西？

## 第 02 课 · 装备：开源件与自检基线（L1）

- 记忆锚点：十项工具装的不是十件事，是给后面每一课先把地基铺平，装错一步后面全部对不上。
- 开篇契约：上一课交付了端到端流程图和人出现点清单；输入是 ADR §5 十项工具清单；产出 `docs/00-toolchain.md` + 一份全绿自检输出。
- 一级标题：
  1. 基础运行环境：Claude Code、Node、uv、ffmpeg/ffprobe —— 这四项是其余六项工具能跑起来的前提，装错版本后面全数报错。
  2. 内容生产开源件：web-video-presentation、baoyu-image-gen、agent-reach —— 三个 skill 各自独立，互不依赖，各自能自检出结果。
  3. 发布与配音：social-auto-upload、飞书自建应用、TTS 引擎 —— 涉及外部账号和余额，装的同时要准备申请材料。
  4. 自检基线：一次跑完，全绿（收尾）—— 单项自检都过不等于流水线能跑，得拼成一份能一次跑完的清单。
- 结尾抛出的问题：工具装齐了，但它们各自为政，没有一个仓库把它们串起来。这套流水线的骨架长什么样？

## 第 03 课 · 立骨架：仓库、目录、契约（L2）

- 记忆锚点：骨架仓不是把文件堆起来，是把「谁能看懂谁」从人脑挪到契约文件上——AI 只读契约就能复述流程，才算立住。
- 开篇契约：上一课交付了 `docs/00-toolchain.md` 和全绿自检输出；输入是学员口述的目录切法；产出能 `git init` 的骨架仓（目录树 + CLAUDE.md + pipeline 五份契约 + content 模板 + backlog.yaml 头部）。
- 一级标题：
  1. 目录树设计：六个目录各管什么 —— 六个目录各自只装一类东西，装混了后面每课都要返工去分。
  2. CLAUDE.md：规格表而不是成品 —— 五节要学员自己填空回答，照抄现成范例 AI 读不出账号判断。
  3. pipeline 五份阶段契约：骨架与审查点 —— 每份契约只写输入/输出/状态翻转/闸口四项，操作细节住 skill。
  4. content 模板与 backlog.yaml 头部：骨架与审查点 —— 模板文件和 backlog 头部要按 pipeline 契约的产物名对齐字段。
  5. 验证：让 AI 只读契约复述流程（收尾）—— 复述对不上说明契约本身没写清楚，不是 AI 理解错了。
- 结尾抛出的问题：骨架有了，AI 能读你的契约复述流程。可它不知道你的账号该做什么内容、用什么口气说话。这些判断依据写在哪？

## 第 04 课 · 账号大脑：五份文件怎么写（L2）

- 记忆锚点：账号大脑四份文件通过同一道审——写得出能排产的判断句才算填对，写成谁都读不出优先级的形容词不算。
- 开篇契约：上一课交付了骨架仓；输入是学员对账号定位/人设/语气/素材来源的口述；产出 `brain/` 五份 md（四份填满、benchmarks 留空）+ `tts.config.json`。
- 一级标题：
  1. positioning 与 persona：账号是谁、对谁说话 —— 两份文件要写成能被下游排产的判断句，不是形容词堆砌。
  2. style-guide 与 sources：怎么说话、素材从哪来 —— 要写成可执行判据（禁用词表、句式范例、信息源清单），不是无法照做的形容词。
  3. benchmarks：为什么现在留空 —— 要靠真实播放数据才写得出来，现在硬填等于编数字。
  4. tts.config.json：音色、语速、多音字规则住配置（收尾）—— 规则写进配置而不是代码，供后面模块 2 的 Loop 接住修复。
- 结尾抛出的问题：大脑写完了，AI 知道你要什么内容了。现在真去做一条出来，从稿子到成片要走几步？

## 第 05 课 · 用开源 Skill 跑通一条内容（L1）

- 记忆锚点：这条内容从网页到成片一次走完，讲的是流程在哪一步、人在哪一步确认，不是工具怎么调参。
- 开篇契约：上一课交付了 `brain/` 五份和 tts 配置；输入是账号大脑里的定位/人设/语气规范和一份口播稿选题；产出 `build/` 工程 + `final.mp4` + 竖版 `cover.png` + `tts-dub` skill。
- 一级标题：
  1. 口播稿到网页 demo：装 web-video-presentation —— 网页 demo 是成片骨架，人确认段落划分和大纲对不对，不是画面细不细。
  2. 网页录制成片：npm run record 与字幕层 —— 录制无人值守，人确认时长和翻页节奏，字幕层用 `?subs=1` 单独核对。
  3. 配音与合成：tts-dub skill（L1，两条 Prompt）—— 只给配置契约和合成脚本两条 Prompt，多音字/语速/去停顿留到模块 2。
  4. 封面与产物归位：baoyu-image-gen 与 build/ 目录（收尾）—— 封面要竖版比例，人确认第一眼观感。
- 结尾抛出的问题：第一条成片出来了，你眼睛看着觉得还行。可下次你不在场的时候，谁来看这个「还行」？

## 第 06 课 · 验证信号流向谁（方法论）

- 记忆锚点：AI 工具能不能自己纠错，只看验证结果最后回给谁，不看用了什么框架、模型能力强不强。
- 开篇契约：上一课交付了 `build/` 工程、`final.mp4`、封面和 `tts-dub` skill；输入是学员自己第 03 课写的 `pipeline/` 五份契约；产出一张填完第 4 列的验证信号去向表。
- 一级标题：
  1. 四代演进，一刀切法：验证结果回给谁 —— 唯一决定 AI 工具能不能自己纠错的，是验证结果最后回给谁；第三代改称**护栏代**（不叫 Sandbox，也不是治理线 `harness/`）。
  2. 四个位置：信号能落在哪 —— 信号只有四个可能终点：人、机器、文档、没人管；「文档」没人读就等于「没人管」。
  3. 把自己的契约摊开填表 —— 每个检查点该落在哪个位置，是从学员自己第 03 课的 pipeline 契约里找出来的，不是抄来的。
  4. 该交给机器的格子，先标出来（收尾）—— 只解决判断，不解决怎么造检测脚本，机器要接手得先有信号。
- 结尾抛出的问题：验证该由机器接的那些格子已经标出来了。机器要接，得先有信号。这些信号从哪来？

## 第 07 课 · 反馈信号从哪来（方法论）

- 记忆锚点：一个 Loop 转不转得起来，先看它的输入信号有没有在动手写脚本之前就定义清楚——配音质检只是拿来验证这句话的一个例子。
- 开篇契约：上一课交付了验证信号去向表（第 4 列已填完）；输入是表里标"机器"的格子 + 学员自己的 `pipeline/2-create.md` 步骤 3 和 `brain/tts.config.json`；产出一张配音批次检查点表（六项：量什么/怎么量/阈值/谁来判）。
- 一级标题：
  1. 检查点候选：从「该交给机器」的格子倒推 —— 检查点不是先想清楚要测什么再列出来的，是倒着从"哪些验证格子标了机器"这件已定的事往回问出来的。
  2. 三条判据：能不能现在写成一句断言 —— 一项检查该不该进这一轮 Loop，看的不是它重不重要，是它此刻能不能被写成一句"是/否"的断言。
  3. 六项检查点定案，以及 overrides 落在哪 —— 阈值从"错到什么程度会导致返工"倒推；`overrides` 统一落在 build 内 `tts.config.json`，与仓库里 `dubbing-check`/`dubbing-reviewer` 另一套口径不一致，正文以 `tts.config.json` 为准。
  4. 从检查点表到可跑的脚本（收尾）—— 六项检查点现在只是一张表，没有一行代码能跑出数字。
- 结尾抛出的问题：检查点表定了六项要量什么。表还只是表，怎么变成能跑出数字的脚本？

## 第 08 课 · 造出六个检测脚本（L1）

- 记忆锚点：六个脚本要不要自动下 PASS/FAIL，不是写代码那一刻才知道的——它能不能被写成一句断言，第 07 课分类的时候就已经定了。
- 开篇契约：上一课交付了配音批次检查点表（六项定案）；输入是这张表 + 学员自己第 05/06 课的 `build/` 工程；产出一个全量的 `dubbing-check` skill（六个检测脚本 + `depause.mjs` + `SKILL.md`）。
- 一级标题：
  1. 六个脚本的共同契约：先定形状，再动手写 —— 三项能断言的该是硬门槛（exit 1/0），三项只能候选的该是建议（恒 exit 0），契约要把这条边界写死。
  2. 造一个样板，照样板批量复制剩下五个 —— 六个脚本结构同构，写一条钉死样板、一条照样板批量复制；`depause.mjs` 不断言具体命令行格式，只写「不切词、不能原地写、跑完必须复扫」三条约束。
  3. 打包成 skill：一份 SKILL.md 把脚本变成检查清单 —— 脚本单独能跑不等于能被下一课的裁判直接复用，这层说明书是 `SKILL.md` 的活。
  4. 数字有了，判断还没交出去（收尾）—— 脚本只负责吐数字和候选清单，PASS 还是 FAIL 现在还是学员自己拍板。
- 结尾抛出的问题：六个脚本能出数字了，可下判断的还是你。让写稿的那个 AI 自己判自己的活，行不行？

## 第 09 课 · 裁判与选手分离（L1）

- 记忆锚点：判断权和执行权握在同一个上下文里，裁决就会不自觉地偏向"过"——要把判的人和改的人拆开，靠的是工具白名单里物理上没有 Edit/Write，不是靠自觉。
- 开篇契约：上一课交付了全量 `dubbing-check` skill（六个脚本，三硬门槛+三候选）；输入是这六个脚本和它们的退出码类型 + 学员一批真实配音；产出 `dubbing-reviewer.md` 子代理定义 + 一份真实判决输出。
- 一级标题：
  1. 谁来判：执行和判断不能是同一个角色 —— 写稿、改文案、判 PASS/FAIL 如果都在同一个 AI 的同一个上下文里做，它会不自觉地觉得自己刚做完的东西"过得去"。
  2. 工具白名单：把"不能改"焊进定义里 —— 判改分离不是靠这个角色"记得"不去改，是靠它的工具列表里物理上没有 Edit 和 Write。
  3. 裁决口径：保守判 FAIL，输出格式钉死 —— 裁判必须对真问题判 FAIL、对统计假象不判，判断标准和输出格式都不能临场自由发挥。
  4. 跑一次真实判决（收尾）—— 定义写在纸上不算数，得让它真的判一次、拿到一份 PASS 或 FAIL 才算立住。
- 结尾抛出的问题：裁判独立了，一次判决能给出 PASS 或者 FAIL。判 FAIL 之后呢，谁去修，修完再判，什么时候停？

## 第 10 课 · 自愈回路与三轮熔断（—）

- 记忆锚点：自愈回路要有客观出口，出口不是"判得准不准"，是有没有一条谁都认的熔断线——三轮是这个项目自己定的工程约定，不是从数据里算出来的最优值。
- 开篇契约：上一课交付了 `dubbing-reviewer.md` 和一份真实判决；输入是这份裁判定义和它的判决输出 + 学员自己第 05/06 课那条内容；产出一次真实的 FAIL → 修 → 重合成 → PASS 全过程记录。
- 一级标题：
  1. 回路怎么接：判、修、复判轮流交棒 —— 自愈回路不是"失败了重试一次"，是判、修、复判三件事轮流换人做，每次交棒都换一个角色。
  2. 熔断线画在哪：三轮不过就停，不是统计出来的 —— 三轮上限是这个项目自己拍板的工程约定（全链路返工代价太大），不是从大量样本里统计出来的"最优轮次"。
  3. 熔断落地：状态怎么记，人从哪接手 —— 按"阻塞即上报"的铁律推给人；此时只能手改 `meta.yaml`，是临时手段，第 15 课收敛；写作时按 `tts.config.json` 的 `overrides` 口径。
  4. 跑一次真实闭环，把它记下来（收尾）—— 闭环立没立住，看的是有没有一次真实发生过的 FAIL 到 PASS 记录，不是设计文档写得多完整。
- 结尾抛出的问题：自愈回路合上了。可你一路走来手改了一堆 `meta.yaml`，后面还有几件大得多的东西要造（状态中枢、飞书闸口、控制台）。一条 prompt 显然不够，怎么让 AI 造这种量级的东西？

## 第 11 课 · SPEC 方法：从调研到验证的六步（L3 方法）

- 记忆锚点：六步方法的分量都压在「讨论选型」这一步——不逼 AI 给每个方案当一次辩护人，前面摆再多候选也是陪衬。
- 开篇契约：上一课交付一次真实的 FAIL → PASS 全过程记录，留下一堆手改的 `meta.yaml`；本课产出 `docs/spec/` 目录约定 + 六步模板四件套（调研 / ADR / 执行方案 / 施工记录）。
- 一级标题：
  1. 从一条 prompt 到大件：什么时候要换挡 —— 能不能交给一条 prompt，看有没有互斥路线、返工贵不贵，不看代码行数。
  2. 调研：把选型空间摊开 —— 先让 AI 出候选清单，再逐个填进固定四列的对比表（方案 / 适用前提 / 代价 / 已知失败模式）。
  3. 讨论选型：逼每个方案当自己的辩护人 —— AI 会把自己想选的写饱满，单独一轮逼它说清每个方案在什么情况下会输。
  4. 决策：把选择钉成 ADR —— ADR 只记决策 / 理由 / 被否方案 / 反悔成本四件事。
  5. 写 SPEC：把决策展开成可施工的规格 —— 执行方案固定四节，节名不许各课改写。
  6. 执行：照 SPEC 交付里程碑 —— 里程碑出口条件必须是一句能跑的验证动作，不写「基本完成」。
  7. 验证：一句能跑的验证动作收口 —— 验证靠留痕（施工记录）不靠肉眼看代码。
  8. 回看六步：如果第 08 课走过这条路（收尾）—— 用六个检测脚本回看六步会多出什么、少踩什么。
- 结尾抛出的问题：六步方法有了。拿第一件重活来练：状态写入口这件事，先走前三步，调研、讨论选型、拍板，一行代码都不写。

## 第 12 课 · media 调研与选型讨论（L3，六步的 1-3 步）

- 记忆锚点：这一课不写代码——四组互斥路线，每一组都要让候选方案自己交代什么时候会输，选型才立得住。
- 开篇契约：上一课交付 `docs/spec/` 目录约定和六步模板四件套；本课产出 `00-调研.md` + `01-ADR.md`。
- 一级标题：
  1. 开篇：这一课不产一行代码 —— 判断的是「选哪条路」，不是「路怎么修」。
  2. 调研：四组路线逐组摊开 —— 入口形态 / YAML 写法 / 并发保护 / 派生视图，各自一张固定四列对比表。
  3. 讨论选型：四组各自的辩护人 —— 同一条辩护式 Prompt 换掉候选清单，对四组各跑一遍。
  4. 决策：四份 ADR 拍板 —— 四组各自独立拍板，互不牵连。
  5. 收尾：从决策到规格还差一步 —— 决策落纸，AI 还照着施工不了。
- 结尾抛出的问题：四组路线拍完板，ADR 写好了。决策变不成代码，中间还差一份能让 AI 照着施工的执行方案。

## 第 13 课 · media 写 SPEC（L3，六步的第 4 步）

- 记忆锚点：决策落了纸不等于能施工，执行方案要把每条命令拆到「读什么、写什么字段、失败怎么报」这个粒度，AI 才照得着做。
- 开篇契约：上一课交付 `00-调研.md` + `01-ADR.md`，四组路线都拍完板；本课产出 `02-执行方案.md`。
- 一级标题：

## 第 17 课 · 人审闸口：闸设在哪（方法论）

- 记忆锚点：可逆的 AI 自行，不可逆的等人。
- 开篇契约：上一课交付 `03-施工记录.md` + 验收输出（`media check` 跑通、写路径唯一自证）；输入 `state.ts` 的 `review` 三条出边、`pipeline/3-review.md`、`pipeline/4-publish.md`；产出不可逆动作表 + 卡片字段草案。
- 一级标题：
  1. 判据：错了能不能收回，不是会不会犯错 —— 四类动作收不回（发出去收不回/花钱/对外可见/覆盖真相源），其余不需要设闸。
  2. 闸口位置：定在哪条边上 —— `review` 三条出边全可逆，真正的闸是 `approved` 之后的 `media publish-done` 与真发。
  3. 卡片放什么：三十秒判完的信息配额 —— 字段草案划清必须上卡与点进去看的界限；飞书通道是参考仓库历史实现，首次点明企业/团队账号门槛。
  4. 收尾：第二件重活 —— 字段定了，技术通道（通道形态/卡片拆法/超时/隔离）一件未定，转入六步方法。
- 结尾抛出的问题：不可逆动作表和卡片字段草案有了。这是第二件重活，六步再走一遍：飞书通道要定哪几件事？

## 第 18 课 · 飞书通道 SPEC（L3，六步的 1-4 步）

- 记忆锚点：选型不是选喜欢的方案，是先让每条路自己说清在什么条件下会输。
- 开篇契约：上一课交付不可逆动作表 + 卡片字段草案；输入 `feishu-notify` SKILL.md、`tools/feishu-bot/` 六个 py 文件、第 11 课六步模板四件套；产出 `docs/spec/feishu-gate/` 三份（调研/ADR/执行方案）。
- 一级标题：
  1. 调研：企业自建应用怎么配，四个决策点是什么 —— 六步配置无选型空间照做即可，真正要拍板的是通道形态/卡片拆法/超时/隔离四件事。
  2. 长连接 vs webhook —— 选长连接，因为学员机器没有公网地址，webhook 要多接一层内网穿透。
  3. 卡片结构：一张卡还是按流程拆几张 —— 按状态拆三张卡（审核卡→原因卡→确认发布卡），每张两个按钮，没有查看全文按钮，封面由 `notify.py` 单独发一条图片消息。
  4. 3 秒回调窗口 —— 飞书强制 3 秒响应，同步路径只做内存操作，重活甩异步线程。
  5. 命名空间隔离：一个应用服务两条线 —— 复用同一应用靠 `ns` 字段过滤回调，事件是负载均衡投递不是广播，不匹配静默丢弃。
  6. 决策与写 SPEC —— 四个决策点收成 ADR 的四条独立记录，落进执行方案四节模板（决策点 × 功能 × 详细设计）；服务还没实现，抛向第 19 课。
- 结尾抛出的问题：飞书 SPEC 定完四个决策点。照着它把服务实现出来，按钮点下去怎么回流成状态？

## 第 19 课 · 飞书实现与按钮回流（L3，六步的 5-6 步）

- 记忆锚点：闸口信不信自己做成了，只看状态变没变，不信自己的汇报。
- 开篇契约：上一课交付 `docs/spec/feishu-gate/` 三份，四个决策点定死；输入 `notify.py`/`cards.py`/`server.py` 全文、`state.ts` 的 `review` 三条出边；产出一个能推卡、收按钮、把结果落成状态的服务。
- 一级标题：
  1. 执行：出站发卡 —— 先推口播稿/封面再推审核卡，让人看真实内容判断，不是看摘要卡。
  2. 执行：按钮回流 —— 三个按钮对应 `review` 三条出边，重做上限 `REWORK_LIMIT = 2`（`server.py`），与第 10 课三轮熔断是两个独立数字，不能混用。

- 结尾抛出的问题：人点头这一关通了。点头之后真发出去这一步，怎么做才不会误发？

## 第 20 课 · 发布 Skill 与 dry-run（L2）

- 开篇契约：上一课交付能推卡收按钮的飞书服务，人审闸口通了；输入 `douyin-publish` SKILL.md 与 references、`pipeline/4-publish.md`；产出 `douyin-publish` skill + 一次真发或 dry-run 到底。
- 一级标题：

## 第 21 课 · 双线闭环与资产读写表（方法论）

- 记忆锚点：生产线消费资产，治理线保养资产，治理只提议不改。
- 开篇契约：上一课交付 `douyin-publish` skill + 一次 dry-run 到底；本课产出 `harness/` 骨架（README + tasks.md + report-template.md）+ 一张资产读写表。
- 一级标题：
  1. 双线边界：谁消费、谁保养 —— 生产线只消费存量资产，治理线是唯一按自己节奏保养这些资产的线。
  2. 只提议不落笔：治理线的第一条铁律 —— 自动改错了没人发现，所以边界要写进契约不能靠自觉。
  3. harness 骨架与 line 字段记账 —— `line` 字段是唯一能让机器判定这笔账归哪条线的地方。
  4. 资产读写表 —— 权限要落成表格，文字铁律会被绕过。
  5. 反哺大环：三课才能讲完的一件事 —— 大环横跨 21（为什么只提议）/22（单次归因）/24（自审作用在治理线自己身上），提前点破全貌。

- 结尾抛出的问题：治理线的骨架和读写边界画好了，第一个治理任务是复盘。数据怎么拉、怎么归因、提议怎么写？

## 第 22 课 · 复盘归因反哺大脑（L2）

- 记忆锚点：复盘只回答一件事——这条内容漏在哪一环，不是给账号打总分。
- 开篇契约：上一课交付 `harness/` 骨架 + 资产读写表；本课产出一个 `douyin-retro` skill + 一份真实复盘报告。
- 一级标题：
  1. 传播漏斗：一条内容漏在哪一环 —— 第一个跌破基线的环才是真正要修的地方。
  2. douyin-retro skill 封装：拉数据、记账、出报告 —— 记账写入 `backlog.yaml` 的 `metrics` 字段。
  3. 归因练习：脱敏样例数据怎么用 —— 没有真实播放数据用课程材料附录的脱敏样例，方法论和真实账号跑起来一样。

## 第 23 课 · 选题池与外网情报（L2）

- 记忆锚点：情报只从外网来，抖音那边的信号靠复盘反向补——选题池自己会烂，得有一条线专门喂它。
- 开篇契约：上一课交付 `douyin-retro` skill + 一份复盘报告；本课产出一个 `douyin-ideate` skill + 一批入池候选。
- 一级标题：
  1. 选题池的数据契约：为什么只入不出会烂 —— `backlog.yaml` 需要三态加过期规则才不腐化。
  2. agent-reach 情报采集：只从外网来，不爬抖音 —— 抖音反爬重，能不能无人值守跑下去的硬约束，不是图省事。
  3. douyin-ideate skill 封装：双赛道打分与入池 —— 深度题和流量题共用一套引擎，权重不同。
  4. 去重与清扫：撞题不进池，过期就退池 —— 30 天去重和规则化清扫可自动，撞题判断留给后面的治理任务，要人审。
  5. 选题池养起来之后（收尾）—— 选题池能自己养起来了，四个治理任务各跑各的。
- 结尾抛出的问题：选题池能自己养起来了。四个治理任务各跑各的，谁来决定今天该跑哪几个？

## 第 24 课 · 治理总调度与自审元层（L2）

- 记忆锚点：自审是反哺作用在治理线自己身上——大环合上之后，连「怎么治理」这件事本身也进了回路。
- 开篇契约：上一课交付 `douyin-ideate` skill + 一批入池候选；本课产出一份任务注册表 + 四个治理 skill + 一轮巡检记账。
- 一级标题：
  1. harness-dispatcher：读注册表，到点才跑 —— 调度和执行解耦，三种触发类型的到点判据各不相同。
  2. 三个治理 skill 起步：backlog-gardener / benchmark-refresher / account-audit —— 各管一类没人催但会烂的资产，一条 L1 prompt 钉死判据即可。
  3. 调参限幅表：自审能自动调什么 —— 可逆数值自动档、启停锁定参数一律提议人审。
  4. 反哺大环第三段：自审作用在治理线自己身上 —— account-audit 不审内容不审 brain，只审治理线自己。
  5. 治理线能自己巡检了（收尾）—— 能自己巡检记账了，可都要敲一次命令才动。

## 第 25 课 · 无头作业：进程流归一与终局裁决（L2）

- 记忆锚点：cc-stream 只认识「子进程 stdout 是一串 JSON 行」这一件事，不认识任何调用方的业务概念；裁决只读文件出结论，不信进程自述——这两条合起来才是「无人值守」的完整定义。
- 开篇契约：上一课交付任务注册表 + 四个治理 skill + 一轮巡检记账；本课产出一个 `cc-stream` 包（六个文件）+ 一个裁决函数 + 一套收尾策略 + 一次 `claude -p` 跑通。学员此时还没有 console，凡涉及「装进哪个常驻进程」的地方都指向模块 7。
- 一级标题：
  1. 三层解析：从 JSON 行到里程碑 —— 每层只做一件事，业务知识留在最外层调用方。
  2. 七种归一事件与三档信任分级 —— 展示类事件永不驱动判断，只有落盘文件才是终局裁决。
  3. 里程碑引擎：声明式规则，业务知识留在外面 —— 换任务类型只换规则表，不改引擎。
  4. 拉起无头 claude -p：三个坑与一次真跑 —— 认证、超时、输出流三个坑排掉，六个文件拼起来跑一次验证。
  5. 只认文件的裁决，加上守住并发的锁 —— 与第 09 课「判的人不能改」同一类约束的第二次出现；拿不到锁直接报错退出，不排队。
  6. 收尾策略：先礼后兵，加恢复规则：内存不可信 —— 先发终止信号给收尾机会，宽限期后仍不退才补杀；内存态不可信，真相必须活在文件里。
  7. 收尾：无人值守闭环合上之后 —— 只能翻文件和日志知道跑到哪，下一件重活是给它做个能看的控制台。
- 结尾抛出的问题：整条流水线能无人值守跑完了，可你只能靠翻文件和日志知道它跑到哪。第三件重活：给它做个能看的控制台。

## 第 26 课 · 读设计稿，定契约（L3，六步的 1-4 步）

- 记忆锚点：原型只抄规格不抄代码——设计稿定的是像素和布局，SPEC 定的是边界和接口，两者不是一回事。
- 开篇契约：上一课交付一个 `cc-stream` 包、一个裁决函数和一套收尾策略，无人值守闭环合上了；本课输入 `docs/design/` 九页原型 + `theme.css`、0818 方案包、第 11 课六步模板；本课产出 `docs/spec/console/` 三份（调研 / ADR / 执行方案）。
- 一级标题：
  1. 调研：九页原型摆出来，先划边界不看像素 —— 只有六页是这轮要建的，`review.html`、`harness-task-detail.html` 现在动手就是白做。
  2. 讨论选型：给每条互斥路线找辩护人 —— AI 会不自觉偏向已内定的方向，得逼它给对照组找一次活路。
  3. 决策：五包一仓和两条写路径落成 ADR —— 每条决策都要回答会不会破坏已有的唯一写入口。
  4. 写 SPEC：把决策展开成 API 清单和执行方案骨架 —— 执行方案（接口 × 功能 × 详细设计）是给第 27、28 课直接施工的穷举清单。
  5. 收尾：契约定完，读路径还没打通 —— 下一课先打通读路径。
- 结尾抛出的问题：契约定完，五包一仓边界和 API 清单有了。先把读路径打通，页面才有东西可显示。

## 第 27 课 · 后端：读写两条路径（L3，六步的第 5 步）

- 记忆锚点：读 API 不是又一套解析逻辑，是 core 的 `parsers` 套了一层 HTTP 壳；写 API 也不是重新发明状态变更逻辑，是把 HTTP 请求原样转成一条 `media` 命令。
- 开篇契约：上一课交付 `docs/spec/console/` 三份；本课输入第 26 课 API 清单、`core/src/snapshot.ts` 与 `dashboard.ts`、`jobs/runner.ts` 与 `defs.ts`、第 15、19 课成稿；本课产出读 API 全通（六个快照 + file/asset/health + SSE）+ 写 API 全通（快写 4 条 + 慢作业 3 条）+ 飞书回调改走它。
- 一级标题：
  1. 六个快照接口：一页一个，不合并成一个大对象 —— 接口按页面切，前端不用再拼一次。
  2. file、asset、health：三个基础设施接口 —— 横切能力单独做，不塞进六个快照接口。
  3. SSE 推变更：store、watcher、revision 三件怎么配合 —— 只推 revision 号，不推数据本身。
  4. 快写 4 条：把点击翻译成一条 media 命令 —— 不重新发明状态变更逻辑，只是转发。
  5. 慢作业 3 条：spawn 一次无头 CC，用 job runner 兜底 —— 仓库 `routes/jobs.ts` 实际注册五个作业端点，课程只讲 `publish`/`rework`/`apply-proposal` 三条，`harness-run`、`create` 不在 1:1 范围。
  6. 飞书回调改道：第 19 课那个服务不再自己写 —— 状态写入只留一个入口。
  7. 收尾：读写两条 API 都通了，界面还没影 —— 下一课立前端骨架，落六页整站。
- 结尾抛出的问题：读写两条 API 都通了。开始做界面，骨架和头两页怎么落设计稿？

## 第 28 课 · 前端：六页整站与联调（L3，六步的第 6 步）

- 记忆锚点：六页能不能立住，看的不是页面好不好看，是数据层的两个 hook 能不能扛住六页原样复用；六页能看只是及格线，两条写路径都要在整站上真的走一遍。
- 开篇契约：上一课交付读写两条 API 全通，飞书回调也改走它了；本课输入 `docs/design/` 六页原型、`theme.css`、`07-界面用语对照表.md`、第 27 课读写 API；本课产出六页整站 + 一份验收输出。
- 一级标题：
  1. AppShell 与两个数据 hook：先立骨架不建页面 —— 六个页面共用同一套取数逻辑。
  2. theme token 映射：抄设计稿的颜色，不重新配色 —— `theme.css` 是唯一真相源。
  3. P1 总览、P3 详情：先落头两页 —— 总览十秒内回答今天正常吗，不做操作入口；详情按 `allowedTransitions` 动态渲染按钮，不把状态机搬到前端。
  4. P4 选题池、P5 治理线：照骨架补，界面说人话不说系统话 —— 文案按对照表换成工作流语言。
  5. P2 看板、P6 数据复盘：只读页面的最后两块 —— 两页都只读，不接写操作。
  6. 单端口出整站，并验证读写两条路径都通 —— 开发和生产同一形态；模块 7 出口条件是六页能看、两条写路径都能从界面上真的走一遍，不是页面数量。
  7. 收尾：整站建完，退一步看它是什么 —— 下一课给它定形态坐标，并给出 1:1 验收报告。
- 结尾抛出的问题：六页整站跑起来了，这套东西建完了。它到底是个什么形态，哪些出口不能关？

## 第 29 课 · 收官：形态坐标与 1:1 验收（—）

- 记忆锚点：全书 28 课积累的判断落在同一条线上，每一课往上加一层约束，不是 28 个并列知识点；1:1 验收对的是结构和工具，不是抄账号。
- 开篇契约：上一课交付六页整站和验收输出，控制台建完了；本课输入第 01 到 28 课收尾段与「学员交付」栏、第 06 课四位置模型表、ADR §2/§4；本课产出形态坐标表 + 撤档判据 + 1:1 验收报告。
- 一级标题：
  1. 回收：从端到端走查到六页整站 —— 01 到 10（人退出到哪三点）、11 到 25（状态写入口收拢、判改分离、只提议不落笔）、26 到 28（人从翻文件退到点按钮）。
  2. 四位置模型收尾：验证信号的第三个去处 —— 第 06 课留的一格在此回收，名字是「文档」；另一张四代演进表的第三代叫**护栏代**，两张表不能混用。
  3. 形态坐标：脚本集合、工作流，还是 agent 系统 —— 一条连续轴，当前落在中段偏工作流。
  4. 撤档判据：哪些出口一关，系统就退化 —— 闸口和无人值守是两件事，关错退化的是可信度。
  5. 验收怎么用，加结构项：五条判据 —— 不写成打分表，不过时给「缺什么、回哪一课」；结构项机器可判（生产线跑通 / 治理线任务被同一调度器派活 / 写入口唯一 / 单端口六页两条写路径通 / 没手写过实现代码）。
  6. 内容项：只看有没有、判不判得了，不比对着抄 —— `brain/`、`CLAUDE.md` 因人而异，验收不比像不像。
  7. 收尾：全书收官 —— 一套功能对等的流水线 + 一份能证明它对等的验收报告。
- 结尾抛出的问题：全书收官。这一课结束时学员手上应该有一套功能对等的流水线，以及一份能证明它对等的验收报告。（第 29 课是全书最后一课，没有下一课承接。）
