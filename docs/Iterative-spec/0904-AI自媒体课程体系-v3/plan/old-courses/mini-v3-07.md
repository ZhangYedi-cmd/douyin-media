# 反馈信号从哪来：配音批次的检查点表与归属判据

上一课交付的是一张验证信号去向表，最后一列填的是链上每一步的验证信号去了哪里，四个去向是流向人、流向机器、流向文档、流向没人管。填流向机器的条件当时给了两条：这一步的不通过能写成一个退出码，而且这个退出码有下一步在接。本仓那条链填下来，符合这两条的只有配音审批那一格。本仓指这门课一路在拆的那个真实仓库，不是你自己那个。

上一课结尾问的是哪些检查写得成一个退出码、哪些写不成。这一课回答前半句：给出判定的依据，把配音这一批检查逐项定下归属。写成脚本是第 08 课的事。

处理范围是表上的一小片，配音合成完的那一批 mp3，到录屏之前这一段。这一片是这条流水线上第一个要合上的 Loop。一条 Loop 指四步能自己转起来：检查出问题，判出该改什么，改完重跑，再拿同一条判据量一次。这一课定的是第一步，检查该量什么。

本课的产出是一张配音批次检查点表，六行四列，行名是出错点，四列是量什么、怎么量、阈值和它的来源、谁来判。

## 1. 先把可能出错的点列全

定归属之前得先有一张全的清单。凭印象列会漏，漏掉的那一项通常要等成片出来才冒头，那时候返工的代价是重录。

配音这一片的坑在本仓记了两处。一处是 dubbing-check 这个 skill 的说明文件，按开工前、合成后、录屏前、录屏后分成四个检查点，每一条都写清了它是从哪次事故来的。另一处是第 03 课立骨架时开的那份教训簿 `pipeline/lessons.md`，一张表，一行一个踩过的坑，右边一列写现行规则落在哪个文件。让 AI 把这两份读完再列清单，漏项会少很多。

```
读 .claude/skills/dubbing-check/SKILL.md 和 pipeline/lessons.md。
只看配音批次这一段：一批 mp3 合成完之后、录屏之前。
把这一段里所有可能出错的点列成一张表，一行一个，三列：
1. 出错点：一句话说清会出什么事，用文档里的原话，不要概括成抽象名词；
2. 症状：这件事发生时，屏幕上或者文件里能看到什么；
3. 出处：写在哪个文件的哪一节或哪一条。
只列文档里写过的，不要补你觉得也可能出错的项。
不要给修法，不要排序，不要打分。
```

这张表是本课后面几节的输入，出处列用来核事实，症状列会变成正式表里的量什么那一列，所以别做完就丢。

拿回来审两件事。

第一件，每一行的出处能不能翻回原文。AI 列清单时容易把两条相近的合成一条，也容易把自己的常识混进来。逐行拿出处 grep 一次，翻不到的删掉。

第二件，症状那一列有没有落到文件里看得见的东西上。写音质不佳的行下一步没法用。写某段 mp3 是 0 字节，写成片里画面是新文案、声音是旧文案，这样的行才用得上，因为第 2 节要判的就是这个症状能不能被程序量出来。

如果它交回来的表只有三四行，多半是它把范围理解成了整条流水线里的配音那一步，只读了说明文件的检查点 2。把教训簿里的 L2、L3、L10、L16 四条点名给它，让它再过一遍。教训簿里还有 L17 和 L18 两条也在这一片，它们记的是修法，不是检测项，列进表里就删掉，第 4 节会用到它们。

两份文档过完，落在配音批次这一段的是六项：真相源不同步、合成不全、段内死气、语速离群、多音字读错、组件里的大字与口播文案不一致。最后一项里的组件，指网页演示每一章那个 tsx 文件，屏幕上那些逐字显示的大标题就写在它里面，它跟口播文案是两处各写各的。

## 2. 什么样的检查写得成断言

上一课那两条件里，有下一步在接是第 09 课和第 10 课的事，判官和回路都还没造。这一课只拆前半条，能不能写成一个退出码。拆开是三件事。

```
判据一（量）：这件事有能测量的量吗，量出来的数代表的就是这件事吗。
  时长、字节数、静音区间的起止秒数、两段文本相不相等，程序都取得到。
  取得到但代表不了的也算没过：数是准的，可它同时对应两种情况，
  区分要靠语境，那这一项就还没被翻译成量。
判据二（线）：有一条能划的线吗，这条线说得出来源吗。
  来源只有两种算数：一次真实事故，或者一个外部标准。
判据三（形）：输出是机器读得懂的信号吗。
  退出码 0 或者 1，或者一份下一段程序能解析的段号列表。
  一段中文评语不算，收信号的是程序，它没法从整体还不错里取出下一步动作。
```

三条都过，这一项写得成断言，判官填机器。卡在判据一的，判官只能填人，程序取回来的数在这一项上分不出对错。量和形都有、只卡在判据二的，是第三种情况：现在写不了，等线有了来源再写，这一档在第 3 节末尾有实例。

判据二那句来源要求，用起来是这样：填数的同时把来源填上，来源栏空着的行，谁来判就不能填机器。你答不上来为什么是这个数，就没法拿它去放行或者拦人，它只能拿来排序，告诉你先看哪几段。

判据三卡的是形状，它还有一层，退出码得代表对内容的判决。上一课那张表里的 `check-av-consistency.mjs`，你第 08 课才会造它，本仓那一份里有一处退出码 1，那是找不到章节目录时报的用法错误，说明你路径写错了，不说明画面和口播对不上。有退出码也不等于这个退出码可信，本仓批量去停顿那次，`depause.mjs` 的输入和输出写成了同一个文件名，ffmpeg 打开输出的一瞬间就把输入截断了。17 段跑完命令一声没吭，退出码全是 0，时长一点没变，死气原样留着（教训簿 L16）。

## 3. 六项归属与阈值来源

| 出错点 | 量什么 | 怎么量 | 阈值与来源 | 谁来判 |
|---|---|---|---|---|
| 真相源不同步 | 分段文案里每段的文本，和章节 `narrations.ts` 里的原文 | 逐字比 | 不等就是问题，没有容忍区间。来源是 EP02 那次成片画面是新钩子、声音是旧钩子（L2） | 机器 |
| 合成不全 | 文件在不在、段数、字节数、时长 | 按分段文案逐段核对应的 mp3 | 文件缺失、段数与分段文案不等，判问题。字节数小于 500、时长小于 0.3 秒，判空壳，这两个数是粗界不是判决线 | 机器 |
| 段内死气 | 段内非句读位置的静音时长 | ffmpeg 的 silencedetect 滤镜先抓，抓回来再按判定线过滤 | 0.45 秒。来源是 EP02 那句 18 个字撑 6.78 秒、含 1 秒死气（L3），线取在事故那 1 秒和正常语气停顿之间 | 机器 |
| 语速离群 | 剔掉停顿之后的音节每秒 | 音节数除以发音时长，发音时长按每个标点扣 0.3 秒算 | 偏离这一批均值 1.3 个标准差算离群。这个数写在脚本里，没有来源，只拿来排序 | 人 |
| 多音字读错 | 这一段里出现了哪些多音字 | 按多音字表扫每段文案 | 无阈值，扫到就列出来 | 人 |
| 组件大字与口播不一致 | 组件文件里的中文长句，和对应段的口播文本 | 把两边并排列出来 | 无阈值，只有整句冲突才算问题 | 人 |

表里排第一的是真相源同步，不是合成完整性。文案对不上的时候，段全不全已经不重要了，全的也是一批旧文案。

合成不全这一行的阈值列写法值得照抄。真正拦人的是文件缺失和段数不等，这两条属于不存在即错，用不着来源。500 字节和 0.3 秒不拦人，它们负责认出空壳：串行批量合成会偶发限流失败，失败那一段留下的是 0 字节或者极小的文件，比正常段小一个量级。第 05 课让你手工核的那条每个文件大于 1KB，跟这里的 500 字节是同一条粗界，差一倍不影响结论，因为正常段和空壳之间差的不是一倍。

死气这一行的两个数得分开看。ffmpeg 里检测静音的滤镜叫 silencedetect，给它两个参数，一个噪声门限，本仓用负 38 分贝，一个时长门限，本仓用 0.3 秒。时长门限是硬的，比它短的静音根本不会出现在输出里。抓用 0.3 秒，判用 0.45 秒，中间 0.15 秒是留给边界段的余量：直接按 0.45 去抓，落在门限附近的那些段就没机会进日志，你连它们存在过都不知道。至于门限为什么取 0.3 而不是 0.35，本仓代码里没写，这个数是拍的。0.45 这条判定线本身有来源，短于它的停顿按正常语气放行，长于它的算死气。

语速这一项卡在判据一。数取得到，问题在于同一个数字有两种解释。一段口播含三个字母以上的英文词，字面算出来的语速会偏慢，因为英文词念出来比它折算的音节数长，本仓按一个英文词约 1.3 个音节粗估。这种偏慢是统计假象，真拖沓和假象在数值上长得一样，分它们的依据是这段话念出来听着赶不赶，得有人听一遍。这一项在判据二上也不干净。1.3 个标准差写在脚本里，教训簿没有对应事故，外面也没有一个通行的音节每秒标准。均值和标准差都在这一批段里算，九段十几段的样本，一两个极端值就能把均值拉走。所以本仓这个脚本跑完总是退出码 0，它只负责把表摆出来，按偏离程度告诉你先看哪几段。一个分不清真假的检查带上退出码，会在真假之间随机拦人。

多音字这一项也卡在判据一。程序查得出某个字是多音字，查不出这一段里它该念哪个音。合成接口的读音字典按字生效，一旦给某个字指定读音，全片所有出现的地方都按这个读。本仓有一集里同时出现了执行和十几行两个词，前一个该读 xíng，后一个该读 háng。字典里把这个字定成 háng 之后，十几行念对了，执行跟着念错，那一批被打回重合成（L10）。所以这一项的输出是一行行带上下文的候选，定读音的是人。

组件大字这一项同样卡在判据一。程序能把组件里的中文长句和对应段的口播文本并排列出来，判不了它们算不算冲突。组件里的概念标签跟口播是关键词和整句的关系，那不叫冲突；只有整句呈现的标题和行动号召，才要求逐字一致。这个判断要看两边在屏幕上是怎么摆的。

填人的这三行不是永远归人。第 09 课会给它们换一个 AI 判官，判的动作交出去，判据还是这三条。

还有一档现在填不出判官。音量有没有削顶、各段采样率一致不一致、整体响度符不符合发布标准。这三件事 ffmpeg 都测得出来，volumedetect 报音量峰值，loudnorm 报响度。量和形都不缺，缺的是线。响度该定在哪一档，本仓没出过事故，也没去查平台的推荐值。判据二给的两个来源，一个还没发生，一个没去取，所以这三项至今没进检查表。哪天补上其中一个，它们就能从这一档挪进机器那一列。

## 4. 判完之后写到哪：逐段覆盖只有一个落点

表里三行的判官是人。人判完的结论要有地方落，落不下去的话，这三项又回到了上一课那个流向没人管的格子里。

多音字和语速这两项的落点是 `build/` 里那份 `tts.config.json` 的 `overrides` 段。第 04 课那张字段表定了它的职责，按段覆盖语速、音高和注音，全局那一栏留空；第 05 课把 `brain/tts.config.json` 复制进当条内容的 `build/`，配音脚本读的是那个副本。这一课往里写的，就是上一节判出来的那几段的读音和语速。

`overrides` 的键是段号，写成章节名加步号的形式。段号说的是位置，同一个键在增删段之后指向的可能已经是另一段话了。本仓有一次为了控时长删掉一段，后面那些段整体前移一位，键还按旧编号写着，注音注到了错的段上，旧键成了死键，新段一个字没注（L18）。所以增删段之后要重排键，并且重跑一次 `npm run extract-narrations`。

改完注音重合成，那一段读音一点没变的话，多半是键指向的段号已经不是你要改的那一段了。这一步让 AI 核比自己数段号快。

```
读 build/tts.config.json 的 overrides 段和 build/audio-segments.json。
逐个 overrides 键去分段文案里找同名的段，输出三列：
1. 键；2. 这一段现在的文案前 20 个字；3. 这条覆盖想改的字或参数。
第 3 列里的注音字，如果在第 2 列的文案里找不到，这一行标死键。
分段文案里有多音字但没有对应 overrides 键的段，单独列一份漏注清单。
只做核对，不要改任何文件。
```

还有一种情况逐段覆盖也解决不了：同一段里同一个字要读两个音。按段生效的字典在这一段里同样是按字生效。本仓遇到过一次，一段话里同时有就得打折和诚实得多，前一个读 děi，后一个是轻声，注哪个都会误伤另一个，最后改的是文案，把诚实得多换成了诚实很多（L17）。改文案要三处一起改：口播稿、章节文件、组件。

## 5. 把表填出来

判据和落点都在上面。剩下的是把你自己那条链的六行填出来。表骨架让 AI 生成，判断和阈值你自己填。

```
输入是第 1 节那张出错点表，和 .claude/skills/dubbing-check/SKILL.md
的检查点 2 与 3.1。
按表里的出错点生成一张空表，一行一项，行名沿用出错点原句。
四列：量什么、怎么量、阈值与来源、谁来判。
量什么这一列，从出错点表的症状列改写成能测量的东西，
症状里没有可测量的，这一格写待定，不要替我猜。
怎么量这一列，只写 SKILL.md 里明确写过的做法，写不出的留空。
阈值与来源、谁来判两列全部留空，我来填。
每一行末尾附一句出处，写清是从哪个文件的哪一节取的。
```

填的时候按判据顺序走：先问量取不取得到、取回来的数代不代表这件事，再问线有没有来源，最后问输出能不能写成一个代表判决的退出码。

交表之前自查三条。

阈值与来源那一列不许只有数字。数字后面接不上一句来源的行，把谁来判改成人，或者像合成不全那一行一样，写清这个数只用来认空壳、不用来拦人。

谁来判这一列只有机器和人两个值。写成视情况的行，说明这一项还没判完，回到判据一重新问一遍。

行数按你的契约来。第 06 课那张去向表里，配音这一片对应的步骤如果比六项少，说明你的创作契约里这一段写得比本仓短，那就按你契约里实际有的项填，少几行是对的。凭空补上本仓有而你这条链上没有的项，填出来的行没人会去实现。

某一行的阈值列如果写着听感自然、节奏舒服这类形容词，多半是这一项卡在判据一上还没被翻译成能测的量。要么换一个能替代它的量，要么把它挪到人那一列，先别硬写检测。

## 6. 小结

- 三条判据：有没有能测的量、量出来的数代不代表这件事，有没有一条说得出来源的线，输出是不是机器读得懂的信号。三条都过才归机器。
- 六项归属：真相源不同步、合成不全、段内死气这三项归机器；语速离群、多音字读错、组件大字与口播不一致这三项归人，人判完的结论落在 `overrides` 里。
- 一张六行四列的配音批次检查点表，每一格都说得出为什么填这个值。

到这里，这条链上第一个 Loop 的第一步定完了。表上写的还都是要量什么，没有一项能自己跑出数字。怎么把这六行变成能跑出数字的脚本？

# 润色报告（Step 6）

## 一、诊断清单逐条处理

### 一等（框架自破）

1. 合成不全那一行来源不成立：改掉表格与正文。现在拦人的判据是文件缺失和段数不等（不存在即错，不需要来源），500 字节和 0.3 秒降级为认空壳的粗界，正文明写这两个数不用来拦人。
2. 0.45 秒来源推不出来：补上从事故到线的那一步。事故给的是这类问题要拦，线取在事故那 1 秒和正常语气停顿之间，短于 0.45 的按语气放行。这一条在 dubbing-check 说明文件里有原文（短停属正常语气，放行）。
