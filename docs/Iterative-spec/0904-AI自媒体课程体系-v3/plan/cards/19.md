## 2.1 大纲

记忆锚点：闸口信不信自己做成了，只看状态变没变，不信自己的汇报。

开篇契约：上一课交付了 `docs/spec/feishu-gate/` 三份，四个决策点都定死了；本课输入是 `tools/feishu-bot/notify.py`、`cards.py`、`server.py` 全文、`meta.py`、`.claude/skills/feishu-notify/SKILL.md`、`tools/console/packages/core/src/state.ts` 的 `review` 三条出边、第 18 课的 SPEC 骨架；本课产出一个能推卡、能收按钮、能把结果落成状态的服务。

### 1. 执行：出站发卡——先推内容，再推卡
- 核心判断：推卡不是直接甩一张摘要卡，是按顺序推：先推口播稿全文（或图文简介），再推封面图，最后才推带「通过/打回」两个按钮的审核卡——让人看着真实内容判断，不是看着一张摘要卡拍板。
- 二级标题：不分。
- 交付物：出站发卡脚本的实现 Prompt（照 SPEC 的卡片结构实现 `notify.py` 与 `cards.py` 里的审核卡）+ 发送顺序清单。
- 学员此时手上有：第 18 课的卡片结构决策（审核卡字段与按钮）。
- 交接：卡推出去了，按钮点下去要有服务接住。

### 2. 执行：按钮回流——落到 state.ts 三条出边
- 核心判断：三个按钮对应 `review` 状态的三条出边——通过 → `approved`、打回并自动重做 → `drafting`、打回挂待办 → `rejected`；重做还带一条第 10 课立过的规矩：自动重做要有熔断上限，达到上限直接转人工，不无限重做。这条闸口自己的重做上限是它自己的一个数字，和第 10 课 dubbing 那条三轮熔断是同一条道理，不是同一个数字，两回事，别混用。
- 二级标题：不分。
- 交付物：按钮到状态出边的映射表 + 熔断上限的判据（达到上限后落 `rejected`、留痕、转人工）。
- 学员此时手上有：第 18 课卡片结构与命名空间隔离决策、`tools/console/packages/core/src/state.ts` 的 `review` 三条出边（第 17 课已经读过一次）、第 10 课的三轮熔断经验（借鉴道理，不借数字）。
- 交接：按钮能落状态了，剩下要定这些改动什么时候做、多久内必须做完。

### 3. 执行：同步与异步边界——3 秒内只改内存，状态只经 media
- 核心判断：回调处理函数在 3 秒窗口内只能做内存操作（读文件判断熔断次数、拼一句提示文案），任何要调用 `claude -p` 或外部请求的重活都要甩进异步线程；状态写入必须经 `media`，服务自己不直接改文件——第 16 课收敛过的「状态记账唯一入口」，在这里第一次被别的服务真正遵守。本地控制台（console）要到第 26 到 28 课才会造出来，这一课的服务自己独立跑通闭环，不依赖还没造出来的东西。
- 二级标题：不分。
- 交付物：同步路径清单（允许做什么）vs 异步路径清单（必须甩出去做什么）+ 一条排障句（卡片点了没反应，多半是同步路径里混进了一次网络调用或耗时操作）。
- 学员此时手上有：第 18 课的 3 秒回调窗口决策、第 16 课「状态记账唯一入口收敛为 media」的结论。
- 交接：服务能推卡、收按钮、改状态了，最后要让它在真实一条内容上走一遍。

### 4. 验证：一条内容真走两次人点头
- 核心判断：服务判断自己做没做成，不看自己有没有报错，看状态变没变——通过要看 `meta.yaml` 真的翻到 `approved`，重做要看它真的翻回 `review`，这条验证比读日志更可靠。
- 二级标题：不分。
- 交付物：验证动作（取一条真实内容，走完"通过 → 出确认发布卡"和"打回 → 自动重做 → 重新出审"两条路径，各自核对状态是否如预期翻转）。
- 学员此时手上有：前三节实现出来的服务。
- 本课做到了什么、还看不到什么、下一课补什么：人点头这一关通了，服务能推卡、收按钮、把结果落成状态；但点头之后真正把内容发出去这最后一步还没做安全。
- 结尾抛出的问题：人点头这一关通了。点头之后真发出去这一步，怎么做才不会误发？
