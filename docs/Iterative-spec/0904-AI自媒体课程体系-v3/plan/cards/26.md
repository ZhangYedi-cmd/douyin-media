## 2.1 大纲

记忆锚点：原型只抄规格不抄代码——设计稿定的是像素和布局，SPEC 定的是边界和接口，两者不是一回事，抄错一个学员就会做出一堆没有后端支撑的页面。

开篇契约：上一课交付了一个 `cc-stream` 包、一个裁决函数和一套收尾策略，无人值守闭环合上了；本课输入是 `docs/design/` 九页 HTML 原型 + `theme.css` + `README.md`（课程附带材料，本课发放）、`0818-看板工作台` 三份拍板方案与三份执行方案、第 11 课的六步模板四件套；本课产出 `docs/spec/console/` 三份：`00-调研.md`、`01-ADR.md`、`02-执行方案.md`。

### 1. 调研：九页原型摆出来，先划边界不看像素

- 核心判断：原型的九页里只有六页是这一轮要建的，`review.html` 和 `harness-task-detail.html` 现在动手就是白做——它们是下一期页面，本仓库没有对应后端。
- 二级标题：不分
- 交付物：一张对比表（方案 / 适用前提 / 代价 / 已知失败模式），至少 4 行，覆盖部署形态（单端口合并 vs 前后端分离部署）、数据同步方式（全量重建 vs 增量重建）、SSE 断线恢复（丢了重拉配 revision vs 事件补发队列）、前端技术栈（组件库 + token 映射 vs 手写/上重型框架）；外加一条 Prompt，让 AI 读九页原型和 `theme.css`，逐页标出「这页对应哪个真实数据源」，标不出来源的页面（`review.html`、`harness-task-detail.html`）单独列出并注明不在本轮范围。
- 学员此时手上有：`docs/design/` 九页原型和 `theme.css`（本课发放）；第 25 课交付的裁决函数与 `cc-stream` 包（用来判断控制台要暴露哪些数据）；第 11 课的六步模板四件套。
- 交接：六页范围划清楚了，但每条路线该怎么选还没吵过。

### 2. 讨论选型：给每条互斥路线找辩护人

- 核心判断：AI 会不自觉把「单端口合并部署」「组件库 + token 映射」写得比对照组饱满，得逼它单独给「分离部署」「手写前端」找一次活路，说清什么条件下它会赢。
- 二级标题：不分
- 交付物：一条辩护式 Prompt，针对调研节列出的对比表，逐条方案要求 AI 扮演该方案的辩护人，说明「在什么情况下这个方案更优」；AI 顺着已经内定的方向说，就是没在辩护，换个问法重来。
- 学员此时手上有：调研节产出的对比表。
- 交接：每条路线都被认真质疑过一轮，可以拍板了。

### 3. 决策：五包一仓和两条写路径落成 ADR

- 核心判断：控制台不是新起一套系统，是给已经跑通的无人值守闭环加一层可视化和可操作的界面，因此每条决策都要回答「会不会破坏已有的唯一写入口」。
- 二级标题：不分
- 交付物：`01-ADR.md` 按固定四项（决策 / 理由 / 被否方案 / 反悔成本）写至少四条：①五包一仓边界（`core` / `cli` / `server` / `ui` / `cc-stream`，单仓多包）；②读路径（六个页面各一个快照接口，外加 `file` / `asset` / `health`，变更用 SSE 推）；③写路径两条（快写走 `execFile media <子命令>` 同步返回；慢作业走 job runner，返回 202 + jobId）；④前端 token 映射（`theme.css` 的 token 映射进组件库配置，不重新配色）。
- 学员此时手上有：讨论选型节的辩护结果。
- 交接：决策拍完板，落地成能施工的规格还差一步。

### 4. 写 SPEC：把决策展开成 API 清单和执行方案骨架

- 核心判断：执行方案不是决策的复述，是给第 27、28 课直接拿去施工的穷举清单，每一条 API 都要写清入参出参和背后的命令或作业类型。
- 二级标题：4.1 API 清单：六个读接口逐条穷举 / 4.2 写路径两条：4 个快写端点与 3 类慢作业各自的输入输出
- 交付物：`02-执行方案.md` 按第 11 课定的四节模板（实施步骤 / 接口 × 功能 × 详细设计 / 对外契约 / 风险与待定项）写出；「接口 × 功能 × 详细设计」节把 API 清单——六个快照读接口（对应 P1 到 P6 六个页面）、`file` / `asset` / `health`、SSE、4 条快写端点、3 类慢作业——逐条列出；一条 Prompt 让 AI 按四节模板生成 `02-执行方案.md` 草稿，人核对 API 清单是否和决策节的 ADR 对得上。
- 学员此时手上有：决策节的 ADR 四条。
- 交接：三份 SPEC 文档齐了，该动手做读路径了。

## 本课必须定死的契约骨架

第 27、28 课的实现全部引用本课定的契约，所以这几条要在本课写死：

- **五包一仓**：`core`（真相源读写与状态机）/ `cli`（media 命令行）/ `server`（HTTP + SSE）/ `ui`（前端）/ `cc-stream`（无头进程流），单仓多包。
- **读路径**：六个页面各一个快照接口，外加 `file`（读任意受控文件）/ `asset`（读封面等静态物料）/ `health`，变更用 SSE 推。
- **写路径两条**：快写走 `execFile media <子命令>`（毫秒级，同步返回）；慢作业走 job runner（返回 202 + jobId，另起进程，前端轮询或听 SSE）。**server 自己不许直接写文件**，一律经 media。
- **前端**：AppShell + 两个数据 hook（快照 hook、SSE 订阅 hook），`theme.css` 的 token 从设计稿映射过来，不重新配色。
字数不设限，心法类内容（SPEC、Loop、状态收敛、反哺）讲透为准，可以多讲。
