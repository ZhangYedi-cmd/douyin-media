## 2.1 大纲

记忆锚点：一个 Loop 转不转得起来，先看它的输入信号有没有在动手写脚本之前就定义清楚——配音质检只是拿来验证这句话的一个例子。

开篇契约：上一课（第 06 课·验证信号流向谁）交付了一张填完第 4 列的验证信号去向表，学员知道哪些格子该交给机器；本课输入是这张表里标"机器"的那些格子，加上学员自己第 03 课写、第 04 课起持续在用的 `pipeline/2-create.md` 步骤 3 和 `brain/tts.config.json`；本课产出一件东西：一张配音批次检查点表（六项：量什么 / 怎么量 / 阈值 / 谁来判）。

### 1. 检查点候选：从「该交给机器」的格子倒推
- 核心判断：检查点不是先想清楚要测什么再列出来的，是倒着从"哪些验证格子标了机器"这件已定的事往回问出来的。
- 二级标题：不分
- 交付物：
  ```
  Prompt：读我 pipeline/2-create.md 步骤 3（配音批次质检）和第 06 课那张验证信号去向表里
  标"机器"的格子，列出配音批次质检可能覆盖的候选检查点清单，每条一句话说清"测的是什么"，
  先出清单不写脚本。
  ```
- 学员此时手上有：第 06 课交付的验证信号去向表（第 4 列已填完）；自己第 03 课写的 `pipeline/2-create.md`（第 04 课起持续在用）
- 交接：候选清单列出来了，但里面混着"能自动判"和"只能人看"两种，得先分开，不然量出来的数字没人知道该不该信。

### 2. 三条判据：能不能现在写成一句断言
- 核心判断：一项检查该不该进这一轮 Loop，看的不是它重不重要，是它此刻能不能被写成一句"是/否"的断言。
- 二级标题：不分
- 交付物：
  ```
  Prompt：把上一步的候选清单按三类分：①能写成断言的（客观可测，如时长/存在性/文本是否一致）；
  ②只能靠人看的（语气/观感这类主观判断）；③现在写不了但以后能写的（缺数据源，如"是否押中热点"）。
  每条给一句话说明属于哪类、为什么。
  ```
- 学员此时手上有：上一节产出的候选清单
- 交接：分完类，"能写成断言"这一类才是这节课真正要交的六项，剩下两类只讲道理没有产出，不算这一课的活。

### 3. 六项检查点定案，以及 overrides 落在哪
- 核心判断：阈值不是拍脑袋定的数字，是从"错到什么程度会导致返工"倒推出来的；同一件"改动记在哪个文件"的事，前后几课的说法必须是同一个答案，不能各说各话。
- 二级标题：
  - 3.1 六项定案：把"能断言"那类整理成四列表（量什么 / 怎么量 / 阈值 / 谁来判）
  - 3.2 overrides 落点：多音字和单段语速的改动，统一落在 build 内 `tts.config.json` 的 `overrides` 字段（沉淀性规则再回写账号级 `brain/tts.config.json` 模板），不新开别的文件
- 交付物：
  ```
  Prompt：把"能写成断言"的检查项整理成表格，四列：量什么 / 怎么量 / 阈值 / 谁来判；阈值旁边
  写一句这个数字是从哪个真实问题倒推的；再补一句：这批检查项发现的问题，改动都写进 build
  内 tts.config.json 的 overrides 字段，不新建别的文件。
  ```
- 学员此时手上有：分类后的"能断言"清单；自己 `brain/tts.config.json` 里已有的 `overrides` 字段结构（第 04 课交付）
- 交接：六项定案了，表还是表，怎么变成能跑出数字的脚本是下一课的事。

### 4. 从检查点表到可跑的脚本
- 本课做到了什么：把"该交给机器"的格子拆成了六项能写成断言的检查点，量什么、怎么量、阈值、谁来判都定了案，`overrides` 的落点也统一了。
- 还看不到什么：六项检查点现在只是一张表，没有一行代码能跑出数字。
- 下一课补什么：把这六项逐条造成脚本。
- 结尾抛出的问题：检查点表定了六项要量什么。表还只是表，怎么变成能跑出数字的脚本？
