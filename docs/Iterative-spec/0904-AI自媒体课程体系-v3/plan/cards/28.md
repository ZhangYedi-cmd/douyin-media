### 1. AppShell 与两个数据 hook：先立骨架不建页面

- 核心判断：六个页面共用同一套取数逻辑，骨架课先把「怎么拿快照」「怎么听变化」这两件事做成 hook，页面只管拿到数据之后怎么摆。
- 二级标题：不分
- 交付物：一张职责表（AppShell 负责什么 / 快照 hook 负责什么 / SSE 订阅 hook 负责什么）；一条 Prompt 让 AI 实现 AppShell（导航 + 布局）和两个 hook——一个按 URL 拿快照数据，一个订阅 SSE 收到 revision 变化后触发重拉。
- 学员此时手上有：第 27 课的六个快照接口和 SSE 端点；第 27 课的写 API（AppShell 里的导航要能跳到详情页触发写操作）。
- 交接：骨架立起来了，可以往里面摆颜色和第一批页面了。

### 2. theme token 映射：抄设计稿的颜色，不重新配色

- 核心判断：`theme.css` 里的 token 是设计稿唯一的真相源，前端不自己挑颜色，把这些 token 映射进组件库配置就够了。
- 二级标题：不分
- 交付物：一张映射表（`theme.css` token 名 / 组件库配置项），至少覆盖强调色、成功/警告/危险色、圆角、字号；一条 Prompt 让 AI 读 `docs/design/css/theme.css` 生成映射代码。
- 学员此时手上有：`docs/design/css/theme.css`（第 26 课发放的课程附带材料）。
- 交接：视觉基调定了，可以落第一批页面了。

### 3. P1 总览、P3 详情：先落头两页

- 核心判断：总览页只做一件事，十秒内告诉人「今天正常吗、有几条在制、有什么要我处理」，不做操作入口；详情页是唯一一个既要展示又要触发写操作的页面，决策区的按钮要按 `allowedTransitions` 动态渲染，不能把状态机逻辑再抄一遍搬到前端。
- 二级标题：3.1 P1 总览：晨检、警报、分级待办 / 3.2 P3 详情：读为主、决策为辅
- 交付物：两条 Prompt——第一条照 `docs/design/overview.html` 的布局落成 P1，数据接第 27 课的 `GET /api/overview`；第二条照 `docs/design/detail.html` 落成 P3，数据接 `GET /api/content/:slug`，决策按钮调用第 27 课的写 API；两组验收清单：P1（警报分级是否可读、SSE 触发一次变更后页面是否自动刷新、空态是否给出下一步动作提示）、P3（非法状态下按钮是否被正确禁用、点击后 SSE 是否推回最新状态、`dry-run` 预览是否先于真正提交展示）。
- 学员此时手上有：第 1 节的 AppShell 与两个 hook；第 2 节的 token 映射；第 27 课的 `GET /api/overview` 与 `GET /api/content/:slug`、写 API。
- 交接：两页可用了，数据层的路子跑通，剩下四页照着补。

### 4. P4 选题池、P5 治理线：照骨架补，界面说人话不说系统话

- 核心判断：这两页涉及的字段最多来自内部技术命名（如触发方式、状态标记），界面文案要按 `07-界面用语对照表.md` 换成工作流语言，不能把契约文档的措辞原样搬上屏幕。
- 二级标题：不分
- 交付物：一条 Prompt，照 `docs/design/backlog.html`、`harness.html` 落成两页，数据分别接 `GET /api/backlog`、`GET /api/harness`，写操作分别接第 27 课的 `backlog-apply`、`apply-proposal` 端点；一张文案核对清单（触发方式、状态词、页面副标题是否按对照表换成中文工作流语言）。
- 学员此时手上有：第 3 节的 AppShell、两个 hook、token 映射经验；第 27 课的 `GET /api/backlog`、`GET /api/harness`、`backlog-apply`、`apply-proposal` 端点；`07-界面用语对照表.md`。
- 交接：选题池和治理线能看能点了，还剩两页。

### 5. P2 看板、P6 数据复盘：只读页面的最后两块

- 核心判断：看板是全局状态的横向铺开，数据复盘是发布之后的效果回看，两页都只读，不接写操作。
- 二级标题：不分
- 交付物：一条 Prompt，照 `docs/design/kanban.html`、`metrics.html` 落成两页，数据分别接 `GET /api/contents`、`GET /api/metrics`；验收清单两点：`metrics` 页在没有复盘数据时是否显示「暂无数据」而不是假装有数据；看板的状态分组是否与总览页的在制统计口径一致。
- 学员此时手上有：第 4 节的两页经验；第 27 课的 `GET /api/contents`、`GET /api/metrics`。
- 交接：六页全部落地，剩最后一步：拼成一个能直接打开、并且验证过读写两条路径的站点。

### 6. 单端口出整站，并验证读写两条路径都通

- 核心判断：开发和生产不是两套部署形态，前端构建产物交给 server 托管静态文件，一个端口就能起整站，不需要额外的反向代理；模块 7 的出口条件不是「页面做完了」，是六页能看、快写和慢作业两条写路径都能从界面上真的走一遍。
- 二级标题：6.1 单端口出整站：前端构建产物由 server 托管 / 6.2 验证：六页可看，两条写路径都通
- 交付物：一条命令块（构建前端 + 启动 server + 打开浏览器验证六页可达）；一份验收清单：①六个页面逐一打开无报错；②在 P3 详情页点一次审批（快写路径），观察状态是否经 SSE 回流到页面；③在 P4 或 P5 触发一次慢作业（如 `apply-proposal`），观察任务面板是否推进到终态；④关掉 server 再重启，六页是否能正常拿到数据（不依赖内存态残留）。出错多半是构建产物路径和 server 托管的静态目录对不上，或者 API 请求被相对路径错误地打到了前端自己的开发端口。
- 学员此时手上有：六页前端代码；第 27 课的 server（读写两条 API）。
- 交接：六页整站跑起来了，这套东西建完了。

### 7. 收尾：整站建完，退一步看它是什么

本课把六页整站做到可用，单端口起站，读写两条路径都在真实界面上验证过；但还不知道这套东西算脚本、算工作流、还是算能自主决策的系统，下一课要给它定一个形态坐标，并给出 1:1 验收报告。

结尾抛出的问题：六页整站跑起来了，这套东西建完了。它到底是个什么形态，哪些出口不能关？
