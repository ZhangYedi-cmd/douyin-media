## 2.1 大纲

记忆锚点：写路径唯一不是设计出来的，是把前十课散落的每一个手改点一个个改喊 media 收出来的。

开篇契约：上一课交付了跑得起来的 core 包和 M1 那批命令；本课输入是执行方案里 M2 的部分，加上前十四课里所有手改真相源的地方；本课产出两件东西：全量 `media` 命令，和一份存量迁移记录。

### 1. 开篇：读写各通一半，还差收敛
- 核心判断：读路径通了、写路径只切了两个历史事故最集中的命令，前面十课手改 `meta.yaml` 的习惯也还散着，这一课把两件事一起补齐。
- 二级标题：不分
- 交付物：一张待办清单（剩余写命令 + `check` 全量规则 + 存量迁移三块）
- 学员此时手上有：第 14 课的 core 包和 M1 那批命令
- 交接：先把剩下的写命令补齐。

### 2. 剩余写命令：flip、next-up、backlog 三命令、metrics record、dashboard rebuild
- 核心判断：这批命令验收标准是 fixture 或真实数据上的具体行为对不对，不是「跑起来不报错」就算过——比如 `backlog add` 撞车条目要被拒收，非撞车要正常入池。
- 二级标题：不分
- 交付物：一条让 AI 按执行方案实现剩余写命令的 Prompt + 逐条验收动作
- 学员此时手上有：第 13 课执行方案里这几条命令的详细设计；第 14 课已跑起来的 core 包
- 交接：写命令全量齐了，进入 `check`。

### 3. check 全量收口：规则怎么问出跨文件漂移，退出码怎么返
- 核心判断：`check` 的每条规则对应一种真实会发生的漂移（比如两层状态不同步、链接迟迟没补），退出码要能让治理线的日巡直接用来判红判绿，不是给人看个热闹。
- 二级标题：不分
- 交付物：一条让 AI 实现 `check` 命令全量规则的 Prompt + check 规则清单（八条规则，各一句判定逻辑）+ 退出码表（0 成功 / 1 规则拒绝 / 2 用法错误 / 3 锁冲突 / 4 解析损坏）
- 学员此时手上有：剩余写命令（本课第 2 节产物）
- 交接：`check` 能跑了，但它检查的是数据本身，管不到「这个状态到底是谁写进去的」，这就是存量迁移要解决的事。

### 4. 存量写点迁移：一处处改喊 media
- 核心判断：判断「谁会写真相源」不能只看文件名，要看动作——学员自己拿编辑器手改 `meta.yaml` 的 `status` 字段，也是一个写入者，扫的时候要把这类「人手」算进去。
- 二级标题：不分
- 交付物：迁移清单表（写点位置 / 原来怎么写 / 现在改成的命令），覆盖 `pipeline/` 五份契约里描述状态翻转的段落，和学员自己手改 `meta.yaml` 的习惯
- 学员此时手上有：`pipeline/` 五份契约；前十四课手改 `meta.yaml` 的真实操作记录；`CLAUDE.md`
- 交接：全部写点都改喊 `media` 了，但「喊了」不等于「真的唯一」，这是下一课要自证的事。

### 5. 收尾：全量齐了，唯一性还没证
- 本课做到了什么、还看不到什么、下一课补什么：全量 `media` 命令跑起来了，存量迁移记录也落盘了；写路径看起来收敛到了一个入口，但这只是「看起来」，还没有证据。
- 结尾抛出的问题：全量命令齐了，存量也迁完了。可你怎么证明写路径真的唯一，而不是自己以为唯一？
