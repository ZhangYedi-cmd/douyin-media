## 2.1 大纲

记忆锚点：读 API 不是又一套解析逻辑，是 core 的 `parsers` 套了一层 HTTP 壳；写 API 也不是重新发明状态变更逻辑，是把 HTTP 请求原样转成一条 `media` 命令——读写两条路径都只做一件事，「多一次真相源」和「多一个写入口」是这一课要防的同一类错。

开篇契约：上一课交付了 `docs/spec/console/` 三份，五包一仓边界和 API 契约都定了；本课输入是第 26 课 `02-执行方案.md` 的 API 清单、`tools/console/packages/core/src/snapshot.ts` 与 `dashboard.ts`（读接口要复用的 parsers）、`tools/console/packages/server/src/jobs/runner.ts` 与 `defs.ts`、第 15 课成稿（唯一写入口怎么立起来的）、第 19 课成稿（飞书回调原先怎么写状态）；本课产出读 API 全通（六个快照 + `file`/`asset`/`health` + SSE）与写 API 全通（快写 4 条 + 慢作业 3 条），且飞书回调改走它。

### 1. 六个快照接口：一页一个，不合并成一个大对象

- 核心判断：六个页面各自只要自己的那份数据，接口按页面切而不是按数据表切，前端才不用自己再拼一次。
- 二级标题：不分
- 交付物：一张对照清单（接口 / 对应页面 / 数据来源）：`GET /api/overview` → 总览页、`GET /api/contents` → 看板页、`GET /api/content/:slug` → 详情页、`GET /api/backlog` → 选题池页、`GET /api/harness` → 治理线页、`GET /api/metrics` → 数据复盘页；一条 Prompt 让 AI 按第 26 课 API 清单逐个实现，读接口内部一律调用 core 的 `snapshot.ts` / `dashboard.ts`，不自己重新解析 YAML。
- 学员此时手上有：第 26 课 `02-执行方案.md` 的 API 清单；`content/`、`brain/`、`harness/` 等真实文件（学员自己仓库前面课攒出来的数据源）。
- 交接：六个页面各有了数据源，但还有几个不属于任何一个页面的通用能力没接。

### 2. file、asset、health：三个基础设施接口

- 核心判断：读任意受控文件、读封面等静态物料、报健康状态，这三件事每个页面都会用到，单独做成横切接口，不塞进六个快照接口里。
- 二级标题：不分
- 交付物：一条 Prompt，要求 `file` 接口只能读白名单目录内的文件（防止越权读取仓库外内容），`health` 带 revision 号；一张验收清单（越权路径应该被拒绝、`health` 返回值里是否带 revision）。
- 学员此时手上有：第 1 节做出的六个快照接口，作为参照实现风格。
- 交接：单次请求的接口都通了，但状态变化怎么让前端知道还没做。

### 3. SSE 推变更：store、watcher、revision 三件怎么配合

- 核心判断：前端不轮询，靠 SSE 收到「有变化」信号后自己重拉，SSE 本身不推数据，只推一个 revision 号。
- 二级标题：不分
- 交付物：一张时序清单（文件变化 → watcher 感知 → store 重建快照 → revision 自增 → SSE 广播），配一条 Prompt 让 AI 实现这条链路并说明怎么避免同一次变化触发两次推送、怎么避免漏推。出错多半是 debounce 窗口设太短导致连环触发，或者 watcher 没有覆盖到某个子目录。
- 学员此时手上有：第 1、2 节做出的六个快照接口和 `health` 接口（SSE 断线重连后靠 revision 判断要不要重拉）。
- 交接：读路径全通了，下一步做写路径。

### 4. 快写 4 条：把点击翻译成一条 media 命令

- 核心判断：审批、打回、选题裁决这几个动作背后就是一条已经存在的 `media` 命令，写路径不重新发明状态变更逻辑，只是把 HTTP 请求原样转成 `execFile media <子命令>`。
- 二级标题：不分
- 交付物：一张映射表（端点 / 背后命令 / 触发场景）：`POST /api/actions/review` → `media flip`、`POST /api/actions/backlog-apply` → `media backlog apply`、`POST /api/actions/promote` → `media promote`、`POST /api/actions/next-up` → `media next-up set`；一条 Prompt 让 AI 实现这四条，非法状态迁移要把 `media` 报的错误原样透传，不能吞掉重新编一句话。
- 学员此时手上有：第 1 到 3 节的读 API（写完之后要能在读接口里立刻看到变化）；学员自己仓库里 `media` 的全量命令（第 15、16 课交付）。
- 交接：毫秒级的记账动作通了，但有几个动作不是一条命令能完事的。

### 5. 慢作业 3 条：spawn 一次无头 CC，用 job runner 兜底

- 核心判断：确认发布、打回重做、治理提议入库这三件事背后是一次会跑几分钟的判断性任务，不能让浏览器挂起等结果，得先返回一个任务 id，进度靠 SSE 或轮询拿。仓库 `routes/jobs.ts` 实际注册了五个作业端点，本课只讲 `publish`、`rework`、`apply-proposal` 这三条慢作业；`harness-run`（治理线巡检）和 `create`（新条目创建）两个端点不在这一轮 1:1 范围，正文一句话说明即可，不展开实现。
- 二级标题：不分
- 交付物：一张作业清单（作业类型 / 超时 / 成败怎么判）：`publish`、`rework`、`apply-proposal`，成败判定要读 `meta.status` 而不是解析 AI 的自然语言输出；一条 Prompt 让 AI 实现 job runner 的这三类作业。出错多半是把 `is_error==false` 当成成功的唯一依据，没有回读状态文件做二次确认。
- 学员此时手上有：第 4 节的快写端点（部分作业开始前要先走一次快写，比如打回要先 `flip` 到 `drafting`）。
- 交接：写路径两条都通了，但这条线原来是飞书那边在走，现在要把它挪过来。

### 6. 飞书回调改道：第 19 课那个服务不再自己写

- 核心判断：飞书按钮点下去之后的记账动作，原来是飞书那个长连接服务自己改状态、自己 spawn CC，现在改成打这条控制台的写 API，状态写入只留一个入口。
- 二级标题：不分
- 交付物：一条 Prompt，比对第 19 课飞书服务里直接改状态的代码段，改成调用第 4、5 节做出的端点；一条验收动作：飞书审核卡点一次「通过」，观察状态变化是不是经过了控制台的写 API（看 `logs/jobs/` 或审计记录里有没有对应记录），而不是飞书服务自己落的盘。
- 学员此时手上有：第 19 课交付的飞书服务（含长连接收按钮逻辑）；第 4、5 节的写 API。
- 交接：读写两条 API 都通了，接下来该做界面，让人不用翻文件也能点。

### 7. 收尾：读写两条 API 都通了，界面还没影

本课把读 API（六个快照 + `file`/`asset`/`health` + SSE）和写 API（快写 4 条 + 慢作业 3 条）全部打通，`server` 不直接写文件，飞书回调也改走这条路径了；但一个像样的界面都没有，操作还得靠命令行或者飞书卡片，下一课要立前端骨架，落六页整站。

结尾抛出的问题：读写两条 API 都通了。开始做界面，骨架和头两页怎么落设计稿？
