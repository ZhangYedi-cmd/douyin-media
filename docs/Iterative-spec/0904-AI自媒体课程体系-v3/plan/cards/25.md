## 2.1 大纲

记忆锚点：cc-stream 只认识「子进程 stdout 是一串 JSON 行」这一件事，不认识任何调用方的业务概念；裁决只读文件出结论，不信进程自述——这两条合起来才是「无人值守」的完整定义：既要能自己跑，也要能自己说清跑得对不对、什么时候该停。

开篇契约：上一课交付了任务注册表、四个治理 skill 和一轮巡检记账，两条线都能跑通了；本课输入是学员已有的 `media` 命令、`douyin-publish`/`douyin-retro`/`douyin-ideate` 等 skill（可以拿来当「被观察对象」）、`media` CLI core 包里已有的锁与原子写逻辑（第 12 到 16 课）；本课产出三件东西：一个 `cc-stream` 包（六个文件：`index.ts`、`normalize.ts`、`milestones.ts`、`spawn.ts`、`transport.ts`、`types.ts`）、一个裁决函数、一套收尾策略，加一次 `claude -p` 跑通。**本课只造这些标准件本身，凡涉及「谁来调用它、装进哪个常驻进程」的地方，指的都是你将在模块 7 造的那个进程——学员此时还没有 console。**

### 1. 三层解析：从 JSON 行到里程碑
- 核心判断：一条 headless 输出的 JSON 行要经过三层加工——原始行、归一事件、里程碑——每层只做一件事，业务知识留在最外层的调用方，引擎本身不掺和。
- 二级标题：不分
- 交付物：三层职责对照表（层 / 输入 / 输出 / 是否认识业务）
- 学员此时手上有：本课首次引入 cc-stream，输入是前面各课已经跑通的、可以拿来当「被观察对象」的 skill（`douyin-publish`/`douyin-retro`/`douyin-ideate`）
- 交接：三层定完，先把最底下这层——事件怎么归一——的形状钉死

### 2. 七种归一事件与三档信任分级
- 核心判断：`say` 和 `thinking` 只展示、永不驱动任何判断，`tool`/`toolDone` 驱动步骤时间线，只有落盘文件才是终局裁决——这条信任分级错了位，AI 的自述会被当成事实。
- 二级标题：不分
- 交付物：七种事件对照表（`started`/`tool`/`toolDone`/`say`/`thinking`/`stalling`/`done`，各自：驱动什么 / 是否只展示）+ prompt 生成 `types.ts` 与 `normalize.ts`
- 学员此时手上有：第 1 节的三层职责表
- 交接：事件归一好了，怎么从事件流里认出「走到哪一步了」

### 3. 里程碑引擎：声明式规则，业务知识留在外面
- 核心判断：里程碑表由调用方注入，引擎本身不认识任何一条规则的业务含义——换一个任务类型，只用换规则表，不用改引擎。
- 二级标题：不分
- 交付物：一张示例里程碑表（拿治理线巡检举例：读任务卡 → 执行技能 → 产报告 → 记账四步）+ prompt 生成 `milestones.ts`
- 学员此时手上有：第 2 节的七种归一事件
- 交接：引擎齐了，剩下的是怎么真的拉起一个无头进程喂给它

### 4. 拉起无头 claude -p：三个坑与一次真跑
- 核心判断：headless 模式下 OAuth token 容易被误当 API key 传进子进程环境，子进程可能卡在某个工具调用里装死，stdout 必须按行解析不能整体读——这三个坑不排掉，无头作业跑不稳；六个文件拼不拼得起来，拿一次最小任务真跑一遍就知道。
- 二级标题：4.1 三个坑（认证 / 超时 / 输出流）/ 4.2 一次真跑验证
- 交付物：prompt 生成 `spawn.ts`、`transport.ts`、`index.ts`（导出面）+ 一次真实 `claude -p` 最小任务的跑通记录（prompt 内容、`allowedTools` 白名单、看到的归一事件序列）
- 学员此时手上有：第 2、3 节的 `normalize.ts` 和 `milestones.ts`
- 交接：cc-stream 包六个文件齐了，能吐出正确的事件流；跑完算不算成功，还得有人拍板。

### 5. 只认文件的裁决，加上守住并发的锁
- 核心判断：子进程说「我成功了」和文件真的落到预期状态是两件事，裁决必须复读文件，不能读进程自述或退出码——这和第 09 课「判的人不能改」是同一类约束的第二次出现；同一条内容不能被两个进程同时改，锁不是排队机制，是拿不到直接报错退出，宁可保守拒绝也不排队卡死。
- 二级标题：5.1 裁决函数：读条目 `meta.yaml` 的 `status`，判它是否落到预期值 / 5.2 单并发与锁：陈旧判据要同时满足「超过时限」和「持锁进程已经不在了」两个条件才能抢占
- 交付物：裁决函数规格表（输入 / 读哪个文件的哪个字段 / 期望状态集合 / 输出 `ok`+说明）+ 锁规格表（锁文件放哪 / 内容 / 陈旧判据的两个条件 / 抢占后要留痕）+ 两条 prompt（一条生成裁决函数，一条复用/扩展学员自己 `media` CLI core 包里已有的锁逻辑）
- 学员此时手上有：第 4 节 cc-stream 的 `done` 事件（`ok` 只是第一道信号）、`media flip`/`media st` 等命令认识的合法状态值（`core/state.ts`）、第 12 到 16 课造的 media CLI core 包（写事务里已经有锁与原子落盘）
- 交接：裁决和并发管住了，进程本身怎么正常收尾、收不住的时候怎么恢复，还没定。

### 6. 收尾策略：先礼后兵，加恢复规则：内存不可信
- 核心判断：超时不能直接一记强杀——先发终止信号给收尾机会，等一段宽限期仍不退才补杀，粗暴强杀会留下半写文件和收不回的孤儿进程；内存里的任务状态同样不可信——它会随进程一起死掉，真相必须活在文件里，人工取消和意外重启都靠这条原则兜底。
- 二级标题：6.1 收尾时序：SIGTERM 先给宽限期，仍不退再 SIGKILL / 6.2 恢复规则：触发场景、内存态怎么处理、从哪个文件兜底重建结论
- 交付物：收尾时序表（信号 / 等待时长 / 下一步）+ 恢复规则表（触发场景 / 内存态怎么处理 / 从哪个文件兜底重建结论）+ 一条 prompt 扩展第 4 节 cc-stream 的进程终止逻辑，补上「宽限期后仍未退出再补杀」这一段
- 学员此时手上有：第 4 节 cc-stream 的 `spawn.ts`（目前只有超时路径会杀进程）；第 5 节的裁决函数与锁
- 交接：无人值守这条线该收口了。

### 7. 收尾：无人值守闭环合上之后
- 本课做到了什么：一个不认识任何业务概念的 `cc-stream` 包（三层解析、七种归一事件、里程碑引擎、无头 `claude -p` 跑通），一个只认文件的裁决函数，一套先礼后兵的收尾策略，加一条「内存不可信、真相在文件里」的恢复原则。
- 还看不到什么：整条流水线能无人值守跑完了，但学员只能翻文件和日志才知道它跑到哪，没有一个能看的地方。
- 下一课补什么：第三件重活——给它做一个能看的控制台。
- 结尾抛出的问题：整条流水线能无人值守跑完了，可你只能靠翻文件和日志知道它跑到哪。第三件重活：给它做个能看的控制台。
