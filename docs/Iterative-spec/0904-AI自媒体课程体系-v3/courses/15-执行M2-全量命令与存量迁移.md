# 执行 M2：全量命令与存量迁移

第14课交出了两样东西：跑得起来的 core 包（`parsers`、`state`、`writer` 三部分，带往返测试），和 M1 那批命令。读命令这边，`st`、`next`、`backlog ls`、`doctor` 四条已经跑通，只有 `check` 被单独留了下来，跟写命令一起放到这一课补。写命令这边，M1 只做了 `promote`（取题记账）和 `publish-done`（发布收尾），选它们两个打头，是因为这两处是过去最容易出岔子的地方：发布收尾要一次改对三处文件，漏一处就对不上账；取题记账牵着 `backlog.yaml` 和 `meta.yaml` 两张表，两边脱节了也没人立刻发现。剩下七条写命令和 `check` 的八条规则，加上前十课攒下的一堆手改习惯，这一课一起收。

## 2. 剩余写命令：flip、next-up、backlog 三命令、metrics record、dashboard rebuild

这七条命令不是七件孤立的小活。`flip` 管单条内容的状态翻转；`next-up` 让人可以指定下一次取题拿哪一条；`backlog add`/`sweep`/`apply` 三条一起管选题池的进出：新增、机械清扫、人审通过后落地；`metrics record` 把复盘拉回来的数据记进账本；`dashboard rebuild` 手动重建看板的机器区，平时用不上，出问题时兜底。第13课的执行方案里，这七条已经拆过四件套（参数、读什么、写什么、失败怎么报），这一课让 AI 按那份方案把代码写出来。

### 2.1 七条命令要不要走完整事务

第13课写方案的时候留过一个问题：每条写命令要不要走完整事务，也就是拿锁、算写计划（把这次要改哪个文件、改哪个字段、改成什么值先列成一张清单，落盘前全部算完）、支持空跑预演、原子落盘、写审计记录这一整套，还是只改一处字段就够。这个问题现在有了答案，答案跟直觉不太一样：七条命令，不管改一处字段还是牵动好几个文件，全部走同一套事务引擎，没有例外。

`flip` 看起来最轻，只改一个状态字段加一个时间戳，可它照样拿锁、照样在 `audit.jsonl` 里留一行；`dashboard rebuild` 看起来最重，要把全仓的状态重新扫一遍再重写整块机器区，走的还是那同一套引擎。这套引擎就是第14课交出来的 core 包里 `writer` 那部分，`promote` 和 `publish-done` 已经在用它了，这一课要做的只是让剩下七条命令的写计划各自接进这同一个入口，不需要也不允许另开一条轻量通道。

拿 `flip` 举个更具体的例子，看这套引擎到底替每条命令兜了什么底。翻转一次状态，除了把 `status` 字段改成目标值，还要在时间戳记录里补一行。如果这个状态之前已经盖过一次时间戳，同一条内容再翻回这个状态，不会覆盖旧值，第一次的时间为准，后来重复经过的历史留在 `audit.jsonl` 里，不留在 `meta.yaml` 本身。落盘这一步也不是直接改原文件，是先写一份临时文件，再整体改名替换掉原文件，防的是有程序正好在这个时间点读到一半写一半的文件。首次时间不覆盖、变更历史进审计记录、落盘用临时文件加改名，这三条不是 `flip` 一条命令专属的讲究，是那套事务引擎自带的，`backlog sweep`、`metrics record` 一样用得上，写一次，七条命令全部有。

为什么不给单字段的命令开个近道。如果 `flip` 可以绕过锁和审计直接改文件，写路径就有了两条实现：一条留痕，一条不留痕。等到下一课要证明写路径唯一，靠的就是审计记录能不能覆盖每一次变更，一旦有条命令走了近道，这句话立刻站不住。留着事务这层麻烦，图的是审计记录不会漏掉任何一条改动，跟哪条命令改动大改动小没关系。

第11课钉死的执行方案模板，第2节固定是命令详设，节名节序不许改，所以下面这条 Prompt 里的第2节，就是你自己那份 `02-执行方案.md` 里的第2节，不用现找。

```
读 docs/spec/media/02-执行方案.md 第2节里 flip、next-up、
backlog add、backlog sweep、backlog apply、metrics record、
dashboard rebuild 这七条命令的四件套（参数/读什么/写什么/失败怎么报）。
按这份方案把七条命令实现出来，接进已有的事务引擎（拿锁、算写计划、
支持 --dry-run、原子落盘、写审计记录）：
1. 每条命令都要走完整事务，不允许因为只改一处字段就跳过锁或审计
2. 失败时按方案里写的错误类型报错，退出码按已有的错误码表映射
3. backlog add 的撞车判定、backlog sweep 的 --dry-run 与 --apply
   两种模式、next-up 只能指向未取用状态的条目，这三处按方案里定的
   规则实现，不要自己简化
实现完之后，把每条命令的 --help 输出贴给我看一眼。
```

拿到结果先看两处：七条命令是不是都在调同一个事务引擎的入口，而不是各写各的落盘逻辑；每条命令的 `--help` 是不是把参数和失败情形都印出来了，不是一句空泛的用法说明。

### 2.2 验收要盯行为不是盯报错

命令跑起来不报错，不代表它对了。这批命令的验收标准要落到具体行为上，不是一句能跑就算过。挑几条最容易被糊弄过去的，具体说说该怎么验：

`backlog add` 输入一批候选选题，判重规则是标签交集至少两个，或者没有标签命中时退化成标题子串加链接完全重合。验收要真的准备一份候选文件，里面故意放一条跟已有条目撞车、一条完全不撞车，跑完看结果：撞车的那条要被拒收，不撞车的那条要正常入池，编号要接着已有条目往后排，不能跳号也不能重号。如果想手动放行某条撞车的候选，命令要支持指定放行第几条，跑一遍确认放行的那条真的进去了，没被放行的那条还是拒收。

`backlog sweep` 有两种模式，缺省是预演，加参数才真的落盘。验收要先跑一遍预演模式，记下会被清扫掉哪几条；再跑一遍真落盘模式，比对结果跟预演时看到的是不是一致，不能预演说清三条，真跑的时候清了四条或者只清了两条。清扫留痕的注释要写在状态行后面，不能光改状态却不留任何说明这是被规则清扫的，不是人手动清的。

`next-up` 只能指向还没被取用的条目，验收要故意拿一个已经取过题的条目 ID 去设置指针，看它是不是老老实实报错拒绝，而不是把指针设过去之后放着不管，让下一次取题的人稀里糊涂拿到一条根本不该拿的题。

`metrics record` 记一次复盘数据，不管拉的是 24 小时、72 小时还是 7 天的窗口，都会往日志文件里追加一行，但只有 7 天这个窗口的数字会回填进选题池对应条目的字段，另外两个窗口只留痕在日志里，不回填。验收要故意跑一次 24 小时窗口的记录，确认它进了日志文件，选题池那条对应条目没有任何字段被改动；再跑一次 7 天窗口的记录，才应该看到字段真的更新了。如果这一步图省事把三个窗口都设成回填，看起来更省事，实际是把日志和选题池这两张表混成了一张，以后想知道某个数字到底是随手记的还是正式认下的，就分不清了。`backlog apply` 落地人审通过的提议，动作分合并和归档两种，验收要各跑一次：合并要看目标字段是不是真按提议内容改了；归档要看条目状态是不是翻到了对应的终态。两种动作各有各的校验逻辑，不能共用一段代码就以为两边都测过了。

`dashboard rebuild` 平时用不上，因为别的写命令写完自己就会顺手把看板机器区那一小块刷新掉，这条命令是全量重来一遍的手动兜底，用在机器区跟真相源对不上、需要整块重算的时候。验收要故意在机器区手动改错一个字段，跑一次 `dashboard rebuild`，看它是不是照着真相源把整块机器区覆盖掉，而不是只挑着修正被改错的那一个字段。只修一处的话，说明它实现成了增量更新，跟这条命令全量重建的定位不符，出问题的时候没法保证靠得住。

如果 `backlog add` 把两条明显重复的候选都收了进去，多半是判重逻辑只比对了标题，没有把标签交集和链接重合这两条退化规则一起接上。这种问题不会在跑命令的时候报错，只会在选题池里悄悄多出一条废条目，隔几天才会被人发现，所以验收这一步不能省，得真的拿真实数据跑一遍看结果，不能光看命令退出码是不是零。

七条写命令这边算是过了关，接下来是唯一的读命令 `check`。

## 3. check 全量收口：规则怎么问出跨文件漂移，退出码怎么返

`check` 跟前面七条不一样，它不改任何文件，只读。但它读的东西比别的命令都多：要把 `meta.yaml`、`backlog.yaml`、`dashboard.md` 全部扫一遍，拿八条规则去问一句话：这几处状态是不是真的对得上。

### 3.1 八条规则各管一类问题

八条规则不是随手拍出来的，每一条对应一种真实会发生的漂移。有的是两层状态记账没对齐，有的是条目断了链，有的是超时没人回填，有的只是提醒快到期了。第13课的执行方案里已经把这八条列过一遍，这一课要把判定逻辑落实到具体阈值：

| 规则 | 级别 | 判定什么 |
|---|---|---|
| CHK-01 双层不同步 | error | `meta.yaml` 的状态和 `backlog.yaml` 的状态没对上 |
| CHK-02 断链 | error | `backlog` 是已取题状态，但对应目录或元数据缺失 |
| CHK-03 超时未回填 | error | 定时发布的状态停留超过 24 小时没人回填结果 |
| CHK-04 审核积压 | warn | 停在审核状态超过 48 小时没人处理 |
| CHK-05 链接待补 | warn | 已发布但没有回填作品链接 |
| CHK-06 指针断裂 | warn | 元数据里的来源指针和选题池对不上 |
| CHK-07 临近过期 | info | 选题在 2 天内会被清扫规则命中 |
| CHK-08 疑似空跑 | warn | 到了当天 21 点还没有新内容，也没人上报 |

CHK-06 里说的来源指针，指的是 `meta.yaml` 里记着这条内容是从选题池哪一条候选取来的那个字段，跟选题池那条候选反过来记着自己被取用到了哪个内容目录，是同一对指针的两头，两头对不上号就是断裂。八条，不是七条，这是第13课就提醒过的地方，写自己的规则时拿这张表逐条核对，别凭印象数。CHK-01 和 CHK-02 是错误级，因为它们意味着两张真相源已经互相矛盾，不修就没法信；CHK-04、05、06、08 是警告级，意味着有事需要留意但不算数据坏了；CHK-07 是提示级，纯粹是给人多一点准备时间。三个级别对应三种不同的处置紧迫程度，这个分级不是写着好看，下一小节退出码要靠它来分辨该不该报红。

```
读 docs/spec/media/02-执行方案.md 里 check 命令对应的八条规则
（CHK-01 到 CHK-08），把判定逻辑实现出来：
1. 规则判定单独放一个模块，只吃仓库当前状态、不碰文件系统，方便以后
   被看板一类的其它读者复用，不要把判定逻辑直接堆进命令入口里
2. 每条规则给出 rule 编号、级别（error/warn/info）、subject（哪条内容
   或哪条选题）、message（说清楚具体哪里对不上）
3. 阈值先用方案里给的默认值：CHK-03 用 24 小时、CHK-04 用 48 小时、
   CHK-07 用 2 天、CHK-08 用 21 点，都做成可配置参数，不要写死
4. check 命令本身不拿锁不写审计，因为它只读，跑完按 error 数量决定
   退出码
跑完给我看一次真实仓库上的输出，八条规则各触发几次列出来。
```

八条规则跑出来的结果，要拿真实仓库现在的内容去对，不能只用一份编好的样例数据。样例数据配合度太高，八条规则随便写写都能全部放行，只有真实数据里那些没被想到的边角情况，才能看出规则漏没漏。

### 3.2 退出码给谁用

`check` 的退出码不是给人看个热闹，是给治理线的日巡用的。日巡是个定时跑的程序，它不会去读 `check` 打印出来的那一堆文字，它只认退出码：

| 退出码 | 含义 |
|---|---|
| 0 | 成功，规则全部通过（没有 error 级） |
| 1 | 规则拒绝：有 error 级条目，或者写命令的校验没通过 |
| 2 | 用法错误：参数拼错、必填参数没给，命令行解析这一层就报了 |
| 3 | 锁冲突：另一个写命令正占着锁 |
| 4 | 解析损坏：`meta.yaml` 或 `backlog.yaml` 本身就是坏的 YAML，读不出来 |

这张表里有个容易想岔的地方：退出码只认 error 级，warn 和 info 再多也不会把退出码从 0 变成 1。这不是漏做了，是故意的。八条规则里 warn 占了四条，如果 warn 也拉高退出码，日巡程序天天都在报红，时间长了没人会真去看这条报警，反而把真正的 error 埋没在一堆噪音里。退出码要留给真正需要立刻处理的问题，warn 和 info 是给人看的参考信息，写在打印输出里，不进退出码的判断。

退出码 3 只出现在写命令上，`check` 本身不拿锁，因为它只读，不会跟别的写命令抢同一把锁。这也带出退出码 3 背后一个容易被漏掉的问题：占着锁的进程如果已经不在了，锁要不要一直占着不放。第12课的 ADR 选并发保护用文件锁的时候，这个问题就该有了答案，第13课的执行方案里应该已经给了一个具体的秒数：锁被占用超过这个时长，且持锁进程确认已经不在了，新来的命令才会把它当成一把陈旧锁抢占过去，抢占之前先打一行提醒，不会悄悄抢过去不留痕迹。正常情况下一条命令从拿锁到释放常常只要几十到几百毫秒，真出现要抢占陈旧锁的情况，多半是上一个命令的进程被强行终止了，没走到释放锁那一步就没了。

退出码 4 意味着连状态都读不出来，这种情况下别的规则也没法判定，直接停在解析这一步报错，不硬凑一个结果出来。

如果 `media check` 跑完报了好几条 error，退出码却还是 0，多半是退出码判断漏了按级别过滤，把 error、warn、info 三类条目一起算了数量，而不是只数 error 这一类。这个问题在样例数据上不容易暴露，因为样例数据往往每种问题只放一条，凑巧总数和 error 数一样，得拿真实仓库里 warn 比 error 多的情况去试一遍才能露出来。

`check` 能跑了，但它检查的是数据本身，管不到这个状态到底是谁写进去的。这就是存量迁移要解决的事。

## 4. 存量写点迁移：一处处改喊 media

从第03课起，学员就在手改 `meta.yaml` 的状态字段，那时候 `media` 还不存在，手改是唯一的办法，也是第10课成稿里明说过的临时手段。现在十四条命令全齐了，这个临时手段该收了。

### 4.1 先扫，人拿编辑器改也算一个写入者

扫写点不能只看文件名，要看动作。一个动作只要改了 `meta.yaml`、`backlog.yaml` 或者 `dashboard.md` 机器区里的任何一个字段，它就是一个写入者，不管这个动作是一段代码执行的，还是人打开编辑器手敲的。前一种容易发现，`grep` 一下 `fs.writeFileSync` 或者类似的调用就能找到；后一种最容易漏，因为它不留代码痕迹，只留在 `pipeline/` 契约文档里一句像是说明书的话，或者干脆只留在学员自己的记忆里。

学员自己的 `pipeline/2-create.md`，经第07、09、10课陆续补写，已经定下配音审批的规则：批次质检最多跑三轮，第三轮还是不过，就停下来升级人审，质检报告记进 `3-review.md`，`meta.yaml` 这边留一句说明，标记这条内容现在卡住了。这里藏着一个写入动作：挂起不是什么都不做，是有人打开 `meta.yaml`，往里面加一点说明。但这个动作跟状态翻转不是一回事：状态本身没变，还是原来那个状态，变的是有没有人往文件里多写了一笔。

这一条不能直接套进现成的九条写命令里去。`flip` 管的是状态从一个值翻到另一个值，挂起的时候状态压根没翻，硬套 `flip` 会撞上非法迁移的校验，直接被拒。碰到这种情况，AI 该做的不是自己悄悄挑一个解决办法糊过去，是老老实实报出来：这一条没有对应的写命令，有两条路可选，一条是继续保留人工编辑，但明确写清楚这是唯一被允许的例外；另一条是给 `meta.yaml` 加一个专门记挂起原因的字段，让下一次 `flip` 顺手把这个字段也带上。这个判断留给学员自己拍板，不是 AI 替学员决定。

这类分歧不止挂起一种。参考流水线的状态机定义里有一条被正式认下来的人工例外可以拿来对照：内容发布并且复盘完成之后，状态会停在 `retro_done` 这个终态；如果之后要人工恢复它的可见性，翻回 `published`，这条路径不进状态机的合法边表，明确留给人工编辑。这条例外之所以站得住，是因为它被写进了状态机的定义本身，谁都能查到这是唯一允许手改的地方。你自己第13课那份迁移表未必留了这一条，如果也要留这类例外，照这个样子写进定义本身，不能只停在嘴上说说。挂起不是这样，它现在只活在一份契约文档的字里行间，没有任何一处代码或者规则承认过它是例外。存量迁移要做的，就是把这种没被承认过的暗门，要么收进某条命令里，要么正式写进定义里承认下来，不能任由它继续悄悄活在文档缝里没人管。

```
扫一遍以下位置，找出所有会改动 meta.yaml、backlog.yaml 或
dashboard.md 机器区的地方，不管是代码里的写操作，还是文档里描述
的人工编辑动作：
1. pipeline/1-ideate.md、2-create.md、3-review.md、4-publish.md、
   daily-run.md 五份契约里描述状态翻转的段落
2. content/_template/meta.yaml 和 content/_backlog/backlog.yaml
   里关于状态字段的注释
3. CLAUDE.md 里跟状态记账相关的条款
每一处列出：写点位置、原来怎么写的、这个动作能不能直接对应到
media 的某条命令。对不上号的，不要自己选一个方案，原样报出来
让我决定。
```

拿到清单先看有没有报出对不上号的条目。如果 AI 把所有写点都判成了能直接对应某条命令，多半是它把有分歧的地方按最省事的方式悄悄归了类，回头拿第10课定下的那条挂起写法（三轮不过，`status` 留在 `drafting`，另加一行说明）去对一遍，看它有没有被漏掉或者被强行套进了某条命令里。

### 4.2 逐个改喊 media

清单里能对上号的那部分，改起来是体力活。挑几处有代表性的：

| 写点位置 | 原来怎么写 | 现在改成 |
|---|---|---|
| `content/_template/meta.yaml` 状态字段注释 | 描述状态由人工维护的一句说明 | 状态只经 `media` 命令翻转，不手编；合法状态与迁移见 `media flip --help` |
| `content/_backlog/backlog.yaml` 头部注释 | 描述选题池状态含义的一段说明 | 合法状态值唯一定义见 `state.ts`；`backlog` 只在取题和发布完成两个时点翻动，均经 `media` 命令记账 |
| `pipeline/2-create.md` 质检全部过之后 | 手写状态翻至审核加更新看板 | 改成调用 `media flip <slug> review` |
| `pipeline/daily-run.md` 取题记账段 | 手写选题池状态迁移加建目录 | 改成调用 `media promote` |
| `CLAUDE.md` 状态记账条款 | 只说状态记在各自的文件里 | 补一句状态记账唯一入口是 `media`，其它环节不代翻 |

这张表里前两行是最容易被忽略的一类：它们不是流程文档，是模板文件本身的注释。学员第03课写这两份模板的时候，`media` 还没造出来，注释里大概率写的是一句提醒自己按规矩改状态的话。现在这句提醒本身也该跟着换，不然新建一条内容的时候，模板文件第一眼告诉人的还是旧办法，跟契约文档里写的新办法对不上，又制造出一条隐性的第二条路。

```
按上一步扫出来的清单，逐条改：
1. 能直接对应某条 media 命令的，把文档里的手改描述换成调用
   对应命令，注明参考哪条命令的 --help
2. content/_template/meta.yaml 和 content/_backlog/backlog.yaml
   的状态字段注释，改成说明状态只经 media 命令翻转
3. CLAUDE.md 补一句状态记账唯一入口是 media
4. 对不上号的写点（比如挂起类），先不动，等我给出裁决再改
改完之后，把改动前后的对照贴给我看，不要只说改完了。
```

改完之后，把这份清单和改动对照一起存下来，就是任务要交的存量迁移记录。

### 4.3 参考流水线是怎么迁的

这一步的迁移不止是改文档，等真正接上飞书闸口（那是17到19课的事），代码里也会有真正调用 `media` 的地方。参考流水线里有个现成的例子，可以先看一眼，提前有个数，但不是这一课要动手做的事：飞书审核卡回调的代码原来直接改一段脚本，用正则匹配去改状态字段那一行；后来换成了调用 `media flip`，还额外带了一个身份参数，让审计记录能分清这次改动是审核卡触发的，不是人在命令行里直接敲的。原来那段直接改文件的代码后来被拿掉了，只剩下几个读数据的函数。

这个例子说明的道理很简单：以后不管接哪个新的触发方式，迁移的做法都是同一套，把原来直接改文件的代码，换成调用同一条 `media` 命令，把是谁触发的这个身份信息一起带进去。不是每接一个新触发方式就重新发明一套写法。这一课不布置这个任务，因为学员现在手上还没有飞书闸口，没有东西可迁，先记住这个例子长什么样就够。

全部写点都改喊 `media` 了，但喊了不等于真的唯一，这是下一课要自证的事。

## 5. 收尾：全量齐了，唯一性还没证

这一课结束，全量 `media` 命令跑起来了：五条读命令加九条写命令，十四条全部能用；`check` 的八条规则也补齐了，退出码能让日巡自动判红判绿；前十四课散落的手改点，能对上号的都改成了调用某条命令，对不上号的也留了一份清单等着裁决。

每条写命令走事务引擎的时候，都会往 `audit.jsonl` 里追加一行记录，理论上这行记录应该覆盖到全仓每一次真正的状态变更。这句话现在还没有人拿真实数据去验证过：接下来这几天里，`meta.yaml`、`backlog.yaml`、`dashboard.md` 机器区的每一次改动，是不是真的都能在 `audit.jsonl` 里翻出对应的一行，没人跑过这一遍。

全量命令齐了，存量也迁完了。可你怎么证明写路径真的唯一，而不是自己以为唯一？
