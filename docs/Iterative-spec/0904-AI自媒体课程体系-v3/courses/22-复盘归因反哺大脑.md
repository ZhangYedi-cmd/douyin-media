# 复盘归因：只定位漏在哪一环

上一课把治理线的骨架立住了：`harness/README.md`、`harness/tasks.md`、`harness/report-template.md` 三份文件到位，一张资产读写表把哪条线能读哪份资产、能不能写、改动要不要过人审钉成了表格，不再靠记忆。骨架立完，第 21 课收尾时留了一句话：治理线的骨架和读写边界画好了，第一个治理任务是复盘。数据怎么拉、怎么归因、提议怎么写？这一课接的就是这句话。

这一课的记忆锚点是：复盘只回答一件事，这条内容漏在哪一环，不是给账号打总分。给账号打总分是把一堆指标揉成一个印象分，好或不好，说不出具体该改哪里；定位漏在哪一环，是先认账这条内容哪些地方做对了，再把力气全部用在唯一一个没做对的地方。这条区分决定了接下来所有的判断都会落在环这个粒度上，不落在内容这个粒度上。

输入是你自己的 `content/_backlog/backlog.yaml`、留空待写的 `brain/benchmarks.md`、第 21 课定的资产读写表。产出两件东西：一个 `douyin-retro` skill，一份真实的复盘报告。

## 1. 传播漏斗：一条内容漏在哪一环

一条内容发布之后，创作者中心后台会给出十几项数字：播放量、完播率、5 秒完播率、封面点击率、2 秒跳出率、平均播放时长、点赞、分享、评论、收藏、主页访问量、粉丝增量。这些数字摆在一起，很容易陷入逐条对比的做法，这条点赞比上条多，那条完播率比均值低，一条一条数，数完了脑子里还是一团数字，说不出这条内容到底哪里没做好。

短视频的分发机制是层层过滤的。把这十几项数字按发生的先后顺序摆一遍，能看出一条清楚的推进顺序：曝光换来点击，点击换来完播，完播换来互动，互动最终换来关注。每一步都是上一步的产物，也都是下一步的前提。没有点击，后面完播、互动、关注全都无从谈起；点击进来了但没看完，互动和关注同样发生不了。这条顺序上，每一环都对应一类具体的制作问题，不是笼统的内容好不好。

| 环 | 量什么 | 对应哪类打法问题 |
|---|---|---|
| 曝光到点击 | 封面点击率 ctr | 封面和标题有没有勾住人 |
| 点击到完播 | 2 秒跳出率、5 秒完播率、完播率、平均播放时长 | 开场留不留得住人、中段节奏拖不拖、信息密度够不够 |
| 完播到互动 | 互动率，点赞、收藏、评论、转发四项加起来除以播放量 | 内容有没有给出共鸣点或明确的价值点 |
| 互动到关注 | 涨粉数、主页访问量、转粉率 | 有没有给出关注的理由、人设钩子强不强 |

参考流水线（这门课参照的一套已经跑起来的抖音自动化实现）的归因模型比这张表拆得更细，这一课按四道转化合并成一张表，先用这张表对照，要不要拆得更细，留给你自己的 skill 去决定。

找漏点的方法只有一条：把每一环的实际数字，跟一条基线比。基线有三种，同类作者百分位，平台白送，创作者中心账号总览页会直接给出你的完播率低于多少同类创作者这类文案；自己的历史均值，`brain/benchmarks.md` 攒起来的；同支柱均值，等你攒了同一支柱的好几条内容才用得上，这一课不展开。你现在 `brain/benchmarks.md` 还是空的，没有历史均值可比，这一课先只用同类作者百分位这一条基线，等复盘攒够几轮，历史均值才会长出来，那是往后几课的事。

找到基线之后，从曝光往关注这条顺序往下比，第一个明显低于基线的环，就是这条内容的主漏点。后面几环再差，也大概率是这个主漏点拖累出来的连带效应，不算各自独立的病。一条内容完播率很低，互动率大概率也不会好看，但互动率低的病因不在互动这一环本身，在前面完播那一环，改互动引导没用，改节奏才对症。

漏斗表定了，接下来要有数据才有东西可定位，这件事值得封成一个能重复跑的工具。

## 2. douyin-retro skill：拉数据、记账、出报告

一条内容一次完整的复盘，做的事情能拆成三段：把数据拉回来，把数据记下来，把归因写出来。这三段值得封成一个 skill，不是图省事，是图能重复跑，24 小时、72 小时、7 天各跑一次，每次跑法要一样，不能这次拉这几项，下次拉那几项。

规格表：三个环节各一行，回答这一步做什么、判据是什么。

| 环节 | 这一步做什么 | 判据是什么 |
|---|---|---|
| 采集 | 去创作者中心把这条内容曝光到关注五环对应的字段拉回来，没有真实播放数据时用附录脱敏样例 | 拉到的是能进一步计算的结构化数据，不是一段网页文案；登录失效要给出明确提示，不能拿空数据继续往下算 |
| 记账 | 拉到一个窗口的数据立刻记一笔，不等归因写完再记 | 24 小时、72 小时、7 天三个窗口各记一次；记账的真实落点要问清楚，不能凭命令名字面意思猜 |
| 产出 | 用 `content/_template/5-retro.md` 写复盘报告 | 报告只点名第一个跌破基线的环，归因写这一环，其余环节用一句带过 |

把这张表口述给 AI，让它整理成 skill：

```
我要给我的仓库加一个 douyin-retro skill,负责单条内容的复盘,分三段:
采集: 去创作者中心把这条内容曝光到关注五环对应的字段拉回来。登录鉴权
  这件事参考我第20课已经建好的 douyin-publish skill 和 pipeline/4-publish.md
  是怎么处理抖音登录的,复用同一套方式,不要另起一套。登录失效要有明确的
  错误提示,不能拿空数据继续往下算。
记账: 每次拉到一个窗口(24h/72h/7d)的数据,立刻调
  `media metrics record <slug> --window <窗口> --json-data '<数据>'`
  记一笔,分析和记账分开,分析被打断数据也已经留痕。
产出: 用 content/_template/5-retro.md 模板写复盘报告,数据快照加归因加
  沉淀动作三段,归因只点名第一个跌破基线的环,不要五环都写一遍。
按这三段整理成 SKILL.md。采集环节如果我仓库里现在还没有可复用的登录方式,
留空并标注待我确认,不要替我编一套。
```

拉数据时如果创作者中心页面跳回登录页，多半是复用的登录状态已经失效，按第 20 课处理登录失败的思路重新处理，不能拿空数据继续往下算。

这条 Prompt 交出去，AI 大概率会顺手把记账这一步写成往一份叫 `metrics.jsonl` 的文件里追加一行，写完就当结论定了。这个说法不算错，但不完整，值得用第二条 Prompt 追问一句，把记账这一步的真实落点问清楚：

```
我们刚才写的 SKILL.md,记账那一步的落点确认一下: media metrics record
这条命令具体会写到仓库的哪个文件、哪个字段? 只回答它代码里实际实现的路径,
不要回答你觉得应该是什么。如果涉及一份叫 metrics.jsonl 的文件,说清楚它跟
backlog.yaml 的 metrics 字段是不是同一份数据,写报告的时候该引用哪一份。
```

真实情况是，`media metrics record` 每次记账都会往 `harness/logs/metrics.jsonl` 追加一行，这是一份审计流水账，你现在的仓库里还没有这个文件，第一次跑这条命令才会新建它。真正要在报告里引用的结构化数据，是只有 `--window 7d` 这个窗口才会回填的 `backlog.yaml` 对应条目的 `metrics` 字段，24 小时和 72 小时那两次只留痕，不回填。AI 写出来的记账步骤如果只提到 jsonl 那份流水账，没说清楚 7 天窗口才回填 backlog 这件事，多半是它只按字面上的命令名猜了一下该干什么。它没有去核对命令的真实行为，第二条 Prompt 就是用来堵这个漏洞的。

skill 造好了，下一步是用一条数据把完整归因走一遍，走顺了再回去跑真的。

## 3. 归因练习：脱敏样例数据怎么用

没有真实播放数据不代表学不了归因方法，这套漏斗定位法认的是数字之间的相对关系，不是账号是谁。本课附录准备了四条脱敏样例数据（`docs/Iterative-spec/0904-AI自媒体课程体系-v3/appendix/22-复盘脱敏样例数据.md`），每条只在一环明显跌破基线，方便先把方法走顺；有自己账号真实数据的，跳过这一节直接用真实数据练。附录里那条基线扮演的是自己历史均值这个角色，方便一次性把方法走顺，真实场景里你现在手上还没有历史均值，第一轮复盘先按第 1 节说的用同类作者百分位。

拿附录里 `sample-completion-leak` 这条数据练一遍：

```
用附录 docs/Iterative-spec/0904-AI自媒体课程体系-v3/appendix/22-复盘脱敏样例数据.md
里 sample-completion-leak 这条数据,对照同一份附录的账号历史均值基线,
按曝光到点击、点击到完播、完播到互动、互动到关注四道转化逐一比较,
找出第一个明显低于基线的环,只归因这一环,写清楚症状、大概率的原因、
下一条内容该改什么。按 content/_template/5-retro.md 的结构写成报告。
```

这条数据里，点击到完播这一段跌得最狠。5 秒完播率 0.33 比基线 0.35 低了 5.7%，完播率 0.010 比基线 0.016 低了 37.5%，点击这一环没掉。互动率和转粉率也比基线低一点，但那是完播差带来的连带效应，不是各自独立的病因，报告里带一句提一下就够。报告只需要写完播这一环：开场没留住人，中段没撑住节奏，播放量 6800 不算小样本，这个判断站得住。

报告如果五环都写了一段归因，多半是没做基线对比这一步，直接把每个数字都当成问题写了一遍。

附录另外两条样例，主漏点落在不一样的环，正好用来核这条规矩站不站得住。`sample-ctr-leak` 那条播放只有 3200，封面点击率 0.08 只有基线 0.16 的一半。点进来的人留得住、看得完、还愿意关注，四道转化里最先跌破基线的是曝光到点击，归因就该落在封面和标题上，不是节奏。`sample-follow-leak` 那条播放 9100，封面点击率、完播、互动全部优于基线，互动率还是基线的两倍多。只有转粉率 9.3% 明显低于基线的 18%，这条内容让人看完了也点赞收藏了，但没给出关注的理由，归因就该落在结尾有没有给关注钩子，不是前面任何一环。同一套方法用在三条不同的数据上，找出来的主漏点各不相同，说明这套方法认的是数字本身的相对关系，不是套死了哪一环。

真实数据还有一层附录数据给不了的东西：判断会随窗口拉长而改。抖音后台的主页访问量数据，发布 24 小时内经常还没同步，24 小时窗口看到 0，多半只是没统计上，不代表真没人点。参考流水线有一条真实复盘记录能验证这一点（`content/2026-07-08/spec-driven-development/5-retro.md`）：24 小时窗口一度判定这条内容涨粉转化弱，7 天正式收口时同一批指标反过来看，转粉表现回到中位以上，问题出在早窗口统计延迟，不是内容本身有变化。别的内容做 24 小时复盘时也会撞上同一个坑，判互动到关注这一环，等 72 小时以后数据稳定了再下结论更稳，24 小时窗口只做数据快照，不急着定性。

## 4. 变更提议与反哺大环第二段

报告写完，里面那句判断，比如这条完播差是因为开场节奏拖，看着已经是结论了，但它现在还不能直接改进 `brain/benchmarks.md`。第 21 课立的那条铁律在这里第一次真正要用上：治理线只产报告和变更提议，人审通过后才回写大脑。原因也是第 21 课讲过的：`brain/benchmarks.md` 是后面每一轮选题打分要读的判断依据，改错了没人发现，等于让系统自己改自己判断对错的标准。参考流水线的 `brain/benchmarks.md` 开头就写着这条规矩：新发现的高赞同类账号、有效打法，由复盘按治理铁律产出变更提议，人审通过后才落地到本表，复盘不自动改本文件。你自己那份现在还空着，这条规矩在你仓库里的落点是第 21 课让 AI 补进 `CLAUDE.md` 的治理线铁律那一节。

记账收口和改大脑是两件事，不要混在一起。这条内容复盘完了，状态要翻到 `retro_done`，这一步走 `media flip <slug> retro_done`，是治理线唯一一次改状态的动作，随时可以自己做，不用等人审，因为翻错了对判断依据没有影响。改 `brain/benchmarks.md` 动的是后面每一轮打分都要用的判断依据，这一步必须停下来等人点头。前者是记账，解决的是这条内容复盘完了没有这件事；后者是判断，解决的是账号打法要不要跟着调这件事，两件事解决的问题不一样，判据也不一样。

变更提议怎么写，对照 `harness/report-template.md` 里的格式：改什么、依据哪条数据、可逆性。用这份格式，把 `sample-completion-leak` 那条报告变成一份提议清单：

```
把 sample-completion-leak 这份复盘报告的归因结论,整理成变更提议清单,
每条按 改什么 / 依据哪条数据 / 可逆性 三项写,对照
harness/report-template.md 的变更提议格式。归因结论只有一条(完播漏点),
提议也只写这一条对应的动作,不要为了凑数额外编。
```

提议清单大概长这样：改什么，写下一条同类选题的开场结构，把结论前置，压缩到五秒内进入正题；依据哪条数据，写 `sample-completion-leak`，5 秒完播率比基线低 5.7%，完播率比基线低 37.5%，为第一个跌破基线的环；可逆性，写可逆，下一条不这么写就是了，不影响已发布内容。这条提议动的是下一条内容怎么写，不去碰 `brain/benchmarks.md` 这份判断依据本身，属于最轻的一类提议。

真要往 `brain/benchmarks.md` 里加一条新打法，门槛要高得多。参考流水线给这件事定过一条起步值：同一个方向要攒够两条以上同向证据才建议钉进去，你自己的门槛可以不一样。单条内容的一次归因肯定够不上改基线这个级别，只够提一条给下一条内容试的建议。播放量掉到三位数的内容，漏斗百分比全是噪音，参考流水线也是这么处理的，这一类数据只登记，不拿来归因。附录里 `sample-small-sample` 那条就是留着示范这种情况的。

单条内容的复盘，到这里做完了。反哺大环还有第三段没讲完：治理线自己的参数要不要跟着复盘结果调，同样要过人审，那是自审那一层的事，不在这条内容的归因范围里。收的是治理线自己的账，不是账号打法的账。

## 5. 复盘做完之后

一个能拉数据、记账、出报告的 `douyin-retro` skill 有了，一份真实，或者用附录脱敏样例练出来的复盘报告也有了。这条内容漏在哪一环，说得清楚，判断也有基线支撑。

复盘管的是已经发出去的内容，管不了还没发的。你现在手上没有正在排队的选题，`backlog.yaml` 打开还是空的，复盘写得再准，也没有下一条内容可以拿这份提议去改。

复盘能把一条内容的成败归因，提议能改大脑。可选题池空了，拿什么内容去发？
