# 裁判与选手分离：把判的人和改的人焊进两个角色

判断权和执行权握在同一个上下文里，裁决就会不自觉地偏向过。要把判的人和改的人拆开，靠的是工具白名单里物理上没有 Edit 和 Write，不是靠自觉。这一课要把这句话变成一份能跑的子代理定义。

上一课交付了全量 `dubbing-check` skill：六个检测脚本（`check-completeness.mjs`、`check-pace.mjs`、`check-silence.mjs`、`check-source-sync.mjs`、`check-pronunciation.mjs`、`check-av-consistency.mjs`）、一个修复用的 `depause.mjs`，还有一份把它们串成检查清单的 `SKILL.md`。数字有了，判断还在你手上：让写稿的那个 AI 自己判自己的活，行不行？这一课把判断交出去，同时把判的人不能改这条约束立起来。本课的输入是这六个脚本和它们的退出码类型，加上你自己第 05、06 课做出来的那条内容的真实配音产物。本课产出两件东西：一份 `dubbing-reviewer.md` 子代理定义，一份真实的判决输出。

## 1. 谁来判：执行和判断不能是同一个角色

第 07 课把六项检查点分过类。真相源不同步、合成不全、段内死气这三项，脚本本身给得出是非结论，谁来判这一格填的是机器。语速离群、多音字读错、组件大字不一致这三项，脚本只给候选，谁来判这一格填的是人。这个人不必是账号主本人每次戴上耳机重听一遍，可以是一个角色，只要这个角色不共享写稿那个上下文，判断就还是独立的。

问题出在同一个上下文里判自己的活。写文案、调注音、跑合成这些动作，都是同一个 AI 在同一段对话里连续做完的。做完之后紧接着让它检查自己刚才的产出，它读到的不再是一批干净的证据，而是掺着自己生成时选过哪条路、为什么这么选的推理过程。这一步实际做的是确认刚才的选择没问题，不会重新去怀疑它。这不是这个模型偷懒或者不诚实，根子在于写和判用的是同一段推理过程，判断的立场从一开始就不独立。

摆成一组对照更看得清楚：

```
反例对照：同一个 AI 既写稿又判自己的活，它对自己刚合成的音频天然有一种这已经很努力了的
倾向，FAIL 的门槛会不知不觉往下调。
正解：拆成两个角色，一个只管改（主回话），一个只管判（子代理），两边看到的都是同一批
客观数字，但判的人不参与改。
```

参考流水线的创作契约把这个分工写得很直接：合成完第一批音频，派 `dubbing-reviewer` 子代理审批质量，职责分离体现在裁判只判不改，修复和重合成都留给主回话。你自己第 03 课写、第 07 课补过落点约定的 `pipeline/2-create.md` 里，配音审批那道闸口现在写了改动记进哪个文件，但还没点出裁判的名字，也没有只判不改这条规则。这一课做完，要把这两条也写进你自己的契约里。角色要分开这件事道理上说得通，但落到子代理定义里，得靠什么让它真的改不了。

## 2. 工具白名单：把不能改焊进定义里

这条约束要焊进配置文件本身，不能只写在提示词里。提示词里写一句裁判不能改文件，裁判的工具列表里如果还留着 Edit 和 Write，这句话就只是一个请求，模型状态一变就可能不当回事。工具列表里物理上没有这两个工具就不一样，裁判想改也拿不到能改的工具，这一条不依赖它记不记得。

参考流水线里已经有一份 `.claude/agents/dubbing-reviewer.md`，这是形状参考，不是你已经有的文件，你自己的 `dubbing-reviewer.md` 得让 AI 起草一份。可以先看看参考文件长什么样。frontmatter 里 name 叫 `dubbing-reviewer`，description 写清楚它只审配音批次、只判不改。tools 一栏只列了 `Bash`、`Read`、`Grep`、`Glob`，没有 `Edit`、`Write`。

```
Prompt：起草一份子代理定义 dubbing-reviewer.md 的 frontmatter：name 叫 dubbing-reviewer，
description 写清它只审配音批次、只判不改，FAIL 由主回话修复重合成，tools 只给 Bash、Read、
Grep、Glob，不给 Edit、Write。
```

拿到结果先审两件事。第一，tools 这一行有没有出现 Edit 或 Write，出现了就是没写对，删掉重来。第二，description 有没有把只判不改这句话说清楚，判断的角色如果连自己的边界都说不明白，后面裁决口径写得再细也没用。

这条约束的边界要说清楚：拿掉 Edit 和 Write，只是拿掉了两个工具，不是把这个角色关进了一个隔离的盒子。Bash 还留在白名单里，Bash 里的重定向照样能把内容写进一个文件，这个课程体系没有做沙盒隔离，没有哪一层技术手段能保证裁判物理上碰不到文件系统。焊进工具列表这一步，拦住的是裁判要不要主动去改这件事本身。Edit 和 Write 从工具列表消失，不用再指望它自己收着；Bash 留着是因为审查动作本身要用它跑六个脚本，这个口子没有被单独封死。补这个口子的办法只有事后核对：跑完一轮判决，回头看一下 `git status`，工作区里不该多出改动就是不该多出改动。如果跑完发现裁判审完之后代码区多了改动，多半是裁判在给出改法的时候顺手用 Bash 敲了一条写文件的命令，不是权限系统被绕过了。回头把这条命令从流程里删掉，比指望权限系统兜底更管用。

权限焊死了，但裁判怎么读六个脚本的结果、判多严，还没定。

## 3. 裁决口径：保守判 FAIL，输出格式钉死

每一次判 FAIL 都要让主回话推倒重来一整轮：改文案、重合成、再判。这个代价不小，所以裁判必须对真问题判 FAIL，对统计假象不判 FAIL。判断标准和输出格式都不能让它临场自由发挥，不然同一批音频换个时间跑，可能给出两份不一样的裁决。

### 3.1 六项检查点各自的裁决口径

六个脚本本身已经分成了两类。`check-completeness.mjs`、`check-silence.mjs`、`check-source-sync.mjs` 这三个跑完会直接给出 exit 1 或 exit 0，这个退出码就是裁决，不用裁判再琢磨。`check-pace.mjs`、`check-pronunciation.mjs`、`check-av-consistency.mjs` 这三个只打印候选清单，退出码不区分对错，候选是不是真问题要裁判逐条辨。

| 检查点 | 脚本 | 口径类型 | 怎么判 |
|---|---|---|---|
| 合成完整性 | `check-completeness.mjs` | 硬门槛 | 段缺失、字节异常或时长异常，脚本 exit 1，直接 FAIL；批量合成偶发接口限流失败，失败段若旧 mp3 还在会被静默保留，这条判据防的是这种情况 |
| 段内死气 | `check-silence.mjs` | 硬门槛 | 段内非句读位置静音超过 0.45 秒，脚本 exit 1，直接 FAIL；0.45 秒是第 07 课定下的起步值，来自参考流水线一次真实返工 |
| 真相源同步 | `check-source-sync.mjs` | 硬门槛 | `audio-segments.json` 每段文本跟对应的 `narrations.ts` 不相等，脚本 exit 1，直接 FAIL；逻辑上要先于完整性检查跑，文案本身不对，数完整没有意义；参考流水线上也有过真实事故：改了口播文案没重新抽取分段文本，连过两轮组件截图检查都没抓出来 |
| 语速离群 | `check-pace.mjs` | 候选 | 脚本按均值和标准差标出偏离段，裁判要看这段文案里有没有较多英文词，比如出现 `query.ts`、`Anthropic`、`QueryEngine` 这类词，念出来实际用的时间会比字数暗示的长，数值偏低是折算方式带来的假象，不算真离群；排除这类假象之后仍然偏离才判 FAIL |
| 多音字读错 | `check-pronunciation.mjs` | 候选 | 脚本按多音字表列出候选，裁判要逐条判断这段语境里该读哪个音；读音覆盖是按整段生效的，一段话里同一个字要读两种音，现有的注音方式治不了，只能改文案，这种情况不是裁判该判 FAIL 就完事的问题 |
| 组件大字不一致 | `check-av-consistency.mjs` | 候选 | 脚本把组件里的中文长句和对应段口播原文并排列出来，裁判要判断这句是逐字呈现的整句还是概念标签，只有整句标题或行动号召对不上才判 FAIL，标签不算 |

段内死气和真相源同步这两项硬门槛，判据都能翻回到参考流水线上真实出过的事故。合成完整性这一项没有对应的具体事故记录，它的判据来自脚本自己防的失败模式：批量合成接口偶发失败，旧文件被误当成新结果留下来。语速、多音字、音画一致这三项，没有能直接给出精确阈值的历史事故，只能靠裁判逐条代入语境判断，这也是它们留在候选这一档、不能直接按退出码判决的原因。

```
Prompt：给 dubbing-reviewer.md 补裁决口径表：完整性、死气、真相源同步三项，脚本判 FAIL
就直接 FAIL；语速离群、多音字、音画一致三项，脚本只给候选，裁判要逐条判断是不是真问题
（比如含英文词的段字面语速偏慢是统计假象，不算真离群）。再钉死输出格式：VERDICT/ROUND/
BLOCKING/NON-BLOCKING/SUMMARY 五段固定结构，BLOCKING 每条必须带可直接执行的改法。
```

### 3.2 输出结构固定

裁判判完之后怎么把结果说清楚，同样不能自由发挥。输出固定成五段。VERDICT 只能是 PASS 或 FAIL。ROUND 记这是第几轮，配合三轮上限用。BLOCKING 列出每一条真问题，格式统一为哪个检查点、哪一段、什么问题、改法是什么，改法必须是能直接照着做的动作，不是重新去分析一遍。NON-BLOCKING 放不阻断但值得看一眼的建议。SUMMARY 一句话总结。

给改法的时候要落在你自己第 07 课定下来的地方。参考流水线里的 `dubbing-reviewer.md` 有的地方把单段调速写成改 `rec/segment-overrides.json`，这是那份参考文件自己的历史说法，跟第 07 课统一的落点对不上。第 07 课已经把这条改动的落点定死在 build 内 `tts.config.json` 的 `overrides` 字段，后面的课不换，因为这是阶段契约定的，操作细节该服从契约。裁判给的改法照这个落点写，一份示例大概长这样：

```
VERDICT: FAIL
ROUND: 1/3
BLOCKING:
- [语速离群] coldopen/2 剔停顿后语速明显偏慢，段内英文词不足一个，非折算假象
  → 改法：build 内 tts.config.json 的 overrides 给该段加 {"coldopen/2":{"speed":1.15}}
NON-BLOCKING:
- 无
SUMMARY: 一处真离群，其余五项过，改完重合成该段再复审
```

定义写完了，得在一批真实配音上真跑一次，才知道它立不立得住。

## 4. 跑一次真实判决

定义写在纸上不算数，得让它真的判一次、拿到一份 PASS 或 FAIL 才算立住。这一步要用到的是你自己第 05、06 课做出来的那条内容，工程目录在 `content/<发布日>/<slug>/build/`，里面有 `audio-segments.json`、按章节分目录存放的 mp3、还有网页演示的 `src/chapters/`。这是真实存在的东西，不是新造的样本。

把上一节写好的 `dubbing-reviewer.md` 放进 `.claude/agents/` 之后，顺手把裁判的名字和只判不改这条规则也补进你自己 `pipeline/2-create.md` 的配音审批那道闸口，再在 Claude Code 主对话里派它去审：

```
用 dubbing-reviewer 子代理，审一遍 content/<发布日>/<slug>/build/ 这条内容的
配音批次，轮次填 1/3，六个检查点全部跑一遍，给出完整的 VERDICT/ROUND/BLOCKING/
NON-BLOCKING/SUMMARY 判决，把结果存进这条内容目录留档。
```

契约补丁写进去之后，以后再翻 `pipeline/2-create.md`，能看到配音审批这一步具体派的是谁、边界在哪，不用回头再问一遍。拿到结果审三件事。第一，六个检查点是不是都跑到了，缺一项就退回让它补跑，尤其是逻辑上该先跑的真相源同步。第二，BLOCKING 里的每一条有没有带可执行的改法，只写了问题没写改法的条目算没写完。第三，如果最后是 PASS，回头核对一下候选类的三项是不是真的被裁判逐条判断过，而不是照抄脚本打印的那份汇总就收工。你自己再戴耳机听一遍成片，如果听着还是觉得有段别扭，判决却是 PASS，多半是 `check-pace.mjs` 打出来的那批候选只被裁判看了均值和标准差，没有逐条判断。得回头在 Prompt 里明确要求它对候选段逐条判断，不能只看汇总数字。

裁判独立了，一次判决能给出 PASS 或者 FAIL。判 FAIL 之后呢，谁去修，修完再判，什么时候停？
