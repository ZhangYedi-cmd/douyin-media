# 后端：读写两条路径

第 26 课把控制台的契约定完了。`docs/spec/console/` 目录下的调研、ADR、执行方案三份文档，把五包一仓的职责分工、六个页面各自需要的接口，都写得很清楚。那一课收尾时留的话是这样的：契约定完，五包一仓边界和 API 清单有了，先把读路径打通，页面才有东西可显示。这一课接的就是这句话：先做读，再做写。

记忆锚点是一句话。读 API 复用 core 包里已有的 parsers，只是在外面套一层 HTTP 壳。写 API 把 HTTP 请求转成一条 `media` 命令，不重新发明状态变更逻辑。两条路径各自只做一件事。多造一次真相源或者多开一个写入口，都是这一课要防住的偏差。

本课的输入是第 26 课 `docs/spec/console/02-执行方案.md` 里的 API 清单，加上你仓库里现有的资产。具体包括几处基础代码和目录。目录包含 `content/`、`brain/`、`harness/` 的真实文件。代码包括第 14 课沉淀的 core 包基础模块（`parsers`、`state`、`writer`），第 15 课建成的 `media` 命令行工具，第 19 课打通的飞书交互服务，以及第 25 课构建的 `cc-stream` 包和裁决函数。有一处背景需要先讲明。参考流水线的 core 包里有一个单独聚合快照的模块。你的 core 包目前还没有这一层，这一课会用 Prompt 引导 AI 补齐它。本课产出是读 API 全通（六个快照接口，外加 `file`、`asset`、`health` 与 SSE 推送），以及写 API 全通（四条快写加三类慢作业）。飞书卡片的回调逻辑也会同步切到这条写路径上。

## 一、六个快照接口：一页一个

六个页面各自只需要专属的数据，接口设计直接按页面维度划分。总览页需要统计在制条数和告警信息，看板页需要按状态分组的内容列表，选题池页需要按评分排序的候选列表，各页面的数据结构差异很大。如果设计成单一大接口一次返回所有数据，前端拿到后还得自行解析拆分，把原本属于服务端的数据组装逻辑压给了前端。这样做虽然减少了接口数量，但代码量并没有减少，反而增加了数据搬运出错的概率。

| 接口 | 对应页面 | 数据来源 |
|---|---|---|
| `GET /api/overview` | 总览页 | 全仓在制条数、告警列表 |
| `GET /api/contents` | 看板页 | 按状态分组的内容列表 |
| `GET /api/content/:slug` | 详情页 | 单条内容的完整信息，含当前允许的迁移 |
| `GET /api/backlog` | 选题池页 | 选题池候选，支持筛选排序 |
| `GET /api/harness` | 治理线页 | 治理任务运行记录 |
| `GET /api/metrics` | 数据复盘页 | 复盘数据 |

六个接口共用同一份底层数据，避免各个接口单独重复读取文件。对于 `meta.yaml`、`backlog.yaml` 和治理线日志，你的 core 包在第 14 课已经有了对应的 parsers 分别解析。这一课需要补充中间的聚合层。也就是用一个聚合模块，把几个 parsers 解析出来的结果拼装成一份完整的仓库快照。六个接口统一从这份快照中提取字段，不需要各自去读磁盘。参考实现里把这一层单独拆成模块，负责集中完成磁盘 IO，只向外层交付内存快照对象。这一课我们让 AI 照着相同的思路给 core 包补齐这一层。模块名称可以灵活定义，核心是收拢读取逻辑，避免在每个接口中重复实现。

详情接口还需要承担一项职责。它要根据 core 包 state 模块定义的迁移表，计算出当前条目允许变更的目标状态，连同响应体一起返回，并标明每项变更是否需要填写原因。下一课构建前端页面时，详情页的按钮直接根据接口返回的状态列表动态渲染。这样前端就不必重复维护一套状态机规则。后端状态机调整时，接口返回值自动联动，前端代码无需改动。

```
读我 docs/spec/console/02-执行方案.md 里六个快照接口的定义（对应总览、看板、
详情、选题池、治理线、数据复盘六个页面），用我 core 包里已有的 parsers
（读 meta.yaml、backlog.yaml、治理线日志的那三个模块）实现这六个只读接口：
1. 六个接口各自只回自己页面要的那份数据，不要合并成一个大对象再让前端拆；
2. 新增一个聚合模块，把 parsers 读出来的几份数据拼成一份完整的仓库快照，
   六个接口都从这份快照里取数据，不要各自重新读一遍文件；
3. 单个文件解析失败时降级返回一个错误标记，不能让整个接口跟着报 500
   （这条规则第 14 课定过一次，接口层要原样遵守）；
4. 响应体统一带一个 revision 字段，取值来自这份快照当前是第几次构建的；
5. 详情接口 /api/content/:slug 额外带一个字段，列出这条内容按 core 包
   state 模块的迁移表，当前允许翻到哪些状态，每条标清楚要不要理由，
   前端只按这份返回值渲染按钮，不在前端把状态机逻辑再抄一遍。
实现完之后，对六个接口各跑一次真实请求，把返回的 JSON 结构贴给我看一眼。
```

测试接口时重点核对两处。首先检查每个接口返回的数据是否纯净，是否混入了其他页面的数据。比如 `/api/overview` 里如果包含了整份选题池列表，常见原因是聚合模块字段提取不彻底，接口应当按需切片，不能直接把整份快照原样吐出。其次检查六个接口返回的 revision 数值是否完全一致。数值不一致通常说明部分接口没有接入聚合模块，依然在独立读取磁盘。最后核对详情接口的新增字段。挑选几条处于不同状态的内容分别请求一次，检查返回的允许迁移列表是否与 core 包 state 模块的状态机规则严格对应，不能有多余或遗漏的选项。

六个页面已经具备了各自的数据源。接下来，我们把 `file`、`asset`、`health` 这三个通用接口接上。

## 二、file、asset、health：三个基础设施接口

读取受控文件原文、查看封面图与视频成片、检查服务运行健康状态，这三类需求在各个页面中都会出现。它们具有全局通用性，单独提取为通用基础接口，结构会比揉进快照接口中更加清晰。

`file` 接口最容易遇到的安全隐患是路径穿越。如果路径参数未经校验直接拼入文件系统读取调用，传入 `../../../etc/passwd` 就会读到仓库外的敏感文件。防范路径穿越需要采用严格的白名单机制，不能只过滤特殊字符。服务端只允许读取 `content`、`harness`、`pipeline`、`brain` 目录下的受控文件，以及根目录的 `dashboard.md`。同时，文件扩展名必须限定为文本格式。路径解析后，只要超出仓库根目录范围，或者不在白名单目录内，服务端一律直接拦截报错。`asset` 接口负责处理图片和视频等二进制文件，同样需要白名单约束，且仅开放 `content` 目录下允许的音视频和图片格式。

`health` 接口用于反馈服务本身的运行状态。它会返回快照最近构建时间、文件监听器运行状态，以及当前是否存在执行中的后台写任务。其响应体中需要包含当前的 revision 版本号。前端断线重连时，可以通过对比该版本号快速判断本地数据是否需要同步，不必被动等待下一次推送。

```
实现 GET /api/file 和 GET /api/asset 两个接口：
1. /api/file 只能读白名单目录内的文本文件（content、harness、pipeline、
   brain 这几个目录，加 dashboard.md），路径参数里出现 .. 或者解析后跳出
   仓库根目录，一律拒绝，不许当成路径不存在悄悄放过；
2. /api/asset 只能读 content 目录下的图片和视频，按扩展名再收一道白名单；
3. GET /api/health 除了报自身状态，响应体还要带上这次对应的 revision 号。
实现完，我会拿几个越权路径试探，你的实现要能把它们全部拒绝。
```

验收阶段准备两类测试路径。第一类是白名单内的正常路径，接口应成功返回文件内容。第二类是构造越权测试路径，例如跳出仓库根目录的相对路径，或者伪造白名单前缀的恶意路径。这类非法请求必须全部被拒绝，不能返回 200。随后检查 `health` 接口的返回体，确认 revision 版本号已正常输出。

现在单次请求读取已经打通。当磁盘文件发生真实变更时，前端如何及时获知，我们接着看变更推送机制。

## 三、SSE 推变更：store、watcher、revision 三件怎么配合

前端无需高频轮询，而是通过常驻的 SSE 连接接收更新信号。这条通道只推送轻量的 revision 版本号，不推送大体积业务数据。每当文件发生改动，服务端就将内部的 revision 计数器递增，并将新版本号广播给在线客户端。客户端比对本地缓存的版本号，一旦发现数值不一致，再主动按需请求第 1 节的快照接口。

业务数据不直接塞入 SSE 推送，主要考虑结构解耦。六个页面所需要的数据结构各不相同。如果每次变更都在推送中把所有页面的数据完整组装一遍，服务端就得额外维护一套重复的数据接口逻辑。采用只推送版本号的轻量信号设计，把刷新决策权交给前端。前端页面按需拉取，服务端则专注于维护单一的数据真相源。

推送链路的运行，由三个独立协作的组件分工完成。首先，磁盘文件发生改动时，watcher 负责感知事件，并设定防抖窗口把密集的多次变符合并。其次，store 收到合并后的通知，调用聚合模块重新生成内存快照，并递增 revision 版本号。最后，SSE 广播层将新版本号和变更原因推送到各个客户端连接。三个环节职责边界分明，各自专注单一功能，便于维护和定位问题。

```
实现 SSE 推送这套配合，三件东西各管一段：
1. watcher：监听 content/、harness/logs/、harness/tasks.md、dashboard.md
   这几个位置（都是你自己第 03、21 课已经交付过的真实目录和文件，
   仓库里没有的目录不要写进去），只认 yaml、md、jsonl 这几类扩展名的
   变化，短时间内的多次变化要合并成一次处理，不要一个文件改一下就
   触发一次；
2. store：收到 watcher 的信号后，重新调用第 1 节的聚合模块生成新快照，
   同时把 revision 计数器加一；
3. SSE：store 每次生成新快照后，把当前 revision 号和一句触发原因广播给
   全部连着的客户端，事件体只带 revision 号，不带任何页面数据。
新连上的客户端要立刻收到一次当前 revision，不用等下一次文件变化才有数据。
```

如果一次文件改动收到了多次连续的 SSE 推送，常见原因是防抖窗口时间设置偏短。一次保存触发的底层文件事件被误切成了多次变动，导致快照重复构建。如果目录文件发生修改，前端却完全收不到推送事件，通常是 watcher 监听范围遗漏了目标目录。例如新创建的条目如果落在未受监听的子路径中，监听器便无法捕获变更。

至此，读取与推送路径全部打通。接下来我们实现写路径。

## 四、快写 4 条：把点击翻译成一条 media 命令

审批通过、打回处理、选题操作背后都对应着现成的 `media` 命令。服务端写路径不另起炉灶开发一套状态流转规则，而是将 HTTP 请求转换为标准的 `execFile media <子命令>`。此前我们在第 12 到 16 课建立的状态机规则、文件原子写入和审计记录，在这里得到完全复用。server 这一层只承担请求解析与参数映射的工作。

| 端点 | 背后命令 | 触发场景 |
|---|---|---|
| `POST /api/actions/review` | `media flip` | 审核卡通过或打回 |
| `POST /api/actions/backlog-apply` | `media backlog apply --action <merge\|archive> --proposal <报告路径>` | 治理提议入库落地 |
| `POST /api/actions/promote` | `media promote` | 选题池取题 |
| `POST /api/actions/next-up` | `media next-up set` | 指定下一次取题 |

`backlog-apply` 接口不能只传递一个条目 id。请求体需要包含 `action`（执行合并或归档）和 `proposal`（对应的治理报告路径）两个参数。接口层将它们透传为 `--action` 与 `--proposal` 参数。回顾第 21 课的规范，`media backlog apply` 本身要求必须指定治理报告路径。缺少报告路径必须直接拒绝执行，确保每一次资产变更都严格锚定在已有的提议依据上。接口层不能擅自省略该参数，必须保持这道审计约束的完整性。

拼装命令时必须使用 `execFile` 传入参数数组，严禁拼接完整字符串交给 shell 解析，从架构上彻底杜绝命令注入风险。当 `media` 拒绝执行某项操作时，会返回具体的原因提示，例如非法状态流转或缺少必填原因。这类错误信息应当原样透传给前端，不宜在中间层包装成模糊的通用文案。如果中间层擅自改写报错信息，一旦底层命令调整提示措辞，两端就容易产生认知差异，给排查问题带来不必要的困扰。

```
实现四个快写端点，每个端点做的事只有一件：把请求体里的参数拼成一条
media 命令的参数数组，用 execFile 调用，不经过 shell：
1. POST /api/actions/review：决策是通过、打回重做还是打回挂待办，
   分别拼成 flip <slug> approved、flip <slug> drafting、
   flip <slug> rejected 三条，后两条要求 reason 参数必填；
2. POST /api/actions/backlog-apply：请求体带 id、action、proposal 三个
   字段，拼成 backlog apply <id> --action <merge|archive>
   --proposal <报告路径>，proposal 缺失直接 400，不许拼一条不带
   --proposal 的命令出去（这条和第 21 课定的「落笔必须绑一份提议
   报告」是同一件事，接口层不能把这个参数省掉）；
3. POST /api/actions/promote：拼成 promote；
4. POST /api/actions/next-up：拼成 next-up set <id> 或 next-up clear。
media 命令拒绝这次操作时，把它退出时报的错误原样透传给前端，不要自己
重新编一句话；media 命令本身跑挂了（进程起不来、超时）单独算一类错误，
跟业务拒绝分开处理，别混在一起。
```

验收时可以先测试一次非法状态流转，例如尝试将已经发布的内容再次提交审核。检查前端接收到的错误提示，是否与在命令行直接运行 `media` 命令的输出完全一致。确认异常拦截后，再执行一次合法的状态变更。操作完成后重新调用读取接口，确认状态已即时刷新到位。

即时生效的快写接口已经齐备。还有部分复杂操作需要执行数分钟，我们来看慢作业的处理方案。

## 五、慢作业 3 条：spawn 一次无头 CC，用 job runner 兜底

确认发布、打回重做、治理提议入库这三类动作，属于耗时较长的决策与执行任务，不能阻塞浏览器连接等待结果。这类请求由服务端先分配一个任务 id 并立刻响应，后续执行进度通过 SSE 推送或轮询获取。底层核心由作业管理模块（job runner）统一负责调度，包括登记任务、调度给后台子进程以及汇总执行状态。参考流水线中一共定义了五类作业端点。本课我们聚焦于核心的 `publish`、`rework`、`apply-proposal` 这三类。其余涉及定时巡检与新建条目的任务，暂不纳入当前实现范围。

| 作业类型 | 超时 | 成败怎么判 |
|---|---|---|
| `publish` | 20 分钟 | 读这条内容 `meta.yaml` 的状态字段，落到 `published` 或 `scheduled` 才算成功 |
| `rework` | 45 分钟 | 读同一个状态字段，落回 `review` 才算成功 |
| `apply-proposal` | 10 分钟 | 检查 `brain/` 目录下有没有真的产生文件改动 |

这三档超时是参考流水线的起步值，你自己按任务实际耗时定，不用照抄这三个数字。

实现这三类作业无需重写子进程管理逻辑。我们在第 25 课已经沉淀了完整的基础设施。`cc-stream` 包负责启动无头 CC 进程并标准化流式输出。裁决函数则在子进程退出后读取磁盘文件，以实际状态判定执行结果。子进程自身报告的执行结果仅作为参考线索，最终定论以裁决函数读取的元数据为准。我们在第 25 课验证过类似案例：子进程日志显示执行成功，但 `meta.yaml` 状态并未推进，裁决函数据此判定为失败。本课的所有慢作业继续沿用这项硬性检验原则。

打回重做任务在处理流程上稍有不同。在启动实际改写子进程之前，必须先调用第 4 节的写接口，将状态推进至创作中（drafting）。如果不先更新状态就直接派发子进程，一旦执行过程中发生重复触发，内容与状态就会出现割裂。同时，job runner 需要维护各条目正在执行的任务索引。同一条内容如果在任务进行中被重复提交，系统应当予以拒绝，避免并发冲突。

```
实现一个作业管理模块（job runner），用第 25 课已经造好的 cc-stream 包和
裁决函数管这三类慢作业，不要重新写一套子进程管理：
1. 每类作业收到请求后，job runner 先登记一条记录、立刻返回 202 和一个
   任务 id，真正的执行放进后台；
2. 拉子进程用 cc-stream 的 runHeadlessCC，进度事件用它的里程碑引擎归一，
   每条里程碑通过 SSE 按这个任务 id 广播出去；
3. 子进程跑完之后不要直接采信它自己报的成功还是失败，调用第 25 课的
   裁决函数，现场读这条内容的 meta.yaml，状态落到这次任务期望的值上
   才算成功；
4. rework 这类要求内容当前处于审核或打回状态的作业，进队列之前先做一次
   前置检查，状态不对直接拒绝，不进队列空跑一次；
5. job runner 记着当前哪条内容正挂着作业，同一条内容重复提交直接拒绝，
   不排进队列跑第二遍。
harness-run 和 create 这两类作业不在这一课范围内，先不要实现。
```

如果子进程执行完毕自评成功，但 `meta.yaml` 中的状态没有变更，通常是因为逻辑过度依赖子进程的自评输出，漏掉了二次校验。验收时可以发起一次打回重做测试，观察系统是否先完成状态流转再启动执行。任务结束后，检查状态是否准确落入目标区间，不能仅凭控制台的任务完成标记就直接认定通过。

快写与慢作业两条路径均已就绪。此前由飞书服务独立承担的重任务，这一课需要平滑迁移过来。

## 六、飞书回调改道：第 19 课那个服务不再自己写

在第 19 课中，飞书服务的状态变更统一经由 `media flip` 处理。但涉及重做的耗时任务，当时是由服务内部自行启动线程与子进程承接的。确认发布在当时也仅发送了占位卡片，未接入具体逻辑。参考设计中通过配置开关，将此类重任务委托给独立的控制台后端处理。由于当时控制台尚未就绪，我们选择在本地线程中直接闭环，避免对接空接口。现在控制台服务端已经完备，可以正式完成架构对接。

现在后端控制台已经就绪，我们直接将这两处逻辑改造为调用控制台接口。对于打回重做流程，将此前直接拉起子进程的代码，替换为向控制台发送 POST 请求，并通过轮询获取裁决结果以更新卡片。确认发布按钮同样直接接入控制台的发布接口，遵循请求、轮询与回写卡片的闭环。至于审核通过和挂待办按钮，保持现有逻辑不变。它们属于纯粹的状态跃迁，沿用直接调用 `media flip` 的方式更为简洁高效，无需经过控制台多转一层。

| 飞书动作 | 原来怎么做 | 现在怎么做 |
|---|---|---|
| 打回并自动重做 | 自己 spawn 一次无头 CC，自己判断结果 | POST 控制台的 rework 接口，轮询任务状态 |
| 确认发布 | 只发占位卡，没有处理代码 | POST 控制台的 publish 接口，轮询任务状态 |
| 审核通过 | subprocess 直接调 media flip | 不变 |
| 打回并挂待办 | subprocess 直接调 media flip | 不变 |

```
把第 19 课飞书服务里打回重做那处直接 spawn 无头 CC 改状态的代码，
改成：
1. 给控制台的写路径发一次 POST（发布或重做接口），带上这次要处理的
   内容 slug；
2. 拿到 202 和任务 id 之后，每隔一段时间轮询一次任务状态；
3. 任务落到终态后，用第 5 节裁决函数给出的结果更新飞书卡片，裁决说
   没成功就如实告诉人没成功，不要把没做成的事说成做成了。
确认发布这条路径原来没有真正的处理代码，只发了占位卡，按同样的三步
新接一条，不用先找旧代码再改。
审核卡的通过按钮、打回原因卡的挂待办按钮不用动，这两处从第 19 课
写出来那天起就是 subprocess 直接调 media flip。
```

验收时在飞书客户端选取一条处于待审状态的内容，输入打回原因并触发自动重做。重点核实两项表现。一是控制台任务列表是否新增了对应的重做记录，并包含任务 id、状态和裁决结果。二是飞书服务进程日志中，是否仅记录了发送给控制台的 POST 请求，不再有本地直接启动无头 CC 的记录。两项表现均符合预期，即表明重做任务已成功交由控制台接管。

读写两条 API 已经全部打通。下一步我们将进入界面开发，让流程操作更直观地呈现。

## 七、收尾：读写两条 API 都通了，界面还没做

至此，控制台后端的读写两条路径已完整落地。读取侧实现了六个快照接口、三个基础服务接口，以及基于 revision 的 SSE 变更推送。写入侧覆盖了四条快速变更命令，以及三类依托无头 CC 和裁决函数的慢作业。server 模块没有直接向 `meta.yaml` 或 `backlog.yaml` 写入数据，全部状态变更均严格收敛在 `media` 入口中，延续了系统的单一写入口规范。飞书服务中的重做与发布流程，也已顺利迁移到写 API 链路。

目前整套接口主要通过终端命令或浏览器进行调试验证，前端界面尚未搭建。读写 API 的贯通为交互层打下了坚实基础。在接下来的课程中，我们将正式开启前端界面的搭建工作。
