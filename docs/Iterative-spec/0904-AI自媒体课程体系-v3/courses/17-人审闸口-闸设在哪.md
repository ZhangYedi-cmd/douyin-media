# 人审闸口：可逆的 AI 自行，不可逆的等人

上一课把状态中枢立住了：全量 `media` 命令收敛成写状态的唯一入口，`03-施工记录.md` 记了两个里程碑的出口条件，`media check` 在自己仓库跑通、退出码干净，`audit.jsonl` 证明了每一次改动都留了痕迹。上一课收尾的时候留了一句话：状态中枢立住了，机器能自己改状态。可有些动作改错了收不回来，哪些动作不能让机器自己拍板？这一课回答这句话。

这一课的记忆锚点是：可逆的 AI 自行，不可逆的等人。输入是你第 14 课造的 core 包里 state 模块的 review 状态三条出边（路径按你自己 SPEC 里定的来）、`pipeline/3-review.md` 和 `pipeline/4-publish.md` 全文、`CLAUDE.md` 的流程纪律那一节。产出两件东西：一张不可逆动作表，一份卡片字段草案。

## 一、判据：错了能不能收回

要不要给一个动作设人审闸口，问的不是 AI 会不会判断错。AI 会判断错，这是前提，不用专门论证。真正要问的是判断错了这个动作能不能撤回。能撤回的大不了再改一次，代价是多花几分钟；不能撤回的，改错了就没有再来一次这个选项。

这条判据跟前面几课立的自愈回路是两件事，容易被并到一起想，实际是两条不同的维度。第 10 课把配音质检的判错、改、复判接成了一个能自己转起来的回路，三轮不过就停下来交人，这条回路解决的是准不准的问题，回路转得越顺，AI 判对的概率越高。但判对的概率再高，也不会让一个不可逆的动作变得可逆。第 01 课列过出审前机器已经查完的七项：声画一致、音频自然度这些能写成一条命令判真假的，都归了机器；事实、语气、定位这些写不出判定命令的，归了人。那条判据看的是这项工作机器能不能干，这一课的判据看的是另一条线：干完了这个动作能不能收回。两条线经常重叠，一个技术结论判得越准，出问题的概率越低，但概率降到再低，发布这个动作跑完了照样是跑完了，收不回来这件事本身没有变。

不可逆的动作分四类：发出去收不回、花钱、对外可见、覆盖真相源。这四类的划法是让 AI 先把流水线上会写文件、调外部服务的动作全部列一遍，再挨个对着判据归类，只凭脑子想列不全这张表：

```
读一遍我的 pipeline/2-create.md、pipeline/3-review.md、pipeline/4-publish.md，
和我 core 包里的 state 模块，
把这条流水线上会写文件或调用外部服务的动作全部列出来，按四类判据分类：
发出去收不回、花钱、对外可见、覆盖真相源。
剩下改错了能再改一次的动作单独放一栏，别混进不可逆那四类里。
每个动作写清楚它对应哪条真实命令或脚本，不要用你自己编的名字，
你的文件里没写到的地方就留空，不要替我猜。
输出一张表，动作 / 判据类别 / 命令或脚本名，我要逐格核对有没有真实出处。
```

参考流水线自己跑这条 Prompt，整理出的表大致是这样：

| 类别 | 判据 | 对应的真实动作 | 可逆吗 |
|---|---|---|---|
| 发出去收不回 | 动作完成后没有技术上的撤销手段 | `sau douyin upload-video`（经 `douyin-publish` skill 真发） | 不可逆 |
| 花钱 | 调用付费服务，一旦成功费用已产生 | `tts-dub` 批量合成配音，调 MiniMax 付费接口。参考流水线的 `pipeline/2-create.md` 里写了先探一次余额，余额不够会返回 1008 停线报充值，这条判据要看的是钱花出去这件事本身，与余额够不够无关，一批配音合成成功，这笔钱就退不回来了 | 不可逆 |
| 对外可见 | 动作结果被外部真实用户看到、留下痕迹 | 跟第一类经常是同一个动作，角度不一样：发出去收不回说的是技术上没有反悔按钮，对外可见说的是就算能删视频，看过的人、截过的图已经在外面了 | 不可逆 |
| 覆盖真相源 | 动作直接改写状态字段，原值不再留痕 | `media publish-done` 一次做三件记账：`meta.yaml` 翻终态并回填时间和链接、`backlog.yaml` 同步翻转、`dashboard.md` 移出在制表。记错了想知道原来的值，只能翻 `audit.jsonl` 反推 | 不可逆 |
| （对照） | 只改单文件状态，不花钱、不对外、不做终态覆盖 | `media flip`（比如把一条内容从 `review` 翻回 `drafting`）翻错了直接再翻一次翻回去就行 | 可逆 |

拿到这张表，你自己的版本先核对两件事：每一格填的命令或脚本名在你自己的仓库里是不是真的存在，划进不可逆那四类的动作是不是真的对得上判据。如果你自己的 `pipeline/2-create.md` 写得比参考流水线粗略，没有 1008 这一级细节，不代表你的文件写错了。你的账号用的配音服务、余额提示方式完全可能是别的写法，判据看的是花钱这件事本身，不是这一个具体错误码。

如果 AI 把某个只改了一个字段又能随时翻回去的动作也划进不可逆那一栏，常见原因是把动作陌生和动作不可逆这两件事混了：前者是没跑过这个动作，跑几次就熟了；后者是动作本身的性质，不会因为跑熟了就变得可逆。判据只认后者。

四类判据定完，这些动作各自落在状态机的哪条出边上，是下一步要查的事。

## 二、闸口位置：定在哪条边上

闸口该设在出了错收不回的那条边前面，而不是设在 AI 最容易出错的那个环节。这两种设法差得很远，`review` 状态实际的出边摆出来看得很清楚。

你第 13 课 SPEC 里定的状态机，`review` 状态一共三条合法出边，全部经 `media flip` 触发。第一条，`review` 到 `drafting`，打回重做，不需要写理由。第二条，`review` 到 `approved`，通过，同样不需要理由。第三条，`review` 到 `rejected`，打回挂待办，这条需要理由，也就是 `media flip` 要求这条边必须带 `--reason` 参数才能执行。这三条边无论走哪一条，都还能再改回来：打回 `drafting` 的可以重新走一遍创作再交回 `review`；`rejected` 的可以再翻回 `drafting` 重做；`approved` 如果你当初也留了退回 `drafting` 这条边，同样能反悔改稿。参考流水线的 state 模块里就留了这条边，旁边一句注释写的是审批后反悔改稿，说明这条退路是特意补上的，不是漏判。如果你自己的 SPEC 当初没留这条边，`approved` 就是单向的，不影响这一课的判据：真正不可逆的边始终在 `approved` 之后，两种情况下这个结论都成立。

真正不可逆的那条边，在 `approved` 之后。参考流水线的 `pipeline/4-publish.md` 写的是一条硬约束：先 dry-run 拼出命令和物料，经 `feishu-notify` 推回飞书做二次确认，人点确认才真发。这条边对应的命令是 `media publish-done`，跑完这条命令，第一节说的真发、花钱、对外可见、覆盖真相源四件事全部已经发生，没有翻回去这个选项。

把这五条边摆到一张表里，让 AI 去你自己的 state 模块和阶段契约里对照着找：

```
读我 core 包里的 state 模块，找出 review 状态的三条出边，
和我自己的 pipeline/3-review.md、pipeline/4-publish.md、CLAUDE.md 的流程纪律那一节，
把 review 的三条出边整理成一张表：出边 / via 命令 / 要不要理由 / 谁触发 /
改错了能不能再改回来。
再单独加一行：approved 状态之后走向真发和记账的那条边，同样这五列，
标出它和前三条的区别在哪。
我自己的阶段契约文件如果还没写到这个细节，留空或标注待补，不要替我编。
```

参考流水线跑出来的表大致是这样。如果你自己的 SPEC 当初没留 `approved` 退回 `drafting` 这条边，把对应那一行删掉，其余四行按你自己 `media flip`、`media publish-done` 的真实行为核对：

| 出边 | via 命令 | 需要理由 | 谁触发 | 改错了能不能再改回来 |
|---|---|---|---|---|
| `review` 到 `drafting`（打回重做） | flip | 否 | 人 | 能，重新走创作再交回 `review` |
| `review` 到 `approved`（通过） | flip | 否 | 人 | 能，`approved` 还能退回 `drafting` |
| `review` 到 `rejected`（打回挂待办） | flip | 是 | 人 | 能，`rejected` 还能翻回 `drafting` |
| `approved` 之后真发 + 记账 | publish-done | 命令层不强制，但动作本身不可逆 | 人（二次确认后） | 不能 |

这张表最容易看错的地方是：`review` 的三条出边全都是人触发的，好像闸口已经设过一次了，为什么还要在 `approved` 之后再设一道。原因是这三条边点错了代价很小，属于流程内部的可逆循环，真正决定这套系统安不安全的，是 `approved` 之后那条边有没有人参与。哪天为了省事把 `publish-done` 也接成自动触发，出审这一关照样在，但闸口已经名存实亡了，因为真正不可逆的那一步已经不需要人点头。

闸口位置定了，这道闸具体长什么样、人在飞书上看到什么、点什么，是下一节要划的字段配额。

## 三、卡片放什么：三十秒判完的信息配额

卡片要让人三十秒内判完，前提是信息够但不多。字段太少，人无法判断；字段太多，人得从一堆无关信息里挑出要看的那几条，反而比不做卡片还慢。哪些字段必须直接上卡，哪些字段点进去看，是这一节要划的线。这份草案是留给第 18、19 课的约束，还不是最终实现。这条闸口这一版只做飞书，这是参考仓库的历史实现，需要企业或团队账号才能建自建应用，这一条会在第 18、19 课动手前反复确认。

先看审核卡要判的六项。参考流水线的 `pipeline/3-review.md` 列了六项人审清单：事实、时效、定位、语气、合规、观感。第 01 课把这六项的名字列出来了，说这六项没有对应的检测脚本，全靠人凭经验现场判断。这一课把判据补上，判据要给出一句能核对的标准，不能停留在让人凭感觉。

事实这一项，判的是技术结论有没有出处：官方文档、开源项目的提交记录、可复现的评测，三选一，查不到出处就判不通过，不能因为读着顺就当成对的。

时效这一项，判的是涉及最新发布或版本更新的内容有没有标来源和抓取日期。这条容易在写完之后过期：抓取时是最新版本，等到出审时可能已经被官方更新覆盖，标了日期至少能看出这个结论是什么时候查的。

定位这一项，判的是内容贴不贴合 `brain/positioning.md` 定的账号支柱，逐条核对，不是凭印象觉得差不多。

语气这一项，回收第 01 课的钩子冷启动判据：第一句脱离上一集单独读，能不能站得住。

合规这一项，对照 `CLAUDE.md` 的内容红线逐条核，无违禁词、无违规导流、无夸大承诺。这条最容易漏检的地方是同音词，文字扫描扫不出发音接近的违禁词，得靠人耳朵听。

观感这一项，封面是不是竖版比例、有没有拿横屏视频帧充数（这是第 05 课定的封面判据），加上字幕逐字看一遍有没有错别字。

| 判据 | 判什么 |
|---|---|
| 事实 | 技术结论能否在官方文档、提交记录或可复现评测里查到出处 |
| 时效 | 涉及最新发布的内容是否标了来源和抓取日期 |
| 定位 | 是否贴合 `brain/positioning.md` 定的账号支柱，逐条核对 |
| 语气 | 第一句脱离上一集单独读，能不能站得住 |
| 合规 | 对照内容红线逐条核，含发音相近的违禁词 |
| 观感 | 封面是否竖版且未拿横屏帧充数，字幕逐字有无错别字 |

这六项判据要走一条 Prompt，补进你自己第 03 课写的骨架 `pipeline/3-review.md`。你这份文件目前只有输入、输出、状态翻转、闸口四项，六项判据这一段还是空的：

```
把这六项人审判据加进我的 pipeline/3-review.md：
事实：技术结论能否在官方文档、提交记录或可复现评测里查到出处。
时效：涉及最新发布的内容是否标了来源和抓取日期。
定位：是否贴合我的 brain/positioning.md 定的账号支柱。
语气：第一句脱离上一集单独读，能不能站得住。
合规：对照我的内容红线逐条核，含发音相近的违禁词。
观感：封面是否竖版且未拿横屏帧充数，字幕逐字有无错别字。
按我文件现有的结构插进去，不要改动我已经写好的输入、输出、状态翻转、闸口四项，
改完把整份文件贴给我看一遍。
```

判据定了，卡片本身是接下来要拆的。这条流水线上有两处闸门，出审和确认发布，第 01 课已经列过。审核卡对应出审，确认发布卡对应 `approved` 之后的二次确认，两张卡各自的字段配额不一样。

审核卡要让人三十秒判完六项判据，直接上卡的字段只能是六项判据里能一眼扫过去的部分：标题和钩子首句（判语气）、选题定位标签（判定位）、封面缩略图（判观感的一半）。事实、时效、合规这三项无法压缩成一眼看完的摘要，需要点进去看，口播稿全文链接放在卡片上，点进去看完整文案。人在这几项上花的时间不能省，卡片能省的是找文件、切窗口的时间，不是判断本身的时间。

按钮这一版做两个：通过、打回。打回带一个文本输入框，写打回原因。通过对应 `review` 到 `approved` 这条边；打回对应 `review` 到 `drafting` 这条边，原因写进 `3-review.md`。你自己的状态机里 `review` 其实还有第三条出边，打回挂待办到 `rejected`，这一版卡片先不单独做这个按钮。要不要把打回拆成两种、什么时候该直接挂 `rejected` 而不是回 `drafting` 重做，这个决策留给第 18、19 课走 SPEC 六步时定，不在这一课草率拍板。

确认发布卡对应的是 `approved` 之后那条不可逆的边，参考流水线的 `pipeline/4-publish.md` 对 dry-run 定的不可退让的一条是先拼出完整的发布命令和物料，推回飞书，人点确认才真发。这张卡上要放的是这次真发会用到的全部具体信息：完整拼好的 `sau douyin upload-video` 命令、标题、话题标签、封面路径、媒体文件清单。这里没有点进去看这一说，要确认的就是这些字段本身对不对，藏起来反而增加误发的风险。按钮同样两个：确认发布、取消。确认发布触发真执行，成功后走 `media publish-done` 记账；取消停在 `approved`，不做任何状态翻转，等着下一次有人点确认发布。

| 卡片 | 卡片作用 | 上卡字段 | 点进去看 | 按钮 | 触发后去哪 |
|---|---|---|---|---|---|
| 审核卡 | 出审闸口，判六项人审判据 | 标题、钩子首句、定位标签、封面缩略图 | 口播稿全文 | 通过 / 打回（带原因） | 通过到 `approved`；打回到 `drafting`，原因写进 `3-review.md` |
| 确认发布卡 | `approved` 之后的二次确认，防误发 | 完整发布命令、标题、话题标签、封面路径、媒体文件清单 | 无，字段本身就是要确认的东西 | 确认发布 / 取消 | 确认发布触发真执行，成功后 `media publish-done` 记账；取消停在 `approved` |

如果卡片上的字段拉得又长又满，三十秒判不完，通常是把点进去看那一栏的字段也一起塞上了卡。审核卡的口播稿全文如果直接铺在卡片正文里，人得先划到底才能点按钮，这跟没做卡片区别不大，点进去看这个动作本身就是配额的一部分，不是偷懒。

字段草案定了，把它变成一条能跑的技术通道，够得上走完整 SPEC 六步。

## 四、收尾：第二件重活

不可逆动作表划清了什么改错能再来一次，什么不能：`media flip` 可逆，真发抖音、付费配音、公开可见、终态记账这四类不可逆。卡片字段草案定了人要看什么、点什么：审核卡放六项判据能一眼扫过去的部分，点进去看口播稿全文；确认发布卡把发布命令原样列全，不留藏起来的字段。

草案只是字段清单，背后还有一堆没定的东西。飞书通道是走长连接还是走公网 webhook，卡片的 JSON 结构具体怎么拆成几层元素，按钮点下去之后飞书那边给多长的响应窗口、超时了会怎样。一个飞书应用如果以后要服务多条业务线，怎么防止彼此的按钮事件串到对方头上，这几件事一件都还没定。这一课的判据够不到这一层，字段草案是接口，接口背后的实现是另一件重活。

不可逆动作表和卡片字段草案有了。这是第二件重活，六步再走一遍：飞书通道要定哪几件事？
