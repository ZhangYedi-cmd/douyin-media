# 验证与收敛：拿 audit.jsonl 证明写路径真的只有一条

上一课把全量 `media` 命令补齐了，写命令、`check` 都跑得起来，前面十几课手改 `meta.yaml`、`backlog.yaml` 的地方也迁移完了。这一课收口：证明这套写入口真的只有一条，把 `docs/spec/media/03-施工记录.md` 补上。

记忆锚点：造完不等于造对，唯一入口的证据不是嘴上说的，是 `audit.jsonl` 里能查到的那一行。这一课的输入是这套刚收敛完的写入口，加上它跑起来之后新生成的 `audit.jsonl`；产出两件东西：`docs/spec/media/03-施工记录.md`，和一份验收输出。

## 1. 开篇：造完了，还没证明造对了

验证这一步验的不是代码能不能跑起来。代码跑起来只说明没有语法错误、没有崩溃。真正要验的是另一件事：状态只有一个地方能写，这个判断到底对不对。这件事容易被自己以为已经对了：你写这套命令的时候，确实只在 `media` 这一个入口里调用写文件的函数，每次跑一遍也确实成功了，看上去没什么可怀疑的。可别的地方有没有偷偷绕过去写，光靠肉眼扫一遍代码容易漏掉，尤其是绕开的那条路径本身就藏得比较深，比如某个 skill 里留了一行旧的直接改 `meta.yaml` 的代码没删干净。

举三种真实会撞到的墙。第一种，两层状态不同步：一条内容的 `meta.yaml` 里状态已经翻到了 `published`，但它在 `backlog.yaml` 里对应的选题条目状态还停在 `picked`，没有跟着翻过去。这种不同步单看任何一个文件都看不出问题，`meta.yaml` 本身没写错，`backlog.yaml` 本身也没写错，问题出在两个文件该一起改的时候没一起改。第二种，发布记录没有链接：内容状态已经是 `published`，但 `publish_url` 字段是空的，等于说这条内容发布了，可你自己都找不到发布到哪去了。第三种跟前两种不太一样，撞的不是逻辑漏了一步，是往返测试会撞到的墙，工具本身在悄悄改动你没让它改的地方。

参考流水线自己造类似的写入口时，真的撞过这第三种墙。它验证 core 包（负责解析和重写 YAML 的那部分）时，实测发现直接调用 YAML 库的序列化方法，对全部 25 个真实文件都会丢注释对齐，文件内容看着大差不差，但注释和它原本挂在哪一行的对应关系乱了。根因在 YAML 库自己的序列化实现，它本来就不保证你没动的部分原样吐出来，代码逻辑本身没写错。后来的做法改成先在文档里定位到要改的那一小块，只替换那一小块对应的原始字节区间，其余部分连一个空格都不碰。这条教训直接决定了这一课要验的第一件事：不能信自己应该没丢东西的感觉，得真的拿全部真实文件跑一遍，逐字节比对。

这三面墙有一个共同点：光靠肉眼看代码看不出来，得留下一个能回查的东西。判据只有一句：凡是改了状态的动作，都要能在 `audit.jsonl` 里查到对应的一行，查不到就不算数。先看怎么留证据，`--dry-run` 和 `audit.jsonl` 两件事。

## 2. 留证据：--dry-run 先出计划再执行，audit.jsonl 当账本

写命令带上 `--dry-run` 参数，只打印这次操作会改哪些文件、改哪个字段，不真的落盘。这一步的意义是把 AI 说它要做什么和 AI 真的做了什么，拆成两次可以分别确认的动作：先看计划，看完确认没问题，再去掉这个参数真跑一遍。跳过这一步直接跑写命令，出了错就已经覆水难收，文件已经改了，你只能靠再翻一次审计记录去反推刚才到底发生了什么，比起先看一眼计划再决定跑不跑，成本高出一截。

跑完带 `--dry-run` 的命令，AI 应该原样打印出这次操作要碰哪几个文件、每个文件哪个字段会变。这份清单读法很直接：一行一个文件路径，路径后面跟着这次会改的字段名。如果打印出来的文件比你预期的多，比如你只想翻一次状态却发现清单里还带着 `dashboard.md`，别急着当成 bug，很多写命令本身就要求同一把锁里连带重建看板的机器区，这是设计如此，不是多写了一步。真正该警觉的是清单里出现了一个你完全没预料到的文件路径，或者同一个文件里出现了两个不相关的字段被同时改动。

真跑一遍之后，这次改动会在 `audit.jsonl` 里追加一行。这是这套写入口留下的唯一账本，一行一条 JSON，逐行独立，不需要整体解析成一个大对象。参考流水线这个文件半个多月里积了三千五百多行，但里面绝大多数是自动化测试反复跑同一批命令留下的记录，真正对着真实仓库根目录跑出来的行数很少。你自己刚把全量命令跑通，账本现在多半只有几十行，行数不多是正常的，不用觉得比参考流水线的规模小就是没做对。抽两条真实的给你看它长什么样：

```json
{"ts":"2026-08-18T09:33:13.903Z","actor":"yedizhang","cmd":"flip","argv":["flip","open-weight-5","published","--json","--root","..."],"result":"error","files":[],"summary":"scheduled → published 须走 media publish-done（三翻齐事务）；flip 只做单文件状态迁移"}
{"ts":"2026-08-18T09:28:01.396Z","actor":"yedizhang","cmd":"publish-done","argv":["publish-done","ep04-esc-abort-chain","--url","https://v.douyin.com/ep04xyz","--json","--root","..."],"result":"ok","files":[{"path":"content/2026-06-18/ep04-esc-abort-chain/meta.yaml","fields":["status","timestamps.published","publish_url"]},{"path":"content/_backlog/backlog.yaml","fields":["topics[].status"]},{"path":"dashboard.md","fields":["auto:wip","auto:backlog","auto:alerts"]}]}
```

六个字段每次都在，各管一件事。`ts` 是这次操作的时间戳，`actor` 是谁跑的这条命令，`cmd` 是命令名。`argv` 是完整的命令行参数，出了问题第一件事就是回头看这一列，能原样复现。`result` 只有 `ok` 和 `error` 两种取值，`files` 是这次操作真的碰了哪些文件、每个文件改了哪个字段，跟 `--dry-run` 打印的计划应该对得上。操作失败的时候还会多一个 `summary` 字段，用一句人话交代原因，成功的时候这一项不出现。第一行是一次失败的尝试：想直接把状态从 `scheduled` 翻到 `published`，被拦了下来，`summary` 里写清楚了原因，这类跨越式的发布状态翻转只能走三翻齐的发布收尾命令，单文件翻转命令不认这条路。第二行是一次成功的发布收尾，`files` 里三个文件一起动：内容自己的元数据翻了状态、补了时间戳和发布链接，选题池那边跟着翻状态，看板的机器区跟着重建。这一行本身就是判据里说的查到对应的一行，三个文件是不是真的一起改的，不用你猜，这一行摆在那。

有一条边界要留意：`audit.jsonl` 只记会写文件的命令，`check` 这类只读命令跑了多少次、结果如何，不会出现在这个文件里。指望在 `audit.jsonl` 里翻出某次 `check` 跑没跑过，是找错了地方。`audit.jsonl` 证明的是写了什么，`check` 证明的是现状自不自洽，两件事分工不同。

知道怎么留证据、怎么读证据了，接下来用它自证写路径唯一。

```
在我自己的仓库里，用 --dry-run 跑一次 media flip <slug> <目标状态>，
把打印出来的变更清单原样贴给我，逐行说清楚：
1. 这次操作打算改哪几个文件、每个文件改哪个字段；
2. 会不会连带触发 dashboard.md 机器区重建；
3. 去掉 --dry-run 真跑一遍之后，在 audit.jsonl 里新增的那一行，
   ts/actor/cmd/argv/result/files 六个字段分别是什么，
   跟第 1、2 步的预告对不对得上。
```

如果这条命令跑完 `audit.jsonl` 没有新增任何一行，多半是命令本身走了一条没有接到审计记账的分支，比如某个失败提前 return 的路径漏挂了记账逻辑，这种情况值得单独让 AI 去核对一下这条命令的完整代码路径，不是简单重跑一次就能解决的。

## 3. 自证写路径唯一：media check 在自己仓库跑通

模块 3 的出口条件是一句能跑的验证动作：`media check` 在自己仓库上跑一遍，返回退出码，error 级警报为零才算过。这是全书状态中枢立住的标志，前面五课做的所有事，最后收敛到这一条能不能通过。

`media check` 的判定标准，第 13 课已经列过一张八条规则的表，从双层状态对不上、条目断链、超时没人回填，到疑似哪天忘了出内容，各管一类问题。这八条盯的字段，都是你从第 03 课起就一直在用的同一批字段（状态、来源指针、发布链接），拿这张表当自己 `check` 命令的检验清单没问题；如果你的 `01-ADR.md` 给某个字段起了别的名字，对应到自己的字段名上再核对。`check` 命令的退出码只看 error 级：只要有一条 error 级警报没清零，退出码就非零；warn 和 info 级警报不影响退出码，是提醒你留意但不算错。

| 规则 | 级别 | 判定什么 |
|---|---|---|
| CHK-01 双层不同步 | error | meta 的状态和 backlog 的状态没对上 |
| CHK-02 断链 | error | backlog 是已取题状态，但对应目录或元数据缺失 |
| CHK-03 超时未回填 | error | 定时发布的状态停留太久没人回填结果 |
| CHK-04 审核积压 | warn | 停在审核状态太久没人处理 |
| CHK-05 链接待补 | warn | 已发布但没有回填作品链接 |
| CHK-06 指针断裂 | warn | 元数据里的来源指针和选题池对不上 |
| CHK-07 临近过期 | info | 选题快要被清扫规则命中 |
| CHK-08 疑似空跑 | warn | 到了该出内容的时间点还没有新内容，也没人上报 |

光跑一遍拿到 0 error 还不够，这个结果本身也得验一遍是不是真的在起作用，不是凑巧什么问题都没撞上。最直接的办法是故意制造一次错误，看 `check` 能不能真的抓出来：找一条已经进了 `review` 状态的内容，手动把它的 `source` 字段改成一个选题池里不存在的 id，这正好踩中 CHK-06 的判定条件，指针在 backlog 里查无此 id。跑一遍看 warn 数有没有从原来的数字往上加一。加了，说明规则确实在盯这个字段；没加，说明这条规则要么没接上你自己的字段名，要么判定逻辑本身有漏洞。

```
在我自己的仓库里做三件事，把每一步的原始输出贴给我，不要转述：
1. 跑一遍 media check，报出 error / warn / info 各多少条，退出码是几；
2. 找一条已经进入 review 状态的内容，手动把它 meta.yaml 里的
   source 字段改成一个 backlog 里不存在的 id，保存后再跑一遍
   media check，对比这次和第 1 步比 warn 数有没有变化，
   变化对不对得上 CHK-06 的判定条件；
3. 把手改的那一行改回原样，再跑一遍 media check，
   确认警报数字回到第 1 步的数字。
```

如果第 2 步跑完 warn 数没有任何变化，多半是这条规则的判定字段名跟你自己 `01-ADR.md` 里实际用的字段名对不上。第 13 课就提醒过这一点，规则表的字段名要按自己的项目改名字再抄，不能连名字一起照搬。这时候该做的不是怀疑 `check` 本身坏了，是回头核对这条规则实际读的是哪个字段，跟你手改的那个字段是不是同一个。

退出码之外，`audit.jsonl` 还能反过来印证 `check` 报的东西站不站得住脚。任意挑一条 `check` 报出的 error，去 `audit.jsonl` 里查这条内容最近几次状态变更，能不能找齐一段完整的经过：什么时候取的题、什么时候进的 `review`、有没有一次发布收尾的记录。找不齐，说明这条内容的状态是从别的地方改出来的，不是走 `media` 写入口写的，这正是唯一入口这条判据要抓的漏网之鱼。

唯一性有证据了，最后一件事是把这轮施工的过程记下来。

## 4. 施工记录怎么写：出口条件、卡在哪、怎么绕过去

施工记录不是把跑过的命令按时间顺序抄一遍的流水账，是给每个里程碑一行结论：出口条件是什么、实际结果是什么、卡在哪、怎么绕过去，绕不过去的留给以后的人接着看。判断这份记录写得够不够格，有一个简单的办法：拿给一个没参与这次验证的人看，他能不能照着这几行判断这个里程碑是不是真的过了。能，就算立住了；卡在哪、怎么绕过去两栏空着或者写得含糊，说明验证本身还没做完。

M1、M2 的出口条件是第 13 课定好的，直接抄过来，不重新措辞。M1 是：真实仓库里跑 `media check` 能通过，YAML 文件里原有的注释一处都没丢。M2 是：全仓状态写路径唯一，连续七天内元数据、选题池、看板机器区的每一次变更，都能在审计记录里找到对应的一行。

M1 这句话拆开看是两件事。`check` 能通过，前面第 3 节已经有了具体的验证动作。注释一处都没丢，验的办法是往返测试：拿全仓所有真实的 `meta.yaml` 和 `backlog.yaml`，不改动内容，只做一次读进来再写出去的动作，逐字节比对写出去的结果跟原文件是不是完全一样。这条测试要用真实文件跑，不能只拿一两个精心构造的样例文件测，第 1 节说的丢注释那次教训，就是栽在样例太干净、真实文件太脏这个差距上。

M2 这句话里的七天窗口，一课的篇幅里没法真等七天过完。如实的做法是先把验证方法定下来：连续七天，每天抽查一次 `audit.jsonl`，核对当天发生的每一次状态变更是不是都能找到对应行，再对照当天实际操作过的内容条目数，数目对不上就要去查漏在哪一步。这条出口条件现在的真实状态是验证方法已定，窗口进行中，不是已经通过，施工记录里如实写这一句，不拿基本符合这类话糊过去。

```
帮我写 docs/spec/media/03-施工记录.md，用这五个字段一行一个里程碑：
里程碑 / 出口条件 / 实际结果 / 卡在哪 / 怎么绕过去。
M1、M2 的出口条件抄 02-执行方案.md 里定的原话，不重新措辞。
实际结果只能填我们在这一课里真跑出来的东西：
- media check 的退出码和 error / warn / info 计数；
- 往返测试的结果：全部真实 meta.yaml、backlog.yaml 原样 parse
  再序列化，逐字节比对，注释丢了几处；
- audit.jsonl 里能不能查到对应的写入行。
卡在哪和怎么绕过去如实填：卡住了写清楚卡在哪一步、报的什么错；
七天窗口这类还没跑完的出口条件，如实写验证方法已定、窗口进行中，
不许写成已经通过。
```

参考流水线自己那份施工记录，形状可以借来参考：按时间线记关键事件，按每个交付的部分记一条结论加关键发现，另开一节专门记裁决过的分歧点，末尾留一节人工待办，那些一课篇幅内没法验完的事，比如那条七天窗口，明明白白写成待办交给之后的自己。你自己这一份不用有它那么长的篇幅，但卡在哪和怎么绕过去这两栏不能省，这是这份记录跟一份验收通过的公告最大的区别。

五个字段落成表，长这样，方括号里是等你真跑出来再填的位置：

| 里程碑 | 出口条件 | 实际结果 | 卡在哪 | 怎么绕过去 |
|---|---|---|---|---|
| M1 | 真实仓库里跑 media check 能通过，YAML 文件里原有的注释一处都没丢 | ［填 check 的 error/warn/info 计数和退出码；填往返测试逐字节比对的结果，注释丢了几处］ | ［没卡住写无；卡住了写清楚具体报错原文］ | ［真解决了写解法；没解决写清楚留给谁接手、接手时先看哪里］ |
| M2 | 全仓状态写路径唯一，连续七天内元数据、选题池、看板机器区的每一次变更，都能在审计记录里找到对应的一行 | ［填 CHK-06 自测的 warn 数变化；填第 3 节抽查到的几条内容的状态经过是否完整；七天窗口如实写验证方法已定、窗口进行中］ | ［同上］ | ［同上］ |

这张表里最容易被填成模糊话的是实际结果这一栏。填了退出码 0 或者查到了对应行，才叫实际结果；填基本没问题看起来还行，等于没填。方括号里的话现在都是占位，交给以后的你或者接手的人，拿真实跑出来的数字和报错原文替换掉，替换不了的留着不删，让人一眼看出这一格还没填。

`03-施工记录.md` 落盘，模块 3 收口。

## 5. 收尾：状态中枢立住了，但不是所有动作都能自己拍板

这五课走完，`media` 收敛成了全仓状态改动唯一的入口，`check` 跑通、退出码干净，往返测试证明了 YAML 文件改完还是原来的样子，`audit.jsonl` 证明了每一次改动都留了痕迹，`03-施工记录.md` 也落了盘。这一课做到的，是把前面四课攒下来的东西从看着对变成有证据地对。还看不到的，是这套写入口自己会不会拍板：现在所有写命令都听人指挥，一条命令对应一次明确的意图，但下一步要往这套系统里接的飞书审核、定时发布这些环节，会有一部分动作不再是人一条一条敲命令，而是系统自己判断该不该往下走。这一步现在还没做，下一课开始补。

第 11 课定的六步方法，从第 12 课到这一课，第一次从调研走到验证，完整跑了一整轮，值得回头看看这一轮里哪一步的力气花得值。

调研和讨论选型那两步，第 12 课，当时看着最快。一次坐下来把入口形态、YAML 写法、并发保护、派生视图四组互斥路线拍了板，感觉像是走个过场。但拍板拍得清楚，才有了后面写 SPEC 时不用回头重新争论入口该长什么样的底气。如果当初这两步含糊带过，验证这一步很可能卡在一个更麻烦的地方：不知道当初为什么这么设计，也不知道现在这个结果算不算对。

写 SPEC 那一步，第 13 课，当时看着最费工。十四条命令逐条拆到参数、读什么、写什么字段、失败怎么报，一条都不能省，写的时候没少花时间。事后看，正是这一步救了这一课的场。这一课能拿出注释一处都没丢这种一句能跑的判据去验证，前提是当初写 SPEC 的时候就把每条命令的输出边界定死了，而不是含糊地写一句翻转状态就带过去。CHK-01 到 CHK-08 这八条规则也是同一个道理，要不是当初逐条列过判定什么，这一课没法拿它当自测清单直接用。

执行那两步，第 14、15 课，力气花在把规格变成能跑的命令、把存量迁移干净。这两步没有捷径可抄，规格写得再细，代码也得一行一行跑起来才算数，两课占的篇幅和花的时间都摆在那，谈不上多余，但也确实没有像写 SPEC 那一步一样反过来给这一课省下什么。

真正在这一课才显出价值的，是当初没觉得多要紧的一件小事：第 13 课那句提醒，规则表的字段名要按自己项目改名字再抄，不能连名字一起照搬。这一课自测 CHK-06 的时候，如果这条提醒没记住，第一反应大概率是怀疑 `check` 坏了，而不是回头查字段名对不对得上。

状态中枢立住了，机器能自己改状态。可有些动作改错了收不回来，哪些动作不能让机器自己拍板？
