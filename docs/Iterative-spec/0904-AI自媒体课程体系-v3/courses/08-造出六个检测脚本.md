# 造六个检测脚本：把检查点表变成能跑的契约

六个脚本能不能自动判断 PASS 还是 FAIL，在上一课给检查点分类时就已经确定了。凡是能写成明确断言的，就交给脚本自动判断；需要结合语境理解的，就只输出候选让人工确认。这一课的任务，就是把这条界线落实为六个能独立运行的检测脚本。

上一课把配音质检拆成了一张六行四列的检查点表：出错点、量什么、怎么量、阈值、谁来判。六项检查里，真相源不同步、合成不全、段内死气这三项归机器判；语速离群、多音字读错、组件大字与口播不一致这三项归人判。上一课结尾留了一个问题：表格整理好了，但怎么把它变成能跑出客观数字的脚本？

这一课的输入正是这张表，加上第 05、06 课跑通的那条内容的 `build/` 工程：`tts-dub` 合成配音时产出的分段文案 `audio-segments.json`，以及按段落生成的配音文件 `public/audio/<chapter>/<step>.mp3`。产出的成果很明确：一套完整的 `dubbing-check` skill，包括六个检测脚本、一个去停顿工具 `depause.mjs`，以及一份把它们串联起来的 `SKILL.md`。这一课无需手动写代码，脚本与工具全部交由 AI 产出，你主要负责定契约、审结果，并决定是否需要调整重来。

## 一、六个脚本的共同契约：先定形状，再动手写

一个检查能不能自动判 PASS 或者 FAIL，取决于所检测的指标本身有没有唯一的对错标准。真相源不同步、合成不全、段内死气这三项，检测逻辑是文本是否一致、文件是否存在、静音是否超过阈值。这些指标规则明确，符合条件就是有问题，无需结合上下文猜测。语速离群、多音字读错、组件大字与口播不一致这三项，虽然能测算出具体数字，但数字本身无法直接下定论。比如语速慢半拍可能是情绪表达需要放缓。多音字列出候选后，具体读音要结合上下文句意。组件上的大字和口播不一致，也要看画面展示的是并列提炼的关键词，还是逐字复述的完整句子。这三项检查该做的是把可疑候选列出来，把最终的裁决权留给人工审核。

这条界线承接了上一课定好的判据类型（能写成断言、只能靠人看、现在写不了）。目前的六项检查点全部属于前两类，第三类暂无对应项。六个脚本刚好覆盖这两类需求：三个负责断言 PASS 或 FAIL，三个负责输出风险候选。

在具体实现前，先固定三项契约：统一输入方式、统一输出格式、区分退出码策略。先把这三条规则用一条统一的 Prompt 规范下来，后续批量生成脚本时直接复用，每个脚本无需重复设计通用逻辑。

### 1.1 输入统一：都读 build/ 里的 audio-segments.json，用同一个工程目录参数

六个脚本拼装音频文件路径时，都需要明确 `build/` 的所在位置。如果每个脚本各自使用不同的参数命名，后续的裁判角色就需要适配六套调用方式，容易产生接口混乱。因此统一约定：脚本接收一个位置参数作为工程目录路径，缺省时使用当前目录。脚本运行时先读取该目录下的 `audio-segments.json`，再根据其中的 `chapter` 与 `step` 字段拼出 `public/audio/<chapter>/<step>.mp3` 的路径。这份文件每段记录一个章节、一个序号及对应文本，是六个脚本统一依赖的分段索引。

### 1.2 输出统一：每段一行 `✗`/`✓`，末尾一句汇总结论

为了让裁判快速定位问题段落，最直接的办法是规范脚本的打印格式。有异常的段落单独输出一行，标明问题类型与段落序号；正常的段落不单独输出，避免刷屏；执行完毕后输出一行汇总结论，清晰说明总检查段数与异常段数。格式统一后，裁判查看结果时无需适应多种排版，快速扫一眼是否存在 `✗` 标记，就能判断是否需要深入核对。

### 1.3 退出码分两类：完整性、死气、真相源同步判 FAIL 直接 exit 1；语速离群、多音字、音画一致只列候选，恒 exit 0

退出码是脚本向调用方传递状态的核心信号。属于硬门槛的检查，发现异常直接返回 `exit 1`，全部通过返回 `exit 0`。下一课的裁判只需检查退出码，就能明确是否需要拦截。属于候选类的检查，由于脚本本身无法独立断定正误，如果也返回 `exit 1`，容易干扰裁判判断，无法分清是真正阻断的错误还是待审的提示。因此候选类脚本始终保持 `exit 0`，其价值主要体现在打印出的候选清单中。

理清这三项契约后，让 AI 把对应关系整理成表格：明确脚本名称、对应检查点、分类归属以及退出码策略，为后续批量生成打好基础。

```
给这六项检查点定一份共同契约：都接受同一个“工程目录”参数，都读 audio-segments.json，
输出格式都是“每段一行结果 + 末尾一句汇总”；六项里，完整性、死气、真相源同步这三项属于能
写成断言的硬门槛，退出码按有问题 exit 1、无问题 exit 0；语速离群、多音字、音画一致这三项
只能列候选给人判断，脚本只打印风险点，不设 exit 1，退出码恒为 0。按这份契约写出一张六行表，
每行：脚本名 / 检查点 / 属于哪一类 / 退出码策略。
```

AI 交回来的表大致是这个样子：

| 脚本名 | 检查点 | 类别 | 退出码策略 |
|---|---|---|---|
| check-source-sync.mjs | 真相源不同步 | 硬门槛 | 有问题 exit 1，无问题 exit 0 |
| check-completeness.mjs | 合成不全 | 硬门槛 | 有问题 exit 1，无问题 exit 0 |
| check-silence.mjs | 段内死气 | 硬门槛 | 有问题 exit 1，无问题 exit 0 |
| check-pace.mjs | 语速离群 | 候选 | 恒 exit 0，只列风险点 |
| check-pronunciation.mjs | 多音字读错 | 候选 | 恒 exit 0，只列候选 |
| check-av-consistency.mjs | 组件大字与口播不一致 | 候选 | 恒 exit 0，只列候选 |

拿到这张契约表后，重点核对两处细节。
首先，核对分类是否与上一课划分的标准一致。六项应当清晰划分为三项硬门槛与三项候选。如果数量不符，常见原因是 AI 误将语速离群等仅能统计数值的项强行归入硬门槛，需要及时纠正。
其次，确认脚本名称与检查点严格一一对应，避免出现遗漏或一个脚本承担多项职责的情况。
确认表格无误后，就可以挑选一个典型检查项作为样板，为批量生成奠定基础。

## 二、先写样板脚本，再批量生成其余脚本

六个脚本在基础结构上高度一致，无需为每个脚本分别编写 Prompt。统一的契约已经规范了输入参数、输出格式与退出码策略，不同脚本之间仅在具体的判断逻辑上存在差异。因此，可以先让 AI 产出一个高质量的样板脚本。样板验证通过后，其余五个脚本直接参照样板结构批量生成，既保证了风格统一，也能大幅减少重复调试的工作量。

### 2.1 用完整性检查做样板

在三个硬门槛中，完整性检查的逻辑最为轻量。它只需检查音频文件是否存在、文件体积是否大于零、时长是否正常，以及总段数与 `audio-segments.json` 是否一致。这四项判断无需引入复杂的外部音频滤镜。选用完整性检查作为样板，能让 AI 快速写出规范的骨架代码。后续生成其他脚本时，只需替换核心的判断逻辑，输入路径解析、结果格式化输出以及退出码策略都可以直接复用。

```
按上一步的契约表，写 check-completeness.mjs：读 audio-segments.json，
逐段检查 public/audio/<chapter>/<step>.mp3 是否存在、非 0 字节、时长 > 0，段数与
audio-segments.json 一致；不一致的每段打印一行，末尾汇总，属于硬门槛，有问题 exit 1。
```

AI 交回来的骨架大致是这个样子：逐段核对文件，缺失或时长异常的打一行 `✗`，最后按有没有坏段决定退出码。

```javascript
// PRES 就是契约里定的那个工程目录参数，缺省用当前目录
for (const s of segs) {
  const mp3 = join(PRES, "public", "audio", s.chapter, `${s.step}.mp3`);
  if (!existsSync(mp3)) { console.log(`✗ 缺失 ${s.chapter}/${s.step}`); bad++; continue; }
  const dur = ffprobeDuration(mp3);
  if (!dur || dur < 0.3) { console.log(`✗ 时长异常 ${s.chapter}/${s.step} (${dur}s)`); bad++; }
}
console.log(bad ? `✗ ${bad} 段有问题` : `✓ 全部 ${segs.length} 段完整`);
process.exit(bad ? 1 : 0);
```

脚本生成后先执行一次，重点验收三个细节。
其一，检查输出的总段数是否与 `audio-segments.json` 记录一致。如果不一致，通常是路径拼接逻辑有误，未能正确匹配 `chapter` 与 `step` 对应的文件名。
其二，验证退出码是否准确。可以临时重命名一个音频文件制造异常，确认脚本确实返回退出码 1。
其三，确认打印格式符合约定，每段异常单独占一行，末尾附带汇总信息。
这三点验收通过后，样板脚本就算成功确立，后续脚本即可基于它快速派生。

### 2.2 参照样板批量生成其余脚本与 depause.mjs

样板确立后，剩下的五个检测脚本和一个去停顿工具，可以通过一条 Prompt 集中生成。
硬门槛中，真相源同步负责比对分段文案与源文案是否一致；死气检查通过 ffmpeg 的 silencedetect 滤镜扫描段内过长静音。
候选类中，语速检查负责计算发音字速并标记偏离段落；多音字检查负责提取多音字并给出上下文；音画一致检查负责将组件中文文本与对应口播文案并排呈现。
将这五项逻辑与此前定下的契约相结合，AI 便能一次性补全所有脚本。

```
照 check-completeness.mjs 的结构，按契约表剩下五行，依次写出
check-silence.mjs（死气检查，硬门槛）、check-source-sync.mjs（真相源同步，硬门槛）、
check-pace.mjs（语速离群，候选类）、check-pronunciation.mjs（多音字，候选类）、
check-av-consistency.mjs（音画一致，候选类），以及 rec/depause.mjs（去停顿工具，按
“去停顿不切词、不能原地写、跑完必须复扫”三条约束实现）。
```

前五个检测脚本的验证方式与样板相同，直接运行并检查退出码与输出格式是否合规即可。
去停顿工具 `depause.mjs` 的核对方式则有所不同。该工具属于文件处理脚本而非裁决脚本，不能仅凭退出码判断。重点在于三项安全约束是否落实：

1. 切除中段静音且不误伤字尾：在静音两端保留自然的呼吸气口。
2. 禁止原地覆盖写文件：当输入与输出路径相同时，ffmpeg 初始化输出可能清空输入文件，导致音频截断或损坏。稳妥的做法是先写入临时文件，处理成功后再覆盖原文件。
3. 处理后必须复测：使用 silencedetect 进行二次扫描，确认异常停顿已真正消除，不能仅凭进程正常退出就认定修复成功。

这三项约束来自真实的工程踩坑记录。在参考流水线的事故台账中（`pipeline/lessons.md`，编号 L16），曾发生过批量去停顿直接原地写入的问题。当时命令未报任何错误，但实际上静音完全未被消除。同时，过度裁剪会导致词尾发音被生硬削断。而仅看脚本执行状态，也无法确认静音是否被有效压降。
实际排查时可以留心两个现象。如果运行 `depause.mjs` 后音频时长没有任何变化，通常是误用了原地写入，需要检查是否先生成了临时文件。如果二次扫描依然提示超标，一般是裁剪幅度设定过于保守，微调目标时长后重新处理即可。

六个脚本加上 `depause.mjs` 准备就绪后，还需要统一打包，形成规范的操作清单。

## 三、打包成 skill：一份 SKILL.md 把脚本变成检查清单

脚本单独能跑，不等于后续的裁判角色可以直接调用。裁判需要知道执行顺序、每个检查点对应的脚本，以及如何解读输出结果。这份说明正是 `SKILL.md` 的职责，脚本本身并不承载编排逻辑。参考流水线里 `.claude/skills/dubbing-check/SKILL.md` 按开工前、合成后、录屏前、录屏后四个时机组织流程，那是针对全流程长链条的设计。当前聚焦的核心任务是从配音合成完到录屏前的质检，按照检查点表重新梳理即可。

六项检查点按执行时机可以分为三组。多音字读错仅依赖分段文案文本，无需等待音频生成，安排在合成前执行。真相源同步、合成不全、段内死气、语速离群这四项都需要读取生成的 mp3 文件，安排在合成后执行。其中真相源同步排在最前面，文案若不匹配，后续音频完整性检查便失去了基准。组件大字与口播不一致主要对照网页演示中的视觉组件文件，与音频文件无直接依赖，安排在录屏前的最终巡检中执行，避免录屏完成后才发现画面文案脱节。

```
把六个脚本和 depause.mjs 整理成 dubbing-check 的 SKILL.md：按检查点编号列出每个
脚本对应哪个检查点、怎么调用、退出码怎么读；末尾给一条“一页流程”，按合成前/合成后/录屏前
的顺序把六项检查点串成一条能贴在工位上的清单。
```

收到 `SKILL.md` 后，有一处容易疏漏的关键点需要核查：语速离群和多音字读错这两项候选结果，最终应该记录在哪个文件中，必须在文档中明确标出。落点对应 `pipeline/2-create.md` 中的配音审批闸口：统一记录在 `build/` 目录下的 `tts.config.json` 的 `overrides` 字段中，不另外新建分散的文件。这份文件是在当条内容构建时，从账号级模板 `brain/tts.config.json` 复制进 `build/` 目录的本地副本。参考流水线的踩坑记录（`pipeline/lessons.md`，编号 L18）明确指出，在增删段落后，需要同步重排该字段中的键。编写文档时应严格遵循这一规范，保持前后配置的一致性。

`SKILL.md` 落地后，整套 `dubbing-check` skill 就完成了初步封装：六个检测脚本、一个 `depause.mjs`，以及一份组织有序的 `SKILL.md`。

六项检查点已经落实为可执行的脚本，退出码也按断言与候选完成了分类划分。不过脚本目前只负责输出指标与候选清单，最终的合格判定依然依赖人工。下一课将引入独立的裁判角色，将机械的审核任务从人工手中交接出去。让负责写稿的 AI 自己审核自己的产出，是否可行？
