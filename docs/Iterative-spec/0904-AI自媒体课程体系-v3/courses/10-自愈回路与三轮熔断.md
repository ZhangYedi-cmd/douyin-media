# 自愈回路与三轮熔断：判、修、复判怎么接成一个能停下来的循环

一个自愈回路能不能真正发挥作用，关键在于它能否回答一个根本问题：回路在什么条件下应当终止。上一课确立了 `dubbing-reviewer` 代理的职责边界：只读不改，运行客观检测脚本，并输出 PASS 或 FAIL 的裁决。产出包括一份 `dubbing-reviewer.md` 子代理定义与真实的判决输出。本课的目标是将这一判决接入实际运转的回路。明确当判决为 FAIL 时由谁负责修复、修改后如何复判，以及多次复判不通过时的熔断机制。

本课的输入为上一课确立的 `dubbing-reviewer.md` 及其质检判决，结合第 05、06 课生成的工程资产（包括 `build/` 目录、合成音频与 `final.mp4` 成片）。本课产出是一份完整的实践记录：记录从初审 FAIL 到排查修复、重新合成并最终获得 PASS 的完整过程。本课的核心原则十分明确：自愈回路必须设定客观的终止边界。出口的标准在于是否存在明确公认的停止线。设定三轮上限是本项目的工程约定，属于权衡返工代价与修复概率后的实用选择，而非纯粹基于大样本统计得出的数学最优解。

## 一、回路的三个角色与交接顺序

自愈回路是判决、修复、复判轮流交接的过程，不同于简单的盲目重试。第 07 课曾梳理过这个四步循环：检查发现问题、判定修改方案、修复后重新生成，并使用同一标准再次核验。本课将这四步归入三个明确的角色：检测与判决归属于裁判代理，修改归属于主回话，修改完成后再次触发裁判进行复验。角色的职责边界始终保持独立，变化的是各个阶段的工作流转。

独立裁判角色的价值正在于此。如果生成音频与审查音频由同一个会话承担，审查时容易受到先前生成意图的干扰。一段听感欠自然的音频，自己评审往往容易放过。裁判坚持只读不改的原则，能够保证每一轮审查都基于客观标准进行评判。

参考流水线的 `dubbing-reviewer.md` 将判决输出标准化为固定结构：包含 PASS 或 FAIL 裁决、当前轮次编号、BLOCKING 阻断清单，以及 SUMMARY 总结。实际输出应至少涵盖三项核心信息：是否通过、当前轮次以及具体的阻断原因。后续提及 BLOCKING、ROUND、SUMMARY 等标签，均指代这类结构化信息。

与裁判交接时，主回话需要严格遵循纪律：仅修改判决中明确指出的问题段落，已通过的正常段落保持原状。判决涉及的问题主要分为三类，各自的修复落点有所不同：

第一类是配音输入配置层面的问题，例如多音字发音覆盖或单段语速微调。改动统一写入 `build/` 目录下的 `tts.config.json` 中的 `overrides` 字段。这里需要明确一处配置口径：参考文档中曾出现过写入独立文件的历史遗留描述，本体系已统一收敛至 `build/` 目录下的 `tts.config.json`，无需维护多份分散的配置文件。

第二类是文案层面的问题。比如英文缩写的读法统一（课程中称为 normalize，只调整发音，不改字幕）。又如同一段文案中同一个字需要读出两种音（同段两读，第四节将展开真实案例）。这类问题需要修改 `2-script.md` 原文。改完后需同步更新 `narrations.ts` 与对应组件，并重新提取分段文案，否则合成出的仍是旧内容。

第三类是段内死气问题，即段落内部出现非预期的长时间停顿（参考标准为超过 0.45 秒）。此时应针对判决指定的段落运行去停顿脚本，先输出临时文件再执行替换，严禁原地覆盖。

```
上一课 dubbing-reviewer 判过的这批音频，这次是 FAIL，判决里 BLOCKING 列了几条问题和改法。
按顺序逐条改：
1. 属于 tts.config.json 的 overrides（多音字、单段语速）：改 build 内的 tts.config.json，
   不改 brain/tts.config.json 那份账号级模板。
2. 属于文案层面的问题（normalize、同段两读）：改 2-script.md，同步 narrations.ts 和
   对应组件，跑一遍抽分段文案的命令重新提取。
3. 属于死气类问题：按判决给的段落跑去停顿脚本，写到新文件再替换，不要在原文件上直接覆盖。
只改判决里点名的段落，其余已经 PASS 的段落不要动。
改完在 build/ 里删掉这些段落的旧 mp3，重新跑一遍合成，再派 dubbing-reviewer 复审，
这次带上轮次号（第几轮，共 3 轮）。
```

结果返回后重点核查三项。第一，修改范围是否严格限定在阻断清单指定的段落内，修改未受影响的段落容易引入新的变量。第二，确认是否删除了旧音频文件，相关风险见下文说明。第三，指派复审时必须明确附带轮次编号，裁判需要依据轮次信息在达到上限时执行熔断。

若重新合成后试听音频毫无变化，常见原因是未删除旧有的音频文件。合成脚本检测到目标路径已存在同名文件便会跳过生成，导致配置修改未能生效。

确认回路能够流转后，还需要进一步限定其最大重试次数，以控制整体执行成本。

## 二、熔断线画在哪：三轮上限的由来

三轮上限是结合工程实际确立的运行约定。判决、修改、合成与复判这一完整周期，涉及较高的执行成本。修改文案需要同时维护 `2-script.md`、`narrations.ts` 以及相关组件三个位置。之后还要重新提取文案、清除旧音频并触发合成，最终才由裁判复审。任何一个步骤出现遗漏，都需要重新循环。参考流水线的裁判定义中明确要求保守裁决，避免将偶然的统计假象误判为阻断性问题。这也说明三轮机制是在特定工程代价下平衡产出与成本的经验值。在不同的项目环境下，合理的重试上限可能会有所调整。

| 熔断线 | 代价 | 已知问题 |
|---|---|---|
| 无限重试 | 容易卡死，问题难以收敛 | 持续失败通常属于结构性缺陷，盲目重跑可能破坏已有成果 |
| 1 轮 | 无法排除偶发误伤 | 单次判断存在误伤概率，裁判定义本身也要求保持审慎 |
| 3 轮（本课采用） | 循环代价在可控范围内 | 属于工程实用约定，参考裁判定义中达到第 3 轮后的处置规则 |

持续不收敛的失败通常属于结构性问题。质检中发现的缺陷大致分为两类。第一类可以通过调整参数直接解决，例如配置发音覆盖或切除停顿，这类调整通常能迅速收敛。第二类则无法单纯通过调参解决，必须跨文件修改原始文案。如果经过两到三轮针对同一问题的微调依然无法通过，往往说明当前的解决思路未能触及根因。盲目继续重试不仅无法修复，还可能引入新的不同步风险。

三轮上限机制在范围上按批次独立核算。它统计的是同一批待审音频的流转次数，而非整条内容生命周期内的总重试次数。裁判代理专注于合成后至录屏前的单批质检。如果在后续环节为该内容追加了新的文案并生成新批次，新音频的轮次将重新计数。这一机制主要防止单批音频陷入死循环。对于跨批次可能累积的返工成本，仍需人工关注整体进度。

明确了停止条件后，还需要规范终止时的状态记录与人工接管机制。

## 三、熔断落地：状态怎么记，人从哪接手

触发熔断的核心在于如实记录当前状态，并根据阻塞即上报的原则通知人工介入，避免问题悬置。现阶段通过手动更新 `meta.yaml` 进行记录，后续课节将收敛至统一的命令行管理工具。

当前 `meta.yaml` 中支持的状态包括 ideated、drafting、review 等，尚未引入专门的挂起状态。若经历三轮复审仍未通过，状态保持在 drafting，不随意新增非标准状态名。同时在文件中补充一行清晰的排障备注，记录阻断轮次与具体判决，方便后续接手排查。裁判最后一轮的完整 BLOCKING 内容需要完整记录到当条内容的 `3-review.md` 中，清晰列出遗留缺陷及已尝试的解决步骤，避免仅记录简短的停滞结论。

触发熔断时的关键原则是阻塞即上报，仅记录本地日志不构成有效上报。这一规则源于参考流水线的真实教训：曾因仅在日志中输出警报而未主动通知，导致流水线连续空转数日。在后续章节建立自动化通知渠道之前，目前可以通过约定的即时消息通知到责任人。上报内容必须包含三项要素：停滞节点、根本原因以及需要人工介入的明确事项。

```
这批音频到第 3 轮复审仍是 FAIL，dubbing-reviewer 的 SUMMARY 已经写了已达 3 轮上限。
按下面几步把现场收好：
1. 把这一轮判决的 BLOCKING 全文（问题、改法、卡在哪个环节）追加写进这条内容的 3-review.md。
2. meta.yaml 现在没有专门的挂起状态可用，让 status 留在 drafting，另外加一行
   清晰的说明，写清楚卡在第几轮、卡在哪条判决。
3. 按 pipeline/daily-run.md 阻塞即上报那条硬约束，在你约定的通道通知人，三件事写清楚：
   卡在哪、根因是什么、需要人做什么。只在本地写日志不算完成上报。
```

交付后重点检查两项。第一，`3-review.md` 中的记录是否能够让未参与前序流程的协作者快速理清阻断原因，如果仅记录失败二字，将无法支持后续的高效排查。第二，确认通知是否确实触达责任人，确保问题得到及时响应。

明确了判定、修复与熔断规则后，便可以在实际工程中运行完整流程。

## 四、跑一次真实的回路并留下记录

机制的有效性需要通过真实运行并留下完整的流转记录来检验。将前述规则串联，执行一次端到端的自愈流程：

```
合成第一批音频 → 派 dubbing-reviewer 判 R1
R1 FAIL → 按判决类别逐条修（overrides / 文案 / 去停顿）→ build/ 里重新合成
派 dubbing-reviewer 判 R2，带上轮次号
R2 PASS → 往下走到录屏那一步；R2 仍 FAIL 且已到 R3 上限 → 走上一节的熔断动作，不再重合成
```

在实际执行过程中，通常会遇到三类典型缺陷，可以对照排查。

死气类：去停顿脚本严禁原地覆盖写入。若将输入输出指定为同一文件，ffmpeg 在打开输出流时可能清空原文件，导致读取到空音频。此时命令可能依然返回退出码 0，掩盖真实错误。稳妥的做法是先写入临时文件，替换完成后调用静音检测脚本复验，确认死气数量真正归零。

如果运行去停顿脚本后音频时长未见任何变化，通常是误将输出路径设置成了原文件。

多音字类：在 `overrides` 中配置段落发音能够解决多音字问题。但在批量修改时需警惕漏配现象。若中途对文案段落进行了增删，会导致后续段落编号整体偏移。若未同步更新 `overrides` 中的段落键名，旧配置就会作用在错误的段落上。因此在调整段落结构后，必须重新梳理配置键名并重新提取分段。

若复审中反复提示同一发音未生效，常见原因是段落增删后未同步重排配置键名。

同段两读类：该问题属于无法通过单纯调参解决的结构性限制。例如同一句话中同一个字承担两种不同读音，而现有的音频参数配置以整段为最小生效单元，无法实现段内局部细分。此时唯一的解决路径是微调文案用词，从文本层面消除发音歧义。文案调整后需同步更新 `2-script.md`、`narrations.ts` 及相关展示组件，防止出现音画内容脱节。

若同一音频片段内多次出现读音冲突且难以调和，通常是碰到了同段两读的情况，应果断通过优化文案来化解。

流程走通后，将各轮次的执行时间、裁决结论、阻断项及修复措施整理归档，保存在该内容的工程目录下。

```
配音自愈记录（<日期>）
批次：<chapter>/<step 范围>
R1 判决：FAIL，BLOCKING：<列出问题与改法>
R1 到 R2 之间的改动：<改了哪几个文件、加了哪几条 override>
R2 判决：PASS
```

验收标准非常直接：文档记录应当详实完整，能够让其他工程师仅凭记录便能清晰复现当时的排查与修复轨迹。

自愈回路跑通后，基础流程已经具备弹性。后续还有几个体量更大的核心模块要构建（状态中枢、飞书闸口、控制台）。面对更复杂的工程目标，如何引导 AI 系统化地构建此类规模的模块？
