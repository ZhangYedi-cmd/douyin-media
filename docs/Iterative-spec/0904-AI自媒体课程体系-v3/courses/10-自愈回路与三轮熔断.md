# 自愈回路与三轮熔断：判、修、复判怎么接成一个能停下来的循环

一个自愈回路能不能真正用起来，先看它答不答得上一个问题：它什么时候该停。上一课（第 09 课·裁判与选手分离）给 dubbing-reviewer 划了一条干净的边界：它只读不改，跑客观检查脚本，给出 PASS 或者 FAIL 的判决。具体产出是一份 dubbing-reviewer.md 子代理定义，加一份真实的判决输出。这一课要把这份判决接进一个真正会转的回路：判完 FAIL 之后谁来改、改完谁来复判、复判还不过又该怎么办。

本课的输入是上一课那份 dubbing-reviewer.md 和它给出的判决，加上你自己第 05、06 课做出来的那条内容：build 工程目录、已经合成过的一批 mp3、还有那份真实存在的 final.mp4。产出是一件东西：一次真实发生过的 FAIL 到修到重合成到 PASS 的完整过程记录，存进这条内容的目录里。这一课要立住的判断只有一条：自愈回路要有客观出口。出口的标准，是有没有一条谁都认的停止线：三轮是这个项目自己定的工程约定，不是从数据里算出来的最优值。

## 1. 回路怎么接：判、修、复判轮流交棒

自愈回路是判、修、复判三件事轮流换人做的过程，跟单纯的失败重试是两回事。第 07 课定义过一个 Loop：检查出问题、判出该改什么、改完重跑、再拿同一条判据量一次，四步能自己转起来。这一课把这四步安进三个角色里：检查和判都归裁判，改归主回话，改完重跑之后再判一次，又回到裁判，角色本身没变，变的是每一步该谁做。

上一课把裁判独立出去的意义就在这：如果生成音频的和评审音频的是同一个角色，它天然会觉得自己给的参数没问题，一段听着别扭的音频，自己评审多半会放过。裁判只读不改这条边界，保证了每一轮判决都不是自己人给自己人打分。

参考流水线的 dubbing-reviewer.md 把每轮判决都写成同一套结构：PASS 或 FAIL 的裁决、当前轮次号、FAIL 时列出的 BLOCKING 问题清单、一句话的 SUMMARY 结论。你自己上一课写的判决，字段名不一定逐字对得上，但至少要能拿出这几样东西：判没判过、第几轮、卡在哪几条。后面提到 BLOCKING、ROUND、SUMMARY，指的都是这一类信息，不是要求你的字段名必须跟这个例子一模一样。

交棒的另一半是主回话这边的纪律：只改判决里点名的地方，已经 PASS 的段落不要碰。判决里的问题分三类，各自的改法落在不同文件上：

第一类是配音输入层面的问题，多音字、单段语速这类，改法落在 build 内的 tts.config.json 的 overrides 里。这里有个口径要点破：参考流水线里 pipeline/2-create.md 写的是改这份 build 内 tts.config.json 的 overrides，但 `.claude/agents/dubbing-reviewer.md` 那份定义里给的示例改法写的是 segment-overrides.json，两处不是同一个文件。这门课统一按 tts.config.json 的 overrides 来。你上一课写自己的 dubbing-reviewer 时，也把改法这一栏对齐到这一个文件，不要留着两个口径互相打架。

第二类是文案层面的问题，比如英文缩写的配音读法要统一（课程里管这类调整叫 normalize，只改配音听感，不改字幕原文），或者同一段音频里同一个字要读两种音，逐段注音解不了这种情况（同段两读，第 4 节会讲一次真实案例）。这两种都要改 2-script.md 本身，改完同步到 narrations.ts 和对应的组件，再跑一遍抽分段文案的命令，否则合成出来的还是旧文案。第三类是死气类问题，也就是段落内部的非自然停顿（参考流水线用的判据是超过 0.45 秒），按判决给的位置跑去停顿脚本，写到新文件再替换旧文件，不在原文件上直接覆盖。

```
上一课 dubbing-reviewer 判过的这批音频，这次是 FAIL，判决里 BLOCKING 列了几条问题和改法。
按顺序逐条改：
1. 属于 tts.config.json 的 overrides（多音字、单段语速）——改 build 内的 tts.config.json，
   不改 brain/tts.config.json 那份账号级模板。
2. 属于文案层面的问题（normalize、同段两读）——改 2-script.md，同步 narrations.ts 和
   对应组件，跑一遍抽分段文案的命令重新提取。
3. 属于死气类问题——按判决给的段落跑去停顿脚本，写到新文件再替换，不要在原文件上直接覆盖。
只改判决里点名的段落，其余已经 PASS 的段落不要动。
改完在 build/ 里删掉这些段落的旧 mp3，重新跑一遍合成，再派 dubbing-reviewer 复审，
这次带上轮次号（第几轮，共 3 轮）。
```

拿回结果审三件事。第一，改动是不是只落在判决点名的段落上，顺手改了没被点名的段落，等于给下一轮复审埋了一个新的未知量。第二，删旧 mp3 这一步有没有做，漏删的后果见下面这条排障提示。第三，派复审的时候有没有带轮次号，裁判需要知道自己是在判第几轮，真到第三轮仍不过，才能按下一节的熔断动作给出结论，而不是照着前两轮的口径继续判。

如果重合成之后播放出来的音频跟改之前一模一样，多半是没删旧的 mp3 文件，合成脚本检测到目标文件已存在就跳过了生成，配置改了但没生效。

环能转起来了，但没人规定它能转几圈。不停下来的话，代价谁来兜。

## 2. 熔断线画在哪：三轮不过就停，不是统计出来的

三轮上限是这个项目自己拍板的工程约定。判、改、合成、复判绕一圈，这一圈本身就不便宜：改文案要同步 2-script.md、narrations.ts、组件三处，改完还要重新跑一遍抽分段文案的命令，删掉受影响段落的旧 mp3，再重新合成一遍，最后才轮到裁判重新判一次。哪一步漏掉，整圈就要再走一次。参考流水线的 dubbing-reviewer.md 自己写得很直白：每一次 FAIL 都消耗主回话一轮重合成，判、改、合成、复判全部重来，代价大。所以裁判要保守裁决，只对真问题判 FAIL，不能把统计上的假象当真问题。这句话反过来也在提醒你：三轮是在这个代价结构下拍出来的板，样本不够撑出统计意义上的最优轮次。换一个项目，代价结构变了，答案未必还是 3。

| 熔断线 | 代价 | 已知问题 |
|---|---|---|
| 无限重试 | 卡死，问题不收敛 | 不停下来的失败多半是结构性的，继续跑只会破坏已经修好的段 |
| 1 轮 | 排除不了偶发的假 FAIL | 一次判决可能误伤，参考流水线的裁判定义里自己都强调要保守裁决 |
| 3 轮（本课用的） | 整圈重走一遍的代价可控 | 是项目约定，见参考流水线 dubbing-reviewer.md 里若 ROUND 已是 3 那条原文 |

为什么说不收敛的原因是结构性的。判决里的问题分两种：一种是参数能解的，改一条 override、去一段停顿，属于同一类动作反复调参数就能收敛。另一种是参数解不了的，得靠改文案这种跨文件的动作才能解开，第 4 节会具体讲一个这样的例子。如果第 2 轮、第 3 轮还在对着同一类问题用同一种改法反复试，判决已经在暗示这条路走不通，跟运气无关。继续跑只会在已经改对的段落上引入新的风险，比如漏做一步同步，让画面和声音又对不上。

三轮这条线还有一处局限，按批计轮：轮次数的是同一批音频的判、改、复判次数，跟这条内容从头到尾的总重试次数是两件事。参考流水线的 dubbing-reviewer.md 里写的是只审音频批次，合成后、录屏前这一段。如果你后面往这条内容里加了新的一段文案，产生了新一批合成，那批音频的轮次是从头计的，跟前一批用没用满三轮无关。这条线只保证单批音频不至于无限返工，一条内容被拆成好几批、每批各自蹭满三轮上限的情况，它管不到，真出现这种苗头，得靠人自己留意总的返工量。

停在哪定了，停下来之后状态怎么落、谁接手，还没写清楚。

## 3. 熔断落地：状态怎么记，人从哪接手

熔断做的是把状态如实记下来，按阻塞即上报的铁律推给人，问题不会被扔在原地不管。这一步现在只能手改 meta.yaml，因为还没有一个统一的状态命令入口，这是临时手段，第 15 课会把它收敛掉。

meta.yaml 里合法的状态值到目前为止只有 ideated、drafting、review 这几档，没有一个单独的挂起状态。三轮仍不过，就让它留在 drafting，不硬造一个状态名出来。另外加一行你自己看得懂的说明，写清楚卡在第几轮、卡在哪条判决，方便过后回来接手的人一眼看懂当时停在哪。裁判最后一轮的完整 BLOCKING 内容要写进这条内容的 3-review.md，不要只留一句停在这了。具体是哪几条、每条对应的改法都试过没有，都要留下来。

上报这一步，铁律是阻塞即上报，只写本地日志不算上报。这条铁律是参考流水线上真实踩出来的代价：那条流水线曾经连续六天空跑，日志里天天喊人，但只写日志没人看见。你现在手上还没有第 18、19 课才会造出来的飞书通道，先用你自己约定的方式通知人，哪怕是给自己发一条消息也算。但三件事要写全：卡在哪、根因是什么、需要人做什么。

```
这批音频到第 3 轮复审仍是 FAIL，dubbing-reviewer 的 SUMMARY 已经写了已达 3 轮上限。
按下面几步把现场收好：
1. 把这一轮判决的 BLOCKING 全文（问题、改法、卡在哪个环节）追加写进这条内容的 3-review.md。
2. meta.yaml 现在没有专门的挂起状态可用，让 status 留在 drafting，另外加一行你自己
   看得懂的说明，写清楚卡在第几轮、卡在哪条判决。
3. 按 pipeline/daily-run.md 阻塞即上报那条铁律，在你约定的通道通知人，三件事写清楚：
   卡在哪、根因是什么、需要人做什么。只在本地写日志不算完成上报。
```

拿回结果审两件事。第一，3-review.md 里的记录能不能让一个没参与前三轮的人看懂卡在哪，光写一句失败了没用。第二，通知有没有真的发出去，写进日志不算，得是一条你自己会看见的消息。

判、修、停三条路都定了，该真跑一次留下记录了。

## 4. 跑一次真实的回路，把它记下来

回路立没立住，看的是有没有一次真实发生过的 FAIL 到 PASS 记录，设计文档写得再完整也不算数。这一节把前三节定的三条路串成一次真实的走法。

```
合成第一批音频 → 派 dubbing-reviewer 判 R1
R1 FAIL → 按判决类别逐条修（overrides / 文案 / 去停顿）→ build/ 里重新合成
派 dubbing-reviewer 判 R2，带上轮次号
R2 PASS → 往下走到录屏那一步；R2 仍 FAIL 且已到 R3 上限 → 走上一节的熔断动作，不再重合成
```

真跑一遍多半会撞上三类缺陷，参考流水线上都留过真实教训，可以直接对照着排查。

死气类：去停顿脚本不能原地写。如果把输入输出写成同一个文件，ffmpeg 打开输出文件的瞬间就会把它清空，导致读取输入流时读到空数据，命令退出码却还是 0，看起来什么都没报错。参考流水线在这上面栽过一次，17 段音频全跑完，命令一次没报错，可实际时长一点没变，死气全留着。正确做法是先写到临时文件，替换成功后立刻用去停顿脚本自带的静音检测再扫一遍，扫到的死气数量必须是 0 才算这一处真的修好了，退出码不能信。

如果去停顿脚本跑完之后一量时长，秒数和处理前一模一样，多半是把输出路径写成了跟输入一样的文件。

多音字类：按段注音写进 overrides 能解决同一个字在不同段落该怎么读的问题。但参考流水线撞见过漏注音的情况：一段文案里连着十几行都出现同一个字，本该按行业里的读音读，结果被读成了另一个读音，第 1 轮判 FAIL 重合成才补上。还有一种更隐蔽的错法：段落中途做了增删，后面的段号整体挪了位，但 overrides 里的键还留着旧编号。注音就会注到错的段上，旧键变成没人用的死键，新段反而漏了注音。增删段之后必须先重排 overrides 的键，再重跑一遍抽分段文案，键位和段号才能对得上。

如果复审总是同一个字被打回来，多半是段号变过之后 overrides 的键还留着旧编号，得重排键再重跑一遍抽取。

同段两读类：这是三类里唯一没法靠调参数解决的。参考流水线记过一次真实案例，同一段话里同一个字要读两种音：前半句就得打折的得读必须的必，后半句诚实得多的得读轻声的的。逐段注音只能解决同一个字在不同段落该怎么读，解决不了同一段里同一个字要读两种音这种情况，注成前一种读法后半句就读错，注成后一种前半句又读错。这种局部死锁没法靠改配置解，唯一的路是改文案，把其中一个得换成别的说法，把冲突从读音层面挪走。改完要同步三处真相源：2-script.md、narrations.ts、还有对应的组件，三处漏了一处，就会出现声音已经改了、字幕还是旧词这种音画不符。

如果同一段音频里同一个字听感总有一处别扭，注音怎么调都调不对，多半是同段两读，注音解决不了，得改文案。

三轮走完，把每一轮的时间、判决、BLOCKING、改法整理成一份记录，存进这条内容的目录，格式不用太讲究，能让后面的自己看懂当时发生了什么就够。

```
配音自愈记录（<日期>）
批次：<chapter>/<step 范围>
R1 判决：FAIL，BLOCKING：<列出问题与改法>
R1 到 R2 之间的改动：<改了哪几个文件、加了哪几条 override>
R2 判决：PASS
```

判断标准很具体：把它给一个没参与这次自愈的人看，他能不能照着走一遍你刚才做的事。能，这次从 FAIL 到 PASS 的完整过程就算立住了；不能，说明记录里漏了关键的一步，得补。

自愈回路合上了。可你一路走来手改了一堆 meta.yaml，后面还有几件大得多的东西要造（状态中枢、飞书闸口、控制台）。一条 prompt 不够用，怎么让 AI 造这种量级的东西？
