# 反馈信号从哪来：把配音质检拆成能写成断言的六项检查点

一个自愈回路能否稳定运转，关键在于其输入信号在编写脚本之前是否已得到严谨定义。本课以配音质量检测为例，将这一原则拆解为具体的判定基准。语音数据是具体载体，核心在于提炼出客观可执行的工程指标。

上一课交付了一张填完第 4 列的验证信号去向表。四个去向分别是流向人、流向机器、流向文档与流向没人管，明确了哪些环节应当交由程序承接。既然要交由程序承接，前提是具备明确的输入信号。本课的任务就是为流水线上的首个自愈回路确立信号源。完整的回路包含四个环节：检测异常、定位修正项、更新重跑、复查检验。回路顺畅运转的基石在于第一步：检测环节度量的指标必须清晰，获取的数值必须客观可信，否则后续的判定、修正与复查都将失去根基。

本课聚焦的范围，是去向表中标记为机器的核心区间：从配音合成完毕生成一批 mp3 文件，到正式启动视频录屏之前的校验阶段。本课的输入包括该区间内的各检查项、你在第 05 课合成配音时实际碰到的问题、在第 03 课编写并持续复用的 `pipeline/2-create.md` 中的配音审批闸口，以及 `brain/tts.config.json` 配置文件。最终交付物是一张配音批次检查点表：六行四列，行维度代表异常类别，列维度包含度量指标、采集方法、判断阈值以及判定主体。具体的脚本代码编写将放在下一课展开。

## 一、检查点候选的两个来源

检查点应当基于去向表中已标记为机器的单元格反推梳理。如果脱离实际流程凭空罗列，极易发生遗漏。一旦漏掉关键检查项，往往要等到成片录制完成后才暴露问题，届时只能重录，返工代价极高。

检查项候选主要来自两个现实依据。第一是你在第 05 课配音合成及核对时实际碰到的问题。例如某段 mp3 为 0 字节（限流或合成失败残留的空文件）。又如某段存在多音字读错，某段语速明显偏快或偏慢。以及抽帧核对字幕与时长时发现某一步画面被提前截断。

第二是第 06 课验证信号去向表中标记为机器的单元格，结合你在 `pipeline/2-create.md` 中写下的配音审批闸口。目前这道闸口只有原则性描述，缺乏具体细则，本课需要把核验细节补充完整：

```
下面是我第 05 课配音合成完自己核对时碰到过的问题（贴清单：0 字节的 mp3、读错的字、
特别快或特别慢的段、字幕和时长核对时发现的画面切断）。
下面是我上一课整理的验证信号去向表（贴表格内容），标“机器”的格子对应的就是这些问题。
我自己 pipeline/2-create.md 里配音审批这道闸口现在只有一句话，没有细节。
把这些问题整理成候选检查点清单，每条一句话说清测的是什么，先出清单不写脚本。
```

AI 返回清单后需要把好两道关。第一，核对每一条能否追溯到第 05 课的实际报错，或者对应去向表中标记为机器的格子。无法溯源的条目通常是 AI 凭空填充的通用常识，应当予以剔除。第二，核对每一条定义的是否为具体的物理特征。“音质不佳”属于模糊描述，无法直接计算；而“某段 mp3 字节数为 0”或“某段多音字命中读音候选”则是可测指标，可以直接转换为程序判断逻辑。

若 AI 输出的清单条目过少，常见原因是其仅照搬了第 05 课的表面报错，未进一步抽象为类别。例如“某个字读错”这一具体现象，向上归纳即为“多音字注音匹配”这一通用检查类别。

在参考工程的实际运行中，从配音合成到录屏前沉淀出了六类成熟检查项。分别是真相源一致性核对、音频合成完整性、段内异常停顿检测、分段语速离群识别、多音字注音匹配，以及组件文本与口播文案对齐。这六类指标均来自历史踩坑与返工经验。

其中完整性、语速离群、多音字、音画一致四类，与第 05 课遇到的问题一一对应。0 字节文件对应完整性检查。过快或过慢对应语速离群。读错字对应多音字检测。画面文字与语音脱节对应音画一致。至于真相源同步与段内停顿两类，在初期制作中可能暂时还未遇到。但随着制作批次增加，这两类问题终会出现，提前纳入规范能有效规避后续返工。

对照上述六类标准复核你整理出的候选清单，查漏补缺。最终确立的六个检查项为：真相源不同步、合成不全、段内死气停顿、语速离群、多音字读错，以及组件大字与口播文案不一致。此处的组件指网页演示各章节的前端代码文件，屏幕上呈现的大标题即定义在此处，与口播文案分别维护在不同文件中。

六项检查指标明确后，其中部分可以直接由程序自动判定，另一部分则依赖人工审校。若混为一谈，会导致检验结果公信力受损。

## 二、三条判据：能不能现在写成一句断言

一项检查能否接入自动化回路，取决于它当下能否转化为确定性的逻辑断言，而与该指标的主观重要程度无关。本节将六项检查按三个去向进行分类。第一类可写成断言，指标无需复杂语境即可得出是非结论。第二类需人工介入，指标数值虽然可测，但同一数值可能对应正常与异常两种业务情境，必须结合具体语境甄别。第三类当下无法编写，指标尚缺乏稳定的数据源支撑。

划分归属的标准非常直接：该项检查是否存在可量化的客观指标，且该指标无需附加主观语境即可得出明确的是非结论。

真相源不同步、合成不全、段内死气三项，符合上述标准。文本是否一致、物理文件是否存在、静音区间是否超时，代码获取到对应数据后即可直接得出判定，无需人工介入复核。这三项归入可编写断言类，判定主体标记为机器。

若将这三项交由人工逐一核对，效果反而会打折扣。人工试听整段语音时，容易被语调和节奏吸引，难以察觉某些近义词的微小替换。在参考流水线的实操中曾出现过类似情况：修改文案后未重新提取分段文本，录音依然沿用旧文本，导致声画脱节，人工连续核对两轮均未发现。程序进行逐字逐字符比对则不会遗漏此类细节。

语速离群、多音字读错、组件大字不一致三项，则不符合上述标准。

在语速检测中，数值虽然能够测算，但同一数值存在多种合理解释。如果某段文案包含密集的专业英文缩写，实际发音耗时通常会超出中文字数折算的预期。按字数折算的语速数值会偏低，这属于度量折算机制引起的偏差，并非发音拖沓。真实的发音拖沓与此类结构性偏差在数值上无法直接区分，只能由人工试听甄别。

若强行将语速离群设定为机器硬性阻断，超过固定阈值即打回重跑，将带来负面效应。英文缩写密集的段落会被反复打回重新合成，耗费算力且无法解决问题，真正存在语速异常的段落反而容易被掩盖。

在多音字检测中，程序能够根据字表扫描出潜在多音字，但无法仅凭字形确认读音是否准确。且云端合成接口的读音标注通常作用于整段，若同一段落中同一多音字需要使用不同读音，全局标注反而会引发冲突，此时往往需要调整文案本身。

在组件大字检测中，程序能够提取前端文件中的中文标题并与口播原文并列展示。但在界面呈现中，部分概念标签属于概括性关键词，与完整口播句子并不同构，不能简单判定为内容冲突。只有当逐字呈现的核心主标题出现错别字或断句偏差时才构成缺陷。这种层级关系的甄别同样超出单纯字符比对的能力范畴。

因此这三项归入依赖人工判定类，判定主体标记为人工。自动化脚本负责提取数据并呈现候选异常，最终确认保留给人工拍板。

第三类指标指当下缺乏数据支撑的维度，例如判断选题是否精准切中了即时热点。由于缺乏稳定的结构化输入源，配音阶段的候选指标中不包含此类内容。

若为追求形式完整而为这类维度生造一个硬性阈值，例如规定命中三个关键词即视为合格，判定结论缺乏客观依据。既无法拦截真实问题，又会造成误报。长此以往会导致整个质检机制失去可信度。

```
把上一步的候选清单按三类分：①能写成断言的（客观可测，如时长/存在性/文本是否一致）；
②只能靠人看的（语气/观感这类主观判断）；③现在写不了但以后能写的（缺数据源，如“是否押中热点”）。
每条给一句话说明属于哪类、为什么。
```

完成归类后，能写成断言与依赖人工核验的两类条目均需纳入最终的检查点表：前者由程序执行判定，后者由人工执行审核。量化指标与采集手段必须在表中明确记录。

## 三、六项检查点定案，以及 overrides 落在哪

阈值的设定必须基于历史实际返工经验推导，避免凭空拟定数值。同时，参数覆盖应当记录在规范约定的配置文件中，保证各环节标准一致。

### 3.1 六项定案

将分类后的六个检查项填入四列表：度量指标、采集方法、判断阈值以及判定主体。在阈值一栏中，有历史案例支撑的需注明出处；缺乏出处依据的则如实记录，仅作为排序参考，不作为硬性阻断依据。

| 出错点 | 量什么 | 怎么量 | 阈值 | 谁来判 |
|---|---|---|---|---|
| 真相源不同步 | 分段文案与章节 narration 对应段原文 | 逐段逐字精确比对 | 文本不一致即判异常，无容忍区间。参考流水线曾发生改文案后未重新提取文本，导致成片声音滞后的事故 | 机器 |
| 合成不全 | mp3 文件存在性、字节数、音频时长及总段数 | 按分段文案逐段核验 mp3 属性 | 文件缺失或总段数不符即判异常。文件字节数与时长偏小用于识别空壳文件，不作为绝对卡点 | 机器 |
| 段内死气 | 段落内部非句读停顿位置的静音时长 | 调用 ffmpeg silencedetect 滤镜捕获静音区间，提取内部停顿。处理后需基于产物二次复扫验证 | 停顿超过 0.45 秒判定异常，低于 0.45 秒放行。0.45 秒来自参考工程的返工经验起步值，后续可结合实际微调 | 机器 |
| 语速离群 | 剔除停顿后的纯语音发音速率 | 计算各段语速数值并排序，标出偏离平均值的段落 | 无绝对事故阈值，数值用于辅助排序并提示优先试听，不作为机器硬性拦截依据 | 人 |
| 多音字读错 | 文案中出现的多音字及其上下文读音 | 依据多音字表扫描各段文案并提取候选词 | 无自动阈值，命中候选均需人工确认。若单段包含读音冲突，需评估调整文案 | 人 |
| 组件大字不一致 | 演示界面逐字展示的标题文案与口播原文 | 提取前端组件中文字符串，与对应口播文案并列展示 | 无自动阈值，仅核心标题表达冲突时判定异常，概括标签不作冲突处理 | 人 |

表中将真相源不同步置于首位。当文案源头出现脱节时，音频文件是否完整已经失去检验意义，即便文件齐全也是旧版文案。

合成不全的阈值区分两个层次。物理文件缺失与总段数不匹配属于明确的硬性错误。而文件体积与时长过短则用于排查异常空壳文件。正常文件与异常空壳在体积上相差数倍，两者界限十分明确。

```
把“能写成断言”的检查项整理成表格，四列：量什么 / 怎么量 / 阈值 / 谁来判；阈值旁边
写一句这个数字是从哪个真实问题倒推的；再补一句：这批检查项发现的问题，改动都写进 build
内 tts.config.json 的 overrides 字段，不新建别的文件。顺带把这条规则补进我自己
pipeline/2-create.md 里配音审批那一段：配音质检发现的问题，改动进 build 内
tts.config.json 的 overrides，沉淀性规则回写 brain/ 里的账号级模板。
```

### 3.2 overrides 落点：判完的结论记在哪

语速与多音字审校发现的问题必须有清晰的落盘位置，避免结论遗失。规范的保存位置是 `build/` 目录中 `tts.config.json` 的 `overrides` 字段。该字段支持按段落覆盖语速、音高与注音，全局默认字段则保持原样。该数据结构在第 04 课完成了初步预留。第 05 课的 `tts-dub` skill 则固化了结构定义：以 segment id 为键，逐段声明 speed、pitch 与 pronunciation 配置。

账号级模板在制作开始时会被复制至具体内容的 `build/` 目录下，合成脚本直接读取该工作区副本。在质检过程中发现的特定微调参数，统一写入此副本中，仅对当前内容生效。只有具备通用价值的专有名词读音规则，才同步回写至 `brain/` 下的全局模板中，供后续制作继承复用。

该项规则需要补充至你的 `pipeline/2-create.md` 契约中。通过上一环节的提示词，AI 会将该约定更新至配音审批章节，使后续闸口具备明确的落地指引。

`overrides` 的字典键采用章节与步骤编号组合命名，指向具体的分段位置。在修改注音重新合成后，若特定段落读音未发生变化，常见原因是分段结构调整导致段落编号发生了偏移。增删文案分段会引起后续编号位移，此时键名需要同步调整，避免参数覆盖落空。

## 四、从检查点表到可跑的脚本

将适宜机器处理的检查点拆解为能够表达为断言的结构，明确了度量指标、采集手段、判断阈值与判定归属，统一了微调参数的保存位置，并在 `pipeline/2-create.md` 中完善了对应契约规则。此时检查点表已经成型。虽然尚未编写提取数字的测试代码，但六项核心指标的量化方式、阈值标准和判别归属已经全部清晰落地。

下一课我们将把这六项指标逐一转化为可实际运行的自动化校验脚本。
