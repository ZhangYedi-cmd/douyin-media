# 账号大脑：五份文件怎么写

在上一课中，我们搭好了一个结构完整的骨架仓：目录树按职责划分清晰，`pipeline/`、`content/`、`brain/`、`harness/`、`tools/`、`docs/` 各尽其责，`CLAUDE.md` 总纲也已就绪。`pipeline/` 下的四份阶段契约（`1-ideate`、`2-create`、`3-review`、`4-publish`）分别明确了输入、输出、状态翻转与闸口规则，`daily-run` 负责统筹当天的执行顺序。`content/_template/` 模板目录与 `backlog.yaml` 头部注释也已准备妥当。阶段契约规范的是文件流转与环节衔接：选题结果保存在哪里、创作环节读取哪份文件、审批卡片在何时推送。但具体到当天应当挑选哪条选题、口播稿应当保持怎样的语气，这些核心判断依据目前在仓库里还是空白，`brain/` 目录依然空着。

这一课的输入，是你对账号定位、人设特征、语言风格以及素材来源的构想。产出是 `brain/` 目录下的五份说明文档（`positioning`、`persona`、`style-guide`、`sources` 四份填入具体规则，`benchmarks` 规范留空）以及一份 `tts.config.json`，共计六个文件。

在编写这几份文档时，我们需要贯穿一条核心原则：规则必须可判定、可执行。比如写“技术深度与流量型选题比例为六比四”，下游选题环节就能依照确切数字排定日程。如果写成“以技术深度为主兼顾流量”，下游就很难推断具体的排产倾斜，只能凭借主观感觉猜测。这条可判定原则是我们审阅大脑文件的关键尺度，接下来每一份文档都要对照它仔细核对。

## 一、positioning 与 persona：账号是谁、对谁说话

我们要先明确账号的角色定位与目标受众。这两项基础若界定不清，后续的语气规范与素材源文档就容易失去依托。定位和人设文件需要写成能够直接指导排产的具体判断句，尽量避免抽象的形容词堆叠。比如“技术深度与流量型选题比例为六比四”可以直接用于排班，而“内容有深度且有趣”则无法作为具体的执行依据。

`positioning.md` 管的是取题规则，规格如下：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 内容比例：深度和流量怎么排产 | 给一个具体数字，选题那一步能照着混排 | “以深度为主兼顾流量”，排不出今天该做哪条 |
| 目标人群：讲给谁听 | 分类列出，每类写清他们想从内容里拿走什么 | “泛 AI 关注者”，泛到选题时随便一条都能套上 |
| 不做什么：什么题一眼否掉 | 每条能对着一条具体选题当场判真假 | “不做低质量内容”，没有给出评判低质量的清晰标准 |

内容比例中的数值会被下游模块直接读取消费。在上一课编写的 `pipeline/1-ideate.md` 中，输入文件列表中包含了 `positioning.md`。选题环节需要从中读取出量化的配比，用以决定当天优先选取深度题还是流量题。如果写成主观形容词，算法和流程就失去了可量化的依据。

在让 AI 起草定位文件时，建议分步推进，不要让它一次性直接生成落盘文件。当业务方向存在多种可能时，先让它梳理候选方案，我们便于对比选优。

```
我要做一个 [账号方向，例如 AI 工程提效和源码解读] 的抖音账号。
先不要写文件，给我三个内容支柱划分方案，每个方案讲清楚：
1. 分几个支柱，各自面向哪类观众；
2. 支柱之间按什么比例排产，这个比例要能落成一个数字，
   给下游选题环节直接用；
3. 这个方案的不做清单，每一条要能对着一条具体选题当场判真假，
   不要写“不做低质量内容”这种谁都读不出标准的话。
三个方案要有实质差异，不要同一个方案换几个词充数。
我选定一个之后，你再写 brain/positioning.md。
```

方案选定后，重点检查三项要点。第一，内容比例是否给出了明确的数字配比。第二，不做清单中的每一条是否容易快速判定。边界模糊的规则要调整到能够明确区分，定不准的可以先移除。第三，目标人群部分是否夹带了未经核实的受众规模或增长率等预测数据。这一项在日常生成中较为常见。目标人群如果出现了宏观市场规模或增长数据，通常是 AI 参照商业报告模板自发补充的内容，这些未经验证的数据不应保留。我们在 `CLAUDE.md` 中约定了不编造事实与数据的红线，此时要求 AI 移除这些无据可查的修饰内容即可。

`persona.md` 由创作环节读取，专门约束文案的语气与口吻。如果语气规则写得过于抽象，创作环节就会缺乏明确的质检标准：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 口播语气：这段话该用什么调子说 | 写成创作那步能对着稿子逐句核对的条目，例如第一人称、开口三秒给钩子 | “语气要生动有趣”，稿子写成什么样都能自称生动 |
| 禁忌：什么话不能说 | 只写能判定的，例如不堆术语装高深、不空喊太强了 | “不端着”，端不端着看谁的感受，判不了 |
| 待补充：尚未明确的事项 | 暂时无法确定的规则先留白，整理为清单，避免随意填补 | 过早固定开场白，一旦后续发现不够自然，前期已发布的文案修改成本很高 |

```
按 brain/positioning.md 的定位写 brain/persona.md，分四块：
人设一句话、口播语气规则、图文语气规则、禁忌。
约束：
1. 语气规则要写成创作那一步能对着稿子核对的条目，
   例如第一人称、开口三秒给钩子、术语必须解释，
   不要写“生动有趣”这类无法核对的词；
2. 禁忌只写能判定的，例如不堆术语装高深、不空喊太强了；
3. 还没定的东西留成待补充清单，不要替我编，
   比如固定开场白、固定结尾引导语、账号自称。
```

文档生成后，建议首先检查待补充清单。如果清单被填得满满当当、一项不剩，常见原因是 AI 按照常规套路自动补全了未定内容。此时建议把未经推敲的条目重新移回待补充清单，等业务实践充分后再行补充。接下来，拿一段现成的文案对照语气条目，检查是否能够逐句核验；再逐条审视禁忌条目，确认每项规则是否具备清晰的判别标准。

`positioning` 与 `persona` 共同明确了账号的身份定位与目标受众。这两份文档梳理清楚后，接下来需要借助另外两份文档，将这些宏观判断拆解为可操作的执行规范。

## 二、style-guide 与 sources：怎么说话、素材从哪来

语气规范与信息源两份文档，需要转化为具体可执行的工程判据，例如明确的禁用词表、句式示例、信息源分类与检索参数。如果仅写成“口语化”或“生动有趣”这类模糊要求，执行时便缺乏明确的操作依据。这两份文档分别由创作与选题阶段调用，在 `pipeline/2-create.md` 的输入节中，明确依赖了 `persona.md` 与 `style-guide.md`。

`style-guide.md` 管视听工程规范，时长、结构、张数这些量都要落成数字：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 口播时长与结构：视频多长、怎么排 | 给区间秒数和分段结构，能拿秒表核 | “节奏明快”，快到什么程度秒表核不了 |
| 图文张数与配图风格：单条几张、什么调子 | 给可数的张数上限和风格归类 | “排版美观”，美不美看感觉，核不了 |
| 违禁词与视觉资产：什么词不能出、封面模板长什么样 | 现在给不出具体内容的就留白，等真被判过一次再填 | 照平台公开合规规范抄一份长清单，和账号实际会踩的点对不上 |

```
写 brain/style-guide.md，六块：标题钩子套路库、口播时长与结构、
字幕与封面、图文张数与配图风格、违禁词与合规、视觉资产。
约束：
1. 时长、张数、结构这三块全部给出明确可数的量化标准，
   例如时长区间、单条几张以内，不要写“节奏明快”这类词；
2. 标题钩子写成套路名加一个示例句，给出模板结构与示例，
   便于依样套用；
3. 违禁词清单和视觉资产这两块，我没给你具体内容的就留成待补，
   不要照平台公开合规规范抄一份长清单充数。
```

在准备合规规则时，很容易产生一次性填满清单的想法。市面上确实能找到很多通用的平台合规词库，但直接搬运过来的词条，往往与账号实际遇到的审核规则并不匹配。哪些表达容易触发审核预警，通常需要结合实际发布反馈来逐步积累。因此，前期对于尚未明确的违禁词适当留白，遇到实际问题再逐条沉淀，反而比在一开始就加载冗长的通用词库更加精准高效。

`sources.md` 由选题环节读取，为自动化抓取提供入参，因此需要整理成可供检索直接调用的词表，单纯罗列平台名称并不足以支撑自动化执行：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 素材源：去哪抓 | 按用途分类列平台，时效类和沉淀类分开 | 把时效源和沉淀源混一张单子，选题分不清今天该往哪边抓 |
| 关键词矩阵：用什么词检索 | 分层给词，每层判据不同，字数可数 | 一层里全塞近义词凑数，检索不出增量结果 |
| 对标账号：谁是参照 | 指向 `benchmarks.md`，不在这份文件里重复维护 | 在 `sources.md` 里又列一遍对标账号，两份文件对不上时不知道信哪个 |

关键词矩阵分三层。`douyin-ideate` 是第 23 课才会造的选题技能，现在还没有它，但这三层词表就是留给它用的骨架：

```
按 brain/positioning.md 的支柱写 brain/sources.md 的关键词矩阵，分三层：
Layer A 平台体裁词：同类内容在这个平台上以什么形式在火，5 个左右；
Layer B 深度域词：对应技术深度支柱的具体技术名词，10 个左右；
Layer C 流量信号词：追新闻和新模型热度的词，7 个左右。
每层给词就行，不要写解释性长句。
词表下面加一句：这是起步值，复盘时标注哪个词出的选题更火，动态增删。
凑不满某一层就少给几个，不要用近义词凑数。
```

这三层词表的关注维度各不相同。Layer A 关注能否准确描述内容载体形式；Layer C 关注热点时效，随着行业变化通常需要定期更替。Layer B 则承担双重职责：既作为检索种子，又负责为选题打上技术标签。因此这一层允许保留少量概括性词汇，但如果全部填入宽泛词，检索的针对性就会大打折扣。如果发现 Layer B 中大量充斥着“大模型”或“AI 工具”等泛化词汇，往往是在分类时把体裁词与技术词混在了一起，建议按照层级重新拆分梳理。

关于规则必须可判定的原则，我们来看一组对照示例：

- 正例：口播 30 到 90 秒，深度内容可以到 2 到 3 分钟。创作环节可以用秒表精准核验，时长是否超标一目了然。
- 反例：节奏明快。快到什么程度缺乏量化标准，执行时无法客观把关。

前四份文档的核心规则梳理完毕后，第五份文档 `benchmarks.md` 目前需要暂时保持留空。

## 三、benchmarks：为什么现在留空

对标账号的选择与有效打法的总结，必须建立在真实数据的基础之上。在账号启动初期，由于尚未发布任何内容，我们并没有自己的实测数据。如果此时提前录入未经检验的外部推论，在后续选题打分时就会产生偏差。我们在 `CLAUDE.md` 中约定了不编造事实与数据的红线，落实到 `benchmarks.md` 上也是同样的原则：坦诚留白并注明生效触发条件，远比填入缺乏佐证的推测更有价值。

`benchmarks.md` 的文件头部需要明确约定四项原则。第一，这份文件管辖什么，包括对标账号、爆款拆解以及自身验证过的打法。第二，谁拥有修改权限，治理线复盘只产出变更提议，经人工审批通过后才允许回写。第三，何时录入首批数据，必须等到首批内容发布且复盘沉淀出真实指标之后。第四，每条有效打法必须附带哪些凭证，包括对应的作品样本、同向数据指标以及复盘报告路径。

规范凭证是确保长期维护可靠性的关键。在启动阶段保持留白，客观上意味着起步期选题缺少定制化数据加持。在参考账号的演进过程中，`benchmarks.md` 中的有效打法栏目，也是在内容持续发布近一个月后才正式沉淀出第一批实证打法。在这段过渡期内，选题打分主要依赖通用经验摸索，相关过程记录在复盘日志 `harness/logs/2026-07-17-retro.md` 中。明确这一客观过渡规律，有助于我们在冷启动阶段保持理性预期，耐心积累真实的反馈数据。

```
写 brain/benchmarks.md 的骨架，不要编任何账号或数据。
只要两块：
1. 一句留空说明：这份文件要靠真实播放数据才写得出来，
   在第一批内容发布并复盘之前，正文留空；
2. 待填字段名清单：以后每条打法要带的字段，
   例如打法名称、适用赛道、证据（几条内容、几个数据点同向、
   报告文件路径）。
不要给出任何示例数字，字段名可以举例，但不许编造具体的
账号名或播放量。
```

文档生成后，重点检查三项要求：正文是否杜绝了杜撰的数据或账号名称；字段清单是否包含了同向指标与报告路径等可溯源要素；留空说明是否交代清楚了生效节点。如果 AI 主动填充了几个看似具体的示例账号，通常是出于模板完整性的习惯性补充。对于未经实际业务检验的账号名称，建议统一清理干净，保持骨架纯粹。

文本层面的业务判断梳理完毕后，还剩下最后一项关键工程配置：自动化配音的参数规范。

## 四、tts.config.json：音色、语速、多音字规则

配音相关的工程参数变动相对频繁：更换音色、微调语速、修正缩写发音或纠正个别多音字。这些参数全部集中存放在配置文件中，脚本仅负责读取解析。这样一来，日常调参无须修改任何业务代码，也避免了在不同脚本间排查硬编码参数的隐患。在第 07 至 10 课的配音质检流程中，多音字修复需要依托配置中的 `overrides` 字段来承接，这项规范在当前阶段就需要确立下来。

| 键 | 管什么 | 什么时候改 |
|---|---|---|
| `provider` / `voice_id` | 用哪家合成服务、账户里哪个克隆音色 | 换服务商或换音色时 |
| `speed` / `pitch` | 全局语速和音高 | 整体听着快了慢了 |
| `normalize` | 缩写的念法规整，只改配音文本，不改字幕源 | 听到某个缩写念错时 |
| `pronunciation` / `overrides` | 全局多音字（先留空）/ 按段覆盖语速与注音 | 多音字一律走 `overrides`，合成后发现某段离群时 |

`normalize` 与 `pronunciation` 的职责分工需要在配置注释中明确注明。`normalize` 仅处理送往语音合成引擎的文本，比如将 `RAG` 规范为带空格的读音形式，让配音念出三个单字发音，而字幕源文件中依然保持规范的缩写形态。如果没有把这条原则写明，后续排查时容易直接改动正文稿件，导致字幕显示异常。对于 `pronunciation` 建议保持留空，多音字统一通过 `overrides` 进行分段定向处理。这样可以避免全局注音造成的误伤，因为同一个多音字在不同语境下的读音可能完全不同，全局固定注音容易引发其他段落的发音错误。

这份配置文件存放在 `brain/` 目录下，作为账号层面的基准模板。根据 `pipeline/2-create.md` 的创作流程约定，启动创作时会将其复制到对应内容的 `build/` 工作目录中。单条内容特有的多音字修正与局部语速微调，直接记录在工作副本的 `overrides` 中；当确认某项发音规则具备普遍适用性时，再沉淀回写至 `brain/` 下的基准模板。

```
写 brain/tts.config.json，字段包含：
provider（合成服务商）、voice_id（账户里的克隆音色编号，
现在先留占位，换成真实编号前先保留占位，不要随意填入假编号）、
speed 和 pitch（全局语速语调，先给一个默认值）、
normalize（高频英文缩写的念法规整列表，只改配音文本不改字幕）、
pronunciation（全局多音字，留空）、
overrides（按段覆盖的占位对象，先给空对象）。
每个字段旁边用注释写清楚它管什么、什么时候改。
```
