# 账号大脑：五份文件怎么写

上一课交付了一个能 `git init` 的骨架仓：目录树按流程角色分好，`pipeline/`、`content/`、`brain/`、`harness/`、`tools/`、`docs/` 各就各位，`CLAUDE.md` 写完。`pipeline/` 下四份阶段契约（`1-ideate`、`2-create`、`3-review`、`4-publish`）各自钉死了输入、输出、状态翻转、闸口，`daily-run` 只写当天的执行顺序，不算阶段契约。`content/_template/` 六份模板文件也就位，`backlog.yaml` 的头部写好。契约管的是文件之间怎么交接：选题该往哪写、创作该读哪份契约、卡片什么时候弹出来。契约里一个字没提的是，今天该做哪条题、稿子该用什么口气说。这个判断依据现在还没地方放，`brain/` 那个目录是空的。

这一课的输入是你自己对账号定位、人设、语气、素材来源的口述。产出是 `brain/` 下五份 md（`positioning`、`persona`、`style-guide`、`sources` 四份填满，`benchmarks` 留空）加一份 `tts.config.json`，一共六个文件。

五份 md 要过同一道审：不许出现判不了的词。技术深度和流量型六比四，这句话选题那一步能照着数字排出今天做哪条题；以深度为主兼顾流量，同样一句话，谁都读不出该往哪边多排一条，只能靠猜。这道审就是本课全篇的尺子，四份文件每一条都要拿它量一遍。

## 1. positioning 与 persona：账号是谁、对谁说话

先定账号是谁、讲给谁听，这两件事定不清楚，后面语气和素材两份文件跟着歪。定位和人设两份文件要写成能被下游用来排产的判断句，不是形容词堆砌。“技术深度和流量型六比四”能拿去排选题，“有深度又有趣”不能。

`positioning.md` 管的是取题规则，规格如下：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 内容比例：深度和流量怎么排产 | 给一个具体数字，选题那一步能照着混排 | “以深度为主兼顾流量”，排不出今天该做哪条 |
| 目标人群：讲给谁听 | 分类列出，每类写清他们想从内容里拿走什么 | “泛 AI 关注者”，泛到选题时随便一条都能套上 |
| 不做什么：什么题一眼否掉 | 每条能对着一条具体选题当场判真假 | “不做低质量内容”，低质量按什么标准判没说 |

内容比例那一行的数字会被下游直接消费，不是写着好看。你上一课写的 `pipeline/1-ideate.md` 输入节里列了 `positioning`，选题那一步要从这份文件里读出一个能排产的数字，才能决定今天多做深度题还是流量题。写成形容词，这一步就没有输入可用。

交给 AI 起草的时候，别让它一步到位直接写文件。产出物有多种可能的时候，直接落盘只能看到一个结果，看不到它排除掉的其他方案。

```
我要做一个 [账号方向，例如 AI 工程提效和源码解读] 的抖音账号。
先不要写文件，给我三个内容支柱划分方案，每个方案讲清楚：
1. 分几个支柱，各自面向哪类观众；
2. 支柱之间按什么比例排产，这个比例要能落成一个数字，
   给下游选题环节直接用；
3. 这个方案的不做清单，每一条要能对着一条具体选题当场判真假，
   不要写"不做低质量内容"这种谁都读不出标准的话。
三个方案要有实质差异，不要同一个方案换几个词充数。
我选定一个之后，你再写 brain/positioning.md。
```

选定之后审三件事：内容比例有没有落成一个数字；不做清单每一条能不能一眼判定，判不了的改到能判为止，改不动就删；目标人群那一节有没有夹带受众规模、增长率这类数字。第三件事经常中招。目标人群那节要是带着规模和增长率，多半是 AI 按训练里见过的市场分析文档在补，这些数字你手上没有。`CLAUDE.md` 内容红线写着不编造事实、不臆造数据，这条红线在这份文件上的落地方式，就是让 AI 把它删干净。

`persona.md` 归创作读，管的是这段话该用什么口气说。语气条目一旦写成形容词，创作那步就没有东西可核对：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 口播语气：这段话该用什么调子说 | 写成创作那步能对着稿子逐句核对的条目，例如第一人称、开口三秒给钩子 | “语气要生动有趣”，稿子写成什么样都能自称生动 |
| 禁忌：什么话不能说 | 只写能判定的，例如不堆术语装高深、不空喊太强了 | “不端着”，端不端着看谁的感受，判不了 |
| 待补充：还没定的东西 | 编不出的先留白，标成清单，不替自己编一个 | 现在就编一句固定开场白，等发现不合适，前面几十条口播稿已经这么念完了 |

```
按 brain/positioning.md 的定位写 brain/persona.md，分四块：
人设一句话、口播语气规则、图文语气规则、禁忌。
约束：
1. 语气规则要写成创作那一步能对着稿子核对的条目，
   例如第一人称、开口三秒给钩子、术语必须解释，
   不要写"生动有趣"这类没法核对的词；
2. 禁忌只写能判定的，例如不堆术语装高深、不空喊太强了；
3. 还没定的东西留成待补充清单，不要替我编，
   比如固定开场白、固定结尾引导语、账号自称。
```

结果拿回来先看待补充清单：一条都不剩，多半是它把没定的东西按常见套路补齐了，回去把补上的那几条挪回待补充，等你真的想清楚再填。语气条目再对着一句已经写好的稿子核一遍，能不能逐句核对；禁忌条目挨个问一句，能不能判定。

positioning 和 persona 合起来回答了账号是谁、讲给谁听。这两份定得清楚，后面两份要把这个判断变成能照做的动作。

## 2. style-guide 与 sources：怎么说话、素材从哪来

语气规范和信息源两份文件要写成可执行的判据：禁用词表、句式范例、信息源清单加抓取方式，不是“口语化、有梗”这类无法照做的形容词。这两份归创作和选题分别读，`pipeline/2-create.md` 的输入节列的就是 `persona.md` 和 `style-guide.md`。

`style-guide.md` 管视听工程规范，时长、结构、张数这些量都要落成数字：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 口播时长与结构：视频多长、怎么排 | 给区间秒数和分段结构，能拿秒表核 | “节奏明快”，快到什么程度秒表核不了 |
| 图文张数与配图风格：单条几张、什么调子 | 给可数的张数上限和风格归类 | “排版美观”，美不美看感觉，核不了 |
| 违禁词与视觉资产：什么词不能出、封面模板长什么样 | 现在给不出具体内容的就留白，等真被判过一次再填 | 照平台公开合规规范抄一份长清单，和账号实际会踩的点对不上 |

```
写 brain/style-guide.md，六块：标题钩子套路库、口播时长与结构、
字幕与封面、图文张数与配图风格、违禁词与合规、视觉资产。
约束：
1. 时长、张数、结构这三块全部给数字或者可数的东西，
   例如时长区间、单条几张以内，不要写"节奏明快"这类词；
2. 标题钩子写成套路名加一个示例句，它是拿来套的模子，
   不是拿来抄的稿子；
3. 违禁词清单和视觉资产这两块，我没给你具体内容的就留成待补，
   不要照平台公开合规规范抄一份长清单充数。
```

这里容易和“凑数”混在一起。违禁词清单看着像一份现成能抄的东西，平台公开规范确实抄得到，但抄来的那份和账号实际会被判违规的点对不上。哪些词真的会踩线，要真的发过内容、被判过一次才知道。留白等着一次加一条，比先摆一份长清单每天进创作上下文有用。

`sources.md` 归选题读，读完要能直接开抓，所以它得写成检索时能当参数用的词表，光列平台名单不够：

| 这份管什么问题 | 填对的判据 | 一处反例 |
|---|---|---|
| 素材源：去哪抓 | 按用途分类列平台，时效类和沉淀类分开 | 把时效源和沉淀源混一张单子，选题分不清今天该往哪边抓 |
| 关键词矩阵：用什么词检索 | 分层给词，每层判据不同，字数可数 | 一层里全塞近义词凑数，检索不出增量结果 |
| 对标账号：谁是参照 | 指向 `benchmarks.md`，不在这份文件里重复维护 | 在 `sources.md` 里又列一遍对标账号，两份文件对不上时不知道信哪个 |

关键词矩阵分三层。`douyin-ideate` 是第 23 课才会造的选题技能，现在还没有它，但这三层词表就是留给它用的骨架：

```
按 brain/positioning.md 的支柱写 brain/sources.md 的关键词矩阵，分三层：
Layer A 平台体裁词：同类内容在这个平台上以什么形式在火，5 个左右；
Layer B 深度域词：对应技术深度支柱的具体技术名词，10 个左右；
Layer C 流量信号词：追新闻和新模型热度的词，7 个左右。
每层给词就行，不要写解释性长句。
词表下面加一句：这是起步值，复盘时标注哪个词出的选题更火，动态增删。
凑不满某一层就少给几个，不要用近义词凑数。
```

三层各自判的东西不一样。Layer A 判词描不描述得了内容形式，Layer C 判时效，这一层的词半年后大概率要换一批。Layer B 稍微绕一点：这层词除了给检索当种子，还给选题结果打标签分类，所以宽词不必删光；但一层全是宽词，检索这个用途就落空了，这是两码事。Layer B 如果满屏都是“大模型”“AI 工具”这类宽词，多半是图省事把体裁词和深度词混着填了，回去按层拆开重填。

“不许出现判不了的词”这道审，这两份文件上再摆一条正反例：

- 正例：口播 30 到 90 秒，深度内容可以到 2 到 3 分钟。创作那步能拿秒表核，超没超一看就知道。
- 反例：节奏明快。快到什么程度谁都说不出一个数，核不了。

四份能填的都填完了，第五份 `benchmarks` 现在填不出来。

## 3. benchmarks：为什么现在留空

对标账号是谁、哪条打法有效，这两件事要有数据才写得出来。现在一条内容都还没发，手上没有一条属于自己账号的数据。这时候硬填进去的东西全来自别处看来的经验，而它会被当成打法用在之后每一轮的选题打分上。`CLAUDE.md` 内容红线写着不编造事实、不臆造数据，套在 `benchmarks.md` 上就是一句话：留空并写清什么时候才能填，比编一个假数字诚实。

`benchmarks.md` 的头部要写清四件事：这份文件管什么（对标账号、爆款拆解、自己验证过的打法）；谁能改（复盘那段只产变更提议，人审通过后才落到这份文件里）；什么时候长出第一行（第一批内容发出去、复盘拉到数据之后）；每条打法必须带什么（证据是哪几条内容、几个数据点同向、报告文件路径）。

最后一件事决定这份文件几个月后还能不能用。留空是有代价的，这笔账不是编的：这条流水线本来跑着的参考账号里，`benchmarks.md` 的有效打法那一栏，第一次填上内容是账号发布近一个月之后。此前空置了二十多天，那段时间里选题每轮都在读它打分，读到的是一张空表，打出来的分靠的全是没验证过的经验，事情记在这个账号留下的复盘报告 `harness/logs/2026-07-17-retro.md` 里。你的账号现在一条内容都还没发，这笔代价此刻还没轮到你，但账认下来就行，等你也走到那一步，得知道那段时间的选题分数是什么成色。

```
写 brain/benchmarks.md 的骨架，不要编任何账号或数据。
只要两块：
1. 一句留空说明：这份文件要靠真实播放数据才写得出来，
   在第一批内容发布并复盘之前，正文留空；
2. 待填字段名清单：以后每条打法要带的字段，
   例如打法名称、适用赛道、证据（几条内容、几个数据点同向、
   报告文件路径）。
不要给出任何示例数字，字段名可以举例，但不许编造具体的
账号名或播放量。
```

回头看三件事：正文有没有夹带编出来的数字或账号名，字段清单覆盖没覆盖“几个数据点同向”“报告路径”这类可溯源要求，留空说明写没写清楚什么时候会长出第一行。AI 主动给你填了几个示例对标账号的话，多半是它想着模板要写完整，按常见同类账号名单先垫上了，这些名字你没验证过，一律删掉。

文字判断都写完了，还剩一件事没定：配音要用的参数放在哪。

## 4. tts.config.json：音色、语速、多音字规则住配置

配音有一批参数经常会动：音色换了、语速快了半档、某个缩写念错了、某个多音字读错了音。这些参数全都住配置文件，脚本只负责读它。调参数不用改代码，也不用回头确认脚本里还有没有别的地方硬写着同一个值。第 07 到 10 课的配音质检 Loop 要靠这份配置的 `overrides` 字段接住多音字修复，这条判断这一课就得定下来。

| 键 | 管什么 | 什么时候改 |
|---|---|---|
| `provider` / `voice_id` | 用哪家合成服务、账户里哪个克隆音色 | 换服务商或换音色时 |
| `speed` / `pitch` | 全局语速和音高 | 整体听着快了慢了 |
| `normalize` | 缩写的念法规整，只改配音文本，不改字幕源 | 听到某个缩写念错时 |
| `pronunciation` / `overrides` | 全局多音字（先留空）/ 按段覆盖语速与注音 | 多音字一律走 `overrides`，合成后发现某段离群时 |

`normalize` 和 `pronunciation` 分工不同，这条分工要写进配置的注释里：`normalize` 只改送去合成的那份文本，把 `RAG` 写成 `R A G` 之后，念的是三个字母，字幕上还是原样的 `RAG`。不写清楚，改的人会直接去改稿子，字幕跟着变成三个字母连着的样子。`pronunciation` 留空，多音字一律走 `overrides` 逐段处理，因为全局注音会误伤：同一个字在不同段落读音不同，全局写死一个，另一段就错了。

这份配置住在 `brain/` 下当账号级模板。`pipeline/2-create.md` 的步骤 3 写着，创作开工时把它复制进当条内容的 `build/` 工作目录，那条内容特有的多音字和单段语速加在副本的 `overrides` 里；确认是通用规则的，再回写到 `brain/` 这份模板。

```
写 brain/tts.config.json，字段包含：
provider（合成服务商）、voice_id（账户里的克隆音色编号，
现在先留占位，换成真实编号前不要瞎编）、speed 和 pitch
（全局语速语调，先给一个默认值）、normalize（高频英文缩写
的念法规整列表，只改配音文本不改字幕）、pronunciation
（全局多音字，留空）、overrides（按段覆盖的占位对象，
先给空对象）。
每个字段旁边用注释写清楚它管什么、什么时候改。
```

落盘之后核三处：`voice_id` 是不是留了占位而不是编了一个假编号，`normalize` 和 `pronunciation` 的分工有没有写进注释，`overrides` 是不是空对象而不是塞了示例数据。`voice_id` 如果被填成一串像模像样的编号，多半是它把占位符当成了要填的示例。这个编号要连上配音服务商的账户去查，编不出来的就先留一个占位字符串，等下一课装上配音工具再回来填。

账号大脑写完了，AI 知道你要什么内容了。现在真去做一条出来，从稿子到成片要走几步？
