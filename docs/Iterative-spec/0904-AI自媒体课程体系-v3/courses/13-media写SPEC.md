# media 写 SPEC：把决策拆到能施工的粒度

上一课交付了 `docs/spec/media/00-调研.md` 和 `01-ADR.md`，四组互斥路线（入口形态、YAML 写法、并发保护、派生视图）均已拍板定案。但架构决策主要明确了技术路线，并未展开具体的实现细节。在这条技术路线上包含十几条命令，每条命令的输入参数、读取范围、改写字段以及失败反馈均需逐一界定。仅凭决策结论，AI 协同开发时仍然缺乏明确的施工依据。

记忆锚点：决策落档不等于具备施工条件。执行方案必须将每条命令拆解至明确参数、读写边界与报错规范的详实粒度，AI 才能据此稳定执行。本课输入为上述两份调研与决策文档，结合第 11 课确立的执行方案四节模板。产出为技术规范文档：`docs/spec/media/02-执行方案.md`。

## 一、开篇：把决策展开成规格

编写 SPEC 阶段暂不编写代码。该阶段交付一份规范的技术方案，严格遵循四个固定章节，章节名称与排序保持规范统一：

```
# 02-执行方案
## 1. 实施步骤    按顺序编号第 1 步到第 N 步；每步 = 做什么 / 产出物 / 验收标准 / 依赖
## 2. 命令 × 功能 × 详细设计    逐条穷举
## 3. 对外契约    本部分提供给 / 依赖其他部分的接口
## 4. 风险与待定项    拍板未覆盖的点全部落这里，标注需要用户裁决的项
```

因为本次构建的目标是 media 命令行工具，因此采用命令作为最小详设单元，其余三节标题保持不变。

以具体案例说明为何 ADR 无法直接支撑编码。ADR 中可能记录并发保护选用了文件锁，理由是轻量且无需常驻服务。这一论据在架构层面是自洽的，但在编码落地时，程序必须明确回答锁文件的存放路径、过期超时时间的具体数值、抢占失败时的退出码，以及报错信息中是否包含占用进程的信息。这些工程细节在 ADR 中并未覆盖，但程序逻辑必须有唯一确定值。执行方案的核心价值，就是将这些未决细节逐一梳理并给出精准解答。

参考规范中有一份成熟文档 `docs/Iterative-spec/0818-看板工作台/01-CLI执行方案.md`，篇幅五百余行。其开篇明确界定：本文只做两件事，把拍板拆成天级步骤，把每条命令与 core 模块写到可照抄实现的粒度，决策理由一律回指拍板章节，不复述。SPEC 文档无需赘述决策依据，背景原因已在 ADR 中完整沉淀；它的核心职责是将架构决策精准映射为具备可操作性的施工参数。本课的 `02-执行方案.md` 聚焦于 media 单个命令行工具，篇幅相对精简，但架构骨架与设计精细度要求一致。

模板明确后，首先展开核心详设部分：十四条命令的规范穷举。

## 二、命令 × 功能 × 详细设计：十四条逐条穷举

### 2.1 十四条命令逐条四件套（参数 / 读什么 / 写什么字段 / 失败怎么报）

此处所说的四件套，特指参数、读取对象、写入字段、失败响应这四项内容。这与第 11 课约定的六步方法四件套模板分属不同维度，阅读时注意区分。

若仅提供命令名称与简短说明，AI 在编写代码时容易产生自主推断。例如仅描述 media flip 用于状态流转，AI 通常会自行推测是否需要事务机制、写入前是否校验，以及失败时如何返回。这往往会导致实现偏离预期。四件套机制旨在严格锁定每条命令的输入输出边界：明确输入参数、明确合法性校验需读取的文件、明确校验通过后具体修改哪个文件的哪个字段，以及非法操作时的报错格式。四项要素缺一不可，只读命令的写入字段显式标注为“无”，不能省略跳过。

参考规范中 flip 命令的设计规格如下：

| 项 | 内容 |
|---|---|
| 参数 | slug（必填）、目标状态（必填）、--reason（仅目标为 rejected 时必填） |
| 读 | 该条内容自己的元数据文件 |
| 写 | 元数据文件的状态字段和对应的时间戳字段，外加派生看板的机器区 |
| 失败怎么报 | 目标状态不在当前状态的合法出边里，报错并在提示里列出当前状态还能去哪几个状态；rejected 没带 --reason 单独报一种错；目标是发布类状态一律拒绝，提示改走发布收尾命令 |

表格中所述的机器区，指看板文件中通过标记注释圈定的专属区块，其内容每次由工具自动计算并重新渲染。标记之外的人工说明文字保持原样，工具不予改动。

表格最后一行是设计中最容易被忽视的细节。错误提示不仅需要说明状态非法，还应列出当前状态允许流转的合法目标。这样调用方在重试时能获得明确指引，无需二次查询。

具体命令清单在第 12 课的架构决策中尚未穷举，本课需要将完整清单予以锁定。在流水线各阶段契约中，取题、出审、发布收尾这三处已有手工记账的基础。后续章节还将引入飞书审核回调、选题池入池与清扫，以及复盘数据汇总。这六类业务场景各自对应至少一条写命令。预先在清单中预留位置，便于一次性固化入口规范，避免后续频繁变更。结合纯查询与体检类命令，整套工具梳理为十四条具体命令。

读命令共 5 条：包括总览与单条查询（st）、模拟取题（next）、选题池查询（backlog ls）、一致性体检（check）、产物体检（doctor）。

写命令共 9 条：包括取题记账（promote）、状态翻转（flip）、发布收尾（publish-done）。批量入池（backlog add）、机械清扫（backlog sweep）、落地人审提议（backlog apply）。指定取题指针（next-up）、重建看板（dashboard rebuild）、复盘数据落账（metrics record）。

```
读 docs/spec/media/01-ADR.md 里关于入口形态和 YAML 写法的两条决策。
下面这十四条命令，逐条拆成四件套，一条不许省：
读命令：st、next、backlog ls、check、doctor
写命令：promote、flip、publish-done、backlog add、backlog sweep、
       backlog apply、next-up、dashboard rebuild、metrics record
1. 参数：必填参数、可选参数、每个参数的取值范围
2. 读：这条命令要读仓库里哪些文件才能判断这次操作合不合法
3. 写：写命令写清楚具体改哪个文件的哪个字段；只读命令这一栏写无
4. 失败怎么报：校验不过时报什么错误、提示信息里要不要写出当前状态
   还能去哪几个状态
写命令额外标一句：这条命令要不要走完整事务
（拿锁、算写计划、支持 dry-run、原子落盘、写审计记录这一整套），
还是只改一处字段就够。字段名和写法按我的 01-ADR.md 里的决策来定，
不要照抄任何示例里的字段名。
```

拿到生成结果后重点核查三项。首先核对十四条命令是否完备，防止相近命令被自行合并。其次核实失败反馈是否提供了明确的错误类型与提示文案，避免模糊答复。最后确认事务性命令是否明确标注了事务支持级别，区分仅改单处字段的轻量操作与跨多文件原子落盘的操作。

若生成结果中存在遗漏失败响应的情况，通常是由于未严格遵循四件套硬性约束。可在提示词中强化要求：四项内容必须逐一覆盖，无对应内容的项目需明确注明原因。

只读命令中的 check 承担全仓状态快照校验，检查逻辑相对集中。参考规范中定义了八项检查规则，覆盖状态失步、条目断链、超时未填以及异常空跑等维度：

| 规则 | 级别 | 判定什么 |
|---|---|---|
| CHK-01 双层不同步 | error | meta 的状态和 backlog 的状态没对上 |
| CHK-02 断链 | error | backlog 是已取题状态，但对应目录或元数据缺失 |
| CHK-03 超时未回填 | error | 定时发布的状态停留太久没人回填结果 |
| CHK-04 审核积压 | warn | 停在审核状态太久没人处理 |
| CHK-05 链接待补 | warn | 已发布但没有回填作品链接 |
| CHK-06 指针断裂 | warn | 元数据里的来源指针和选题池对不上 |
| CHK-07 临近过期 | info | 选题快要被清扫规则命中 |
| CHK-08 疑似空跑 | warn | 到了该出内容的时间点还没有新内容，也没人上报 |

这八项规则关注的字段（状态、来源指针、发布链接），均源自前期搭建的核心元数据。以这张表作为 check 命令的设计起点十分稳妥。若你的 01-ADR.md 对部分字段采用了不同命名，映射至自身字段即可。这八项规则覆盖全面，编写自身规范时应当逐一核对，避免遗漏。

### 2.2 状态迁移表：谁能到谁、谁触发、前置条件是什么

状态流转逻辑应当通过结构化表格精准表达，避免使用大段文字叙述。文字描述容易引发多义性理解，而表格形式则能直观呈现原状态、目标状态、触发命令、前置约束以及附带说明等关键维度。

前期手工维护的元数据状态主要包括 ideated、drafting、review 三档。approved、scheduled、published、rejected、retro_done 五档，属于后续发布与复盘流程中的扩展状态。选题池方面，目前已涉及 idea 与 picked，而 published、expired、rejected、archived 同样用于后续阶段。执行方案应当在当前阶段将完整流转图绘制齐备，无需临时生造状态名称。表格范例如下：

| from | to | 触发命令 | 前置条件 | 需要理由 |
|---|---|---|---|---|
| ideated | drafting | flip | 无 | 否 |
| review | approved | flip | 无 | 否 |
| review | rejected | flip | 无 | 是 |
| approved | published | publish-done | 当前状态是 approved | 否 |
| published | retro_done | flip | 只能由治理线那条线触发，生产线不能碰 | 否 |

最后一行体现了操作权限的隔离。同一条命令在不同阶段的触发主体应当严格限定。发布完成转向复盘属于治理线的专属动作，生产线自动化流程不可擅自触发。将此类前置约束明确写入表格，能有效防止权限混淆。

```
参考我们从第 03 课开始手改元数据和选题池时实际用过的全部状态值，
画两张迁移表：
1. 元数据的状态迁移表：from / to / 触发命令 / 前置条件 / 是否需要理由
2. 选题池的状态迁移表：同样五列
穷举每一个当前状态能合法到达的下一个状态，没写到的组合视为非法。
特别检查这两类边：审批之后允许反悔退回上一个状态吗，如果允许，
在哪个状态生效；哪几条跳转只能由治理线触发，生产线的自动化不能碰。
这两类是最容易漏写或者写反的地方。
```

若状态迁移表中出现了从未接触过的新状态名，通常是模型套用了通用的状态机惯例。此时应当对照 01-ADR.md 和历史元数据进行核实，非本项目所需的状态名一律不予收录。

命令详设完备后，下一步是规划合理的实施分期。

## 三、实施步骤：里程碑怎么切

里程碑的划分应当立足于可验证性，避免单纯依据底层代码模块做机械切分。优先关注每个阶段能否基于真实数据完成明确的验收断言。如果无法得出确定的验收结论，说明该里程碑的划分粒度仍需调整。本课程后续章节依次以 M1 与 M2 展开具体实施。

参考规范的划分策略为：M1 阶段完成只读命令、事务写入底层引擎，并优先实现历史上出错最为集中的两条写命令。M2 阶段补齐其余写命令，并完成全仓调用入口的统一切换。优先实现核心写命令的原因在于及时收敛风险。历史上高频出现故障的场景包括发布收尾时跨文件状态遗漏，以及定时发布后由于结果未回填导致流程阻塞。优先覆盖高风险操作，比过早开发低频命令更能提升系统稳定性。

在自身项目中，应当结合过往手工维护元数据时的易错环节，自主评估首批覆盖的命令，不应机械套用参考步骤的编号顺序。

```
读 docs/spec/media/02-执行方案.md 现在已经写好的第 2 节
（十四条命令四件套和状态迁移表），提两个里程碑方案：
1. 里程碑不按代码模块切，按能不能拿真实数据跑出一句能验的话切
2. 参考我自己 pipeline 各阶段契约和各个 skill 里现在还在手改
   meta.yaml、backlog.yaml、dashboard.md 的那几处，这十四条命令里
   哪几条对应的手编写点最容易出错，放进第一个里程碑
每个里程碑给三样：里程碑名、做什么（对应哪几条命令）、出口条件。
出口条件必须是一句能跑的验证动作，不许写基本完成、差不多了这类
判不出真假的话。
```

验收条件始终遵循统一准则：必须是一句可直接验证的操作陈述。M1 的验收条件可定义为：真实仓库下执行 media check 顺利通过，且 YAML 文件内原有注释完整保留。M2 的验收条件可定义为：全仓状态写入路径保持唯一，连续七天内元数据、选题池与看板机器区的每一次改动均能在审计日志中追溯对应条目。这类表述具备明确的可判定性，通过执行命令或检索日志即可得出确定结论。

审阅方案时重点核验两项指标。其一是十四条命令是否均被 M1 和 M2 完整覆盖，无任何遗漏。其二是验收条件是否具备可执行性，能否立即对应到具体命令与目标文件。若仍为空泛表述，则需要进一步细化。

若验收条件写成类似“流程基本顺畅”的模糊描述，往往说明设计阶段缺乏客观验证思路。此时必须重新推敲可落地的验收动作。

命令详设与里程碑规划完成后，方案即可进入工程对接阶段。

## 四、对外契约与风险待定项

第三节与第四节虽然篇幅精炼，但具有不可替代的约束作用。对外契约明确界定该模块的上下游依赖关系，风险与待定项则负责客观记录决策阶段尚未最终裁定的边界，避免在编写文档中途私自做出非正式决策。

对外契约章节聚焦一个核心目标：media 命令是全流水线状态写入的唯一合法入口。后续构建的飞书闸口与各个自动化 skill，涉及状态变更时均调用该命令，不再直接修改文件。参考规范以表格形式列出了各调用方的对接契约。例如后端服务依赖命令的 JSON 输出格式与退出码，前端看板依赖共享的数据类型。本项目的调用方相对聚焦，明确写清调用场景与依赖返回格式即可。

风险与待定项章节专门用于留存未决的技术边界。参考规范在此记录了诸多弹性约定。例如锁文件的超时阈值先采用默认值实现，后续保留调优空间；部分规则的判定阈值同样记录在案，便于后续观测调整。这些记录明确标示出尚待验证的边界，绝非无依据的留白。编写自身方案时，若遇到尚未完全确定的细节，如实记录即可，避免主观臆断。

```
按第 12 课的 01-ADR.md 和刚写完的第 2、3 节，补齐执行方案的第 3、4 节：
第 3 节对外契约，一句话说清楚这份规格谁会用、依赖谁；
第 4 节风险与待定项，把你在生成前两节内容时遇到过的、没有明确答案、
需要我来裁决的点都列出来，每条注明这是个什么问题，不许自己替我拍板。
如果确实一条都想不出来，写一句当前无风险待定项，不要留空。
```

完成方案编写后应当通篇核对。实施步骤、命令详设、对外契约三节必须具备充实内容，禁止留空。风险与待定项若暂无内容可明确标注当前无待定项，但不可缺失章节内容。留空意味着逻辑存在盲区，AI 在实施时容易产生自由推测，从而带来不可控的代码缺陷。

规格制定完毕，即可推进后续实现。

## 五、收尾：规格写完，第一个里程碑做哪些

本课结束时，`docs/spec/media/02-执行方案.md` 已完成落地。命令清单、四件套详设、状态流转图以及 M1 和 M2 里程碑的验收标准均已具备明确定义。

当前阶段仍属于技术规格制定，底层的解析逻辑、状态机实现以及事务落盘代码尚未编写，命令行工具本身也尚未构建。文档明确了实现目标，具体的代码构建仍需稳步推进。

执行方案编写完毕，十四条命令逐项穷举。进入施工阶段，首个里程碑将重点攻坚哪几项核心能力？
