# 飞书通道 SPEC：四个决策点怎么拍板

上一课（第 17 课，人审闸口：闸设在哪）交付了两样东西：一张不可逆动作表，把发出去收不回、花钱、对外可见、覆盖真相源这四类动作挑了出来；一份卡片字段草案，先把飞书卡片上大致要放哪些字段列了个初稿。闸设在哪已经定了，闸怎么造还没定。这一课要把飞书这条通道走一遍六步 SPEC 方法的前四步：调研、讨论选型、决策、写 SPEC，执行和验证留给第 19 课去做。

除了这份卡片字段草案，这一课还要用上你自己第 02 课申请飞书自建应用时存下的 App ID、App Secret、Verification Token、`chat_id`，以及第 11 课交付的六步模板四件套（调研表固定四列、ADR 固定四项、执行方案固定四节、施工记录模板），这一课只引用，不重新定义。产出是 `docs/spec/feishu-gate/` 目录下三份文档：`00-调研.md`、`01-ADR.md`、`02-执行方案.md`。

记忆锚点：选型看的是每条路自己说不说得清在什么条件下会输，不靠个人喜好挑一个。飞书这条闸口要拍板的四件事，每一件都有一条看起来更省事的路，这条路上多半藏着一个具体会摔跟头的场景，这一课要做的是把那个场景先摆到台面上。

## 一、调研：企业自建应用怎么配，四个决策点是什么

### 1.1 六步配置照做

飞书自建应用这一步你在第 02 课已经走过一遍：在开放平台建一个企业自建应用，拿到 App ID 和 App Secret；在应用能力里开机器人，发布应用，把机器人拉进要收卡的那个群；在事件与回调里把订阅方式选成长连接，订阅 `card.action.trigger` 这个事件；加密策略选不加密，记下 Verification Token；最后把这几个字符串和群的 `chat_id` 一起存好。这六步没有选型空间，官方文档写清楚照做就行，第 02 课你已经把值拿到手了，这一课不用重走一遍。

这里要点破一条第 02 课没细讲的约束：建自建应用这一步，飞书开放平台要求这个应用挂在一个企业或团队账号下，纯个人版飞书账号进不去创建自建应用那个入口。你第 02 课能顺利建成，说明你当时用的账号本来就满足这个条件；这里把它写明白，是因为它是六步里唯一一步不能靠装个软件、跑条命令过去的，属于要挂靠身份的前提，以后要在另一台机器上重新走一遍，或者帮别人配这同一套东西，先确认对方手上有一个能创建自建应用的企业或团队身份，没有的话，飞书允许免费注册一个只挂自己一个人的企业账号，花的是几分钟注册时间，不是钱。

六步配置照做，四个待决策点才是这一课真正要走六步方法的地方。

### 1.2 四个待决策点长什么样

六步配置定的是怎么把一个应用挂起来，没定这个应用具体要怎么工作。挂起来之后，还有四件事没人拍板：

- 通道形态：卡片按钮被点了之后，这条回调事件怎么送到你的服务，走长连接还是走 webhook。
- 卡片结构：从推出待审内容到确认发布，中间要经过几次人工确认，每次确认用几张卡片装。
- 回调窗口：人点了按钮之后，服务要在多长时间内给出响应，响应窗口内能做哪些事、不能做哪些事。
- 命名空间：如果同一个飞书应用以后要服务不止一条业务线，回调事件怎么分辨这次点击是冲着哪条线来的。

这四件事任何一件拍错了，第 19 课照着实现的时候都要推倒重来：通道形态定错了，服务的骨架要整个换一套网络模型；卡片结构定错了，按钮和状态的对应关系要重新设计；回调窗口踩了坑，表现是按钮点了没反应，人还分不清是网络问题还是代码问题；命名空间漏了，以后想再加一条业务线，旧代码全部要回头改。四件事一件不落地过一遍六步方法。

## 二、长连接与 webhook：两种回调订阅方式的对比

先摆两个候选各自的样子：

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 长连接（飞书官方 SDK 的 WebSocket 模式，服务主动连出去） | 服务所在的机器不需要有公网可达的地址，服务是主动去连飞书，不是等飞书连进来 | 这个服务要一直常驻，连接断了要有重连逻辑；本地跑一个不落地的常驻进程，重启机器后要记得重新拉起 | 常驻进程被误杀或者僵尸进程占着连接，表现是卡片点了没反应，本地也没有新日志 |
| webhook（飞书按 HTTP POST 把回调事件推到你指定的地址） | 服务已经跑在一台有公网地址、能被外部直接访问到的机器上 | 本机没有公网地址时要另外接一层内网穿透工具，把本地端口暴露出去；穿透工具本身要装、要配、要保活，是额外一层依赖 | 内网穿透工具的连接掉线或者免费额度用完，表现和长连接掉线一样，都是卡片点了没反应，但根因多了一层要排查 |

你自己开发机上大概率没有一个公网可达的地址，选 webhook 意味着要先解决这个前提缺失的问题，多接一层内网穿透。多一层依赖就多一层会挂的地方，内网穿透工具自己也会掉线、也有免费额度上限，这层依赖本身不属于这条闸口要解决的问题，是为了凑齐 webhook 的前提专门加上去的。长连接不需要这个前提，服务主动连出去，本机在不在公网上不影响。

把这条判断走一遍讨论选型，让两个候选各自交代清楚自己的账。这条 Prompt 后面三节复用同一个模板，只换候选和场景描述：

```
针对"长连接"和"webhook"这两个飞书卡片回调订阅方式，分别扮演它们的
支持者，依次回答四件事：
1. 这个方案在什么场景下是对的选择？
2. 选它要多付出什么代价？
3. 主动交代它已知的失败模式：什么情况下它会输，输给对方？
4. 不要下"综合来看方案更好"这类结论，只交代前三条。
两个方案都要独立走完这四步，不要在中途比较。
背景：这台机器是我自己的开发机，日常联网但没有公网可达的固定地址。
```

如果某个候选只报优点、说不出一条具体的失败模式，常见原因是候选描述本身带了倾向，比如把开发机的网络条件写得模棱两可，AI 顺着这个模糊往它倾向的方向答。把背景那句话写死成一个确定的事实（有没有公网地址），是对是错让它自己接得住，重问一遍。

通道形态定了长连接，下一步定卡片本身怎么拆。

## 三、卡片结构：一张卡还是按流程拆几张

一条内容从推出待审到真正发布，中间要经过三次人工触点：先是内容审核，通过或者打回；打回之后要再问一句，是自动重做还是先挂起来等人处理；通过之后走到发布确认，把最终要执行的命令和物料摆出来给人核对一遍，人点确认才真发。这三次触点各自要显示的字段和按钮都不一样，决定了卡片要拆成几张。

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 一张卡装完所有字段和按钮（通过、打回、打回原因、确认发布、取消全塞进同一张卡） | 从审核到发布只有一两次人工触点，比如打回之后直接结束，不需要再问自动重做还是挂起 | 每次状态变化都要在同一张卡里显示或隐藏不同的字段和按钮，卡片的更新逻辑要自己维护一套显示规则 | 打回需要人填一句原因，这句话要用输入框承接；一张卡上同时摆通过按钮、打回按钮、打回原因输入框、发布确认按钮，容易让人在卡片状态还没切换过来的时候点错按钮 |
| 按状态拆多张卡（审核卡、打回原因卡、确认发布卡各自独立） | 从审核到发布有三次以上的人工触点，且触点之间的字段和按钮完全不同 | 卡片之间的状态流转要靠服务端主动更新或者新发一张卡来接力，多了一层记录哪张卡对应哪个状态的账 | 卡片之间接力的时候，如果服务端没有正确更新旧卡，容易留下一张已经过时的卡，人点了旧卡上的按钮却拿不到预期的响应 |

这条闸口正好是三次触点都齐全的那一种，装进一张卡意味着这张卡要在三种状态之间显示不同的内容，比拆成三张卡更容易在状态切换的一瞬间显示出不对的内容。参考流水线（这是历史实现，你按下面的字段和按钮走）走的是拆卡这条路，三张卡各管一段：

审核卡，内容是选题标题、类型、目录，按钮两个：通过、打回。打回原因卡，内容是一个输入框，让人填一句打回的具体理由，按钮两个：打回并自动重做、打回并挂待办。确认发布卡，内容是物料摘要（标题、正文、话题、封面、媒体文件、发布时间这类字段）和最终要执行的命令原文，按钮两个：确认发布、取消；如果物料检查发现缺东西，这张卡只显示取消按钮，不给确认发布的选项。三张卡加起来一共六个按钮，没有第七个查看全文的按钮，文稿全文和封面在推审核卡之前已经用两条独立的消息先发过一遍，人在点通过或打回之前已经看过真实内容，卡片上不需要再重复一份。

这跟第 17 课的卡片字段草案对不上，要交代一下。第 17 课那份草案是审核卡上卡标题、钩子首句、定位标签、封面缩略图，点进去看口播稿全文，按钮是通过和打回，打回自带一个原因输入框。到这一课定稿，改了两处：口播稿全文和封面从点进去看，改成推审核卡之前先发两条独立消息，因为一张飞书卡片本身装不下一整篇口播稿，独立消息人能直接往下翻，不用先点进卡片再点开全文；打回原因从审核卡上的一个输入框，拆成单独一张打回原因卡，因为输入框要和提交按钮平铺在同一层，强行归入审核卡会跟通过按钮挤在一起。打回要不要拆成两种（重做还是挂起），第 17 课当时留给这一课定，这里定了：拆成打回原因卡上的两个按钮。

把这条判断走一遍讨论选型：

```
针对"一张卡装完所有字段和按钮"和"按状态拆审核卡、打回原因卡、
确认发布卡三张卡"这两个方案，分别扮演它们的支持者，依次回答：
1. 这个方案在什么场景下是对的选择？
2. 选它要多付出什么代价？
3. 主动交代它已知的失败模式：什么情况下它会输？
4. 不要下综合结论，只交代前三条。
背景：从审核到发布一共有三次人工触点（通过或打回、打回后选重做
还是挂起、确认发布或取消），三次触点各自的字段和按钮都不一样。
```

拿到结果核一点：打回原因这个输入框有没有被单独摆出来讨论。它是这一步里最容易被漏掉的一个环节，很多方案会把打回和打回原因合并成一步来想，但填原因这个动作需要一个输入框控件，控件在飞书卡片里怎么摆是有讲究的，一个输入框和两个提交按钮必须直接摆在同一层，不能再套一层容器，套了容器输入框不会显示出来。这条约束不属于选型层面要决定的事，是卡片结构定下来之后，第 19 课具体实现打回原因卡时要注意的一处坑，先记在这里，免得到时候踩了不知道从哪查起。

卡片结构定了，按钮点下去之后要多久给响应，是接下来要定的事。

## 四、同步与异步路径的分工

人点一下按钮，飞书要求服务端在 3 秒内给出响应，超时飞书会判定这次回调失败，报一个错误码。这条时间限制是飞书平台定的，不是这条闸口自己能商量的，能商量的是响应窗口里放什么、不放什么。

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 同步路径只做内存操作和状态标记 | 3 秒窗口内要完成的事情本身很轻：判断这是不是自己该处理的事件、组装一句提示语、组装一张要原地更新的卡片内容 | 真正的重活（改状态记账、拼发布物料、起子进程做重做或发布）要挪到另一条执行路径上去做，人点完按钮看到的只是一句处理中的提示，不是最终结果 | 如果误把一次网络调用留在同步路径里，比如顺带把卡片更新的 HTTP 请求也放在这条路径上，网络慢的时候整个响应会超过 3 秒 |
| 同步路径直接跑完重活再返回 | 重活本身能稳定在 3 秒内跑完 | 状态记账、拼物料、起子进程这几步只要有一步涉及网络调用或者进程调度，耗时就不可控，稳定在 3 秒内基本做不到 | 起一个子进程去做真正的重做或发布，冷启动加执行本身就是秒级到分钟级，同步路径直接跑完这条路先天做不到 3 秒内返回 |

真正要发布或者要重做的动作，背后是起一个子进程去执行，这类动作稳定在 3 秒内跑完做不到。同步路径只能挑轻的事情做：

同步路径能做的，判断这次回调是不是自己该管的事件（这是内存里比较两个字符串），组装一句要弹给人看的提示文案（内存拼字符串），组装一张要原地更新的卡片内容（内存拼一段 JSON，这一步能直接放进响应体里跟着响应一起返回，不用额外发一次请求）。参考流水线的打回护栏判断也放在同步路径里，读一次本地的审核记录文件数一下这条内容已经被自动重做过几次，这类单次本地文件读取够快，能算进同步路径。

异步路径要做的，改状态记账（这一步在第 15 课收敛、第 16 课验过写路径唯一的 `media flip` 一条命令，比如把状态从 review 翻到 approved，起子进程调它）、拼真正要发布的物料、起子进程委托做重做或者发布、真正把内容推到抖音、把处理结果更新回卡片。最后这一步容易被漏看：卡片内容已经在同步路径里通过响应体更新过一次了，但重活跑完之后往往还要再更新一次卡片显示最终结果，这第二次更新本身是一次独立的网络请求，同样不能算进同步路径，要跟着重活一起放到异步那边去做。

同步和异步两条路径的分工，是这条决策要落进执行方案的核心内容，先用一张表把两边各自装哪些动作定死，供第 19 课直接对着实现：

| 路径 | 装的动作 | 允许的操作类型 |
|---|---|---|
| 同步（3 秒窗口内） | 命名空间判断、组装提示文案、组装要原地更新的卡片内容、读一次本地文件判断打回次数 | 内存操作、单次本地文件读取，不含网络请求 |
| 异步（另起线程或子进程） | 状态记账、拼发布物料、起子进程做重做或发布、把最终结果再更新回卡片 | 允许网络请求和子进程调用，不受 3 秒限制 |

超时报错的错误码是 -356，参考流水线的真实故障记录里，这个码出现过两类根因：一类是点的卡片本身就不该由这个服务处理，被静默丢弃后飞书那边等不到响应；另一类是同步路径里混进了一次网络调用，跑得比 3 秒慢。点按钮报这个错，通常是这两条里的一条，先查是不是同步路径悄悄多做了一件不该做的事。

回调窗口定了，最后一个决策点是一个应用怎么服务多条业务线不串。

## 五、命名空间隔离：一个应用服务两条线

一个飞书自建应用可以被拉进多个群，也可以同时服务多个项目。如果以后你不止做抖音这一条流水线，还想拿同一个应用去服务另一条业务线，甚至复用同一个群，回调事件要怎么分辨这次点击是哪条线的事。

| 方案 | 适用前提 | 代价 | 已知失败模式 |
|---|---|---|---|
| 各业务线各建独立应用 | 每条业务线都单独申请一次企业自建应用，互不共享 App ID | 每条业务线都要重复走一遍六步申请配置，多一条业务线多一份要维护的凭据 | 无（各建独立应用本身没有事件串线的风险，代价体现在申请和维护成本上，不体现在运行期失败） |
| 复用同一个应用，靠命名空间字段过滤 | 已经有一个申请好的应用，想让它同时服务多条业务线，不想重复申请 | 卡片的按钮 value 里要统一带一个命名空间字段，服务收到回调时要先判断这个字段是不是自己认的那一个 | 同一个应用的回调事件，如果同时有两个服务实例都在跑长连接监听同一个应用，飞书是按负载均衡把事件投给其中一个实例，不是广播给所有实例；如果某张卡是命名空间字段加上去之前发的旧卡，收到的服务会判断字段不匹配，直接静默丢弃，不报错也不处理 |

复用同一个应用的失败模式里，负载均衡投递这条要单独说清楚。多个服务实例监听同一个应用的回调，飞书按负载均衡挑一个正在监听的实例，把这次点击投过去，不会广播给全部实例。如果两条业务线各自起了一个服务在监听同一个应用，一次点击可能被另一条线的服务截走，这条线自己的服务什么反应都没有。命名空间字段管的是事件被截走之后怎么处理这一步，它挡不住事件被哪个实例截走：截走事件的那个服务先判断这次事件的命名空间是不是自己的，不是就直接丢弃，不去动它不该管的内容，把处理权交还给对的那个服务去响应。

这条决策，落到实现层面就一句话：卡片的按钮 value 里统一加一个命名空间字段，服务收到回调的第一件事，是拿这个字段跟自己配置里记的命名空间比一下，不相等直接返回，什么都不做。

把这条走一遍讨论选型：

```
针对"各业务线各建独立应用"和"复用同一个应用，靠卡片 value 里的
命名空间字段过滤"这两个方案，分别扮演它们的支持者，依次回答：
1. 这个方案在什么场景下是对的选择？
2. 选它要多付出什么代价？
3. 主动交代它已知的失败模式：什么情况下它会输？
4. 不要下综合结论，只交代前三条。
背景：目前只有一条业务线在用这个应用，但以后可能会加第二条，
第二条线要不要单独申请应用还没定。
```

排障句先记一条：点了一张卡没反应，多数情况下是这张卡的命名空间字段跟当前服务配置的不匹配，被静默丢弃了，先确认点的是不是最新发出来的那张卡，不是一张更早、字段还没补上命名空间的旧卡。

四个决策点都拍完板了，收进正式的 ADR 和执行方案。

## 六、决策与写 SPEC：ADR 四项与执行方案四节

四个决策点收进同一份 `01-ADR.md`，写成四条独立的记录，不单独开四份文档；写 SPEC 也是一份 `02-执行方案.md`，四个决策点一起落进同一套四节模板。三份文档按第 11 课定的目录约定落进 `docs/spec/feishu-gate/`。

`00-调研.md` 是本课第 2 到 5 节那四张对比表原样收进去，按通道形态、卡片结构、回调窗口、命名空间的顺序排列，每张表前面留一句话说清这一组在比什么。这份文档不重复讨论选型阶段的辩护内容，辩护内容留给 ADR 的理由字段引用。

`01-ADR.md` 四项固定：决策、理由、被否方案、反悔成本，多的字段不加：

```
ADR-1 通道形态
决策：长连接（飞书官方 SDK 的 WebSocket 模式）。
理由：开发机没有公网可达的地址，webhook 需要额外接一层内网穿透
  工具，多一层依赖就多一层会挂的地方；长连接是服务主动连出去，
  不依赖机器本身能不能被外部访问到。
被否方案：webhook。
反悔成本：中。以后如果服务改跑在一台有公网地址的机器上，换成
  webhook 只需要改接入方式，业务处理逻辑不用动；但现在这个阶段
  换成 webhook，要先解决没有公网地址这个前提缺失的问题。

ADR-2 卡片结构
决策：按状态拆三张卡——审核卡、打回原因卡、确认发布卡，各两个
  按钮，没有查看全文按钮。
理由：从审核到发布有三次人工触点，三次触点的字段和按钮完全不同，
  装进一张卡意味着同一张卡要在三种状态间切换显示内容，比拆成
  三张卡更容易在状态切换的瞬间露出破绽；文稿全文和封面已经用
  独立消息先发过，卡片不需要重复承载。
被否方案：一张卡装完全部字段和按钮。
反悔成本：低。三张卡各自独立，以后要再加一次人工触点（比如
  发布后再加一次复核），加一张新卡不影响已有的三张。

ADR-3 回调窗口
决策：同步路径只做内存操作和状态标记，重活（状态记账、拼物料、
  起子进程做重做或发布、更新最终结果）全部甩到异步路径。
理由：飞书要求 3 秒内响应，超时报错；真正的重活背后是起子进程，
  耗时是秒级到分钟级，稳定在 3 秒内跑完做不到。
被否方案：同步路径直接跑完重活再返回。
反悔成本：高。想改回同步路径直接跑完重活再返回，前提是重活本身
  能稳定压缩到 3 秒内，但状态记账、拼物料、起子进程这几步只要沾上
  网络调用或者进程调度，耗时就不受控，这个前提基本凑不齐，退不
  回去。

ADR-4 命名空间隔离
决策：复用同一个应用，靠卡片 value 里的命名空间字段过滤，不属于
  自己命名空间的事件收到即丢弃，不处理也不报错。
理由：目前只有一条业务线，暂时不需要为了隔离而重复申请应用；
  命名空间字段的实现成本是一个字段的读写比较，比维护多套应用
  凭据轻。
被否方案：各业务线各建独立应用。
反悔成本：低。以后真的要拆成独立应用，把命名空间字段原样保留
  当冗余校验也不影响正确性，不需要先删掉这套过滤逻辑再拆分。
```

`02-执行方案.md` 沿用第 11 课钉死的四节模板，第二节的单位换成决策点：

```
# 02-执行方案
## 1. 实施步骤
## 2. 决策点 × 功能 × 详细设计
## 3. 对外契约
## 4. 风险与待定项
```

第 1 节实施步骤，按能不能拿真实点击跑出一句能验的话切，不按代码模块切。三步：第 1 步，起一个只做命名空间判断和打日志的服务骨架，产出物是能常驻运行的进程，验收标准是真实点一下测试卡片，本地日志能看到这次点击被判定为自己的命名空间，依赖是第 02 课存下的 App ID、App Secret、Verification Token。第 2 步，接上三张卡片模板和按钮分发，产出物是三张卡各自能发送，验收标准是从推审核卡到点确认发布卡，三张卡的切换在一次真实走查里全部走通，依赖第 1 步的服务骨架。第 3 步，补上 3 秒窗口内的同步异步拆分，验收标准是故意让异步那部分的动作变慢（比如手动加一段延时），同步响应仍然在窗口内返回，不报超时错误，依赖第 2 步的按钮分发已经跑通。

第 2 节决策点乘功能乘详细设计，逐条穷举，四个决策点各自要交代清楚这条决策具体落到实现上要做什么。通道形态这一条，功能是服务常驻监听回调，详细设计是用飞书官方 SDK 的长连接客户端，App ID、App Secret、Verification Token 从本地一份不提交进版本库的配置文件里读，服务起之前先确认没有另一个僵尸进程占着同一个连接。卡片结构这一条，功能是三张卡各自的模板和状态切换，详细设计按第 3 节定的字段和按钮表逐张实现，打回原因卡的输入框和两个提交按钮必须直接平铺在同一层，不能再嵌套一层容器。回调窗口这一条，功能是响应窗口内外的动作分工，详细设计按第 4 节那张同步异步分类表逐条落实，同步路径产出的卡片更新内容直接放进响应体本身返回，不额外发请求。命名空间这一条，功能是按命名空间过滤回调事件，详细设计是卡片 value 统一注入命名空间字段，服务收到回调后第一步就做这个比较，不匹配直接返回，后面的逻辑都不再执行。

第 3 节对外契约，一句话说清楚：这份 SPEC 交给第 19 课的实现用，也是第 20 课发布 Skill 要接的通道；依赖第 02 课已经存好的应用凭据、第 14 到 16 课收敛出来的 `media flip` 和 `media publish-done` 两条状态记账命令、第 17 课的卡片字段草案。

第 4 节风险与待定项，把这一课没顾上的角落列出来，不能悄悄替以后拍板。三条：自动重做要不要设一个次数上限，超过上限之后怎么处理，这条不属于本课定死的四个决策点，留给第 19 课结合实际重做效果再定；打回原因卡上如果人不填任何内容直接点提交，这种情况该怎么处理，是当作没有理由继续走流程，还是拦下来要求必须填一句话，这条也留给第 19 课；如果以后真的要接第二条业务线，除了命名空间过滤这道保险之外，要不要再给应用加一层访问权限控制，现在还没有需求，先记下这个问题。

## 七、收尾：从纸面 SPEC 到能跑起来还差什么

这一课结束时，四个决策点定死了，`docs/spec/feishu-gate/` 三份文档落了盘，但服务端一行代码都没有，服务常驻、卡片模板、回调分发这些东西都还不存在。

飞书 SPEC 定完四个决策点。照着它把服务实现出来，按钮点下去怎么回流成状态？
