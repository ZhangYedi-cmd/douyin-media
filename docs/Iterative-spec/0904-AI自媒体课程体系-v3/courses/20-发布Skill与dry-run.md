# 发布 Skill 与 dry-run：从登录验证到记账收口

第 19 课把飞书闸口从纸面决策变成了一个能跑的服务。卡按正确顺序推出去，两张卡上的按钮各自落到了对应的状态出边，回调守住了 3 秒窗口。改状态的动作全部经过 `media flip` 这个唯一入口并带着调用者身份，一条真实内容也真的走完了两次人点头，两次翻转在 `meta.yaml` 和 `audit.jsonl` 里都能查到对应的一行。那一课只碰到一件事没做完：通过按钮触发之后飞书会推出一张确认发布卡，那一课只核对了这张卡有没有出，卡上内容还是占位。人点头这一关通了，点头之后真发出去这一步，怎么做才不会误发？这一课把它做安全。

记忆锚点是一句话：发布前最后一次确认，不是走流程，是把要发的东西原样摆给人看一遍。这句话要拆成四件事去核对。不带发布信号的时候，有没有真的什么都没执行，只是把命令和物料摆出来。摆出来的命令和摘要，跟内容自己那份 `4-publish.md` 里的字段能不能一一对上。带着发布信号真发出去之后，状态和记录有没有真的落到位。失败的时候，状态是不是原地没动。四件事各自都有具体的观察结果能去查，skill 自己嘴上说成功不算数。

本课的输入有这几样：你自己第 2 课交付的 `docs/00-toolchain.md` 里 social-auto-upload 那条安装记录；第 3 课立的 `pipeline/4-publish.md` 骨架，闸口那句只带过一笔 dry-run，字段和判据都还没有展开；同样是第 3 课那批 `content/_template/` 模板里那份 `4-publish.md`，当时只按对照表生成了空文件，具体字段还没定；第 19 课走完审核流程、状态翻到 `approved` 的那条内容，它自己那份 `content/<slug>/4-publish.md` 已经填过，字段名不一定跟这一课要用的规格对得上；第 19 课那张确认发布卡，人点确认带的就是这一课要用的授权信号；第 12 到 16 课交付的全量 `media` 命令。产出是一个 `douyin-publish` skill，加一次真发或者 dry-run 到底。参考流水线自己有一套跑在生产里的实现，住在 `.claude/skills/douyin-publish/` 目录下，这一课会反复引它的字段映射和铁律写法，但引的是形状，不是给你抄的现成文件。你的字段名、判据文字要从你自己的文件出发，让 AI 照你定的规格去写。

## 1. 登录抖音：环境已经装好，这一课只做账号绑定

social-auto-upload 在第 2 课已经进了工具清单，`uv` 建的 Python 虚拟环境、浏览器内核当时都装完并且拿到过一次全绿自检。这一课不重装。环境和账号是两件不同的事：环境装一次能一直用，账号的登录态会过期，跟装没装工具本身无关。把这两件事混着讲，将来某天登录失效了，你会分不清是环境坏了还是账号该重新扫码了。所以这一课单独把账号绑定这件事拎出来讲清楚：cookie 存哪、扫码登录怎么做、登录态怎么验。

cookie 落在你 social-auto-upload 项目目录下的 `cookies/` 里，按账号名分文件，比如账号名是 `main`，文件就叫 `douyin_main.json`。第 2 课那次全绿自检里如果 `sau douyin check --account main` 真的跑通过，说明账号当时绑定过一次；这里要做的是把这个动作重新走一遍，确认登录态还有效，失效了就重新扫。

```
sau douyin check --account main
```

看到 `valid` 就说明这次不用重新登录，跳到下一节。看到 `invalid`，跑登录：

```
sau douyin login --account main --headed
```

这条命令会弹出一个有头的浏览器窗口显示二维码，用手机抖音 App 扫。扫完等浏览器窗口自己关掉，再跑一次 `check`，确认这次输出变成了 `valid`。

如果扫完码 `check` 还是报 `invalid`，多半是手机端点了扫码确认，但浏览器窗口在页面完全跳转回创作者主页之前就被手动关掉了，登录态没来得及写进 cookie 文件。重新跑一次 `login`，这次等到浏览器窗口自己关闭再去 `check`。

拿到结果核两点：`check` 的输出是不是字面上的 `valid`，不是别的近似字样；`cookies/` 目录下对应账号的那份文件的修改时间是不是刚刚更新过。登录验证过了，接下来把发布这件事封装成一个能被飞书服务调用的 skill。

## 2. douyin-publish 封装：一张规格表定映射

这一步不是一条 Prompt 钉死，是先把一张规格表填清楚，再让 AI 照表实现。字段名不用你现想：参考流水线的模板里，`4-publish.md` 定的是标题、正文/简介、话题标签、封面、建议发布时段、媒体文件这六项，这一课就照这个规格来。第 3 课那一步只让 AI 按一张对照表生成了六份空模板，没有具体到 `4-publish.md` 里该有哪几个字段，你自己第 3 课生成的那份、以及第 19 课那条走完审核流程的内容已经填过的那份，字段名可能跟这六项对不上，先照这六项把它们对齐。这一课要补的还有另一份文件：阶段契约 `pipeline/4-publish.md` 里，现在只有第 3 课立的输入、输出、状态翻转、闸口四项，闸口那句当时只带过一笔先 dry-run 再确认，没展开成能照着执行的判据，也没写清楚发布物料具体是哪六个字段。两份文件名字撞了，指的不是同一样东西：一份是每条内容自己的物料文件，一份是全局阶段契约。

先决定硬软之分：标题、正文、话题标签、封面、媒体文件这五样是硬字段，建议发布时段是软备注。硬字段缺一个就该拦住，不能拿空值往下走。软备注只是给人看的参考，不能被当成机器能解析的时间直接传给发布命令。参考流水线的 `pipeline/lessons.md` 记着两条教训，编号 L5、L6，就栽在这两点上：一次是出审时压根没产这份物料文件，人点过审后确认发布卡当场报缺标题；另一次是建议发布时段写成了能被解析的日期格式，被原样传给了 `--schedule` 参数。你自己的 `pipeline/lessons.md` 第 3 课立起来时还是空的，这两条算是提前替你踩过的坑。

把这五个硬字段加一条软备注，对上 `sau` 命令的参数，就是这一节要填的规格表，来源字段都在 `content/<slug>/4-publish.md` 这份每条内容自己的文件里：

| sau 参数 | 来源字段 | 说明 |
|---|---|---|
| `--title` | 标题 | 必填，缺了中止 |
| `--desc` / `--note` | 正文/简介 | 视频类用 `--desc`，图文类用 `--note` |
| `--tags` | 话题标签 | 去掉开头的 `#`，转成英文逗号分隔。发布时 `sau` 会自动把 `#` 补回去，没去掉原来的号就会叠成 `##` |
| `--file` / `--images` | 媒体文件（`assets/` 下的实际文件） | 视频类一个绝对路径，图文类按发布顺序给多个绝对路径 |
| `--thumbnail` | 封面（`assets/` 下的实际文件） | 视频类专用，图文类首图即封面不用这个参数 |
| `--schedule` | 建议发布时段，写成的具体时间 | 只有写成可解析的 `YYYY-MM-DD HH:MM` 才传，写的是散文备注就不传，视为立即发布 |

规格定完，让 AI 分两步实现：

```
先帮我在 pipeline/4-publish.md 的闸口那条之后，补一段说明：
发布物料具体是哪六个字段，照参考流水线的规格来：标题、正文/简介、
话题标签、封面、建议发布时段、媒体文件，外加发布回填那两行（实际
发布时间、链接）。这一步不算重新定义字段，是把阶段契约和物料模板
的字段名对上，再补一条 dry-run 铁律：默认只拼命令和物料摘要给人看，
不执行，只有拿到发布信号才真发。
补完再检查我自己的 content/_template/4-publish.md，字段名跟这六项
对不上的地方改过来对齐，多出来的字段先留着别删。
最后照它实现 douyin-publish skill 的读取与校验：
1. 读 content/<slug>/meta.yaml，status 必须是 approved，不是就中止并报告当前状态；
2. 读 content/<slug>/4-publish.md（每条内容自己那份，不是 pipeline/4-publish.md
   那份阶段契约），按六个字段逐条提取，缺哪项就报哪项，不许拿空值往下走；
3. 查 assets/ 下媒体文件和封面文件是否真的存在，转成绝对路径；
4. 话题标签去掉开头的 # 号，转成英文逗号分隔的纯文本。
```

```
按我这张规格表（sau 参数 / 来源字段 / 说明），把上一步校验通过的字段
拼成完整的 sau 命令：内容是视频类就用 upload-video，图文类就用
upload-note，账号名固定用我第一节验证过的那个。
发布时段只有 content/<slug>/4-publish.md 里写了具体的 YYYY-MM-DD HH:MM
才传 --schedule，写的是散文备注就不传。
命令拼完之后，另外拼一份人看得懂的物料摘要：标题、正文摘要、话题、
封面文件名、发布时间是立即还是定时到几点。命令和摘要都先只输出给我看，
不要执行、不要发送任何请求。
```

拿到结果审三点：缺字段的时候有没有真的中止，报出缺哪一项，没有拿空字符串接着往下拼命令；话题标签里的 `#` 号是不是被剥干净了；建议发布时段写的是散文备注时，命令里有没有真的没出现 `--schedule` 这个参数。字段读出来却对不上文件里写的内容，多半是 `content/<slug>/4-publish.md` 里那一行还留着模板占位符没删，看着像有内容，其实是示例文字。

skill 能拼命令了，命令拼完之后能不能直接执行，是这一课真正的红线。

## 3. dry-run 铁律：先摆出来，人点头才发

发布是这整条流水线里唯一一个真正不可逆的动作。文案写偏了可以重新生成，视频剪错了可以重新渲染，但一条内容一旦真的发到了抖音上，标题错了、封面错了，都已经在公网上了。所以这个 skill 默认要做的事，是把命令和物料摆出来等人看，不直接执行：不带发布信号，只把上一节拼好的命令和物料摘要打印给人看，绝不执行，然后停在这里等确认；只有带上发布信号，才直接真发。

这里容易绕的一点是，这不是先 dry-run 再问一遍确认这种两段式流程。带发布信号这一件事本身就等于人已经确认过了，因为这个信号的来源就是第 19 课那张确认发布卡，人在飞书上点确认发布的那一下，触发的正是带着发布信号重新调用这个 skill。真发那一次如果还停下来再问一遍，等于把已经拿到的授权当没拿到，自动化调用的场景里没人能回一个交互式确认，反而会卡死在等待上。

| 路径 | 触发条件 | 做的事 | 不做的事 |
|---|---|---|---|
| dry-run（默认） | 没带发布信号 | 校验字段、拼命令、拼物料摘要，打印出来 | 执行命令、发起任何网络请求、拉起浏览器 |
| 真发 | 带发布信号（等价于确认发布卡被人点过） | 直接执行拼好的命令 | 再次询问确认 |

验证这条闸有没有真的挡住：

```
把这个 skill 的执行逻辑加一条闸：默认情况下（没有传发布信号）跑完
字段校验和命令拼装两步之后就停在这里，把完整命令和物料摘要打印出来，
不能调用任何执行工具去跑这条命令，也不能建立任何网络连接；
只有明确传了发布信号，才跳过打印确认这一步，直接执行。
现在只测试没带发布信号的这条路径：拿一条我准备好的 approved 内容跑一遍，
把实际输出贴给我，我要看到的是命令和摘要，不能有任何执行过的痕迹。
```

拿到结果审两点：dry-run 那次浏览器有没有被拉起来，终端或日志里有没有出现过任何一次网络请求；打印出来的命令里，绝对路径、标题、话题标签，跟内容自己那份 `4-publish.md` 里写的内容能不能一一对上。命令打印出来是对的，真跑起来却卡在原地不动，多半是登录态在这中间过期了，回到第一节重新验证一次登录。

命令能安全拼出来、安全发出去了，最后要把这次发布记进真相源。

## 4. 记账收口：发布成功之后喊 media publish-done

发布收尾是全流水线状态记账的唯一位置。一条内容发布之后要改的地方有三处：`meta.yaml` 的状态要翻到终态、`backlog.yaml` 里对应的选题条目要跟着翻、`dashboard.md` 要把这条内容从在制表里移出去。这三处只要有一处漏改，选题池就可能重复拾取同一个题目，或者看板上一直挂着一条其实已经发完的内容。第 12 到 16 课已经把这三件事收口到一条命令里，这一课第一次真正用上它：`media publish-done <slug>`。

先看真发那次成功之后，内容自己那份 `content/<slug>/4-publish.md` 该长什么样。参考流水线的模板长这样，发布回填这一节本来就带在模板里：

```
# 发布物料

- **标题**：
- **正文/简介**：
- **话题标签**：#  #  #
- **封面**：assets/
- **建议发布时段**：
- **媒体文件**：口播视频 / 图片清单

## 发布回填
- **实际发布时间**：
- **链接**：
```

第 2 节那一步已经把你自己那份文件的字段对齐到这六项加发布回填两行，出审时应该已经填成真实值。这一课要让 skill 在真发成功之后，自己把最下面发布回填那两行填上实际时间和链接，账号按第一节验证过的那个另记一笔，这是 skill 直接编辑这份文件，不经过 `media publish-done`。

`sau` 命令跑完，看输出里有没有出现 `视频发布成功` 或者 `submitted` 这类成功字样。出现了才算成功，`sau` 的输出不一定带作品链接，链接常常要去抖音作品管理页面里人工确认再补。判定成功之后喊记账命令，命令怎么分流看的是这条内容当前的状态，不是你传了哪个参数：

```
# 情况一：当前状态 approved，立即发布成功，还没拿到作品链接
media publish-done <slug>

# 情况二：当前状态 approved，定时发布成功，先记一次 scheduled
media publish-done <slug> --scheduled "2026-06-16 19:30"

# 情况三：当前状态已经是 scheduled，定时任务到点真的发出去了，
# 再喊一次同一条命令、不用带参数，直接收尾成 published
media publish-done <slug>

# 情况四：当前状态已经是 published，事后补链接，必须带 --url
media publish-done <slug> --url https://www.douyin.com/video/xxx
```

这条命令自己也带着几道拦截：内容已经是 `published` 状态时，必须带 `--url` 才能跑，不带就直接拒绝，因为已经发布过的东西没有理由再空跑一次状态翻转；`--scheduled` 传的时间点必须晚于当前时间，传一个已经过去的时间点会被直接拒绝；`--url` 必须以 `http` 或 `https` 开头，格式不对也会被拒绝，不会把一串乱写的字符当成链接存进真相源。

失败了怎么办：先原样重试一次再排查，不急着转人工。参考流水线的 `pipeline/lessons.md` 记着两次真实失败又原样重试一次就过的案例：一次是首发时视频渲染慢导致上传超时，重跑同一条命令一次就过了；一次是抖音页面弹出的 UI 浮层挡住了选择封面的按钮，`sau` 报了非零退出码，人清掉浮层重跑一次也过了。原样重试一次还是失败，才转人工排查，这种情况不能调用 `media publish-done`，状态原地不动，等人工确认清楚了再决定下一步。

拿到结果核两点：`meta.yaml` 里的状态字段是不是真的翻到了预期的终态，不是停在半路；`content/<slug>/4-publish.md` 末尾发布回填那两行有没有真的写上实际发布时间和链接，链接暂时拿不到就先留空，事后再用 `media publish-done` 带 `--url` 补一次。安全发布的技术条件都齐了，剩下是真的按下去。

## 5. 收尾

有真实抖音号的学员，这里可以走完一次真发，看着 `media publish-done` 把状态和链接一次记完；没有号的，dry-run 走到底，停在完整命令和物料摘要这一步，同样算完成这一课，不因为没账号卡住。这一课能拿出来的证据不是 skill 没报错，是打印出来的命令跟物料对得上、`meta.yaml` 和 `content/<slug>/4-publish.md` 里能查到那几行。

生产线从取题到发布整条通了，可它只会消费资产：选题池会空，大脑不会自己长。谁来保养这些资产，按什么纪律改？
