# 无头作业：进程流归一与终局裁决

治理线能自己巡检记账了。可这些都要你敲一次命令才动。怎么让它在你睡觉的时候自己跑？

第 24 课交付了一份任务注册表、四个治理 skill（`douyin-retro`、`douyin-ideate`、`backlog-gardener`、`benchmark-refresher`）加自审元层 `account-audit`，外加一轮真实的巡检记账。到这一步，生产线和治理线都能跑通了，但两条线的起点都是你在终端里敲一条命令，或者把一份 Prompt 粘进对话框。这一课要把人从触发这一步摘出去：让一个进程去拉起 Claude Code 的无头模式，自己跑完一个任务，跑完之后自己说清楚这次跑得对不对。

记忆锚点是一句话。这一课要造的标准件只认识一件事：子进程 `stdout` 是一串 JSON 行，不认识任何调用方的业务概念。裁决同样只认一件事：落盘的文件状态，不信进程自己的自述。这两条合在一起，才是无人值守的完整定义：既要能自己跑，也要能自己说清楚跑得对不对、什么时候该停。

本课的输入是前面已经跑通的资产。一是 `douyin-publish`、`douyin-retro`、`douyin-ideate` 等技能，作为本课观察与解析的目标。二是 `media` CLI 的 core 包，第 12 到 16 课打磨好的文件锁与原子写逻辑，本课直接复用。最终产出包含三部分：一个 `cc-stream` 基础包（涵盖 `types.ts`、`transport.ts`、`normalize.ts`、`milestones.ts`、`spawn.ts`、`index.ts` 六个文件），一个只认磁盘文件的裁决函数，以及一套先礼后兵的子进程退出策略。本课聚焦把这些基础标准件做扎实。至于后续由谁拉起、常驻服务如何调度，属于模块 7 控制台要串联的内容。本课结束时，你手头将拥有可靠、能自证的无头作业基石。

## 一、三层解析：从 JSON 行到里程碑

一条无头模式吐出来的 JSON 行，要经过三层加工，才能变成一句人能看懂的进度。第一层只管把子进程的输出流安全地读成一个个 JSON 对象；第二层把这些半成品对象收敛成几种固定形状的事件；第三层拿这些事件去对一张规则表，看看命中了哪一条。三层各管一件事，业务知识只留在第三层的规则表里，前两层的代码里不应该出现任何一个具体任务的名字。

参考流水线在工程上划清了职责。传输层实现在 `transport.ts`：逐行读子进程的 `stdout`，把能解析成 JSON 的行往下传，解析不了的行直接跳过，不会因为一行坏数据把整条流读挂。归一层实现在 `normalize.ts`：把传输层给的半文档化对象，按照几条固定规则收敛成几种统一形状的事件。这一层需要维护轻量状态，因为同一条消息里的工具调用会在流里重复出现好几次，得做去重。里程碑层实现在 `milestones.ts`：只认一种事件，拿它去匹配调用方注入的规则表，命中了就吐出一个里程碑。这个包在源码头注中写得很直接：这是一个通用的无头 CC 观察器，只识别子进程的输出是一串事件，不感知任何调用方的业务概念。

这一课要观察的对象，就是你自己已经跑通的那几个 skill。cc-stream 不需要知道 `douyin-publish` 是发布还是别的什么，它只需要知道这段 Prompt 最终会被 `claude -p` 从命令行拉起来执行、往 `stdout` 吐一串 JSON。反过来想最糟的做法：如果归一层或者里程碑引擎的代码里直接判断某个工具调用是不是在发布，这个包就跟某一次具体任务绑死了，明天换一个任务类型，得回头改引擎本身。三层分工的意义就在这里，规则表可以按需替换，中间两层的代码始终保持稳定。

| 层 | 文件 | 输入 | 输出 | 是否认识业务 |
|---|---|---|---|---|
| 传输层 | `transport.ts` | 子进程 `stdout` 的字节流 | 半文档化的原始事件对象 | 不认识 |
| 归一层 | `normalize.ts` | 上一层给的原始事件对象 | 固定形状的归一事件 | 不认识 |
| 里程碑层 | `milestones.ts` | 归一事件 + 调用方注入的规则表 | 里程碑命中记录 | 规则表本身是业务知识，但住在调用方，引擎不认识 |

三层的骨架定完了，先把最底下这层的形状定下来：归一事件到底有几种，各自管什么。

## 二、七种归一事件与三档信任分级

一条 `assistant` 消息进来，里面可能同时混着一句话、一次工具调用、一段思考过程；一条 `user` 消息进来，可能带着一次工具调用的结果。归一层要把这些拆开，收敛成固定的几种事件，供后面两层统一处理。参考流水线的 `types.ts` 里定义了七种：会话启动 `started`、工具调用开始 `tool`、工具调用结束 `toolDone`、模型的文字旁白 `say`、模型的思考过程 `thinking`、卡顿信号 `stalling`、子进程收尾时给出的终局自述 `done`。

这七种事件的权重各不相同，参考流水线在设计规范中将其划分成三档。模型的文字旁白只用来展示，永远不参与任何判断。工具调用相关的两种事件驱动步骤时间线，告诉人现在走到哪一步了。真正的裁决只认落盘的文件状态，这一层里的任何一种事件都不能直接作为裁决的终局依据。即便是携带执行自评布尔值的 `done` 事件，第五节也会带你看到，它仅代表进程自评的第一道初步信号，不能作为终局裁决的依据。

| 事件 | 携带什么 | 驱动什么 | 是否只展示 |
|---|---|---|---|
| `started` | 会话 id | 标记一次运行的起点 | 是 |
| `tool` | 工具名、入参 | 驱动步骤时间线（喂给里程碑引擎） | 否，但也不裁决 |
| `toolDone` | 是否报错、结果摘要 | 驱动步骤时间线的收尾 | 否，但也不裁决 |
| `say` | 一段文字 | 仅供前端显示，不驱动状态 | 是 |
| `thinking` | 模型的思考文本 | 仅供前端显示，不驱动状态 | 是 |
| `stalling` | 卡顿原因 | 提示人这里在等待，不驱动状态 | 是 |
| `done` | 子进程自评的 `ok`、花费、轮数 | 作为第一道参考信号，不作终局裁决 | 是（就判断而言） |

`thinking` 这一档有个反直觉的地方：无头模式下，这类事件的正文实测恒为空。参考流水线在真实日志里统计过，十二份任务日志里出现过一百一十一个 `thinking` 内容块，正文字段全部是空字符串，只有一段加密签名有内容。另外单独做过两次真实实验，打开增量输出选项之后，思考过程的增量字段同样是空的。归一层因此只在真的拿到文本时才吐这类事件，今天你几乎看不到它。等哪天命令行工具放开明文输出，这里不用改代码就能自动生效。

```
Prompt：新建 cc-stream 包的 types.ts，定义七种归一事件的类型：started（带会话 id）、
tool（带这次工具调用的 id、工具名、入参）、toolDone（带 id、是否报错，外加一份用于
展示的结果摘要）、say（带 messageId 和文本，同一个 messageId 后来的内容按最新一条
覆盖）、thinking（带思考文本，仅在真有文本时才用这个类型）、stalling（带卡顿原因，
取值只有两种）、done（带子进程自评的是否成功、花费、轮数、耗时）。再新建
normalize.ts，实现一个有状态的归一函数：接收子进程 stdout 解析出来的半文档化对象，
按对象里的类型字段分流处理，收敛成上面七种事件之一；同一条 assistant 消息里的工具
调用会随着内容增长在流里重复出现，要按调用的 id 去重，只在第一次出现时吐出对应的
事件。
```

事件归一好了，下一个问题是怎么从这串事件里认出走到哪一步了。

## 三、里程碑引擎：声明式规则，业务知识留在外面

里程碑引擎只对工具调用开始这一种事件求值。这一设计经过深思熟虑。参考流水线的核心判断是：真实的执行进度要看子进程实际调用了哪些工具，不看模型输出了哪些旁白。`say` 和 `thinking` 仅用于界面展示，不驱动里程碑流转。

引擎本身设计得非常轻巧：接收一张规则表，每条规则写明要匹配哪个工具名，可选地再匹配这次调用的入参里某个字段要满足什么样的正则。命中一条规则后默认只吐出一次，后续同类事件不会重复命中。规则表具体包含什么业务，引擎并不关心。参考流水线的 `milestones.ts` 头注写得很直白：规则表内容属于领域知识，留在调用方配置，引擎本身不感知具体业务。后续遇到新的任务类型，只需替换规则表，无需改动引擎代码。

拿治理线的巡检举例。一次 `harness-dispatcher` 调度出去的巡检任务，大致要走四步：先读任务卡，再执行对应的技能，技能跑完要产出一份报告，最后记一笔账。这四步落成一张规则表，大概是这样：

| 里程碑 | 匹配条件 | 命中一次后 |
|---|---|---|
| 读任务卡 | 工具是 Read，入参的文件路径匹配 `harness/tasks.md` | 失效，不重复吐 |
| 执行技能 | 工具是 Skill | 失效，不重复吐 |
| 产报告 | 工具是 Write 或 Edit，入参的文件路径匹配 `harness/logs/` 或 `content/_research/` | 失效，不重复吐 |
| 记账 | 工具是 Bash，入参的命令里出现 `index.jsonl` | 失效，不重复吐 |

这张表跟三层引擎完全不冲突。读任务卡这个动作发生时，引擎不需要理解它读的是哪条流水线的任务卡，只管将这次工具调用与规则表里的正则做比对，命中后输出对应的记录。

```
Prompt：新建 cc-stream 包的 milestones.ts，实现一个里程碑引擎 createMilestoneEngine(table)，
接收调用方注入的规则表（数组，每条含 id、label、match.tool 精确名或正则、可选的
match.input 逐字段正则、once 默认 true），返回一个 feed(event) 函数：只对事件种类是
工具调用开始的事件求值，其余一律返回空数组；命中一条 once 规则后记住它的 id，同一次
运行内不再重复吐出；这个文件不能出现任何具体任务的字眼，比如“配音”“发布”，只做通用
匹配。再单独给我一张治理线巡检的示例规则表：读任务卡（Read 读 harness/tasks.md）→
执行技能（调用 Skill 工具）→产报告（Write 或 Edit 写 harness/logs/ 或 content/_research/
下的文件）→记账（Bash 命令里出现 index.jsonl），四条都设成只命中一次。
```

引擎齐了，剩下的问题是怎么真的拉起一个无头进程，把它的输出喂给这套三层解析。

## 四、拉起无头 claude -p：三个坑与一次真跑

拉起子进程、处理继承的环境变量、接入标准输出流，这三处关键细节背后各自对应一处容易疏漏的技术细节。参考流水线给出了针对性的解法。

### 4.1 三个坑（认证 / 超时 / 输出流）

第一个坑是认证问题。参考流水线遇到过的故障是：运行环境中登录 Claude Code 后，环境变量 `ANTHROPIC_API_KEY` 中保存的值其实是一段 OAuth token。如果子进程直接继承该变量，会被当成常规 API key 传给服务端，从而引发认证失败。对策是在 spawn 子进程之前，从继承的环境变量表中将该变量剔除。剔除后子进程会自动回退读取本地 `~/.claude` 目录下的登录凭证，与你在终端直接执行 `claude` 命令使用同一套身份认证。

第二个坑是超时处理。子进程有可能在某个工具调用中受阻挂起，例如等待一个没有返回的网络请求。如果缺少超时保护，子进程就会一直滞留在系统里，外部无法获知它是仍在执行还是已经挂起。因此需要预留可选的超时参数，到期主动触发终止。至于具体的退出时序，收尾这么关键的步骤不能草率，会在第六节展开梳理。

第三个坑是输出流的接入。`stdout` 采用按行输出 JSON 对象的格式，每一整行对应一条独立的消息记录。切忌将整条输出流当作单个大 JSON 进行解析，否则必须等待进程彻底退出才能读取内容，让长时间任务失去实时监控意义。稳妥的做法是采用逐行读取机制，对每一整行独立尝试解析，遇到解析异常的行直接跳过，避免单行错误阻塞整条流。在此基础上还可以增加一层兜底：无论单行 JSON 解析是否成功，均先将原始行文本无损追加到日志文件中，为后续排查问题保留可靠的依据。

```
Prompt：新建 cc-stream 包的 transport.ts，实现 parseStream(stdout, { onRaw })，用逐行
读取的方式接子进程 stdout，每一整行（不管后面 JSON 解析成不成功）先过一遍 onRaw 钩子，
用于原始行落盘排障；JSON 解析失败的行直接跳过，不抛异常；如果这一行本身是系统噪音
（比如钩子事件），在这里丢弃，不传给下一层。再新建 spawn.ts，实现 runHeadlessCC(opts)：
拉起 claude -p <prompt> --output-format stream-json --verbose --allowedTools <白名单>，
子进程环境变量默认剔除 ANTHROPIC_API_KEY（留一个参数可以扩展要剔除的其它变量名）；
opts 留一个可选的超时时长，到时候触发终止（怎么终止下一步会补）；把 spawn、传输层、
归一层组合好，返回一个归一事件的异步流、进程 pid、一个终止方法和一个收尾结果的
Promise。最后建 index.ts，把这几个函数和用到的全部类型统一导出。
```

### 4.2 一次真跑验证

各个模块是否能够顺畅协同，光看静态代码不够直观，需要通过最小任务完成一次真实执行验证。参考流水线的测试策略中，用于检测协议是否漂移的探测任务非常克制：读取一个文件、执行一条 `echo` 命令，然后正常收尾退出。按照这一思路，选取工程中已有的文件即可，例如读取一遍 `pipeline/daily-run.md`，随后执行一条 `echo` 输出一段确认信息。工具白名单仅配置 `Read` 与 `Bash` 两个，避免引入多余依赖。

跑完之后，对着归一事件流核查三项指标。第一项，会话启动事件中的会话 id 必须为非空字符串。第二项，每一次工具调用事件都必须能找到对应的一次工具调用结束事件，两者的调用 id 准确配对。第三项，流的最后一个事件必须是收尾事件，其中的自评状态 `ok` 符合预期。

如果在输出流中没有看到工具调用结束事件，常见原因是工具白名单限制过紧，或者给出的 Prompt 本身并未指示其调用文件读写或终端命令。另外需要留意的是界面展示字段的设计：工具调用结束事件的结果摘要通常仅截取前二十行，超出部分会标注截断提示并记录原始字节数。如果需要查看完整输出，应当查阅落盘的原始 JSONL 记录文件。展示字段本身定位于轻量摘要，并不适合用来通读全部内容。

cc-stream 的六个核心文件准备就绪，能够吐出规范的事件流。一次执行完毕后究竟算不算成功，还需要可靠的仲裁机制来把关。

## 五、只认文件的裁决，加上守住并发的锁

在一次真实的创作任务中，进程执行中途触发了服务商的会话限额，模型直接输出了配额超限的提示文字。子进程收尾自评虽然返回了报错，但并不能作为该任务的最终定案。裁决函数会现场读取该内容条目的 `meta.yaml`。当发现其状态仍停留在创作中，未翻转到出审，由此确认该任务未执行完毕。这是一份真实的运行记录，也印证了参考流水线的设计理念：子进程自身的语言表达与落盘的业务状态是两码事，系统裁决始终以后者为准。

### 5.1 裁决函数：读条目 meta.yaml 的 status，判它是否落到预期值

另一份测试日志同样说明了这个问题。在一次发布任务中，模型输出的旁白中已经说明发布动作并未实际执行，阻塞在物料校验阶段。然而裁决函数生成的总结日志却是一条固定文案：子进程自评通过，但状态停留在审核通过。之所以与模型的语言表述不一致，原因在于裁决函数的代码实现中完全不包含解析旁白字段的逻辑。从设计上看，裁决模块完全与自然语言解耦，只针对结构化文件进行校验。

这种通过架构限制杜绝失控的做法，在前面的课程中已经出现过。第 9 课在配置 `dubbing-reviewer` 裁判子代理时，白名单中剥离了 `Edit` 与 `Write`，使质检环节从物理权限上无法直接修改文件。本课则是同一种设计原则在裁决逻辑上的延续：裁决函数从输入源头就不接入自然语言，从依据上杜绝了对模型自述的盲目采信。

裁决函数的核心逻辑十分聚焦：现场读取对应内容目录下 `meta.yaml` 的状态字段，判断该状态是否属于本次任务期望的终态集合。之所以要求现场读取磁盘，是因为常驻服务维护的内存缓存快照可能存在数百毫秒的延迟。在关键状态裁决环节，任何细微的快照延迟都可能导致误判，必须以磁盘最新数据为准。子进程本身的退出码与报错信号同样会被记录，但它仅用于生成辅助说明日志，不直接参与终态判定。

| 裁决类型 | 输入 | 读哪个文件的哪个字段 | 期望状态集合 | 输出 |
|---|---|---|---|---|
| 创作裁决 | 内容的 slug | 该条目 `meta.yaml` 的状态字段 | `review` | 是否落到期望值、读到的真实状态、期望集合、一句说明 |
| 重做裁决 | 内容的 slug | 同上 | `review` | 同上 |
| 发布裁决 | 内容的 slug、子进程是否报错 | 同上 | `published` 或 `scheduled` | 同上 |

```
Prompt：写一个裁决函数，输入是内容条目的 slug 和子进程有没有报错这个布尔值，不读任何
模型生成的自然语言输出。函数体只做一件事：现场读这条内容目录下 meta.yaml 的状态字段
（不要用任何缓存的快照，直接读磁盘），判断它是不是落在这次任务期望的状态集合里（比如
创作任务期望 review，发布任务期望 published 或 scheduled）。返回一个对象：是否落到
期望值、读到的真实状态、期望集合、一句给人看的说明。子进程报没报错这个信号只用来拼
说明文案里的措辞，不能单独决定裁决结果。
```

如果裁决判定未通过，而翻看日志发现子进程实际已经推进完成了目标动作，常见原因是期望状态集合定义得过于狭窄，遗漏了合法的可选终态。此时应当检查并完善期望状态集合，将遗漏的合法终态补充进去，避免脱离裁决逻辑去人工硬编码。

### 5.2 单并发与锁：陈旧判据要同时满足两个条件才能抢占

裁决负责在任务执行完毕后给出判定，文件锁则负责在执行前防止并发冲突。同一条内容不能被两个进程并发修改，这是贯穿全局的核心约束。第 12 到 16 课开发 `media` CLI 时，core 包内已经构建了完善的文件锁机制，本课直接复用现有设计。

加锁机制依赖原子排它创建：首个以排它模式创建锁文件的进程获得执行权，并在文件中写入当前进程号、时间戳以及正在执行的命令。如果锁文件已存在，则读取其中的进程号和时间戳，评估该锁是否已进入陈旧状态。陈旧判定需要同时满足两项前置条件，二者缺一不可：第一项是锁文件的记录时间距今已超过陈旧阈值；第二项是原持有该锁的进程已不再存活。参考流水线将该阈值默认设置为三十秒。你在第 13 课制定规范时如果采用了其他阈值数值，继续沿用既有配置即可，双重条件的逻辑判定保持一致。只有在两个条件同时成立时，才允许移除旧锁文件并重新抢占。抢占操作需要在标准错误流中记录详细日志，标明被抢占的进程号、对应命令以及加锁时间戳。只要有一项条件不满足，均立即报错退出，不进入排队等待。

| 锁规格 | 内容 |
|---|---|
| 锁文件放哪 | 仓库根目录下一个约定文件名，跟具体某条内容的目录分开放，一次只需要一把全局锁 |
| 锁文件里写什么 | 当前进程号、抢锁时的时间戳、正在执行的命令 |
| 陈旧判据的两个条件 | 距记录时间超过陈旧阈值（参考流水线默认三十秒，按你自己第 13 课定的数来），且记录的进程号已经不在了；两个都满足才算陈旧 |
| 抢占后要留痕 | 往标准错误流打一行，写清楚被抢占的进程号、命令、留锁时间 |

为什么必须两个条件同时满足才允许抢占？如果仅超时但原进程仍然存活，可能只是某项重型任务耗时较长，盲目抢占会引发两个进程并发修改同一份数据。如果原进程虽已退出但尚未超过时间阈值，异常退出后的清理动作可能仍在收尾，立即接管同样存在安全风险。只有双重条件叠加，才能确认该锁确实已被遗弃。这里的咨询锁定位于冲突拦截而非排队机制。采用保守报错策略，可以有效防止多任务交错写入。

抢锁总是失败，常见原因是陈旧判据只满足了一个条件：进程其实还活着，或者时间还没到陈旧阈值。两个条件缺一个就只能等，手动删锁文件反而可能把一个正在正常跑的任务写乱。

```
Prompt：看一下 media CLI core 包里已有的锁实现，抢一把咨询锁、判断陈旧、原子创建锁
文件那部分逻辑，给无头作业复用同一套：抢锁时用排它方式创建一个锁文件，写进当前进程号、
时间戳、正在执行的命令；抢不到就读旧锁文件里记的进程号和时间戳，只有同时满足超过
它现有的那个陈旧阈值未释放、且那个进程号已经不存活这两个条件，才允许删掉旧锁文件
重新抢占，阈值本身不要改，直接用已有实现里的那个值；抢占这一下要往标准错误流打一行
痕迹；两个条件缺一个就直接报错退出，不排队等待。
```

裁决和并发都管住了，进程本身怎么正常收尾，收不住的时候怎么恢复，还没定。

## 六、收尾与恢复：先礼后兵，内存不可信

任务超时不能直接强行终止。子进程在收到退出信号的瞬间，可能正在落盘临时文件。如果不给缓冲直接杀死进程，容易在文件系统中遗留损坏的数据分块和无主的子进程。参考流水线采取先礼后兵的策略：先发出温和的终止信号，给子进程预留退出时间；若宽限期结束后进程仍未退出，再执行强制终止。

### 6.1 收尾时序：SIGTERM 先给宽限期，仍不退再 SIGKILL

到达预设的超时时限，或者外部调用方主动取消任务时，系统首先发送 SIGTERM 终止信号，同时启动一个十秒倒计时的定时器。子进程如果在十秒内正常完成退出，定时器随之注销，清理流程顺利结束。如果十秒倒计时结束时子进程仍未退出，定时器回调将补发 SIGKILL 强制终止信号，确保系统资源被彻底释放。

| 信号 | 触发时机 | 等待时长 | 下一步 |
|---|---|---|---|
| 终止信号 | 到达超时时长，或调用方主动喊停 | 立即发出 | 挂一个十秒定时器，等子进程自己退出 |
| 强制终止 | 十秒宽限期内子进程仍未退出 | 立即发出 | 子进程被系统强行终止，收尾结果随之确定 |

这套逻辑最早只接在超时这一条路径上。参考流水线后来在看板上加了取消任务这个能力，才把人工喊停也接进同一套先礼后兵的处理。两条触发路径现在共用同一个十秒宽限期的定时器，重复调用是幂等的：定时器已经挂上了，再喊停一次也不会重复挂一个。

进程终止后，若监控显示系统资源仍未释放，通常是子进程自身派生了子进程导致的。向主子进程发送强制信号时，若未绑定进程组，容易残留子孙进程。

```
Prompt：给子进程实现一个先礼后兵的终止方法：调用时先发一个终止信号，同时起一个十秒
的定时器；十秒内子进程自己触发了退出事件就清掉这个定时器，什么都不用再做；十秒后
子进程还没退出，定时器触发时补发一次强制终止。这个方法要同时接住两条触发路径：到
达超时时长时自动调用它，调用方主动喊停时也调用同一个方法，不要各写一套；两条路径
共用同一个定时器状态，重复调用要幂等，定时器已经挂上就不再挂第二次。
```

### 6.2 恢复规则：触发场景、内存态怎么处理、从哪个文件兜底重建结论

一个进程记着任务跑到哪一步了，这份记忆只活在内存里，进程一死就没了。这一课能给的真相源，从头到尾只有一个：`meta.yaml`。判断一个任务的最终结果，永远走一遍第 5.1 节的裁决函数，现场读这个文件。内存记录仅用作展示加速，磁盘落盘的元数据才是系统的最终真相源。

两种场景都会让内存状态变得不可信：使用者在操作界面主动取消，或者运行进程及其宿主服务遭遇崩溃重启。在这两种场景下，处置的第一准则完全一致：丢弃不可靠的内存状态，通过裁决函数重新校验落盘文件。区别在于清理阶段是否需要额外处理锁文件。遭遇意外重启后，上一轮任务如果持有着文件锁未释放，新一轮任务需要依照第 5.2 节的两项陈旧判定条件接管锁资源。进程如果随宿主崩溃退出，系统已无法查到其进程号，但陈旧阈值的计时判定依旧需要等待满足。

| 触发场景 | 内存态怎么处理 | 从哪个文件兜底重建结论 |
|---|---|---|
| 人工取消 | 丢弃，不当成真实结果 | 复跑一次裁决函数，现场读 `meta.yaml` |
| 进程或服务意外重启 | 整份内存记录当成不存在 | 同样复跑裁决函数读 `meta.yaml`；上一轮留下的咨询锁按第 5.2 节的两个条件正常抢占 |

参考流水线在这条原则上又往前走了一步：控制台后端给每次任务收尾都额外落一份终态快照。重启后先查这份快照，查不到再退回原始事件流当中途状态处理，两者都没有才算没跑过。这一层更细的兜底属于模块 7 要造的控制台，这一课不用去搭它。但它遵守的还是同一条原则：内存不可信，真相在文件里，落盘的东西会随着系统长起来变得更细，原则本身不变。重启后新一轮任务反而抢不到锁，常见原因是旧锁刚好卡在陈旧阈值的判定窗口里，等一下就好，不用手动删。

无人值守这条线该收口了。这一课造出了一个不认识任何业务概念的 `cc-stream` 包：三层解析、七种归一事件、一个通用的里程碑引擎、一次真跑通的无头 `claude -p`。加上一个只认文件的裁决函数，一套先礼后兵的收尾策略，还有一条内存不可信、真相在文件里的恢复原则。整条流水线能无人值守跑完了，可你只能靠翻文件和日志知道它跑到哪。第三件重活：给它做个能看的控制台。
