## 十、UX 走查与三波返工（2026-08-19 白天）

### 起因
用户上线试用后报三类体验问题（样式错位、markdown 无预览、任务面板关不掉）。我用 Playwright
按 1440/1280/1120/1024 四档视口把六个页面 + 详情页真机点了一遍，产出审计报告：**总分 4.6/10**
（布局稳健性 3、文案语义 3、错误与空态 3、危险动作防护 4、信息架构 5、视觉一致性 5、交互反馈 6、
数据价值 8），13 条缺陷。报告见对话内 artifact（含 8 张截图取证）。

### 三条系统性根因（不是十几个独立 bug）
1. **原型是在「一种宽度 + 短假数据」下调出来的**。`theme.css` 从 `docs/design` 原样搬入，那份稿子
   只在单视口、短标题假数据下验证过；装上真实数据（长标题、17 条同类警报、不可断的 slug）再混
   antd 组件盒模型，布局假设即破。**验收只断言功能，没有「真实数据 × 多视口」的视觉关**——
   这才是这批问题一条都没被拦住的原因。
2. **界面文案的作者是契约文档，不是使用者**。执行方案里的术语（P1 / 口径 / 留痕 / 降级 /
   DeadlineBadge / periodic:2d）被原样搬上屏幕。量化：总览页出现 `meta.yaml` 21 次、`published`
   23 次；选题池「口径」18 次；详情页直出拼音枚举 `kouban · depth`。
3. **把两种生命周期塞进同一个容器**。任务面板既是「正在跑」的进度条又是「跑完了」的成本/裁定
   存档，需求打架，于是既关不掉又不敢清。三个 P0 里有两个同源于此（另一个是详情页加载失败仍
   渲染上一条内容的 stale render）。

### 编排方式

逐文件核对无越界）：

  E 信息架构（警报聚合、侧栏徽标、健康灯、刷新按钮）。
- **第二波（1 个）**：F 全站文案扫盲，规格书 = 新增的 `07-界面用语对照表.md`（由总指挥手写，
  判断密集的部分不外包）。
- **第三波（1 个）**：G 收尾第一波修完才暴露出来的下一层问题（R1~R7）。

配套三件基建：① 起 vite dev server + 通用截图脚本，agent 改完能自查并把图读回去确认，不是盲改；

### 值得记住的技术坑
1. **flex/grid 子项默认最小尺寸**是这批布局问题的总根因，且有两种镜像表现：一边被挤扁（详情页
   `h1` 无 `min-width:0`，被 nowrap 的命令条抢光宽度，1024 下标题塌成一列竖排 461px 高），
   一边被撑破（`.grid.cols-2` 用 `1fr` 而非 `minmax(0,1fr)`，一个宽表格把治理线整页顶到 ~4500px）。
   `theme.css` 所有多列 grid 已统一补 `minmax(0, …)`。
2. **antd v6 Table 的 `table-layout:auto` 是内联写死的**，纯 CSS 压不过——列宽给足也照样按内容
   抢空间。必须给 `<Table scroll={{ x: 980 }}>`（不能用 `'max-content'`，会连标题列也强制单行把
   表格顶到 2305px）才会真正切到 `table-layout:fixed`。
3. **「按钮被挤压」的自动判定别用高度启发式**（高度 > 行高×N）——内部嵌了徽标子元素的正常控件
   会被误判。正确做法是量文本节点的行盒数（`Range.getClientRects()` 的不同 top 数），直接判定
   「这段文字有没有被折成多行」。第一版脚本因此误报，已修正并回告 agent。
4. **服务端文案不能直接改成人话**：`core/src/alerts.ts` 的 13 条 message 同时是 `media check` 的
   终端输出，命令行读者要的就是那种精确度。正解是 UI 层加 `rule → 人话标题` 映射
   （`components/AlertCard/ruleTitles.ts`，rule id 是稳定连接键），主行人话、次要行技术原文，
   未登记的 rule 回退显示原 message。收尾时发现「待我处理」漏用同一映射，导致同一页左右两种
   口径，已补齐（`todo.kind === alert.rule`，同源）。

## 十一、CC 运行日志查看（2026-08-19 晚）

### 起因
用户：「点击开始创作，在小框子里看日志也太难受了……能在详情页中加入一个 CC 运行时日志解析、
分析的功能么？这样可以看到创作的全链路。」随后补充：「claude -p 输出的是管道数据流，我们做一个
管道数据解析器就可以」，并要求先 review `cc-stream` 是不是过度设计了。

### cc-stream 的体检结论（先想清楚再动手）
- **确实过度设计的是里程碑引擎**（`milestones.ts` + 配套四个类型 ≈ 73 行）：它是个正则匹配 DSL，
  实际干的事是「Bash 命令含 `sau` → 标记『上传/真发』」。实锤在今天的代码里——加「开始创作」时
  封面那步需要「写文件**或**跑脚本」的语义，DSL 表达不了 OR，只能用**两条共享同一个 id 的规则**
  绕过去。比宿主语言表达力更弱的 DSL 是过度抽象的典型病征，写成普通谓词函数本来就一行。
  **但没顺手拆**：它现在能用、有测试，拆它对本需求零收益，属于没有触发条件的重构。
- **整包不算过度设计**：`spawn.ts`（超时 + 信号升级）、`transport.ts` 的 `onRaw` 落盘钩子
  （**今天能回放历史日志全靠它**）都付得起自己的成本。它比用户给的 55 行参考实现重，是因为活不
  一样：参考实现打印完就退出，cc-stream 要喂一个必须自洽的 UI，光 `tool_use` 块按 id 去重就少不了。
  **这个差别值约 60 行，值不了 360 行。**
- **真正的病不是「多」，是方向反了**：归一层有两处明确丢弃，注释写着「信任分级——模型叙述只有
  text 才展示」。这条原则在**决定任务成败**上完全正确（不让模型自述翻转状态），但被越界用到了
  **展示**上。看得见工具输出不会让任何状态翻转，只是让人看得懂。所以这个需求撞上的不是「包太重」，
  恰恰是「包在该留的地方太轻」。扩容只加展示字段（`at`/`preview`/`truncated`/`bytes`/`interrupted`），
  不改任何驱动语义：里程碑引擎仍只吃 `kind==="tool"`，裁决仍只复读文件。

### 编排
总指挥先定 `NormEvent` 契约（`cc-stream/src/types.ts`），再派两个并行 agent：K 号做归一层扩容 +
回放端点 + SSE 实时推送，L 号做界面。K 交付后验收中又发现一个缺口，追派 K 补 `/api/jobs/history`；
L 交付后走查发现治理线挂载点结构错误，另派一个 agent 改成弹窗。

### 值得记住的技术坑（续 §十）
5. **headless 模式下模型思考明文根本拿不到**。契约里排了 `thinking` 事件、UI 也做了默认折叠，
   实测才发现：12 份真实日志共 111 个 thinking 内容块，`thinking` 字段 **100% 是空串**，只有
   加密 `signature` 有内容。又跑了两次真实 `claude -p --include-partial-messages` 实验，
   `thinking_delta` 增量事件的明文**同样是空**——CLI 在 headless 出站时一律抹掉思考明文，
   **没有开关能打开**。归一层因此改成「只在明文非空时才吐事件」：今天恒不触发（界面不会出现
   一串点开永远是空的折叠块），将来 CLI 若放开则自动生效。**别再试第二遍。**
6. **`GET /api/jobs` 的磁盘兜底是死分支**。它只在 `recent.length === 0 && !active && queued.length === 0`
   时才从 `*.result.json` 重建，所以只要当天跑过任意任务，超过 24h 的历史就永久不可见——详情页
   「执行记录」tab 对一周前创作的内容会是空的。修法是**开新端点** `GET /api/jobs/history?slug=|task=`，
   刻意不改 `JobsListData.recent` 的语义：`recent` 是 JobPanel「近期」该显示的东西，让它冒出一周前
   的任务是另一个 bug。（本项目已在「同一份数据两种口径」上栽过三次：警报区 vs 待我处理、
   账本 vs 注册表、报告路径归一化。这是第四次机会，没重演。）
7. **同一界面出现两种时间口径**：日志事件时间直接渲染了 `NormEvent.at` 原文
   （`2026-08-19T05:45:48.606Z`，UTC + ISO），而同一页上方的里程碑走本地 `13:46:05`——读的人
   要么以为任务跑了两次，要么以为时间轴错了。已抽 `ui/src/lib/format.ts` 的 `clockTime()`，
   两处都调它。判据（07-对照表）：这串字符不会被人原样复制去对账 → 说人话。
8. **别把又长又宽的正文塞进 antd 表格的展开行**。治理线最初把日志挂在 `expandable` 展开行里，
   实测 `.ant-table-body` 的 `clientWidth=1134` 而 `scrollWidth=4280`——要横滚近 4 屏才读得完。
   根因：展开行是表格里的一个 `<td>`，表带 `scroll={{x:980}}` 按内容自然宽度撑开，日志里不换行的
   `pre` 块的 min-content 宽度直接决定整张表的宽度。改回弹窗承载——与本页治理报告同一个结论
   （用户原话「在右侧展示就很奇怪，点击后直接在弹窗中展示吧」），是同一个错误换了个更糟的形式。
