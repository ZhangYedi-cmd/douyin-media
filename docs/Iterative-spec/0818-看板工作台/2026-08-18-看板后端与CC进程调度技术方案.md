# 看板后端与 CC 进程调度 · 技术方案

> 版本：v0.1｜日期：2026-08-18｜状态：已拍板（本轮讨论定案）
> 范围：**看板后端架构（含写路径）+ CC 进程调度与消息解析**。前端路线与产品形态另行成文。
> 关联：`../2026-07-15-看板后端架构决策.md`（ADR，本文是其修订与扩展）｜`2026-08-18-流水线CLI技术方案.md`（CLI `media`，本文写路径的地基）｜`../2026-07-11-流水线看板-PRD.md`
> 一句话：看板从「只读催办台」升级为「裁决台」（审批发布、治理结论入库），但 server 本体永远不写文件——所有写动作收敛为 subprocess 调 `media`（快写）或 spawn 无头 CC（慢任务），配一个独立的 CC 消息流解析包。

---

## 1. 演进背景

原 ADR 铁律「零写接口」的成因是当时写 = Claude 手编文件，看板不敢碰。CLI 方案落地后写路径收敛到 `media`，且用户明确要求看板承担：①审批发布；②裁决治理线结论是否入库。故铁律**重新表述**（非废除）：

> **看板 server 永远不直接写文件（不 import `writer.ts` 的包边界不变）；所有写动作 = subprocess 调 `media` 或 spawn `claude -p`。**

server 因此始终只是「调度员」：不含业务规则、不碰文件，可随便崩随便重启——规则在 CLI，真相在文件。

## 2. ADR 五决策复核（CLI 落地后）

| ADR 决策 | 结论 |
|---|---|
| 无数据库、内存态全量重建 | **原样成立且被强化**：重建逻辑上移为 core 纯函数，CLI/server 共用 |
| chokidar + SSE 推 refresh | 成立；监听层加防护（§8） |
| Hono | 成立；**微调**：废弃 ADR 依赖清单里的 `js-yaml`，全仓统一用 `yaml` 包（CLI 方案 §4 已定，一份解析实现） |
| 只推 refresh 信号 | 成立；信号附带单调 **revision** 号（§3） |
| 文件读取白名单 | 成立；`PIPELINE_REPO_ROOT` 注入沿用 |

## 3. ADR 三个开放问题——拍板

1. **全量重建 vs 增量：拍死全量。** 百余个小文件全量 <100ms；5 条警报全是跨源交叉校验（meta×backlog×logs），增量失效图≈全量。规模十倍后再议。
2. **部署：合并，单端口 5170。** server `serveStatic` 托管 UI；前端零构建（另文），故无需 Vite dev server，开发/生产同一形态。
3. **SSE 断线：维持「丢了重拉」+ revision 保险。** 每次快照重建 revision++；SSE 事件与 `/api/health` 均带它；EventSource 重连后比对 revision，不一致即全量重拉。不做事件补发队列。

## 4. 包结构（四包，依赖方向即架构）

```
tools/console/                       （独立仓，npm workspaces）
├── packages/core/        领域核心：parsers + state + alerts + writer（纯函数，仅依赖 yaml 包，零服务端依赖）
├── packages/cli/         media（依赖 core；全仓唯一 import writer.ts 的包）
├── packages/cc-stream/   无头 CC 观察器（零依赖叶子包，只用 node 内建，见 §7）
└── packages/server/      Hono + 动作层 + job runner（依赖 core + cc-stream）
```

硬边界三条：

- **server 禁 import `writer.ts`**——零写铁律焊死在依赖方向里。
- **core 与 cc-stream 互相不认识**：一个管领域规则、一个管进程观察，无交集。
- **cli 不依赖 cc-stream**：`media` 自己不 spawn CC。

### core 的 API 形态：纯函数快照式

```ts
buildSnapshot(root): Snapshot                 // parsers 聚合，无内部状态、零 IO 绑定
computeAlerts(snapshot, now: Date): Alert[]   // now 必须注参
```

理由：`media check` 是一次性同步调用，看板是常驻消费，同一份警报代码服务两者的唯一解是无状态纯函数。chokidar/watcher 归 server 壳。**时间型警报**（待审积压 >48h、治理逾期）在文件不变时也会过期，server 除文件事件外加 **10 分钟定时 tick** 用新 `now` 重跑 computeAlerts。

## 5. 写路径一：动作层（毫秒级记账）

新增少量 POST endpoint，**每个 1:1 映射一条白名单内的 `media` 命令**，参数走 args 数组 `execFile`（不经 shell，注入面为零）：

| Endpoint | 背后的命令 | 场景 |
|---|---|---|
| `POST /api/actions/review` | `media flip <slug> approved/drafting/rejected --reason` | 审批过/打回 |
| `POST /api/actions/backlog-apply` | `media backlog apply <id> …` | 结构化治理提议入库 |
| `POST /api/actions/promote` `next-up` | `media promote` / `media next-up set` | 选题裁决 |

流程：浏览器 POST → server 白名单校验 → `execFile("media", [...], {cwd, timeout})` → media 内部完成锁/校验/事务/check → server 读 exit code + `--json` stdout 回给浏览器。**界面数据更新不走响应**，走正常的 chokidar→快照→SSE 链路——写者与读者经文件系统解耦。

每个动作 UI 先展示 `--dry-run` 输出再确认（CLI 的 dry-run 能力 = 审批界面的变更预览）。

**安全**：写端点只 bind `127.0.0.1`；UI 携带启动时生成的 token 防浏览器侧 CSRF。单机单用户，到此为止，不上认证系统。

## 6. 写路径二：job runner（分钟级判断性任务）

「确认发布」「打回重做」「散文提议入库」不是机械命令，spawn 无头 CC（`claude -p`）执行。设计：

- **内存任务表 + 单并发**（流水线本来串行），一个 Map + 子进程句柄，不引队列中间件。
- **幂等锁**：同一 slug 同时只允许一个任务（继承 feishu server `_publishing` set 的教训——回调重投/人连点会双发，真发不可逆）。
- POST 立即返回 202 + 任务 id；进度经 SSE 推 `job:<id>` 事件；stdout 原始流落盘 `logs/jobs/<id>.jsonl`。
- **崩溃安全**：server 挂了任务表丢了无所谓——真相在文件里，重启后快照 + `media check` 给出真实状态；发布任务有「只发 approved」闸口 + sau 幂等，重发起安全。「事件可丢、状态可重建」延伸到任务层。

### spawn `claude -p` 的四个防坑点（继承自 feishu server 实测）

1. 子进程环境**剔除 `ANTHROPIC_API_KEY`**（本机是 OAuth token，子 claude 误当 API key → Invalid API key；剔除后回落 `~/.claude` 登录凭证）。
2. `--allowedTools` 白名单，只授予该任务所需工具。
3. **授权语义写死在 prompt 里**：`claude -p` 非交互无人可答确认，prompt 必须明说「人已在界面确认 = 授权」。
4. **成败判定读状态不读文字**：`result` 事件的 `is_error` **加上**复读 meta.status 双重确认，绝不解析自然语言输出判成败。

## 7. cc-stream 包：CC 消息流解析（独立子包，已拍板）

### 7.1 协议事实（2026-08-18 实测）

`claude -p --output-format stream-json --verbose` 的 stdout 为 JSONL 事件流，实测事件谱系：`system/init`（会话启动）、`system/hook_*`（噪音）、`assistant` 消息（含 `thinking`/`text`/`tool_use` 内容块）、`tool_result`（带 `is_error`）、`api_retry`/`rate_limit_event`（健康信号）、`result`（终局：`is_error`/`num_turns`/`duration_api_ms`/`total_cost_usd`）。

**核心洞察：`tool_use` 是事实不是叙述**——进度靠看子 CC 实际动了什么手，不靠理解它说的话。

### 7.2 三层解析

1. **传输层**：逐行 readline + JSON.parse（半行缓冲）；hook 噪音过滤；未知 type 静默跳过（前向兼容）；原始 JSONL 原样落盘。
2. **事件归一层**（有状态）：收敛为 6 种内部事件：`started(sessionId) | tool(name, input) | toolDone(ok) | say(text) | stalling() | done(ok, costUsd, turns, ms)`；同一 assistant 消息随内容块增长重复出现，按 `tool_use.id` 去重（2026-08-18 验收对齐：去重需跨事件状态，归此层——传输层不认识 assistant 结构）。
3. **里程碑引擎**：吃调用方注入的声明式匹配表（正则 × tool_use），吐 milestone 事件。

### 7.3 包边界：引擎进包，知识留外

| 进 cc-stream | 留在 server |
|---|---|
| spawn 助手（env 剔除、allowedTools、参数拼装） | 任务表 / 幂等锁 / SSE 接线 |
| 传输层 + 事件归一层 | **里程碑表内容**（各任务类型的匹配规则 = 领域知识） |
| 里程碑引擎（通用） | **终局裁决**（复读 meta.status——包绝不知道 meta.yaml 的存在） |
| 原始流落盘钩子 | 成本/耗时展示策略 |

包内没有一行代码认识「发布 / meta.yaml / media」，是通用「无头 CC 观察器」，可跨项目复用。

### 7.4 信任分级（设计纪律）

1. 模型叙述（`text`）= **只展示**，永不驱动状态；
2. 工具事件（`tool_use`/`result`）= 驱动步骤时间线；
3. 文件状态（meta.status 经 chokidar）= **唯一裁决**。

附加：`api_retry`/`rate_limit_event` 连续出现 → 面板显示「任务卡顿中」；`total_cost_usd` 做成任务成本标签（审批一次发布花多少钱，可见）。

### 7.5 测试策略：真实 fixture

2026-08-18 探测已捕获一份完整真实输出作为首个 fixture。**每次 Claude Code 升版跑一次探测、存一份新 fixture**——stream-json 是半文档化协议，协议漂移让测试先红，这是本包唯一的真实风险及其对策。

## 8. CLI 写入 × chokidar 监听：四坑与对策

1. **一事务多文件多触发**：trailing debounce 500ms 聚合成一次重建（事务落盘毫秒级，窗口足够）。
2. **跨文件中间态假警报**（meta 已翻、backlog 未翻的瞬间）：debounce 覆盖为主，**警报去抖**（同一警报连续两次快照都在才推）兜底。
3. **dashboard 自触发环——实际无环**：CLI 写后重生成 dashboard 只是同一 debounce 批次多一个事件；server 零写，环路闭不上。
4. **脏事件源是 git 与编辑器**：chokidar ignore `.git`、只 watch 白名单目录+扩展名；writer.ts 用 temp-then-rename 原子写防半写 YAML（parser 降级容错是最后防线不是第一道）。

## 9. CC 进程调度清单（全系统 7 场景）

两种形态：**甲类** = 我们 spawn 的 `claude -p`（stdout 在手，白盒，cc-stream 解析）；**乙类** = CC 客户端定时会话（黑盒，靠文件轨迹观测）。

| # | 场景 | 类 | 调起方 | 时长 | 解析方式 |
|---|---|---|---|---|---|
| 1 | 生产线日跑 daily-run | 乙 | CC 客户端定时任务 | 1~3h | 文件轨迹（见下） |
| 2 | 治理线日跑 dispatcher | 乙 | CC 客户端定时任务 | 10min~1h | `harness/logs/index.jsonl`（天然结构化台账）+ 报告落盘事件 |
| 3 | 飞书·确认发布真发 | 甲 | feishu server | 3~15min | 现状：取 stdout 尾 12 行；目标：收口 job runner（§9.1） |
| 4 | 飞书·打回重做 | 甲 | feishu server | 10~30min | 现状：**stdout=DEVNULL 全丢**（改造收益最大）；目标：同上 |
| 5 | 看板·确认发布 | 甲 | console job runner | 同 3 | stream-json：dry-run→上传→publish-done→通知 |
| 6 | 看板·打回重做 | 甲 | console job runner | 同 4 | stream-json：改稿→重配音→重录屏→回 review→重推卡 |
| 7 | 看板·散文提议入库 | 甲 | console job runner | 1~5min | stream-json；重点在终局审计：任务卡嵌 brain diff 供人回看 |

**场景 1 的文件轨迹进度条**（零改造成本，观测点全是现成文件事件）：backlog 翻 picked / 目录出现 → 已取题；`2-script.md` 出现 → 口播稿完成；`audio-segments/` 出现 → 配音中；`assets/*.mp4` 出现 → 成片；meta 翻 review → 出审等人。配套 alerts 新规则：「工作日 X 点后仍无当日目录且无飞书阻塞上报 = 疑似空跑」（6 天空跑事故的机制化防复发）。

### 9.1 收口决策

1. **甲类 5 场景统一进 console job runner + 同一 cc-stream 解析器**：飞书 server 的场景 3/4 改为回调时 `POST localhost:5170/api/actions/*`，自己不再 spawn。全系统一份 CC 进程台账、一份解析器、一份里程碑表配置；飞书卡片与看板面板显示同一任务的同一进度；feishu server 退化为纯卡片 UI。
2. **乙类 2 场景保持黑盒**：迁移成 console spawn 技术可行，但会让 console 从「可随便崩」变成「不能崩」，违背调度员定位；文件轨迹已覆盖晨检需求。留为开放问题，跑稳后再议。
3. 解析器服务对象收敛为：甲类 = stream-json 事件流，乙类 = chokidar 文件事件流，**两者归一成 SSE 任务/进度事件，前端不感知来源差异**。

## 10. API 契约（读接口沿 ADR，写接口为本文新增）

读：`GET /api/{overview,contents,content/:slug,backlog,harness,metrics}` + `/api/file` `/api/asset`（safeResolve 白名单）+ `/api/health`（带 revision）+ SSE `/api/events`。
写：§5 动作层 + `POST /api/actions/{publish,rework,apply-proposal}`（job runner，202+任务 id）+ `GET /api/jobs/:id` + `GET /api/jobs`（活动+近期任务列表；2026-08-18 增补：页面刷新后 JobPanel 需能重新发现进行中任务，纯读不碰写纪律）。
metrics 数据源：`harness/logs/metrics.jsonl`（由 CLI v0.2 的 `media metrics record` 产生，见 CLI 方案增补；server 只读，零写无损）。

## 11. 运行形态

- 端口 5170；feishu-bot 是飞书 ws 长连接客户端不占本地端口，无冲突。**共存即协同**：飞书侧写文件自动被 chokidar 捕获，人审结果实时上看板，两进程零直接耦合，文件系统即总线。
- 启停：先配与 feishu-bot 同款 `start.sh`（start/stop/status，喂 G1 健康灯）；跑稳后升 launchd（RunAtLoad + KeepAlive）常驻——晨检场景要求「打开浏览器就有」。日志落 `tools/console/logs/`。
