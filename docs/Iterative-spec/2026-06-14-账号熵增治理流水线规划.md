## 〇、宪法（这条线只做一件事）

> **本流水线只做一件事：逆账号存量资产的熵增。**
> 不造新内容（那是 `pipeline/`），不追增长。
> 判据：**没人催、但放着会烂的**，才进这条线。

这一句是硬边界。往这条线里加任务时先过这个判据，防止它慢慢长成第二条生产线。

**为什么需要它**：账号每运营一天，"系统记录的状态"和"世界的真实状态"就多偏离一点，
而**没有任何一个生产环节负责把偏差拉回来**——生产线只管造新的。所以必须有一条专门、
常驻、定时巡检的线去逆这个熵。Harness 的精髓就一句：**用机器的「全年无休 + 小步高频」，
对抗人的「有压力时永远不会把维护排进 sprint」。**

### 人机闸口（全系统只在这三处停）

```
 ③审核        生产线:客观项已被自愈门禁滤过,人只审主观(语气/钩子真不真抓人)
 ④发布授权    dry-run 给人看 → 授权才真发(不可逆)
 治理·落地    AI 只产"执行记录报告+变更提议",改大脑/改线上一律人审后应用
```

> **一句话**：生产线把大脑变成内容，治理线把内容的真实表现变回大脑——`brain/` 是唯一交汇点。
> 闭环 ③ 是价值核心(选题越来越准)，④ 让系统能无人长跑(连配置都自调)，② 让 AI 多做人少管，① 是看得见的生产流。

## 一、它和生产线是两条正交的线

| | 生产线 `pipeline/` | 熵增治理线 `account-harness` |
|---|---|---|
| 对象 | 还不存在的新内容 | 已经存在的账号资产 |
| 方向 | 前向、一次性、有时效 | 后向、持续、可延迟 |
| 触发 | 选题驱动（有题就跑） | 时间驱动（定时巡检） |
| 调度 | 固定线性五阶段 | 加权随机选任务+目标 |
| 失败成本 | 高（错过热点 / 发了烂内容） | 低（没清就下次再清） |
| 类比 | 写新 feature | 还技术债 |

**区分口诀**：这件事**有人催**吗？有人催 → 生产线；**没人催但放着会烂** → 治理线。

> ⚠️ 关键边界：**不要把生产线改造成加权随机 dispatcher**。内容生产有时效、有编排顺序、
> 不可随机延迟，加权随机只适用于「一堆同质、无序、可延迟的维护债」。

## 二、当前生产线 vs Harness 八大机制（对照体检）

| Harness 机制 | 现状 | 结论 |
|---|---|---|
| 人机边界铁律 | 自动到出审，人审发布（红线） | ✅ 已有，清晰 |
| audit 自迭代 | 复盘产大脑变更提议→人审写 `brain/benchmarks.md` | 🟡 有雏形，缺「读运行日志调流水线配置」的元层 |
| repo-lens 就绪分数选目标 | 选题阶段双赛道 6 维打分选 Top-N | ✅ 同构（选题打分 ≈ repo-lens） |
| 准入条件（可溯源/范围可控） | 内容红线（不编造/可溯源） | ✅ 已有 |
| **质量门禁 + 自愈循环** | 阶段2 质量自检清单 + 录屏验音画，**失败靠人** | ❌ **最大缺口** |
| 分层解耦（调度/执行分离） | pipeline=SOP，skill=执行 | 🟡 像，但无中央调度器（生产线也不需要） |
| tasks.md 加权随机注册 | 无 | ➖ 生产线不该有，治理线才需要 |
| 失败=Draft 不沉默 | 无 | ❌ 缺 |

**两个真缺口**：① 生产线缺自愈循环；② 整个账号缺一条治理存量债的 harness。

## 三、补生产线：质量自检 → 自愈门禁（缺口①）

现在阶段2 的质量自检是「人看的 checklist」，录屏验音画失败也是人处置。照搬 Harness 的
validator + 自愈：

```
创作产出 → 自动门禁 → 失败把错误当 context 喂回 AI 重做（≤3 轮）→ 仍不过则产出「草稿+诊断报告」待人审
```

- **可机器验证的项走自愈**：录屏音画不同步、字幕错位、违禁词命中、技术结论无 source 标注、
  前 3 秒无钩子 —— 自动判定，失败自动重做。
- **不可机器验证的项直接交人审**：语气是否到位、钩子是否真抓人。
- 自愈轮次设 **3**（经验：3 轮修不好往往是任务定义有问题，该报告不该硬刷）。

> 推论（文章 6.1）：**自动化验证的覆盖范围，直接决定人需要介入的空间。**
> 想让 AI 多做、人少管，就把更多自检项做成可机器判定的门禁（例：建违禁词表、
> 给「结论必须带 source 字段」做 schema 校验）。

### 3.1 自愈门禁落地清单（按杠杆排序，逐项可独立接）

每项做成一个**机器可判定的 checker**，挂在创作产出后、出审前；客观项失败自动喂回重做（≤3 轮），半客观项判一轮兜底后并入人审。

| # | 门禁项 | 怎么机器判定 | 落地方式 | 客观度 | 难度/杠杆 |
|---|---|---|---|---|---|
| 1 | **违禁词命中** | 扫 `2-script.md`+字幕 比对违禁词表 | 建 `brain/banned-words.txt`，checker 正则扫，命中即 fail | 全客观 | 易·高杠杆 |
| 2 | **技术结论无 source** | schema 校验：结论项必须带 `source` 字段 | `1-brief`/`2-script` 结论加 `source:`，checker 校验非空+可达 | 全客观 | 易·高杠杆（直接落红线"可溯源"） |
| 3 | **音画不同步** | 成片总时长 ≈ Σ各段音频时长 ± 阈值 | `auto-record.mjs` 已有 per-step 对齐基础，补一句总时长断言 | 全客观 | 易（已有基础） |
| 4 | **字幕错位/缺失** | 字幕条数 = narration 段数；时间码连续覆盖 | 若出字幕，checker 比对 `audio-segments.json` ↔ 字幕 | 全客观 | 中 |
| 5 | **前 3 秒无钩子** | 首段 narration 是否痛点/结论/反常识前置 | 规则+LLM 判定，失败自愈一轮再交人 | 半客观 | 中（判一轮兜底） |

**先接 1+2**：违禁词表 + source schema——最易、且直接把内容红线（不编造/可溯源/合规）从"人肉 checklist"变成"机器门禁"，③人审 的负担立刻下降。3 顺手（auto-record 已有时长数据）。4、5 后补。

> 边界：门禁只做**客观项**。语气是否到位、钩子是否"真"抓人——机器判不了，留 ③人审。门禁覆盖越广，人审越聚焦在真正主观的地方。

## 四、主菜：account-harness 治理线（缺口②）

架构 1:1 复刻文章五层：**触发层（定时）→ 调度层（dispatcher）→ 执行层（各治理 skill）
→ 验证层（validator+自愈）→ 审计层（audit 回写配置）**。调度与执行分离，加新任务只写执行 skill。

> **落地修正（2026-06-14）**：调度层 `harness-dispatcher` 已建，采**触发感知**而非纯加权随机——
> 复盘是事件触发(发布后窗口)、benchmark 是周期(月)，都不是同质随机债；加权池(`weighted-pool`)
> 作为一种 trigger 类型**预留**给未来 per-item 任务(link-rot/stale-fact/cover)。见 `automation/harness/tasks.md`。
> 验证层不单独建 skill：治理产出是"报告+提议"不自动改，校验(格式对、没碰 brain)塞进 dispatcher 即可。

### 4.2 验证层：客观的走自愈，主观的只出报告

代码的验证天然客观（tsc/lint/build），内容质量多为主观——所以治理线必须**显式分流**：

- **数据/事实客观的**（复盘拉数+归因）：可自动产出报告/草稿。
- **需人审的**（benchmark-refresher 改对标、未来 stale-fact/cover 改线上资产）：**只产出诊断报告**，不擅自改。
- 未来 TODO 任务接入时各自归类（link/sop/retro-debt 全客观可自动改文件→待审草稿）。

> ✅ **已定（2026-06-14）**：取方案 A——**复盘不自动改大脑**，与全线统一。
> 复盘只产**执行记录报告 + 大脑变更提议**，人审通过后才应用。早先"全自动回写 benchmarks"作废。
> 这条成为全线铁律：**AI 出执行记录报告 → 人审 → 应用**（改 `brain/`/线上资产不可逆，不自动化）。

### 4.3 人机边界

harness 只做到「产出草稿 + 诊断报告」为止。**改动已发布内容 / 账号大脑是不可逆的，必须人审**
—— 与现有发布铁律完全一致。

### 4.4 audit 元层

`account-audit` 读治理日志、按成功率调 `tasks.md` 权重：
- 「封面巡检连续没发现问题」→ 降权；「链接巡检每次都中」→ 升权；「stale-fact 跳过率>50%」→ 降权。
- 这是 benchmarks 回写的升级版：从「回写打法」扩展到「回写流水线自己的配置」。运行越久越准。

## 五、顺手采纳的工程教训

1. **`dashboard.md` 是共享状态文件，会变成冲突源**（文章 6.5）。现在它被每条内容更新，
   一旦并发跑多条/多任务必冲突。改法：**每条内容的 `meta.yaml` 是唯一真相源；dashboard 改为
   由脚本从所有 meta.yaml + 一个 append-only `index.jsonl` 重新生成**，谁都不直接手改 dashboard。

2. **风险分层设初始权重**（文章 6.6），别一刀切：纯客观低风险（link/sop/retro）给 10，
   需人审（stale-fact/cover）给 3–4，攒够成功案例再提。

3. **运行日志用 append-only `index.jsonl`**，不写进会被多 MR 共改的状态文件，避免 rebase 冲突；
   audit 先读 index 做统计，需要细节再读具体日志。
