# 附三：9.2 挖出的第二个真实系统缺口（已核实）

9.2 断言 `lock.ts` 的 EPERM 判活分支从提交起就没被单测覆盖过。主回话核实了，属实：

- `tools/console/packages/core/` 下没有任何 lock 测试文件（只有 `src/lock.ts` 和它的 dist 产物）
- 全部 `*.test.ts` 里零处提到 `EPERM`
- `src/lock.ts:24` 是 `process.kill(pid, 0)`，`:27` 是 `return (err as NodeJS.ErrnoException).code === 'EPERM'`

为什么这条最危险：这个分支写错（比如 catch 里直接 `return false`）会偷走一把还活着的锁，打开两个写入者同时改同一批文件的窗口。而单用户机器永远走不到 EPERM 分支，本地怎么测都是绿的。**测试全绿和这条分支正确与否，是两件无关的事。**

两条防法（9.2 正文里给了）：

1. mock `process.kill` 抛 EPERM 写单测，把这条分支钉住
2. 把这类 catch 分支登记成 diff 里的强制人工复核点

我倾向两条都做，第一条尤其便宜。但这是改生产系统的测试，不在本次课程任务范围内，等你定。

## 两个缺口放在一起看

附二（`publish-done` 崩溃后 backlog 无命令可修）和附三（EPERM 分支无单测）都是执行中的 agent 撞到边界时报上来的，不是任何一轮规划找出来的。两个都不影响课程交付，都影响生产系统。

# 附四：7.3 扩写时读代码发现的第三处缺口

`tools/feishu-bot/server.py` 里两处启动 `claude -p` 的地方，对子进程输出的处理不一样：

- `_async_publish` 的旧路径用 `capture_output=True`，认证失败的报错会出现在失败卡片的尾部，人看得见
- `_run_rework` 把 `stdout` 和 `stderr` 都送进 `subprocess.DEVNULL`

后果：**重做路径上的认证失败是真的被吞掉的**，只能靠 SKILL.md 里那条自检命令事后查。而认证失败的典型成因（子进程继承了 `ANTHROPIC_API_KEY`，OAuth token 被当 API key 用）恰恰是静默的，不崩溃、不报错。

这条 SKILL.md 里没写，是扩写 agent 读代码比对两处调用点时发现的。

要定的事：重做路径要不要也 `capture_output`，或者至少把 stderr 留下。我倾向留下——吞掉错误省不了多少东西，但排查时的代价很大。同样是改生产系统，不在课程任务范围内，等你定。

## 三处缺口的共同点

附二（backlog 崩溃后无命令可修）、附三（EPERM 分支无单测）、附四（重做路径吞错误），全都是执行中的 agent 撞到具体代码时发现的，没有一处来自规划或通读。
