# 【Server / CLI】AI 自媒体流水线后端技术方案

## 1. 方案结论

本项目的“后端”不是传统数据库服务，而是本地 Hono Server、领域 Core、`media` CLI 和无头 Agent JobRunner 的组合。

Server 负责读投影、鉴权、动作白名单、任务调度和 SSE；Core/CLI 负责状态与文件事务；无头 Claude Code 负责长时判断性任务；最终成功由文件状态、治理账本或 Git Diff 裁决。

## 2. 技术栈与包边界

| 包 | 路径 | 技术 | 职责 |
|---|---|---|---|
| Core | `tools/console/packages/core` | TypeScript + `yaml` | 领域类型、解析、快照、状态机、警报、Doctor、事务写 |
| CLI | `tools/console/packages/cli` | Commander | `media` 命令、JSON 信封、业务写入入口 |
| Server | `tools/console/packages/server` | Hono + Node Server + chokidar | API、Store、Watcher、SSE、JobRunner、静态 UI |
| CC Stream | `tools/console/packages/cc-stream` | Node child_process + stream-json | 启动无头 CC、解析和归一事件 |
| UI | `tools/console/packages/ui` | React | 只通过 API 使用后端能力 |

包边界硬约束：

- Server 可以 import `@console/core` 的只读能力和领域类型。
- Server 不得 import `@console/core/writer`。
- CLI 是唯一可以 import Writer 的包。
- UI 对 Core 和 Server API 类型只做 type-only import。
- `cc-stream` 不认识发布、创作、治理等领域概念，里程碑知识留在 Server。

## 3. Server 启动链

入口：`tools/console/packages/server/src/index.ts`。

```text
loadConfig
  → loadOrCreateToken
  → new Store(repoRoot)
  → store.init()
  → startWatcher()
  → store.startTick()
  → sse.startPing()
  → new JobRunner()
  → Hono 路由装配
  → 静态托管 ui/dist
  → 监听 127.0.0.1:5170
```

配置来自 `tools/console/packages/server/src/config.ts`：

```ts
interface Config {
  consoleRoot: string
  repoRoot: string
  port: number
  mediaBin: string
  tokenPath: string
}
```

环境变量：

- `PIPELINE_REPO_ROOT`：主仓根目录。
- `CONSOLE_PORT`：默认 `5170`。
- `MEDIA_BIN`：可选的 `media` 可执行文件。

`media` 裸命令启动失败时，Server 会用 `process.execPath + packages/cli/dist/index.js` 兜底，不依赖全局 PATH 和可执行位。

## 4. Store、Snapshot 与 Watcher

### 4.1 Snapshot

`tools/console/packages/core/src/snapshot.ts` 是主仓读模型的聚合入口：

```ts
interface Snapshot {
  generatedAt: string
  root: string
  contents: ContentEntry[]
  backlog: { nextUp: string | null; topics: BacklogTopic[] }
  harness: HarnessRun[]
  metrics: MetricsRecord[]
  parseErrors: { path: string; error: string }[]
}
```

单个 `meta.yaml` 解析失败时，Snapshot 将错误降级放入 `parseErrors`，不会让整个服务启动失败。

### 4.2 Store

`tools/console/packages/server/src/store.ts` 维护：

- 最新 Snapshot。
- `harness/tasks.md` 派生的任务注册表。
- 页面投影需要的每日轨迹和治理摘要。
- 单调递增 revision。
- 最近构建时间、构建耗时和 tick 状态。

请求路由主要读取 Store 内存，不在每次 GET 时重新扫描全仓。

### 4.3 Watcher

`tools/console/packages/server/src/watcher.ts` 使用 chokidar 监听核心业务文件。文件变化后 debounce rebuild：

1. 重新构建 Snapshot 和页面派生数据。
2. revision 自增。
3. SSE 广播 `refresh`。

同时保留周期 tick，用于时间相关警报即使没有文件变化也能刷新。

## 5. API 总体约定

### 5.1 鉴权

全部 `/api/*` 经过 `createAuthMiddleware`：

```http
Authorization: Bearer <token>
```

或：

```text
?token=<token>
```

query token 只用于 EventSource 和浏览器媒体标签等不能设置 header 的场景。token 首次生成后保存为 `tools/console/.runtime/token`，权限 `0600`。

### 5.2 读接口信封

```ts
interface ApiEnvelope<T> {
  revision: number
  now: string
  data: T
}
```

### 5.3 错误信封

```ts
interface ApiErrorBody {
  error: {
    code:
      | 'AUTH_BAD_TOKEN'
      | 'BAD_PARAM'
      | 'PATH_FORBIDDEN'
      | 'NOT_FOUND'
      | 'MEDIA_REJECTED'
      | 'JOB_DUPLICATE'
      | 'PRECONDITION_FAILED'
      | 'REWORK_LIMIT'
      | 'FILE_TOO_LARGE'
      | 'MEDIA_UNAVAILABLE'
      | 'INTERNAL'
    message: string
    detail?: string
  }
}
```

### 6.1 文件读取安全

`routes/files.ts` 与 `util/safeResolve.ts` 必须保证：

- 输入是仓根相对路径。
- 解析后仍在允许根目录内，拒绝 `../` 和符号链接逃逸。
- 文本文件有大小上限和截断标记。
- 媒体通过已校验路径和鉴权返回。
- 不提供任意本地文件浏览能力。

## 7. 快写动作

快写动作由 `routes/actions.ts` 接收，在 `actions/whitelist.ts` 中映射为固定 `media` 参数，再由 `execMedia.ts` 用 `execFile` 参数数组执行。

| Method | Path | 请求 | CLI 映射 |
|---|---|---|---|
| POST | `/api/actions/review` | `{slug, decision, reason?, dryRun?}` | `media flip <slug> <status>` |
| POST | `/api/actions/backlog-apply` | `{id, action, proposal, into?, dryRun?}` | `media backlog apply ...` |
| POST | `/api/actions/promote` | `{id?|auto, slug, date?, dryRun?}` | `media promote ... --slug ...` |
| POST | `/api/actions/next-up` | `{id?|clear, dryRun?}` | `media next-up set|clear` |

### 7.1 参数白名单

- slug：`^[a-z0-9][a-z0-9-]{1,64}$`。
- backlog id：`YYYY-MM-DD-NNN`。
- proposal/report：必须在 `harness/logs/` 下。
- review decision：仅 `approved|rework|rejected`。
- merge 必须带合法 `into`。
- promote 的 slug 必填，由人或 UI 显式给出。

Server 不接受自由形式命令字符串，也不通过 shell 执行，避免命令注入和绕过业务状态机。

### 7.2 执行结果映射

`execMedia.ts` 的分类依据是 CLI JSON 错误信封，而不是只看不稳定的进程退出码：

- 成功且 JSON `ok:true`：HTTP 200。
- 业务规则拒绝、锁冲突：HTTP 409 `MEDIA_REJECTED`。
- `E_PARSE` 真相源损坏：HTTP 500 并打印告警。
- 参数拼装错误或异常输出：HTTP 500 `INTERNAL`。
- spawn 失败或超时：HTTP 502 `MEDIA_UNAVAILABLE`。

正式写入后，响应附带 Check 摘要；dry-run 不执行写后 Check。

## 8. 慢作业 API

| Method | Path | 请求 | 前置条件 |
|---|---|---|---|
| POST | `/api/actions/create` | `{slug}` | 内容存在且 `status=ideated` |
| POST | `/api/actions/rework` | `{slug, reason}` | `review|drafting|rejected`，累计重做 <2 |
| POST | `/api/actions/publish` | `{slug}` | `status=approved` |
| POST | `/api/actions/harness-run` | `{task}` | 注册、启用且配置了 Skill |
| POST | `/api/actions/apply-proposal` | `{report, note?}` | 报告在治理账本且 `applied!=true` |

受理成功返回 HTTP 202：

```ts
interface JobSubmittedResponse {
  jobId: string
  statusUrl: string
  sseEvent: string
}
```

取消接口：

| Method | Path | 语义 |
|---|---|---|
| POST | `/api/jobs/:id/cancel` | queued 立即移除；running/verifying 发终止信号 |
| POST | `/api/jobs/cancel-all` | 清空全部 queued，并取消 active |

## 9. JobRunner

入口：`tools/console/packages/server/src/jobs/runner.ts`。

### 9.1 Job 模型

```ts
type JobType =
  | 'publish'
  | 'rework'
  | 'apply-proposal'
  | 'harness-run'
  | 'create'

type JobState =
  | 'queued'
  | 'running'
  | 'verifying'
  | 'succeeded'
  | 'failed'
  | 'cancelled'
```

Job 还包含 milestones、narration、stalling、耗时/成本、verdict、error、logPath 和可选 slug/task/report。

### 9.2 单并发队列

JobRunner 当前只允许一个 active Job：

```text
submit → precheck → lockKey 查重 → queued → runNext
→ running → verifying → terminal → 释放锁 → 下一个
```

单并发是当前资源约束下的安全选择：浏览器、抖音账号、媒体文件、仓库写锁和外部凭证都可能冲突。

### 9.3 幂等锁

| Job | lockKey |
|---|---|
| publish | `<slug>` |
| rework | `<slug>` |
| create | `create:<slug>` |
| harness-run | `harness:<task>` |
| apply-proposal | `proposal:<report>` |

同一锁域已有任务时返回 `JOB_DUPLICATE`。

### 9.4 超时

| Job | 超时 |
|---|---:|
| create | 60 分钟 |
| rework | 45 分钟 |
| harness-run | 30 分钟 |
| publish | 20 分钟 |
| apply-proposal | 10 分钟 |

`cc-stream` 超时时先 SIGTERM，10 秒后仍未退出再 SIGKILL。

### 9.5 允许工具

无头 CC 使用固定列表：

```ts
['Bash', 'Read', 'Write', 'Edit', 'Skill']
```

权限来源写入专用 Prompt。Prompt 明确人已在哪个界面授权、允许做到哪一步、不得越过哪些红线。

## 10. CC Stream

`tools/console/packages/cc-stream/src/` 分三层：

1. `spawn.ts`：启动 `claude -p`，设置 `--output-format stream-json --verbose --allowedTools`，管理环境、超时和日志。
2. `transport.ts`：按行读取 JSONL，过滤 hook 噪音，坏行跳过。
3. `normalize.ts`：归一成 `started/tool/toolDone/say/thinking/stalling/done`。

归一事件的信任分级：

- `say`、`thinking`：只展示。
- `tool`：可驱动里程碑。
- `toolDone`：展示结果摘要和中断信息。
- `stalling`：连续两次才标 Job stalling。
- `done`：记录成本、轮次和 API 耗时，但不直接决定业务成功。

原始流逐行写到 `tools/console/logs/jobs/<id>.jsonl`。终态写到 `<id>.result.json`。

## 11. 里程碑与实时推送

Server 在 `jobs/milestones.ts` 定义领域规则，例如：

- create：写稿、配音、录屏、封面、出审。
- publish：dry-run、上传、publish-done、通知。
- rework：改稿、重配音、重录屏、回审。
- harness-run：读任务卡、执行 Skill、产报告、记账。
- apply-proposal：读报告、改 brain、产 Diff。

每条归一事件会：

1. 追加广播 `job-log:<id>`。
2. 更新 Job narration/milestones/stalling。
3. 广播 `job:<id>` 完整快照。

里程碑正则可能随 Skill 命令变化而漂移，因此属于展示层规则，不能作为终局成功条件。

## 12. 终局裁决

`jobs/verdict.ts` 不信任子进程的完成说明，按 Job 类型复读事实：

| Job | 成功判据 |
|---|---|
| create | `meta.status === review` |
| rework | `meta.status === review` |
| publish | 子进程无错误，且 `meta.status` 为 `published|scheduled` |
| harness-run | `harness/logs/index.jsonl` 在 Job 开始后新增该 task 记录 |
| apply-proposal | `git status/diff -- brain/` 存在变更 |

Job 状态在 executor 结束后先进入 `verifying`，裁决完成才进入 `succeeded` 或 `failed`。

## 14. 飞书 Bot 后端

`tools/feishu-bot/` 是独立 Python 服务：

- `notify.py`：发送审核卡、文本通知和阻塞通知。
- `server.py`：使用飞书官方 SDK 长连接接收按钮事件。
- `meta.py`：解析内容元数据与 `4-publish.md`。
- `publish.py`：拼接 dry-run/发布命令和发布物料。
- `prompts.py`：审核通过、重做和发布的 Agent Prompt。

审核与发布的职责必须分开：审核通过只进入发布准备，确认发布卡才授予真实发布权限。

## 15. 边界与异常处理

- Snapshot 单文件解析失败：页面降级显示，不拖垮全仓。
- CLI 业务校验失败：零写入，HTTP 409。
- CLI 锁冲突：不排队，明确返回占用者。
- Job 重复：按 lockKey 拒绝。
- Job 取消：running 状态先标 `cancelRequested`，进程实际结束后才变 cancelled。
- Server 重启：内存队列丢失，但可以从 `<id>.result.json` 和 `<id>.jsonl` 恢复历史可见性。
- 外部工具失败：不得伪造 published、review 或 applied 状态。
- cookie 失效：不自动登录，返回人工处理提示。
- 治理任务无 Skill：不启动无头 CC，纯 CLI 任务由现有机制执行。

| `tools/feishu-bot/*` | 配置化、模拟卡片和公开说明 |

## 17. 后端验收

- `npm run build` 通过。
- Server 只监听 loopback，token 权限正确。
- 所有 API 都经过鉴权，静态 UI 除外。
- Server 无 Writer import，快写只有白名单参数。
- dry-run 零业务写入，正式动作返回 writes 和 Check 摘要。
- 五类 Job 的 precheck、幂等锁、超时、取消和 verdict 有测试。
- 原始 JSONL 与 result.json 可回放。
- 单个坏文件不影响其它页面。
- Server 重启后终态 Job 仍可查询。
- 真实发布失败时文件状态保持未发布。
