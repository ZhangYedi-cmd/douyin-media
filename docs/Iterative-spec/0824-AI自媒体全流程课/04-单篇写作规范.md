# 单篇写作规范

> 日期：2026-08-24 ｜ 上游：`00-ADR.md`、`03-已拍板补充.md`
> 适用：27 篇教程的每一篇。本文附进每个写作 agent 的提示词。
> 本文定的是**性质**，不是形式。章节数量、层级与标题由每篇内容自己长出来。

## 一、为什么不给模板

上一版课程死于模板。单章塞六个待填 markdown 加九条 checkbox，学习者的亲手实验变成填表，模板用一级标题还污染了章节层级。

分级模板同样不行。哪怕分成概念篇与工程篇两套，27 篇仍然只有两种长相，读者翻到第五篇就知道第六篇长什么样，而内容会被反向裁剪成模板的形状。

所以本文不给章节清单。给的是四条必须满足的性质、一套生成方法、以及判断合格的判据。**写完之后章节长什么样，取决于这一篇要立什么。**

## 二、四条性质，一条都不能违反

来自金字塔原理，逐条给出可操作的判据。

### 2.1 结论先行

每篇开篇一句话给出**本篇结论**，说清这篇要立什么判断。

每一节的开头同样一句话给出**本节小结论**。读者只读所有标题与每节第一句，就应该能复述这篇的完整论证。

判据：把全文的节标题与每节首句抽出来单独成段，读起来仍然是一段通顺、完整、能自证的论述。做不到就是没做到结论先行。

### 2.2 以上统下

每一节都必须支撑它上一级的结论。支撑不了的，删掉或移走，不许因为「材料有趣」留在原地。

判据：对每一节问一句，去掉它之后上一级结论还站得住吗。站得住说明这节没在支撑，是装饰。

### 2.3 归类分组

同一级的各节之间不重叠，合起来足以撑住上一级结论。

判据两条。其一，任意两节的内容能不能互换标题，能换说明分组没分开。其二，把所有同级节列出来问，读者同意了这几条，会不会自然得出上一级结论。答案是否，说明分组有缺口，缺的那一块就是漏掉的节。

### 2.4 逻辑递进

同一级各节之间必须有序，而不是并列罗列。序可以是时间序、因果序、重要性序或认知负荷序，但必须有一种，且要能说出是哪一种。

判据：任意两个相邻节调换顺序，读者的理解成本会不会上升。不会上升说明这两节之间没有序，那它们要么该合并，要么其中一节的位置错了。

## 三、由浅至深怎么落地

「由浅至深」不是感觉，是三条可测的约束。

### 3.1 前置依赖单调

后一节不许要求读者掌握前面没有给过的东西。

写的时候维护一份**本篇已立概念表**，每写完一节就把这节新立的概念追加进去。下一节用到的每个概念，要么在这张表里，要么在本篇的可消费概念清单里（前序篇目已立）。两处都没有就是断层。

### 3.2 认知负荷递增

三个可数的指标，逐节应当整体上升而不是跳变：

- 新术语密度，即这一节引入的新概念数
- 前置依赖数，即这一节要求读者同时记住几件事
- 抽象层级，即这一节离读者的直接经验有多远

跳变的地方就是读者掉队的地方。发现某一节的三项指标比前一节高出一截，要么在它前面补一个过渡节，要么把它拆成两节。

### 3.3 每节都要有出口

每一节结束时，读者手里应当多一样具体的东西：一个判断、一个能跑的产物、一次能复现的验证。

判据：给每一节在心里写一句「读完这节你手里多了什么」。写不出来的节，说明它只是在铺垫，铺垫不能单独成节，并进相邻节。

**这句话是自检用的，不许写进正文。** 上一版每篇结尾都硬挂一句「这一章你手里多了什么」，那是模板尾巴，见 §8.5。

## 四、章节怎么动态生成

五步。先有结论，再有章节，顺序不能反。

### 4.1 定结论

一句话写出本篇结论。写不出来说明这篇的边界没想清楚，**不许动笔**，回去找主回话谈边界。

结论必须是判断句，不是话题。「讲一下状态机」不是结论，「状态不能藏在聊天记录、文件名或 Agent 的记忆里」才是。

### 4.2 拆支撑点

问一句：**要让读者接受这个结论，他必须先同意哪几件事。**

答案就是本篇的一级节。答案有三条就是三节，有五条就是五节。**节数由答案决定，不由模板决定。**

拆完用 §2.3 的两条判据自检，有重叠就合并，有缺口就补。

### 4.3 递归下沉

对每个一级节问同样的问题，得到二级节。一直问到答案能直接落到具体材料上（某个文件的某一段、某条命令的输出、某个真实事故）为止。

多数篇目下沉到二级就够。下沉到三级还落不到材料，说明这一支太抽象，考虑砍掉。

### 4.4 排序

按 §2.4 给同级节定序，并说出定的是哪一种序。同时用 §3.1 与 §3.2 检查前置依赖与认知负荷，不满足就调序或补过渡。

### 4.5 起标题

**节标题必须是这一节的小结论，不是这一节的话题名。**

| 差 | 好 |
|---|---|
| 二、设计选择 | 二、三个方案里只有一个能同时守住并发与审计 |
| 三、实现 | 三、先定命令契约，再让 Agent 写实现 |
| 四、验收 | 四、Agent 说完成不算数，回读文件状态才算 |

判据见 §2.1，把标题抽出来单独读，应当自成一段论述。含「设计选择」「实现」「验收」「总结」「背景」这类无信息量的词，一律重起。

## 五、素材类型自查清单

ADR §9 的八段在此处的唯一用途：写完之后对照检查有没有漏掉某类内容。**不规定顺序，不要求全有，不作为节标题。**

| 类型 | 自查问题 |
|---|---|
| 事故或问题 | 读者能感到痛吗，还是只在听道理 |
| 工程原理 | 有没有摆出可选方案与各自代价，还是只给了一个答案 |
| 仓库证据 | 有没有真实代码与路径撑着，还是全靠说；**证据只能放在问题和设计取舍讲清楚之后当佐证，不许把参照仓的选择本身当论证起点**（反例见 §5.2） |
| AI 实现 | 有没有给出可直接粘贴的任务契约 |
| 证据验收 | 有没有说清看哪个文件、跑什么命令、Agent 常踩哪个坑 |
| 故障注入 | 有没有主动造反例验证边界 |
| 跨域迁移 | 这个设计在别的业务里叫什么 |
| 架构决策卡 | 选择、代价、当前约束、演进条件记下来了吗 |

概念篇天然长不出故障注入与决策卡，**缺就缺，不许硬凑**。工程篇缺了证据验收则是硬伤，必须补。

### 5.1 验收信息不许单独成节

上一版的每一篇都顶着同一个标题「怎么验收它交回来的东西」，把验收堆在文章最后。读者翻到第三篇就知道第四篇最后一节长什么样，这时候里面写什么都救不回来。

**验收信息贴着它对应的设计点写。** 讲某个设计的时候顺手带出这里 AI 会怎么错、错了从哪看出来。做过这行的人本来就是这么讲的。

例外只有一个：本篇结论本身就是关于验收的（比如 7.1 讲 Check 与 Doctor），那时验收是主体不是附录。

同理，其余七类素材也都不许固定占据某一节的位置。它们是内容，不是槽位。

### 5.2 仓库证据不许当论证起点

工程篇最容易犯的错，是一段话开头就是"约束是靠 XX 焊死的"，接着甩出一串文件路径、字段名、函数名，让读者自己从这堆专有名词里反推"所以这里要解决的问题是什么"。读者读到的是参照仓做了什么，不是为什么这么做，更不知道除了这么做还能怎么做。

反例（真实发生过，来自某篇初稿）：

> 把这条约束焊死的是状态机。`state.ts` 的迁移表除了记每条边合法与否，还给它带一个 `viaCommand` 字段，写明这条边归哪条命令走……`flip.ts` 拿到迁移规格之后多做一步检查，`spec.viaCommand !== 'flip'` 就抛 `E_ILLEGAL_TRANSITION`……

这段话本身没有事实错误，问题在**起手式**。读者还不知道要防的是什么、有几种防法，就先看见了`viaCommand`这个字段名，只能死记，记不住原因。

正确的顺序是 ADR §7 那张工程设计专题模板的顺序，**问题 → 可选方案 → 当前选择 → 原因 → 代价**，仓库证据放在"当前选择"和"原因"之后，充当"这个选择在真实系统里落地了"的佐证：

1. **问题**：Agent 十有八九会抄近路直接跑它已经会用的命令，绕开需要跨文件收口的那条专用命令，怎么在系统里把这条近路堵死。
2. **可选方案**：不做限制、靠人审兜底；在 CLI 入口写一串 if 判断硬拒绝；在状态机的迁移表上给每条边标注归属命令，由**唯一一处**判断逻辑去查表。
3. **当前选择与原因**：选第三种，因为迁移表本来就要维护，标注顺手带上，而且能整表渲染成 `--help` 的活文档，比散在各处的 if 判断更不容易漏改。
4. **仓库证据（佐证，不是起点）**：`state.ts` 迁移表里三条边的 `viaCommand` 都写着同一条命令；`flip.ts` 读到不匹配就抛 `E_ILLEGAL_TRANSITION`，报错文案里指明该走哪条命令。

判据：把一段工程原理内容的仓库证据部分单独抠掉，前面剩下的问题和设计取舍是不是仍然成立、仍然能让读者自己判断"换我来设计我会怎么选"。抠掉之后前面站不住、只剩"因为仓库这么写"，就是把仓库证据当成了论证起点，要重新排序。

还有一种更常见的坏法，是道理和证据都在，但顺序反了：论证本身站得住，只是被埋在一堆专有名词后面。上面那条判据测不出这种，它只测"道理在不在"，测不出"道理排在第几句"。

补一条能机械执行的：**每个三级小节的前两句话里，必须已经出现一句脱离专有名词也能读懂的问题陈述。** 前两句全是文件名、字段名、行数、命令名，就是证据抢跑，把问题陈述提到最前面重排。

概念篇引用仓库材料不受本条约束，那类引用的作用是**证明一个抽象定义在真实系统里确实存在**（例如证明"Agent 会自己转读环境→观察这一圈"不是纸面说法），不是在教一次设计决策，不需要先摆问题和可选方案。

## 六、怎么不写出 AI 味

学员一眼看出这是 AI 写的，通常不是因为句子不通，是因为**内容里没有只有做过的人才知道的东西**。

### 6.1 陌生人判据

对每一段问一句：**一个没做过这个项目、只读过公开资料的人，能不能写出这段话。**

能写出来的，删掉或换掉。

| 谁都能写 | 只有做过的人知道 |
|---|---|
| 检查代码是否正确 | `yaml` 包的 `toString()` 会改掉注释对齐，25 个真实 fixture 全中 |
| 确认功能正常运行 | `npm link` 的符号链接会让全局 `media` 命令静默空转，读代码读不出来 |
| 注意测试覆盖率 | 测试全绿是因为合成 fixture 把 bug 的行为编码成了预期 |
| 依赖版本要配置正确 | 执行方案里写了 `workspace:*`，npm workspaces 不认，报 `EUNSUPPORTEDPROTOCOL` |

右边那一列不需要写得多，一句就够。左边那一列写多少都是废话。

### 6.2 没有真材料就不写那一段

写到某处发现只能写出左边那种话，说明这一处没有材料。**正确动作是删掉这一段或缩短本篇，不是把话说得更漂亮。**

上一版第 0 章的验收段就是这么坏掉的。那一章确实没有代码要验，于是硬造了三个坑，读起来立刻塌方。

### 6.3 并列罗列是模板的尾巴

「坑一、坑二、坑三」「第一点、第二点、第三点」这种并列，本身就是模板留下的形状。同一篇里出现两次以上，基本可以判定内容是被塞进格子的。

真实的经验不是并列的。它有主次、有因果、有时间先后。按 §2.4 给它找出那个序，用序把它们串起来，而不是编号。

### 6.4 不要点题

写完一段判断，不要再补一句「这正说明了……」把它拔高到课程主张上。暗线自然复现即可，读者能看出来。

上一版每章结尾都硬点一次暗线，连起来读像每集片尾都放同一段旁白。

## 七、工程篇要能被跟着搭起来

课程是训练营，学员跟着造。**工程篇读完，读者手里必须多出一个能跑的东西**，而不是多懂一个道理。

### 7.1 判据

读者照着这一篇做，做完能拿到一个可运行的产物，并且能自己证明它是对的。做不到就是这一篇没写完。

反例是上一版：一整篇讲清楚了设计，施工内容只剩四百字的示例提示词，读者合上文档手里是空的。

### 7.2 提示词用自然语言，不许填表

给读者的是**复制进 Claude Code 就能开工**的一段话，不是一张表。

**禁止把提示词写成「目标 / 上下文 / 范围 / 约束 / 验收 / 停止」的分栏填空。** 第 2 章立的六件事仍然要交代到，但要用人说话的方式说出来，不是当小标题去填。填表式的提示词是模板病的另一种形态，读者一眼就知道这是生成的，而且真实的人不那么下任务。

一段合格的提示词大致覆盖这几件事，顺序按说话的自然顺序，不固定：

- 要什么，一到三句说清楚
- 动手前先读哪儿
- 最容易写歪的那一两处，点出来
- 我会怎么验
- 什么情况下停下来问我

**控制在 20 行以内。** 细节靠正文承载，提示词只是个能直接开工的起点，不需要自成一份规格。

写的时候有个判据：**这段话像不像一个做过这件事的人随手打出来的。** 面面俱到地罗列每条约束就不像，只交代那几句自己栽过跟头的地方才像。

对比一下同一件事的两种写法：

```text
差（填表）
约束
  判进程存活用 process.kill(pid, 0)。catch 分支里 code 为 EPERM 必须判定为存活。

好（人话）
这里有个坑，判存活用 process.kill(pid, 0)，catch 里 code 是 EPERM 的话要判它活着，不是死了。
```

后一种拦得住，因为它带着「我在这儿栽过」的语气，读者会多看一眼。

提示词里出现的每个文件路径、命令、错误码都要真实存在，读者会照着敲。

### 7.3 施工要拆步，每步能单独验

不许把一整个模块塞进一个大提示词。拆成几步，**每一步都有自己的产物和验收动作**，读者做完一步就能确认这一步对了，再往下走。

拆步的顺序通常是：先只读、后写入；先单文件、后跨文件；先正常路径、后失败路径。哪一步先做，取决于哪一步的产物是下一步的前提。

每一步都要写清楚 **Agent 在这一步大概率会怎么错**。这是本课的核心价值所在，读者不知道要拦什么，就拦不住。

### 7.4 与 §5.1 的关系

§5.1 禁止的是把验收信息堆成文章末尾的附录。**施工内容不受此限**，它是工程篇的主体，可以成节，也应当成节。

区别在于：施工是「怎么造出来」，验收是「怎么知道它对了」。前者是主线，后者贴着每一步走。

### 7.5 概念篇不适用

第 1 章这类概念篇没有工程产物，不适用本节。**不许为了满足本节而硬造一个施工步骤。**

判断标准看这一篇在里程碑（ADR §8）里承担哪个工程增量，承担不了的就是概念篇。

## 八、长文怎么写得住

工程篇讲透往往要几千字。长文最容易散，以下五条是防散的具体手段。

### 8.1 两层标题分工

**二级标题承载论证推进，三级标题承载具体点。**

只有一层标题的文章写到三四千字必散，读者失去位置感。分两层之后，二级标题连起来是本篇的论证主干（满足 §2.1 的抽取判据），三级标题是每一步内部的展开。

三级以下不再分。需要第四层说明这一支该独立成篇。

**两级标题都要编号。** 二级用 `N.`，三级用 `N.M`，从 1 起，篇内连续。例如：

```text
## 1. Agent 手改状态文件，先烂掉的是两个文件之间的账
### 1.1 漏翻的是两个文件之间的账
### 1.2 注释被冲平，diff 里认不出真改动
## 2. 一次发布动三个文件，收口的单位就得是这次发布
### 2.1 一条命令收三个文件
```

不要用「一、二、三」这类中文序号，读者在长文里跳转和引用时数不清位置。编号只标序，标题本身仍然要是小结论（见 §4.5）。

### 8.2 故障实验要给证据解读

只写「造一个反例，看它报错」等于没写。完整的故障实验是三段：

1. **怎么造**：具体操作，读者能复现
2. **看到什么，它证明了什么**：把现象翻译成结论。同一个现象往往能排除掉好几种猜测，说清楚排除了哪些
3. **正确的修复动作是什么**：尤其要点名读者最容易做的那个错误动作

第三段最值钱。读者遇到故障时的第一反应通常是错的，比如看到状态读不出来就去删库重来，那会把最有价值的证据一起删掉。

### 8.3 诊断要分层，不要平铺

一个故障现象背后有多个可能的层，按从外到内给一张分层表：**层 × 该层能观察到的证据 × 该层的常见问题**。

然后对高频场景各给一段，说清楚这个场景下每一层的证据分别长什么样。

平铺罗列可能原因的写法帮不了读者，他仍然不知道先查哪个。

### 8.4 代码要能跑，输出要真实

贴出的代码读者会照着敲，所以必须是完整可运行的，不是伪代码片段。

命令与代码要配上**真实的输出**，并在输出里用注释标出关键位置（哪一行证明了什么）。编造输出是本规范最严重的违规，比写错还糟，因为读者跑出来对不上会怀疑整篇。

跑不出真实输出的，就不要贴那段输出，改成描述会看到什么。

### 8.5 正文不写总结节、自检节、参考文献节

**这三样一律不许出现在正文里。** 它们是模板尾巴，27 篇都挂同一副尾巴，读者翻两篇就知道后面长什么样。

- **总结节**：读者刚读完，不需要有人把同样的话再说一遍。真正该沉淀的判断在各节的小结论里已经给过了
- **自检节**：属于练习材料，不属于正文
- **参考文献节**：为凑数而引是上一版的病根。确实读过且必要的外部资料，在用到它的那一句话旁边就地给出，不单独成节

同理禁止的还有篇末那句「这一章你手里多了什么」。上一版每篇都写一句，连起来读像每集片尾放同一段旁白。

正文写到哪里讲透了就停，不需要收尾仪式。

自检题与练习如果课程需要，另出练习材料承载，不进正文。

## 九、材料纪律

动笔前在内部逐条列出**至少 5 件具体材料**并注明来路（哪个文件、哪一段、哪条 lesson、哪次运行的哪条输出）。

列不出就缩短本篇，或与相邻篇合并，或回报主回话要料。**不许用重复解释灌字数。**

不许自行编造代码、路径、行号、命令输出。素材清单里没有而本篇确实需要的，向主回话要，不得推测。

全文零「以你实际为准」式模糊表述。写不实就删。

## 十、篇与篇之间

每篇的派工任务书钉死三件事，写作时不得越界：

| 项 | 含义 |
|---|---|
| 可消费概念 | 前序篇目已立，直接用，不重复解释 |
| 必须产出概念 | 后续篇目要用，本篇必须立住 |
| 工程增量 | 读完这篇，学员手里的项目多了什么 |

跨越可消费清单去引用还没出场的概念，合流时打回。

### 10.1 概念首出索引

任务书里的可消费清单只管本篇的上游，管不住"三篇文章各自以为自己是第一个讲这件事的人"。真实发生过：只读工具是物理约束这个判断，在 1.1、1.2、2.3 被从头论证了三遍，每一遍都没提前一遍。

所以另有一份全局登记：`05-跨篇概念首出索引.md`，记每个概念**第一次被完整论证**是在哪篇哪节。

- 动笔前先查这份索引。要用的概念已经登记过，只能一笔带过或显式承接（"1.2 已经把这件事讲透了，往前再推一步是……"），不许重新搭一遍论证脚手架。
- 本篇立住了索引里没有的概念，交付时把它补进索引。
- 索引里登记的位置和实际交付文件对不上（比如登记在 3.1，实际讲清楚的是 4.2），以**实际交付文件**为准，改索引，不是改文章去迁就索引。

### 10.2 同一处仓库证据不许跨篇重复当主证据

§10.1 管的是概念，这条管的是证据。同一个文件、同一段代码、同一条 lesson，如果已经在前序篇目里当过一整节的主证据，后续篇目只能一笔带过或显式承接，不许再展开成一个小节。

判据：这处证据在别处已经承担过论证核心的角色吗？是的话，本篇引用它时有没有增加新的认知台阶？没有增加，就删掉重新展开的部分，改成一句承接。

## 十一、篇幅

**不设下限也不设上限，不预估字数，不在派工时下达篇幅指标。** 唯一标准是把这一篇讲通透。

讲透了就停，写到一半发现材料只够半篇就缩短或与相邻篇合并，材料多到一篇装不下就拆成两篇并重排编号。**篇幅是结果，不是目标。**

这一条是对更早一版「单章不低于 3000 字」的直接纠正，那是注水、待填模板与凑数引用的制度来源。同一个错误的变体是给每篇预估一个目标字数，写作 agent 会为了凑到那个数而灌水，所以派工任务书里一律不写字数。

## 十二、写作红线

走 `human-writing` skill。以下逐条覆盖标题、小标题、正文、表格与图注。

- 禁破折号 `——` `—` `–`
- 冒号只允许引出人物直接原话。「一句话总结：」「核心是：」这类提示性冒号全禁。网址、代码块内、机器字段、mermaid 围栏内不受限
- 禁翻案腔。「不是……而是……」「看似……实则……」「你以为……其实……」「说到底」及一切变形。禁的是修辞动作不是字面，换字继续做同一动作仍算命中

  **这条最容易误判，判据是：把对照结构整个去掉，读者少知道一件事吗。**

  少知道，是技术辨析，保留。它划的是两个读者真会混淆的东西之间的界，去掉之后信息就没了。比如「拆分的依据不是把工作量对半分，是每个包能不能单独判断自己做完了」，读者默认就是按工作量分，这句在纠正一个真实的错误预期；比如「B 闸不是问声音听着自然吗，是要求去停顿之后再跑一次 silencedetect」，主观听感和机器复扫是两回事；比如「不是空值，是这个键从没出现过」，两种状态在代码里行为不同。

  不少知道，是修辞翻案，改。它立的是一个没人真信的靶子，或者拿「从来不是」「并不是」当强调词使，去掉对照之后句意不变，只是气势弱了。比如「这条镜像不是理论上的风险，测试里留着一条真实复现的用例」，没人说过它是理论风险；比如「这不是一句抽象的架构道理，是这个仓真的摔过的跟头」，同理；比如「扛得住搬家的从来不是任何一份具体答案，是问那几个问题的方法」，正着说更有力，「从来不是」只是在加戏。

  改法是把结论正着说，不先立靶子。上面最后一句改成「扛得住搬家的是问那几个问题的方法，换一个业务，答案要重新推一遍，问题不用换。」
- 禁三项以上同构排比，两项为限
- 禁给抽象名词配具体动词抒情
- 禁动词名词化。「完成了对流程的优化」写成「把流程改顺了」
- 禁「说白了」「说穿了」「先说结论」
- 禁洞察路标：「更微妙的是」「还有一层」「值得注意的是」「需要指出的是」「从某种意义上说」
- 禁商业黑话与模型黑话
- 禁用仓库、抽屉、温度、坍塌、浪潮、钥匙、底座等借喻包装抽象概念

逐字引用真实仓库里**人写的**文档原文时，如果原文本身含被禁用的标点或修辞，改引用方式，不改原文：转述 + 局部加引号，不要整段照搬。原文本身就是被讨论的对象时除外（比如本节下面这个例子）。

机器生成的文案不受限。参照仓 `dashboard.md` 里 `（空——check 无警报）` 是 `dashboard.ts` 渲染的原文，改了会与 `media dashboard sync` 输出对不上。

## 十三、配图

**机制图**用 mermaid，写作时直接画进正文。判据是这东西本身就是图，用文字描述要绕好几段的才画。每篇至多两张。标签用中文，一张图不超过一屏能看完的复杂度。mermaid 围栏内不受 §9 红线约束，但图注是正文，受全部约束。

**叙事插图**写作阶段只留占位 `<!-- ILLUST: 描述 -->`，正文定稿后统一出图。描述要具体到能照着画，写清画面里有什么、谁在干什么，不许写「体现 Loop 思想」这类抽象要求。

顺序不能反。先出图再写文字，文字会被图牵着走。写完再硬塞图，图与文字互相打架。

## 十四、交付前自查

按顺序过，任一条不过不许交付。

1. 本篇结论一句话写得出来，且是判断句
2. 抽出全部节标题与每节首句，单独读仍是通顺完整的论述（§2.1）
3. 每一节去掉之后上级结论会塌（§2.2）
4. 同级节两两不可互换标题，合起来撑得住上级结论（§2.3）
5. 相邻节调序会让理解成本上升（§2.4）
6. 每个概念在用到之前已经立过（§3.1）
7. 没有认知负荷跳变的节（§3.2）
8. 每节写得出「读完这节你手里多了什么」（§3.3）
9. 节标题无「设计选择」「实现」「验收」这类无信息量词（§4.5）
10. 材料 5 件以上且各有来路，零编造，零「以你实际为准」（§9）
11. 无越界引用后续篇目的概念（§10）
12. 每一段都过陌生人判据，没有「谁都能写」的空话（§6.1）
13. 验收信息贴着设计点，没有单独的验收节（§5.1）
14. 仓库证据只在问题和设计取舍讲清楚之后出现，抠掉证据段前面仍站得住（§5.2）
15. 同一篇里并列罗列不超过一次（§6.3）
16. 篇幅由内容定，没有为凑长度而写的段落（§11）
17. 工程篇给出了可直接粘贴的完整任务契约，六部分齐全（§7.2）
18. 施工拆成了可单独验证的步骤，每步写明 Agent 会怎么错（§7.3）
19. 读者照着做，手里确实能多出一个可运行的产物（§7.1）
20. 超过三千字的篇目用了两层标题，二级标题连起来是论证主干（§8.1）
21. 故障实验三段齐全，写明了读者最容易做错的那个动作（§8.2）
22. 代码完整可运行，输出真实未编造（§8.4）
23. 正文没有总结节、自检节、参考文献节，也没有篇末的「你手里多了什么」（§8.5）
24. 二级三级标题都按 `N.` 与 `N.M` 编号，篇内连续（§8.1）
25. 提示词是自然语言，没有填表式分栏，每段 20 行以内（§7.2）
26. `check_prose.py` 零命中（§12）。**翻案腔那一项脚本判不了**，它只认字面，分不出技术辨析和修辞翻案，按 §12 的判据逐条人工过
27. 动笔前查过 `05-跨篇概念首出索引.md`，已登记的概念只承接不重讲；本篇新立的概念已补进索引（§10.1）
28. 每个三级小节的前两句里有一句脱离专有名词也能读懂的问题陈述（§5.2）
29. 没有把前序篇目当过主证据的同一处仓库证据重新展开成一节（§10.2）
30. 逐字引用人写的文档时，原文里的禁用标点已改成转述加引号，没有整段照搬（§12）

交付后由独立 subagent 按本清单逐条判 PASS / FAIL，只判不改。同一篇连续两轮 FAIL 转主回话亲写。
