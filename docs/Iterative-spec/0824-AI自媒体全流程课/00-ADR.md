## 0. 决策摘要

### 0.1 课程名称

**《让AI跑完自媒体全流程：从选题到复盘》**

### 0.2 一句话定位

以一条真实运行过的内容自动化流水线为贯穿案例，带领已经开始使用 AI Agent、但仍停留在“不断和 AI 对话”阶段的学员，从零搭建一套完整系统，逐步完成三次能力升级：

```text
Chat：让 AI 回答问题
  ↓
Agent：让 AI 独立完成一次任务
  ↓
Harness：让任务能够稳定、可验证地重复执行
  ↓
Loop：让系统根据真实结果持续改进下一轮
```

### 0.3 金字塔顶层结论

课程只证明一个核心命题：

> 任何能够固化的工作流程，都可以被拆成输入、状态、执行、检查、人审、反馈和规则更新；Agent 负责判断与执行，Harness 负责约束与验证，Loop 负责从结果中学习。

这个结论由三层能力支撑：

1. **Agent Engineering**：把模糊需求变成 Agent 能独立完成的一次任务。
2. **Harness Engineering**：用协议、状态机、CLI、质量闸和人审边界，让任务稳定重复。
3. **Loop Engineering**：用真实结果、归因、人审和策略回写，让下一轮发生可解释的改进。

三层不能颠倒。没有 Agent，系统没有执行者；没有 Harness，Loop 只会放大随机性；没有可信反馈，循环执行也不等于持续改进。

### 0.4 课程结构决策

| 决策 | 结论 |
|---|---|
| 组织方式 | 不按仓库目录逐文件讲，按学员认知台阶和项目增量组织 |
| 教学主线 | AI 协作能力线与工程设计能力线并行 |
| 实现方式 | 所有代码、测试和配置由 Agent 生成，学员不手写业务代码 |
| 学员职责 | 设计目标、上下文、边界、验收、停止条件；阅读 Diff 与运行证据 |
| 案例角色 | 抖音内容流水线是案例载体，不是课程能力边界 |
| 工程重点 | 真相源、状态机、CLI、事务、幂等、质量闸、人审、反馈污染防护 |
| 工具主线 | 以 Claude Code 原生仓库能力演示，补充 Codex 等价操作与协作模式 |
| 最终考核 | 将同一套架构迁移到一个非内容生产的真实流程 |

## 1. 背景与问题定义

### 1.1 目标学员现状

目标学员已经初步使用 Claude Code、Codex 或类似 Agent 工具开发和写代码，但熟练度不高，常见工作方式仍是：

- 把 Agent 当成更强的聊天机器人。
- 一次给一个局部要求，靠多轮对话不断纠偏。
- 关注 Prompt 怎么写，不关注任务如何验收。
- 看到 Agent 说“完成了”就默认任务已经完成。
- 不清楚规则应放在 Prompt、项目规则、SOP、Skill 还是代码中。
- 不知道什么时候使用主 Agent、Sub Agent 或 Agent Team。
- 不理解为什么 AI 时代仍需要 CLI、状态机、测试、事务和审计。
- 能让 AI 生成一个功能，但不能让它长期、稳定、可恢复地运行。

### 1.2 课程要解决的根问题

学员缺少的不是更多提示词技巧，而是把 AI 纳入软件系统后的工程思维：

```text
过去的问题：我怎么把代码写出来？

AI 时代的问题：
我怎么把问题描述成一个可靠系统，
让 AI 完成实现，并证明系统真的可靠？
```

AI 显著降低了写代码、生成测试和尝试不同实现的成本，但没有自动降低以下成本：

- 选择正确问题的成本。
- 划分系统边界的成本。
- 设计状态和真相源的成本。
- 处理失败、重试、并发和不可逆动作的成本。
- 验证 Agent 是否真的完成任务的成本。
- 防止错误反馈进入 Loop 后被持续放大的成本。

因此，本课程重点训练的问题建模、协议设计、状态设计、验证设计和反馈设计，比具体代码语法更重要。

## 2. 面向人群、前置条件与非目标

### 2.1 面向人群

- 已使用过 Claude Code、Codex、Cursor Agent 或类似工具。
- 能看懂基本目录结构、命令输出和 Git Diff。
- 有基础的软件开发经验，但未必熟悉架构设计。
- 希望把个人工作流、团队 SOP 或业务流程交给 AI 执行。
- 希望从“AI 辅助写代码”升级到“AI 原生系统设计”。

### 2.2 建议前置知识

- 基本终端使用能力。
- 基本 Git 概念：工作区、Diff、提交、回滚。
- 能阅读 Markdown、YAML、JSON。
- 理解函数、接口、状态等基础开发概念。

课程不要求学员熟练掌握 TypeScript、Python、React 或后端框架。涉及代码时，重点是读懂职责、输入输出和设计取舍，不要求记忆语法。

### 2.3 课程非目标

- 不把课程做成 Claude Code 命令大全。
- 不把课程做成 Prompt 技巧合集。
- 不教授如何运营一个真实抖音账号。
- 不要求学员复刻教学仓里的全部媒体生产能力。
- 不把“不手写代码”误解成“不读代码、不审 Diff、不做验证”。
- 不宣称文件、CLI 或 Markdown 是所有业务的通用最佳实践。

## 3. 课程目标与硬约束

### 3.1 学习目标

完成课程后，学员应当能够：

1. 把一个模糊流程拆成工作单元、阶段、状态、产物和人审节点。
2. 用项目规则、阶段契约和 Skill 为 Agent 提供分层上下文。
3. 判断什么时候使用主 Agent、Sub Agent 和 Agent Team。
4. 设计一套 Agent 友好的 CLI 或 API 协议。
5. 把状态写入从 Agent 的自由编辑中收回到确定性工具。
6. 设计事务、锁、原子写、幂等、审计和 Dry Run。
7. 区分账本一致性检查与产物质量检查。
8. 为不可逆动作和主观判断设计 Human-in-the-loop。
9. 观察无头 Agent 的执行过程，并用文件状态而不是模型自述裁决结果。
10. 建立独立治理线，对流程资产做周期维护和事件复盘。
11. 用真实结果形成提议，经人审后更新未来决策依据。
12. 将同一套方法迁移到内容生产之外的真实流程。

### 3.2 “不手写代码”约束

课程中的“不手写代码”按以下口径执行：

- 学员不手工编写业务代码、测试代码和工程配置。
- 学员可以写任务契约、架构决策、验收标准和人工判断意见。
- 所有工程文件由 Agent 创建或修改。
- 每次修改必须经过 Git Diff 审查。
- 每个功能必须用测试、命令输出或文件状态验收。
- Agent 修改测试以绕过失败，视为验收不通过。
- Agent 声称“完成”但无法提供后置条件证据，视为未完成。

### 3.3 统一任务契约

课程要求学员用同一个任务结构委托 Agent：

```text
目标：最终要得到什么结果
上下文：必须读取哪些材料
范围：允许修改什么，不允许修改什么
约束：必须遵守哪些规则和架构边界
验收：用什么证据判断完成
停止：遇到什么情况必须停下来并上报
```

## 4. 案例与通用工程概念映射

抖音内容流水线只是案例。课程必须持续把仓库对象翻译成通用概念：

| 教学仓对象 | 通用工程概念 |
|---|---|
| `brain/` | 组织规则、领域知识、策略配置、未来判断依据 |
| `content/_backlog/backlog.yaml` | 需求池、任务库存、工作队列 |
| 一个内容目录 | 一个订单、Issue、项目或工作单元 |
| `meta.yaml` | 工作单元状态账本 |
| `pipeline/*.md` | 阶段契约、可执行 SOP |
| `.claude/skills/` | 可复用执行能力 |
| `media` CLI | 唯一可信写入器、业务命令协议 |
| `check` | 状态与引用一致性检查 |
| `doctor` | 阶段产物完整性与格式检查 |
| `dashboard.md` / Web UI | 派生视图和控制面 |
| 飞书审核卡 | 人工决策与不可逆动作授权界面 |
| `harness/` | 评估、治理和维护系统 |
| `retro` | 结果采集、漏斗定位和复盘 |
| 修改 `brain/` | 用反馈修改未来决策依据 |

课程迁移示例包括但不限于：

- 从 Issue 到开发、Review、发布的软件交付流程。
- 从会议录音到纪要、决策和知识库的沉淀流程。
- 从客户需求到方案、报价和跟进的销售流程。
- 从岗位需求到初筛、面试和录用的招聘流程。
- 从数据源到日报、告警、归因和策略调整的数据流程。
- 从客服工单到解决、质检、复盘和知识更新的服务流程。

## 5. 金字塔课程结构

### 5.1 一个顶层结论，三层核心能力

课程先给出结论，再逐层回答支撑结论的问题：

    顶层结论：任何可固化流程，都能被设计成可验证、可治理、可进化的 AI 流水线
                                    ▲
                            Loop Engineering
                     系统能否根据结果改进下一轮
                                    ▲
                           Harness Engineering
                    任务能否安全、稳定、可验证地重复
                                    ▲
                            Agent Engineering
                         AI 能否独立完成一次任务

三层能力分别解决：

1. **Agent Engineering**：上下文、任务契约、工具调用、协作方式和证据验收。
2. **Harness Engineering**：流程协议、CLI、状态机、质量闸、人审、事务和恢复。
3. **Loop Engineering**：结果采集、归因、治理任务、变更提议和策略更新。

三层不能颠倒。不会委托 Agent，就无法稳定实现系统；没有 Harness，自动循环只会放大随机性；没有可信反馈，周期执行也不等于持续改进。

### 5.2 五个学习阶段

三层核心能力按初学者的认知顺序展开为五个学习阶段：

| 学习阶段 | 包含主章 | 关键问题 | 能力跃迁 |
|---|---:|---|---|
| 第一阶段：认识并驾驭 Agent | 第 1-2 章 | 如何从聊天转向可验收的任务委托？ | Chat → Agent |
| 第二阶段：把工作变成流水线 | 第 3-4 章 | 如何把隐性经验变成 Agent 可执行的流程？ | Agent → Workflow |
| 第三阶段：让流水线稳定可信 | 第 5-7 章 | 如何让流程可重复、可恢复、可审计？ | Workflow → Harness |
| 第四阶段：让系统形成闭环 | 第 8 章 | 如何让真实结果影响下一轮？ | Harness → Loop |
| 第五阶段：组装与跨域迁移 | 第 9 章 | 如何证明这套方法可以迁移？ | Case → Method |

前四个阶段负责搭建能力金字塔，第五阶段负责综合应用和迁移验证。每一阶段的出口产物，都是下一阶段的输入。

### 5.3 章节数量与教程拆分标准

课程压缩为：

- **5 个学习阶段**：只负责组织学习路径，不单独计算教程篇数。
- **9 个主章**：每章回答一个完整的核心问题。
- **27 个子章节**：每个子章节对应一篇可独立发布的教程文档。

因此，正式教程共 **27 篇**。命名统一采用“第 N 章 + N.1/N.2/N.3”的图书式结构，例如：

    第 1 章：学习 Agent
    1.1 Agent 是什么
    1.2 Agent 的工作原理
    1.3 Claude Code / Codex 最小工作流

不再把概念说明、项目演示和工程专题拆成大量平级章节。每篇教程只承担一个明确问题，但必须推动本章的工程产物向前一步。

### 5.4 两条贯穿主线

| AI 协作能力线 | 工程设计能力线 |
|---|---|
| Chat → Agent | 模糊需求 → 任务契约 |
| Agent → Skill / Sub Agent / Team | 操作经验 → 职责与上下文边界 |
| Agent → Workflow | 隐性流程 → 阶段与产物协议 |
| Workflow → Harness | 自动执行 → 状态、检查、审计和恢复 |
| Harness → Loop | 周期运行 → 证据、归因和策略更新 |

## 6. 详细课程大纲

课程由 5 个学习阶段、9 个主章和 27 个子章节组成。以下每个编号子章节对应一篇教程文档。

### 第一阶段：认识并驾驭 Agent

**阶段问题**：如何不再靠反复对话纠偏，而是把一个工程任务完整地委托给 AI？

**阶段目标**：理解 Agent 的能力边界，掌握 Claude Code / Codex 的最小工作方式，并能通过上下文、任务契约、协作分工和证据完成一次可靠委托。

#### 第 1 章：学习 Agent

##### 1.1 Agent 是什么：从 Chat 到自主执行

- 区分 Chat、Agent、Workflow、Harness 和 Loop。
- 理解 Agent 不只是生成文本，而是能够读取环境、调用工具、执行动作并观察结果。
- 找出“不断和 AI 对话”中被人隐性承担的规划、纠错和验收工作。
- 建立课程中的人机分工：AI 负责实现，人负责目标、边界、判断和验收。

##### 1.2 Agent 的工作原理：模型、上下文、工具与反馈

- 用“目标 → 上下文 → 计划 → 工具调用 → 环境反馈 → 再判断”理解一次 Agent 执行。
- 理解模型为什么会遗忘、误判、越权和声称已经完成。
- 认识权限、上下文窗口、工具结果和停止条件对 Agent 行为的影响。
- 解释为什么 Agent 的自然语言自述不能成为系统事实。

##### 1.3 Claude Code / Codex 最小工作流

- 完成读取仓库、搜索代码、修改文件、运行命令、执行测试和审查 Diff。
- 认识交互式任务、无头任务、项目规则和工具权限。
- 建立“先读项目 → 再提出方案 → 委托实现 → 检查 Diff → 运行验证”的基本节奏。
- 说明 Claude Code 与 Codex 的能力映射，而不把课程变成命令大全。

**本章产物**：一份 Agent 能力边界图；一次最小仓库任务的完整执行记录。  
**出口条件**：学员能够解释 Agent 如何工作，以及一次执行为什么可能出现假完成。

#### 第 2 章：学会与 Agent 协作

##### 2.1 把模糊需求写成任务契约

- 使用目标、上下文、范围、约束、验收和停止六部分任务契约。
- 把“帮我做一个流水线”改写成结果明确、范围可控的工程任务。
- 要求 Agent 先读取指定材料，再做设计和实现。
- 为余额不足、登录失效、需求冲突和越权修改设置停止条件。

##### 2.2 设计 Agent 的上下文：Prompt、规则、SOP 与 Skill

- 区分本次 Prompt、项目规则、阶段 SOP、可复用 Skill 和确定性工具。
- 理解 CLAUDE.md / AGENTS.md、brain、pipeline 和 Skill 的职责边界。
- 学会把冗长 Prompt 拆成稳定规则、阶段契约和可复用能力。
- 避免同一规则在多处复制导致行为漂移。

##### 2.3 主 Agent、Sub Agent、Agent Team 与证据验收

- 强共享上下文、顺序推进的任务交给主 Agent。
- 独立检查、只回传结论的任务交给 Sub Agent。
- 可并行实施、可独立验收的工作包交给 Agent Team。
- 用 Git Diff、测试结果、命令输出和文件状态识别部分完成、假完成和越权完成。
- 坚持“模型自述是说明，工程证据才是结论”。

**本章产物**：通用任务卡、项目上下文分层图、多 Agent 选型表和一次证据完整的委托任务。  
**出口条件**：学员能够选对协作方式，并用后置条件而不是模型自述验收结果。

**阶段产物**：零手写协作公约、Agent 任务模板、上下文地图和协作决策表。

---

### 第二阶段：把工作变成流水线

**阶段问题**：如何把存在于聊天和个人经验中的流程，变成 Agent 可以重复执行的工程系统？

**阶段目标**：完成从单次 Agent 任务到 Workflow 的跃迁，搭出“选题 → 创作 → 审核”的最小自媒体生产线。

#### 第 3 章：学习流程建模

##### 3.1 识别工作单元：系统到底在推进什么

- 定义可以独立创建、推进、暂停、恢复和审计的工作单元。
- 将一条内容映射为工作单元，并迁移到 Issue、订单、候选人或客服工单。
- 分清任务库存、生产中的对象和最终资产。
- 避免按工具或 Agent 名称错误划分业务对象。

##### 3.2 划分阶段：输入、输出、状态与闸口

- 按产物和责任变化划分选题、创作、审核、发布和复盘阶段。
- 每个阶段只定义输入、输出、状态变化以及通过/停止/升级条件。
- 区分确定性步骤、主观判断和不可逆动作。
- 让一个阶段失败时可以停在明确位置，而不是从头重来。

##### 3.3 设计产物链、真相源和人审节点

- 设计 Brief、脚本、审核意见、发布记录和复盘报告的产物链。
- 区分中间产物、最终产物和派生视图。
- 为同一事实指定唯一可信来源，避免脚本在多个文件中互相冲突。
- 把人放在主观质量、不可逆动作和策略更新三个关键节点。

**本章产物**：工作单元定义、阶段契约、产物关系图、真相源清单和人审节点图。  
**出口条件**：任何阶段都能回答“读什么、产出什么、状态怎么变、何时必须停”。

#### 第 4 章：搭建第一条 AI 创作流水线

##### 4.1 看懂教学项目的分层架构

- 认识 SOP/Agent 层、CLI 记账层、飞书/Web 控制层和 Harness/Loop 层。
- 区分“选题到发布”的生产线与“养池、复盘、对标、自审”的治理线。
- 理解大环：brain → backlog → content → publish → retro → brain。
- 解释为什么课程按认知和工程增量讲，而不是按仓库目录逐文件讲。

##### 4.2 不手写代码，实现选题到待审核

- 让 Agent 创建 Backlog、内容目录、阶段文档、Skill 和最小执行入口。
- 第一版只完成“选择任务 → 生成 Brief → 生成内容 → 进入待审核 → 停止”。
- 暂不接真实发布、复杂媒体、Web 看板和自动复盘。
- 通过任务契约控制 Agent 的修改范围，并逐步验收每个工程增量。

##### 4.3 验证、停止与恢复第一条流水线

- 验证无可用选题、缺失输入和内容生成失败时不会伪造成功产物。
- 检查流程能否明确停在人审，而不是擅自执行真实发布。
- 从中间产物和显式状态恢复任务，而不是依赖旧聊天记录。
- 把同一建模方法映射到软件交付、知识库或销售跟进流程。

**本章产物**：一条可以运行到待审核的最小内容生产线。  
**出口条件**：流程能够重复运行、明确停止、从中间阶段恢复，并保留完整产物证据。

**阶段产物**：Backlog、工作单元模板、阶段 SOP、最小 Skill 和第一条可运行生产线。

### 第三阶段：让流水线稳定可信

**阶段问题**：当人、Agent、定时任务和界面都能触发流程时，系统如何保持一致、可验证和可恢复？

**阶段目标**：用 CLI、状态机、事务、质量 Harness 和 Human-in-the-loop，把一次可运行的 Workflow 升级成可信 Harness。

#### 第 5 章：为什么 AI 时代更需要 CLI

##### 5.1 CLI 是什么：人与 Agent 共用的业务协议

- 观察 Agent、Bot、Server 和定时任务各自写文件时产生的多套业务规则。
- 理解 CLI 不是终端偏好，而是多个入口共同遵守的稳定协议。
- 建立分工：Agent 决定“该不该做”，CLI 决定“如何可靠地做”。
- 让人、Skill、Agent、CI、飞书卡片和 Web Server 复用同一写入路径。

##### 5.2 如何设计 Agent 友好的 CLI

- 提供稳定参数、结构化 JSON、明确退出码和稳定错误码。
- 提供 Dry Run、幂等语义、Help 活文档和审计 Actor。
- 比较 CLI、Library、HTTP API、MCP、Web UI 和 Webhook 的适用场景。
- 理解“Web/飞书 → Server → CLI → 文件真相源”的适配器结构。

##### 5.3 让 Agent 实现并验收 CLI

- 先定义命令行为、输入输出、错误语义和不可修改边界，再委托 Agent 实现。
- 从只读命令开始，再增加受控写入命令。
- 用契约测试验证 JSON Schema、退出码、Dry Run 和幂等行为。
- 检查 Server 是否复用 CLI，而不是复制第二套业务逻辑。

**本章产物**：Agent 友好的 CLI 契约、只读命令和首批契约测试。  
**出口条件**：所有业务入口可以复用同一协议，写入规则只维护一份。

#### 第 6 章：设计状态机与可信记账

##### 6.1 为什么需要显式状态和双层状态机

- 状态不能藏在聊天记录、文件名或 Agent 的记忆中。
- Backlog 状态机管理任务库存，Meta 状态机管理内容生产进度。
- 定义合法迁移、非法跳转、阻塞原因和终态。
- 用双向指针和一致性检查管理双层状态的必要冗余。

##### 6.2 把状态写入权从 Agent 手里收回来

- Agent 保留判断权，CLI 独占状态写入权。
- 发布完成等跨文件变化必须通过专用事务命令一次收口。
- 使用预校验、锁、临时文件 Rename、原子写和零写入失败语义。
- 使用幂等、审计日志和 Actor 保证重试安全与责任可追踪。

##### 6.3 让系统能够恢复：并发、失败与故障注入

- 模拟两个写入者竞争、陈旧锁、半写入和重复命令。
- 验证非法迁移被拒绝，跨文件更新要么全部成功、要么零写入。
- 根据显式状态和账本恢复，而不是让 Agent 猜测上次做到哪里。
- 记录当前文件存储方案的适用边界和迁移数据库的条件。

**本章产物**：双层状态机、可信写入命令、事务与并发测试、审计账本。  
**出口条件**：系统面对非法状态、并发和重复执行时仍能保持一致并恢复。

#### 第 7 章：构建质量闸、人闸与控制面

##### 7.1 Check、Doctor 与自动化测试

- Check 检查状态、引用和账本是否一致。
- Doctor 检查当前阶段产物是否存在、完整且可解析。
- 将错误分成 Error、Warn 和 Info，并提供对象、原因、证据路径和建议动作。
- 让 Agent 根据行为契约和反例生成测试，再由人审查断言是否真正守住边界。

##### 7.2 Human-in-the-loop 与两次发布确认

- 主观质量、不可逆动作和策略更新必须保留人闸。
- 第一次审核判断“内容是否合格”，第二次确认授权“现在是否真实发布”。
- 区分审核结论、操作授权和最终动作结果。
- 为自动重做设置次数上限，为登录失效、余额不足和合规风险设置升级与停止条件。

##### 7.3 飞书、Web、JobRunner 与最终裁决

- 飞书卡片承担轻量审核和授权，Web 看板承担观察、筛选和控制。
- 重任务通过无头 Agent 和 JobRunner 异步执行，支持排队、锁、取消和超时。
- Dashboard 是由事实生成的派生视图，不能成为新的业务真相源。
- 模型文本用于说明，工具调用用于展示过程，文件状态和运行账本裁决最终成败。

**本章产物**：Check、Doctor、故障测试、人审与二次确认、可观察 JobRunner。  
**出口条件**：即使 Agent 自述成功，只要后置条件不成立，系统仍必须判定失败。

**阶段产物**：统一 CLI、双层状态机、事务与审计、质量闸、人闸和控制面。

---

### 第四阶段：让系统形成闭环

**阶段问题**：系统如何从真实结果中学习，而不是只把同一流程机械重复？

**阶段目标**：建立独立治理线，以可信数据形成归因和变更提议，经人审后影响下一轮。

#### 第 8 章：从 Harness 到 Loop Engineering

##### 8.1 建立独立治理线：注册表与 Dispatcher

- 生产线负责当天交付，治理线负责维护选题池、SOP、对标、事实和反馈资产。
- 每个治理任务在注册表中声明目标选择、触发方式、产物、记账、人审和跳过条件。
- 使用发布后窗口、周期触发和加权池处理不同维护任务。
- Dispatcher 只负责选择和调度，不亲自执行具体治理工作。

##### 8.2 用数据复盘：指标、基线、漏斗与归因

- 区分过程指标、结果指标和护栏指标。
- 区分单次读数、趋势、基线和同类对照。
- 沿“曝光 → 点击 → 留存 → 完播 → 互动 → 转粉”定位最先低于基线的环节。
- 区分事实、相关性、归因、假设和提议，并显式记录混淆变量。

##### 8.3 形成真正的 Loop：提议、人审与策略回写

- 将“发布 → 采集 → 复盘 → 提议 → 人审 → 更新 brain → 影响下一轮”闭合。
- 一般治理任务只产报告和变更提议，不直接修改未来策略。
- 小样本只产心跳或观察结论；受限自调只能修改可逆、限幅的参数。
- 记录提议是否采纳、旧策略为何被替换，以及如何回滚错误反馈。

**本章产物**：治理任务注册表、Dispatcher、复盘报告、待审提议和一次获批策略更新。  
**出口条件**：经批准的策略变化能够真实影响下一次选题或执行方式。

**阶段产物**：生产线之外的治理 Harness，以及一条证据可追溯的完整反馈回路。

---

### 第五阶段：组装与跨域迁移

**阶段问题**：如何证明学到的是一套通用架构方法，而不是只会照抄自媒体仓库？

**阶段目标**：从零组装完整系统，通过故障演练验证边界，并迁移到一个非内容生产流程。

#### 第 9 章：完成你的 Loop Engineering 项目

##### 9.1 从零组装完整 AI 自媒体流水线

- 组装项目规则、领域 Brain、Backlog、工作单元、阶段 SOP 和 Skill。
- 接入 CLI、双层状态机、Check、Doctor、人审、控制面和治理任务。
- 跑通“选题 → 创作 → 审核 → 发布 → 复盘 → 策略更新”。
- 用设计说明、Agent 任务记录、Git Diff 和运行结果提交完整证据链。

##### 9.2 用故障演练证明系统可信

- 注入无可用任务、双层状态不同步、Agent 假成功和并发写入。
- 注入余额不足、登录失效、自动重做超限、Job 状态丢失和小样本调参。
- 对每个故障回答：在哪里发现、能否重试、是否需要人介入、最终相信哪个事实源。
- 验证恢复路径，而不是只验证理想路径能够跑通。

##### 9.3 毕业项目：迁移到另一个真实流程

- 从软件交付、会议知识库、销售跟进、招聘、客服或数据报告中选择一个流程。
- 重新定义工作单元、真相源、状态机、Agent 权限、人审节点和 Harness。
- 说明主 Agent、Sub Agent 或 Agent Team 的选择依据。
- 通过架构决策卡说明当前选择、代价、适用边界和下一阶段演进条件。

**本章产物**：一个非内容生产领域的完整 Loop 项目和毕业答辩材料。  
**出口条件**：学员能够脱离教学仓目录，独立设计、委托、验证并解释一套可信 AI 流水线。

**阶段产物**：完整自媒体 Loop、故障演练报告和跨领域毕业项目。

## 7. 贯穿课程的工程设计专题

课程不能只展示“项目用了什么”，每个设计点都必须按以下顺序讲：

```text
问题 → 可选方案 → 当前选择 → 选择原因 → 代价 → 演进条件
```

### 7.1 为什么使用文件作为真相源

当前选择：Markdown、YAML、JSONL 与 Git。

适合当前项目的原因：

- 单机、低并发、数据量小。
- 人和 Agent 都可以直接读写。
- Git 天然提供 Diff、审计和回滚。
- 调试时可以看到完整事实，不依赖额外服务。

代价：

- 全量扫描。
- 粗粒度锁。
- 多机写入困难。
- 复杂查询和强事务能力有限。

演进条件：当系统出现多机并发、高频写入、复杂查询或细粒度权限时，迁移到数据库；CLI 契约可以保留，底层存储实现替换。

### 7.2 为什么 Markdown 可以成为程序的一部分

AI 时代，文档可以被 Agent 直接执行：

```text
传统软件：文档 → 人理解 → 人翻译成代码
AI 原生软件：文档 → Agent 理解 → Agent 执行
```

但 Markdown 只适合目标、约束、判断标准和阶段契约；状态迁移、并发、事务和格式校验必须沉到确定性程序。

### 7.3 为什么 Agent 不能直接修改状态文件

直接修改虽然简单，但容易：

- 跳过非法状态。
- 只改一个文件，漏掉其他真相源。
- 在并发写入时互相覆盖。
- 丢失审计记录。
- 让不同 Skill 产生不同写法。

决策：**Agent 拥有判断权，CLI 拥有状态写入权。**

### 7.4 为什么需要双层状态机

Backlog 关心任务库存，Meta 关心生产进度。把两者混成一个状态机，会让选题去重、清扫、制作和复盘相互耦合。

代价是存在状态冗余，因此必须补充双向指针和一致性检查。

### 7.5 为什么 Check 和 Doctor 分开

- Check 检查账本与引用是否一致。
- Doctor 检查当前阶段产物是否齐全。

两者混合后，错误无法归类，修复动作不明确，也难以决定是否阻断流程。

### 7.6 为什么 Dashboard 不能成为真相源

Dashboard 是由 Meta、Backlog 和账本计算出来的派生视图。如果它也可以独立编辑状态，系统会出现多个互相冲突的事实源。

因此：事实存文件，Dashboard 自动生成；机器区可覆盖，人写叙事区保持不动。

### 7.7 为什么 Server 不直接写业务文件

Server 只负责鉴权、参数映射、投影和调度，写入继续调用 CLI，从而复用同一套状态机、锁、事务、审计和错误码，避免出现第二套业务规则。

### 7.8 为什么最终结果不相信 Agent 自述

Agent 可能把“准备完成”理解成“整体完成”，也可能遗漏最后一步。因此最终裁决必须回读 `meta.status`、运行账本、产物文件或 Git Diff。

### 7.9 为什么不可逆操作需要独立授权

内容审核通过，只能证明内容可以发布，不能证明现在就应该发布。发布、部署、发消息和付款都应把质量判断与动作授权拆成两个节点。

### 7.10 为什么生产线与治理线分离

生产线追求交付，治理线维护系统资产。二者耦合后，生产模式一变，调研、复盘和维护也会停摆。

## 9. 统一章节教学模板

为了保持课程连贯，27 篇教程都采用相同结构；主章负责把三篇教程的产物组装成一个可验收的工程增量：

1. **事故或问题**：先展示没有这一层会发生什么。
2. **工程原理**：抽象出通用设计判断。
3. **仓库证据**：查看参照实现如何处理。
4. **AI 实现**：学员写任务契约，Agent 完成代码和测试。
5. **证据验收**：检查 Diff、测试、文件状态和未验证边界。
6. **故障注入**：主动制造反例，验证系统是否守住边界。
7. **跨域迁移**：讨论该设计在其他业务中的对应物。
8. **架构决策卡**：记录选择、代价和演进条件。

### 9.1 架构决策卡模板

```markdown
## 本章架构决策

### 要解决的问题
多个 Agent 和入口都可能修改业务状态。

### 可选方案
A. Agent 直接编辑 YAML
B. 每个入口分别实现写入
C. 所有写入统一经过 CLI

### 选择
C：统一经过 CLI。

### 原因
统一状态机、事务、锁、审计和错误协议。

### 代价
增加一层命令协议；每次写入需要启动进程。

### 当前约束
单机、低频写入，进程开销可以接受。

### 演进条件
当系统变成多机并发时，将 CLI 内核迁移成服务，
CLI 退化为 HTTP 客户端，业务契约保持不变。
```

| 维度 | 权重 |

| Loop 的证据、归因和反馈边界 | 15% |
| Human-in-the-loop 和权限边界 | 5% |
| 跨领域迁移能力 | 10% |

最终判断标准：

> 学员能否指挥 AI 建造系统，并用工程证据解释这个系统为什么可信。

---

## 12. 教学仓组织建议

为避免学员直接照抄完整答案，后续可将教学材料组织为：

```text
starter/                 课程起始骨架
checkpoint/m01...m09/    九个主章里程碑的参考状态
reference/               当前完整参照实现
labs/                    故障注入与迁移练习
```

教学顺序应先让学员经历问题、作出设计并委托 Agent 实现，再开放对应参照文件。否则课程容易退化成复杂仓库讲解，无法完成从 Agent 到 Harness 再到 Loop 的能力转换。
