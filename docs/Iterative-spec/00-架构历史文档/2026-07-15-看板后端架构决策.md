# 看板后端（pipeline-console）架构决策记录（ADR）

> 日期：2026-07-15｜状态：已采纳（三个开放点未拍板，见 §4）
> 关联：`docs/2026-07-11-流水线看板-PRD.md`（产品契约）；代码 `tools/console/`（独立 git 仓推 GitHub）

## 1. 总体形态

单进程本地服务，三层 + 一条推送通道：

```
                     ┌──────────────────────────────────────────┐
   真相源(仓库文件)   │           pipeline-console (单进程)        │      浏览器(UI)
 content/*/meta.yaml─┤→ ①解析层 parsers/   ②聚合层 store+alerts  │
 backlog.yaml       ─┤   每源一个parser  →  内存态+警报计算       │
 harness/{tasks,logs}┤   独立容错          (无数据库)            │
 pipeline/logs      ─┤                        │                 │
                     │  chokidar 文件监听 ──→ 重建 ──→ SSE ──────┼──→ 前端自动刷新
                     │              ③接口层 Hono REST ───────────┼──→ fetch /api/*
                     └──────────────────────────────────────────┘
```

分层职责：
- **解析层** `src/parsers/`：一个数据源一个 parser（contents / backlog / harness / logs），互相不知道彼此；解析失败降级返回原文 + parseError，绝不抛穿。
- **聚合层** `src/store.mjs` + `src/alerts.mjs`：内存态，交叉校验产出 5 条警报规则（状态失联/双层不同步/待审积压/治理逾期/日志报错）。
- **接口层** `server.mjs`：Hono REST（overview/contents/content/backlog/harness/metrics/health/file/asset）+ SSE `/api/events`。

## 2. 五个核心决策（决策 / 备选 / 理由）

| # | 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|---|
| 1 | 存储 | **无数据库**，内存态，文件变更全量重建 | SQLite 缓存 / 增量更新 | 数据量小（几十条内容），全量重建 <100ms；加 DB 产生"两份真相"的同步问题，违背 PRD 铁律 1（派生视图） |
| 2 | 实时性 | **chokidar 监听 + SSE 单向推** | WebSocket / 前端轮询 | 只需服务器→浏览器单向"该刷新了"，SSE 最简且 EventSource 自带重连；WS 双向能力用不上 |
| 3 | 框架 | **Hono** | Express / Nest / 裸 node:http | 轻、TS 原生、Web 标准 API；Nest 对此规模过度设计 |
| 4 | 推送粒度 | **只推 refresh 信号**，前端自行重新 fetch | 推数据 diff | 信号+重拉最简，不维护 diff 协议；本地多一次请求无成本。设计等价于"事件可丢、状态可重建"（至少一次 + 幂等的亲戚） |
| 5 | 安全 | **文件读取白名单**（5 目录 + 文本扩展名）防路径穿越 | 本机不设防 | 本机也养权限边界习惯；`/api/file` `/api/asset` 都过 safeResolve |

补充约束（继承 PRD 铁律）：**零写接口**——后端没有任何写状态的 endpoint，状态记账唯一位置仍是 douyin-publish Step 5。

## 3. 工程化决定

- 代码住 `tools/console/`，**独立 git 仓**推 GitHub（与 douyin-media 主仓解耦；主仓含敏感物料不推）。
- 仓库根路径经 `PIPELINE_REPO_ROOT` 环境变量注入，默认取相对路径（在 tools/console 原位运行时零配置）。
- 依赖仅 4 个：hono / @hono/node-server / js-yaml / chokidar。

## 4. 开放问题（讨论中，未拍板）

1. **全量重建 vs 增量**：规模扩十倍后全量扫描是第一瓶颈。当前立场 YAGNI，先全量，慢了再改。
2. **前后端合并部署 vs 分离**：当前设计后端可托管静态 UI（单端口）；备选 UI 走 Vite dev server + CORS。待 UI 接入时定。
3. **SSE 断线丢事件**：当前答案"丢了无所谓，重连后全量重拉"。若未来推 diff 则需序号/补发机制。
