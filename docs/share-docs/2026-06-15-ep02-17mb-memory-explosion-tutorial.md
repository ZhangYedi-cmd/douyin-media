# 一个 17MB 的 JS 文件，让内存从 35MB 暴涨到 1GB

`claude --version` 是 Claude Code 里最轻的一条命令——它不建立会话、不读项目上下文，唯一的工作就是打印一行版本号。按直觉，这种命令的内存占用应该小到可以忽略。但实测数据不是这样：用 Bun 跑这条命令，进程内存峰值一度冲到 966MB，逼近 1GB。同一份构建产物换 Node 跑，峰值只要 220MB 出头。一行版本号，两种跑法，内存差了 4 倍多——这不是哪个开发者手滑写崩了代码，是构建产物和运行时之间的一个隐藏假设没对齐。

如果只看现象就动手排查，很容易走偏：先怀疑是不是哪个依赖装漏了内存，或者代码里是不是有对象没释放。这两个方向都会扑空——因为峰值出现在启动的瞬间，而不是随时间推移慢慢爬升，这个特征本身就在提示排查方向不对。真正的根因出在一层大多数人不会去看的地方：JS 引擎怎么解析你的构建产物。

这篇文章的任务是把这次排查完整走一遍：从「一行版本号吃掉 1GB」这个反直觉现象出发，排除掉内存泄漏这个最容易想到但错误的假设，定位到 Bun 和 Node 两个引擎在解析策略上的根本差异，再落到一个可以直接抄的修复动作——用代码分割把大文件切小。做完这篇文章，你应该能看懂：为什么同一份 JS 产物在不同引擎下内存表现能差出一个量级，以及打包体积超过几 MB 时，什么时候需要主动做代码分割。文末有一张验证清单，把这次排查用到的每个检查点串起来。

## 一、为什么会内存暴涨

### 1.1 现象：一行版本号，吃掉了将近 1GB

先把现象钉死。触发条件很简单：敲一行 `claude --version`，只是想看一个版本号。正常预期是这条命令几乎零开销——它不需要加载项目、不需要建立网络连接、甚至不需要解析用户的任何输入。但实测内存峰值（RSS）到了 966MB，差不多顶格 1GB。

对照组更能说明问题不在业务逻辑：同一份构建产物，换成 Node 来跑，内存峰值只要 220MB 出头。构建产物完全一致，只是换了个运行时，峰值就相差了 4 倍多。这个对照直接排除了「代码本身写得有问题」这个可能——如果是代码逻辑的锅，两个引擎应该表现一致地差，而不是只有一个引擎爆表。

### 1.2 根本问题：不是泄漏，是引擎一次性吃太多

内存暴涨的第一反应通常是内存泄漏，或者是依赖装得太多、体积太大拖累了运行时。这两个方向都要先排除掉，排除的依据是这次异常的**时间特征**：

- **内存泄漏**的特征是随时间持续增长——请求越多、跑得越久，内存曲线越往上爬。
- 这次观测到的是**启动瞬间的一次性峰值**——命令一执行，内存立刻顶到 966MB，不是慢慢爬上去的。

一次性的启动尖峰，不是「越用越涨」，而是「一启动就顶格」。这意味着问题不是某处忘记释放引用，而是某个操作在启动时一次性做了远超实际需要的工作。

顺着这条线去看构建产物：Claude Code 打包出来的 CLI，是**一个 17MB 的单文件 JS**。17MB 对于一条只打印版本号的命令来说不算小——这就是那个「一次性做了远超实际需要的工作」的候选对象：会不会是引擎在启动时，把这整整 17MB 都处理了一遍？

### 1.3 从现象到根因的排查思路

把上面这条排查链路串起来，整体思路是这样的：

```mermaid
flowchart TD
    A["现象：claude --version<br/>内存峰值 966MB"] --> B{"是内存泄漏吗？"}
    B -->|"否——瞬间顶格,不是持续增长"| C{"是依赖装太多吗？"}
    C -->|"否——Node 跑同一份产物只要 220MB"| D["定位：问题在运行时引擎<br/>不在业务代码"]
    D --> E["证物：打包产物是<br/>一个 17MB 单文件 JS"]
    E --> F["假设：引擎在启动时<br/>一次性解析了整个 17MB"]
```

这张图上最关键的一步是从 C 到 D 的转折——排除泄漏和依赖膨胀之后，唯一还没排除的变量就是「跑它的那个引擎」。Node 和 Bun 跑同一份产物结果差 4 倍，这个对照实验本身就是把嫌疑锁定在引擎层的直接证据，不需要再去猜测其他可能性。下一步要做的，就是打开这两个引擎内部，看它们各自怎么处理这 17MB。

## 二、真凶：两个引擎的解析策略不一样

带着「引擎在启动时一次性解析了整个文件」这个假设，去看 Claude Code 用的运行时和对照组用的运行时分别是什么：Claude Code 默认用 **Bun**，底层引擎是 **JavaScriptCore（JSC）**；对照组用的是 **Node**，底层引擎是 **V8**。同一份 17MB 的产物，在这两个引擎里走的是完全不同的解析路径。

**JSC 的策略是全量解析**：拿到文件之后，把整个 17MB 一次性解析成字节码，还会顺手做一轮 JIT 编译——不管这次调用实际会不会用到文件里的每一行代码，JSC 都会先把全部内容嚼一遍。

**V8 的策略是懒解析（lazy parsing）**：只解析当前这次调用实际会用到的那部分代码，没被触碰到的函数体先跳过、放着，等真正被调用时才补上完整解析。

用一个更直觉的类比：这就像自助餐。JSC 是那种一上来把整桌菜全部吃光的人——不管接下来饿不饿，先把面前的都吃掉，直接撑爆；V8 则是饿了才去夹一盘，吃多少拿多少。`claude --version` 这条命令实际只需要用到 17MB 里很小的一部分代码，但 JSC 不管这些，照样把整个 17MB 全部解析一遍——这就是 966MB 内存峰值的直接来源。

两个引擎的解析策略对照如下：

| 维度 | Bun（JavaScriptCore） | Node（V8） |
| --- | --- | --- |
| 解析策略 | 全量解析——启动时解析整个文件 | 懒解析——只解析当次调用会用到的部分 |
| 是否顺带 JIT | 是，解析后立刻做一轮 JIT 编译 | 按需，未触发的函数不编译 |
| 面对 17MB 单文件的行为 | 一次性吃满整个文件 | 只碰实际用到的那一小块 |
| `--version` 实测内存峰值 | 966MB | 220MB 出头 |

需要说明一点边界：全量解析不是 JSC 的设计缺陷，它在很多场景下（比如反复调用同一批函数）反而因为提前 JIT 而更快。问题出在这里的具体使用场景——一个 17MB 的单文件产物，塞进了一个默认全量解析的引擎，而 CLI 的大多数调用（像 `--version`）实际只碰到文件里极小的一部分代码。真凶不是某个引擎「更差」，是**产物的组织方式（单个大文件）和引擎的解析策略（全量解析）撞在了一起**。

## 三、怎么做：用代码分割把大文件切成能按需加载的小块

### 为什么

既然真凶是「17MB 单文件 + 全量解析」这个组合，摆在面前的选项其实只有两个：换掉引擎，或者改变文件的组织方式。换引擎意味着放弃 Bun 本身带来的启动速度优势，代价太大；真正划算的做法是保留 JSC 全量解析的行为不变，但把「要解析的那一份」变小——把 17MB 的大块拆成很多个小文件，让 JSC 只需要解析当次调用实际引用到的那几个小文件，而不是囫囵吞下整个产物。

### 怎么做

这个改动落在构建配置上，核心是打开代码分割（code splitting）。以 Bun 的构建 API 为例，思路是这样的（真实实现见仓库 `build.ts:23`，下面是按同一原理写的示意代码）：

```typescript
// 示意：构建时打开代码分割，让产物按调用路径拆成多个 chunk
// 参考 Bun.build 文档：https://bun.sh/docs/bundler
await Bun.build({
  entrypoints: ["./src/cli.ts"],
  outdir: "./dist",
  splitting: true,   // 关键开关：把单文件产物拆成按需加载的 chunk
  target: "bun",
});
```

`splitting: true` 这一个开关，会让打包器按代码的实际引用关系，把原本一整块的 17MB 拆成**600 多个小 chunk**。拆完之后，运行 `claude --version` 时，JSC 只需要解析 `--version` 这条命令路径实际引用到的那几个 chunk，其余五百多个跟这次调用无关的 chunk 完全不会被碰，更不会被解析。

### 产物长什么样

拆分前后的解析路径对比如下：

```mermaid
flowchart TD
    subgraph BEFORE["拆分前"]
        F1["17MB 单文件产物"] --> P1["JSC 全量解析<br/>+ JIT 整个文件"]
        P1 --> M1["--version 峰值：966MB"]
    end
    subgraph AFTER["拆分后（splitting: true）"]
        F2["17MB 拆成 600+ 个 chunk"] --> P2["JSC 只解析<br/>--version 引用到的少数几个 chunk"]
        P2 --> M2["--version 峰值：35MB"]
    end
```

这张图的关键约束在 AFTER 分支里的第二步——JSC 依然是「全量解析」这个策略本身没变，变的是**要解析的对象从一整块 17MB 缩小成了几个小 chunk**。这也是为什么这个修复不需要换引擎：只要喂给 JSC 的东西足够小，全量解析反而不是问题。

拆分前后的实测数字：

| 场景 | 拆分前 | 拆分后 | 变化 |
| --- | --- | --- | --- |
| `claude --version` 内存峰值 | 966MB | 35MB | 约 27 倍（966÷35≈27.6） |
| 完整加载内存峰值 | 1GB 出头 | 约 500MB | 明显下降 |
| 同产物 Node 跑 `--version` | 220MB 出头 | —（对照组，未拆分前的参考值） | — |

拆分后 `--version` 的峰值从 966MB 降到 35MB，比 Node 跑未拆分产物的 220MB 还要低得多——这也验证了前面的判断：真正的开销来自「解析了多少代码」，而不是引擎本身孰优孰劣，Bun 在拆分之后完全可以比 Node 更省内存。

### 人工审查点

这里有两个坑需要提前说明。第一，代码分割依赖打包器能正确识别调用路径之间的引用关系——如果代码里有动态 `import()` 或者反射式的引用方式，打包器可能识别不到，导致该拆的地方没拆开，或者拆出来的 chunk 在运行时找不到。拆分之后，务必挑几条不同的命令路径（不只是 `--version`，还要包括核心功能命令）分别跑一遍，确认每条路径都能正常加载到它需要的 chunk。第二，chunk 数量从 1 个变成 600 多个，如果构建流程里有对产物文件数量或体积做校验的步骤，这里需要同步调整预期。

### 验证

代码分割生效后，可以用系统自带的时间/资源统计命令直接测内存峰值：

```bash
# macOS：/usr/bin/time -l 会打印 maximum resident set size（单位：字节）
/usr/bin/time -l bun run dist/cli.js --version 2>&1 | grep "maximum resident"
# 预期：拆分前该数值接近 966MB（约 1,013,000,000 字节量级）
# 拆分后应降到 35MB 量级（约 36,700,000 字节量级）
```

看到拆分后的数值降到 35MB 量级，说明代码分割生效，这一步就算通过。

## 四、怎么做：让同一份产物在 Bun 和 Node 之间通用

### 为什么

代码分割解决了内存问题，但切完之后还有一个新坑：Bun 提供了一个专属 API `import.meta.require`，用来在 ESM 模块里做类似 CommonJS `require` 的同步引入。这个写法在 Bun 里能跑，但 Node 不认——产物如果原样保留这个写法，就意味着只有装了 Bun 的用户才能运行 Claude Code CLI，安装了 Node 但没装 Bun 的用户跑起来会直接报错。这与「给尽可能多的用户提供开箱即用的 CLI」这个目标是冲突的，所以拆分完成之后还需要做一道兼容处理。

### 怎么做

处理方式是在构建流程结尾加一道后处理（post-build）步骤：扫描产物文件，把 Bun 专属的 `import.meta.require` 写法自动替换成 Node 也能识别的兼容写法（真实实现见仓库 `build.ts:45–56`）；与此同时，产物里对 `globalThis.Bun` 的解构引用也需要做同一类型的兼容 patch（见 `scripts/post-build.ts:17`），避免代码在 Node 环境下因为访问不存在的 `Bun` 全局对象而直接崩溃。

这类后处理脚本的通用形状大致是「扫描产物文件 → 用正则或 AST 匹配目标写法 → 替换成兼容写法 → 回写文件」，具体替换规则要跟着 Bun 专属 API 的实际用法走，不建议脱离真实产物去套一份通用模板——这也是它被安排在构建脚本里紧跟代码分割之后执行、而不是写成一份独立文档的原因：它必须扫描的是分割后的最终产物，不能提前做。

### 产物长什么样

经过这道处理后，产物在 Bun 和 Node 环境下的行为收敛成一致：

```
产物文件（.js chunk）
  - 原来：包含 import.meta.require(...)  ← 只有 Bun 能跑
  - 处理后：替换为 Node 兼容的引入写法    ← Bun / Node 都能跑
```

### 验证

分别在两个运行时环境下执行同一份产物，确认都能正常输出版本号：

```bash
# 分别用 Bun 和 Node 跑同一份产物，确认两边都能正常执行
bun run dist/cli.js --version    # 预期：正常打印版本号
node dist/cli.js --version       # 预期：同样正常打印版本号,不报 Bun 相关的引用错误
```

两条命令都拿到正常输出、且都没有报出跟 `import.meta.require` 或 `globalThis.Bun` 相关的引用错误，这一步才算通过。

## 五、验证清单与小结

把这次排查从头到尾涉及的检查点收拢成一张表：

| 检查项 | 验证方式 | 预期结果 |
| --- | --- | --- |
| 是否为内存泄漏 | 观察内存曲线是否随时间持续增长 | 否——是启动瞬间的一次性尖峰，不是持续增长 |
| 引擎解析策略差异 | 同一产物分别用 Bun / Node 跑 `--version` | Bun（JSC）966MB vs Node（V8）220MB 出头 |
| 代码分割是否生效 | `/usr/bin/time -l` 测 `--version` 内存峰值 | 由 966MB 降到 35MB 量级（约 27 倍） |
| 完整加载内存峰值 | 同样方式测完整加载路径 | 由 1GB 出头降到约 500MB |
| Bun/Node 兼容性 | 分别用 `bun run` 和 `node` 执行同一产物 | 两边都能正常输出，无引用错误 |

回顾这次排查的几个决策点：第一，遇到内存异常先看时间特征——是持续增长还是瞬间尖峰，这个特征决定了排查方向是查泄漏还是查一次性开销，走错方向会白白浪费排查时间。第二，怀疑引擎层问题时，最快的验证方式是换一个引擎跑同一份产物做对照——如果两个引擎表现一致地差，问题就在代码；如果只有一个引擎异常，问题大概率在引擎和产物的组合方式上。第三，代码分割不是只对 Web 前端产物有意义，对 CLI 这类「单次调用只用到全部代码一小部分」的场景，同样是能直接压缩内存峰值的手段。

内存问题解决了，但故事没完。JS 文件切小之后能省内存，同样的「按需加载、别一次性吃太多」这个思路，放到另一个地方还有更大的收益——每次调用大模型时喂进去的上下文。下一篇讲的就是这件事：Claude Code 每个月花掉的 token 费用里，有一半其实花在了它「记性太好」上，而这背后的根因和这次内存暴涨，是同一类问题的不同表现形式。
