# 第 07 课材料盘点：自愈机制与 3 轮熔断

## 1. 核心问题与痛点
- 痛点 1：长流程自动化缺乏反馈回路，遇到单点错误直接报错退出，重新执行耗时且丢失上下文。
- 痛点 2：无约束的自愈循环容易陷入死循环，大模型在同一种报错上反复尝试相同错误改法，消耗大量 Token 且无法收敛。
- 痛点 3：缺乏物理度量手段，大模型基于文本幻觉误判音画质量，导致成片出现死气、多音字错误或字幕丢失。

## 2. 核心架构与数据流
- 状态机四级流转：生成音频（tts-dub）-> 质检判决（dubbing-reviewer）-> 路由修复（主流程修补）-> 重抽与复验。
- 三大出口路径：
  - 出口 A：首轮通过（R1 PASS），直接流转至录屏阶段。
  - 出口 B：第 2 轮或第 3 轮修复后通过（R2/R3 PASS），记录自愈日志后放行。
  - 出口 C：满 3 轮仍未通过（R3 FAIL），触发硬熔断，状态置为 drafting_blocked，生成工单上报飞书。
- 录屏后独立抽帧小循环（检查点 4.1）：防 headless 渲染时间膨胀，校验画面与音频时间戳对齐，验证 ?subs=1 字幕烧录。

## 3. 三大自愈修补套路与工程教训
- 套路 1（音频死气）：silencedetect 抓取超过 0.45 秒静音，调用 depause.mjs 裁切，必须写临时文件避免原地截断静默失败（L16 教训），复扫确认静音数清零。
- 套路 2（多音字漏注）：解析 reviewer 建议的拼音，注入 build/tts.config.json 的 overrides 字典，删旧 mp3 重合成，注意增删段落时重排编号（L18 教训）。
- 套路 3（同段两读冲突）：同一句中同一个字存在不同读音（如 děi 与 de），配置级注音失效，必须重构文案，同步修改 2-script.md、narrations.ts 与前端组件（L17 教训）。

## 4. 三轮熔断机制的数学与工程依据
- 为什么是 3 轮：第 1 轮解决简单确定性格式与漏配置问题（修复率约 75%）；第 2 轮解决残余复合问题（修复率约 20%）；第 3 轮未解决通常意味着规则冲突或模型认知死锁（继续尝试成功率低于 5%），必须硬熔断止损。
- 熔断降级动作：保留现场 YAML 诊断与 diff，状态机挂起，通过飞书卡片推给人工接管。

## 5. 提示词交付物
- 提示词 1：自愈闭环启动提示词（将客观测试失败日志打包为修复任务信封喂给修补 Agent）。
- 提示词 2：多轮修复迭代提示词（携带前一轮修复记录与残余报错，避免重复踩坑）。
- 提示词 3：触发 3 轮熔断后的兜底提示词（自动挂起任务、标记状态、生成人工接管工单）。
