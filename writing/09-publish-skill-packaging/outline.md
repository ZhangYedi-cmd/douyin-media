# 课程大纲：包装 social-auto-upload 发布 Skill

## 整体设计
- 篇幅目标：6500 到 7500 字。
- 风格规范：工程教程体，无加粗，无花哨标点，无好评口头禅，无黑话，纯事实与代码驱动。
- 核心交付：完整的 Skill 设计方案、物料契约、3 组核心发布引导提示词（Dry-run 检查提示词、授权执行提示词、异常排错提示词）、环境与 Cookie 排坑指南。

## 详细目录

### 1. 技术选型：为什么不要自己手写平台上传脚本
- 1.1 短视频平台上传链路的复杂性与脆弱性
  - 手写 Playwright/Selenium 脚本的现实崩溃点：DOM 动态类名与 A/B 测试、切片上传协议握手、封面裁剪与活动弹窗遮挡、滑动风控验证码。
  - 维护成本测算：单平台脚本月均维护耗时与多平台扩展代价。
- 1.2 开源项目 social-auto-upload 核心架构与薄封装原则
  - sau 架构解析：uv + Python 3.12 虚拟环境隔离、多平台（抖音/小红书/B站/视频号）适配、内置 Cookie 持久化。
  - 薄封装设计哲学：不侵入开源库核心代码，只封装外层 CLI 契约映射与物料流转。

### 2. 物料准备与契约映射：4-publish.md 规范
- 2.1 出审前必产的发布物料清单
  - 4-publish.md 键值结构定义：标题、正文简介、话题标签、封面路径、媒体文件。
  - 静态物料隔离原则：严禁在发布阶段由大模型临时即兴生成文案。
- 2.2 物料解析器设计与发布时段避坑
  - 正则严格提取字段：防解析错位与标签格式转换（去除 # 号逗号分隔）。
  - 定时发布参数避坑：禁止自然语言时间，强制标准 YYYY-MM-DD HH:MM 格式，校验平台时间窗口（2小时至14天）。

### 3. 打造专属发布 Skill：douyin-publish 与 Dry-run 机制
- 3.1 双模式设计：--dry-run vs --publish
  - 模式一：--dry-run 模式只解析物料、拼装底层命令并输出摘要，不执行任何实际上传。
  - 模式二：--publish 模式表示获得人类明确授权，直接调用底层的 sau 命令，不再发起二次确认。
- 3.2 为什么 Dry-run 是发布环节的绝对铁律
  - 防大模型参数组装幻觉：标题截断、路径错漏与参数污染。
  - 发布不可逆的心理保障：让操作者在物理执行前看到完整的真实执行命令行。
- 3.3 核心提示词实战：三步引导 AI 完成发布调度
  - 提示词一：发布前 Dry-run 检查提示词（校验物料存在性、生成 CLI 命令与核对清单）。
  - 提示词二：人类授权执行提示词（识别授权标志、驱动子进程执行、解析成功标识）。
  - 提示词三：异常重试与挂起排错提示词（网络超时、Cookie 假死、页面改版拦截、严禁重复提交）。

### 4. 账号登录态管理与异常排查
- 4.1 Cookie 持久化存储与自动探针校验
  - sau 的 Cookie 文件结构与管理路径。
  - 探针误报陷阱：check 弱探针报 valid 但实际上传因 sessionid 失效被拦截的问题。
  - 强制重新拉起扫码登录与验证 sessionid 过期时间的方法。
- 4.2 常见发布异常排查与环境防污染
  - NODE_OPTIONS 环境变量污染排查与 env -u 清理命令。
  - 发布成功后的原子状态记账：media publish-done 同步翻转三处状态。

### 5. 验收标准与课后练习
- 验证清单：环境可用性检查、Dry-run 命令输出核对、真实发布与状态流转闭环。
- 实战作业：搭建本地 sau 发布环境并完成一次带 Dry-run 的完整发布调度。
