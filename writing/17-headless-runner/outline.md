# 第 17 课详细大纲与章节规划

## 课程标题
第 17 课：无头CC作业与进程流归一：如何用后台无头Agent实现无人值守全自动运转？

## 引言与全景脉络
1. 痛点切入：在自动化流水线中，创作、重做、配音与录屏等 AI 作业动辄耗时数分钟。如果在 HTTP 请求中直接同步等待，会导致网关 504 超时、浏览器崩溃与界面锁死。
2. 核心方案：建立快写与慢跑严格分流的异步 Job 架构。前端请求立即返回 202 Accepted 与任务唯一 ID，后台派生无头 Claude Code 子进程异步执行，并通过零依赖叶子包 cc-stream 将杂乱的终端流解析为结构化事件，通过 SSE 实时推送到前端。
3. 全景 Mermaid 架构图：前端、HTTP 路由、JobRunner、子进程与 cc-stream 的协作链路。

## 1. 长耗时 AI 作业的交互困境与架构解法
### 1.1 为什么在 AI 作业场景下同步请求必定崩溃？
- 耗时分布实测：调用大模型起草文案约 20 秒，TTS 批量合成音频约 40 秒，无头浏览器录屏约 90 秒，整体耗时在 2 到 5 分钟。
- 同步 HTTP 的三大死穴：网关 504 Gateway Timeout、浏览器刷新连接中断导致孤儿任务、前端单线程渲染完全被阻塞。
- 卡点拦截：如果出现 `504 Gateway Timeout: The gateway did not receive a timely response from the upstream server`，说明将慢作业直接挂在了普通同步 HTTP 接口上。
- 架构原则：快写毫秒级返回，慢跑秒级给 ID 进后台。

### 1.2 标准异步 Job 架构模型
- 交互时序：前端 POST 请求 -> 后端秒级生成 jobId 并返回 202 Accepted -> 启动后台子进程 -> 前端通过 SSE 监听进度。
- 状态机定义：queued（排队）、running（执行中）、verifying（文件核验）、succeeded（成功）、failed（失败）、cancelled（取消）。
- 内存任务表与磁盘降级：运行时在内存中维护 Map，服务重启时通过读取磁盘日志文件实现历史回放。

## 2. 后台执行器设计：JobRunner 与无头 Claude
### 2.1 spawn claude -p 无头模式原理解析
- 核心参数拼装：-p 传入提示词、--output-format stream-json 输出结构化流、--verbose 打印详情、--allowedTools 限制工具白名单。
- 环境变量净化：剔除 ANTHROPIC_API_KEY，避免 OAuth 登录凭据与 API Key 发生冲突。
- 标准输入输出隔离：使用 ignore 关闭 stdin，通过 pipe 接管 stdout 与 stderr。
- 卡点拦截：如果子进程退出码为 1 且 stderr 报错 `Error: API key not found`，说明父进程的环境变量注入了未配置的密钥或者缺少了登录凭证。

### 2.2 单任务串行排队锁与并发防御
- 保护机制：同一时刻只允许一个长耗时作业运行，避免本地 CPU、显存与模型配额被挤爆。
- 互斥锁实现：基于条目标识（slug）的细粒度锁，防止同一个视频被重复触发重做。
- 队列调度与取消机制：支持单个任务取消与排队任务一键清空。
- 优雅退出策略：先发送 SIGTERM 信号，设置 10 秒宽限期，若子进程仍未退出则补发 SIGKILL。

### 2.3 作业日志落盘与历史回放
- 落盘路径设计：logs/jobs/<jobId>.jsonl。
- 写入流管理：使用常驻 WriteStream 顺序写入，防止异步追加导致乱序。
- 历史回放机制：页面刷新或重新打开历史任务时，直接从磁盘读取 jsonl 文件重构时间线。

## 3. 进程输出归一化：打造零依赖叶子包 cc-stream
### 3.1 为什么严禁将原始终端字符串直接透传给前端？
- 终端脏字符问题：ANSI 颜色转义字符、光标移动码、重复渲染的增量消息。
- 业务解耦要求：底层解析包不认识任何业务词（如视频、发布、飞书），只专注流式协议。
- 信任分级原则：模型输出的文本（say）仅供展示，工具调用（tool）驱动步骤，文件状态才是最终裁决。

### 3.2 cc-stream 内部三层处理管道
- 第一层 parseStream：拆解子进程 stdout，按行切分并清洗脏字符。
- 第二层 createNormalizer：将原始事件收敛为 7 类标准事件（started、tool、toolDone、say、thinking、stalling、done），包含工具调用去重与结果截断（preview 保留前 20 行）。
- 第三层 createMilestoneEngine：声明式规则表匹配，根据工具名称与参数正则推导里程碑与 0 到 100% 进度。
- 卡点拦截：如果在前端看到进度条跳变或者步骤重复出现，通常是因为没有对 tool_use_id 进行跨事件去重。

### 3.3 终局裁决与模型自述解耦
- 严禁信任模型自报的执行结果（例如模型宣称已经完成发布）。
- 裁决器实现：通过复读 meta.yaml 里的 status 字段或者检查 git diff 作为唯一成功标准。

## 4. 提示词引导全流程与异常自愈实战
### 4.1 第一步：编写提示词驱动无头 Claude Code 自主执行
- 提示词三要素：授权来源声明、SOP 规则文件路径、收尾记账与状态翻转命令。
- 实战提示词模板：开始创作提示词、重做打回提示词、治理任务执行提示词。
- 约束纪律：严禁中途私自翻转终局状态，遇到人工对齐节点必须停下并记录待办。

### 4.2 第二步：编写提示词引导无头 Agent 执行结构化输出与流式归一
- 动作规范引导：通过明确工具调用顺序（Read -> Write -> Skill -> Bash）驱动后台产生清晰的事件流。
- 日志规整与进度映射：如何让提示词与里程碑规则表精确咬合。

### 4.3 第三步：任务卡死、进程异常与自愈熔断机制
- 重做 3 轮物理熔断：打回次数达到 3 次时，调度器直接拒绝提交，防止模型陷入死循环消耗 Token。
- 进程超时熔断：设置 5 到 15 分钟硬超时，自动触发进程清理。
- 异常上报与飞书联动：当遇到不可恢复错误或任务挂起时，主动调用 feishu-notify 推送告警卡片。
- 卡点拦截：如果无头 Agent 遇到权限确认或交互式询问会无限期挂起，必须在提示词中显式声明已在界面确认，并配置 allowedTools 免去二次确认。
