## 1. 为什么你需要一个声明式治理调度框架？
核心判断: 传统定时工具无法处理基于内容生命周期的动态事件窗口，调度系统必须将时钟评估与业务执行彻底解耦。
支撑材料: Linux Cron 表达式的无状态局限，自媒体长链路治理（24h/72h/7d 复盘、2d 选题补水、30d 对标复核）对状态感知的强需求。
交付物: 传统 Cron 与 harness-dispatcher 架构对比表、系统交互架构 Mermaid 图。
二级标题:
- 1.1 传统定时任务的无状态困境
- 1.2 harness-dispatcher 的解耦设计原则
收尾交接: 明确了框架层与执行层的解耦原则后，下一节进入核心调度协议的载体，即声明式任务注册表。

## 2. 声明式任务注册表：tasks.md 设计
核心判断: 调度框架的稳定性来自于机器可读的声明式契约与人类可读的任务卡规范，新增任务只需修改配置而无须改动调度代码。
支撑材料: 真实项目 `harness/tasks.md` 中的 YAML 字段定义，事件触发器 `post-publish-window`、周期触发器 `periodic:<N>d` 与加权池触发器 `weighted-pool`。
交付物: tasks.md 完整配置定义规范、核心触发器决策流程图、任务卡五要素模板。
二级标题:
- 2.1 任务定义规范：YAML 契约
- 2.2 核心触发器机制深度剖析：事件窗口与固定周期
- 2.3 任务卡模式：把执行边界与人审关注点落在文档
收尾交接: 掌握了注册表的定义与触发器评估方式后，下一节探讨调度器赖以判断时间差和历史记录的底层存储。

## 3. 运行账本设计：logs/index.jsonl
核心判断: 调度器不维护任何易失的内存状态，唯一的真相源是追加写入的日志账本，由此实现严格幂等与零锁竞争。
支撑材料: 真实项目 `harness/logs/index.jsonl` 的实测数据，JSONL 格式在单行追加写入、异常恢复与流式统计上的工程优势。
交付物: 账本字段 Schema 规范、状态变更与应用追踪对比表、幂等判定逻辑代码。
二级标题:
- 3.1 为什么选择追加写入的 JSONL 格式？
- 3.2 账本字段规范与生命周期记账
- 3.3 基于账本的历史时间窗口计算与幂等防重跑机制
收尾交接: 确立了注册表与运行账本两大数据结构后，下一节讲解如何通过结构化提示词驱动调度器完成端到端自动化。

## 4. 提示词工程落地：用三步引导实现无人值守调度
核心判断: 调度器 Agent 的可靠性来自严谨的输入契约与分阶段状态隔离，通过三步递进提示词消除幻觉与执行漂移。
支撑材料: `.claude/skills/harness-dispatcher/SKILL.md` 的真实生产提示词设计。

- 4.3 步骤三提示词：驱动调度器原子追加运行账本并生成汇报
二级标题:

## 5. 元层治理：account-audit 自审任务与调参限幅
核心判断: 没有自审的调度系统会在初始参数偏差中持续空转，元层治理通过统计账本数据对调度参数实施限幅微调与人工预警。
支撑材料: 真实项目 `harness/tasks.md` 中的 `account-audit` 任务卡、自调边界表与熄火保护线。
交付物: account-audit 执行流程图、参数自调边界与步长约束表、自审报告模板。
二级标题:
